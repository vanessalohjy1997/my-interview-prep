Frontend interview prep

Performance is attribution, not vibes.

Measure a baseline, change one thing, verify no regression. This guide covers the pipeline that turns HTML into pixels, what blocks it, and the Web Vitals you'll be asked to diagnose.

00 — The mindset

Frame everything as attribution

The senior signal on performance is method, not tricks: measure a baseline, change one thing, verify no regression.

How it works. Establish a baseline with a real tool (Profiler, Performance panel, Lighthouse, RUM). Change one variable. Verify the improvement without a regression. “I measured X, changed Y, confirmed Z” beats “I added useMemo everywhere.”

Why it matters. This isn't process hygiene. It's that intuition about performance is unusually bad, for three specific reasons:

  • The bottleneck is rarely where the code looks slow. A nested loop over 200 items runs in microseconds. The 900ms you're chasing is almost always a network round trip, a blocking script, a synchronous layout, or a component tree re-rendering 40×. None of those look expensive when you read the source.
  • You are not the user. You develop on a fast laptop, on a fast connection, with a warm cache, in a dev build. Each of those makes you 2–10× faster than the median visitor. Optimising against your own experience optimises the one profile that was never in trouble.
  • Every optimisation has a cost. Memoisation costs a comparison and a reference held in memory. Code splitting costs a network waterfall. Virtualization costs Ctrl+F and accessibility. If you can't show the win, you've paid the cost for nothing. And you've made the code harder for the next person.

The four beats of a strong performance answer

Whatever the question, the same four-beat skeleton works, and interviewers are listening for it.

Why it matters. Only the third beat is about a technique. The other three are what separate a senior answer from a list of tips.

  1. Symptom — what the user actually experiences, in their words. “The dashboard takes four seconds before anything appears.”
  2. Measurement — the tool you'd reach for and the number you'd expect it to give you. “Performance panel on a 4× CPU throttle, plus the LCP breakdown from RUM.”
  3. Hypothesis and fix — one change, tied to the number. “LCP was 80% resource load delay, so the image wasn't being discovered early — preload it and drop the lazy attribute.”
  4. Verification — re-measure, and check what you might have broken. “LCP 4.1s → 2.2s at p75, bundle unchanged, no CLS regression.”
Worked example — the shape in one breath“Support said the orders page felt slow on mobile. Field data put LCP at 4.6s at p75 while our lab runs were 1.9s — that gap alone told me it was device and network, not code. The LCP breakdown showed most of the time in resource load delay: the hero image was inside a lazily-hydrated component, so it wasn't in the HTML for the preload scanner to find. I moved it into the server-rendered markup with fetchpriority="high". p75 LCP went to 2.3s over the next week, and I checked CLS hadn't moved because the image now lands earlier.”

When measuring first is the wrong answer

Measure before you spend a week on something clever, not before you spend a minute on something obvious.

How it works. Don't over-rotate. If someone shows you a 4MB unoptimised PNG hero, a node_modules import of all of lodash, or a list rendering 10,000 rows into the DOM, the correct response is to fix it. Profiling to confirm that 4MB is slow is theatre. The rule is really about ordering effort.

The trap. Measurement itself has failure modes. A React development build is roughly 2–5× slower than production and double-invokes components under StrictMode. Profiling it exaggerates render cost, and can send you memoising something that's free in prod.

Two more. Extensions inflate main-thread time. A single Lighthouse run has enough variance that a 5-point score move usually means nothing. Measure the thing you ship, more than once.

Say this“I don't optimise by guessing. I profile to find where the time actually goes, fix that, and re-measure — otherwise I'm adding complexity for an unproven win.”
01 — Where the numbers come from

Lab data, field data, and why p75

“Measure it” is only half an answer. The follow-up is measure it where.

How it works. There are two families of data, and they answer different questions. Confusing them is the most common way a performance discussion goes wrong.

ToolKindWhat it's good atWhat it can't tell you
Lighthouse / PageSpeedLab (synthetic)Reproducible before/after on one page; an opinionated audit listWhether real users are affected. It's one load, one device, simulated network
Performance panelLab (trace)Attribution — which task, which function, which frame. The only tool that shows you whyAnything about scale or frequency across your user base

Two things about CrUX that interviewers like to probe: it is opt-in Chrome only, and it is a 28-day rolling window.

  • Opt-in Chrome only. Users who sync history and report usage statistics, on desktop Chrome and Android Chrome.
  • Chrome on iOS (a WebKit shell), Android WebView and Edge are not in it. So an iPhone-heavy audience is invisible to Google's grade, and only your own RUM sees it.
  • Origin- or URL-level and 28-day rolling. The API updates daily around 04:00 UTC, roughly two days behind. But each data point aggregates the previous 28 days, so a fix shipped today is fully reflected a month later.

The quick check. Since Chrome 129 the DevTools Performance panel shows your local LCP/CLS/INP live next to the CrUX field numbers for the same URL. That's the quickest way to see the lab/field gap before you record anything.

How it works. The practical workflow uses both, in one direction: field data tells you what to fix and lab data tells you how. RUM says “checkout LCP is 4.5s at p75 on Android”. You reproduce that in the Performance panel with throttling until you can see the offending task. You fix it and confirm in lab. But you only believe it when the field number moves a week later.

Why p75 and not an average

Averages hide the users you're losing. p75 is the slowest experience that 3 in 4 users beat.

Example. If 80% of your visitors load in 1s and 20% load in 9s, the mean is a healthy-looking 2.6s. Meanwhile a fifth of your traffic is having an awful time.

Why the mean lies. Performance distributions are heavily right-skewed. There's a floor on how fast a load can be, and no ceiling on how slow. So the mean drifts toward a tail that no individual user experiences.

Why p75. The 75th percentile is the compromise Google settled on. It's the slowest experience that 3 in 4 users beat, so a passing p75 means the large majority are fine. But it's not so extreme that a handful of users on a train tunnel connection define your score. A page passes Core Web Vitals only when p75 is in the “good” band for all three metrics.

The number that makes this concreteMedian mobile hardware is roughly 4–8× slower on CPU than a developer laptop. That's why Lighthouse's mobile preset applies a 4× CPU slowdown and a simulated Slow 4G link (~1.6 Mbps down, 150ms RTT). If you only ever test unthrottled on desktop, you are testing a device profile that may be 5% of your traffic. Throttle, or better, keep a genuinely cheap Android phone on your desk.

Two traps worth naming out loud

The Lighthouse score is not a metric, and lab and field disagreeing is information, not an error.

The score. It's a weighted composite mapped onto a log-normal curve: TBT 30%, LCP 25%, CLS 25%, FCP 10%, Speed Index 10%. Those weights are unchanged from Lighthouse 10 through 13.5 (September 2026). INP is not in the score at all, because a lab run has no real interactions. TBT stands in for it (good under 200ms, poor over 600ms on the mobile preset). Lighthouse 13 (October 2025) replaced most of the old audit list with the DevTools “Insights” but did not touch the weights.

Where it bites. Two sites with identical LCP can score 20 points apart. Moving 92 → 98 can be pure run-to-run variance. Quote the underlying metric, not the score.

The disagreement. Lab fast + field slow usually means device/network diversity, a cold cache, or a real-user path your synthetic test never takes (logged-in, personalised, ad-heavy). Lab slow + field fast usually means your synthetic config is harsher than reality. Either way the gap is the first clue. Say what it implies rather than dismissing one source.

When the thresholds don't apply

Core Web Vitals thresholds are Google's: a good default, not a law.

Where they come from. They were chosen partly for ranking and partly from research on perceived responsiveness.

Example. An internal admin tool used by 30 staff on managed laptops doesn't need a 2.5s LCP budget. A trading dashboard cares about update latency that CWV doesn't measure at all. A native-feeling app may care far more about INP than LCP, because the first load happens once a day.

The senior move. Say which metric maps to your product's moment of value, and defend a budget for that.

Say this“I use field data to decide what's worth fixing and lab traces to work out why. I look at p75, not averages, because the average hides the slow tail — and I'd rather know what the worst quarter of my users experience.”
02 — HTML to pixels

The critical rendering path

The browser turns bytes into pixels through a pipeline, and it won't start until it has both a DOM and a CSSOM.

HTML  → DOM
CSS   → CSSOM
DOM + CSSOM → render tree (visible nodes + computed styles)
      → layout   (geometry: position + size)
      → paint    (fill pixels: text, colours, borders)
      → composite (assemble layers on the GPU)

Why it matters. Two properties of this pipeline explain most first-paint problems:

  • It is a pipeline. Nothing downstream can start until the stage above it has what it needs, so a delay at the top is a delay everywhere.
  • The browser will not run it at all until it has both a DOM and a CSSOM. The render tree is their intersection.
  • That second fact is the mechanism behind “CSS is render-blocking”.

Why CSS blocks rendering — the real reason

CSS blocks rendering because no element's style is final until every stylesheet in the head has been parsed.

The shallow answer. People say “to avoid a flash of unstyled content”. That's true but shallow.

How it works. The deeper reason is that CSS has no partial-evaluation guarantee. The last rule in the last stylesheet can override the first rule in the first one, so no element's computed style is final until every stylesheet in the head has been parsed. The browser can't paint a half-known style: it would have to repaint the whole page seconds later, which looks worse than waiting. So it waits.

Where it bites. The slowest stylesheet in your head sets your floor for first paint. Not the total size. Stylesheets are fetched in parallel, and the render tree waits for the last one.

Scripts: parser-blocking vs render-blocking

A synchronous <script> is worse than a stylesheet, because it stops the parser dead.

How it works. It has to. The script might call document.write, so the browser cannot know what the rest of the document is until the script has run. Worse, a synchronous script also waits for any stylesheet still in flight above it, since the script might read computed styles.

Where it bites. The order guarantee is the part people forget. async on two scripts where one depends on the other is a race you'll lose intermittently. Usually only in production, usually only on slow connections. It's the classic “works on my machine” bug.

The preload scanner, and why it decides your LCP

The preload scanner is the single biggest reason a page feels fast, and it only sees markup that is actually in the HTML response.

How it works. While the main parser is blocked, a second lightweight parser, the preload scanner, races ahead through the raw HTML. It looks for URLs it can start fetching early: images, scripts, stylesheets. It has one hard limitation: it only sees markup that is actually in the HTML response.

Where it bites. That one sentence explains a whole family of bugs. A hero image inserted by JavaScript, set as a CSS background-image, or hidden behind a client-only component is invisible to the scanner. Its download can't begin until the JS has parsed, executed and rendered. That is often a second or more after the HTML arrived.

The fix. Either put the real <img> in the server-rendered HTML, or declare it explicitly:

<!-- Tell the browser about a resource it cannot discover by parsing -->
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">

<!-- Warm up a connection to a third-party origin (DNS + TCP + TLS) -->
<link rel="preconnect" href="https://cdn.example.com">

<!-- The LCP image itself: never lazy, always high priority -->
<img src="/hero.webp" width="1200" height="600" fetchpriority="high" alt="...">
The three hints, and what each actually doespreconnect opens the connection only (DNS, TCP, TLS) for an origin you know you'll hit. It doesn't fetch anything, so it's cheap but only saves the handshake. preload fetches one specific URL early at the priority of its as type and parks it in the cache. The browser warns if nothing uses it within a few seconds. modulepreload goes one step further for ES modules. It fetches and parses and compiles the module into the module map, always in CORS mode, so a deep import graph downloads in parallel instead of one level per round trip. fetchpriority is orthogonal. It doesn't discover anything; it reorders what's already queued. It's been Baseline since October 2024 (Chrome 101, Safari 17.2, Firefox 132).

Fonts, the other quiet blocker

A webfont is discovered only after the CSS that references it has been parsed, so it's two round trips deep by default.

  • FOIT: until the font arrives the browser shows nothing, a blank gap where your text should be. Chromium and Firefox give up after a 3s block period and swap.
  • FOUT: the browser shows a fallback that later swaps, a visible reflow.
  • Neither is free. FOIT delays LCP if your largest element is text. FOUT can cost you CLS if the fallback has different metrics.

The fix. The standard remedy is font-display: swap plus a <link rel="preload" as="font" crossorigin> for the one or two faces above the fold. Add size-adjust/ascent-override on the fallback so the swap doesn't move anything.

The trap. crossorigin is mandatory on font preloads. Fonts are fetched in CORS mode, and without it you fetch the file twice.

Numbers worth quotingTTFB under 800ms is the usual target. It's pure server and network, and it's a floor under every other metric. Critical CSS is often budgeted around 14KB, because that's roughly the initial TCP congestion window (~10 packets), so it can arrive in the first round trip. Treat 14KB as a useful heuristic rather than a hard rule. With modern congestion-window tuning and HTTP/3 the cliff is softer than the folklore suggests.

What inlining costs you

Inlining critical CSS trades cacheability for a faster first visit.

How it works. Inlining critical CSS is the standard advice, and it's a genuine trade: inlined bytes are uncacheable. They ship again on every single navigation, including for returning visitors who already had the stylesheet.

When it wins. A clear win when the first visit is the whole point (a landing page, a checkout entry). A clear loss on an app that a user opens 20 times a day.

Same logic for preload. It's a priority boost, not free bandwidth. Preload five things and you've boosted nothing. You've just reordered the queue and starved whatever you didn't list.

03 — The expensive middle

Reflow vs repaint (and thrashing)

Everything in this section is governed by one number: a 60Hz display gives you 16.7ms per frame.

Numbers. After the browser's own compositing and housekeeping you realistically have ~10ms of main-thread budget to produce one frame. On a 120Hz phone it's 8.3ms. Miss the deadline and the frame is dropped. The user sees a stutter, not a slightly late frame.

Why it matters. This is why the stage your change lands in matters more than how much code you wrote.

The other number. The 50ms long task comes from the same place. Google's RAIL model gives an interaction 100ms to feel instant, and budgets half of it for whatever is already running when the input arrives. So any single task over 50ms can make a tap feel late.

The three stages. A change lands in one of three places, from most to least expensive:

  • Reflow / layout: recomputing geometry. Expensive and cascading. Layout is a dependency graph, so a width change on one element can force re-measurement of every descendant, every following sibling in normal flow, and any ancestor sized by its content. Triggered by changing width/height/position/margin/font-size, adding or removing DOM, or reading layout after a write. Cost scales with the number of affected nodes, which is why it hurts most on exactly the big pages you care about.
  • Repaint: refilling pixels for a change that moves nothing (color, background, visibility, box-shadow). Skips layout, so it's cheaper. But it's still main-thread rasterisation over the affected area. A repaint of a full-screen element is not cheap in absolute terms.
  • Composite-only: transform and opacity on an element that has its own layer. The compositor thread handles them on the GPU, without layout or paint. The layer's texture already exists; the compositor just draws it at a different offset or alpha. That's why these two properties can animate smoothly even while the main thread is busy, and why every other animatable property can't.

The properties that force synchronous layout

Reading a geometric property while layout is dirty forces the browser to run layout now, instead of once before the next paint.

How it works. The browser wants to batch. It queues your style writes and flushes layout once, before the next paint. Reading a geometric property breaks that deal: you've asked for a value that's only correct after layout, so the browser must stop and compute it now. In DevTools this shows as a purple Recalculate Style / Layout block, often labelled “Forced reflow is a likely performance bottleneck”.

The offenders. Worth memorising: offsetTop/Left/Width/Height, clientTop/Left/Width/Height, scrollTop/Left/Width/Height, getBoundingClientRect() and getClientRects() (on elements and on a Range), scrollTo()/scrollIntoView(), innerText, focus(), and elementFromPoint().

The subtle one. getComputedStyle() always forces a style recalc. It only forces layout when you ask for a layout-dependent property (width, height, top, left, margin, padding, transform), the element is in a shadow tree, or the page has viewport-based media queries.

When it's free. None of these cost anything if layout is already clean. The price is paid only when a write has dirtied it first.

Layout thrashing

Interleaving reads and writes forces one synchronous layout per iteration. Batching reads, then writes, forces one in total.

// BAD — read, write, read, write forces sync layout each loop
for (const el of items){
  el.style.height = el.offsetHeight + 10 + 'px';  // read then write, repeatedly
}
// GOOD — batch reads, then batch writes
const hs = items.map(el => el.offsetHeight);      // all reads
items.forEach((el, i) => el.style.height = hs[i] + 10 + 'px'); // all writes

How it works. Walk the bad version one iteration at a time and the cost is obvious. Iteration 1 writes a height, which invalidates layout. Iteration 2 reads offsetHeight, and because layout is dirty the browser must run it now to answer: a full layout pass. Then iteration 2 writes, dirtying it again for iteration 3.

Numbers. With 200 items you've triggered 200 synchronous layouts instead of one. The total is quadratic-ish in practice, because each pass re-measures a growing set of dirty nodes. The fixed version reads everything while layout is clean (one pass, reused 200 times), then writes everything, and lets a single layout happen before the next frame.

The general trick. Batch writes inside requestAnimationFrame so they land right before the browser's own layout pass. Prefer IntersectionObserver / ResizeObserver over polling getBoundingClientRect(). They deliver geometry asynchronously, computed as a side effect of layout the browser was doing anyway.

Layers are not free

Every compositor layer is a GPU texture, so promoting everything trades jank for memory pressure.

How it works. will-change: transform promotes an element to its own compositor layer, which is what makes transform animations cheap. But each layer is a GPU texture: width × height × 4 bytes. A full-screen layer on a 1080p phone is roughly 8MB of VRAM, plus upload cost.

Where it bites. Promote everything and you'll trade jank for memory pressure and crashes on low-end Android. That's a real and common regression.

The rule. Apply will-change shortly before the animation and remove it after. Or just let the browser promote automatically when it sees a transform animation. Never ship it as a blanket rule in a utility class.

The modern escape hatches

Two escape hatches let the browser skip layout and paint work it doesn't need to do yet.

  • content-visibility: auto: tells the browser it may skip layout and paint entirely for off-screen subtrees. Pair with contain-intrinsic-size so the scrollbar doesn't jump.
  • contain: layout paint: a promise to the browser that this subtree's layout can't affect anything outside it, so a reflow inside stops at the boundary. This is the cheap, targeted version of the same idea.

Numbers. content-visibility is an enormous win on long documents. web.dev's travel-blog demo went from 232ms to 30ms of initial rendering. It's been in every engine since Safari 18 and Firefox 125 (2024).

Where it bites. Skipped content is still findable by Ctrl+F and still in the accessibility tree. But its layout is deferred, which can surprise scroll-anchoring code.

When “just use transform” isn't enoughCompositing only saves you if the layer's texture is still valid. Animating transform: scale() on text re-rasterises at the new scale, so it can still cost paint. filter is composited in Chrome alongside transform and opacity. But a blur() is recomputed by the GPU over the whole layer every frame, so it's still expensive on a low-end GPU. A huge box-shadow isn't composited at all and repaints. And an element inside overflow: hidden with a border-radius may be forced back onto the main thread for masking. If the Performance panel still shows paint during your transform animation, that's what happened.
04 — The toolkit (framed as attribution)

Techniques, and what each one costs

Every item here is a trade, not an improvement.

Why it matters. The interview answer that lands is the one that states the cost as fluently as the benefit. It reaches for the boring wins before the clever ones.

Order of operations

Check the cheap structural things first, because they routinely dwarf application-level work.

  • Compression on (Brotli), and images in a modern format and correctly sized.
  • Cache-Control set properly, and a CDN in front.
  • The third-party scripts audited.

Where it bites. It is extremely common to find one marketing tag costing more main-thread time than the entire application bundle. Establish that before you memoise anything.

Code splitting

Code splitting ships less JS up front, and the real win is main-thread parse and execute time, not just bytes.

How it works. import() / React.lazy + Suspense pull in routes or features on demand. The reason it works isn't only bytes over the wire. It's parse, compile and execute time on the main thread, which is what actually shows up as TBT and input delay.

Numbers. Compressed transfer size understates the cost. A 400KB gzipped bundle can be 1.5MB of JS to parse on a mid-range phone.

Attribution: measured a 400KB initial bundle → split by route → verified TBT and LCP dropped.

What it costs. Every split point is a potential waterfall. If the chunk is only requested once the route renders, the user waits for a round trip after they've already navigated, and sees a spinner they didn't see before. Route-level splitting is nearly always worth it. Splitting a 4KB component is a network request to save nothing. Mitigate with prefetching on intent (hover, viewport) so the chunk is warm before it's needed.

A budget you can defendAttribute the number or it sounds invented. Alex Russell's original 2017 budget was ~130KB of compressed JavaScript for a JS-driven site (170KB total for a mostly-markup one), to be interactive in 5s on a Moto G4 over slow 3G. His 2024 revision targets the p75 phone (a 2020 Galaxy A51) on a 7.2 Mbps / 94ms RTT link. That gives ~365KiB of JS for a 3s target on a JS-heavy app and ~75 KiB for a content site (100 KiB if you accept a 5s target). Pick the one that matches your product. Set a hard CI budget so it can only grow deliberately. Say out loud that an editor or a map app will legitimately blow past it.

Lazy loading images

loading="lazy" goes on below-the-fold images only, never on the LCP image.

How it works. The mechanism is the reason for the caveat. A lazy image is deliberately skipped by the preload scanner. It isn't fetched until layout has established that it's near the viewport.

Where it bites. Put it on your hero and you have converted an image that could have started downloading in the first 50ms into one that starts after layout. That's a self-inflicted LCP regression, and one of the most common ones in the wild. The LCP image gets fetchpriority="high" and no lazy attribute.

List virtualization / windowing

Virtualization renders only the visible rows, turning O(n) DOM into O(viewport).

How it works. Render only the visible rows of a long list (a 10k-row order history), recycling nodes as the user scrolls. The win is compounding: fewer nodes means cheaper layout, cheaper style recalculation, less memory, and a smaller tree for React to diff.

What it costs. The rows that don't exist can't be found by Ctrl+F, can't be indexed, and aren't in the accessibility tree. So screen-reader users need correct aria-setsize/aria-posinset to know how long the list is. Variable row heights need measurement and cause scrollbar jitter. Anchor links into the middle of the list stop working without extra code.

When not to. Below a few hundred rows, none of this is worth it. Pagination is usually the better product answer anyway.

Avoiding unnecessary re-renders

A re-render is not a DOM write, so memoise where the Profiler shows an expensive subtree, not on principle.

How it works. Stable references plus React.memo; the mechanics live in the React Rendering tab. The thing to be precise about here is that a re-render is not a DOM write. React re-runs the component and diffs, and touches the DOM only where the diff differs. So a re-render costs the function call, the hook bookkeeping and the diff, which for a small component is genuinely trivial.

Attribution: Profiler flame chart showed a parent re-rendering a heavy child → memoised → confirmed the child dropped out of the commit.

What it costs. React.memo adds a props comparison on every render plus a retained reference. useMemo/useCallback add a dependency-array comparison and keep the old value alive. Wrapping everything makes the code noisier and keeps memory alive longer.

The real risk. A single unstable prop silently defeats the memo, so you pay the comparison forever and get nothing. Memoise where the Profiler shows an expensive subtree, not on principle. (The React Compiler shifts this calculus, but be ready to say what it does rather than assuming it's on.)

Structural sharing and field-level selectors

Structural sharing keeps identity checks meaningful. Field-level selectors stop unrelated changes waking a component.

How it works. Immutable updates reuse the unchanged subtrees of a state object. So identity checks stay O(1) and memoised selectors don't recompute. This is why prevState !== nextState is a meaningful signal at all. Field-level selectors then subscribe a component to one slice, so an unrelated change doesn't wake it.

Where it bites. A selector returning a new object or array each call (state.items.filter(...)) breaks referential equality. It re-renders every subscriber on every store update, exactly the bug the pattern was meant to prevent.

Getting work off the main thread

Move genuinely expensive, pure work to a Web Worker. For work that must stay on the main thread, yield.

How it works. When the work is genuinely expensive and genuinely pure (parsing a large CSV, diffing, search indexing, image processing), the answer isn't to make it faster. It's to move it. A Web Worker runs it on another thread, so the main thread stays free to paint and respond to input.

What it costs. The postMessage boundary. Data is structured-cloned (unless you transfer an ArrayBuffer), there's no DOM access, and the setup is real complexity. Worth it above roughly tens of milliseconds of repeated work; not worth it for a 2ms function.

Yielding. For work that must stay on the main thread, yield instead. scheduler.yield() (with a setTimeout(…, 0) fallback for Safari) breaks one long task into several short ones, letting the browser service input between them. The total work is unchanged. The responsiveness is what improves, and being clear about that distinction is itself a senior signal.

The difference. scheduler.yield() (Chrome 129, Firefox 142; still absent from Safari as of September 2026) puts your continuation at the front of the queue, so input runs and then you resume. A setTimeout fallback goes to the back, behind every other queued task.

The third option. requestIdleCallback is for genuinely deferrable work. The callback gets a deadline of at most 50ms and may not fire for seconds. So pass a timeout for anything that must eventually run, and know that Safari doesn't ship it.

Skipping the load entirely: bfcache and speculation rules

The fastest navigation is one the browser doesn't have to do: restore it from the bfcache, or prerender it before the click.

How bfcache works. The back/forward cache keeps the whole page (DOM, JS heap, scroll position) in memory when the user leaves, and restores it instantly on Back. A restored page fires pageshow with persisted: true, and the web-vitals library reports a fresh, near-zero LCP for it.

What blocks it. Desktop Chrome and Firefox refuse to cache a page that has an unload listener, which is why that event is deprecated. Chrome only started caching Cache-Control: no-store pages in 2025 (fully rolled out March–April), for 3 minutes instead of 10 and evicting on any cookie change. Debug it in DevTools → Application → Back/forward cache, or in the field via notRestoredReasons (Chrome 125).

How speculation rules work. They go the other way. A <script type="speculationrules"> block tells Chrome which links to prefetch or fully prerender in a hidden tab. The eagerness knob sets when: conservative = on pointerdown, moderate = after a 200ms hover, eager/immediate. An activated prerender gives a near-zero LCP because the paint happened before the click.

What it costs. The ones you'd expect: wasted bandwidth and server load on wrong guesses, and analytics that must check document.prerendering. It's Chromium-only (Chrome 109+, Safari 26.2 behind a flag, not in Firefox). So it's a progressive enhancement, never a dependency.

05 — What Google measures

Core Web Vitals & diagnosing a slow interaction

Three metrics, deliberately chosen to cover three different user complaints, each graded at p75 of real users.

  • “It took ages to show up”: LCP.
  • “It didn't respond when I tapped”: INP.
  • “It moved and I hit the wrong thing”: CLS.

The diagnostics. Two more you'll be asked about are diagnostics, not vitals. TTFB (<800ms) is server + network, and bounds everything else. FCP (<1.8s) is the first pixel of any content. TBT is the lab stand-in for INP, because a synthetic run has no real interactions to measure.

What counts as the LCP element — the follow-up that catches peopleCandidates are <img>, <image> inside SVG, a <video> poster or first frame, an element with a CSS background-image: url(), and block elements containing text. Chrome then throws out things that look like content but aren't. Paints at opacity: 0 (Chrome 86). Images covering the whole viewport, treated as background (Chrome 88). Images with under 0.05 bits of data per rendered pixel, i.e. placeholders and gradients (Chrome 112). Transparent text (Chrome 130). Measurement also stops at the first scroll or tap. So a blurred placeholder that is swapped for the real image doesn't “win” LCP early, and stretching a tiny image over the fold doesn't game it.

LCP is four phases — this is the answer that stands out

LCP is four phases, and each phase has a completely different fix.

Why it matters. Almost everyone answers “LCP is slow” with “optimise the image”. The stronger answer breaks it into the four sub-parts the attribution build of web-vitals reports:

  1. TTFB — how long before the HTML starts arriving. Fixed with caching, CDN, server work, streaming.
  2. Resource load delay — the gap between HTML arriving and the LCP resource starting to download. This is the preload-scanner problem: the element was in JS, in CSS, or lazy. Fixed by putting it in the markup, preloading, and raising priority. The most surprising slice: CrUX data for pages with poor LCP shows a median 1.3s of load delay against only 0.35s of actual download.
  3. Resource load duration — the actual download. Fixed with format (AVIF/WebP), correct sizing, srcset, compression, CDN.
  4. Element render delay — the resource is there but nothing has painted yet, because the main thread is busy or the content is blocked behind hydration or a webfont. Fixed by unblocking the main thread.

Why it lands. Say that breakdown out loud and the follow-up question usually becomes an easier one. You've shown you know where to look, rather than which trick to try.

Numbers. The field numbers back it up. In web.dev's CrUX analysis the median poor-LCP page spends ~2.3s in TTFB and ~1.3s in load delay. Most origins with poor LCP spend under 10% of their LCP downloading the image. So “compress the hero” is the answer that has been over-sold for a decade.

Diagnosing a slow interaction (INP)

Record the interaction, find the long task, split INP into its three parts, fix the dominant one, then re-measure.

  1. Reproduce it in the Performance panel and record.
  2. Look for long tasks (> 50ms) around the interaction. Better, look for long animation frames (LoAF, Chrome 123, Chromium-only). They measure the whole frame including style, layout and paint, catch several small tasks that together block a frame, and name the script's source URL and function.
  3. Break INP into its three parts and fix the dominant one:
    • Input delay — the main thread was already busy when the tap arrived, so the handler couldn't even start. The culprit is usually something unrelated: hydration, a third-party script, a timer. Fix by yielding and deferring, not by touching the handler.
    • Processing duration — your own event callbacks running to completion. Fix by doing less synchronously, or by moving non-urgent state updates into startTransition.
    • Presentation delay — everything between your handler finishing and the pixels landing: React's render and commit, style, layout, paint. Fix by memoising the expensive subtree, virtualizing, or splitting the update.
  4. Re-measure, and check you haven't just moved the cost somewhere less visible.

How INP picks its number. A common follow-up. Only clicks, taps and key presses count; hovering and scrolling don't. Each interaction's latency is the full input-to-next-paint time. The page's INP is the single worst interaction, except that on busy pages one outlier is discarded per 50 interactions. That's why a page can feel fine and still fail: one 600ms tap on a menu is the score.

Why the split matters. All three present identically to the user (“the button doesn't work”) and have entirely different fixes. Optimising your click handler when 300ms of the 400ms was input delay from a third-party tag is wasted work. The number won't move.

CLS: what the score actually is

CLS isn't a count of shifts. It's the worst burst of unexpected movement, scored by how much moved and how far.

How it works. Each unexpected shift scores impact fraction × distance fraction: how much of the viewport moved, multiplied by how far it travelled, as a share of viewport size. Your CLS is the worst session window (a burst of shifts with under 1s between each, capped at 5s in total), not the sum over the whole page.

Where it bites. That's why a single big shift can fail you while a lot of tiny ones don't. It's also why a long-lived SPA doesn't accumulate an ever-worsening score.

“Unexpected”. That word is doing real work in the definition. A shift within 500ms of a user interaction is excluded. That's why an accordion opening is fine and an ad injecting itself is not.

Common CLS causes, in the order you'd check themImages, ads and embeds without reserved dimensions; content injected above existing content (banners, cookie bars); webfonts swapping to different metrics; and @media-dependent content that lands late. Fix by setting width/height attributes or aspect-ratio, reserving a min-height for slots you know will fill, and using size-adjust on fallback fonts. Animate with transform — compositor transforms don't count as layout shifts.
2026 change: soft navigationsUntil this year Core Web Vitals only saw hard navigations. An SPA's route changes were invisible: one LCP for the first load, then nothing. Chrome 151 (July 2026) shipped two new performance entries. soft-navigation starts a new time origin when a user action changes the URL and paints something. interaction-contentful-paint is the LCP-equivalent for the DOM region that interaction modified. They are Chromium-only, observable via PerformanceObserver, and Google has said they are not yet in CrUX or Search Console. So today they belong in your own RUM. The interview-safe line is “shipped in Chrome, not yet graded”.
Say this“I'd start from field data at p75 to see which of the three is failing, then break that metric into its sub-parts — LCP into TTFB, load delay, load duration and render delay; INP into input delay, processing and presentation — and fix the dominant slice. Otherwise you're optimising the part that wasn't the problem.”
06 — Drill until reflex

Scenario drills

Drill 1 — animate without jank
“A sliding panel animates with left and stutters. What do you change and why?”

Animate transform: translateX() instead of left. left triggers layout + paint every frame; transform runs on the compositor once the element has its own layer, skipping layout and paint, so it keeps up with the refresh rate even while the main thread is busy. Add will-change: transform sparingly to hint a layer.

Drill 2 — spot the thrash
boxes.forEach(b => {
  b.style.width = b.offsetWidth * 2 + 'px';
});
Layout thrashing — forced sync reflow per box

Reading offsetWidth after writing width forces the browser to flush layout on every iteration. Batch: read all widths into an array first, then write them all. O(n) reflows become one.

Drill 3 — which metric?
“Users say the page 'jumps' as it loads and they mis-tap. Which Web Vital, and the fix?”

CLS (Cumulative Layout Shift). It's caused by content loading without reserved space — images/ads/fonts pushing layout. Fix by setting explicit width/height or aspect-ratio on media and reserving space for late-loading content.

Drill 4 — the slow click
“Clicking 'Filter' freezes for 400ms. Walk me through diagnosing it.”

That's an INP problem. Record the interaction in the Performance panel, find the long task, and split INP into input delay / processing / presentation. Usually it's a heavy synchronous render. Fix by breaking up the long task, moving the expensive state update into startTransition so the click paints first, memoising, or offloading pure work to a Web Worker — then re-measure.

Drill 5 — render-blocking
“Why does a big <link rel=stylesheet> in the head delay first paint, and what helps?”

CSS is render-blocking: the browser won't paint until the CSSOM is built to avoid a flash of unstyled content. Inline critical CSS, split and defer non-critical CSS, minimise and compress it, and preload key resources so the CSSOM completes sooner.

Drill 6 — attribute the LCP
“Field data says LCP is 4.2s at p75, but the hero image is only 60KB and downloads in 200ms. Where is the time?”

If the download is 200ms, the time is in one of the other three phases, so I'd break LCP down rather than optimise the image further. Most likely resource load delay — the image isn't discoverable in the HTML (rendered by JS, or a CSS background, or marked loading="lazy"), so its 200ms download doesn't start until a second or more in. Next most likely is TTFB eating 1–2s before the HTML even arrives, or element render delay if hydration or a blocking webfont is holding up the paint. The fix follows the phase: put a real <img> with fetchpriority="high" in the server-rendered markup, or fix caching, or unblock the main thread. Optimising the file size here would have won nothing.

Drill 7 — push back
“A teammate wraps every component in React.memo and every callback in useCallback. Do you approve the PR?”

No, and I'd want to be constructive about why. memo isn't free — it's a props comparison plus a retained reference on every render, and one unstable prop (an inline object, a fresh array from a selector) defeats it silently, so you pay the cost forever and get no skip. A re-render is also cheaper than people assume: React re-runs the function and diffs, and only writes to the DOM where the diff differs. So blanket memoisation adds real noise and memory for a mostly imaginary win, and it hides the two or three places where it genuinely matters. I'd ask for a Profiler trace and memoise what it shows is expensive. If the team wants this by default, that's an argument for the React Compiler, not for hand-wrapping everything.
