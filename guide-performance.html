Performance is attribution, not vibes.

Measure a baseline, change one thing, verify no regression. This guide covers the pipeline that turns HTML into pixels, what blocks it, and the Web Vitals you'll be asked to diagnose.

00 — The mindset

Frame everything as attribution

The senior signal on performance isn't a list of tricks — it's method: establish a baseline with a real tool (Profiler, Performance panel, Lighthouse, RUM), change one variable, and verify the improvement without a regression. “I measured X, changed Y, confirmed Z” beats “I added useMemo everywhere.”

The reason this matters isn't process hygiene. It's that intuition about performance is unusually bad, for three specific reasons:

  • The bottleneck is rarely where the code looks slow. A nested loop over 200 items runs in microseconds. The 900ms you're chasing is almost always a network round trip, a blocking script, a synchronous layout, or a component tree re-rendering 40× — none of which look expensive when you read the source.
  • You are not the user. You develop on a fast laptop, on a fast connection, with a warm cache, in a dev build. Each of those makes you 2–10× faster than the median visitor. Optimising against your own experience optimises the one profile that was never in trouble.
  • Every optimisation has a cost. Memoisation costs a comparison and a reference held in memory. Code splitting costs a network waterfall. Virtualization costs Ctrl+F and accessibility. If you can't show the win, you've paid the cost for nothing — and you've made the code harder for the next person.

The four beats of a strong performance answer

Whatever the question, the same skeleton works, and interviewers are listening for it. Notice that only the third beat is about a technique — the other three are what separate a senior answer from a list of tips:

  1. Symptom — what the user actually experiences, in their words. “The dashboard takes four seconds before anything appears.”
  2. Measurement — the tool you'd reach for and the number you'd expect it to give you. “Performance panel on a 4× CPU throttle, plus the LCP breakdown from RUM.”
  3. Hypothesis and fix — one change, tied to the number. “LCP was 80% resource load delay, so the image wasn't being discovered early — preload it and drop the lazy attribute.”
  4. Verification — re-measure, and check what you might have broken. “LCP 4.1s → 2.2s at p75, bundle unchanged, no CLS regression.”
Worked example — the shape in one breath“Support said the orders page felt slow on mobile. Field data put LCP at 4.6s at p75 while our lab runs were 1.9s — that gap alone told me it was device and network, not code. The LCP breakdown showed most of the time in resource load delay: the hero image was inside a lazily-hydrated component, so it wasn't in the HTML for the preload scanner to find. I moved it into the server-rendered markup with fetchpriority="high". p75 LCP went to 2.3s over the next week, and I checked CLS hadn't moved because the image now lands earlier.”

When measuring first is the wrong answer

Don't over-rotate. If someone shows you a 4MB unoptimised PNG hero, a node_modules import of all of lodash, or a list rendering 10,000 rows into the DOM, the correct response is to fix it — profiling to confirm that 4MB is slow is theatre. The rule is really about ordering effort: measure before you spend a week on something clever, not before you spend a minute on something obvious.

The other exception is that measurement itself has failure modes. A React development build is roughly 2–5× slower than production and double-invokes components under StrictMode, so profiling it exaggerates render cost and can send you memoising something that's free in prod. Extensions inflate main-thread time. And a single Lighthouse run has enough variance that a 5-point score move usually means nothing. Measure the thing you ship, more than once.

Say this“I don't optimise by guessing. I profile to find where the time actually goes, fix that, and re-measure — otherwise I'm adding complexity for an unproven win.”
01 — Where the numbers come from

Lab data, field data, and why p75

“Measure it” is only half an answer — the follow-up is measure it where. There are two families of data and they answer different questions. Confusing them is the most common way a performance discussion goes wrong.

ToolKindWhat it's good atWhat it can't tell you
Lighthouse / PageSpeedLab (synthetic)Reproducible before/after on one page; an opinionated audit listWhether real users are affected. It's one load, one device, simulated network
Performance panelLab (trace)Attribution — which task, which function, which frame. The only tool that shows you whyAnything about scale or frequency across your user base
React ProfilerLab (trace)Which components rendered, how often, and why they re-renderedNon-React cost: network, images, CSS, third-party scripts
RUM / web-vitalsField (real users)What's actually happening, segmented by device, country, routeThe cause. It gives you a number and a page, not a call stack
CrUX / Search ConsoleField (Chrome, aggregated)How Google grades you — a 28-day rolling p75 of real Chrome usersFast feedback. It lags by weeks, so it can't be your inner loop

The practical workflow uses both, in one direction: field data tells you what to fix and lab data tells you how. RUM says “checkout LCP is 4.5s at p75 on Android”; you then reproduce that in the Performance panel with throttling until you can see the offending task, fix it, and confirm in lab — but you only believe it when the field number moves a week later.

Why p75 and not an average

Averages hide the users you're losing. If 80% of your visitors load in 1s and 20% load in 9s, the mean is a healthy-looking 2.6s while a fifth of your traffic is having an awful time. Performance distributions are heavily right-skewed — there's a floor on how fast a load can be and no ceiling on how slow — so the mean drifts toward a tail that no individual user experiences.

The 75th percentile is the compromise Google settled on: it's the slowest experience that 3 in 4 users beat, so a passing p75 means the large majority are fine, but it's not so extreme that a handful of users on a train tunnel connection define your score. A page passes Core Web Vitals only when p75 is in the “good” band for all three metrics.

The number that makes this concreteMedian mobile hardware is roughly 4–8× slower on CPU than a developer laptop, which is why Lighthouse's mobile preset applies a 4× CPU slowdown and a simulated Slow 4G link (~1.6 Mbps down, 150ms RTT). If you only ever test unthrottled on desktop, you are testing a device profile that may be 5% of your traffic. Throttle, or better, keep a genuinely cheap Android phone on your desk.

Two traps worth naming out loud

  • The Lighthouse score is not a metric. It's a weighted composite (LCP and TBT dominate) mapped onto a curve. Two sites with identical LCP can score 20 points apart, and moving 92 → 98 can be pure run-to-run variance. Quote the underlying metric, not the score.
  • Lab and field disagreeing is information, not an error. Lab fast + field slow usually means device/network diversity, a cold cache, or a real-user path your synthetic test never takes (logged-in, personalised, ad-heavy). Lab slow + field fast usually means your synthetic config is harsher than reality. Either way the gap is the first clue, so say what it implies rather than dismissing one source.

When the thresholds don't apply

Core Web Vitals thresholds are Google's, chosen partly for ranking and partly from research on perceived responsiveness. They are a good default, not a law. An internal admin tool used by 30 staff on managed laptops doesn't need a 2.5s LCP budget; a trading dashboard cares about update latency that CWV doesn't measure at all; a native-feeling app may care far more about INP than LCP because the first load happens once a day. The senior move is to say which metric maps to your product's moment of value, and to defend a budget for that.

Say this“I use field data to decide what's worth fixing and lab traces to work out why. I look at p75, not averages, because the average hides the slow tail — and I'd rather know what the worst quarter of my users experience.”
02 — HTML to pixels

The critical rendering path

The browser turns bytes into pixels through a pipeline:

HTML  → DOM
CSS   → CSSOM
DOM + CSSOM → render tree (visible nodes + computed styles)
      → layout   (geometry: position + size)
      → paint    (fill pixels: text, colours, borders)
      → composite (assemble layers on the GPU)

Two properties of this pipeline explain most first-paint problems. First, it is a pipeline: nothing downstream can start until the stage above it has what it needs, so a delay at the top is a delay everywhere. Second, the browser will not run it at all until it has both a DOM and a CSSOM — the render tree is their intersection. That's the mechanism behind “CSS is render-blocking”.

Why CSS blocks rendering — the real reason

People answer this with “to avoid a flash of unstyled content”, which is true but shallow. The deeper reason is that CSS has no partial-evaluation guarantee: the last rule in the last stylesheet can override the first rule in the first one, so no element's computed style is final until every stylesheet in the head has been parsed. The browser can't paint a half-known style — it would have to repaint the whole page seconds later, which looks worse than waiting. So it waits.

The consequence is that the slowest stylesheet in your head sets your floor for first paint. Not the total size — the slowest one, because they're fetched in parallel and the render tree waits for the last.

Scripts: parser-blocking vs render-blocking

A synchronous <script> is worse than a stylesheet, because it stops the parser dead. It has to: the script might call document.write, so the browser cannot know what the rest of the document is until the script has run. Worse, a synchronous script also waits for any stylesheet still in flight above it, since the script might read computed styles.

The order guarantee is the part people forget. async on two scripts where one depends on the other is a race you'll lose intermittently, usually only in production, usually only on slow connections — the classic “works on my machine” bug.

The preload scanner, and why it decides your LCP

While the main parser is blocked, a second lightweight parser — the preload scanner — races ahead through the raw HTML looking for URLs it can start fetching early: images, scripts, stylesheets. It is the single biggest reason a page feels fast, and it has one hard limitation: it only sees markup that is actually in the HTML response.

That one sentence explains a whole family of bugs. A hero image inserted by JavaScript, set as a CSS background-image, or hidden behind a client-only component is invisible to the scanner. Its download can't begin until the JS has parsed, executed and rendered — often a second or more after the HTML arrived. The fix is either to put the real <img> in the server-rendered HTML, or to declare it explicitly:

<!-- Tell the browser about a resource it cannot discover by parsing -->
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high">

<!-- Warm up a connection to a third-party origin (DNS + TCP + TLS) -->
<link rel="preconnect" href="https://cdn.example.com">

<!-- The LCP image itself: never lazy, always high priority -->
<img src="/hero.webp" width="1200" height="600" fetchpriority="high" alt="...">

Fonts, the other quiet blocker

A webfont is discovered only after the CSS that references it has been parsed — so it's two round trips deep by default. Until it arrives the browser either shows nothing (FOIT, a blank gap where your text should be, up to a 3s timeout) or a fallback that later swaps (FOUT, a visible reflow). Neither is free: FOIT delays LCP if your largest element is text, and FOUT can cost you CLS if the fallback has different metrics.

The standard remedy is font-display: swap plus a <link rel="preload" as="font" crossorigin> for the one or two faces above the fold, and size-adjust/ascent-override on the fallback so the swap doesn't move anything. Note crossorigin is mandatory on font preloads — fonts are fetched in CORS mode, and without it you fetch the file twice.

Numbers worth quotingTTFB under 800ms is the usual target — it's pure server and network, and it's a floor under every other metric. Critical CSS is often budgeted around 14KB because that's roughly the initial TCP congestion window (~10 packets), so it can arrive in the first round trip. Treat 14KB as a useful heuristic rather than a hard rule — with modern congestion-window tuning and HTTP/3 the cliff is softer than the folklore suggests.

What inlining costs you

Inlining critical CSS is the standard advice, and it's a genuine trade: inlined bytes are uncacheable. They ship again on every single navigation, including for returning visitors who already had the stylesheet. That's a clear win when the first visit is the whole point (a landing page, a checkout entry), and a clear loss on an app that a user opens 20 times a day. Same logic for preload: it's a priority boost, not free bandwidth. Preload five things and you've boosted nothing — you've just reordered the queue and starved whatever you didn't list.

03 — The expensive middle

Reflow vs repaint (and thrashing)

Everything in this section is governed by one number: a 60Hz display gives you 16.7ms per frame, and after the browser's own compositing and housekeeping you realistically have ~10ms of main-thread budget to produce one. On a 120Hz phone it's 8.3ms. Miss the deadline and the frame is dropped — the user sees a stutter, not a slightly late frame. This is why the stage your change lands in matters more than how much code you wrote.

  • Reflow / layout — recomputing geometry. Expensive and cascading: layout is a dependency graph, so a width change on one element can force re-measurement of every descendant, every following sibling in normal flow, and any ancestor sized by its content. Triggered by changing width/height/position/margin/font-size, adding or removing DOM, or reading layout after a write. Cost scales with the number of affected nodes, which is why it hurts most on exactly the big pages you care about.
  • Repaint — refilling pixels for a change that moves nothing (color, background, visibility, box-shadow). Skips layout, so it's cheaper, but it's still main-thread rasterisation over the affected area — a repaint of a full-screen element is not cheap in absolute terms.
  • Composite-only — transform and opacity on an element that has its own layer are handled by the compositor thread on the GPU, without layout or paint. The layer's texture already exists; the compositor just draws it at a different offset or alpha. That's why these two properties can animate smoothly even while the main thread is busy — and why every other animatable property can't.

The properties that force synchronous layout

The browser wants to batch: it queues your style writes and flushes layout once, before the next paint. Reading a geometric property breaks that deal — you've asked for a value that's only correct after layout, so the browser must stop and compute it now. In DevTools this shows as a purple Recalculate Style / Layout block, often labelled “Forced reflow is a likely performance bottleneck”.

Worth memorising the common offenders: offsetTop/Left/Width/Height, clientTop/Left/Width/Height, scrollTop/Left/Width/Height, getBoundingClientRect(), getComputedStyle(), focus(), and window.getSelection().getRangeAt().

Layout thrashing

// BAD — read, write, read, write forces sync layout each loop
for (const el of items){
  el.style.height = el.offsetHeight + 10 + 'px';  // read then write, repeatedly
}
// GOOD — batch reads, then batch writes
const hs = items.map(el => el.offsetHeight);      // all reads
items.forEach((el, i) => el.style.height = hs[i] + 10 + 'px'); // all writes

Walk the bad version one iteration at a time and the cost is obvious. Iteration 1 writes a height, which invalidates layout. Iteration 2 reads offsetHeight, and because layout is dirty the browser must run it now to answer — a full layout pass. Then iteration 2 writes, dirtying it again for iteration 3. With 200 items you've triggered 200 synchronous layouts instead of one, and the total is quadratic-ish in practice because each pass re-measures a growing set of dirty nodes. The fixed version reads everything while layout is clean (one pass, reused 200 times), then writes everything, and lets a single layout happen before the next frame.

The same trick generalises: batch writes inside requestAnimationFrame so they land right before the browser's own layout pass, and prefer IntersectionObserver / ResizeObserver over polling getBoundingClientRect() — they deliver geometry asynchronously, computed as a side effect of layout the browser was doing anyway.

Layers are not free

will-change: transform promotes an element to its own compositor layer, which is what makes transform animations cheap. But each layer is a GPU texture: width × height × 4 bytes, so a full-screen layer on a 1080p phone is roughly 8MB of VRAM, plus upload cost. Promote everything and you'll trade jank for memory pressure and crashes on low-end Android — a real and common regression.

So: apply will-change shortly before the animation and remove it after, or just let the browser promote automatically when it sees a transform animation. Never ship it as a blanket rule in a utility class.

The modern escape hatches

  • content-visibility: auto — tells the browser it may skip layout and paint entirely for off-screen subtrees. Pair with contain-intrinsic-size so the scrollbar doesn't jump. Enormous win on long documents; be careful, because skipped content is still findable by Ctrl+F but its layout is deferred, which can surprise scroll-anchoring code.
  • contain: layout paint — a promise to the browser that this subtree's layout can't affect anything outside it, so a reflow inside stops at the boundary. This is the cheap, targeted version of the same idea.
When “just use transform” isn't enoughCompositing only saves you if the layer's texture is still valid. Animating transform: scale() on text re-rasterises at the new scale, so it can still cost paint. A filter: blur() or a huge shadow on an animating layer is repainted per frame on many devices. And an element inside overflow: hidden with a border-radius may be forced back onto the main thread for masking. If the Performance panel still shows paint during your transform animation, that's what happened.
04 — The toolkit (framed as attribution)

Techniques, and what each one costs

Every item here is a trade, not an improvement. The interview answer that lands is the one that states the cost as fluently as the benefit — and that reaches for the boring wins before the clever ones.

Order of operations

Before any of the techniques below, check the cheap structural things, because they routinely dwarf application-level work: compression on (Brotli), images in a modern format and correctly sized, Cache-Control set properly, a CDN in front, and the third-party scripts audited. It is extremely common to find one marketing tag costing more main-thread time than the entire application bundle. Establish that before you memoise anything.

Code splitting

import() / React.lazy + Suspense ship less JS up front and pull in routes or features on demand. The reason it works isn't only bytes over the wire — it's parse, compile and execute time on the main thread, which is what actually shows up as TBT and input delay. Compressed transfer size understates the cost; a 400KB gzipped bundle can be 1.5MB of JS to parse on a mid-range phone.

Attribution: measured a 400KB initial bundle → split by route → verified TBT and LCP dropped.

What it costs: every split point is a potential waterfall. If the chunk is only requested once the route renders, the user waits for a round trip after they've already navigated, and sees a spinner they didn't see before. Route-level splitting is nearly always worth it; splitting a 4KB component is a network request to save nothing. Mitigate with prefetching on intent (hover, viewport) so the chunk is warm before it's needed.

A budget you can defendRoughly <200KB of compressed JavaScript on the critical path for a content site, and set a hard CI budget so it can only grow deliberately. Quote it as a budget you'd agree with the team, not a universal truth — an editor or a map app will legitimately blow past it, and the honest version of the answer says so.

Lazy loading images

loading="lazy" on below-the-fold images only. The mechanism is the reason for the caveat: a lazy image is deliberately skipped by the preload scanner and isn't fetched until layout has established that it's near the viewport. Put it on your hero and you have converted an image that could have started downloading in the first 50ms into one that starts after layout — a self-inflicted LCP regression, and one of the most common ones in the wild. The LCP image gets fetchpriority="high" and no lazy attribute.

List virtualization / windowing

Render only the visible rows of a long list (a 10k-row order history), recycling nodes as the user scrolls. It turns O(n) DOM into O(viewport), and the win is compounding: fewer nodes means cheaper layout, cheaper style recalculation, less memory, and a smaller tree for React to diff.

What it costs: the rows that don't exist can't be found by Ctrl+F, can't be indexed, and aren't in the accessibility tree — so screen-reader users need correct aria-setsize/aria-posinset to know how long the list is. Variable row heights need measurement and cause scrollbar jitter. Anchor links into the middle of the list stop working without extra code. Below a few hundred rows, none of this is worth it — pagination is usually the better product answer anyway.

Avoiding unnecessary re-renders

Stable references plus React.memo; the mechanics live in the React Rendering tab. The thing to be precise about here is that a re-render is not a DOM write — React re-runs the component and diffs, and touches the DOM only where the diff differs. So a re-render costs the function call, the hook bookkeeping and the diff, which for a small component is genuinely trivial.

Attribution: Profiler flame chart showed a parent re-rendering a heavy child → memoised → confirmed the child dropped out of the commit.

What it costs: React.memo adds a props comparison on every render plus a retained reference; useMemo/useCallback add a dependency-array comparison and keep the old value alive. Wrapping everything makes the code noisier, keeps memory alive longer, and — the real risk — a single unstable prop silently defeats the memo, so you pay the comparison forever and get nothing. Memoise where the Profiler shows an expensive subtree, not on principle. (The React Compiler shifts this calculus, but be ready to say what it does rather than assuming it's on.)

Structural sharing and field-level selectors

Immutable updates reuse the unchanged subtrees of a state object, so identity checks stay O(1) and memoised selectors don't recompute — this is why prevState !== nextState is a meaningful signal at all. Field-level selectors then subscribe a component to one slice, so an unrelated change doesn't wake it. The failure mode to name: a selector returning a new object or array each call (state.items.filter(...)) breaks referential equality and re-renders every subscriber on every store update — exactly the bug the pattern was meant to prevent.

Getting work off the main thread

When the work is genuinely expensive and genuinely pure — parsing a large CSV, diffing, search indexing, image processing — the answer isn't to make it faster, it's to move it. A Web Worker runs it on another thread so the main thread stays free to paint and respond to input. The cost is the postMessage boundary: data is structured-cloned (unless you transfer an ArrayBuffer), there's no DOM access, and the setup is real complexity. Worth it above roughly tens of milliseconds of repeated work; not worth it for a 2ms function.

For work that must stay on the main thread, yield instead: scheduler.yield() (with a setTimeout(…, 0) fallback for Safari) breaks one long task into several short ones, letting the browser service input between them. The total work is unchanged — the responsiveness is what improves, and being clear about that distinction is itself a senior signal.

05 — What Google measures

Core Web Vitals & diagnosing a slow interaction

Three metrics, deliberately chosen to cover three different user complaints: “it took ages to show up”, “it didn't respond when I tapped”, and “it moved and I hit the wrong thing”. Each is graded at p75 of real users.

MetricMeasuresGoodNeeds work
LCPLargest Contentful Paint — loading; when the main content appears< 2.5s> 4.0s is poor
INPInteraction to Next Paint — responsiveness across all interactions (replaced FID in March 2024)< 200ms> 500ms is poor
CLSCumulative Layout Shift — visual stability; unexpected movement< 0.1> 0.25 is poor

Two more you'll be asked about that are diagnostics, not vitals: TTFB (<800ms) is server + network and bounds everything else, and FCP (<1.8s) is the first pixel of any content. TBT is the lab stand-in for INP, because a synthetic run has no real interactions to measure.

LCP is four phases — this is the answer that stands out

Almost everyone answers “LCP is slow” with “optimise the image”. The stronger answer breaks it into the four sub-parts the attribution build of web-vitals reports, because each one has a completely different fix:

  1. TTFB — how long before the HTML starts arriving. Fixed with caching, CDN, server work, streaming.
  2. Resource load delay — the gap between HTML arriving and the LCP resource starting to download. This is the preload-scanner problem: the element was in JS, in CSS, or lazy. Fixed by putting it in the markup, preloading, and raising priority. Usually the biggest and most surprising slice.
  3. Resource load duration — the actual download. Fixed with format (AVIF/WebP), correct sizing, srcset, compression, CDN.
  4. Element render delay — the resource is there but nothing has painted yet, because the main thread is busy or the content is blocked behind hydration or a webfont. Fixed by unblocking the main thread.

Say that breakdown out loud and the follow-up question usually becomes an easier one, because you've shown you know where to look rather than which trick to try.

Diagnosing a slow interaction (INP)

  1. Reproduce it in the Performance panel and record.
  2. Look for long tasks (≥ 50ms) — or better, long animation frames (LoAF), which attribute the whole frame including render and are far more actionable — around the interaction.
  3. Break INP into its three parts and fix the dominant one:
    • Input delay — the main thread was already busy when the tap arrived, so the handler couldn't even start. The culprit is usually something unrelated: hydration, a third-party script, a timer. Fix by yielding and deferring, not by touching the handler.
    • Processing duration — your own event callbacks running to completion. Fix by doing less synchronously, or by moving non-urgent state updates into startTransition.
    • Presentation delay — everything between your handler finishing and the pixels landing: React's render and commit, style, layout, paint. Fix by memoising the expensive subtree, virtualizing, or splitting the update.
  4. Re-measure, and check you haven't just moved the cost somewhere less visible.

The reason the split matters: all three present identically to the user (“the button doesn't work”) and have entirely different fixes. Optimising your click handler when 300ms of the 400ms was input delay from a third-party tag is wasted work, and the number won't move.

CLS: what the score actually is

CLS isn't a count of shifts. Each unexpected shift scores impact fraction × distance fraction — how much of the viewport moved, multiplied by how far it travelled, as a share of viewport size — and your CLS is the worst session window (a burst of shifts, capped at 5s), not the sum over the whole page. That's why a single big shift can fail you while a lot of tiny ones don't, and why a long-lived SPA doesn't accumulate an ever-worsening score.

“Unexpected” is doing real work in that definition: a shift within 500ms of a user interaction is excluded, which is why an accordion opening is fine and an ad injecting itself is not.

Common CLS causes, in the order you'd check themImages, ads and embeds without reserved dimensions; content injected above existing content (banners, cookie bars); webfonts swapping to different metrics; and @media-dependent content that lands late. Fix by setting width/height attributes or aspect-ratio, reserving a min-height for slots you know will fill, and using size-adjust on fallback fonts. Animate with transform — compositor transforms don't count as layout shifts.
Say this“I'd start from field data at p75 to see which of the three is failing, then break that metric into its sub-parts — LCP into TTFB, load delay, load duration and render delay; INP into input delay, processing and presentation — and fix the dominant slice. Otherwise you're optimising the part that wasn't the problem.”
06 — Drill until reflex

Scenario drills

Drill 1 — animate without jank
“A sliding panel animates with left and stutters. What do you change and why?”

Animate transform: translateX() instead of left. left triggers layout + paint every frame; transform runs on the compositor once the element has its own layer, skipping layout and paint, so it keeps up with the refresh rate even while the main thread is busy. Add will-change: transform sparingly to hint a layer.

Drill 2 — spot the thrash
boxes.forEach(b => {
  b.style.width = b.offsetWidth * 2 + 'px';
});
Layout thrashing — forced sync reflow per box

Reading offsetWidth after writing width forces the browser to flush layout on every iteration. Batch: read all widths into an array first, then write them all. O(n) reflows become one.

Drill 3 — which metric?
“Users say the page 'jumps' as it loads and they mis-tap. Which Web Vital, and the fix?”

CLS (Cumulative Layout Shift). It's caused by content loading without reserved space — images/ads/fonts pushing layout. Fix by setting explicit width/height or aspect-ratio on media and reserving space for late-loading content.

Drill 4 — the slow click
“Clicking 'Filter' freezes for 400ms. Walk me through diagnosing it.”

That's an INP problem. Record the interaction in the Performance panel, find the long task, and split INP into input delay / processing / presentation. Usually it's a heavy synchronous render. Fix by breaking up the long task, moving the expensive state update into startTransition so the click paints first, memoising, or offloading pure work to a Web Worker — then re-measure.

Drill 5 — render-blocking
“Why does a big <link rel=stylesheet> in the head delay first paint, and what helps?”

CSS is render-blocking: the browser won't paint until the CSSOM is built to avoid a flash of unstyled content. Inline critical CSS, split and defer non-critical CSS, minimise and compress it, and preload key resources so the CSSOM completes sooner.

Drill 6 — attribute the LCP
“Field data says LCP is 4.2s at p75, but the hero image is only 60KB and downloads in 200ms. Where is the time?”

If the download is 200ms, the time is in one of the other three phases, so I'd break LCP down rather than optimise the image further. Most likely resource load delay — the image isn't discoverable in the HTML (rendered by JS, or a CSS background, or marked loading="lazy"), so its 200ms download doesn't start until a second or more in. Next most likely is TTFB eating 1–2s before the HTML even arrives, or element render delay if hydration or a blocking webfont is holding up the paint. The fix follows the phase: put a real <img> with fetchpriority="high" in the server-rendered markup, or fix caching, or unblock the main thread. Optimising the file size here would have won nothing.

Drill 7 — push back
“A teammate wraps every component in React.memo and every callback in useCallback. Do you approve the PR?”

No, and I'd want to be constructive about why. memo isn't free — it's a props comparison plus a retained reference on every render, and one unstable prop (an inline object, a fresh array from a selector) defeats it silently, so you pay the cost forever and get no skip. A re-render is also cheaper than people assume: React re-runs the function and diffs, and only writes to the DOM where the diff differs. So blanket memoisation adds real noise and memory for a mostly imaginary win, and it hides the two or three places where it genuinely matters. I'd ask for a Profiler trace and memoise what it shows is expensive. If the team wants this by default, that's an argument for the React Compiler, not for hand-wrapping everything.
