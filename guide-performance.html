00 — The mindset

Frame everything as attribution

The senior signal on performance isn't a list of tricks — it's method: establish a baseline with a real tool (Profiler, Performance panel, Lighthouse), change one variable, and verify the improvement without a regression. “I measured X, changed Y, confirmed Z” beats “I added useMemo everywhere.”

Say this“I don't optimise by guessing. I profile to find where the time actually goes, fix that, and re-measure — otherwise I'm adding complexity for an unproven win.”
01 — HTML to pixels

The critical rendering path

The browser turns bytes into pixels through a pipeline:

HTML  → DOM
CSS   → CSSOM
DOM + CSSOM → render tree (visible nodes + computed styles)
      → layout   (geometry: position + size)
      → paint    (fill pixels: text, colours, borders)
      → composite (assemble layers on the GPU)

What blocks the first render:

  • CSS is render-blocking — the browser won't paint until the CSSOM is built, because it needs styles to avoid a flash of unstyled content. Ship critical CSS small and fast; defer the rest.
  • Synchronous <script> is parser-blocking — it pauses HTML parsing. Use defer (run after parse, in order) or async (run as soon as fetched, unordered) to unblock.
  • <link rel="preload"> fetches a critical resource early without blocking.
02 — The expensive middle

Reflow vs repaint (and thrashing)

  • Reflow / layout — recomputing geometry. Expensive and cascading: changing one element's size can re-lay-out its subtree or the whole page. Triggered by changing width/height/position, adding/removing DOM, or reading layout after a write.
  • Repaint — filling pixels for a visual change that doesn't move anything (colour, background, visibility). Cheaper than reflow.
  • Composite-only — transform and opacity can be handled by the compositor on the GPU without layout or paint. That's why animations should prefer them.

Layout thrashing

// BAD — read, write, read, write forces sync layout each loop
for (const el of items){
  el.style.height = el.offsetHeight + 10 + 'px';  // read then write, repeatedly
}
// GOOD — batch reads, then batch writes
const hs = items.map(el => el.offsetHeight);      // all reads
items.forEach((el, i) => el.style.height = hs[i] + 10 + 'px'); // all writes

Interleaving DOM reads (offsetHeight, getBoundingClientRect) with writes forces the browser to recompute layout synchronously on every read. Batch all reads, then all writes — or batch your writes inside requestAnimationFrame, and use IntersectionObserver/ResizeObserver, which hand you geometry asynchronously instead of forcing a sync read.

03 — The toolkit (framed as attribution)

Techniques

  • Code splitting — import() / React.lazy + Suspense to ship less JS up front and load routes/features on demand. Attribution: measured a 400KB initial bundle → split routes → verified TBT and LCP dropped.
  • Lazy loading — loading="lazy" on below-the-fold images only (never the LCP image — that one gets fetchpriority="high"), plus offscreen components and below-the-fold routes.
  • List virtualization / windowing — render only the visible rows of a long list (e.g. a 10k-row order history), recycling DOM nodes. Turns O(n) DOM into O(viewport).
  • Avoid unnecessary re-renders — stable references + React.memo; see the React Rendering tab. Attribution: Profiler flame chart showed a parent re-rendering a heavy child → memoised → confirmed the child dropped out of the commit.
  • Structural sharing — immutable updates reuse unchanged subtrees, so referential equality checks stay cheap and memoised selectors don't recompute.
  • Field-level memoised selectors — subscribe a component to one slice of state so unrelated changes don't re-render it.
04 — What Google measures

Core Web Vitals & diagnosing a slow interaction

MetricMeasuresGood
LCPLargest Contentful Paint — loading; when the main content appears< 2.5s
INPInteraction to Next Paint — responsiveness across all interactions (replaced FID in March 2024)< 200ms
CLSCumulative Layout Shift — visual stability; unexpected movement< 0.1

Diagnosing a slow interaction (INP)

  1. Reproduce it in the Performance panel and record.
  2. Look for long tasks (≥ 50ms) — or better, long animation frames (LoAF), which attribute the whole frame including render — blocking the main thread around the interaction.
  3. Break INP into input delay (main thread busy when the event arrives), processing duration (your event callbacks running to completion), and presentation delay (rendering, paint and compositing until the next frame is on screen).
  4. Fix the dominant part: break up long tasks (scheduler.yield(), with a setTimeout fallback for Safari), move heavy state updates into startTransition, memoise the expensive render, or offload pure computation to a Web Worker.
Common CLS causeImages/ads/embeds without reserved dimensions, and injecting content above existing content. Fix by setting width/height (or aspect-ratio) and reserving space.
05 — Drill until reflex

Scenario drills

Drill 1 — animate without jank
“A sliding panel animates with left and stutters. What do you change and why?”

Animate transform: translateX() instead of left. left triggers layout + paint every frame; transform runs on the compositor once the element has its own layer, skipping layout and paint, so it keeps up with the refresh rate even while the main thread is busy. Add will-change: transform sparingly to hint a layer.

Drill 2 — spot the thrash
boxes.forEach(b => {
  b.style.width = b.offsetWidth * 2 + 'px';
});
Layout thrashing — forced sync reflow per box

Reading offsetWidth after writing width forces the browser to flush layout on every iteration. Batch: read all widths into an array first, then write them all. O(n) reflows become one.

Drill 3 — which metric?
“Users say the page 'jumps' as it loads and they mis-tap. Which Web Vital, and the fix?”

CLS (Cumulative Layout Shift). It's caused by content loading without reserved space — images/ads/fonts pushing layout. Fix by setting explicit width/height or aspect-ratio on media and reserving space for late-loading content.

Drill 4 — the slow click
“Clicking 'Filter' freezes for 400ms. Walk me through diagnosing it.”

That's an INP problem. Record the interaction in the Performance panel, find the long task, and split INP into input delay / processing / presentation. Usually it's a heavy synchronous render. Fix by breaking up the long task, moving the expensive state update into startTransition so the click paints first, memoising, or offloading pure work to a Web Worker — then re-measure.

Drill 5 — render-blocking
“Why does a big <link rel=stylesheet> in the head delay first paint, and what helps?”

CSS is render-blocking: the browser won't paint until the CSSOM is built to avoid a flash of unstyled content. Inline critical CSS, split and defer non-critical CSS, minimise and compress it, and preload key resources so the CSSOM completes sooner.
