Frontend interview prep

A promise is a value that hasn't arrived yet.

Everything async in a modern frontend — a fetch to the order-book API, a WebSocket handshake, a debounced save — is a promise underneath. This course builds the model from states up, then drills the timing and combinator questions senior interviews actually ask.

00 — The mental model

Why promises exist

Promises exist so an async result can be returned, passed around and chained, instead of buried in nested callbacks.

Before promises. Async results were delivered through callbacks: you pass a function in, it gets called later. That works for one operation. It falls apart the moment operations depend on each other:

// callback hell — nesting grows with every step, errors handled 3 times
getUser(id, (err, user) => {
  if (err) return done(err);
  getBalance(user, (err, bal) => {
    if (err) return done(err);
    getOrders(bal, (err, orders) => {
      if (err) return done(err);
      done(null, orders);
    });
  });
});

How it works. A promise is an object that represents the eventual result of an async operation. Instead of handing your continuation into the function, the function hands a promise back to you. You attach continuations to it. That inversion is the whole point. It makes async values composable: they can be returned, passed around, chained, and combined.

// the same thing, flat and with one error path
getUser(id)
  .then(user => getBalance(user))
  .then(bal => getOrders(bal))
  .then(orders => done(orders))
  .catch(err => handle(err));   // one catch covers every step
The one-liner definition "A promise is a placeholder for a future value. It's a state machine with three states and a guarantee: it settles once, and any handler you attach for that outcome — even after it settles — will fire exactly once, asynchronously."

The two guarantees. Two structural guarantees make promises trustworthy. Both are worth naming in an interview:

  • They settle once and are then immutable. A promise moves from pending to either fulfilled or rejected, exactly one time. After that its value never changes. A late resolve() or reject() is silently ignored.
  • Handlers always run asynchronously. Even on an already-resolved promise, a .then callback never runs synchronously. It's scheduled as a microtask. This removes the "sometimes-sync, sometimes-async" ambiguity that made raw callbacks so bug-prone.
01 — The state machine

States & anatomy

A promise is always in exactly one of three states, and it leaves pending exactly once.

Pending

The initial state. The async work hasn't finished. No value yet.

Fulfilled

Completed successfully. Carries a value. Reached via resolve(value).

Rejected

Failed. Carries a reason (usually an Error). Reached via reject(reason) or a throw.

Vocabulary. Interviewers listen for these words. A promise is settled (or "resolved" in the loose sense) once it is either fulfilled or rejected, i.e. no longer pending. Settled is permanent.

The precise meaning of "resolved". A promise is resolved once it's settled or locked onto another promise's eventual outcome. It may still be pending if that inner promise is.

Creating one with the executor

The executor runs synchronously; only the settlement and your handlers are async.

const p = new Promise((resolve, reject) => {
  // executor runs SYNCHRONOUSLY, immediately, right now
  connectToOrderBook()
    .on('open',  ()   => resolve('connected'))
    .on('error', (e)  => reject(e));
});

Three facts that get tested.

  • The executor function runs synchronously the instant you call new Promise. Only the settlement (and your .then handlers) is async.
  • If the executor throws, the promise rejects with the thrown value. throw e is equivalent to reject(e) there.
  • Calling resolve or reject more than once, or both, has no effect after the first. The promise is already resolved, even if it's locked onto a promise that's still pending.

The shortcuts

The statics build a promise without an executor: already settled, adopted, or with the resolvers handed to you.

Promise.resolve(42);          // already-fulfilled promise of 42
Promise.reject(new Error('x'));// already-rejected promise
Promise.resolve(otherPromise);// adopts otherPromise's state (no double-wrap)

The two newer statics. They're worth knowing, because “how would you get resolve out of the executor?” is a common warm-up.

  • Promise.withResolvers() (ES2024; Chrome 119, Safari 17.4, Node 22) returns { promise, resolve, reject }. You stop smuggling the resolvers out of the executor by assigning them to outer variables.
  • Promise.try(fn) (ES2025; Chrome 128, Firefox 134, Safari 18.2, Node 23 and so not Node 22) calls fn synchronously and returns a promise either way. A sync throw becomes a rejection instead of escaping. Unlike Promise.resolve().then(fn), it doesn't defer the call by a tick. It's the clean way to wrap a “may be sync, may be async” callback.
const { promise, resolve, reject } = Promise.withResolvers();
socket.once('open', resolve);
socket.once('error', reject);
await promise;

Promise.try(() => maybeSyncMaybeAsync(x))   // sync throw → rejection, not an escape
  .then(use)
  .catch(report);
Subtle but asked: thenables & resolving with a promise Resolving with a promise adopts it; a promise never holds another promise as its value. If you resolve() with another promise (or any "thenable", an object with a .then method), the outer promise doesn't fulfill with that promise as its value. It adopts it: it stays pending until the inner one settles, then takes on its outcome. Separately, Promise.resolve(p) === p for a native promise p. It short-circuits rather than re-wrapping. Adoption is why you can't have a promise that fulfills to another promise. Two details the follow-up probes. A thenable's then is called asynchronously, in its own microtask (the spec's NewPromiseResolveThenableJob). So Promise.resolve(thenable) returns before then has run, and a hostile then method never runs inside your stack, though a then getter still does. Resolving with a native promise costs two extra ticks; a thenable that calls back synchronously costs one. And the Promise.resolve(p) === p short-circuit applies only when p.constructor === Promise: an instance of a Promise subclass is re-wrapped in a base promise.
02 — Composition

Chaining & error propagation

Every .then / .catch / .finally returns a brand-new promise, and what it settles to depends on what your callback does.

How it works. The power is in .then. That one rule unlocks everything. Your callback's outcome decides the new promise's outcome:

Inside the handler you…The returned promise…
return a plain valuefulfills with that value
return a promiseadopts that promise (waits for it, then mirrors it)
throw an errorrejects with that error
return nothingfulfills with undefined

Why it matters. Because a returned promise is adopted, you can flatten async steps into a linear chain. That's the callback-hell fix from section 00.

Errors fall down the chain

A rejection skips every success handler until it hits a .catch, so one trailing catch covers the whole chain.

How it works. A rejection skips every .then success handler until it hits a .catch (or a .then's second argument). Think of it like a synchronous try/catch laid out vertically:

fetchPrice(symbol)
  .then(price => price * qty)      // skipped if fetchPrice rejects
  .then(total => render(total))     // skipped too
  .catch(err => showError(err));    // catches a rejection from ANY step above
  • .catch(fn) is just sugar for .then(undefined, fn).
  • A .catch that doesn't re-throw recovers the chain. The next .then runs with the fulfilled value the catch returned. This is how you supply fallbacks.
  • Placement matters. In .then(a, b), the b reject handler does not catch an error thrown by a, because they're registered on the same promise. A trailing .catch does. Prefer the trailing catch.

.finally — cleanup, transparently

.finally runs on both paths and passes the original outcome through untouched, unless its callback throws.

showSpinner();
loadData()
  .then(render)
  .catch(showError)
  .finally(hideSpinner);   // runs on BOTH paths

How it works. .finally(fn) runs whether the promise fulfilled or rejected. Crucially, it is transparent: it passes the original value/reason straight through. It ignores its callback's return value. But if finally's callback throws or returns a rejecting promise, that does override the outcome.

Two more details. The callback receives no arguments. It can't see the value or the reason, which is the point: it's for cleanup that doesn't care. And finally is transparent to values, not to time. If the callback returns a pending promise, the chain waits for it to settle before the next .then runs, and only then discards its fulfilled value. So .finally(() => flush()) delays everything downstream until flush() completes.

The #1 chaining bug: forgetting to return Inside a .then, if you start an async op but don't return its promise, the chain doesn't wait for it. .then(u => { save(u); }) moves on immediately; .then(u => save(u)) (or return save(u)) waits. Missing returns cause races and swallowed errors.
03 — When callbacks actually run

Promises run on the microtask queue

Promise callbacks are microtasks, and the whole microtask queue drains before the next macrotask or render.

How it works. This is the highest-value section for a senior loop, because it ties promises to the event loop. A resolved promise's .then callback is queued as a microtask. The event loop drains the entire microtask queue after each macrotask (like setTimeout) and before the next one. It also drains it before rendering.

console.log('1');
setTimeout(() => console.log('2'), 0);      // macrotask
Promise.resolve().then(() => console.log('3')); // microtask
console.log('4');
// 1  4  3  2

Example. 3 beats 2 even though the timer is 0ms and was scheduled first. The microtask queue is fully drained before any macrotask runs. Say it as: "it's not about time, it's about queue priority."

  • Each link in a chain is a separate microtask. .then only schedules the next link once the current one runs. Two independent chains therefore interleave tick-by-tick.
  • An endless promise chain (Promise.resolve().then(loop)) starves the loop. It never renders or handles input. Yield with setTimeout when you need to loop.

The precise rule. “After each macrotask” is the simplification. The precise rule (HTML spec, “clean up after running script”) is that a microtask checkpoint runs whenever the JS stack empties, i.e. after every callback. So with two listeners for the same click, promise callbacks queued by the first listener run before the second listener. Dispatch that click from script with el.click() and they run after both, because your script is still on the stack between the listeners.

Node has a second queue. process.nextTick callbacks drain before promise microtasks in a CommonJS script. Inside an ES module, which is itself evaluated as a promise job, promise callbacks run first. Node's own docs show both orders. If an interviewer asks “nextTick or promise first?”, the answer is “depends on whether we're in ESM”.

How many ticks does await cost?

Since V8 7.2 an await on a native promise costs one microtask; a thenable costs two and a promise subclass three.

How it works. This is what the harder drills turn on, and it has a date attached. Since V8 7.2 (Chrome 72, January 2019; Node 12 was the first Node release to carry it, on V8 7.4) an await on a native promise or a plain value costs exactly one microtask. The engine uses the spec's PromiseResolve and takes the promise as-is instead of wrapping it. Before that every await allocated a wrapper promise and cost three. That is why pre-2019 articles quote different drill outputs and call await slow.

The slow path still exists. await on a thenable costs two ticks (the extra then job). await on an instance of a Promise subclass costs three, because only base-class promises skip the wrapping.

You await…Microtasks before the continuationWhy
a native Promise, or a plain value1fast path: PromiseResolve returns it unchanged, one reaction job
a thenable ({ then() {…} })2a job to call then, then the reaction job
an instance of class Sub extends Promise3re-wrapped in a base promise, then resolved through then

The consequence people get backwards. Same mechanism. Inside an async function, return await p is one tick cheaper than return p (measured 2 vs 3 when awaited from outside). Returning a promise resolves the function's promise with a promise, which is the two-tick thenable path. That is why ESLint deprecated its no-return-await rule in v8.46.0.

Say this in the room "Promise callbacks are microtasks. After each macrotask the loop drains all microtasks before rendering or taking the next macrotask — so promises always run before the next timer, and a runaway microtask chain can freeze the UI even though you 'used promises'."
04 — Combining many promises

The four static combinators

The four combinators differ on two axes: do you want all the results or just one, and does a rejection stop everything.

How to learn them. You will be asked to compare these. Learn them as a 2×2: do you want all of them or just one? and does a rejection stop everything or not?

CombinatorFulfills whenRejects whenGives you
Promise.allevery input fulfillsthe first one rejects (fail-fast)array of values, in input order
Promise.allSettledall settle (never rejects)— neverarray of {status, value|reason}
Promise.racethe first to settle fulfillsthe first to settle rejectsthat one settlement
Promise.anythe first to fulfillall reject → AggregateErrorfirst fulfilled value

The distinctions that get probed

all stops at the first rejection, allSettled never rejects, race takes the first settlement, and any takes the first success.

all is fail-fast. The instant one input rejects, all rejects with that reason. But the other operations keep running (promises can't be cancelled); you just stop waiting for them. Any resolved values are lost. A sibling that rejects later is not an unhandled rejection either: all attached handlers to every input up front, so the second failure is swallowed silently.

allSettled never rejects. Use it when you want every result regardless of individual failures, e.g. loading six independent dashboard widgets and showing the five that worked. Each entry is {status:'fulfilled', value} or {status:'rejected', reason}.

race settles on the first to settle, including a rejection. A fast failure wins the race. This is why the classic "timeout" pattern uses race: whichever finishes first, the real fetch or the timeout rejection.

any settles on the first to fulfill, ignoring rejections. Only when they're all rejections does it reject, with an AggregateError collecting every reason. Good for "first mirror/CDN to respond wins." err.errors lists the reasons in input order, not the order they failed. V8's message is All promises were rejected.

Inputs and the empty case. All four accept any iterable and pass each element through Promise.resolve, so plain values and thenables are fine. Given an empty input: all/allSettled fulfill immediately (with []); race stays forever pending; any rejects immediately with an empty AggregateError.

Choosing between them is a question about failure, not about waiting

Each combinator encodes a different answer to “what should a partial failure mean?”

Why reframe. The 2×2 gets you the definitions. The interview follow-up is always a scenario, and the scenario is always about a failure:

If one fails…UseBecause
…the whole operation is meaninglessallRendering a checkout page that needs the cart, the user and the shipping options — two out of three is not a page. Fail fast and show one error.
…the rest is still worth showingallSettledSix independent dashboard widgets. One dead endpoint should degrade one card, not blank the screen.
…you only ever needed one answeranyThree CDN mirrors, or a cache and an origin. Failures are expected and uninteresting until they all fail.
…the first outcome is the outcomeraceA timeout, or a user cancellation racing real work. Note this includes a fast failure winning.

Where it bites. Two consequences are worth stating out loud, because they're where the bugs are. all's fail-fast discards work that succeeded. The other requests still run to completion (nothing is cancelled); you simply throw their results away. So a slow, expensive query whose sibling failed at 10ms was pure waste.

allSettled moves error handling to you. It never rejects, so nothing forces you to look. Code that maps over the results without checking status silently treats failures as missing data. That is worse than a crash, because nobody notices.

The trap in the timeout patternThe withTimeout below is the standard whiteboard answer. It's worth naming what it does not do: losing the race doesn't stop the fetch. The request keeps running, the connection stays open, and the server still does the work. You've stopped waiting, not stopped the operation. The timer also keeps its handle alive until it fires, so a naive version leaks a timer per call. The complete answer pairs the race with an AbortController (or uses AbortSignal.timeout(ms), which handles both) and clears the timeout in a finally.
timeout via race — a pattern you can write on a whiteboard
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error('timed out')), ms));
  return Promise.race([promise, timeout]);
}
await withTimeout(fetch('/orderbook'), 3000);
Parallel vs sequential — the efficiency answer await a(); await b(); runs them one after another (sum of times). If they're independent, start both first, then await together: const [x,y] = await Promise.all([a(), b()]). That runs them concurrently (max of times). Kicking off the calls before awaiting is the whole trick.
05 — Syntax over promises

async / await is promises in disguise

async/await adds no capability; it's syntactic sugar over promises and microtasks.

The equivalences. Naming them shows depth:

  • An async function always returns a promise. return v fulfills it with v; throw e rejects it. Returning a promise adopts it.
  • await p pauses the function until p settles, then evaluates to its fulfilled value. If p rejects, await throws its rejection reason, which you catch with an ordinary try/catch.
  • Code runs synchronously up to the first await; everything after an await is a microtask continuation. So await is never a no-op. Even await 5 yields to the microtask queue.
// the .then chain from section 00, in async/await
async function loadOrders(id) {
  try {
    const user   = await getUser(id);
    const bal    = await getBalance(user);
    const orders = await getOrders(bal);
    return orders;
  } catch (err) {
    handle(err);           // catches a rejection from ANY await
  } finally {
    hideSpinner();
  }
}

The mistakes await makes easy

The usual await bugs are accidental serialisation and loops that never wait.

  • Accidentally sequential. await-ing independent calls in a row serialises them. Await a Promise.all of both instead.
  • await inside forEach does nothing useful. forEach ignores the returned promises, so the loop doesn't wait. Use a for…of loop (sequential) or Promise.all(arr.map(async …)) (parallel).
  • A lone await in a loop over N items is N round-trips back to back. Fine when each depends on the last; a latency bug when they don't.
Common trap 
[1,2,3].forEach(async id => {
  await save(id);          // forEach does NOT await these
});
console.log('done');        // prints BEFORE any save finishes

Async iteration, and the syntax that's landing next

for await pulls one value at a time from an async iterable, and cleans the generator up if the loop exits early.

How it works. for await (const chunk of source) awaits each value in turn. It works over async iterables (async generators, ReadableStream, Node streams) and over sync iterables of promises. An async function*'s next() returns a promise of { value, done }. Array.fromAsync(iterable) (ES2026; Chrome 121, Safari 16.4, Node 22) drains one into an array. If the loop body throws, the loop calls the generator's return() before the error propagates, so its finally runs. If an async generator's yielded promise rejects, the loop does not call return(); the rejection is thrown inside the generator at the yield, so its finally runs that way and the loop then sees the throw.

async function* pages(url) {
  while (url) {
    const res = await fetch(url);
    const body = await res.json();
    yield* body.items;
    url = body.next;
  }
}
for await (const item of pages('/orders')) render(item);   // pulls one page at a time
The eager-promise trap for await over an array of already-started promises is just sequential await. If item 2 rejects while you are still waiting on a slow item 1, that rejection has no handler at the next microtask checkpoint: the browser fires unhandledrejection, and Node 22's default mode crashes the process before the loop ever reaches item 2. Same for const a = f(); const b = g(); await a; await b;. Promises you created eagerly belong in Promise.all or allSettled, which attach handlers to all of them at once.

using / await using (Explicit Resource Management) is the next thing an interviewer may name. A value with a [Symbol.dispose]() or [Symbol.asyncDispose]() method is released when the block exits, even on a throw. Think of a lock, a stream reader, a DB connection. await using awaits the async disposer.

Status as of September 2026: TC39 advanced it to conditional Stage 4 in May 2025, recorded all conditions met in May 2026, and its finished-proposals table slots it into ES2027. It ships in Chrome 134, Firefox 141 and Node 24, while Safari has it only in preview and Node 22 rejects it as a SyntaxError. Say “shipping everywhere but Safari, not yet Baseline” rather than “standard”.

async function withLock(key) {
  await using lock = await locks.acquire(key);   // [Symbol.asyncDispose]() runs on block exit
  return await doWork();
}
06 — Things you'll be asked to write

Real-world patterns

These are the four snippets you'll be asked to write on a whiteboard, and the follow-ups each one invites.

Promisify a callback API

Wrap the callback API in an executor: the error argument goes to reject, the data to resolve.

const readFile = (path) => new Promise((resolve, reject) => {
  fs.readFile(path, 'utf8', (err, data) =>
    err ? reject(err) : resolve(data));
});

Retry with backoff

Retry in a loop, doubling the delay each attempt, and re-throw on the last one.

async function retry(fn, times = 3, delay = 300) {
  for (let i = 0; i < times; i++) {
    try {
      return await fn();
    } catch (err) {
      if (i === times - 1) throw err;      // last attempt: give up
      await new Promise(r => setTimeout(r, delay * 2 ** i)); // backoff
    }
  }
}
What the whiteboard retry leaves out Three things a senior interviewer will ask for. Jitter: with pure exponential backoff every client that failed at the same moment retries at the same moment. The retries arrive as synchronised spikes. AWS's analysis shows “full jitter”, sleep = random(0, min(cap, base * 2 ** attempt)), cut total calls by more than half against a contended service. A cap: 300 * 2 ** 10 is five minutes, so clamp the exponent (a cap of 10–30 s is typical). Retry only what can succeed: most 4xx responses, a validation error or an AbortError will fail identically on every retry. Retry on network errors, 429 and 5xx, and honour Retry-After when the server sends one. 
const wait = Math.random() * Math.min(cap, delay * 2 ** i);   // full jitter
if (!isRetryable(err) || signal?.aborted) throw err;

Cancellation with AbortController

Promises can't be cancelled, but the work behind them can be aborted through an AbortController.

How it works. This is the modern, correct answer to "how do you cancel a fetch?" The controller owns a signal. You pass the signal to fetch and call abort() when the result is no longer wanted:

const ctrl = new AbortController();
fetch('/orderbook', { signal: ctrl.signal })
  .then(r => r.json())
  .catch(err => {
    if (err.name === 'AbortError') return;  // expected on cancel
    throw err;
  });
ctrl.abort();   // e.g. user navigated away / newer request supersedes
The error names, because the catch above depends on them abort() with no argument rejects with a DOMException named AbortError; abort(reason) rejects with whatever you passed. AbortSignal.timeout(ms) (Chrome 124, Firefox 100, Safari 16, Node 17.3) rejects with a TimeoutError, not AbortError. Chrome has had the method since 103, but until 124 its fetch ignored the signal's reason and always rejected with AbortError. So the check above lets a timeout propagate as a failure while swallowing a deliberate cancel, which is usually the behaviour you want. Its clock pauses while the page is in the bfcache. Combining signals. To combine “user cancelled” with “took too long”, AbortSignal.any([ctrl.signal, AbortSignal.timeout(3000)]) (Chrome 116, Safari 17.4, Node 20.3) gives one signal whose reason is whichever fired first. Your own functions. Cancellation is opt-in. Call signal.throwIfAborted() on entry and per loop iteration. If you add an 'abort' listener, remove it when the work settles. A long-lived signal reused across many calls otherwise accumulates listeners.

Concurrency limit (a pool)

A pool keeps a fixed number of workers pulling from a shared queue, so at most limit tasks are in flight.

The question. "Fetch 500 symbols but only 5 in flight at once" is a very common senior follow-up. The idea: keep a worker count, pull from a queue as each finishes.

async function pool(items, worker, limit = 5) {
  const results = [];
  const queue = [...items.entries()];
  async function run() {
    while (queue.length) {
      const [i, item] = queue.shift();
      results[i] = await worker(item);      // preserve order by index
    }
  }
  await Promise.all(Array.from({ length: limit }, run));
  return results;
}
Naming the tradeoff Promise.all(items.map(worker)) fires all requests at once. Simplest, but it can hammer the API and trip rate limits (HTTP 429). A pool caps concurrency at the cost of a little more code. Knowing when to reach for which is the senior signal.

Reading the pool, since you may be asked to defend it

The pool caps concurrency because each of its limit workers loops on the queue; batching would add a barrier per batch.

How it works. The structure is worth understanding rather than memorising. It starts limit workers, and each worker loops pulling the next item until the queue is empty. That's what caps concurrency at exactly limit: there are only ever that many await worker(item) calls in flight. It self-balances, because a worker that gets a fast item simply comes back for another rather than idling. Writing to results[i] by the original index is what keeps the output in input order despite the completion order being arbitrary.

Why not batches. The version people write first chunks into batches of five with Promise.all per batch. It is worse in a specific way worth naming: each batch waits for its slowest member, so four fast requests idle while one slow one finishes. With 100 items and one 3-second outlier per batch, that's dead time repeated 20 times. The pool has no barriers, so a slot frees the instant its item finishes.

Where it bites. Two things it doesn't handle, which is the honest follow-up. A throw from any worker propagates out of Promise.all, so the caller sees a rejection immediately. But the other workers don't stop. Nothing cancels them, so they keep draining the queue in the background, writing into a results array nobody will read. Any later throw is swallowed, because Promise.all already attached handlers to every worker. (Run it: with two workers and item 1 throwing, the caller gets the rejection as soon as item 1 fails, and items 2–5 still complete afterwards.)

The fix. Usually you want a try/catch inside the loop recording failures per item, or an AbortSignal the workers check so a fatal error really does stop the fleet. And there's no backpressure or retry, so a 429 from the API just becomes N failures. In production this is a job for p-limit or similar. Being able to say “I'd write this in an interview and use a library in production” is the right answer to both questions.

What “promises can't be cancelled” really means

A promise is a read handle on a result, not a handle on the work, so there is nothing for it to cancel.

The design reasoning. A promise has no reference to whatever is going to settle it, so there is nothing for a cancel() method to act upon. And if there were, it would be unsound: multiple consumers can attach to one promise, so one of them cancelling would break the others. That's why the platform put cancellation in a separate object (AbortController) held by whoever owns the operation, with the signal passed down to whoever performs it.

The practical consequence. Cancellation is always cooperative. fetch honours a signal; your own new Promise wrapper honours it only if you wire it up. And aborting is best-effort at the far end. The server may already have processed the request, so abort saves your bandwidth and parsing, never the side effect.

07 — The senior signal

Gotchas that separate levels

These seven are where a mid-level answer stops and a senior answer keeps going.

1. Floating promises & unhandled rejections

A floating promise is one nobody awaits or catches; if it rejects, the runtime fires unhandledrejection, and Node crashes by default.

How it works. A promise whose rejection is never handled triggers a global unhandledrejection event (and a console error; in Node it crashes the process by default since v15). Calling an async function and ignoring its result is a "floating promise". If it rejects, nothing catches it.

Browsers. Know the two runtimes' rules separately, because they differ. Browsers fire unhandledrejection on window (a PromiseRejectionEvent with .promise and .reason). event.preventDefault() suppresses the console error. If a handler is attached later, a rejectionhandled event follows.

Node. Node uses a differently-cased event on process, 'unhandledRejection' (plus 'rejectionHandled'). Its --unhandled-rejections flag has five modes: throw (default since v15: emit the event, and if nobody listens raise it as an uncaught exception with exit code 1), strict, warn (the pre-15 default), warn-with-error-code and none. In the default throw mode, merely installing a process.on('unhandledRejection') listener stops the crash (strict still crashes). That is why a logging hook that only logs can silently turn a crashing service into a leaking one.

doAsyncThing();          // floating — a rejection here is unhandled
void doAsyncThing().catch(reportError);  // explicit: handled & intentional

2. Errors inside the executor after resolve

Once the executor has called resolve, a later throw inside it is swallowed.

new Promise((resolve) => {
  resolve(1);
  throw new Error('boom');   // IGNORED — already settled
});

How it works. Once settled, the promise is immutable, so a later throw in the executor is swallowed. Order matters.

3. Returning vs awaiting in try/finally

Inside a try, return await keeps the rejection where catch and finally can see it; a bare return doesn't.

async function f() {
  try {
    return await risky();    // finally can observe/override a rejection
  } finally {
    cleanup();
  }
}

How it works. return await (not bare return risky()) keeps the rejection inside the try, so a surrounding catch/finally handles it correctly. Bare return risky() leaves the try block the instant risky() is called. finally runs before the result is known. The catch never sees the rejection, because the function's own promise merely adopts risky()'s outcome after the block has already exited.

What it costs. Outside a try the two are behaviourally equivalent. And return await is not the slower one. Since the V8 7.2 change it costs one microtask less than returning the promise (2 vs 3, measured) and gives a better async stack trace. That is why ESLint deprecated no-return-await in v8.46.0.

4. .then(f, f) vs .then(f).catch(f)

The second argument of .then cannot catch an error thrown by the first argument.

Why. Covered in §02, worth repeating because it's a favourite. Both handlers in .then(f, f) are registered on the same promise. A trailing .catch can catch the throw. Always prefer the trailing catch.

5. Microtask starvation

An endless microtask chain never lets the queue empty, so the browser never paints.

function loop(){ Promise.resolve().then(loop); }
loop();   // freezes the page — the microtask queue never empties

How it works. The loop fully drains microtasks before rendering, so an ever-growing microtask chain means the browser never paints. Yield with a macrotask (setTimeout) if you must loop.

6. Unhandled rejections, and why they're worse than exceptions

An unhandled rejection is quiet by design: the runtime waits for the microtask queue to drain before it reports one.

How it works. A synchronous throw with no try is loud: it unwinds the stack and you see it. An unhandled rejection is quiet by construction. The promise has settled correctly; it simply has no rejection handler yet, and the runtime can't know whether you're about to attach one. So it waits until the microtask queue drains, then fires unhandledrejection.

Where it bites. The failure mode is a request that died, a spinner that never stops, and only a console error on the user's machine to say why.

// the shapes that produce a floating rejection
somethingAsync();                    // no await, no .catch — fire and forget
promise.then(onOk);                  // handles success only
[a, b].forEach(async x => { await f(x) });  // forEach discards the returned promises

// the global net — report it, don't swallow it
window.addEventListener('unhandledrejection', e => {
  report(e.reason);
  // e.preventDefault() only if you genuinely intend to suppress the log
});

The forEach case. Note it specifically, because it's the one that catches people. forEach ignores its callback's return value, so the async callbacks are started, never awaited, and any rejection floats. for…of with await (sequential) or Promise.all(map(...)) (concurrent) both keep the promises attached.

7. Settle-once is a guarantee you can build on

A promise settles once, and later resolve or reject calls are silent no-ops, which is what makes it safe to hand around.

How it works. Everything after the first resolve or reject is ignored. Subsequent calls are silently no-ops, not errors. That's what makes the promise safe as an interface: a handler attached long after settlement still fires exactly once. It fires asynchronously even then, so a .then on an already-resolved promise never runs synchronously.

Why it's deliberate. A function's callers get consistent timing whether the value was cached or fetched. That is precisely the “don't release Zalgo” problem that plagued callback APIs. And it's why resolve() inside a setTimeout race is harmless: whichever fires first wins and the loser does nothing.

How to sound senior on promises Don't just list .then/.catch. Frame it as a state machine (settle-once, immutable), tie handlers to the microtask queue, compare the combinators by failure mode, and reach for consequences: fail-fast data loss, floating rejections, accidental serialisation, concurrency limits. That framing gets you the level.

Output prediction drills

Predict the output before revealing. Say your reasoning out loud. That's what's scored.

Drill 1 — the classic ordering
console.log('start');
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('promise'));
console.log('end');
start · end · promise · timeout

start/end are synchronous. The stack empties → the microtask queue drains → promise. Only then does the one macrotask (timeout) run, even at 0ms.

Drill 2 — async function ordering
console.log('A');
async function foo(){
  console.log('B');
  await Promise.resolve();
  console.log('C');
}
foo();
console.log('D');
A · B · D · C

foo() runs synchronously to the await (prints B), then suspends and returns control. D prints. Stack empties → the continuation after await runs as a microtask → C.

Drill 3 — chain values & a missing return
Promise.resolve(1)
  .then(x => x + 1)
  .then(x => { x + 1; })     // no return!
  .then(x => console.log(x));
undefined

First .then passes 2 on. The second computes x + 1 but doesn't return, so its promise fulfills with undefined — which is what the third receives. Missing-return bug, made visible.

Drill 4 — Promise.all fail-fast
const p1 = Promise.resolve('ok');
const p2 = Promise.reject('boom');
const p3 = new Promise(r => setTimeout(() => r('late'), 100));
Promise.all([p1, p2, p3])
  .then(v => console.log('then', v))
  .catch(e => console.log('catch', e));
catch boom

all is fail-fast: it rejects the moment p2 rejects, with 'boom', without waiting for p3. p3 still runs to completion in the background — its value is just discarded. Swap in allSettled to keep every result.

Drill 5 — interleaving two chains
Promise.resolve().then(() => console.log('a'))
                 .then(() => console.log('b'));
Promise.resolve().then(() => console.log('c'))
                 .then(() => console.log('d'));
a · c · b · d

Each .then schedules the next link only once the current one runs — one microtask per link. So the first link of each chain runs (a, c), then the second of each (b, d). The chains interleave tick-by-tick.

Drill 6 — await in a loop, timed
async function run(){
  const start = Date.now();
  for (const url of ['/a','/b','/c']) {
    await sleep(100);        // each takes 100ms
  }
  console.log(Date.now() - start);
}
~300

The await inside for…of serialises the three sleeps: 100 + 100 + 100 ≈ 300ms. If they were independent, await Promise.all(urls.map(u => sleep(100))) would finish in ~100ms. This is the sequential-vs-parallel trap.

Drill 7 — the conceptual one
"What's the difference between Promise.all and Promise.allSettled, and when would you pick each?"

all is fail-fast: it fulfills with all values only if every input fulfills, and rejects on the first rejection — so one failure loses every result. allSettled never rejects; it waits for all to settle and hands back a status/value-or-reason for each. Pick all when the operation is all-or-nothing (you can't proceed without every piece — e.g. data needed to render a page). Pick allSettled when failures are independent and you want partial success — e.g. loading several dashboard widgets, rendering the ones that succeeded and flagging the ones that didn't.

Drill 8 — the timeout that didn't cancel
“Your withTimeout wrapper fires after 3s and shows an error, but the server logs still show the request completing. Bug?”
Working as designed — race stops waiting, not working

Losing a Promise.race has no effect on the loser: the fetch is still in flight, the connection is open, and the server finishes the work. A promise is a read handle on a result, not a handle on the operation. To actually stop it I'd pair the race with an AbortController — or just use AbortSignal.timeout(3000), which does both — and clear the timer in a finally, since the naive version also leaks a pending timeout per call.

Drill 9 — the silent failures
const results = await Promise.allSettled(urls.map(fetchJson));
const items = results.map(r => r.value);
render(items);
Failures become undefined and nobody finds out

That's the trade allSettled makes: it never rejects, so nothing forces you to look at status. Rejected entries have no value, so this maps them to undefined and renders holes — worse than a crash, because there's no error and no signal. The fix is to branch on status: keep the fulfilled values, and report or degrade the rejected ones deliberately. Choosing allSettled means accepting responsibility for partial failure, and that's the sentence to say out loud.

Drill 10 — the loop that doesn't wait
items.forEach(async (item) => {
  await save(item);
});
console.log('all saved');
'all saved' prints first, and any rejection floats unhandled

forEach ignores its callback's return value, so it starts every async callback and moves on immediately — there's nothing to await and nothing holding the returned promises, so a failure becomes an unhandled rejection that no try/catch around the loop can catch. Use for (const item of items) await save(item) when order or rate-limiting matters, or await Promise.all(items.map(save)) when they're independent. If they're independent but numerous, cap concurrency with a pool.
