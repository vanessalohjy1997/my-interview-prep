Frontend interview prep

Deploying is not releasing.

Code goes out continuously; exposure is a decision you can reverse in seconds. Flags, canaries and progressive rollout are how you control blast radius — and A/B testing is how you find out whether the change was actually an improvement.

Deploy Flags Experiments Rollback
00 — The distinction the whole topic rests on

Deploy is not release

Deploying is putting code on a server. Releasing is exposing behaviour to users. Conflating them is what makes shipping scary: if every deploy is a release, then every deploy is a decision, and decisions get batched into big risky ones.

Separating them — deploy the code dark, release it with a flag — is the idea that everything else in this guide follows from. It is also the answer that distinguishes a senior candidate: they talk about controlling exposure, not about a deployment pipeline.

Deploy

The build is live on the CDN. Nobody's experience has changed.

Release

A flag turns the behaviour on — for 1% of users, then 10%, then everyone.

Experiment

Two variants run concurrently and are measured against a hypothesis.

Rollback

Flip the flag off. Seconds, not a redeploy.

The opening line“I separate deploy from release. Code goes out continuously behind flags; exposure is a product decision I can reverse in seconds without a pipeline run.”
01 — The frontend-specific mechanics

Shipping the assets

A frontend deploy is mostly a caching problem. The pattern that works is immutable, content-hashed assets plus a never-cached entry document.

ResourceCache-ControlWhy
/static/main.4f3a9c.jspublic, max-age=31536000, immutableThe URL changes when the content does, so it can be cached for a year. max-age does the work; immutable only suppresses revalidation on an explicit user reload, and Chromium never implemented it.
/index.htmlno-cacheIt is the pointer to the current asset URLs. Revalidate every time or users pin themselves to an old build.
/sw.jsno-cacheSame reason, with worse consequences — see the service worker guide.
  • Deploys must be atomic. Upload all new assets before switching the HTML that references them. Doing it the other way round means a window where the document asks for files that do not exist yet.
  • Keep the previous build's assets. A user who loaded the page before the deploy will request a lazy chunk from the old build afterwards. If it is gone, they get a ChunkLoadError and a blank screen. Retain at least one or two previous builds, and catch chunk-load failures in the app to prompt a reload.
  • Invalidate the CDN for the entry document only — the hashed assets never need it.
  • Version the build visibly. Embed the commit SHA in the bundle and report it with every error and analytics event; otherwise you cannot tell which build a bug came from.
Rollback is not symmetric on the frontendYou can re-point the CDN to the previous build in seconds, but users who already loaded the new HTML keep it until it revalidates, and anyone mid-session may hold references to assets from either build. This is exactly why flag-based rollback beats redeploy-based rollback: flipping a flag changes behaviour without changing which files the browser is holding.

Why the frontend is the hard case for rollback

Worth spelling out because it's the part backend-shaped answers miss. On a server, a rollback replaces the running code and the next request gets the old behaviour — the state lives in one place you control. On the frontend, the “running version” is distributed across every open tab, and you cannot reach into them. After a rollback you have users on the new build, users on the old build, and users who will lazily request a chunk from whichever build their HTML pointed at when they loaded it.

That produces a specific failure worth naming: a user loads the app at 10:00, you deploy at 10:05 and prune old assets, they click a route at 10:10 that lazy-loads a chunk — and the URL 404s. The symptom is a ChunkLoadError and a white screen for anyone who left a tab open across a deploy, which on a workday app is a large fraction of your users.

// the standard mitigation: catch it and recover, don't just report it
window.addEventListener('error', e => {
  if (/Loading chunk|ChunkLoadError|dynamically imported module/.test(e.message)) {
    if (!sessionStorage.reloadedForChunk) {      // guard against a reload loop
      sessionStorage.reloadedForChunk = '1';
      location.reload();
    }
  }
});

Better still, treat it as a product moment rather than a crash: detect that a new build exists (poll a version endpoint, or compare the SHA in the HTML) and show an unobtrusive “A new version is available — reload” prompt. Retaining the previous two or three builds' assets is the other half, and it's cheap — hashed files, a CDN, and no invalidation needed.

The number that makes this concreteKeep at least two previous builds live, and expire them on the order of a week rather than an hour — long enough to cover a user who left a tab open over a weekend. The storage cost is trivial next to the failure mode, and it is the single cheapest reliability win in a frontend deploy pipeline.
02 — Ways to limit the blast radius

Release strategies

StrategyHow it worksTrade-off
Big bangEveryone gets the new version at onceSimple; the blast radius is 100% of users, and you find out from Twitter
CanaryA small slice of traffic gets the new version while you watch metricsReal signal from real users; needs routing and per-version monitoring
Blue-greenTwo complete environments; flip traffic from one to the otherInstant rollback by flipping back; you pay for two environments and must handle shared state
Progressive rolloutFlag percentage stepped up 1% → 5% → 25% → 100%, gated on metricsThe default for frontend work; requires flag infrastructure and honest guardrails
Ring / dogfoodInternal users, then beta cohort, then everyoneCatches obvious breakage cheaply; internal users are not representative

Roll back or roll forward? Roll back when the impact is user-visible and the cause is not yet understood — restore known-good first, diagnose after. Roll forward when the fix is small, understood, and rolling back would itself be disruptive (a database migration, for instance). Having a rehearsed answer for both, and a stated preference for rollback under uncertainty, is what interviewers are listening for.

03 — The control plane for exposure

Feature flags

Flags are not all the same thing, and treating them as one is how you end up with hundreds of them. The useful taxonomy:

TypePurposeLifetime
Release toggleHide unfinished work so it can be merged and deployed darkDays to weeks — remove after rollout
Experiment toggleAssign users to variants for an A/B testThe length of the experiment
Ops toggleKill switch — disable an expensive or fragile feature under loadLong-lived, deliberately
Permission toggleEntitlements — beta cohorts, paid tiers, internal toolsPermanent; really product configuration

Where the flag is evaluated matters most

  • Server-side / at the edge — the HTML arrives already reflecting the decision. No flicker, no extra request, and the variant is invisible to users inspecting the bundle. This is the right default for anything above the fold.
  • Client-side SDK — flexible and easy, but the app renders before the flags arrive, so you either flash the wrong variant or block rendering. Also ships the existence of every variant to the browser.
  • Build-time — dead-code eliminated, zero runtime cost, but you cannot change it without a deploy, which forfeits the whole point.
Flags must fail safeIf the flag service is unreachable, what does your code do? The answer must be a deliberate default — normally “off”, meaning the existing behaviour — bootstrapped from a cached or server-rendered value. An app that renders nothing because a flag SDK timed out has turned an availability problem into an outage.

Flag debt is real debt

Every flag is a branch in production and a multiplier on the states you must test. Give release flags an owner and an expiry date, fail the build when one is past it, and delete the flag and the dead branch as part of the rollout — not as a follow-up ticket that never happens.

The multiplier is the part to state numerically: n independent boolean flags describe 2ⁿ possible configurations, and your test suite exercises approximately one of them. Ten flags is a thousand combinations; the incidents come from the pairs nobody imagined interacting. That's the real argument for aggressive removal — not tidiness, but that the tested surface shrinks exponentially relative to the deployed surface.

It's also why the taxonomy above matters operationally. Release toggles are the ones that rot, because their job ends the moment a rollout completes and nothing forces the cleanup. Ops toggles and permission toggles are meant to be permanent and shouldn't be counted as debt at all. A team that reports “we have 300 flags” usually has 20 legitimate ones and 280 finished rollouts nobody deleted.

Where flags belong in the code

// scattered checks: the flag's blast radius is unbounded and removal is a refactor
if (flags.newCheckout) { … } else { … }        // in six components

// one decision at a boundary: removal is deleting a branch and a file
const Checkout = flags.newCheckout ? NewCheckout : LegacyCheckout;

Concentrating the branch at a single boundary — a component swap, a route, a strategy object — is what makes a flag removable in one commit. It also keeps the two implementations honestly separate rather than interleaved, which is the state that makes people afraid to delete either one.

04 — A hypothesis, a unit, and a metric

A/B testing fundamentals

An A/B test is a randomised controlled experiment. The vocabulary is what gets probed:

  • Hypothesis — a directional, falsifiable statement. “Moving the CTA above the fold will increase signups”, not “let us try a new design”.
  • Randomisation unit — usually the user, not the session or the pageview. Randomising per pageview lets one person see both variants, which destroys the comparison and any funnel metric.
  • Assignment must be sticky and deterministic. The standard approach is a hash of user ID plus experiment ID, bucketed into 100 slots — so the same user always lands in the same variant, on any device where they are identified, with no lookup.
  • Control vs variant — the control is the current experience, and it must run concurrently. Comparing this week to last week is not an experiment; it is a seasonality measurement.
  • Primary metric — one metric, chosen before launch. Guardrail metrics — things that must not get worse: error rate, latency, Core Web Vitals, revenue, support contacts.
  • MDE and sample size — the minimum detectable effect is the smallest change you want to be able to detect at a stated significance level and power (conventionally α = 0.05 and 80% power). It determines how much traffic you need, and the requirement grows roughly with the square of how small an effect you want to detect: halving the MDE roughly quadruples the sample.
  • Significance — a p-value below your threshold means the observed difference is unlikely under the null hypothesis. It does not tell you the effect is large, nor that it will persist.
// deterministic, sticky bucketing
function variantFor(userId, experimentId, split = 50) {
  const bucket = hash32(`${experimentId}:${userId}`) % 100;
  return bucket < split ? 'control' : 'treatment';
}
PeekingChecking results daily and stopping as soon as you see significance dramatically inflates the false-positive rate — with enough looks, almost any test crosses the line eventually. Either fix the horizon in advance from your sample-size calculation, or use a method designed for continuous monitoring (sequential testing, always-valid confidence intervals, or a bandit).

Why most frontend A/B tests can't work — and what to say about it

This is the answer that separates someone who has run experiments from someone who has read about them. Sample size is driven by baseline rate and effect size, and the numbers are much larger than people expect. Detecting a relative lift of 5% on a 3% conversion rate at α = 0.05 and 80% power needs on the order of 100,000 users per arm. At 5,000 visitors a day split two ways, that's over a month — during which you can't ship anything else to that surface.

So the honest position, and a strong thing to volunteer: most teams don't have the traffic to A/B test most changes. What follows from that is a set of alternatives rather than a shrug:

  • Test bigger changes. A redesign that might move a metric 20% is detectable in a week; a button colour that might move it 1% is not detectable at all at your traffic. Reserve experiments for changes whose expected effect exceeds your MDE.
  • Move up the funnel. Measure a higher-frequency proxy — click-through on the CTA rather than completed purchase — accepting that it's a weaker signal in exchange for a vastly smaller sample requirement.
  • Use a progressive rollout with guardrails instead. If you can't prove an improvement, you can still prove you haven't broken anything: ship at 1%, watch error rate, latency and vitals, and step up. That's a release-safety mechanism, not an experiment, and calling it what it is matters.
  • Reduce variance rather than increasing traffic. CUPED and similar techniques use pre-experiment data to cut the noise, which can meaningfully shorten a test — worth naming if the conversation gets statistical.
The framing that lands“Before designing the test I'd work out the minimum detectable effect at our traffic. If the change we're proposing plausibly moves the metric less than that, an A/B test can't answer the question — and I'd rather say so than run a four-week test that ends in a non-result everyone interprets as they like.”
05 — Where the frontend engineering actually lives

Implementing a test

The flicker problem

Assign on the client and the sequence is: render control → fetch assignment → re-render treatment. The user sees a flash of the original content, and if the variants differ in size you have also caused layout shift. Three ways out, in order of preference:

  1. Decide on the server or at the edge. Read or set the assignment cookie, render the right variant into the HTML. No flicker, no CLS, no extra round trip.
  2. Bootstrap the assignment into the initial HTML even if the SDK runs client-side, so the first render is already correct.
  3. Anti-flicker snippet — a blocking script that hides the body until assignment resolves. It works, and it directly damages LCP. Treat it as a last resort with a hard timeout, not a default.

Experiments and caching fight each other

A CDN that caches one HTML response for everyone cannot serve two variants. Your options: make the assignment part of the cache key (vary on the bucket cookie — this doubles the number of cached objects and so roughly doubles origin fetches, which is negligible on a high-traffic page and painful on a long-tail one), run assignment at the edge so the origin stays cacheable, or keep the experiment entirely below the fold and hydrate it client-side. Getting this wrong produces the worst outcome — a cached variant served to everyone, so both arms are contaminated and the test measures nothing.

Fire an exposure event

// log the assignment where the user could actually SEE it
useEffect(() => {
  track('experiment_exposure', { experiment: 'cta_position', variant, userId });
}, [variant]);

Analysis must be based on users who were exposed, not on everyone who was assigned. If the variant only appears on the checkout page, including users who never reached checkout dilutes the effect toward zero and can hide a real win. Equally, fire the event on render — not on interaction, which would only ever log people who engaged.

The senior caveat on exposure filteringThis only holds if the exposure condition is independent of the variant. If the treatment itself changes who gets exposed — say it changes how many users reach checkout at all — then filtering on exposure is a post-treatment filter, which breaks randomisation and reintroduces selection bias. The fix is counterfactual or triggered analysis: restrict to users who would have triggered in either arm, using pre-treatment attributes.
06 — What you look at, and for how long

Measuring it

  • Run for at least one full business cycle — a week, usually — so weekday and weekend behaviour are both represented in both arms.
  • Watch for novelty and primacy effects. Regular users react to change itself: a new button gets clicked because it is new. If the effect decays over the run, the lift was novelty. Conversely, power users may be temporarily slower with a changed interface.
  • Check sample ratio mismatch first. If you split 50/50 and observe 52/48 with large traffic, something is broken — a bot filter, a redirect, an SDK failing in one arm — and no result from that test is trustworthy. SRM is the first thing a good analyst checks and a great thing to mention unprompted.
  • Segment cautiously. Slicing until something is significant is p-hacking with extra steps. Pre-register the segments you care about.
  • Guardrails are not optional. A variant that lifts conversion 2% while adding 400 ms to LCP and doubling the JS error rate is not a win.
  • Keep a holdout. A small group excluded from new releases lets you measure the cumulative effect of everything shipped over a quarter, which is often surprisingly different from the sum of the individual wins. Time-box and rotate it — a permanent holdout accumulates a badly degraded experience and stops being representative of anyone.
Shipping the resultWhen a test wins, the work is not done: remove the losing branch and the flag, and re-baseline your metrics. A codebase where every past experiment is still branching is unmaintainable and quietly slows every future test.
07 — Knowing before your users tell you

Release safety

  • Client-side error monitoring — Sentry or equivalent, with the release SHA attached and source maps uploaded privately so stack traces are readable without exposing your source publicly.
  • Real-user monitoring — Core Web Vitals and custom timings from the field, segmented by release, so a regression shows up as a step change at the deploy boundary.
  • Automatic gates. A progressive rollout should pause or revert itself when error rate or latency crosses a threshold. A rollout that requires a human watching a dashboard is a rollout that ships regressions overnight.
  • Smoke tests after deploy — a handful of end-to-end checks against production on the critical path. They catch environment problems unit tests structurally cannot.
  • A kill switch for anything expensive or external — a third-party widget, a new recommendation service, an animation you are unsure about.
The line that lands“My rollback plan is a flag flip, my detection is field metrics segmented by release, and my rollout is automated to stop itself. The goal is that a bad change costs minutes and a fraction of a percent of users, not a war room.”

09 — Drill until reflex

Scenario drills

Drill 1 — how do you release a risky redesign?
“A checkout redesign. Walk me through getting it to 100% of users.”

Separate deploy from release. Merge behind a release flag defaulted off and deploy continuously so the code is never a big-bang merge. Evaluate the flag server-side so there is no flicker on a conversion-critical page. Enable for internal users, then 1%, watching guardrails — JS error rate, LCP and INP, checkout completion — with the rollout gated to pause automatically on regression. Step to 5, 25, 50, 100 over days, keeping a control arm long enough to measure the conversion effect rather than assuming it. Then delete the flag and the old branch.

Drill 2 — the flash
“Our A/B tool makes the page visibly flash the old layout before the variant appears. Fix it.”

That is client-side assignment: the page renders control, the SDK resolves, and the app re-renders. Move the decision earlier. Best is server-side or edge assignment — read or set the bucket cookie and render the correct variant into the HTML. If the SDK must stay client-side, bootstrap the resolved assignment into the initial HTML so the first render is already right. The anti-flicker snippet that hides the body is a last resort: it converts a visual glitch into an LCP regression, and it damages the very metric the experiment is measuring.

Drill 3 — is this result real?
“A test shows +8% signups, p = 0.04, after 3 days. Ship it?”

Not yet. Check, in order: SRM — is the observed split the configured one? Duration — three days is under a business cycle, so weekday and weekend mixes differ between arms. Peeking — was this the first look, or the fourth? Repeated checks inflate false positives, so p = 0.04 on day three means much less than it appears. Power — was the sample size planned from an MDE, and is +8% plausible or suspiciously large for the change? Guardrails — did latency, errors, or downstream conversion move? Novelty — is the effect decaying day over day? A single p-value is the least informative number in that list.

Drill 4 — spot the design flaw
const variant = Math.random() < 0.5 ? 'A' : 'B';
renderCheckout(variant);
track('conversion', { variant });
Randomised per pageview, not per user; no sticky assignment

Assignment is random per page load, so the same user sees different variants across pages and even across reloads — funnel metrics are meaningless and the arms are contaminated. It is also not persisted, so nothing can be reconciled later, and there is no exposure event distinct from conversion. Fix: bucket deterministically from a stable identifier, hash(experimentId + userId) % 100, persist it in a cookie for anonymous users, and log an exposure event when the variant is actually rendered.

Drill 5 — the CDN and the experiment
“Our HTML is cached at the edge for 10 minutes. Marketing wants an above-the-fold headline test. What do you tell them?”

As it stands the test cannot work: one cached response is served to everyone, so both arms see the same headline and the experiment measures nothing. Three options. 1) Assign at the edge — a worker reads or sets the bucket cookie and serves the matching cached variant, keeping the origin cacheable. 2) Add the bucket cookie to the cache key — correct, but it doubles the number of cached objects and therefore roughly doubles origin fetches (barely noticeable at high traffic, costly on long-tail pages). 3) Move the test below the fold and hydrate it client-side, which avoids the caching problem at the cost of flicker risk. For an above-the-fold headline, edge assignment is the right answer.

Drill 1 — white screens after a deploy
“Every deploy, a handful of users report a blank page until they hard-refresh. What's happening?”
ChunkLoadError — old HTML asking for pruned assets

Users who loaded the app before the deploy are holding the previous build's HTML, which references the previous build's chunk URLs. When they navigate to a lazily-loaded route afterwards, that chunk has been deleted and the request 404s. Two fixes, and I'd do both: retain the last two or three builds' hashed assets for about a week — they're immutable, so it costs storage and nothing else — and catch chunk-load failures in the app, with a sessionStorage guard against a reload loop. Better than an automatic reload is detecting the new build's SHA and offering “a new version is available”, since a silent reload can lose form input.

Drill 2 — the test that can't win
“Product wants to A/B test a new CTA colour. The site gets 5,000 visitors a day and converts at 3%. What do you say?”

That the maths doesn't support it, before anyone builds anything. Detecting a 5% relative lift on a 3% baseline at 80% power needs roughly 100,000 users per arm — at 2,500 per arm per day that's over a month, and a colour change plausibly moves conversion far less than 5%, so the real requirement is larger still. I'd offer three alternatives: test something with a big enough expected effect to be detectable; measure a higher-frequency proxy like CTA click-through, accepting the weaker signal; or drop the experiment framing and do a guarded progressive rollout, which proves we haven't broken anything even though it can't prove an improvement. What I'd avoid is running it anyway and calling a non-result whatever we wanted it to be.

Drill 3 — the numbers don't add up
“Your 50/50 experiment shows 53% / 47% after 200,000 users. Do you read the results?”
No — that's a sample ratio mismatch, and it invalidates the test

At that volume a 53/47 split is far outside chance, so something systematic is dropping or misassigning users — and whatever it is, it's almost certainly correlated with something that affects the metric. Typical causes: an SDK error that fails in one arm and defaults the user to the other, a redirect or CDN cache serving one variant, bot traffic filtered asymmetrically, or exposure events failing to fire in one arm. I'd check the assignment hash distribution, compare exposure counts against assignment counts per arm, and look at bot filtering before reading a single conversion number. SRM is the first thing to check and the reason to check it is that no amount of significance rescues a broken randomisation.

Drill 4 — flicker
“Users see the old headline flash before the new one. Why is that worse than an aesthetic problem?”

Because it biases the metric you're measuring. The treatment group experiences a flash and a layout shift that the control group doesn't, so the two arms now differ by more than the change under test — you're measuring your variant plus a worse experience, which pushes results toward null or negative. It also damages CLS specifically for one arm, which contaminates any performance guardrail. The fix in order of preference: decide at the edge or on the server so the HTML arrives correct; bootstrap the assignment into the initial HTML if the SDK is client-side; and only as a last resort an anti-flicker snippet with a hard timeout, accepting that it directly damages LCP for everyone.
