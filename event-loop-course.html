How JavaScript does many things at once with one thread.

The event loop is the answer to a paradox: JavaScript runs on a single thread, yet it never blocks on a network call, a timer, or a click. This course builds the model from the ground up — then makes you predict output until it's reflex.

00 — The mental model

Why the event loop has to exist

The event loop exists so single-threaded JS can wait for slow things without freezing the page.

  • JS runs one thing at a time, on one call stack.
  • fetch(), timers and clicks take an unknown amount of time.
  • Waiting on the main thread would freeze the tab: no scrolling, no clicks, no repaints.

How it works. JS doesn't wait. It hands slow work to the host (the browser or Node), which does the waiting off the main thread. When the work finishes, the host drops your callback into a queue. The event loop checks that queue every time the call stack is empty, and runs the next callback. So “later” in async JS means “the next time the stack is free”, not a fixed delay.

Example. setTimeout(fn, 0) doesn't run fn immediately. It queues fn, and fn runs only after the current code finishes. If that code takes 200ms, fn waits 200ms.

Where it bites. A callback can only run when the stack is empty. A long synchronous loop blocks every callback behind it, including clicks and fetch results. That's why a heavy calculation on the main thread freezes the UI even though “it's async”.

What's actually in the room

“The JavaScript engine” does not do everything. The engine and the host are distinct pieces.

PieceWho owns itJob
Call stackEngine (V8)Runs your synchronous code, one frame at a time.
HeapEngine (V8)Where objects live.
Web APIs / libuvHost (browser / Node)Timers, network, DOM events, file I/O — the actual waiting.

The senior insight. The engine (V8) does not contain the event loop or setTimeout. The host provides both. V8 just runs whatever is on the stack. That is why the same JS behaves differently in a browser and in Node: different host, different queues, different timing.

The follow-up. The microtask queue is the one piece the engine does own. Promise jobs and queueMicrotask go into V8's queue. The host only decides when to run the checkpoint that drains it. Node's docs say it outright: the microtask queue “is managed by V8”, while the process.nextTick queue “is managed by Node.js”.

Say this. Stack and microtask queue are engine. Task queues, timers, I/O and rendering are host.

01 — Synchronous execution

The call stack

The call stack is where synchronous code runs, and a task runs uninterrupted until the stack is empty.

How it works. The call stack is a LIFO stack of frames. Calling a function pushes a frame. Returning pops it. Nothing asynchronous happens while there are frames on the stack. That is the whole point of “run-to-completion”.

// each call pushes a frame; each return pops one
function third(){ return 3; }
function second(){ return third() + 2; }
function first(){ return second() + 1; }
first();
// stack grows: first → second → third, then unwinds

Where it bites. Two consequences matter for interviews:

  • Blocking is real. A while(true){} or a heavy synchronous loop keeps the stack busy. So no queued callback can run: not a click handler, not a timer. The page is frozen because the loop can't take anything off a queue while the stack is occupied.
  • Stack overflow is just the stack exceeding its size limit, usually from unbounded recursion. It has nothing to do with the queues.
Say this in the room "The event loop can only move a callback onto the stack when the stack is empty. So async isn't about doing two things at once — it's about interleaving work between run-to-completion tasks."
02 — The algorithm

The loop, as an algorithm

The event loop is a tiny, endless routine: one macrotask, then every microtask, then maybe a render.

How it works. Strip away the jargon and here it is in the browser, close to how the HTML spec frames it:

while (true) {
  task = macrotaskQueue.pop()        // take ONE macrotask
  run(task)                           // run it to completion

  while (microtaskQueue.length)       // drain ALL microtasks
    run(microtaskQueue.pop())         // (including ones added while draining)

  if (needsRender)
    render()                          // rAF callbacks, style, layout, paint
}

Read it carefully. Almost every trick question lives inside it:

  1. Take exactly one macrotask and run it to completion.
  2. Then drain the entire microtask queue. Not one, all of them, including any that get added while you're draining.
  3. Then, if it's time, the browser may render.
  4. Repeat.
Read the if (needsRender) honestly Rendering is not a step after every task. The HTML spec calls it a rendering opportunity, decided by “hardware refresh rate constraints and user agent throttling”. So at 60Hz the browser runs as many tasks as it can in ~16.7ms and paints once. The guarantee is only one-directional: a paint can never happen inside a task or between a task and its microtasks. It can, and usually does, skip many task boundaries.
The single most tested fact Between two macrotasks, the microtask queue is emptied completely. A macrotask can only run once there are zero microtasks left. This is why a promise scheduled after a setTimeout still runs first.
03 — Two queues, two priorities

Macrotasks vs microtasks

There are two queues, and the difference in when they drain is the entire game.

PropertyMacrotask (task)Microtask
SourcessetTimeout, setInterval, setImmediate (Node), I/O, UI events, postMessage / MessageChannel, scheduler.postTask.then/.catch/.finally, await continuations, queueMicrotask, MutationObserver
How many run per loop turnOne (browser). Node runs every due callback in the phase.All of them (queue fully drained)
Can it delay rendering?Not indefinitely — render comes next, but a long one delays the frameYes — render waits until the queue is empty
PriorityLowerHigher (always drained before the next macrotask)

Two details in the microtask column. A follow-up will reach for either one.

  • MutationObserver is a microtask, but a coalesced one. The DOM spec keeps a single “mutation observer microtask queued” flag per agent. So a thousand synchronous DOM writes queue one microtask, and your callback receives all the records in one batch. It is not one callback per mutation.
  • queueMicrotask is not just sugar for Promise.resolve().then. An exception thrown inside it is reported as an ordinary uncaught error. The promise version turns it into an unhandled rejection. And queueMicrotask skips allocating a promise at all.

Say this. A microtask is “finish this before doing anything else”; a macrotask is “get to it on the next turn.” Promises resolve via microtasks precisely so a chain of .thens completes as one coherent unit before the browser does timers or repaints.

Why two queues exist at all

Microtasks exist so a promise chain can run as an atomic unit, with nothing else interleaving.

The problem. This is the “why” behind the table, and it's a genuinely good design story. Before promises, async callbacks were all macrotasks. That created a real problem: state could change underneath you between scheduling a callback and running it. Another task could run in between and mutate the world your callback assumed: a click handler, a timer, a network callback.

How it works. Microtasks close that window. The queue is drained completely before the next macrotask and before rendering. So a promise chain runs as an atomic unit with respect to everything else in the page. No user event, no timer and no repaint can interleave into the middle of it. That guarantee makes .then chains safe to reason about, and it's why await continuations are microtasks rather than tasks.

What it costs. The price is exactly the starvation problem in §08: a queue that must be fully drained is a queue you can fill forever. The design trades “can't be interrupted” for “can't be escaped”. Knowing that both sides come from the same decision is what makes the answer sound considered rather than memorised.

Where each queue comes from — engine vs host

The JavaScript engine (V8) provides none of this. Timers, events, I/O and rendering all come from the host.

How it works. This is a distinction interviewers use to separate levels. The spec defines a job queue for promises. But setTimeout, setInterval, DOM events, I/O and the render step are all supplied by the host environment: the browser or Node. That's why the same language has a different event loop in each. One has a render step and animation frames. The other has phases and setImmediate. And it's why setTimeout is not in the ECMAScript specification at all.

The canonical warm-up
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// 1  4  3  2   — identical in every browser and in Node

Example. 1 and 4 are synchronous. When the stack empties, the loop drains microtasks. So 3 (the promise) beats 2 (the timer), even though the timer was scheduled first and set to 0ms. Watch it happen in the simulator below.

05 — The part people fake

      
async / await is just promises + microtasks

      
async/await adds nothing new. It is syntax over promises, and the trick is knowing exactly where it yields. The rule:

      

        The await rule
        Code runs synchronously up to the first await. At await, the function pauses and returns control to its caller. Everything after the await is scheduled as a microtask that runs once the awaited value settles.
      

      
So this:

      
async function f(){
  console.log('a');
  await something;
  console.log('b');   // ← this line is a microtask continuation
}

      
is roughly equivalent to:

      
function f(){
  console.log('a');
  return Promise.resolve(something).then(() => {
    console.log('b');
  });
}

      
Example. That's why in the async / await simulator example, console.log('C') (after the await) doesn't run inline. It waits in the microtask queue while the rest of the synchronous script finishes.

      
The follow-up. A senior interviewer will often push here: “So how many microtask ticks does one await cost?” Modern engines: one tick per await on a native resolved promise. An older spec made it three; that was optimised away.

      

        Common trap
        await on a non-promise value (e.g. await 5) still yields to the microtask queue. await is never a no-op, even when the value is already available.
      

      
The one-tick rule, and the exception that breaks it

      
“One microtask tick per await” holds for a native promise. A thenable costs more.

      
How it works. The exception is worth carrying because it's both a real performance footgun and a favourite follow-up. Awaiting a thenable costs extra ticks. A thenable is anything with a .then method that isn't a native promise. The spec has to wrap it and call its then asynchronously. Subclasses of Promise take a slower path still, because await only skips the wrapping when the value's constructor is exactly Promise.

      
Numbers. Measured on Node 22 (V8), and worth saying out loud: a plain value or a native promise costs 1 tick, a thenable 2, a Promise subclass 3. The 3-to-1 change for native promises landed in V8 v7.2 (Chrome 72, Node 12). That is when the spec was fixed to stop allocating two throwaway promises per await.

      
Where it bites. In ordinary application code you'll never notice. In a hot loop, or in code whose whole purpose is demonstrating ordering, it silently changes the answer.

      
// sequential — each await waits for the previous. 3 seconds.
const a = await fetchA();   // 1s
const b = await fetchB();   // 1s — didn't need a
const c = await fetchC();   // 1s — didn't need b

// concurrent — start all three, then wait. 1 second.
const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()]);   // 1s

      
Where it bites. This is the most valuable practical consequence of the await rule. It's the version of the question that shows up as a real bug rather than a puzzle. await in a loop has the same shape: for (const id of ids) await load(id) is N sequential round trips, where Promise.all(ids.map(load)) is one.

      
The counter-case. Sequential is correct when each call genuinely needs the previous result. It is also right when you must not hammer a rate-limited API, or when you need to stop at the first failure rather than firing everything.

      
The async-function detail people missAn async function always returns a promise, and it always starts running synchronously. The body executes up to the first await before control returns to the caller. So an async function with no await runs entirely synchronously and merely wraps its result. Two consequences. A throw before the first await still becomes a rejection rather than a synchronous throw. And calling an async function without awaiting it starts the work immediately, which is how you deliberately kick off concurrent requests before awaiting them.

    


    
    

      
06 — Where the pixels happen

      
Rendering & requestAnimationFrame

      
The browser can only paint between macrotasks, after microtasks are drained.

      
How it works. The browser wants to paint at the display's refresh rate (usually ~60fps → every ~16.7ms). But it can only render between macrotasks, after microtasks are drained. So the real cycle is closer to:

      
one macrotask
  → drain all microtasks
  → requestAnimationFrame callbacks   // run just before paint
  → style → layout → paint
→ back to the next macrotask

      
Where it bites. Practical implications you can name:

      
    
        
  • requestAnimationFrame callbacks fire right before the browser paints. That is why it's the correct place for visual/animation updates, not setTimeout.
    • 
        
  • The spec's order inside “update the rendering” is worth knowing exactly, because it decides what you can read where: resize and scroll events → media-query changes → animation events → rAF callbacks → style and layout → ResizeObserver callbacks (looping if they change layout) → IntersectionObserver → paint. So a rAF callback runs before style and layout, and reading offsetHeight there forces a synchronous layout. A ResizeObserver callback runs after layout and gets the fresh numbers for free.
    • 
        
  • A flood of microtasks can starve rendering. If a promise chain keeps queuing more microtasks, the loop never reaches the render step. The UI locks up even though you “used promises.”
    • 
        
  • A long macrotask (heavy synchronous work in one handler) blocks the very next paint. This is what “jank” usually is. Break work into chunks across tasks, or move it to a Web Worker.
    • 
      

      
The numbers that make this concrete

      
You get 16.7ms per frame at 60Hz, and a missed frame is dropped, not delayed.

      
Numbers. At 60Hz you have 16.7ms per frame. After the browser's own style, layout, paint and compositing work, realistically about 10ms of main-thread budget is left. On a 120Hz phone it halves to 8.3ms. Miss the deadline and the frame is dropped, not delayed: the user sees a stutter.

      
Why 50ms. That's the whole reason a “long task” is defined as >50ms. By then you've missed roughly three frames and the page feels stuck. The precise definition, from the Long Tasks spec, is a task plus the microtask checkpoint that follows it, or a rendering update, exceeding 50ms. The number comes from RAIL's 100ms response budget: 50ms to finish whatever is running when the input arrives, 50ms to handle the input.

      
Where it bites. The rendering step is not a suggestion the loop can defer politely. It's a slot that either happens or is missed. Anything that keeps the loop busy removes that slot entirely: a long task, or an unbounded microtask queue.

      
rAF versus setTimeout, and why it isn't a style preference

      
rAF is synchronised to the paint and a timer is not. The difference is visible on screen, not a matter of style.

      
    
        
  • requestAnimationFrame is synchronised to the paint: the callback runs immediately before style and layout, so a mutation made there is rendered in this frame with no intermediate state. A setTimeout(fn, 16) drifts against the refresh clock, so some frames get two updates and some get none. That shows as uneven motion even at the same average rate.
    • 
        
  • rAF pauses in a background tab, where timers merely throttle. That's the right behaviour for animation (nothing is visible) and the wrong behaviour for a data buffer you flush per frame. A backgrounded tab will queue forever unless you cap it or flush on visibilitychange.
    • 
        
  • rAF runs once per frame regardless of how often you schedule it. That is what makes “buffer events, flush in rAF” the standard fix for a handler firing hundreds of times a second.
    • 
      

      
Two related APIs. requestIdleCallback runs when the browser has spare time in a frame. It is good for logging, prefetching and analytics, never for anything the user is waiting on. scheduler.yield() lets you break a long task into pieces while keeping your place in the queue, with a setTimeout(…, 0) fallback where it isn't available.

      
How it works. Know the difference and the shipping status, because “just use setTimeout(0)” is the answer that gets the follow-up. A setTimeout(0) continuation goes to the back of the task queue, behind every click and fetch callback that arrived meanwhile. await scheduler.yield() puts the continuation at the front of its priority level. So the browser can paint and handle input, but your work resumes before other same-priority tasks start. scheduler.postTask(fn, {priority}) is the general form, with user-blocking, user-visible (default) and background.

      
Shipping status. As of September 2026: postTask is in Chrome/Edge 94+ and Firefox 142+ (August 2025). yield() is in Chrome/Edge 129+ (September 2024) and Firefox 142+. Safari has neither through 27.x, so neither is Baseline and the fallback is still required.

    


    
    

      
07 — Same idea, different host

      
Node.js: phases, nextTick, setImmediate

      
Node runs the loop in phases, and adds a process.nextTick queue that drains before even promises.

      
How it works. Node uses libuv and runs the loop in phases, each with its own macrotask queue. Simplified order per iteration:

      
    
        
  1. timers — setTimeout / setInterval callbacks whose time is due.
    2. 
        
  2. pending callbacks — certain deferred system callbacks.
    3. 
        
  3. poll — retrieve new I/O events; run I/O callbacks.
    4. 
        
  4. check — setImmediate callbacks.
    5. 
        
  5. close callbacks — e.g. socket.on('close').
    6. 
      

      
The part that trips people up. Microtasks run between phases and between each callback. That has been true since Node 11; before that, Node drained the whole timers list and only then ran microtasks. So in 2018 promise ordering inside timer callbacks actually changed. And Node has an extra, even-higher-priority queue:

      

        
QueuePriorityDrained when

        
process.nextTickHighestAfter the current operation, before the promise microtask queue

        
Promise microtasksHighAfter nextTick drains, before moving to the next phase

        
Phase macrotasksNormalIn their phase

      

      
Say this. In Node the priority is process.nextTick → promises → then the next phase's tasks.

      

        The ESM exception
        That ordering holds in CommonJS and inside any callback. At the top level of an ES module it flips. Module evaluation itself runs as part of the microtask queue, so a Promise.resolve().then or queueMicrotask registered there fires before a process.nextTick registered next to it. Node's docs call this out, and it reproduces on Node 22: the same three lines print nextTick · promise in a .cjs file and promise · nextTick in a .mjs file. Node's own advice is to prefer queueMicrotask in userland for exactly this portability reason.
      

      

        Classic Node question
        setTimeout(fn, 0) vs setImmediate(fn) at the top level is non-deterministic in order. It depends on how fast the loop reaches the timers phase. The mechanism: Node floors every setTimeout delay below 1 to 1ms, so the order depends on whether process start-up has already burned that millisecond when the timers phase is first checked. On a warm machine setImmediate usually wins (39 of 40 runs on Node 22 here). But “usually” is the answer, not “always”. Inside an I/O callback, though, setImmediate always fires first. After the poll phase, the check phase (setImmediate) comes before the loop wraps back to timers.
      

      

        Say this
        "Recursive process.nextTick can starve the event loop entirely — it keeps draining before Node ever advances to I/O. It's why setImmediate is usually the safer 'run this soon' choice in Node."
      

      
Two more Node-versus-browser differences an interviewer may test:

      
    
        
  • Node has no nesting clamp on timers. A recursive setTimeout(fn, 0) chain keeps ticking at the 1ms floor (about 1.2ms per hop measured on Node 22), where a browser slows it to 4ms.
    • 
        
  • Node has no render step at all, so “microtasks block painting” is meaningless there. The equivalent harm is starving I/O.
    • 
      

    


    
    

      
08 — The senior signal

      
Gotchas that separate levels


      
1. setTimeout(fn, 0) is not 0ms

      
The delay is a minimum, not a guarantee.

      
How it works. The callback only runs after the stack is empty and all microtasks are drained. Browsers also clamp nested timers to a minimum: 4ms once the nesting level exceeds 5, i.e. from the sixth timer in a setTimeout-inside-setTimeout chain. Background tabs throttle timers hard. Node has no nesting clamp but floors every delay at 1ms.


      
2. Microtask starvation

      
// this freezes the page — the microtask queue never empties
function loop(){ Promise.resolve().then(loop); }
loop();

      
An ever-growing microtask queue means the browser never paints.

      
How it works. The loop always fully drains microtasks before rendering or running a macrotask. A microtask that queues another microtask never lets the queue empty. Contrast with setTimeout(loop, 0), which yields between turns and keeps the page alive (if choppy).


      
3. Order within a promise chain

      
Promise.resolve()
  .then(() => console.log('a'))
  .then(() => console.log('b'));
Promise.resolve()
  .then(() => console.log('c'))
  .then(() => console.log('d'));
// a  c  b  d

      
Two promise chains interleave, one link at a time.

      
How it works. Each .then only schedules the next link once the current one runs. So the two chains interleave. The first .then of each runs (a, c), then the second of each (b, d). This “one tick per link” behaviour is a favourite.


      
4. The loop can't interrupt a task

      
A click that arrives mid-task doesn't preempt anything. Its handler is queued as a macrotask and waits its turn. There's no interruption, only interleaving between tasks.

      
5. Why the timer clamps exist

      
The clamps are a defence against a page burning a core, and the exact numbers differ by browser, nesting level and tab visibility.

      
The nesting clamp. The 4ms floor past five levels of nesting isn't arbitrary. It's a defence against a page burning a core with a setTimeout(fn, 0) recursion, standardised because every browser had shipped some version of it. The exact rule in the HTML spec: if the nesting level is greater than 5 and the timeout is under 4ms, set it to 4ms. Chromium implements that literally (its constant is 6 because it counts from 1). WebKit is more generous and only clamps one-shot timers from nesting level 10, repeating ones from 5. Chrome experimented in 2022 with raising the threshold to 15 and even 100, but current Chromium source is back at the spec value.

      
The first-level clamp. This is the part that went stale. Chrome and Safari historically rounded setTimeout(fn, 0) up to 1ms. Chrome removed that for setTimeout in 2022 and for setInterval in Chrome 135 (2025). Firefox never had it, and WebKit still keeps a 1ms floor for repeating timers only. So “a zero timer is really 1ms” is now wrong in the browser, and still true in Node, whose docs floor any delay below 1 to 1.

      
Background tabs. These go much further, and the numbers are specific. Chrome throttles a hidden page's timers to once per second. Since Chrome 88 (2021) it applies intensive throttling, once per minute, when all of these hold: the page has been hidden for more than 5 minutes, the timer chain is at nesting 5 or deeper, the page has been silent for 30 seconds and no WebRTC connection is open. Since Chrome 133 (2025), under Energy Saver, a tab that has been hidden and silent for over 5 minutes and is still burning CPU can be frozen outright: no timers at all until it is foregrounded. Firefox desktop clamps hidden tabs to 1 second and Firefox for Android to 15 minutes. WebKit aligns hidden-page timers to 1 second.

      
Where it bites. A timer-driven clock or poller is wrong when the tab is hidden. Long-running work should be checked against document.visibilityState rather than assumed to have kept ticking.

      
The escape hatch. A postMessage / MessageChannel message is queued as a task with no timer at all, so none of these clamps apply. That is why it was the classic “setImmediate for browsers” polyfill. It's still what React's scheduler package uses in browsers to yield between units of work without paying a timer delay. It prefers setImmediate where that exists, i.e. Node, and falls back to setTimeout last.

      
6. The loop is not concurrency, and where the real threads are

      
The event loop gives you interleaving, not parallelism.

      
How it works. This is the framing that earns the level. One task runs to completion on one thread. Nothing you can write in JavaScript on the main thread runs at the same time as anything else. That is precisely why there are no data races and no locks. It is equally why a 200ms computation makes the whole UI unresponsive, no matter how many promises wrap it.

      
The trap. The corollary people get wrong: async does not mean “in the background”. Wrapping a heavy synchronous loop in an async function changes nothing. The body still runs to completion on the main thread.

      
Where the real threads are. What is genuinely parallel lives outside JavaScript. The network stack, timers, disk I/O and the compositor are host-provided and run elsewhere. They merely deliver their results back as tasks. If you need real parallelism for JS, that's a Web Worker. It needs postMessage rather than shared variables because a second thread would otherwise reintroduce every race the single-threaded model eliminated.

      
7. Microtasks run between listeners — unless you dispatched the event yourself

      
btn.addEventListener('click', () => { console.log('L1'); Promise.resolve().then(() => console.log('M1')); });
btn.addEventListener('click', () => { console.log('L2'); Promise.resolve().then(() => console.log('M2')); });
// real user click:   L1  M1  L2  M2
// btn.click():       L1  L2  M1  M2

      
Microtasks run whenever the JavaScript stack empties, and a synthetic click keeps the stack busy between listeners.

      
How it works. The rule is not “microtasks run after the task”. It's “microtasks run whenever the JavaScript stack empties”. A user click is dispatched by the browser, so the stack is empty after each listener returns and a microtask checkpoint runs between them. btn.click() dispatches synchronously from your script. Your script is still on the stack between listeners, so the checkpoint waits until the whole dispatch returns.

      
Where it bites. Same code, different order, and the difference is the caller. Any test that drives the UI with .click() or dispatchEvent sees the second ordering.

    


    
    

      
09 — Drill until reflex

      
Interview drills

      
Predict the output before revealing, and say your reasoning out loud. That's what the interviewer scores, not just the answer. To watch any of these run one step at a time, open event-loop-playground.html and paste it in.

      

        Which environment
        Every ordering below was executed on Node 22 and is the same in Chrome, Firefox and Safari, because each one only pits timers against microtasks, a rule the HTML spec and Node share. Where Node diverges (setImmediate, process.nextTick, the ESM top level, the 1ms timer floor) is in §07; nothing here depends on it.
      


      

        
Drill 1 — mixing all four

        
console.log('start');
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('promise'));
queueMicrotask(() => console.log('microtask'));
console.log('end');

        
        

          
start · end · promise · microtask · timeout

          
start/end are synchronous. Then both microtasks drain in FIFO order (promise was queued before microtask). Only after the microtask queue is empty does the single macrotask (timeout) run.

        

      


      

        
Drill 2 — async ordering

        
console.log('A');
async function foo(){
  console.log('B');
  await Promise.resolve();
  console.log('C');
}
foo();
console.log('D');

        
        

          
A · B · D · C

          
A prints. foo() runs synchronously to the await, printing B; at await it suspends and returns control. D prints (still synchronous). The stack empties → the microtask continuation runs → C.

        

      


      

        
Drill 3 — await vs a later .then

        
console.log('A');
async function foo(){
  console.log('B');
  await null;
  console.log('C');
}
foo();
Promise.resolve().then(() => console.log('D'));
console.log('E');

        
        

          
A · B · E · C · D

          
foo() runs synchronously through B. At the await it suspends and queues its continuation — before the .then(D) on the next line is even registered. E is still synchronous, so it prints next. Then the queue drains in FIFO order: C, then D. Note await null yields as well — await is never free, even on a value that is already available.

        

      


      

        
Drill 4 — microtask scheduled inside a macrotask

        
console.log('start');
setTimeout(() => {
  console.log('timeout');
  Promise.resolve().then(() => console.log('inner promise'));
}, 0);
Promise.resolve().then(() => console.log('outer promise'));
console.log('end');

        
        

          
start · end · outer promise · timeout · inner promise

          
start/end sync. Drain microtasks → outer promise. Now take the one macrotask → timeout, which queues a new microtask. Before the loop takes another macrotask, it drains microtasks again → inner promise. The key point: microtasks queued inside a macrotask run before the next macrotask.

        

      


      

        
Drill 5 — do timer delays sort?

        
setTimeout(() => console.log('100ms'), 100);
setTimeout(() => console.log('0ms · first'), 0);
setTimeout(() => console.log('0ms · second'), 0);
setTimeout(() => console.log('50ms'), 50);
console.log('sync');

        
        

          
sync · 0ms · first · 0ms · second · 50ms · 100ms

          
The macrotask queue is not one FIFO line across different delays — the host queues each callback when its own timer elapses, so they arrive in delay order. Equal delays keep registration order. And every delay is a minimum, never a guarantee: a busy stack or a full microtask queue pushes all of them back. One environment note: in Node both 0ms timers are really 1ms timers, and in a browser they'd be 4ms only if this code were already five timers deep — neither changes the order.

        

      


      

        
Drill 6 — await on a timer

        
const sleep = ms => new Promise(r => setTimeout(r, ms));

async function main(){
  console.log('fetching…');
  await sleep(200);
  console.log('got it');
}
main();
Promise.resolve().then(() => console.log('microtask wins'));
console.log('sync tail');

        
        

          
fetching… · sync tail · microtask wins · got it

          
sleep(200) registers a macrotask and hands back a pending promise, so main suspends straight away. The synchronous tail finishes, the microtask queue drains (microtask wins), and only then does the loop take the timer — which resolves the promise and schedules main's continuation as yet another microtask. Two queue hops, in the order the algorithm dictates.

        

      


      

        
Drill 7 — the conceptual one

        
"If both are async, why does a Promise callback run before a setTimeout callback?"

        
        

          
Because they live in different queues with different draining rules. Promise callbacks are microtasks; the loop drains the entire microtask queue after each macrotask and before rendering. setTimeout callbacks are macrotasks; only one runs per loop turn, and only after microtasks are empty. So even a 0ms timer waits behind every pending microtask. It's not about timing — it's about queue priority within the loop's algorithm.

        

      


      

        
Drill 8 — spot the freeze

        
"A colleague replaced setTimeout(poll, 0) with Promise.resolve().then(poll) to make polling 'faster,' and now the UI hangs. Why?"

        
let n = 0;
function spin(){ n++; queueMicrotask(spin); }   // same shape as .then(poll)
queueMicrotask(spin);
setTimeout(() => console.log('this timer never runs'), 0);

        
        

          
Recursive microtasks never let the queue empty, so the loop never reaches the render step or any macrotask — the page can't paint or handle input, and the setTimeout above never gets its turn no matter how long you wait. setTimeout yields between loop turns, allowing rendering and events in between. The fix is to yield with a macrotask (or better, stop polling and use an event/observer).

        

      


      
      

        
Drill 9 — the await that costs three seconds

        
async function load(){
  const user  = await getUser();      // 1s
  const posts = await getPosts();     // 1s
  const tags  = await getTags();      // 1s
  return { user, posts, tags };
}

        
        
3 seconds — and only the first await is justified

          
Each await suspends the function until that promise settles, so the requests are strictly sequential even though none of them uses the previous result. Promise.all([getUser(), getPosts(), getTags()]) starts all three immediately and finishes in ~1s. The rule to state: await where you need the value, not where you make the call. And the counter-case, so it doesn't sound like a blanket rule — sequential is right when each call genuinely depends on the last, when you're rate-limited, or when you want to stop at the first failure instead of firing everything.

      


      

        
Drill 10 — async isn't a thread

        
async function crunch(){
  let total = 0;
  for (let i = 0; i < 2e9; i++) total += i;   // ~2 seconds
  return total;
}
crunch();
document.querySelector('button').addEventListener('click', handle);

        
        
The page freezes for ~2s — clicks queue and fire afterwards

          
An async function still runs its body synchronously until the first await, and there isn't one here — so the loop occupies the main thread to completion. async means “this returns a promise and may suspend at an await”, never “this runs in the background”. Clicks during that window aren't lost, but they can't preempt a running task: they're queued as macrotasks and handled after. Fixes are a Web Worker for genuine parallelism, or chunking the loop across tasks with scheduler.yield() so the loop can render and service input between chunks.

      


      

        
Drill 11 — the render that never happens

        
btn.onclick = () => {
  el.textContent = 'Working…';
  const rows = parse(hugeCsv);   // 800ms, synchronous
  el.textContent = `Done: ${rows.length}`;
};

        
        
'Working…' is never seen — only 'Done' appears, 800ms later

          
Both writes happen inside one macrotask, and the browser can only render between tasks after microtasks drain. By the time the loop reaches the render step, the DOM's final state says 'Done', so the intermediate text is never painted. This is the mechanism behind “my loading spinner doesn't show”. To let it paint, the expensive work has to be in a later task — a microtask alone is not enough, because rendering happens after the microtask queue drains. But be precise about the yield, because this is where the follow-up lands: rendering is an opportunity tied to the refresh rate, not a step after every task, so a bare setTimeout(fn, 0) usually fires long before the next frame and the parse still lands in front of the paint. The reliable shape is requestAnimationFrame(() => setTimeout(parse, 0)): rAF runs just before this frame's paint, and the timer queued from inside it runs after it. await scheduler.yield() is the modern equivalent where it exists. Or move the parsing to a Worker, which is the better answer for 800ms of work.

      


      

        How to sound senior on this topic
        Don't just recite "microtasks first." Explain the loop's algorithm (one macrotask → drain all microtasks → maybe render), name where things come from (host vs engine), and reach for consequences (starvation, jank, rendering timing). That framing is what gets you the level.
