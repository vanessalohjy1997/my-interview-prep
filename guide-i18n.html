Speaking every user's language.

Internationalisation is the engineering that lets one codebase adapt to any locale; localisation is filling that frame with real translations, formats, and conventions. For a trading product that lists prices in dozens of currencies and mirrors right-to-left across many of its markets, both are load-bearing.

00 — What this covers

i18n vs l10n, and why it's not just translation

i18n is the one-time engineering that makes a product able to adapt; l10n is the per-locale work done inside that frame.

  • Internationalisation (i18n): externalising strings, using locale-aware formatters, and building layouts that survive text expansion and direction changes.
  • Localisation (l10n): the translations, the number and date conventions, the currency, the calendar, the imagery.
  • The numeronyms count the letters between the first and last: i-nternationalisatio-n (18), l-ocalisatio-n (10).

How it works. The naive mental model is "swap the English strings for French ones." The senior model is that locale touches almost every layer. The number 1234.5 renders as 1,234.5, 1.234,5, or 1 234,5. A date's month/day order flips. A name may sort differently. The whole page may mirror.

What this guide covers. The browser-native toolkit, the Intl API, plus the patterns libraries add on top. It is framed around a trading UI as the hard case.

Why a trading UI is the hard case A financial product is close to a worst case. Real-time prices in fiat and assets with eight or more decimals and no ISO currency code. Settlement timestamps users read in their own timezone. RTL markets (Arabic, Persian, Hebrew). Legal copy that must be exact per jurisdiction. Getting a decimal separator wrong here isn't a cosmetic bug: it misreports a price.
01 — The platform gives you a lot for free

The Intl API

Intl is the browser's built-in, CLDR-backed formatting toolkit, and its output is data, so never snapshot-test it.

  • CLDR is the data: the Unicode Common Locale Data Repository (patterns, symbols, plural rules, names; release 48 landed October 2025).
  • ICU is the library that consumes it (International Components for Unicode, C/C++/Java/Rust). V8 and SpiderMonkey bundle their own ICU; JavaScriptCore on Apple platforms links the OS's copy (libicucore).
  • Node prints its pair as process.versions.icu / .cldr. It moves within a major: Node 22.13 prints ICU 76 / CLDR 46, Node 22.23 prints ICU 78 / CLDR 48.

How it works. Modern browsers ship the ECMAScript Internationalization API (Intl), backed by the Unicode CLDR locale database. It handles the mechanical, locale-dependent formatting, so you don't ship hand-rolled tables. Keep the two names straight: CLDR is the data, ICU is the library that consumes it.

Where it bites. Formatted output is data, not spec, so it drifts between engines and versions. A space becomes U+202F; "A, B, and C" gains or loses a comma. Snapshot-testing exact Intl strings is fragile. Assert on formatToParts types, or on the number you parsed back. The workhorses:

ConstructorDoes
NumberFormatNumbers, currency, percent, units; grouping & decimal separators; compact notation
DateTimeFormatDates & times in a given calendar and timezone
RelativeTimeFormat"3 minutes ago", "in 2 days" — localised relative phrasing

Numbers & currency

Grouping and decimal marks are locale-specific, so never build them by hand and never parse a display string back. This is the single most useful class. Never build separators by hand, and never parseFloat a display string back into a number.

// Same value, three locales — separators differ
new Intl.NumberFormat('en-US').format(1234567.89) // → "1,234,567.89"
new Intl.NumberFormat('de-DE').format(1234567.89) // → "1.234.567,89"
new Intl.NumberFormat('fr-FR').format(1234567.89) // → "1\u202F234\u202F567,89"  — the gaps are U+202F NARROW NO-BREAK SPACE, not " "

// Currency: the symbol, placement and spacing all come from the locale
new Intl.NumberFormat('en-US', {style:'currency', currency:'USD'}).format(9.5) // → "$9.50"
new Intl.NumberFormat('de-DE', {style:'currency', currency:'EUR'}).format(9.5) // → "9,50\u00A0€"  — U+00A0 no-break space before the symbol

// Compact for dashboards; signDisplay for P&L
new Intl.NumberFormat('en', {notation:'compact'}).format(2_400_000) // → "2.4M"
new Intl.NumberFormat('en', {signDisplay:'exceptZero'}).format(3.2) // → "+3.2"
Crypto has no ISO 4217 code style:'currency' only knows fiat codes from CLDR. There is no currency:'BTC' that yields a ₿ symbol. A well-formed but unknown code like 'BTC' just renders the code literally, joined by a no-break space ("BTC\u00A01.00"), and defaults to 2 fraction digits. You can raise that with maximumFractionDigits; the real blocker is the missing symbol/ticker, not a hard precision cap. For a known code the default fraction digits are the ISO 4217 minor units, which is why you must not hard-code 2. JPY has 0: ja-JP renders ¥1,234.5 as "￥1,235", rounded. KWD and BHD have 3 ("KWD 1.000"). Intl.supportedValuesOf('currency') lists the ~160 codes the engine knows; BTC is not among them. For a crypto amount, format with style:'decimal', set maximumFractionDigits to the asset's precision (often 8), and append the ticker/symbol yourself: `${fmt.format(amt)} BTC`.

Reuse formatter instances

Build each Intl formatter once and reuse it; construction costs roughly 60× a format call.

  • Constructing an Intl.* formatter is expensive: it resolves the locale and loads CLDR data.
  • Measured in Node 22: constructing a de-DE EUR formatter and formatting once costs roughly 24 µs. A reused instance formats in about 0.4 µs.
  • That ~60× gap means 5,000 rows re-rendering per tick is 120 ms versus 2 ms.

Where it bites. In a hot path (an order book repainting every tick, a virtualised table of thousands of rows) you must create the formatter once and reuse it. Do not build one per cell.

// ✗ builds a formatter per row, per render — a real profiler hotspot
rows.map(r => new Intl.NumberFormat(locale, opts).format(r.price))

// ✓ hoist it (module scope, useMemo, or a small cache keyed by locale+opts)
const priceFmt = new Intl.NumberFormat(locale, {minimumFractionDigits:2, maximumFractionDigits:2})
rows.map(r => priceFmt.format(r.price))

How it works. A common pattern is a memoised factory: getFormatter(locale, opts) that caches by a stringified key. The react-intl library (FormatJS) does this internally. That is one reason to prefer it over ad-hoc Intl calls in components.

Precision & rounding — the numbers must not lie

On an exchange, how a number is rounded is financially material, so pin it down explicitly rather than trusting defaults.

  • roundingMode: 'halfExpand' (default) vs 'trunc', 'floor', 'ceil'. A displayed balance you round up when the backend truncates is a support ticket.
  • minimumSignificantDigits / maximumSignificantDigits: essential for crypto prices that span many magnitudes. 0.00000842 and 64,120 want the same significant precision, not the same fraction digits.
  • style:'percent' (with a value already in 0–1) for P&L and funding rates. trailingZeroDisplay:'stripIfInteger' drops .00 where you don't want it.
Display rounding ≠ settlement rounding Intl rounds for the eye. Match its roundingMode and precision to what the backend actually settles. Otherwise a user reconciles a fill against a total that's a cent off. The exact value still lives in your integer/decimal representation (see §05); this only governs the render.

Collation: sorting is locale-aware too

Sort with a reused Intl.Collator, because the default sort compares UTF-16 code units and gets accents, CJK and numbers wrong.

  • A market list, a coin search, an order history: all need sorting.
  • JavaScript's default Array.prototype.sort compares UTF-16 code units. That is wrong for accented and CJK text, and it even puts "10" before "9".
  • Use Intl.Collator, reused like any formatter, as the comparator:
const collator = new Intl.Collator(locale, {numeric:true, sensitivity:'base'})
markets.sort((a, b) => collator.compare(a.symbol, b.symbol))
// numeric:true → "BTC10" sorts after "BTC9"; sensitivity:'base' ignores case/accents

Where it bites. Two follow-ups an interviewer reaches for. 'a'.localeCompare(b, locale, opts) is the same engine. With no options, V8 reuses a cached collator, so a 20k-item sort in Node 22 ran within about 2× of a reused Intl.Collator, sometimes faster. Pass any options object, even {}, and V8 builds a collator per call: roughly 15–40× slower with {numeric, sensitivity}.

Order is locale order. Not "alphabetical". Swedish sorts ä after z; German sorts it with a. Chinese defaults to pinyin, but zh-u-co-stroke gives stroke order. Collation is data too, so the same list can sort differently on a different ICU.

Length, case and equality are locale problems too

JavaScript strings are UTF-16 code units, not characters, so length, slicing, case and equality all need locale-aware tools. That is the trap under "how long is this string". Run these; the numbers are what an interviewer expects you to know cold.

'👨‍👩‍👧'.length                                          // 8   code units (3 emoji + 2 ZWJ = 5 code points, 3 of them surrogate pairs)
[...'👨‍👩‍👧'].length                                     // 5   code points — still not "one character"
[...new Intl.Segmenter().segment('👨‍👩‍👧')].length      // 1   grapheme cluster — the only "length" a user would agree with
'👨‍👩‍👧'.slice(0, 2)                                        // "👨" — slicing by code units cuts the family in half

'e\u0301' === 'é'                                         // false — decomposed vs precomposed (NFD vs NFC)
'e\u0301'.normalize('NFC') === 'é'                        // true — normalise before comparing, hashing or searching

'I'.toLocaleLowerCase('tr')                                // "ı" (dotless, U+0131) — Turkish; 'TITLE' → "tıtle"
'straße'.toUpperCase()                                    // "STRASSE" — one code point becomes two; length changes
'İ'.toLowerCase().length                                  // 2 — in a non-Turkish locale the dot survives as U+0307

Where it bites. A "max 20 characters" validator must count graphemes (Intl.Segmenter, Baseline 2024), not .length. Truncation with an ellipsis must cut on grapheme boundaries, or it emits half a surrogate pair.

Case and equality. Case-insensitive matching must go through Intl.Collator with the user's locale (sensitivity:'accent'; 'base' also ignores accents) or a locale-aware lowercase. toLowerCase() is locale-blind, so a Turkish "İ" never matches "i" and "I" never matches "ı". Anything you compare or index should be NFC-normalised first: macOS file names and some keyboards produce NFD.

02 — Text that survives translation

Messages, interpolation & plurals

The cardinal rule: never concatenate translated fragments.

  • Word order, gender agreement, and plural forms differ per language.
  • So a sentence assembled from pieces in English grammar will be wrong elsewhere.
  • Externalise whole messages keyed by id, with named placeholders.
// ✗ concatenation bakes in English word order & a broken plural
`You have ` + count + ` new ` + (count === 1 ? 'order' : 'orders')

// ✓ one message with an ICU plural — the translator controls every form
// en: "You have {count, plural, one {# new order} other {# new orders}}"
// pl: needs one / few / many / other; ar: needs zero / one / two / few / many / other
t('orders.badge', {count})

ICU MessageFormat

ICU MessageFormat is the de-facto message syntax, and i18next does not speak it by default.

  • It is a mini-syntax for plural, select (e.g. gender), selectordinal ("1st/2nd/3rd"), and inline number/date formatting. The # inside a plural arm is the locale-formatted count.
  • Who actually speaks it natively: react-intl/FormatJS (v12, via intl-messageformat), Lingui (v6) and next-intl (v4).
  • Current majors, September 2026: i18next 26, react-i18next 17, react-intl 12, Lingui 6, next-intl 4.

The trap. i18next does not speak ICU out of the box. Its default syntax is {{name}} interpolation with _one/_other key suffixes for plurals (it still uses Intl.PluralRules to pick the suffix). ICU only arrives via the i18next-icu plugin, which swaps the whole message engine for intl-messageformat. Saying "i18next uses ICU" in an interview is the tell that you've never configured it.

Ordinals. selectordinal is its own rule set, not cardinal's. English cardinal has two categories, but ordinal English has four: one 1st/21st, two 2nd/22nd, few 3rd/23rd, other 4th/11th/12th/13th. Read them from new Intl.PluralRules('en', {type:'ordinal'}).

How it works. Intl.PluralRules is the primitive underneath. It tells you which category a number falls into for a locale. The CLDR set is zero, one, two, few, many, other. English uses only one/other; Chinese and Japanese use other only; Arabic uses all six. Your message catalogue must supply every form the target language needs. You can't assume two.

MessageFormat 2 — know the status, don't claim it shipped Unicode MessageFormat 2 (MF2) is the successor syntax: .match {$count :number} one {{You have {$count} order}} * {{You have {$count} orders}}, with declared variables and pluggable functions instead of nested braces. The spec went stable in CLDR 47 (March 2025) and was refined in LDML 48 (October 2025). But the runtime side hasn't caught up. The TC39 Intl.MessageFormat proposal is still Stage 1 on the ECMA-402 proposals list. No browser ships it. FormatJS, Lingui and next-intl are all still MF1. The messageformat npm package (v4) is the reference implementation and doubles as the polyfill. On the file side, XLIFF 2.2 (OASIS, March 2025) added a Plural/Gender/Select module to carry these variants; XLIFF 2.1 is the ISO standard (ISO 21720:2024). Say: "MF2 is stable on paper and unshipped in practice; I'd build on ICU MF1 today and keep messages behind a t() boundary so the syntax can change once."
Why a library, not raw Intl Intl formats values. It does not parse ICU message strings, manage catalogues, load per-locale bundles, or wire React context. Libraries add message compilation, pluralised interpolation, rich-text tags (<b>{x}</b> inside a translation), and a fallback chain. Pick one (react-intl, i18next, or Lingui) rather than reinventing them.

Keys, not English, as the source

Reference messages by stable ids (orders.badge), not by the English text. English-as-key is tempting. But it breaks the moment the copy is tweaked, collides on homographs ("Right" the direction vs "Right" the entitlement), and gives translators no context. Ship context/description metadata with each key, so a translator knows "Buy" is a verb on a button.

What a plural category actually is

A plural category is a property of (number, locale, and cardinal-or-ordinal), never of the number alone.

  • The rules are defined by CLDR and are genuinely arbitrary from an English point of view.
  • Russian uses one for 1, 21 and 31 but few for 2–4 and 22–24 and many for 5–20 (a lookup, not a calculation).
  • Welsh has six categories; Japanese has one.

How it works. The mistake underneath every broken plural is assuming the category is a property of the number. It isn't. You cannot derive any of those rules in code. That is exactly why the message format asks the translator to fill in the arms rather than asking your code to choose.

// the category is a lookup, not a calculation
new Intl.PluralRules('en').select(1)   // "one"
new Intl.PluralRules('en').select(0)   // "other"  — English says "0 orders"
new Intl.PluralRules('ru').select(21)  // "one"    — 21 заказ, not заказов
new Intl.PluralRules('cy').select(3)   // "few"    — Welsh has six categories

// and decimals get their own answer
new Intl.PluralRules('en').select(1.0) // "one"
new Intl.PluralRules('en').select(1.5) // "other" — "1.5 orders"

Where it bites. Two practical consequences. A ternary on count === 1 is wrong even in English the moment a decimal or a zero-special-case appears, and it's structurally wrong everywhere else. And your catalogue format has to allow a variable number of arms per language. A schema with exactly singular and plural fields cannot represent Arabic, so the bug is baked in before any translation starts.

The costs nobody mentions in the interview

Translation costs you layout room, deploy time and an XSS surface, not just words.

  • Text expands. The sourced numbers come from IBM's globalisation guidelines, reproduced by the W3C. Strings over 70 characters grow about 30% on average when translated out of English. 31–50 characters grow 40–60%. Strings of 10 characters or fewer expand to 200–300% of their length (2–3×), so a one-word label is the worst case, not the safe one ("views" became "visualizzazioni", 3× the length). German is the usual offender in European layouts, but the rule is about string length, not one language. Microsoft's pseudo-localisation heuristic is to pad every string by 40%; Netflix uses the same figure. That's a design constraint, not a translation problem: fixed-width buttons, single-line truncation and tight nav bars break in exactly the languages you didn't test. Pseudo-localisation (rendering [!!! Ĥéļļö Ŵöŕļð !!!] in development) catches this before a translator is ever involved. It also surfaces hard-coded strings, because anything not bracketed wasn't externalised.
  • Every catalogue is a deploy dependency. New copy means a translation round trip: days, not minutes. So a feature that ships English-only and backfills translations later needs a defined fallback behaviour, not a blank string.
  • Rich text inside translations is where it gets ugly. A sentence with a link or a bold span in the middle can't be split. So the message needs inline tags (You have <b>{n}</b> orders. <a>View</a>) that the library maps to components. Passing raw HTML into a translation and rendering it with dangerouslySetInnerHTML makes your translation vendor an XSS vector.
03 — Choosing and loading the right locale

Locale negotiation & bundle loading

BCP 47 language tags

Locales are named with BCP 47 tags, language[-script][-region][-variant], and each subtag is recognisable by its shape.

  • Examples: en-US, en-GB, pt-BR vs pt-PT, and script subtags for Chinese: zh-Hans (Simplified) vs zh-Hant (Traditional).
  • Script matters more than region for Chinese. A Traditional reader in Taiwan wants zh-Hant, not "Chinese".

How to read a tag. The subtags are recognisable by shape, which is how parsers (and you, reading a tag aloud) tell them apart. Language is 2–3 letters (ISO 639). Script is exactly 4 letters, title-case (ISO 15924). Region is 2 letters (ISO 3166-1) or 3 digits (UN M.49; es-419 is Latin-American Spanish). Variant is 5–8 characters or 4 starting with a digit (de-CH-1901).

Extensions. After those come extensions with a single-letter singleton. The one that matters for the web is -u-, the Unicode locale extension that Intl reads directly: ar-EG-u-nu-latn (Western digits), ja-JP-u-ca-japanese (era calendar: "令和8年8月27日"), en-US-u-hc-h23, de-u-co-phonebk. -x- is for private use.

Canonicalising. Tags are case-insensitive but conventionally cased. Intl.getCanonicalLocales('ZH-hans-cn') fixes the casing and also rewrites legacy codes (iw → he, in → id). new Intl.Locale('zh').maximize() gives zh-Hans-CN, and 'zh-TW' gives zh-Hant-TW. Those are CLDR's "likely subtags": the right way to infer script from region instead of a hand-written map.

What the user actually prefers

Read the ordered preference list (navigator.languages / Accept-Language), but make sure negotiation still works when it has only one entry.

  • The browser exposes an ordered list. Read navigator.languages (plural, best → worst), not just navigator.language.
  • On the server the same information arrives as the Accept-Language header, weighted with q-values: fr-CH, fr;q=0.9, en;q=0.8, *;q=0.5.
  • Chrome also inserts the base language after each regional tag, so ["en-US","zh-CN"] is sent as en-US,en;q=0.9,zh-CN;q=0.8,zh;q=0.7.

Where it bites. Don't over-trust the length of that list. Safari always sends a single language in both the header and navigator.languages. Chrome does the same in Incognito. And Chrome has an intent to reduce the header to one language (plus its base) for everyone as a fingerprinting measure. So negotiation must work from one entry, with your own switcher as the real signal.

How it works. Your app's job is to match that preference list against the locales you actually ship and fall back gracefully.

const supported = ['en', 'zh-Hans', 'ar', 'pt-BR']

// getCanonicalLocales only normalises a tag (case, subtag order) — it does NOT match:
Intl.getCanonicalLocales('ZH-hans-cn')   // → ["zh-Hans-CN"]

// Matching is separate: the 'lookup' algorithm walks the fallback chain
// zh-Hans-CN → zh-Hans → zh, picking the first tag you actually support.
const best = pickSupported(navigator.languages, supported, 'en')

The fallback chain. Design an explicit fallback chain: requested → language-only → region-default → app default. fr-CA should fall back to fr before it ever hits en. Never let a missing key render blank or show the raw id to the user. Fall back to the default-locale string.

The user's choice must win — and persist Auto-detection is a default, not a verdict. Offer an explicit switcher and persist the choice (a cookie so SSR can read it, or storage). Reflect it in the URL or <html lang> so it survives reload, is shareable, and is crawlable.

Don't ship every locale to every user

Code-split catalogues by locale and load only the active one; on SSR, inline it so server and client agree.

  • Every locale's catalogue but the active one is dead weight for a given user.
  • Load the active one on demand: a dynamic import(`./locales/${locale}.json`), or per-route message chunks.
  • Load the negotiated locale first, and lazy-load others only on switch.

Where it bites. On SSR, inline the chosen locale's messages into the initial HTML so there's no flash of untranslated content. More generally, any server/client divergence in locale or timezone produces a hydration mismatch. So the server must format with the same locale and zone the client will.

Language is not jurisdiction The most senior distinction here: a user's language (navigator.language) is not their legal region. A German speaker may be trading from Singapore. An English speaker may be in a jurisdiction where a product is restricted. Which features, risk disclaimers, and regulatory copy you must show is driven by geo/jurisdiction (KYC, IP, account region). That is a separate axis from the locale that controls formatting and translation. Never gate a legal obligation on Accept-Language.

Locale is more than one axis, and users mix them

Language, region, timezone, currency and calendar are independent axes, and real users mix them.

  • A single locale string can't express the combination. This is the assumption most implementations bake in wrongly.
  • A British expat in Tokyo wants English text, JPY prices, Asia/Tokyo times, and possibly metric or imperial depending on the value.
  • Collapsing all of that into en-GB gets three of the five wrong.

How it works. The design that survives contact with users: derive formatting from the negotiated locale by default, but source the other axes separately. Keep currency from the account or the product, never from the language. Showing a euro price to a French speaker paying in dollars is a real bug. Keep timezone from an explicit user setting, defaulted from Intl.DateTimeFormat().resolvedOptions().timeZone. Keep jurisdiction from the account. Each of those should be overridable, and each override should persist somewhere the server can read.

How the URL should carry the locale

Put the locale in the URL path by default; cookie-only at one URL is uncrawlable and unshareable. The three options and their trade-offs, since this is an architecture question as much as an i18n one:

ApproachGoodCost
Path prefix — /fr/pricingCrawlable, shareable, cacheable per locale, obvious in logs. The default recommendationEvery route gains a segment; needs a redirect at the root
Subdomain — fr.example.comClean separation, can be served from different infrastructureCookies and auth need care across subdomains; more DNS and certificates
Cookie only, same URLNo routing changesUncrawlable and unshareable — one URL with unstable content. Search engines index whichever version they saw first, and a link you send a colleague may open in a different language

Where it bites. That last row is the one to argue against explicitly. It's the easiest to implement and the one that quietly costs you SEO. The SEO guide reaches the same conclusion from the other direction: each locale needs its own crawlable URL for hreflang to mean anything.

04 — When the layout flips

RTL & bidirectional text

RTL is not "align text right": the entire layout mirrors, so set direction once at the root and let everything inherit.

  • Arabic, Hebrew, Persian and Urdu read right-to-left.
  • The nav moves to the right, back-arrows point right, progress runs right-to-left, and the reading order of rows reverses.
  • Set direction at the root so everything inherits:
<html lang="ar" dir="rtl">

What lang does. dir and lang are two different declarations, and lang does real work on its own. Browsers use it to pick glyphs for CJK: Japanese and Simplified Chinese share code points but expect different shapes, and an untagged page gets the OS default. It enables hyphenation (hyphens:auto only fires when lang is set and a dictionary exists). It chooses quotation marks for <q> („…“ in German, «…» in French), and drives :lang(ar) CSS selectors. Spell-check and browser translation read it too.

Where it bites. The accessibility reason WCAG 3.1.1 requires lang: it switches the screen-reader voice. A page that swaps strings but leaves lang="en" passes visual QA and fails all of those. And if you render the wrong-direction UI briefly (before the locale bundle loads), the flip is a full re-layout. So set dir server-side, never after hydration.

Logical properties do the mirroring for you

Author with CSS logical properties and one stylesheet serves both directions. Use CSS logical properties instead of physical left/right. They resolve relative to the writing direction. This is the single biggest lever for RTL support.

Physical ✗

margin-left, padding-right, left: 0, text-align: left, border-top-left-radius

Logical ✓

margin-inline-start, padding-inline-end, inset-inline-start: 0, text-align: start, border-start-start-radius

Exceptions. Target direction-specific tweaks with the :dir(rtl) selector or a [dir="rtl"] attribute. For example, mirror a chevron icon (transform: scaleX(-1)) that shouldn't flip automatically.

Bidi: numbers and tickers inside RTL text

Isolate any run of unknown direction with <bdi> or unicode-bidi: isolate, so the bidi algorithm can't reorder the text around it.

  • A trading UI mixes scripts constantly: an Arabic sentence containing a Latin ticker BTCUSDT and a Western-Arabic number.
  • The Unicode bidirectional algorithm orders these runs, and it can reorder punctuation next to a number in surprising ways.
  • When you splice user- or data-supplied strings of unknown direction into your text, isolate them so they can't corrupt the surrounding order:
// Isolate a value of unknown direction inside a sentence
<bdi>{symbol}</bdi>          // HTML element, or…
.iso { unicode-bidi: isolate; }   // …the CSS equivalent

// Content whose direction you can't know at all (a comment, a display name)
<p dir="auto">{comment}</p>    // direction from the first strong character; <bdi> is dir="auto" inline

How dir="auto" works. It is a heuristic, not language detection. It looks at the first strongly-directional character, so an Arabic comment that opens with a Latin username lays out LTR. It's still the right default for user-generated text and for <input>/<textarea>, where the user may type either script.

Where it bites. Two more things to know. Intl output already contains invisible bidi controls: ar-EG currency strings start with U+200F (RLM), and the EGP symbol ends with another. Negatives carry U+061C (ALM) with Arabic-Indic digits, U+200E (LRM) with Latin ones. So "strip everything that isn't a digit" parsers and exact-string tests break on them. And the :dir(rtl) selector (Baseline since December 2023) matches computed direction including dir="auto" results, whereas [dir="rtl"] only matches the literal attribute.

Keep the chart LTR Direction flips reading order, but price axes, candlestick time-series and order books stay left-to-right. Time and magnitude aren't language. Mirror the chrome (labels, panels, nav) and pin the data viz to dir="ltr". Numerals themselves are also usually kept Western even in Arabic locales; digit shaping (Arabic-Indic ٠١٢) is a separate, deliberate choice via numberingSystem. Careful: CLDR defaults ar-EG and ar-SA to Arabic-Indic digits (arab: ١٬٢٣٤٫٥) and fa to Extended Arabic-Indic (arabext: ۱٬۲۳۴; Persian's ۴۵۶ differ from Arabic's ٤٥٦). Bare ar, ar-AE and he resolve to Western digits, and ar-MA even switches to 1.234.567,89. So the region subtag changes the digits, and keeping Western digits is the deliberate choice (pass numberingSystem:'latn', or tag -u-nu-latn).
05 — The details that misreport a trade

Dates, timezones & money

Store UTC, format per user timezone

Store and transmit time in UTC; format to the user's timezone only at the edge.

  • Store and transmit in UTC: an epoch, or ISO-8601 with offset.
  • Format to the user's timezone only at the edge, with Intl.DateTimeFormat.
  • A funding time or trade fill must read correctly whether the user is in Singapore or São Paulo.
const fmt = new Intl.DateTimeFormat('en-GB', {
  dateStyle:'medium', timeStyle:'short', timeZone:'Asia/Singapore'
})
fmt.format(new Date('2026-08-27T00:00:00Z')) // → "27 Aug 2026, 08:00"

// Relative phrasing, localised
new Intl.RelativeTimeFormat('en', {numeric:'auto'}).format(-1, 'day') // → "yesterday"  (default numeric:'always' → "1 day ago")

// 24-hour clocks: say hourCycle, not hour12
new Intl.DateTimeFormat('en-US', {hour:'numeric', minute:'2-digit', hourCycle:'h23'}).format(midnight) // → "00:05"
// hour12:false resolves to h23 in current engines (the spec takes h23 vs h24 from locale data), but older Chromium mapped it to h24 and printed "24:05" for five past midnight — a bug still live in old WebViews

Where it bites: parsing. Two traps on the way in. new Date('2026-08-27') is UTC midnight. But new Date('2026-08-27T00:00'), the same date with a time and no offset, is local midnight. That is ECMAScript's rule: date-only forms are UTC, date-time forms without an offset are local. A settlement date read from one and a timestamp read from the other are hours apart in Singapore.

The constructor trap. dateStyle/timeStyle cannot be mixed with field options like year or hour. The constructor throws a TypeError. That is exactly the kind of thing that only surfaces in the one locale branch you didn't run.

Date math is not formatting Intl only displays. For arithmetic across zones and DST ("the daily settlement at 00:00 UTC in the user's zone") use the Temporal API (ZonedDateTime) or a maintained library. Temporal is Stage 4 (TC39 lists it for ES2027), shipped in Chrome/Edge 144+ and Firefox 139+, but not Safari stable yet, so ship temporal-polyfill. Do not hand-roll offset math on Date; it mishandles DST transitions. On 29 March 2026 Europe/London goes 00:30 → (add 3,600,000 ms) → 02:30, so "add 24h to get tomorrow's settlement" is an hour out for a day. The reverse transition has a wall-clock hour that exists twice. Temporal's status, precisely: Stage 4 at the March 2026 TC39 plenary, and TC39's finished-proposals table lists it for ES2027, not ES2026. Firefox was first (139, May 2025), Chrome 144 followed in January 2026, Safari 27 (September 2026) still ships without it, so only Technology Preview has it. Node 22 has no Temporal global; Node 26 turns it on by default. Also mind calendar systems. Intl.DateTimeFormat supports calendar:'islamic', 'buddhist', etc., and there are five Islamic variants. 'islamic' and Saudi Arabia's 'islamic-umalqura' gave dates one day apart for 27 Aug 2026 in Node 22, so a Gulf market wants the specific one. Intl.Locale exposes week metadata (first day of the week, weekend) via getWeekInfo(): Chrome 130, Safari 17, Firefox 153, so Baseline only since mid-2026; Node 22 still has the older weekInfo getter, and the Locale Info proposal it comes from reached Stage 4 in November 2025. The data is worth having: en-US starts the week on Sunday, de on Monday, ar-EG on Saturday with a Friday–Saturday weekend, and ar-AE has moved to Monday with a Saturday–Sunday weekend.

Money is never a float

Hold money as integer minor units or a decimal type; use Intl.NumberFormat purely for the final render.

  • Locale controls the display of money. It never fixes the deeper bug of using binary floating point for value.
  • 0.1 + 0.2 !== 0.3, and for an exchange that's real money lost.
  • Hold amounts as integer minor units (or a decimal/BigInt type, and strings on the wire). Do all math in that exact representation.

Where it bites: parsing. Symmetrically, never parse a localised display string back to a number with parseFloat: "1.234,56" becomes 1.234. Parse from the raw machine value where you can. Sometimes you must read a number a user typed in their own locale, such as an order-entry field where a German trader types 1,5. Then derive that locale's marks from formatToParts and normalise before parsing:

// Learn this locale's group + decimal marks, then normalise "1.234,56" → 1234.56
const parts = new Intl.NumberFormat(locale).formatToParts(11111.1)
const group   = parts.find(p => p.type === 'group').value
const decimal = parts.find(p => p.type === 'decimal').value
const toNumber = str => Number(str.split(group).join('').replace(decimal, '.'))
Whitespace trapStrip all space-like characters, not just the exact group mark. A French user types U+0020, but CLDR emits U+202F, so a literal split(group) silently fails to match. Normalise with something like str.replace(/\s|\u00A0|\u202F/g, '') first.

06 — Predict the output

Drills

Cover the answer, commit to a prediction out loud, then reveal. These are the ones that catch people.

1. What does this log?

new Intl.NumberFormat('de-DE').format(1234.5)
"1.234,5"

German groups thousands with . and marks the decimal with , — the mirror image of US English. This is exactly why you must never assemble numbers by hand or parseFloat a display string.

2. Why is this a bug, and what breaks?

`Showing ` + n + ` result` + (n === 1 ? '' : 's')
Concatenation + an English-only plural rule

It bakes English word order into code and assumes two plural forms. In Polish 2, 3, 4 take few and 5–21 take many; Arabic has six categories. Use an ICU plural message with Intl.PluralRules underneath so each locale supplies its own forms.

3. A price shows correctly on your machine but is 8 hours off for a Singapore user. Likely cause?

Formatting a Date without an explicit timeZone

Left unset, Intl.DateTimeFormat uses the runtime's timezone, so a server or a differently-located user renders a different wall-clock time. Store UTC and pass an explicit timeZone. The same class of bug causes SSR hydration mismatches when server and client zones differ.

4. Your Arabic build mostly works, but paddings and the back-button sit on the wrong side. What did you likely use?

Physical CSS properties instead of logical ones

margin-left, padding-right, left:0 don't flip with dir="rtl". Switch to margin-inline-start, padding-inline-end, inset-inline-start, text-align:start and the layout mirrors itself.

Drill 5 — the plural that survives translation
const label = count === 1 ? `${count} order` : `${count} orders`;
Wrong in English too, and structurally wrong everywhere else

The plural category isn't a property of the number — it's a property of the number and the locale, and it comes from CLDR rules you can't derive. Russian uses 'one' for 21 and 'few' for 22; Welsh has six categories; Japanese has one. Even in English this breaks on 1.5 ('1.5 orders' is 'other'). The fix is one whole message with an ICU plural so the translator supplies every arm — and a catalogue format that allows a variable number of arms per language, because a schema with just singular and plural fields cannot represent Arabic at all.

Drill 6 — the German button
“QA reports the German build has overlapping text and truncated buttons across the app. How would you have caught this earlier?”

Translated text expands — IBM's figures, reproduced by the W3C, are roughly 30% growth for long strings and 2–3× (200–300% of the original) for labels of ten characters or fewer, and German is where European layouts usually meet it first — so this is a layout constraint, not a translation defect. I'd add pseudo-localisation to the dev build — render every string as something like [!!! Ĥéļļö Ŵöŕļð !!!], padded to simulate expansion. It catches truncation before any translator is involved, and it doubles as a hard-coded-string detector, because anything that isn't bracketed was never externalised. Structurally the fixes are the same ones responsive design wants: no fixed-width text containers, allow wrapping, and test at the narrowest supported width with the longest locale.

Drill 7 — the wrong currency
“A French-speaking user in Singapore sees prices in euros. Where's the design error?”

Currency was derived from the language. Language, region, timezone, currency and calendar are independent axes and users mix them constantly — a British expat in Tokyo wants English text, JPY prices and Asia/Tokyo times. Currency must come from the account or the product, never the locale; the locale only decides how that amount is formatted. Same reasoning applies to jurisdiction: which disclaimers and features are legally required is driven by the account region, not Accept-Language. And separately from all of it, the amount itself should be integer minor units, never a float.
