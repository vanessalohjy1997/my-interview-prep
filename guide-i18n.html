Speaking every user's language.

Internationalisation is the engineering that lets one codebase adapt to any locale; localisation is filling that frame with real translations, formats, and conventions. For a trading product that lists prices in dozens of currencies and mirrors right-to-left across many of its markets, both are load-bearing.

00 — What this covers

i18n vs l10n, and why it's not just translation

Internationalisation (i18n) is the one-time engineering that makes a product capable of adapting: externalising strings, using locale-aware formatters, and building layouts that survive text expansion and direction changes. Localisation (l10n) is the per-locale work done on top of that frame — the translations, the number and date conventions, the currency, the calendar, the imagery. The numeronyms count the letters between the first and last: i-nternationalisatio-n (18), l-ocalisatio-n (10).

The naive mental model is "swap the English strings for French ones." The senior model is that locale touches almost every layer: the number 1234.5 renders as 1,234.5, 1.234,5, or 1 234,5; a date's month/day order flips; a name may sort differently; the whole page may mirror. This guide is the browser-native toolkit — the Intl API — plus the patterns libraries add on top, framed around a trading UI as the hard case.

Why a trading UI is the hard case A financial product is close to a worst case: real-time prices in fiat and assets with eight or more decimals and no ISO currency code, settlement timestamps users read in their own timezone, RTL markets (Arabic, Persian, Hebrew), and legal copy that must be exact per jurisdiction. Getting a decimal separator wrong here isn't a cosmetic bug — it misreports a price.
01 — The platform gives you a lot for free

The Intl API

Modern browsers ship the ECMAScript Internationalization API (Intl), backed by the Unicode CLDR locale database. It handles the mechanical, locale-dependent formatting so you don't ship hand-rolled tables. The workhorses:

ConstructorDoes
NumberFormatNumbers, currency, percent, units; grouping & decimal separators; compact notation
DateTimeFormatDates & times in a given calendar and timezone
RelativeTimeFormat"3 minutes ago", "in 2 days" — localised relative phrasing
PluralRulesWhich plural category (one/few/many…) a number takes
CollatorLocale-aware string comparison & sorting
ListFormat"A, B, and C" vs "A, B et C"
SegmenterLocale-correct grapheme / word / sentence boundaries

Numbers & currency

The single most useful class. Grouping and decimal marks are locale-specific, so never build them by hand and never parseFloat a display string back into a number.

// Same value, three locales — separators differ
new Intl.NumberFormat('en-US').format(1234567.89) // → "1,234,567.89"
new Intl.NumberFormat('de-DE').format(1234567.89) // → "1.234.567,89"
new Intl.NumberFormat('fr-FR').format(1234567.89) // → "1\u202F234\u202F567,89"  — the gaps are U+202F NARROW NO-BREAK SPACE, not " "

// Currency: the symbol, placement and spacing all come from the locale
new Intl.NumberFormat('en-US', {style:'currency', currency:'USD'}).format(9.5) // → "$9.50"
new Intl.NumberFormat('de-DE', {style:'currency', currency:'EUR'}).format(9.5) // → "9,50\u00A0€"  — U+00A0 no-break space before the symbol

// Compact for dashboards; signDisplay for P&L
new Intl.NumberFormat('en', {notation:'compact'}).format(2_400_000) // → "2.4M"
new Intl.NumberFormat('en', {signDisplay:'exceptZero'}).format(3.2) // → "+3.2"
Crypto has no ISO 4217 code style:'currency' only knows fiat codes from CLDR. There is no currency:'BTC' that yields a ₿ symbol — a well-formed but unknown code like 'BTC' just renders the code literally, joined by a no-break space ("BTC\u00A01.00") and defaults to 2 fraction digits (you can raise that with maximumFractionDigits; the real blocker is the missing symbol/ticker, not a hard precision cap). For a crypto amount, format with style:'decimal', set maximumFractionDigits to the asset's precision (often 8), and append the ticker/symbol yourself: `${fmt.format(amt)} BTC`.

Reuse formatter instances

Constructing an Intl.* formatter is expensive — it resolves the locale and loads CLDR data. In a hot path (an order book repainting every tick, a virtualised table of thousands of rows) you must create the formatter once and reuse it, not build one per cell.

// ✗ builds a formatter per row, per render — a real profiler hotspot
rows.map(r => new Intl.NumberFormat(locale, opts).format(r.price))

// ✓ hoist it (module scope, useMemo, or a small cache keyed by locale+opts)
const priceFmt = new Intl.NumberFormat(locale, {minimumFractionDigits:2, maximumFractionDigits:2})
rows.map(r => priceFmt.format(r.price))

A common pattern is a memoised factory: getFormatter(locale, opts) that caches by a stringified key. The react-intl library (FormatJS) does this internally, which is one reason to prefer it over ad-hoc Intl calls in components.

Precision & rounding — the numbers must not lie

On an exchange, how a number is rounded is financially material, so pin it down explicitly rather than trusting defaults:

  • roundingMode — 'halfExpand' (default) vs 'trunc', 'floor', 'ceil'. A displayed balance you round up when the backend truncates is a support ticket.
  • minimumSignificantDigits / maximumSignificantDigits — essential for crypto prices that span many magnitudes (0.00000842 and 64,120 want the same significant precision, not the same fraction digits).
  • style:'percent' (with a value already in 0–1) for P&L and funding rates; trailingZeroDisplay:'stripIfInteger' to drop .00 where you don't want it.
Display rounding ≠ settlement rounding Intl rounds for the eye. Match its roundingMode and precision to what the backend actually settles, or a user reconciles a fill against a total that's a cent off. The exact value still lives in your integer/decimal representation (see §05) — this only governs the render.

Collation: sorting is locale-aware too

A market list, a coin search, an order history — all need sorting, and JavaScript's default Array.prototype.sort compares UTF-16 code units, which is wrong for accented and CJK text (and even puts "10" before "9"). Use Intl.Collator — reused like any formatter — as the comparator:

const collator = new Intl.Collator(locale, {numeric:true, sensitivity:'base'})
markets.sort((a, b) => collator.compare(a.symbol, b.symbol))
// numeric:true → "BTC10" sorts after "BTC9"; sensitivity:'base' ignores case/accents
02 — Text that survives translation

Messages, interpolation & plurals

The cardinal rule: never concatenate translated fragments. Word order, gender agreement, and plural forms differ per language, so a sentence assembled from pieces in English grammar will be wrong elsewhere. Externalise whole messages keyed by id, with named placeholders.

// ✗ concatenation bakes in English word order & a broken plural
`You have ` + count + ` new ` + (count === 1 ? 'order' : 'orders')

// ✓ one message with an ICU plural — the translator controls every form
// en: "You have {count, plural, one {# new order} other {# new orders}}"
// pl: needs one / few / many / other; ar: zero / one / two / few / many / other; ar: needs zero / one / two / few / many / other
t('orders.badge', {count})

ICU MessageFormat

The de-facto standard (used by react-intl/FormatJS, i18next, Lingui) is ICU MessageFormat: a mini-syntax for plural, select (e.g. gender), selectordinal ("1st/2nd/3rd"), and inline number/date formatting. The # inside a plural arm is the locale-formatted count.

Intl.PluralRules is the primitive underneath: it tells you which category a number falls into for a locale — the CLDR set is zero, one, two, few, many, other. English uses only one/other; Chinese and Japanese use other only; Arabic uses all six. Your message catalogue must supply every form the target language needs — you can't assume two.

Why a library, not raw Intl Intl formats values; it does not parse ICU message strings, manage catalogues, load per-locale bundles, or wire React context. Libraries add message compilation, pluralised interpolation, rich-text tags (<b>{x}</b> inside a translation), and a fallback chain. Pick one — react-intl, i18next, or Lingui — rather than reinventing them.

Keys, not English, as the source

What a plural category actually is

The mistake underneath every broken plural is assuming the category is a property of the number. It isn't — it's a property of (number, locale, and whether the count is cardinal or ordinal), defined by CLDR rules that are genuinely arbitrary from an English point of view. Russian uses one for 1, 21 and 31 but few for 2–4 and 22–24 and many for 5–20; Welsh has six categories; Japanese has one. You cannot derive any of that, which is exactly why the message format asks the translator to fill in the arms rather than asking your code to choose.

// the category is a lookup, not a calculation
new Intl.PluralRules('en').select(1)   // "one"
new Intl.PluralRules('en').select(0)   // "other"  — English says "0 orders"
new Intl.PluralRules('ru').select(21)  // "one"    — 21 заказ, not заказов
new Intl.PluralRules('cy').select(3)   // "few"    — Welsh has six categories

// and decimals get their own answer
new Intl.PluralRules('en').select(1.0) // "one"
new Intl.PluralRules('en').select(1.5) // "other" — "1.5 orders"

Two practical consequences. A ternary on count === 1 is wrong even in English the moment a decimal or a zero-special-case appears, and it's structurally wrong everywhere else. And your catalogue format has to allow a variable number of arms per language — a schema with exactly singular and plural fields cannot represent Arabic, so the bug is baked in before any translation starts.

The costs nobody mentions in the interview

  • Text expands. German and Russian commonly run 20–35% longer than English, and short UI strings can double — a 10-character English label may need 20. That's a design constraint, not a translation problem: fixed-width buttons, single-line truncation and tight nav bars break in exactly the languages you didn't test. Pseudo-localisation (rendering [!!! Ĥéļļö Ŵöŕļð !!!] in development) catches this before a translator is ever involved, and also surfaces hard-coded strings, because anything not bracketed wasn't externalised.
  • Every catalogue is a deploy dependency. New copy means a translation round trip — days, not minutes — so a feature that ships English-only and backfills translations later needs a defined fallback behaviour, not a blank string.
  • Rich text inside translations is where it gets ugly. A sentence with a link or a bold span in the middle can't be split, so the message needs inline tags (You have <b>{n}</b> orders. <a>View</a>) that the library maps to components. Passing raw HTML into a translation and rendering it with dangerouslySetInnerHTML makes your translation vendor an XSS vector.

Reference messages by stable ids (orders.badge) rather than by the English text. English-as-key is tempting but breaks the moment the copy is tweaked, collides on homographs ("Right" the direction vs "Right" the entitlement), and gives translators no context. Ship context/description metadata with each key so a translator knows "Buy" is a verb on a button.

03 — Choosing and loading the right locale

Locale negotiation & bundle loading

BCP 47 language tags

Locales are named with BCP 47 tags: language[-script][-region][-variant]. So en-US, en-GB, pt-BR vs pt-PT, and script subtags for Chinese: zh-Hans (Simplified) vs zh-Hant (Traditional). Script matters more than region for Chinese — a Traditional reader in Taiwan wants zh-Hant, not "Chinese".

What the user actually prefers

The browser exposes an ordered preference list. Read navigator.languages (plural, best → worst), not just navigator.language. On the server the same information arrives as the Accept-Language header. Your app's job is to match that preference list against the locales you actually ship and fall back gracefully.

const supported = ['en', 'zh-Hans', 'ar', 'pt-BR']

// getCanonicalLocales only normalises a tag (case, subtag order) — it does NOT match:
Intl.getCanonicalLocales('ZH-hans-cn')   // → ["zh-Hans-CN"]

// Matching is separate: the 'lookup' algorithm walks the fallback chain
// zh-Hans-CN → zh-Hans → zh, picking the first tag you actually support.
const best = pickSupported(navigator.languages, supported, 'en')

Design an explicit fallback chain: requested → language-only → region-default → app default. fr-CA should fall back to fr before it ever hits en. Never let a missing key render blank or show the raw id to the user — fall back to the default-locale string.

The user's choice must win — and persist Auto-detection is a default, not a verdict. Offer an explicit switcher, persist the choice (cookie so SSR can read it; or storage), and reflect it in the URL or <html lang> so it survives reload, is shareable, and is crawlable.

Don't ship every locale to every user

Every locale's catalogue but the active one is dead weight for a given user. Code-split by locale and load the active one on demand — a dynamic import(`./locales/${locale}.json`), or per-route message chunks. Load the negotiated locale first, and lazy-load others only on switch. On SSR, inline the chosen locale's messages into the initial HTML so there's no flash of untranslated content — and, more generally, any server/client divergence in locale or timezone produces a hydration mismatch, so the server must format with the same locale and zone the client will.

Language is not jurisdiction The most senior distinction here: a user's language (navigator.language) is not their legal region. A German speaker may be trading from Singapore; an English speaker may be in a jurisdiction where a product is restricted. Which features, risk disclaimers, and regulatory copy you must show is driven by geo/jurisdiction (KYC, IP, account region) — a separate axis from the locale that controls formatting and translation. Never gate a legal obligation on Accept-Language.

Locale is more than one axis, and users mix them

Worth naming because it's the assumption most implementations bake in wrongly: language, region, timezone, currency and calendar are independent, and real users combine them in ways a single locale string can't express. A British expat in Tokyo wants English text, JPY prices, Asia/Tokyo times, and possibly metric or imperial depending on the value. Collapsing all of that into en-GB gets three of the five wrong.

The design that survives contact with users: derive formatting from the negotiated locale by default, but keep currency from the account or the product (never from the language — showing a euro price to a French speaker paying in dollars is a real bug), timezone from an explicit user setting defaulted from Intl.DateTimeFormat().resolvedOptions().timeZone, and jurisdiction from the account. Each of those should be overridable, and each override should persist somewhere the server can read.

How the URL should carry the locale

The three options and their trade-offs, since this is an architecture question as much as an i18n one:

ApproachGoodCost
Path prefix — /fr/pricingCrawlable, shareable, cacheable per locale, obvious in logs. The default recommendationEvery route gains a segment; needs a redirect at the root
Subdomain — fr.example.comClean separation, can be served from different infrastructureCookies and auth need care across subdomains; more DNS and certificates
Cookie only, same URLNo routing changesUncrawlable and unshareable — one URL with unstable content. Search engines index whichever version they saw first, and a link you send a colleague may open in a different language

That last row is the one to argue against explicitly, because it's the easiest to implement and the one that quietly costs you SEO — the same conclusion the SEO guide reaches from the other direction, where each locale needs its own crawlable URL for hreflang to mean anything.

04 — When the layout flips

RTL & bidirectional text

Arabic, Hebrew, Persian and Urdu read right-to-left. This is not "align text right" — the entire layout mirrors: the nav moves to the right, back-arrows point right, progress runs right-to-left, and the reading order of rows reverses. Set direction at the root so everything inherits:

<html lang="ar" dir="rtl">

Logical properties do the mirroring for you

Author with CSS logical properties instead of physical left/right. They resolve relative to the writing direction, so one stylesheet serves both. This is the single biggest lever for RTL support.

Physical ✗

margin-left, padding-right, left: 0, text-align: left, border-top-left-radius

Logical ✓

margin-inline-start, padding-inline-end, inset-inline-start: 0, text-align: start, border-start-start-radius

Target direction-specific tweaks with the :dir(rtl) selector or a [dir="rtl"] attribute — for example mirroring a chevron icon (transform: scaleX(-1)) that shouldn't flip automatically.

Bidi: numbers and tickers inside RTL text

A trading UI mixes scripts constantly — an Arabic sentence containing a Latin ticker BTCUSDT and a Western-Arabic number. The Unicode bidirectional algorithm orders these runs, and it can reorder punctuation next to a number in surprising ways. When you splice user- or data-supplied strings of unknown direction into your text, isolate them so they can't corrupt the surrounding order:

// Isolate a value of unknown direction inside a sentence
<bdi>{symbol}</bdi>          // HTML element, or…
.iso { unicode-bidi: isolate; }   // …the CSS equivalent
Keep the chart LTR Direction flips reading order, but price axes, candlestick time-series and order books stay left-to-right — time and magnitude aren't language. Mirror the chrome (labels, panels, nav) and pin the data viz to dir="ltr". Numerals themselves are also usually kept Western even in Arabic locales; digit shaping (Arabic-Indic ٠١٢) is a separate, deliberate choice via numberingSystem. Careful: CLDR defaults ar-EG, ar-SA and fa to Arabic-Indic digits, so keeping Western digits is the deliberate choice (pass numberingSystem:'latn').
05 — The details that misreport a trade

Dates, timezones & money

Store UTC, format per user timezone

The rule for time: store and transmit in UTC (an epoch or ISO-8601 with offset), and format to the user's timezone only at the edge with Intl.DateTimeFormat. A funding time or trade fill must read correctly whether the user is in Singapore or São Paulo.

const fmt = new Intl.DateTimeFormat('en-GB', {
  dateStyle:'medium', timeStyle:'short', timeZone:'Asia/Singapore'
})
fmt.format(new Date('2026-08-27T00:00:00Z')) // → "27 Aug 2026, 08:00"

// Relative phrasing, localised
new Intl.RelativeTimeFormat('en', {numeric:'auto'}).format(-1, 'day') // → "yesterday"
Date math is not formatting Intl only displays. For arithmetic across zones and DST — "the daily settlement at 00:00 UTC in the user's zone" — use the Temporal API (ZonedDateTime — ES2026, shipped in Chrome/Edge 144+ and Firefox 139+, but not Safari stable yet, so ship temporal-polyfill) or a maintained library, not hand-rolled offset math on Date, which mishandles DST transitions. Also mind calendar systems: Intl.DateTimeFormat supports calendar:'islamic', 'buddhist', etc., and Intl.Locale exposes week metadata (first day of the week, weekend) — via getWeekInfo() in current engines (a weekInfo getter in older ones).

Money is never a float

Locale controls the display of money; it never fixes the deeper bug of using binary floating point for value. 0.1 + 0.2 !== 0.3, and for an exchange that's real money lost. Hold amounts as integer minor units (or a decimal/BigInt type, and strings on the wire), do all math in that exact representation, and use Intl.NumberFormat purely for the final render.

Symmetrically: never parse a localised display string back to a number with parseFloat — "1.234,56" becomes 1.234. Parse from the raw machine value where you can. When you must read a number a user typed in their own locale (an order-entry field where a German trader types 1,5), derive that locale's marks from formatToParts and normalise before parsing:

// Learn this locale's group + decimal marks, then normalise "1.234,56" → 1234.56
const parts = new Intl.NumberFormat(locale).formatToParts(11111.1)
const group   = parts.find(p => p.type === 'group').value
const decimal = parts.find(p => p.type === 'decimal').value
const toNumber = str => Number(str.split(group).join('').replace(decimal, '.'))
Whitespace trapStrip all space-like characters, not just the exact group mark. A French user types U+0020, but CLDR emits U+202F — so a literal split(group) silently fails to match. Normalise with something like str.replace(/\s|\u00A0|\u202F/g, '') first.

06 — Predict the output

Drills

Cover the answer, commit to a prediction out loud, then reveal. These are the ones that catch people.

1. What does this log?

new Intl.NumberFormat('de-DE').format(1234.5)
"1.234,5"

German groups thousands with . and marks the decimal with , — the mirror image of US English. This is exactly why you must never assemble numbers by hand or parseFloat a display string.

2. Why is this a bug, and what breaks?

`Showing ` + n + ` result` + (n === 1 ? '' : 's')
Concatenation + an English-only plural rule

It bakes English word order into code and assumes two plural forms. In Polish 2, 3, 4 take few and 5–21 take many; Arabic has six categories. Use an ICU plural message with Intl.PluralRules underneath so each locale supplies its own forms.

3. A price shows correctly on your machine but is 8 hours off for a Singapore user. Likely cause?

Formatting a Date without an explicit timeZone

Left unset, Intl.DateTimeFormat uses the runtime's timezone, so a server or a differently-located user renders a different wall-clock time. Store UTC and pass an explicit timeZone. The same class of bug causes SSR hydration mismatches when server and client zones differ.

4. Your Arabic build mostly works, but paddings and the back-button sit on the wrong side. What did you likely use?

Physical CSS properties instead of logical ones

margin-left, padding-right, left:0 don't flip with dir="rtl". Switch to margin-inline-start, padding-inline-end, inset-inline-start, text-align:start and the layout mirrors itself.

Drill 5 — the plural that survives translation
const label = count === 1 ? `${count} order` : `${count} orders`;
Wrong in English too, and structurally wrong everywhere else

The plural category isn't a property of the number — it's a property of the number and the locale, and it comes from CLDR rules you can't derive. Russian uses 'one' for 21 and 'few' for 22; Welsh has six categories; Japanese has one. Even in English this breaks on 1.5 ('1.5 orders' is 'other'). The fix is one whole message with an ICU plural so the translator supplies every arm — and a catalogue format that allows a variable number of arms per language, because a schema with just singular and plural fields cannot represent Arabic at all.

Drill 6 — the German button
“QA reports the German build has overlapping text and truncated buttons across the app. How would you have caught this earlier?”

German commonly runs 20–35% longer than English and short labels can double, so this is a layout constraint, not a translation defect. I'd add pseudo-localisation to the dev build — render every string as something like [!!! Ĥéļļö Ŵöŕļð !!!], padded to simulate expansion. It catches truncation before any translator is involved, and it doubles as a hard-coded-string detector, because anything that isn't bracketed was never externalised. Structurally the fixes are the same ones responsive design wants: no fixed-width text containers, allow wrapping, and test at the narrowest supported width with the longest locale.

Drill 7 — the wrong currency
“A French-speaking user in Singapore sees prices in euros. Where's the design error?”

Currency was derived from the language. Language, region, timezone, currency and calendar are independent axes and users mix them constantly — a British expat in Tokyo wants English text, JPY prices and Asia/Tokyo times. Currency must come from the account or the product, never the locale; the locale only decides how that amount is formatted. Same reasoning applies to jurisdiction: which disclaimers and features are legally required is driven by the account region, not Accept-Language. And separately from all of it, the amount itself should be integer minor units, never a float.
