00 — Not a device problem

What responsive design actually asks

The weak answer to “how do you implement responsive design” is a list: media queries, percentages, mobile-first. The strong answer starts one level up — responsive design is about making a layout that adapts to an unknown viewport, not about supporting a list of devices. You never know the width, the pixel density, the input type, the font size the user has chosen, or whether the on-screen keyboard is open.

That reframing has a practical consequence: breakpoints should come from where your content breaks, not from an iPhone's dimensions. Resize the browser until the layout looks wrong; that width is a breakpoint. Device-named breakpoints go stale every hardware cycle.

The structure to answer in“Fluid by default, breakpoints only where content demands one, container queries for components that appear in more than one context, responsive images so we are not shipping desktop assets to phones, and respect for user preferences — font size, reduced motion, colour scheme.”
01 — Two viewports and two kinds of pixel

The viewport meta tag & device pixels

Mobile browsers historically assumed pages were designed for desktop, so they render into a layout viewport of roughly 980 CSS pixels and then zoom out to fit the screen. Your media queries would never match. One tag opts out:

<meta name="viewport" content="width=device-width, initial-scale=1">

width=device-width sets the layout viewport to the device's width in CSS pixels; initial-scale=1 starts unzoomed.

Never disable zoomuser-scalable=no and maximum-scale=1 are attempts to block pinch-zoom. Writing them is a WCAG 1.4.4 failure — low-vision users rely on zoom — and it fixes nothing a correct layout would not. Worth knowing for the follow-up: iOS Safari has ignored both since iOS 10, and Android Chrome ignores them when the user enables Force enable zoom, so they mostly just signal carelessness.

CSS pixels vs device pixels

A CSS pixel is a unit of layout; a device pixel is hardware. Their ratio is window.devicePixelRatio — 2 or 3 on most phones. A 300 CSS-px-wide image on a DPR 3 screen needs a 900-device-pixel source to look sharp, which is the entire reason srcset exists. Layout is unaffected by DPR; only raster assets are.

02 — Mobile-first, content-driven

Media queries

/* mobile-first: base styles are the small layout, no query needed */
.cards { display: grid; gap: 16px; }

/* enhance upward with min-width */
@media (min-width: 48rem) { .cards { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 72rem) { .cards { grid-template-columns: repeat(3, 1fr); } }

/* modern range syntax — clearer, and no off-by-one overlaps */
@media (width >= 48rem) { /* … */ }
@media (48rem <= width < 72rem) { /* … */ }
  • Mobile-first means min-width. You write the simplest layout as the base and add complexity as space allows, so you are always adding rules rather than undoing them, which keeps specificity low. Be careful not to overclaim it: the browser downloads and parses the whole stylesheet either way — non-matching rules still land in the CSSOM, they are simply not applied. Mobile-first saves you overrides, not bytes.
  • Do not mix min-width and max-width ranges casually. max-width: 768px and min-width: 768px both match at exactly 768px, and on fractional widths from zoom or scrollbars you get gaps. Pick one direction, or use range syntax.
  • Use rem/em in queries, not px. Inside a media query both resolve against the browser's initial font size, so a user who raises their default text size gets breakpoints that move with it. Your html { font-size } does not affect this.

03 — Most layouts need no breakpoint at all

Fluid layout without media queries

Modern CSS can express “adapt to available space” directly, which is more robust than enumerating widths.

/* wraps to as many columns as fit, each at least 220px */
.gallery { display: grid; grid-template-columns: repeat(auto-fit, minmax(220px, 1fr)); gap: 16px; }

/* a sidebar that collapses on its own when space runs out */
.layout { display: flex; flex-wrap: wrap; gap: 24px; }
.sidebar { flex: 1 1 18rem; }
.content { flex: 999 1 30rem; }

/* bounded fluid value: never below 1rem, never above 2rem */
h2 { font-size: clamp(1.25rem, 1rem + 1.5vw, 2rem); }

/* readable measure without a query */
.prose { width: min(65ch, 100%); }
  • auto-fit collapses empty tracks so items stretch to fill the row; auto-fill keeps them, leaving gaps. That one word is a common interview probe.
  • min(), max() and clamp() replace whole families of breakpoints. width: min(65ch, 100%) means “65 characters, but never overflow the parent”.
  • The flex trick above is Every Layout's “Sidebar” pattern: give the content a huge flex-grow and both items a sensible flex-basis, and they wrap to one column exactly when they no longer fit. (Do not call it the Holy Grail — that name belongs to the header/footer/two-sidebar page shell.)
Say this“I reach for intrinsic sizing first — minmax, clamp, min(), wrapping flex — and only add a media query when the layout needs to genuinely rearrange, not merely resize.”
04 — The component does not know the page

Container queries

Media queries ask about the viewport. That is the wrong question for a reusable component: a product card in a full-width grid and the same card in a 300px sidebar should look different at the same viewport width. Container queries let an element respond to the size of its container instead.

/* 1. declare a containment context on the parent */
.card-wrap { container-type: inline-size; container-name: card; }

/* 2. query it */
@container card (min-width: 400px) {
  .card { display: grid; grid-template-columns: 140px 1fr; }
}

/* container-relative units: 1cqi = 1% of the container's inline size */
.card h3 { font-size: clamp(1rem, 4cqi, 1.5rem); }
  • container-type: inline-size applies containment on the inline axis, so the container's width must not depend on its children — that is what makes the query resolvable without a circular dependency.
  • You query an ancestor, never the element itself. Hence the wrapper element in the example.
  • cqw, cqh, cqi, cqb are to containers what vw/vh are to the viewport.
  • Baseline across all modern browsers since 2023, so “can I use it” is now a yes for evergreen targets.
The senior answer“Media queries are for page layout — the shell. Container queries are for components, because a component should depend on the space it was given, not on the window. Design-system components should ship with container queries so they survive being dropped anywhere.”
05 — The biggest responsive win is bytes

Responsive images

Layout responsiveness is cheap; image responsiveness is where responsive design pays for itself. Sending a 2000px hero to a 390px phone wastes most of the download and usually owns your LCP.

Resolution switching — same image, different sizes
<img
  src="hero-800.jpg"
  srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1600.jpg 1600w"
  sizes="(min-width: 60rem) 50vw, 100vw"
  width="1600" height="900"
  alt="Trading dashboard">
  • srcset with w descriptors declares each file's intrinsic width. sizes tells the browser how wide the image will render at a given viewport. It is not strictly required — omit it and the browser assumes 100vw and over-downloads — but it is effectively mandatory in practice, because the preload scanner chooses a source before any layout exists. (sizes="auto" is the exception, for loading="lazy" images, where the element's own rendered width is already known.)
  • The browser combines sizes with the device pixel ratio and picks a candidate. The spec allows it to take connection speed into account, though no shipping browser currently does; in practice Chrome and Firefox will not downgrade to a smaller file when a larger one is already cached.
  • x descriptors (logo.png 1x, logo@2x.png 2x) are for images with a fixed CSS size — no sizes needed.
  • width and height attributes let the browser reserve the correct box from the aspect ratio, which is how you avoid layout shift. They do not conflict with CSS sizing.
Art direction and format negotiation — <picture>
<picture>
  <source media="(min-width: 60rem)" srcset="hero-wide.avif" type="image/avif">
  <source srcset="hero-square.avif" type="image/avif">
  <img src="hero-square.jpg" alt="Trading dashboard" width="800" height="800">
</picture>

Use <picture> when the crop or content should change (art direction) or when you are offering formats the browser may not support (AVIF, WebP, with a JPEG fallback in <img>). Use bare srcset when only the resolution changes. The <img> is mandatory — it is what actually renders.

06 — Legibility survives zoom

Typography & spacing

  • Never set a px font size on the root. html { font-size: 16px } overrides the user's browser preference. Leave the root alone and size everything in rem.
  • rem vs em: rem is relative to the root, so it is predictable — use it for type and layout spacing. em is relative to the element's own font size, which is exactly what you want for padding inside a button that should scale with its label.
  • Fluid type needs a floor and a ceiling. A bare vw font size does not respond to browser zoom the way users expect and can become unreadable at extremes. clamp(1rem, 0.85rem + 0.6vw, 1.25rem) keeps a rem component in the middle term, so zoom still works.
  • Line length is a responsive property too: 45–75 characters reads best. max-width: 65ch is the usual shorthand — bearing in mind ch is the width of the 0 glyph, so in a proportional face it lands nearer 75–85 actual characters.
  • Test at 200% zoom and 320px width. WCAG requires content to remain usable when text is enlarged to 200% (SC 1.4.4) and to reflow at 320 CSS px without requiring scrolling in two dimensions (SC 1.4.10) — which explicitly exempts content that genuinely needs a second axis, such as data tables and maps. A horizontally scrolling table wrapper is a permitted exception, not a failure.
Overflow is the usual culpritMost “the mobile layout is broken” bugs are one element refusing to shrink: a long unbroken string, a wide table, or a flex item whose default min-width: auto stops it going below its content size. The fixes are min-width: 0 on the flex item, overflow-wrap: anywhere on the text, and an overflow-x: auto wrapper on the table.
07 — Screens are not the only variable

Input, viewport units & user preferences

Viewport units on mobile

100vh on a phone refers to the viewport with the browser toolbars hidden, so a full-height element overflows while the toolbar is visible — the classic “my hero is taller than the screen” bug. The dynamic viewport units fix it:

svhSmall viewport — toolbars visible. Safe for “fits on screen”.
lvhLarge viewport — toolbars hidden.
dvhDynamic — changes as toolbars show and hide. Smooth, but can cause reflow while scrolling.

Touch and pointers

  • Hover does not exist on touch. Guard hover-only reveals with @media (hover: hover), and never hide essential content behind hover.
  • Tap targets: WCAG 2.2 sets a minimum of 24×24 CSS px; platform guidance is more generous (44pt on iOS, 48dp on Android). Increase the hit area with padding rather than by scaling the icon.
  • Do not sniff the user agent to decide “is mobile”. Query capabilities — width, pointer, hover — because a tablet with a trackpad and a touchscreen laptop both break UA logic.

Notches and safe areas

<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">

.bottom-bar { padding-bottom: max(1rem, env(safe-area-inset-bottom)); }

Direction

Use logical properties — margin-inline-start, padding-block, inset-inline-end — instead of left/right. The layout then mirrors automatically under dir="rtl", which is the same technique the localisation guide relies on.

08 — How you know it works

Testing & the usual failures

  • DevTools device mode is a layout preview, not a device. It gets viewport and DPR right and touch behaviour, font rendering, and real network conditions wrong. Verify on at least one real low-end Android.
  • Resize continuously rather than jumping between preset widths — bugs live between your breakpoints.
  • Automate the cheap parts: Playwright can screenshot at a set of widths, and visual regression catches the layout shift you would not have thought to check.
  • Check with content, not lorem ipsum — the longest product name and the largest number are the real test.
  • Watch CLS — responsive images without dimensions, late-loading fonts, and injected banners are the usual sources.
Closing line“Responsive is not a phase at the end. It is intrinsic sizing by default, breakpoints only for genuine rearrangement, container queries in the component library, correctly-sized images, and honouring the user's font size, motion, and colour preferences.”
09 — Drill until reflex

Scenario drills

Drill 1 — how would you implement responsive design?
“Open-ended. Walk me through your approach on a new product page.”

Answer in layers, not as a list. 1) Viewport meta tag, no zoom disabling. 2) Mobile-first base styles; fluid by default with grid minmax, wrapping flex, and clamp(), so most sizes need no query. 3) Breakpoints only where the layout must rearrange, chosen by resizing until the content breaks, expressed in rem. 4) Container queries for reusable components so they respond to their slot, not the window. 5) Responsive images with srcset/sizes and explicit dimensions. 6) Respect prefers-reduced-motion, prefers-color-scheme, and user font size; test at 320px and 200% zoom.

Drill 2 — the hero that overflows
“A height: 100vh hero looks right in Chrome desktop but is cut off on iOS Safari. Why?”

On mobile, vh is resolved against the large viewport — the height with browser toolbars hidden — so while the toolbar is visible the element is taller than the visible area. Use 100svh to guarantee it fits, or 100dvh if you want it to track the toolbar as it shows and hides, accepting the reflow that causes while scrolling.

Drill 3 — same card, two contexts
“A card component looks right in the main grid but cramped in the sidebar, at the same viewport width. What do you use?”

Container queries. The viewport is identical, so a media query cannot distinguish the two placements. Put container-type: inline-size on the card's wrapper and switch the card to a horizontal layout with @container (min-width: 400px). Now the component depends on the space it was given, which is what makes it safely reusable.

Drill 4 — what does sizes do here?
<img srcset="a-400.jpg 400w, a-800.jpg 800w, a-1600.jpg 1600w"
     sizes="(min-width: 60rem) 50vw, 100vw" src="a-800.jpg" alt="…">
sizes = rendered width hint · srcset = available widths

sizes tells the browser how wide the image will render before layout has happened: half the viewport above 60rem, full width below. The browser multiplies that by the device pixel ratio and picks the smallest candidate that meets it — so a 390px-wide DPR-3 phone needs about 1170 device pixels and takes a-1600.jpg, while a 1440px desktop at DPR 1 needs 720 and takes a-800.jpg. Omitting sizes makes the browser assume 100vw and over-download.

Drill 5 — the flex item that will not shrink
“A flex row with a long filename overflows its container instead of truncating. Why, and what is the fix?”

Flex items default to min-width: auto, which refuses to shrink below the intrinsic size of their content — and a long unbroken string has a large intrinsic minimum. Set min-width: 0 on the flex item (or overflow: hidden, which has the same effect) so text-overflow: ellipsis can take over. Grid items have an automatic minimum size too, though a narrower one — it applies only to items spanning a track whose minimum is auto, which the common 1fr case is.
