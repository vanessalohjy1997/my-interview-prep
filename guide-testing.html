Frontend interview prep

Test behaviour, not implementation.

Every test trades confidence against speed and maintenance cost. The senior signal is knowing which layer to spend on for a given risk — and being able to say why a test suite is green and still worthless.

Unit Integration E2E Flake
00 — The mindset

What each layer actually buys you

The classic test pyramid says: lots of unit tests, fewer integration, very few E2E. Kent C. Dodds' testing trophy reshapes it for frontend work: static analysis at the base, then unit, then a fat integration layer, then a thin E2E cap. The reasoning is that most frontend bugs live in the seams — component + state + network — not inside a single pure function.

Static

TypeScript + ESLint. Catches a whole class of bug for zero runtime cost. The cheapest test you will ever write is a type.

Unit

Pure logic: formatters, reducers, selectors, validation, date/number/currency maths. Milliseconds, zero flake, precise failure messages.

Integration

A component tree with real state and routing, network stubbed at the boundary. Best confidence-per-second in a frontend codebase — spend most of your budget here.

E2E

Real browser, real (or seeded) backend. The only layer that proves the whole system works. Slow, flaky-prone, expensive — reserve for critical paths.

The one principle behind all of it

Testing Library's guiding principle“The more your tests resemble the way your software is used, the more confidence they can give you.” Practically: assert on what a user can perceive and do — visible text, roles, labels, navigation — not on component state, prop names, CSS class names, or internal function calls.

The corollary is what makes it a senior answer: a test coupled to implementation fails on refactors that didn't break anything, and passes through rewrites that did. It's negative value twice over. If you can restructure a component without touching its tests, and its tests still catch a real regression, you tested the right thing.

Say this“I choose the layer by what could actually break and how expensive that break is. Money movement and auth get E2E coverage. Feature logic gets integration tests with the network stubbed at the HTTP boundary. Pure computation gets unit tests. I'd rather have 30 tests I trust than 3,000 that I re-write every refactor.”
01 — The runner

Jest vs Vitest

They're deliberately API-compatible — describe, it/test, expect, lifecycle hooks, snapshots. The differences are architectural.

JestVitest
OriginMeta; the long-standing default, huge ecosystemVite-native; the default for new Vite projects
TransformOwn pipeline (babel-jest, ts-jest, or @swc/jest) — configured separately from your buildReuses your vite.config — plugins, aliases and env resolve identically to the app
ESMHistorically awkward; needs --experimental-vm-modules for native ESMESM- and TypeScript-first by design
Mock APIjest.fn(), jest.mock(), jest.spyOn()vi.fn(), vi.mock(), vi.spyOn() — same shapes
Watch modeFast, matureFaster; HMR-style re-runs of only affected tests
DOMjsdom (or happy-dom)jsdom / happy-dom, plus a real-browser mode (stable since v4) driven by Playwright or WebdriverIO
The real reason to prefer Vitest on a Vite appConfig divergence. With Jest you maintain a second transform pipeline that has to be kept in sync with your build's aliases, JSX runtime, TS settings and env handling — a permanent source of “works in the app, fails in tests.” Vitest eliminates that class of problem by construction. On a webpack/Next codebase, Jest is still perfectly reasonable — the switch is not automatically worth the migration cost.

jsdom is not a browser

Worth naming explicitly, because interviewers probe it. jsdom implements the DOM API in Node, but it has no layout or rendering engine. So:

  • getBoundingClientRect() returns zeros. Anything measuring geometry, scroll position, or intersection needs stubbing.
  • IntersectionObserver, ResizeObserver and matchMedia aren't implemented by default — polyfill or mock them in setup.
  • CSS is parsed but not cascaded/laid out, so true visibility, overlap and responsive behaviour can't be asserted. That's what visual regression and E2E are for.

Matchers people get wrong

expect(a).toBe(b);          // Object.is — reference/primitive identity
expect(a).toEqual(b);       // recursive value equality; IGNORES undefined props
expect(a).toStrictEqual(b); // also checks undefined props, class instances, sparse arrays

expect({a:1, b:undefined}).toEqual({a:1});       // ✓ passes
expect({a:1, b:undefined}).toStrictEqual({a:1}); // ✗ fails
Snapshot testsUseful for stable serialisable output (a formatted string, an API response shape). Actively harmful as a component-level default: large snapshots are unreviewable, so the reflex becomes -u and every regression gets rubber-stamped in. Prefer targeted assertions, or inline snapshots that stay small enough to actually read in a diff.
02 — Controlling the world

Test doubles & fake timers

  • Stub — returns canned values. No assertions on it.
  • Spy — wraps a real function to record calls while (optionally) still calling through. vi.spyOn(obj,'m').
  • Mock — a replacement whose interactions you assert on (toHaveBeenCalledWith).
  • Fake — a working lightweight implementation (an in-memory store standing in for a real one).
Over-mocking is the classic anti-patternMock a module and you've frozen its interface into your test. Rename an export or change a signature and the mock happily keeps returning the old shape — the test passes while production breaks. Every mock is a place where your test can be wrong about reality. Mock at architectural boundaries (the network, time, randomness, storage) and use the real thing everywhere inside.

Fake timers

// Deterministic time — no sleeping, no flake
beforeEach(() => { vi.useFakeTimers({ now: new Date('2026-01-01T00:00:00Z') }); });
afterEach(()  => { vi.useRealTimers(); });

it('debounces the search', async () => {
  const spy = vi.fn();
  const debounced = debounce(spy, 300);
  debounced(); debounced(); debounced();

  await vi.advanceTimersByTimeAsync(299);
  expect(spy).not.toHaveBeenCalled();
  await vi.advanceTimersByTimeAsync(1);
  expect(spy).toHaveBeenCalledTimes(1);   // ✓ deterministic, instant
});
Two traps(1) Fake timers plus userEvent deadlock unless you tell user-event to use them: userEvent.setup({ advanceTimers: vi.advanceTimersByTime }). user-event inserts real delays between key/pointer events, and with the clock frozen those never resolve. (2) Use the *Async advance variants when promises are involved, so microtasks get a chance to flush between ticks.

Freeze anything non-deterministic, not just timers: Date.now, Math.random, crypto.randomUUID, locale and timezone (TZ=UTC in CI — otherwise a date test passes in Singapore and fails in London), and any ID generator. A test that depends on when or where it runs is a flake waiting to happen.

03 — Components as users see them

React Testing Library

Query priority — memorise this order

RTL deliberately makes the accessible queries easiest and getByTestId the last resort, because a query that finds an element the way a screen reader does is an accessibility assertion.

TierQueryUse for
1getByRoleAlmost everything. getByRole('button',{name:'Submit'}) — the accessible name matters.
1getByLabelTextForm fields.
1getByPlaceholderTextOnly when there's no label (which is itself a bug).
1getByTextNon-interactive content.
1getByDisplayValueThe current value of a filled input.
2getByAltText / getByTitleImages and elements with title attributes.
3getByTestIdEscape hatch — dynamic text, canvas, or nothing user-visible to target.

get vs query vs find — the question that separates candidates

PrefixNot foundAsync?Use for
getBy…Throws immediatelyNoIt should already be there
queryBy…Returns nullNoAsserting absence — the only correct choice for not.toBeInTheDocument()
findBy…Rejects after timeoutYesIt will appear (after a fetch, transition, or lazy load)

Each has an …AllBy variant returning an array (and queryAllBy returns [] rather than throwing). findBy is literally getBy wrapped in waitFor, retrying until the element appears or the timeout (1000 ms by default) elapses.

userEvent over fireEvent

// fireEvent: dispatches ONE synthetic event. Not what a user does.
fireEvent.change(input, { target: { value: 'BTC' } });

// userEvent: the full interaction sequence a real user produces —
// pointerdown, focus, keydown/keypress/keyup per character, input, change.
// Catches disabled elements, pointer-events:none, and missing focus handling.
const user = userEvent.setup();          // v14+: call before render
await user.type(screen.getByLabelText('Symbol'), 'BTC');
await user.click(screen.getByRole('button', { name: 'Search' }));

expect(await screen.findByRole('table')).toBeInTheDocument();

A complete, idiomatic test

it('shows an error when the order is rejected', async () => {
  server.use(http.post('/api/orders', () =>
    HttpResponse.json({ message: 'Insufficient balance' }, { status: 400 })));

  const user = userEvent.setup();
  render(<OrderForm />);

  await user.type(screen.getByLabelText(/amount/i), '10');
  await user.click(screen.getByRole('button', { name: /place order/i }));

  // findBy* waits for the async result — no arbitrary sleep, no waitFor boilerplate
  expect(await screen.findByRole('alert')).toHaveTextContent('Insufficient balance');
  expect(screen.getByRole('button', { name: /place order/i })).toBeEnabled();
});
Smells that fail an interviewcontainer.querySelector('.btn-primary') (couples to CSS); asserting on component state or a spy on an internal handler; await new Promise(r => setTimeout(r, 500)) instead of findBy; wrapping everything in manual act(); testing that a child component “was rendered with props X” by mocking the child.

What is act() and why the warning?

act() tells React “I'm done making updates — flush effects and re-renders now, before I assert.” RTL already wraps render, fireEvent and userEvent in it, so you rarely call it directly. The “not wrapped in act(…)” warning almost always means a state update happened after your test finished awaiting — usually an un-awaited promise resolving, or a timer firing after the component should have settled. The fix is to await the resulting UI change with findBy/waitFor, not to sprinkle act() until the warning stops.

For custom hooks, renderHook (shipped from @testing-library/react itself) is fine — but prefer testing the hook through a component that uses it when the hook's value is really about UI behaviour.

04 — Stub at the boundary

Mock Service Worker

MSW intercepts requests at the network layer — a Service Worker in the browser, request interceptors in Node. Your app calls real fetch/axios; MSW answers.

// handlers.ts — MSW v2 API
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/orders', () => HttpResponse.json([{ id: 1, symbol: 'BTCUSDT' }])),
  http.post('/api/orders', async ({ request }) => {
    const body = await request.json();
    if (body.amount > 100) return HttpResponse.json({ message: 'Too large' }, { status: 400 });
    return HttpResponse.json({ id: 2, ...body }, { status: 201 });
  }),
];

// setup.ts
import { setupServer } from 'msw/node';   // note: msw/node, not msw

const server = setupServer(...handlers);
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));  // catch typos + real leaks
afterEach(() => server.resetHandlers());   // per-test overrides don't leak
afterAll(()  => server.close());

Why it beats vi.mock('./api') or stubbing global.fetch:

  • It survives refactors. Swap axios for fetch, or React Query for SWR, and the tests don't change — the contract under test is HTTP, which is the thing that's actually shared with the backend.
  • Real code paths run. Your serialisation, headers, auth interceptors, error mapping and retry logic all execute, instead of being skipped by a module mock.
  • One set of handlers, three consumers — unit/integration tests, Storybook, and local development against a not-yet-built API.
  • Error states are trivial to exercise: server.use() in a single test to return 500, a 400 with a body, or a delayed response.
The honest caveatMSW makes your mocks consistent, not correct. If the backend changes a field name, your handlers still return the old shape and everything stays green. Close that gap with schema-derived handlers (OpenAPI/Zod), contract testing (Pact), or a thin E2E layer that hits a real seeded environment. Naming this trade-off unprompted is a strong senior signal.
05 — The real browser

Playwright vs Cypress

The architectural difference drives every other difference: Cypress runs your test code inside the browser, in the same event loop as your app. Playwright drives the browser out-of-process over a debugging protocol.

PlaywrightCypress
ArchitectureOut-of-process, protocol-drivenTest code runs in-browser alongside the app
BrowsersChromium, Firefox, WebKit (real Safari engine)Chromium family, Firefox, WebKit (experimental)
Multi-tab / multi-originNative — contexts, pages, popups, downloadsConstrained by design; cross-origin needs cy.origin()
WaitingAuto-waiting for actionability + retrying web-first assertionsAutomatic command retry + retrying assertions
ParallelismBuilt-in workers & --shard, freeRequires Cypress Cloud + --record; free tier is volume-capped, smart orchestration is paid
DebuggingTrace viewer: DOM snapshots, network, console, screenshot filmstrip per stepTime-travel in an excellent interactive runner
LanguagesTS/JS, Python, Java, .NETJS/TS

Cypress's in-browser model gives a genuinely great interactive debugging experience and direct access to app internals. Playwright's out-of-process model is why it handles multiple tabs, multiple origins, downloads, and true cross-browser testing more naturally, and why free parallelism is straightforward. For a new project in 2026, Playwright is the default recommendation — but “we already have 400 stable Cypress tests” is a perfectly good reason not to migrate.

Auto-waiting is the whole point

// A Playwright locator is a lazy query, re-resolved on every action.
// Before clicking, it waits for the element to be visible, stable,
// enabled, and able to receive events.
await page.getByRole('button', { name: 'Place order' }).click();

// Web-first assertions RETRY until they pass or time out —
// this is what replaces sleeps.
await expect(page.getByRole('alert')).toHaveText('Order filled');

// WRONG — resolves once, immediately, and will flake:
expect(await page.getByRole('alert').textContent()).toBe('Order filled');
Note the await positionawait expect(locator).toHaveText(…) retries. expect(await locator.textContent()) snapshots a value once. Same characters, completely different reliability — and a very common interview follow-up.

Things that make an E2E suite survivable

  • Auth once. Log in in a setup project, save storageState, and have every test start authenticated. Logging in through the UI in 200 tests is the single biggest waste of E2E wall-clock.
  • Isolation via browser contexts. Each test gets a fresh context — separate cookies, storage, cache — which is cheap compared with a new browser process.
  • Seed data per test, ideally via API rather than UI, with a unique identifier so parallel workers can't collide.
  • Trace on retry. trace: 'on-first-retry' gives you a full recording of the failure — DOM snapshots, network, console — without paying the cost on green runs. It is the difference between debugging a CI failure in five minutes and never reproducing it.
  • Shard in CI (--shard=1/4) and merge the reports.
  • Decide what E2E is for: critical revenue and auth paths. Everything else belongs one layer down.
06 — Regressions you can't assert on

Visual regression testing

Functional tests can't catch a broken layout, a wrong token, overlapping text, or a component that renders off-screen. Visual regression fills that gap by rendering, screenshotting, and diffing against an approved baseline.

// Playwright — built in
await expect(page).toHaveScreenshot('order-form.png', {
  animations: 'disabled',              // freeze CSS animations/transitions
  mask: [page.getByTestId('timestamp')], // paint over volatile regions
  maxDiffPixelRatio: 0.01,             // tolerance for AA noise
});
// Update baselines deliberately: npx playwright test --update-snapshots

The hard part is determinism, not diffing

  • Pin the rendering environment. Font rasterisation and antialiasing differ between macOS, Windows and Linux, so a baseline generated on a laptop will never match CI. Generate and compare inside the same container image (Playwright publishes matched Docker images).
  • Kill motion and time. Disable animations, freeze the clock, stop carousels and spinners, and wait for fonts (document.fonts.ready) and images to finish loading.
  • Kill variable data. Stub the network with fixed fixtures; mask avatars, relative timestamps, live prices, and anything randomised.
  • Tolerance is a trade. Too tight and antialiasing noise fails every run; too loose and you miss a one-pixel-shifted button. Tune per surface rather than globally.

The tooling landscape

ToolModelNotes
PlaywrightSelf-hosted pixel diffFree, baselines live in git. You own the infra and the review UX.
ChromaticCloud, Storybook-nativeSnapshots every story; review/approve UI; opt-in TurboSnap re-snapshots only the stories a change affects.
PercyCloud, framework-agnosticHooks into an existing E2E suite; renders across widths/browsers.
ApplitoolsCloud, “visual AI”Perceptual rather than pixel diffing to cut antialiasing false positives.
Where it pays off mostDesign systems. Each component is small, isolated and deterministic, so signal is high and noise is low — and one token change can silently affect a hundred consumers. Full-page visual tests on data-heavy app screens are where teams usually drown in false positives and start rubber-stamping approvals, which is worse than having no visual tests at all.

Storybook is the natural host: stories are already isolated, deterministic renders. Add play functions to drive interactions, run them in CI with the Vitest addon (which supersedes the older Playwright-based test runner), and layer visual snapshots on top — one artefact serving as documentation, interaction test, and visual baseline.

Adjacent “full regression” layers worth naming

  • Accessibility regression — axe-core via jest-axe in component tests or @axe-core/playwright in E2E. Automated checks catch somewhere between the classic 20–30% estimate and Deque's own published 57% figure; they don't replace manual keyboard and screen-reader passes.
  • Performance regression — Lighthouse CI with budgets on LCP/CLS/bundle size, failing the PR on regression.
  • Contract regression — Pact or schema-derived mocks so the frontend's assumptions about the API stay verified against the provider.
07 — The suite killer

Flakiness

A flaky test is worse than no test: it trains the team to re-run CI instead of reading failures, and eventually a real regression gets re-run away. Treat flake as a P1 bug in the suite, not as background noise.

CauseFix
Hard-coded sleepsRetrying assertions (findBy, await expect(locator)). A sleep is a bet on the slowest CI machine you'll ever have.
Animations / transitionsDisable motion in the test environment; wait for the settled state, not a duration.
Real clock & timezoneFreeze time, pin TZ=UTC, avoid tests that break at month boundaries or DST.
Shared state between testsReset stores, caches, MSW handlers and the DOM per test. Never let ordering matter — run in random order to prove it.
Shared backend dataUnique seeded fixtures per test/worker so parallel runs can't collide on the same record.
Real networkStub it, and set onUnhandledRequest:'error' so an unstubbed call fails loudly instead of hitting the internet.
CI resource contentionA slow machine exposes latent races. Cap workers, and raise timeouts only after you've ruled out a real race.
An actual app raceSometimes the test is right and the app is racy. Investigate before “fixing” the test — this is the failure mode worth catching.
On retriesRetries are a reporting tool, not a fix. Enable them so a flake doesn't block a deploy, but record every retry, surface a flake-rate dashboard, and quarantine repeat offenders into a non-blocking job with an owner and a deadline. Silent retries turn a flaky suite into a suite nobody trusts.

Why flake compounds — the arithmetic

The number is what makes this argument land in a planning meeting. If each test independently passes 99.9% of the time, a suite of 500 tests fails ~39% of runs — 0.999⁵⁰⁰ ≈ 0.61. At 99% per test, a 500-test suite essentially never goes green. Per-test flakiness that sounds negligible is a suite that is red more often than not, which is why “it only fails sometimes” is not a defensible position at scale.

// probability the whole suite passes
0.999 ^ 100  = 90%     // annoying
0.999 ^ 500  = 61%     // two in five runs are red for no reason
0.99  ^ 500  = 0.7%    // effectively never green

The second-order cost is the one that actually kills the suite: once a red build is routinely meaningless, people stop reading failures and start re-running. At that point a genuine regression is indistinguishable from noise, and the suite has become a tax that provides no safety. That is the argument for treating flake as a P1 defect rather than as maintenance.

The root cause is almost always the same shape

Nearly every flake reduces to asserting on a moment rather than on a condition. A sleep, a fixed timeout, an assertion immediately after an action — each assumes the app reached a state by a particular time, which is a bet on machine speed. Retrying assertions invert it: they poll a condition until it holds or the timeout expires, so a fast machine finishes fast and a slow one still passes.

// bets on timing — fails on a loaded CI box
await page.click('#save');
await page.waitForTimeout(500);
expect(await page.textContent('.status')).toBe('Saved');

// asserts on a condition — same code, no bet
await page.click('#save');
await expect(page.locator('.status')).toHaveText('Saved');   // auto-retries

The exception worth naming, because it's the one that matters: sometimes the test is right and the app is racy. A test that passes locally and fails under CPU contention may be correctly detecting a real race the user will eventually hit. Reaching for a longer timeout is how a genuine bug gets buried, so the rule is to understand the failure before stabilising it.

08 — Making it pay for itself

Coverage & CI strategy

What testing actually costs

Being able to state the cost is what separates a considered testing answer from an evangelical one. Every test is code you maintain: it has to be read, updated when behaviour changes, and debugged when it fails. That gives a simple test for whether a test is worth writing — will it fail more often for a real regression than for a harmless refactor? A test coupled to implementation fails constantly for the wrong reason and is negative value even when green, because it makes people afraid to refactor.

The costs to name explicitly, roughly in order of how often they bite:

  • CI wall-clock is a shared tax. A suite that takes 25 minutes changes how people work — they batch changes, they stop running it locally, and every review cycle gets longer. Speed is a feature of the suite, not a nice-to-have, which is the real argument for the shape of the trophy: integration tests give the best confidence per second.
  • E2E tests are the expensive ones on every axis — slowest to run, most flake-prone, hardest to debug from a CI log, and they need an environment. That's why they're a thin cap over critical paths (login, checkout, money movement) rather than a coverage strategy.
  • Mocks drift. A mocked API that no longer matches the real one gives you a green suite and a broken product — the most dangerous failure mode in testing, because it is confidently wrong. That's the argument for stubbing at the HTTP boundary with MSW rather than mocking your own modules, and for contract tests where the API is owned by another team.
  • Snapshot tests rot fastest. A large snapshot fails on every unrelated change, and the fix is a keystroke (-u), so they get updated without being read. A snapshot nobody reads is a file, not a test.
The answer to “what's your testing philosophy?”“I choose the layer by what could break and how expensive that break is, and I treat suite speed and flake rate as first-class. I'd rather have thirty tests the team trusts and reads than three thousand that get re-run until green. The test I want to write is one that fails when behaviour changes and survives a refactor that didn't change behaviour.”

Coverage: a map, not a score

  • Line/statement coverage says a line executed, not that anything was asserted. You can hit 100% with zero expect calls.
  • Branch coverage is the more informative number — it tells you which conditional paths never ran.
  • A blanket global threshold pushes people to write tests for trivial getters and to add /* istanbul ignore next */. Diff coverage on changed lines is a far better gate.
  • Instrumentation: Istanbul (transform-based, runtime-agnostic) vs V8/native (Vitest's default — faster, no transform, and as accurate as Istanbul since v3.2's AST-based remapping).
  • Use coverage to find untested error paths and branches — that's where bugs live — not to hit a number.

A pipeline that stays fast

on every commit  typecheck + lint + unit/integration   // seconds–2 min, blocking
on every PR      E2E smoke (critical paths, sharded) // ~5–10 min, blocking
                 visual diff on changed components   // review + approve
on merge/nightly full E2E matrix, cross-browser,
                 a11y sweep, Lighthouse budgets     // non-blocking, alerts

Levers when it gets slow: shard E2E across workers; run only tests affected by the diff for the fast lane; cache dependencies and browser binaries; run typecheck/lint/unit as parallel jobs rather than sequential steps; and keep the blocking set small enough that people don't start bypassing it.

What to test — and what not to

Worth testing

Business rules and edge cases. Error and empty states. Anything that has broken before (write the regression test with the fix). Money, auth, permissions. Accessibility affordances. Public contracts of shared components.

Not worth testing

That React renders props. Third-party library internals. Static markup with no logic. Implementation details — state shape, private handlers, class names. Anything TypeScript already proves.

Say this“I don't chase a coverage number — I gate on diff coverage and spend the budget where failure is expensive. Every production bug gets a regression test as part of the fix, which means the suite grows toward where things actually break rather than where it's easy to write tests.”
09 — Drill until reflex

Scenario drills

Drill 1 — the wrong query
expect(screen.getByText('Deleted')).not.toBeInTheDocument();
Can never pass — getBy throws before the assertion runs

getBy* throws when nothing matches, so if the element is absent the test errors out rather than passing. Use queryBy*, which returns null: expect(screen.queryByText('Deleted')).not.toBeInTheDocument(). And if the element disappears asynchronously, wait for it: await waitForElementToBeRemoved(() => screen.queryByText('Deleted')).

Drill 2 — green suite, broken product
“We have 92% coverage and shipped a checkout bug that took payments and never created the order. How is that possible?”

Coverage measures execution, not assertion, and certainly not integration. The likely picture: heavily unit-tested pieces that all pass in isolation, with the failure living in the seam between them — or mocks that froze an interface the backend has since changed, so tests assert against a fiction. High line coverage with mocked collaborators can approach zero real confidence. Fixes: move the budget to integration tests with the network stubbed at the HTTP boundary rather than modules mocked; add one E2E test for the payment path end-to-end; add a regression test for this specific bug; and gate on diff coverage plus branch coverage rather than a global line percentage.

Drill 3 — the timer deadlock
“A test using vi.useFakeTimers() plus userEvent.type() hangs until the test times out. Why?”

user-event inserts real delays between the events it dispatches (per keystroke, per pointer step). With the clock faked, those delays never elapse, so the promise never resolves. Wire user-event to the fake clock: userEvent.setup({ advanceTimers: vi.advanceTimersByTime }). Related: when promises are involved, advance with the async variants (advanceTimersByTimeAsync) so queued microtasks flush between ticks.

Drill 4 — the flaky assertion
expect(await page.locator('.toast').textContent()).toBe('Saved');
The await is in the wrong place — no retry

This resolves the text content exactly once, the moment the line runs, so it fails whenever the toast hasn't rendered yet. Playwright's web-first assertions retry until they pass or time out: await expect(page.getByRole('status')).toHaveText('Saved'). Note the second improvement too — a role-based locator instead of a CSS class, so a styling refactor doesn't break the test.

Drill 5 — the noisy visual suite
“Our visual regression job fails on ~30% of PRs with diffs nobody can see. The team now approves every diff without looking. What do you do?”

Rubber-stamped approvals mean the suite has negative value, so treat determinism as the bug. Diagnose the source of noise: are baselines generated on developer machines rather than in the CI container (font antialiasing differs per OS)? Are animations, spinners, timestamps, avatars or live prices unfrozen? Are fonts and images awaited before capture? Fix those, mask genuinely volatile regions, and set a tolerance per surface rather than globally. Then narrow scope — component-level snapshots from Storybook are far more stable than full-page shots of data-heavy screens. If it can't be made deterministic, delete it; a check nobody reads is worse than no check.

Drill 6 — mock or not?
“You're testing an OrderTable that fetches via React Query and renders rows. What do you mock?”

Mock the network and nothing else. MSW returns fixture JSON for GET /api/orders; React Query, the fetch wrapper, error mapping and the component all run for real. Then assert what a user sees: loading state, rows with the right values, the empty state, and the error state (via server.use() returning a 500). Don't mock React Query, the fetch client, or child components — each of those replaces real behaviour with an assumption, and turns a refactor into a test rewrite. Remember to give each test a fresh QueryClient with retries off, or cached data and retry backoff will leak between tests and cause flake.

Drill 7 — designing the suite
“You join a team with no tests and a 40-minute manual QA pass before each release. Where do you start?”

Start from risk, not from coverage. First, enumerate the handful of flows where a failure is unacceptable — login, placing an order, withdrawal — and write E2E tests for exactly those, so the release gate stops depending on a human remembering. In parallel, turn on TypeScript strictness and lint, which retire a whole class of bug for free. Then require a regression test with every bug fix, so coverage grows toward real failure sites. Add integration tests for new features as they're built, with the network stubbed at the HTTP boundary. Explicitly do not attempt a retroactive coverage push on legacy code — it's the highest-effort, lowest-signal work available. Track the metric that matters: how much of that 40-minute manual pass has been automated away.

Drill 8 — the suite is red half the time
“CI fails on about 40% of runs and the team just re-runs it. How do you approach that?”

First I'd make the case with arithmetic, because “a few flaky tests” sounds tolerable: at 99.9% per-test reliability, 500 tests fail about 39% of runs. So this is consistent with almost every individual test looking fine. Then: enable retries but record them, build a flake-rate ranking, and fix from the top — the distribution is usually very skewed, so a handful of tests cause most of it. Quarantine repeat offenders into a non-blocking job with an owner and a deadline rather than deleting or ignoring them. Structurally, most fixes are replacing timing bets with condition-based waits, resetting shared state per test, freezing the clock and timezone, and seeding unique fixtures per worker. The one thing I'd guard against is reflexively raising timeouts — sometimes the test is correctly detecting a real race under CPU contention, and stabilising it buries the bug.

Drill 9 — green suite, broken product
“All tests pass but production broke when the API changed a field name. What was wrong with the tests?”
Mock drift — the fixtures encoded an API that no longer exists

The tests were asserting against a fixture, and the fixture was a copy of the API's shape frozen at the moment someone wrote it. Nothing in the suite could ever detect that the real contract moved. It's the most dangerous class of test failure because it's confidently green. Mitigations, in increasing strength: stub at the HTTP boundary with MSW and share one fixture set so there's a single place to update; generate fixtures from the API's own schema or types so a change breaks compilation; add contract tests if the API is owned by another team; and keep a handful of E2E tests running against a real environment so at least the critical paths touch the actual contract.

Drill 10 — is this test worth writing?
“A reviewer asks you to add a test asserting a component calls trackEvent with exact arguments on mount. Do you?”

It depends on whether analytics is a product requirement or an implementation detail. If someone's dashboard genuinely breaks when that event stops firing, it's behaviour and worth a test — though I'd assert it at the boundary (the network call, via MSW) rather than by spying on our own module, so a refactor of how we call the tracker doesn't fail it. If it's incidental, this is the test I'd push back on: it's coupled to implementation, so it fails on refactors that broke nothing, and it passes through rewrites that broke something. My filter is whether the test will fail more often for a real regression than for a harmless change — if not, it's maintenance cost with no safety.
