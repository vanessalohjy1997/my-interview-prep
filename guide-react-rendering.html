Frontend interview prep

Rendering is calling your function, not touching the DOM.

Most React performance and correctness questions reduce to one thing: knowing exactly when React re-runs your component, what it does with the result, and why keys and referential identity decide the rest.

00 — The mental model

What “render” actually means

A render is React calling your component function to produce an element tree — a plain-object description of the UI (“what it should look like”). That is not the same as updating the DOM. React computes the description first, diffs it, then applies the minimal real-DOM changes separately.

  • Render = run components, build the virtual tree. Pure, no DOM writes.
  • Commit = apply the diffed changes to the real DOM, run refs and effects.
Say this“Re-rendering doesn't mean the DOM changed. When React re-renders it diffs, and only touches the DOM where the diff found a difference — and it may skip re-running the component entirely when memo or a bailout applies.”
01 — Two phases

Render vs commit

Render phaseCommit phase
JobCall components, build & diff the element treeApply DOM mutations, run refs & effects
PurityMust be pure — no side effects, no DOM writesSide effects allowed
Interruptible?Yes for transition / deferred work — can pause, abort, restart. Sync work (a click, a controlled input) still renders to completionNo — synchronous, runs to completion

Because the render phase can be paused and even restarted, doing side effects there (mutating a ref, firing a request, subscribing) is a bug: it may run twice or be thrown away. Side effects belong in event handlers or effects, which run during/after commit.

Be precise about “interruptible”Not every render is time-sliced. React only yields for renders on the transition, retry, idle and offscreen lanes — the work behind startTransition, useDeferredValue, Suspense retries and hidden <Activity>. A click handler's setState (sync lane) and a plain root.render or setTimeout update (default lane) render synchronously, start to finish, on one task. The time-sliced loop checks the Scheduler's shouldYield() between fibers and yields after 5 ms (frameYieldMs), then re-posts itself with a MessageChannel message so the browser can paint and handle input in between. “Interruptible” therefore means: a higher-priority update arriving during one of those gaps throws the in-progress transition tree away and restarts it after the urgent render commits.
  • useLayoutEffect runs synchronously at the end of the commit phase — after React applies the DOM mutations, before the browser paints — for DOM measurement/adjustment you don't want to flicker.
  • useEffect runs after paint (asynchronously) — the default for most effects. Caveat worth knowing: when the effect was caused by an interaction like a click, React may flush it before paint.

useLayoutEffect, properly

The ordering within a single commit is worth memorising, because it is exactly what the question is testing:

  1. Old refs are detached (set to null — or, since React 19, the cleanup function a ref callback returned is called instead) and useLayoutEffect cleanups run — both in the mutation phase, before the DOM changes. useInsertionEffect (for CSS-in-JS style injection) also fires here, before any layout effect, with refs not yet attached.
  2. React applies the DOM mutations.
  3. useLayoutEffect setups run and refs are attached — synchronously, blocking the browser, and bottom-up, which is why a parent's layout effect can already read a child's ref.current.
  4. The browser paints.
  5. useEffect cleanups run, then its setups.

So the rule is: if the user must never see the intermediate state, it has to be a layout effect. The canonical cases are measuring a node and immediately repositioning something based on the measurement — a tooltip that would otherwise flash in the wrong place — scroll restoration, and reading a value from the DOM before the browser has a chance to show it.

useLayoutEffect(() => {
  const { height } = ref.current.getBoundingClientRect();
  setPosition(anchorTop - height);   // re-render before paint: no flicker
}, [anchorTop]);
The two costsIt blocks paint, so anything slow in a layout effect is directly visible as a delay — never fetch or do heavy work there. And it does not run during server rendering — no effect does — so a server-rendered component that positions itself in a layout effect ships HTML in the wrong position and corrects it on the first client render, which is the visible cost. React 16.8–18 also logged “useLayoutEffect does nothing on the server”; React 19 removed that warning (facebook/react #26395) because teams were silencing it with a useIsomorphicLayoutEffect shim instead of fixing the flash. If you still see the shim in a codebase, that is why it exists — it is no longer needed on 19.
Say this“useEffect by default. useLayoutEffect only when I am measuring the DOM and writing back to it in the same frame, because that is the only case where paint order is observable.”

Effects that read the latest props without re-running: useEffectEvent (19.2)

The classic follow-up: “your effect reconnects to the chat room every time theme changes, because theme is in the dependency array.” Since React 19.2 the answer is useEffectEvent: wrap the non-reactive part in an Effect Event, which always sees the latest props and state, and leave it out of the dependency array (the lint rule enforces this). Only call it from inside effects, never pass it to children, and do not use it to silence a dependency you actually want to react to.

const onConnected = useEffectEvent(() => showNotification('Connected!', theme));
useEffect(() => {
  const conn = createConnection(serverUrl, roomId);
  conn.on('connected', () => onConnected());
  conn.connect();
  return () => conn.disconnect();
}, [roomId]);   // theme changes no longer reconnect
02 — The cause of every re-render

What actually triggers a re-render

A component re-renders for one of these reasons — and, notably, “its props changed” is not one of them directly:

  1. Its own state changed — a useState/useReducer update (and the new value differs by Object.is).
  2. Its parent re-rendered — by default a parent re-render re-renders all its children, whether or not their props changed.
  3. A Context it consumes changed — every consumer of that context re-renders when the provider's value changes.

Props “changing” is a consequence of reason 2, not an independent trigger — a child re-renders because its parent did, and it happens to receive new props. React's default is “re-render the subtree,” and it only bails out when you opt in (React.memo) or the state value is identical.

Common misconception“My component only re-renders when props change.” No — it re-renders whenever its parent does, even with identical props, unless it's wrapped in React.memo.

Why the default is “re-render the subtree”

It looks wasteful until you consider the alternative. To skip a child, React would have to compare its props — but props can be anything, so a correct comparison is either shallow (cheap but wrong when a nested field changed) or deep (correct but potentially more expensive than just re-rendering). React's position is that re-running a component is usually cheaper than proving you don't need to, so the default is to run it, and opting into comparison is your call via memo.

That's also why the honest framing of “unnecessary re-renders” is more measured than the folklore. A render is a function call plus a diff over a plain-object tree; for a small component that is microseconds. It becomes a problem when it's wide (hundreds of components), deep (an expensive subtree), or frequent (per keystroke, per socket message). Those three words are the ones to say — they turn “too many re-renders” into something measurable.

The fix that isn't memo: move state down, or pass children

Before reaching for memo, restructure. Most “the whole page re-renders when I type” problems are state living above the tree that cares about it.

// state at the top: every keystroke re-renders ExpensiveTree
function Page(){
  const [q, setQ] = useState('');
  return (<><input value={q} onChange={e => setQ(e.target.value)} />
          <ExpensiveTree /></>);
}

// 1. move state down — the input owns it, the tree never hears about it
function Page(){ return (<><SearchBox /><ExpensiveTree /></>); }

// 2. or lift the expensive part into children — it's created by the parent,
//    so the same element object is reused and React bails out on it
function Shell({ children }){
  const [q, setQ] = useState('');
  return (<><input value={q} onChange={e => setQ(e.target.value)} />{children}</>);
}
<Shell><ExpensiveTree /></Shell>   // ExpensiveTree doesn't re-render

The second one is the trick worth knowing, and it's a genuinely good interview answer because it explains a real bailout: children is created in the parent's render, so when Shell re-renders due to its own state, the children prop is the same element object by reference as last time — and React skips re-rendering an element it has already seen unchanged. No memo, no dependency arrays, and it can't be defeated by an unstable prop.

The mechanism, if pressed: in beginWork React compares the fiber's previous props object to the new one by identity (oldProps === newProps). A re-created element always has a fresh props object, so that check fails for every normal child — but an element you reuse carries the very same props object, so the check passes; if the fiber also has no pending update on the current lanes it bails out, and if childLanes is empty the whole subtree is skipped. That identity check is the same reason React.memo falls back to a shallow per-prop comparison: the props object itself is never equal.

03 — What React is actually holding

The Virtual DOM & Fiber

JSX compiles to function calls that return plain objects. There is nothing magic in a React element:

<Button size="lg" onClick={fn}>Save</Button>

// becomes, roughly:
{ type: Button, key: null, props: { size: 'lg', onClick: fn, children: 'Save' } }
// (before React 19 there was also a top-level `ref`; it is now just another prop)

The tree of those objects is the virtual DOM: a cheap description of what the UI should look like. On each render React builds a new one, compares it with the previous, and derives the minimal set of real DOM operations. You describe the destination; React works out the moves.

Answer the “is it faster?” question honestlyThe virtual DOM is not faster than well-targeted direct DOM manipulation — it is an extra layer of work on top of it. What it is faster than is the naive alternative it replaced: re-rendering everything, or hand-maintaining consistency between state and DOM. Its real value is the programming model — you write a pure function of state instead of a pile of mutations — and it is fast enough because object comparison is cheap and DOM writes are the expensive part. Saying this rather than “the virtual DOM is fast” is the difference between a mid and a senior answer.

Fiber

Fiber is the reconciler React has used since version 16. A fiber is a mutable object representing one unit of work — one node of the tree, whether a component, a host element like div, or a text node — holding its type, props, state, effects, and pointers to its child, sibling and parent. Because the tree is a linked structure rather than a recursive call stack, React can walk it incrementally: do a bit of work, hand control back to the browser, and resume.

The real field names are worth having, because “it's a linked list” invites the follow-up:

  • tag, type / elementType, key, stateNode — what kind of node it is, the component function or tag name, and the class instance or DOM node it owns.
  • return, child, sibling, index — the traversal pointers. return is the parent; there is no pointer to the previous sibling, which is why the list diff can only walk forwards.
  • pendingProps / memoizedProps, memoizedState, updateQueue — the props being applied and the last committed ones; for a function component memoizedState is the linked list of hooks, in call order, which is why hook order must be stable.
  • flags, subtreeFlags, deletions, lanes, childLanes — the side-effect bitmask the commit phase reads (Placement, Update, Ref, Passive…) and the pending-priority bitmask the scheduler reads.
  • alternate — the pointer to this fiber's twin in the other tree; the source comments call it “double buffering pooling” because React only ever needs two versions of any node.
  • Two trees. React keeps the current tree, which is on screen, and builds a work-in-progress tree alongside it. Commit is a pointer swap — a double-buffering scheme, which is why an abandoned render costs nothing visible.
  • Interruptible render. Work can be paused, resumed, reprioritised, or thrown away entirely. This is the machinery under useTransition and useDeferredValue.
  • Lanes. Updates are tagged with a priority — a click is urgent, a transition is not — so a typed character can interrupt a large list re-render already in progress, provided that list render was on a transition lane.
  • Commit is never interrupted. Everything above applies to the render phase only; the DOM is mutated in one synchronous pass so the user never sees a half-applied tree.

This is also why render must be pure: a function that may be called twice and discarded cannot be trusted with side effects.

Lanes, concretely

A lane is one bit in a 31-bit mask stored on the root and on every fiber (lanes, childLanes). Lower bit = higher priority. The ones to know: SyncLane (discrete events — click, keydown, and flushSync), InputContinuousLane (drag, scroll, mousemove), DefaultLane (timers, network callbacks, the initial root.render), fourteen TransitionLanes, four RetryLanes for Suspense retries, then IdleLane and OffscreenLane for hidden <Activity> content. A bitmask means the scheduler can ask “what's the most urgent pending work?” with a single lanes & -lanes, and every fiber can say cheaply whether anything below it needs work.

  • Starvation guard. A lane that keeps getting interrupted is not deferred for ever: sync and continuous-input work expires after 250 ms, default and transition work after 5 000 ms, at which point React forces it to finish synchronously (markStarvedLanesAsExpired). Idle and offscreen work never expires.
  • Transitions render independently (19.3). Until 19.2, every pending transition was entangled into one render, so a slow transition held up an unrelated fast one. React 19.3 renders them separately, so a heavy chart update no longer blocks a cheap tab switch that happened to overlap it. The useTransition reference page still says transitions are batched together — the release notes are the newer source.
  • <Activity mode="hidden"> (stable in 19.2) is the public face of the offscreen lane: the subtree keeps its state, its effects are cleaned up, and its updates are deferred until React has nothing else to do — so you can pre-render the next tab or keep a previous one warm without competing with visible work.
Worth mentioning if the topic comes upNot every framework does this. Solid and Svelte compile to fine-grained reactivity: a signal updates exactly the DOM nodes that depend on it, with no diffing at all. React's bet is different — re-run components and diff — which trades some raw update cost for a simpler mental model and a single re-render path. React Compiler is the attempt to recover much of that cost automatically by memoising for you.

04 — The diff

Reconciliation & why keys matter

Reconciliation is how React decides what changed between the old and new element trees. A full tree diff is O(n³); React uses an O(n) heuristic built on two assumptions:

  • Different element type → rebuild. If a node's type changes (div → span, or ComponentA → ComponentB), React tears down that subtree and its state and builds a new one.
  • Same type and same key → reuse. It keeps the instance and DOM node, updates changed props, and recurses into children. Change the key on the same type and React discards the old instance and mounts a fresh one.
  • Lists are matched by key. Keys give siblings a stable identity across renders.

The index-as-key bug

{items.map((item, i) => <Row key={i} item={item} />)}

Using the array index as a key means that when the list reorders, or you insert/remove at the front, the keys stay 0,1,2… but now point at different items. React reuses the wrong instances: local state, focus, and uncontrolled input values “stick” to the position instead of the data — so a deleted first row appears to delete the wrong one, or typed text jumps rows.

The ruleA key must be stable, unique, and derived from the item's identity (a database id) — never the array index (unless the list is static and never reorders) and never Math.random() (which forces a remount every render).

What the list diff actually does

Because a fiber only points forward (sibling, no back-pointer), reconcileChildrenArray cannot search from both ends the way a classic diff would. It runs in two passes: first it walks old and new children by index while the keys match, which is the whole job for the common append/update case; the moment a key differs it stops, puts the remaining old children into a Map keyed by key (or index), and looks each remaining new child up in it. Moves are then decided with a single lastPlacedIndex cursor and only ever move nodes forward: a node whose old index is behind the cursor stays put, anything else is flagged Placement. The consequence worth quoting: moving the last item to the front is one logical move but React flags every other sibling as moved and re-inserts them all, while moving the first item to the end is cheap. Keys make the matching correct; they do not make every reorder cheap.

Why the heuristic is O(n) — and what it gives up

A general tree-diff is O(n³) because it must consider moving any node anywhere. React gets to O(n) by making two assumptions that are wrong in theory and almost always right in practice: elements of different types produce different trees, and siblings can be given a stable identity by the developer. The first lets it stop comparing the moment a type differs; the second turns list reconciliation from a matching problem into a map lookup.

What it gives up is worth naming, because it's the source of the classic bug: React never moves a node between parents. Move a component from one branch of the tree to another and its state is destroyed and rebuilt, even if the element is otherwise identical, because the diff is per-position within a parent. That's why conditionally rendering the same component in two places — {cond ? <A/> : <div><A/></div>} — resets it.

// same component, different position → state is destroyed
{isWide ? <Panel/> : <aside><Panel/></aside>}   // Panel remounts on every toggle

// deliberately using that: a key change forces a fresh instance
<ProfileForm key={userId} user={user} />   // switching users resets the form's state

That second pattern is the one to volunteer: changing the key is the idiomatic way to reset a component's state, and it's far cleaner than an effect that watches a prop and clears state — which renders once with stale state before correcting itself.

When index keys are actually fine

Say the condition precisely rather than repeating “never use index”. Index keys are safe when all three hold: the list never reorders, items are never inserted or removed except at the end, and the items have no state, focus, or uncontrolled inputs. A static list of table headers qualifies. A sortable, filterable list of inputs is exactly where it breaks — and note the symptom is not a crash but state sticking to the position: you delete the first row and the second row's typed text appears to have moved up.

05 — Skipping work

memo / useMemo / useCallback

They all hinge on referential equality. Objects, arrays, and functions created during render get a new identity every render, so passing {}, [], or an inline arrow as a prop defeats a child's React.memo — the prop is “different” each time. useMemo/useCallback exist to keep those references stable across renders.

The senior signal — when NOT to memoizeMemoization is not free; it costs memory and comparison time and adds complexity. It's premature when: the component is cheap to render; a dependency changes every render anyway (the memo never hits); or you're wrapping everything “just in case.” Often the better fix is to pass primitive props (a string/number/boolean, which compare by value) instead of an object, or to restructure so the expensive child isn't re-rendered at all (move state down, or pass it as children).

Note the React Compiler — a build-time tool, stable since v1.0 (Oct 2025) and now what the React team recommends for new apps: default-on in new Expo projects, offered in the Vite/Next.js templates, with its lint rules in eslint-plugin-react-hooks's recommended preset, supporting React 17+. It auto-memoizes components and hooks, so new code should lean on it rather than hand-written useMemo/useCallback. Keep manual memoization where you need precise control, don't rip it out of existing code untested — and understanding referential equality still matters.

What memo actually costs

Put numbers and mechanisms on it, because “don't over-memoise” is otherwise just vibes. React.memo adds a shallow prop comparison on every render attempt — one loop over the props object, each value compared with Object.is. It does not add an extra fiber in the common case: a plain function component with the default comparison is upgraded to a SimpleMemoComponent fast path on the same fiber; only a custom arePropsEqual comparator (or legacy defaultProps) gets the outer wrapper fiber with a child. (Nor does it add meaningful retention: React already stores the previous props on every fiber as memoizedProps, memoised or not.) useMemo/useCallback add a dependency-array comparison and keep the previous value alive, which is real retention. None of it is large; the point is that it is not zero, and it buys nothing unless the skipped render was more expensive than the check.

The failure mode that makes it actively negative: one unstable prop defeats the whole thing. Memoise a component and pass it an inline object, array, or arrow, and the comparison fails every single time — you now pay the comparison forever and never skip a render. The component looks optimised, is measurably slower, and nobody notices because the code says memo.

const Row = memo(RowImpl);

<Row item={item} style={{ padding: 8 }} onSelect={() => pick(item.id)} />
// style and onSelect are new objects every render → memo never hits

// fix: hoist the constant, and pass a stable callback + primitive
const rowStyle = { padding: 8 };                       // module scope
const onSelect = useCallback((id) => pick(id), []);    // stable identity
<Row item={item} style={rowStyle} onSelect={onSelect} />

Note the second fix in that snippet — passing id to the callback rather than closing over it. That's the general move: prefer primitives at the memo boundary, because they compare by value and can't be accidentally recreated.

memo does not stop contextReact.memo only compares props from the parent. If the memoised component calls useContext, it re-renders whenever that context value changes, memo or not — the docs' example is a memoised Greeting that still re-renders on every theme change. The fix is structural: read the context in a parent and pass the piece you need down as a prop, so the memo boundary sees a primitive.
Where memo genuinely earns its placeThree situations, and being specific is the senior signal: a component rendering a large list where each row is memoised so a single row's change doesn't re-render the other 500; an expensive leaf (a chart, a rich-text editor, a canvas) under a parent that re-renders often; and a component whose parent re-renders at high frequency (a timer, a socket, a mouse handler). Outside those, restructure first — move state down, pass children — and reach for the Profiler before the memo.
06 — Timing & inputs

Batching, StrictMode, controlled inputs

Automatic batching

React groups multiple state updates that happen in the same tick into a single re-render. Since React 18 this is automatic everywhere — not just inside React event handlers, but also in promises, setTimeout, and native event handlers. So three setState calls in one handler cause one render, not three.

StrictMode's double-invoke

In development only, <StrictMode> intentionally double-invokes component render functions (and useState initialisers, updaters and useMemo callbacks) and runs an extra mount→unmount→remount cycle for effects and (since React 19) ref callbacks, to surface impure renders and missing cleanup. It's a dev-time check — it does not happen in production. If double-invoke breaks something, the code has a hidden side effect or a missing cleanup.

  • React 19 change: on the second render useMemo and useCallback reuse the result of the first, so a double-invoked expensive memo is no longer computed twice in dev. The ref-callback double-invoke simulates a mounted component being swapped for a Suspense fallback and back.
  • React 19.3 change: effects are now double-invoked during hydration too, matching client-rendered roots — so an SSR app that upgrades may see “my effect ran twice” for the first time. Same diagnosis: the cleanup is missing.

Controlled vs uncontrolled

  • Controlled: React owns the value — value={x} + onChange. Single source of truth; needed for validation, formatting, or driving other UI.
  • Uncontrolled: the DOM owns the value — defaultValue + read via a ref. Less code for simple/forms-that-just-submit.

The mechanism behind the controlled input is worth stating because it explains every bug in the area: React forces the DOM node's value to match the prop — on every render, and right after every change event. So if onChange doesn't update the state there is no re-render at all: React's event system finishes dispatching the handler, sees a controlled input whose DOM value no longer matches its value prop, and restores it (restoreControlledState) before the keystroke is ever painted. The field appears frozen — the classic “I can't type in my input”, which is not a React bug but React doing exactly what you asked. (The restore is why the docs say the handler must update state synchronously: a setState inside a setTimeout loses the race.) Passing value={undefined} and later a string is the other half: the input silently switches from uncontrolled to controlled and React warns, because it can no longer tell who owns the value.

The cost of controlled inputs is a re-render per keystroke, which for a large form is the most common real-world source of typing lag. Three answers, in order: keep the state as local as possible so the re-render is small (a Field component owning its own value); go uncontrolled with a ref or a form library like React Hook Form, which is uncontrolled by design precisely for this reason; or debounce the consequences of the change (validation, search) rather than the value itself, since debouncing the value makes the input laggy.

Why batching matters, and how to observe it

Batching exists because a handler that sets three pieces of state describes one logical change, and rendering three times would both waste work and briefly show inconsistent intermediate states. Since React 18 it applies everywhere — promises, timeouts, native handlers — where before 18 only React event handlers were batched, which is why old code sometimes rendered three times inside a setTimeout.

function handle(){
  setCount(c => c + 1);
  setFlag(true);
  setName('Ada');
  // one re-render, not three — and `count` is NOT updated yet on this line
}

The corollary is the one that gets tested: state is not updated synchronously after a setter. Reading count immediately after setCount gives the old value, because the current render's variables are constants captured from that render. Hence the updater form setCount(c => c + 1), which is also the fix for three increments in a row collapsing into one. If you genuinely need the DOM updated before the next line — measuring after a state change — flushSync opts out of batching, at the cost of a synchronous render, and should be rare. Its costs are specific: it may force a pending Suspense boundary to show its fallback, it flushes pending effects and other queued updates along with yours, it is a no-op (with a warning) inside render or an effect, and in 19.3 it skips any <ViewTransition> animation the update would have triggered.

Two batching details that come up: useTransition's isPending covers all pending transitions for that hook, not one; and since 19.3 React batches updates fired from resize events until the next frame, so a resize listener that sets state no longer renders once per event.

07 — Failure and code, deferred

Error boundaries, lazy & Suspense

Two features share one shape: a component in the tree declares what to show while its subtree cannot render — because it failed, or because its code or data has not arrived.

Error boundaries

Since React 16, an error thrown during render that nobody catches unmounts the entire tree — the user gets a blank page. That is deliberate: a corrupted UI is considered worse than no UI. An error boundary is how you scope that blast radius.

class Boundary extends React.Component {
  state = { error: null };
  static getDerivedStateFromError(error) { return { error }; }   // render the fallback
  componentDidCatch(error, info) { logToSentry(error, info.componentStack); }
  render() {
    return this.state.error
      ? <Fallback error={this.state.error} onRetry={() => this.setState({ error: null })} />
      : this.props.children;
  }
}

  • There is no hook for this. Error boundaries must be class components — or react-error-boundary, which wraps one and adds a reset API and a useErrorBoundary hook for throwing async errors into it deliberately.
  • Place them per independent region, not only at the root: a failed chart widget should not take out the navigation. A root-level boundary is the backstop, not the strategy.
  • Give the fallback a way out — a retry that resets the boundary state, or a resetKeys prop, so the user is not stuck.
  • React 19 adds root-level onCaughtError and onUncaughtError options (alongside 18's onRecoverableError), which is where global reporting belongs. It also changed the defaults: render errors are no longer re-thrown after a boundary catches them, caught errors go to console.error and uncaught ones to window.reportError — so a Sentry setup that relied on the rethrow reaching window.onerror silently stops seeing caught errors on 19.
  • Two async cases a boundary does catch: an error thrown inside a startTransition action (React 19 Actions route it to the nearest boundary), and a rejected promise read with use(), because that throws during render.

React.lazy and Suspense

const Settings = lazy(() => import('./Settings'));

<Boundary>
  <Suspense fallback={<Skeleton />}>
    <Settings />
  </Suspense>
</Boundary>
  • lazy takes a function returning a dynamic import() and returns a component that suspends while the chunk downloads. It requires a default export; a named export needs a small wrapper that re-maps it.
  • A <Suspense> boundary somewhere above it is what you want — but be exact about what happens without one. React does not throw: the suspension propagates to the root, which simply refuses to commit until the chunk arrives — the previous UI stays on screen (or nothing, on first load), with no fallback and no error. React 18 did throw “A component suspended while responding to synchronous input” when the suspension happened in a sync update such as a click; React 19 dropped that and holds the root there too. The symptom of a missing boundary is a page that silently does nothing, not a crash. Also: React keeps no state for a component that suspended before it ever mounted — it retries that subtree from scratch.
  • Route level is the default granularity. Splitting per component tends to produce many small chunks and a request waterfall; split at routes, then at genuinely heavy leaves like an editor or a charting library.
  • Pair it with an error boundary. A failed chunk load — stale HTML after a deploy, flaky network — throws, and without a boundary it blanks the app. This is the same failure the release guide solves from the deploy side.
  • Preload on intent. Calling the same import on hover or focus warms the chunk so the click feels instant, because module imports are cached.
  • Suspense is not only for code. The same boundary handles data with use() or a framework's loader, and on the server it is the unit of streaming.
The detail that impressesAn update wrapped in startTransition will not show the Suspense fallback for content that is already on screen — React keeps the previous UI visible and swaps when ready. That is how you avoid a navigation replacing a full page with a spinner: the fallback is for the first reveal, transitions are for every reveal after it. Two limits: a transition only waits for boundaries that have already revealed content, so a nested boundary that has never shown anything still gets its fallback; and a transition cannot drive a controlled text input — the field must update urgently, so use useDeferredValue for the expensive part instead.

What transitions grew into (React 19 → 19.3)

  • Async transitions / Actions (19). startTransition(async () => …) is supported: isPending stays true until the promise settles, and a thrown error goes to the nearest error boundary. Known limitation: a setState after an await is no longer inside the transition scope and must be wrapped in another startTransition.
  • View Transitions (stable in 19.3). <ViewTransition> animates enter/exit/update/share using the browser's View Transition API — and it only animates for updates that are transitions: startTransition, useDeferredValue, a Suspense reveal or an <Activity> mode change. A plain setState or flushSync is treated as urgent and skips the animation. addTransitionType('back') inside the transition picks which animation runs.
  • Still no hook for error boundaries as of 19.3; the class (or react-error-boundary) remains the answer.
08 — Drill until reflex

Scenario drills

Drill 1 — does the child re-render?
function Parent(){
  const [n, setN] = useState(0);
  return <><button onClick={() => setN(n+1)}>{n}</button><Child /></>;
}
function Child(){ return <p>hi</p>; }  // no props
Yes — Child re-renders on every click

Child has no props, but its parent re-renders on each state change, and by default that re-renders all children. Wrap Child in React.memo to bail out (its props never change, so it would then skip).

Drill 2 — memo that doesn't work
const Child = React.memo(function Child({ opts }){ /* ... */ });
<Child opts={{ sort: 'asc' }} />   // new object each render
memo never skips — the object prop is new every render

{{ sort:'asc' }} is a fresh object each render, so the shallow prop comparison always differs. Fix: pass a primitive (sort="asc"), or useMemo the object, or hoist the constant out of the component.

Drill 3 — the key bug
“A to-do list uses key={index}. Users report that deleting the first item clears the wrong row's checkbox. Why?”

The checkbox state is uncontrolled/local, keyed by position. When the first item is removed, every remaining item shifts up but the index keys stay 0..n, so React reuses each DOM node/state for a different item — the state that belonged to the deleted item (old index 0) is now attached to whatever shifted up into index 0, and every row ends up wearing the checkbox of the row above it. Using a stable id as the key ties state to the item, not the slot.

Drill 4 — why did my effect run twice?
“In dev, my useEffect that opens a websocket fires twice on mount. Bug?”

Not a bug — StrictMode mounts, unmounts, and remounts once in development to verify your effect cleans up. If the second connection leaks, the effect is missing a cleanup that closes the socket. It won't double-run in production, but the fix (return a cleanup) is correct regardless.

Drill 5 — one render or three?
function onClick(){
  setA(1); setB(2); setC(3);
}
One render

React 18 automatically batches updates in the same tick into a single re-render — and since 18 this holds in promises and timeouts too, not only in synchronous event handlers.

Drill 6 — the form that resets itself
<ProfileForm user={selectedUser} />
// switching users leaves the previous user's edits in the fields
Same type, same position → React reuses the instance and its state

Reconciliation keeps the instance because the element type and position are unchanged; only props updated, and the form's internal state is not derived from props. The idiomatic fix is <ProfileForm key={selectedUser.id} … /> — a different key means a different identity, so React unmounts the old instance and mounts a fresh one with clean state. That's much better than a useEffect watching user and clearing fields, which renders once with the stale values before correcting itself.

Drill 7 — memo that never hits
const Row = memo(RowImpl);
<Row item={item} style={{ padding: 8 }} onSelect={() => pick(item.id)} />
The memo is pure cost — it never skips a render

style and onSelect are new objects on every parent render, so the shallow comparison fails every time. You pay the comparison on every parent render and skip nothing — measurably slower than no memo, and invisible because the code says memo. Hoist the constant object to module scope, and pass a stable useCallback that takes the id as an argument rather than closing over it. General rule: prefer primitives at a memo boundary, because they compare by value.

Drill 8 — typing lags on a big page
“A search box at the top of a heavy dashboard makes typing feel sticky. What's your first move?”

Not memo — restructure. A controlled input re-renders whatever owns its state on every keystroke, so if that state lives at the top of the page, the whole dashboard re-renders per character. First move state down into a SearchBox that owns its own value and only notifies the parent on submit or debounce. If the layout needs the state to stay high, pass the expensive subtree as children — it's created in the outer render, so the element reference is unchanged and React bails out on it without any memo. If neither is possible, useDeferredValue lets the input update urgently while the expensive list renders at low priority. I'd confirm with the Profiler first: the fix depends on whether the cost is wide, deep or frequent.

Drill 9 — the input you can't type in
const [q, setQ] = useState('');
<input value={q} onChange={handleSearch} />
// handleSearch fires the API call but never calls setQ
The field appears frozen — React writes the old value back

A controlled input has React force the DOM node's value to match the value prop — and it re-checks right after every change event, not only on render. If onChange doesn't update that state, nothing re-renders at all: React's event dispatch finishes, notices the DOM value no longer matches the prop, and restores the previous value before the keystroke is painted. It's not a React bug — it's React doing exactly what the code asked. Either update the state in the handler, or make the field uncontrolled with defaultValue and read it from a ref. The related warning to know: switching value from undefined to a string flips an input from uncontrolled to controlled and React complains, because ownership of the value changed mid-life.
