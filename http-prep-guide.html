The server forgets you between every request.

HTTP is stateless by design, so every guarantee you rely on — who you are, what may be cached, which origin may read the response, whether a retry is safe — is negotiated in headers on each round trip. Ten topics, six scenario drills, then 109 questions.

00 — Request, response, method

HTTP fundamentals

HTTP is a stateless request–response protocol, and statelessness is the design decision the whole web scales on.

  • It is application-layer. It runs over TCP for HTTP/1.x and HTTP/2, and over QUIC/UDP for HTTP/3.
  • It is stateless: the server keeps no memory between requests.
  • Continuity (login, cart) is layered on via cookies, tokens, or server-side sessions.

Why stateless scales. Statelessness looks like a limitation. It is actually what lets the web scale. Because no request depends on a previous one, any server can answer any request. So you can put a hundred instances behind a load balancer, restart one mid-session, or serve from a CDN node on another continent, and nothing breaks.

What it costs. Every request must re-establish context. That is why a cookie or token rides along on each one. It is also why “sticky sessions” are considered an infrastructure smell: they re-introduce the coupling the protocol deliberately removed.

Request & response shape

A request is a request line, headers and an optional body; a response is the same with a status line in front.

  • Request line: method + path + version: GET /orders?status=open HTTP/1.1
  • Status line: version + code + reason: HTTP/1.1 200 OK
  • Both then carry headers, a blank line, and an optional body.
GET /orders?status=open HTTP/1.1        ← request line
Host: api.example.com                    ← required in 1.1: one IP, many sites
Accept: application/json
Cookie: session=abc123
                                         ← blank line ends the headers
(no body for GET)

How it works. In HTTP/1.1, that blank line is the entire framing rule. Headers are text, terminated by a blank line. The body's length is then given by Content-Length or chunked encoding. It's why HTTP/1.1 can be typed by hand into a telnet session.

Where it bites. Text framing is comparatively slow to parse and impossible to interleave. That is exactly what HTTP/2's binary framing fixed.

Methods, safety & idempotency

Safe means read-only; idempotent means repeating the call changes nothing more. That is what decides whether a request can be retried.

MethodPurposeSafeIdempotent
GETRetrieve a resourceYesYes
HEADLike GET, headers onlyYesYes
POSTCreate / submit / triggerNoNo
PUTReplace a resource entirelyNoYes
PATCHPartially update a resourceNoNot guaranteed
DELETERemove a resourceNoYes
  • Safe = no server-state change (read-only). Idempotent = N calls have the same effect as one.
  • Why it matters: a client or proxy can safely retry an idempotent request after a failure. Retrying a POST may double-submit (double charge), so payment flows use idempotency keys.
  • PUT vs PATCH: PUT sends the whole representation (idempotent); PATCH is partial, idempotent only if the operation is (set vs increment).

Why idempotency is a real engineering concern, not trivia

On an unreliable network a client can never tell a lost request from a lost response, so retries have to be made harmless.

Example. A client sends POST /payments. The server processes it, charges the card, and starts writing the response. Then the connection drops. The client sees a network error. It has no way to distinguish “never arrived” from “succeeded but the answer was lost.” Retry and you may double-charge; don't retry and you may lose a legitimate payment.

How it works. The protocol can't solve this, so the application does, with an idempotency key. The client generates a unique id per logical operation and sends it as a header. The server stores the key with the result. A repeat of the same key returns the stored result instead of charging again. Stripe and every serious payments API work this way.

Say this. The senior version of this answer is one sentence: at-least-once delivery plus an idempotent handler gives you effectively-once semantics. That's the only combination you can actually build on an unreliable network.

Where the tidy definitions leakIdempotency is about the effect on server state, not the response. DELETE is idempotent even though the first call returns 204 and the second returns 404; the state is the same either way. And plenty of “safe” GETs in real systems write something (analytics, a view counter, a cache warm). That is exactly why a crawler prefetching links can cost you money. If a GET changes state that matters, the design is wrong, not the crawler.
01 — Five classes, a handful that matter

Status codes

1xx Informational

100 Continue, 101 Switching Protocols (the WebSocket upgrade), 103 Early Hints.

2xx Success

200 OK, 201 Created, 204 No Content, 206 Partial Content.

3xx Redirection

301/302, 304 Not Modified, 307/308.

4xx Client error

400, 401, 403, 404, 409, 422, 429.

5xx Server error

500, 502, 503, 504.

The class digit is the load-bearing part: it tells any client what to do without understanding the specific code.

  • 4xx means “don't retry, the request is wrong”.
  • 5xx means “the request may be fine, retrying could work”.
  • 3xx means “look elsewhere”.

Why it matters. Any HTTP client can implement sensible retry policy from the first digit alone: your fetch wrapper, a CDN, a load balancer. That's why returning 200 OK with { "error": "not found" } in the body is a genuine design failure, not a style preference. It makes every layer between you and the server unable to do its job. Caches will cache the error, monitoring will report 100% success, and retries won't happen where they should.

The refinement. A follow-up will probe this: the class digit is a default, not a law. Two 4xx codes are explicitly retryable: 408 Request Timeout, and 429 after its Retry-After. One 5xx is not: 501 Not Implemented won't get better by asking again. Retry-After itself carries either delta-seconds (Retry-After: 120) or an HTTP-date. RFC 9110 defines it for 503 and for redirects (“wait before following”); RFC 6585 attaches it to 429.

The distinctions that get asked

The pairs that get asked look alike and differ in what the client should do next.

  • 301 permanent vs 302 temporary. Both historically let clients switch to GET; 307/308 preserve method and body.
  • 303 See Other is the one redirect that is meant to switch to GET: “your POST worked, now go look at this URL”. It's the Post/Redirect/Get pattern that stops a browser refresh re-submitting a form. So: 302 may change the method, 303 should, 307 must not.
  • 451 Unavailable For Legal Reasons (RFC 7725): blocked by a legal demand. It carries Link: <…>; rel="blocked-by" naming who implemented the block. The number is the Bradbury reference.
  • 304 Not Modified: the cached copy is still valid, reuse it. No body is re-sent.
  • 401 is not authenticated (misnamed) vs 403, authenticated but not allowed.
  • 409 Conflict (conflicts with current state) vs 422 Unprocessable (valid syntax, fails validation).
  • 429 Too Many Requests: rate limited; check Retry-After.
  • 502 Bad Gateway (bad upstream response), 503 Service Unavailable (overloaded), 504 Gateway Timeout (slow upstream).

Why 307/308 exist at all

307 and 308 exist because browsers broke 301/302 so consistently that the spec needed redirects that guarantee the method and body survive.

How it happened. This is a “why” question people rarely have an answer for. Early browsers, faced with a 302 after a POST, changed the method to GET and dropped the body. That was technically a violation, but so universal that the spec had to accept reality. So the semantics of 301/302 became ambiguous in practice, and 307 and 308 were introduced as the unambiguous versions that guarantee the method and body survive.

Where it bites. A POST to a URL that 301-redirects can silently become a GET with no body, and a confusing 400 from the target. If you're redirecting anything other than a plain page navigation, use 307/308.

The SEO-adjacent point. A 301 is a strong, cacheable signal. Browsers cache it aggressively, sometimes indefinitely, so a mistakenly published 301 is very hard to walk back. Use 302/307 if there's any chance you'll change your mind.

The 401 that should be a 403 (and the 404 that should be a 403)401 means “I don't know who you are” and is required to carry a WWW-Authenticate header. Sending it to a logged-in user makes clients try to re-authenticate in a loop, the classic cause of an app that logs you out at random. 403 means “I know who you are and the answer is no.” And sometimes the right answer is a deliberate 404 instead. If merely confirming a resource exists leaks information (private repos, another user's order id), returning 404 rather than 403 is a considered security choice, not a bug.
02 — Asking for the right representation

Headers & content negotiation

Content negotiation is the client stating preferences and the server saying, via Vary, which of them changed the answer.

  • Negotiation: the client declares preferences via Accept, Accept-Language, Accept-Encoding; the server returns the best representation and signals what varied via Vary. The q value (0–1) is a priority weight.
  • Vary tells caches which request headers affect the response, so entries are keyed correctly.
  • Compression (Content-Encoding): gzip is the universal baseline; br (Brotli) is smaller for text over HTTPS. Already-compressed media doesn’t benefit.

Vary is the header that breaks caching quietly

Vary tells a cache which request headers to add to the URL when it builds the cache key.

How it works. A cache stores entries keyed by URL. If a server sends different content for the same URL depending on a request header, the URL alone is no longer a sufficient key. English vs French, gzip vs Brotli, mobile vs desktop are the usual cases. Vary is how the server says which headers to add to the key. There are two failure modes, in opposite directions:

  • Forget Vary and the first requester's variant is served to everyone. A French user warms the CDN and English visitors get French. A Brotli-capable browser caches a Brotli response that an older client can't decode. This is a real and hard-to-reproduce class of production bug, because it depends on who arrived first.
  • Over-vary and you destroy your hit rate. Vary: User-Agent is the classic self-inflicted wound. There are effectively unlimited distinct UA strings, so you've given nearly every visitor their own cache entry. A shared cache becomes an expensive miss generator.

Say this. Vary on the smallest set of headers that genuinely changes the bytes. Prefer to encode the variation in the URL (/fr/page, a content hash) where you can, because a distinct URL is a cache key everything already understands. Vary: Accept-Encoding is the one you almost always want, and most servers set it for you.

Compression, with the numbers

Text compresses to a fraction of its size, so a missing Content-Encoding is the first thing to check on a slow site.

Numbers. HTML, CSS, JS and JSON typically drop to 20–30% of their original size with gzip. Brotli usually saves another 15–20% on top for the same content. That's why an uncompressed response is a genuine finding rather than a nitpick.

Two details worth carrying. Brotli has quality levels 0–11, and the top levels are slow. So it's normally used at 11 for static assets precompressed at build time, and at a low-to-mid level for dynamic responses compressed per request. And compressing already-compressed formats (JPEG, PNG, WebP, MP4, zip) buys nothing and costs CPU. Servers exclude them by content type.

What's after Brotli. The 2024–26 addition is Zstandard. Content-Encoding: zstd ships in Chrome 123, Firefox 126 and Safari 26.3, so Accept-Encoding: gzip, deflate, br, zstd is now what Chrome sends. Its pitch is Brotli-class ratios at much faster compression speed, which matters for dynamic responses where you can't precompress. Chromium 130 also added shared-dictionary variants (dcb/dcz) that delta-compress against a previous version of the file. Niche, but it's the answer to “what's after Brotli?”.

Content-Encoding is not Transfer-Encoding

Content-Encoding describes the bytes end-to-end; Transfer-Encoding is hop-by-hop framing that only HTTP/1.1 has.

  • Content-Encoding is end-to-end. It describes the representation itself (the bytes are gzip), it survives caches and proxies, and it changes the strong ETag.
  • Transfer-Encoding: chunked is hop-by-hop HTTP/1.1 framing. It lets a server stream a body of unknown length as size-prefixed chunks, and each hop may strip or re-apply it.

Where it bites. They look alike and get confused in interviews. Two consequences are worth stating. RFC 9112 says that when both Transfer-Encoding and Content-Length are present, the transfer coding wins. The ambiguity between them is the mechanism behind request smuggling. And HTTP/2 and HTTP/3 forbid Transfer-Encoding entirely (RFC 9113 §8.2.2), because their binary frames already carry length. Chunked is a 1.1-only concept.

The other headers a senior round reaches for

Four headers mark a senior answer: early hints, wire priorities, client hints and a proper logout.

  • Link: </app.css>; rel=preload; as=style is the header form of <link rel=preload>, and what 103 Early Hints carries. The server sends the 103 with Link headers while it is still rendering the real response, so the browser preconnects or preloads during server think-time. Constraints to know: browsers honour it over HTTP/2 and HTTP/3 only, and only for top-level navigations. Chrome 103 supports preconnect and preload, Firefox 120/123 likewise, Safari 17 preconnect only.
  • Priority: u=2, i is RFC 9218 extensible priorities: urgency 0–7 (lower is more urgent, default 3) and i for incremental. It replaced HTTP/2's dependency tree. It is how a fetchpriority hint is expressed on the wire over HTTP/3.
  • Accept-CH: Sec-CH-UA-Platform, Viewport-Width opts a site into client hints, the structured replacement for sniffing User-Agent. Chromium-only: Firefox and Safari don't implement it, so it can't be your only path.
  • Clear-Site-Data: "cache", "cookies", "storage" is the logout header: one response wipes the origin's HTTP cache, cookies and storage. Chrome 61, Firefox 63, Safari 17; the "cache" directive can stall for seconds on a big cache, so most sites send only "cookies", "storage".
Compression can be a security bugWhen a response mixes attacker-controlled input with a secret, compression ratio leaks information about the secret. That's the basis of BREACH and CRIME. It's why you don't compress responses containing CSRF tokens or similar secrets alongside reflected user input, and why TLS-level compression was removed outright. Rare in day-to-day work, but knowing why the mitigation exists is the kind of detail that lands in a security-flavoured round.
03 — Freshness & revalidation

Caching

HTTP caching is two questions asked in order: “is my copy still fresh?” and, if not, “has it actually changed?”

  • Freshness avoids the network entirely.
  • Revalidation avoids re-downloading the body.
  • They're different wins, and mixing them up is the usual source of confusion.

Why it matters. This is the most valuable topic on this page. It's the one that shows up in performance rounds, SEO rounds and systems rounds alike.

Cache-Control

Cache-Control says how long a copy is fresh, who may store it, and what a cache may do once it's stale.

  • max-age=N: fresh for N seconds. no-cache: may store but must revalidate first. no-store: never cache.
  • private (browser only) vs public (shared caches/CDN). immutable: don’t revalidate while fresh. stale-while-revalidate: serve stale now, refresh in the background.
  • s-maxage=N is a separate lifetime for shared caches only. It overrides max-age and Expires there and is ignored by the browser. must-revalidate: once stale, never reuse without a successful revalidation. A cache that can't reach the origin must return 504, not the stale copy. proxy-revalidate is the same rule, shared caches only. stale-if-error: serve stale if the origin answers 5xx or is unreachable.

The directive follow-ups, answered precisely

Every directive has an edge case, and the follow-up question is always about the edge case.

  • max-age=0 vs no-cache. Nearly the same, not quite. Both make the copy stale immediately, so every use is a conditional request. The difference is what a cache may do when it can't revalidate. With plain max-age=0, RFC 9111 lets a cache serve the stale copy if the origin is unreachable. no-cache (or max-age=0, must-revalidate) forbids that. Browsers use max-age=0 on a normal reload precisely because it's HTTP/1.0-compatible.
  • must-revalidate does nothing while the copy is fresh. It only bites after max-age runs out. What it removes is the cache's licence to serve stale, including the stale-while-revalidate and stale-if-error windows. So max-age=600, must-revalidate means “ten minutes, then exact”. Without it, an offline CDN could keep serving the ten-minute-old copy.
  • No caching headers at all is not “not cached”. With no Cache-Control or Expires but a Last-Modified, RFC 9111 allows a cache to compute a heuristic freshness lifetime. The spec's example is 10% of the time since the last modification, and Chrome's cache divides by exactly 10 (a file last changed a year ago is treated as fresh for about five weeks). Chrome also treats a 300, 301, 308 or 410 with no freshness headers as fresh forever. That is the mechanism behind “a wrong 301 is hard to walk back”. The heuristic is how a page with no headers ends up served from cache. With neither freshness nor a validator, every use is a full re-fetch. Say caching policy out loud in Cache-Control; never leave it to the heuristic.
  • Expires loses to max-age. When both are present max-age wins, and s-maxage wins in shared caches. Pragma: no-cache is an HTTP/1.0 request header. It means nothing on a response.
  • Age is how a CDN tells the browser how old the copy already is. It's the seconds since the origin generated or last validated the response. Freshness is measured from generation. So max-age=600 arriving with Age: 500 is fresh for 100 seconds in the browser, not 600. If your CDN hit rate is high and users still see stale data, this is the header to read.
  • If-None-Match beats If-Modified-Since. Browsers send both when they hold both validators. RFC 9110 says a server that sees If-None-Match must ignore If-Modified-Since. And a 304 must repeat Cache-Control, ETag, Expires, Vary and Date if the 200 would have carried them. That is why revalidation renews freshness rather than just confirming bytes.
no-cache does not mean no cacheThe single most common misconception in this area. no-cache means store it, but ask before using it. You still get a cache entry and, on revalidation, a cheap 304 with no body. no-store is the one that means don't write it down anywhere. It's what you want for a bank statement or a personalised page, not for a page you simply want kept current. Reaching for no-store when you meant no-cache throws away the 304 saving on every single request.

Revalidation

Revalidation is a conditional request: the browser sends the validator it holds, and the server answers 304 if nothing changed.

  • ETag / If-None-Match (content fingerprint, precise) and Last-Modified / If-Modified-Since (timestamp) → 304 when unchanged, no body re-sent.
// first response
HTTP/1.1 200 OK
Cache-Control: max-age=60
ETag: "v3-a91f"

// 90 seconds later — stale, so the browser asks conditionally
GET /api/orders
If-None-Match: "v3-a91f"

// unchanged: headers only, no body. ~200 bytes instead of 40KB
HTTP/1.1 304 Not Modified
ETag: "v3-a91f"
Cache-Control: max-age=60          // freshness is renewed too

What it costs. Note what a 304 does and doesn't save. It still costs a full round trip. On a 200ms mobile connection it's 200ms whether the body was 200 bytes or 40KB. It saves bandwidth and server rendering, not latency. That's the argument for a real max-age on things that can tolerate it: the fastest request is the one that never leaves the browser.

ETag vs Last-Modified. ETag beats Last-Modified on precision for two reasons. Timestamps have one-second granularity, so a file changed twice in the same second looks unchanged. And a rebuild or a deploy touches mtimes without changing content, producing false misses. A strong ETag ("abc") asserts byte-for-byte identity. A weak one (W/"abc") asserts only semantic equivalence, which is what lets a server keep the same weak tag across a re-compression.

The pattern to state whenever caching comes up

Split your assets by whether the URL identifies the content. That is the one specific answer interviewers are listening for.

AssetHeaderWhy
app.4f2a91.js, hashed CSS, fonts, imagesCache-Control: public, max-age=31536000, immutableThe hash is the version, so the content at this URL can never change. A year is the practical maximum. immutable additionally stops the revalidation a reload would otherwise force, in Firefox (49+) and Safari (11+). Chrome never implemented the directive. It changed normal reload in 2017 to stop revalidating fresh subresources at all, so you get the same effect there for free.
index.html / the app shellno-cache (or a very short max-age) + ETagIt's the document that points at the hashed assets, so it must be checked every time or users run last week's app forever. Cheap: a 304 on a small file.
API responsesprivate, max-age=0, must-revalidate + ETag, or a short max-ageUsually per-user, so it must never reach a shared cache. private is what enforces that.
Anything with a secretno-storeStatements, tokens, personal data: no disk cache, no CDN copy. Note it no longer keeps a page out of the back/forward cache. Since 2025 Chrome restores no-store pages from bfcache too, evicting them if a cookie changed (see below).

Why hashes, not query strings. That split is what “cache-busting” actually means, and it's worth saying why the alternative fails. A query string (app.js?v=3) works in browsers, but some intermediaries treat query strings inconsistently, and it requires you to remember to bump it. A content hash is derived from the bytes, so it can't drift.

stale-while-revalidate, and the two-tier trick

stale-while-revalidate serves the stale copy instantly and refreshes it in the background, so the user never waits for a revalidation.

How it works. Cache-Control: max-age=60, stale-while-revalidate=600 reads as: fresh for a minute; for the next ten minutes serve the stale copy instantly and refresh in the background. The cost is bounded staleness you chose deliberately. It's the HTTP-level version of the same idea a query cache implements in the client. Pairing them is how a page gets to feel instant on repeat visits. Its sibling stale-if-error is arguably more valuable: serve the stale copy when the origin is down, turning an outage into slightly old content.

Support. Since it gets asked: browsers honour stale-while-revalidate from Chrome 75, Firefox 68 and Safari 14, and CDNs have for longer. stale-if-error is a CDN feature in practice; MDN's compatibility data lists no browser support. So it belongs on the edge configuration, not in your mental model of the browser cache.

Reload, hard reload and the back button

Three navigations, three different cache behaviours, and the last one is not the HTTP cache at all.

  • Normal reload (F5 / ⌘R). The document is fetched with Cache-Control: max-age=0 plus its validators, so you get a 304 if unchanged. Since Chrome's 2017 “reload, reloaded” change, subresources are not revalidated if they're still fresh. Firefox does the same only for responses marked immutable. Facebook measured a 60% drop in static-asset requests from those two changes. That is the practical reason immutable exists.
  • Hard reload (Shift+reload, or fetch(url, {cache: 'reload'})). Every request carries Cache-Control: no-cache and Pragma: no-cache. The cache is bypassed for the document and subresources, and the fresh responses overwrite the entries. “Empty cache and hard reload” in DevTools additionally drops the entries first.
  • Back/forward. The browser prefers the bfcache: a frozen snapshot of the whole page including its JS heap, restored in milliseconds with no request at all. no-cache and must-revalidate don't force revalidation on a history navigation. The spec allows that, because history is defined as restoring what you saw. Historically Cache-Control: no-store on the document kept a page out of bfcache in every browser. Chrome changed that in 2025 and now restores no-store pages unless a cookie or other credential changed, with a shorter 3-minute retention. If “the back button shows the logged-out user's page” comes up, the answer is a pageshow handler that checks event.persisted, not a header.
The bit people miss about CDNsA CDN is a shared cache, so private and Vary matter far more once one is in front of you. A personalised response cached publicly is served to the next visitor, which is a data-leak incident rather than a caching bug. Most CDNs also let you set a separate edge TTL (s-maxage) from the browser TTL: long at the edge, short in the browser. Add purge on deploy, which is what makes a long edge TTL safe. If asked how you'd cache a page that changes unpredictably, that's the answer: cache it at the edge effectively forever and purge on publish, rather than guessing a TTL.
The flow Fresh (within max-age) → serve from cache, no network. Stale → conditional request → 304 reuse or 200 replace. Cache-bust static assets with content-hashed filenames served immutable.
04 — A browser boundary, not a server one

CORS & the same-origin policy

CORS is the browser refusing to let your script read a cross-origin response unless the server explicitly permits it.

  • Same-origin policy: origin = scheme + host + port; the browser blocks JS from reading cross-origin responses.
  • Simple request (GET/POST/HEAD, safe-listed headers, basic content types) → no preflight. Anything else (PUT/DELETE/PATCH, custom headers, application/json) triggers an automatic OPTIONS preflight.
  • Server answers with Access-Control-Allow-Origin/-Methods/-Headers; Access-Control-Max-Age caches the preflight.
  • Credentials: with cookies you cannot use Allow-Origin: * — echo the specific origin and set Allow-Credentials: true.

The sentence that makes CORS click

The request is usually sent, and the server usually processes it. The browser blocks you from reading the response.

Why it exists. CORS is not a firewall. It protects the user, not the API. The browser attaches the user's ambient credentials (cookies) to cross-origin requests automatically. Without CORS, any site could read your webmail simply by fetching it from your logged-in browser.

Where it bites. Two consequences explain almost every confusing CORS moment:

  • A blocked request may still have had effects. A cross-origin POST without a preflight is delivered and executed; you just can't read the answer. That's precisely why CSRF is a separate problem needing separate defences. The same-origin policy never stopped the sending.
  • curl and Postman have no CORS. “It works in Postman” isn't evidence the server is wrong-free; it's evidence that CORS is a browser rule. Equally, an attacker with a script rather than a browser is unaffected by it. That is why CORS is not an access-control mechanism. Authentication and authorisation still have to exist on the server.

Preflight: what triggers it and what it costs

A preflight is a permission question asked before any request that an HTML form could not have sent.

How it works. The preflight runs before the real request, and it exists for backwards compatibility. An HTML form could always POST cross-origin, so those “simple” shapes are grandfathered in. Anything a form could not do is new capability: a PUT, a custom header, a JSON content type. So the browser checks first.

// browser sends this automatically. You never write it.
OPTIONS /api/orders HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: content-type, authorization

// server's permission grant
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 86400        // cache this answer for a day

What it costs. A preflight is a whole extra round trip before every affected request. On a 200ms mobile connection that doubles the latency of a small API call. Access-Control-Max-Age is the fix, and it's routinely left off. Set it and the browser stops asking for the same method/header combination for that duration. Browsers cap it (Chrome at 2 hours, Firefox at 24), so asking for a week just gets clamped. Leave it off and the default is 5 seconds, which is effectively no cache.

The specific traps

Most CORS failures come from four rules that are enforced strictly and reported vaguely.

  • Credentials and the wildcard are mutually exclusive. With credentials: 'include', Allow-Origin: * is rejected. You must echo the exact origin and add Allow-Credentials: true. The reasoning is sound: a wildcard means “anyone may read this”, which cannot be true of a response personalised by cookie. Echoing an origin means you must validate it against an allowlist. Reflecting whatever Origin arrives, plus Allow-Credentials, is equivalent to having no policy at all.
  • You can only read the safe-listed response headers: Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified and Pragma. If your JS needs X-Total-Count or a custom Location, the server must list it in Access-Control-Expose-Headers. Symptom: the header is visible in DevTools but undefined in code. That looks like a bug in your client and isn't.
  • The error is deliberately vague. The browser won't tell your JS why it failed, because that would itself leak cross-origin information. So you get a generic network error, and the detail only in the console. Read the console message; it names the missing header.
  • Redirects and preflights don't mix. The Fetch spec makes a redirect during a preflight a network error unconditionally. So it fails in every conforming browser; it's not a browser-variance issue. If your API redirects /api/x to /api/x/, cross-origin PATCHes fail with an unhelpful message.
Debugging A CORS error is the browser enforcing the server’s missing permissions. The fix lives on the server, not in client code. In development a dev-server proxy makes the call same-origin, so the rule doesn't apply. That's a legitimate local workaround, but be clear it changes nothing in production. Be ready to say so rather than presenting a proxy as “the fix”.
05 — Who you are, and who can act as you

Cookies, auth & security

Cookies are sent automatically, which is why they are convenient and why CSRF exists; script-readable storage trades that for XSS exposure.

  • Set-Cookie attributes: HttpOnly (no JS access), Secure (HTTPS only), SameSite (Strict/Lax/None; None needs Secure), plus Domain, Path, Max-Age.
  • Token storage: an HttpOnly cookie is safe from XSS reads but sent automatically → CSRF risk; localStorage avoids CSRF but any XSS can read it.
  • CSRF: a malicious site triggers an authenticated request via auto-sent cookies. Mitigate with SameSite, CSRF tokens, Origin/Referer checks.
  • XSS: injected script runs in your origin. Mitigate with escaping, a CSP, and HttpOnly cookies.
  • Schemes: Authorization: Bearer <token> (JWT/OAuth, stateless) vs cookie/session (server holds state).

The cookie attributes, and what each one actually stops

Each cookie attribute closes one specific hole, and none of them makes a compromised origin safe.

AttributeStopsDoesn't stop
HttpOnlyJavaScript reading the cookie — so an XSS can't exfiltrate the sessionAn XSS using the session. The script can still make authenticated requests from the page; it just can't take the token away with it
SecureThe cookie being sent over plain HTTP, so a network attacker can't read itAnything once the connection is HTTPS
SameSite=LaxThe cookie riding along on cross-site POSTs, iframes, images and fetches — most CSRFTop-level GET navigations, which still send it (that's what keeps normal inbound links logged in). A state-changing GET is therefore still exposed
SameSite=StrictAll cross-site sending, including link clicksBeing annoying: arriving from an external link shows you as logged out, which is why it's usually reserved for a second, high-value cookie

The nuance. HttpOnly doesn't make XSS survivable. It just changes the attack from “steal the session and use it later, anywhere” to “act as the user, now, from this page.” That's a meaningful reduction: no persistence, no exfiltration. But the honest framing is that once script runs in your origin, you've lost that session. Defence-in-depth, not a solution.

The storage question, answered properly

Put the durable token where script can't read it, keep the short-lived one in memory, and say out loud that XSS makes the whole choice second-order.

The question. “Where do I put the JWT: localStorage or a cookie?” is a standard question. The standard answer (“cookies, because XSS”) is only half of it. The real shape:

  • localStorage is readable by any script on your origin. So a single XSS or one compromised npm dependency exfiltrates a long-lived token. It's also readable by every tab and persists indefinitely. In exchange you get no CSRF exposure and easy cross-origin API calls, since you attach the header explicitly.
  • HttpOnly + Secure + SameSite=Lax cookie: not exfiltratable, but sent automatically, which is what creates CSRF in the first place. SameSite mitigates most of it; a token or an Origin check covers the rest.
  • The pattern most teams land on: a short-lived access token in memory only (gone on refresh, never in storage), plus a long-lived refresh token in an HttpOnly, Secure, SameSite cookie scoped to the refresh endpoint. Nothing durable is readable by script. The blast radius of an XSS is one short token lifetime.
Limits, prefixes and the 2025 state of third-party cookiesThe numbers: RFC 6265 requires browsers to allow at least 4096 bytes per cookie (name + value + attributes), 50 per domain and 3000 in total. Chrome's real limits are 180 cookies per site (eTLD+1, purging the 30 lowest-priority when it's hit) and 3300 overall. A Set-Cookie whose name plus value exceeds 4096 bytes is dropped, not truncated. So a session cookie that has quietly grown past it “logs people out” with no error. Since Chrome 104 (2022) Max-Age/Expires is clamped to 400 days; a ten-year cookie is silently shortened, not rejected. Two attributes are worth naming. The __Host- prefix (__Host-session=…; Secure; Path=/, no Domain) makes a cookie un-settable by subdomains and plain HTTP, which is the cheap defence against cookie tossing. And Partitioned (CHIPS: Chrome 114, Firefox 141, Safari 26.2) is a cookie a third party can keep, but only inside the top-level site that embedded it. Chrome's own SameSite default has a wrinkle. A cookie with no attribute is treated as Lax but still sent on top-level cross-site POSTs for its first two minutes (“Lax+POST”, to keep SSO redirects working). An explicit SameSite=Lax gets no such grace. And the state of play: Safari and Firefox block or partition third-party cookies by default. Chrome announced in April 2025 that it will keep them, with no standalone opt-out prompt.

Say this. The point that reframes the whole question: if you have XSS, you have already lost. Storage choice changes what an attacker walks away with, not whether they can act as the user. So the first-order defence is the CSP, escaping, and dependency hygiene. The storage decision is second-order. Saying that explicitly is what turns a memorised answer into a considered one.

The JWT question behind the questionBearer tokens are stateless. That is the selling point and the catch: nothing on the server knows a token exists, so you cannot revoke one. Log out, change your password, fire an employee: an issued token stays valid until it expires. The mitigations all reintroduce state in some form. Short expiry plus refresh tokens, a revocation list checked per request, or a token version in the user record. If someone asks “JWT or sessions?”, revocation is the axis they're usually probing. Sessions are trivially revocable because the server holds them, and that's frequently the more sensible default for a normal web app.
06 — Before a single byte is requested

DNS & connection setup

On a first visit, name resolution and connection setup routinely cost more than the response itself.

Why it matters. “What happens when you type a URL and press Enter?” is the most-asked systems question in frontend interviews. The part candidates skip is everything that happens before the request exists.

The resolution chain

Resolution walks outward through caches until one of them knows the answer.

  1. The browser checks its own DNS cache, then hands off to the OS resolver, which consults the hosts file before its own cache.
  2. On a miss it asks a recursive resolver: your ISP's, or a public one like 1.1.1.1.
  3. The resolver, if it has nothing cached, walks the hierarchy: a root server points it at the TLD servers for .com, which point at the domain's authoritative nameservers, which return the record.
  4. Every layer caches the answer for its TTL.

What it costs. Then the browser opens a TCP connection (one round trip for the handshake). It negotiates TLS (one more round trip with TLS 1.3, or zero on resumption). Only then does it send the request line and headers. On a cold connection to a new origin you have spent three or more round trips before the server has seen a single byte of your request.

Record types worth knowing

A and AAAA are the answer; every other record points at, delegates, or annotates the name.

A / AAAAHostname to an IPv4 / IPv6 address: the actual answer.
CNAMEAn alias to another name. It cannot exist at the zone apex alongside other records. That is why example.com pointing at a CDN needs an ALIAS/ANAME or a provider-specific flattening.
NS / SOADelegation and zone metadata.
TXTVerification and policy — domain ownership, SPF, DMARC.

Encrypted DNS, and the record that advertises HTTP/3

DoH hides your lookups from the network path, and the HTTPS record lets a browser start with QUIC on the very first visit.

Encrypted DNS. Plain DNS is UDP port 53 in cleartext, so anyone on the path sees every hostname you visit. DoT (DNS over TLS, RFC 7858, port 853) and DoH (DNS over HTTPS, RFC 8484, port 443) fix that. DoH is what browsers ship because it's indistinguishable from other HTTPS traffic. Firefox has defaulted US users to DoH via Cloudflare since 2020; Chrome's “Secure DNS” (83+) auto-upgrades to DoH only when your existing resolver supports it, so it doesn't change who answers you. Neither hides the destination IP or, without ECH, the TLS server name.

The HTTPS record. The record a modern interviewer will probe is the HTTPS record (RFC 9460, SVCB/HTTPS RR). Alongside the address it carries alpn="h3,h2", so the browser knows it can open a QUIC connection on the first visit. It also carries ECH keys and an implicit “use HTTPS” that skips the plain-HTTP hop even without HSTS. Chrome, Firefox and Safari all query it.

Without it. HTTP/3 is discovered only after the fact, through the Alt-Svc: h3=":443"; ma=86400 response header. Your first connection is TCP+TLS, and the browser remembers to try QUIC next time for ma seconds (24 hours if omitted). That lag is why measured HTTP/3 usage is far below the number of sites that offer it.

“DNS propagation” is a misnomerNothing propagates. Resolvers simply keep serving the old answer until the TTL you previously published expires. That is why you lower the TTL to 60 seconds a day before a migration. Afterwards is too late, because the long TTL is already cached everywhere.

What a frontend engineer actually controls

You can't make DNS faster, but you can start it earlier and need less of it.

<link rel="dns-prefetch" href="https://api.example.com">
<link rel="preconnect" href="https://api.example.com" crossorigin>
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
  • dns-prefetch resolves the name early. Cheap, and a useful fallback hint.
  • preconnect does DNS plus TCP plus TLS, so the connection is warm when the request is made. It costs a connection you may not use. Limit it to the three or four origins on the critical path.
  • Match the mode. Fonts, and any cross-origin fetch not sent with credentials, are anonymous-mode requests. So their preconnect needs crossorigin. Without it the browser only performs the DNS lookup, and your preconnect quietly degrades to a dns-prefetch.
  • Fewer origins is the bigger win. Every additional third-party domain is another resolution and another handshake. Self-hosting fonts removes a whole chain. Consolidating asset domains lets HTTP/2 reuse one connection.
The connection-reuse detailUnder HTTP/1.1 the browser opened roughly six connections per origin, so sharding assets across domains was a real optimisation. Under HTTP/2 one multiplexed connection carries everything. Sharding is now actively harmful: it forces extra DNS lookups and handshakes for no benefit. HTTP/2 will even coalesce requests for different hostnames onto one connection when they resolve to the same IP and the certificate covers both.
07 — Confidentiality, integrity, identity

HTTPS / TLS

HTTPS gives you three properties, and candidates usually name only the first; authentication is the one encryption alone cannot provide.

  • HTTPS = HTTP over TLS: confidentiality, integrity, and authentication (CA-signed certificate).
  • Handshake: agree a cipher → server presents its certificate → exchange keys → derive a shared symmetric session key.
  • TLS 1.3 is faster (fewer round trips, 0-RTT resumption). HSTS forces HTTPS and blocks downgrade attacks.

Say this. Name all three properties, because candidates usually give only the first. Confidentiality: nobody on the path can read it. Integrity: nobody can modify it undetected, which is what stops an ISP or hotel WiFi injecting ads into your pages. Authentication: you're talking to who you think. That is the one encryption alone doesn't give you. An encrypted connection to an attacker is perfectly private and completely useless.

Why there's asymmetric and symmetric crypto

Asymmetric for the introduction, symmetric for the conversation.

How it works. The question underneath the handshake is this: two parties who have never met need a shared secret, over a wire anyone can read. Public-key cryptography solves that. But it's orders of magnitude too slow to encrypt a whole page with. So TLS uses it once, to establish a shared symmetric key, and everything after that is fast symmetric encryption. That one sentence above is usually the whole answer they're after.

The certificate. The certificate is what ties the key to an identity. A Certificate Authority your browser already trusts has signed a statement that this public key belongs to this domain. That's why a self-signed certificate encrypts perfectly well and still shows a warning. It provides confidentiality with no authentication, so you have no idea whose key it is.

The round trips, and why 1.3 matters

TLS 1.3 cut the handshake from two round trips to one, and to zero on resumption.

  • TLS 1.2: two round trips to handshake, on top of TCP's one. Cold connection to a new origin: 3 RTTs before the first byte of your request. At a 150ms mobile RTT that's ~450ms of pure setup.
  • TLS 1.3 (RFC 8446, 2018): one round trip. It drops the negotiation back-and-forth (the client guesses the key-share up front) and removes the legacy cipher suites that made negotiation necessary. So 2 RTTs total. On resumption it can go to 0-RTT: application data rides along with the first packet.
  • The 0-RTT caveat, which is the follow-up question. Early data is replayable, because it isn't yet bound to a live handshake. An attacker who captures it can send it again. So it's only safe for idempotent requests; never send a POST as 0-RTT data.

HSTS, and the reason it exists

HSTS closes the window in which the first plain-HTTP request can be intercepted before the redirect to HTTPS.

How it works. Without it there's a hole at the very start. A user typing example.com makes a plain HTTP request first, which you redirect to HTTPS. That first unencrypted request is interceptable (sslstrip). Strict-Transport-Security: max-age=31536000; includeSubDomains tells the browser to never use HTTP for this host again. After one clean visit the redirect stops being a window. The preload list closes the remaining first-visit gap by shipping the entry with the browser.

HSTS is hard to undo — say this before enabling itA long max-age is cached by every visitor's browser, and you cannot revoke it remotely. If a subdomain can't do HTTPS and you shipped includeSubDomains, it's unreachable for those users until the max-age expires. Roll it out with a short max-age first, verify every subdomain, then raise it. Only submit to the preload list once you're certain, because removal ships with browser releases. hstspreload.org quotes 6–12 weeks to reach most Chrome users and longer for other browsers.
Certificates are getting short-lived — a 2026 changeThe CA/Browser Forum's ballot SC-081v3 (April 2025, proposed by Apple) cuts the maximum public TLS certificate lifetime from 398 days to 200 days from 15 March 2026, 100 days from March 2027 and 47 days from March 2029. The reasoning is that revocation never worked reliably, so a stolen key should simply expire soon. The practical consequence, and the interview answer, is that manual certificate renewal is over. Issuance has to be automated (ACME, as Let's Encrypt has always required), and an expiry-monitoring alert is table stakes.
08 — What each version fixed

HTTP versions & performance

What actually changed, and what didn't

The semantics never changed. Every HTTP version is a different way of putting the same messages on the wire.

Say this. State it early in any version question. Methods, status codes, headers and caching are identical in HTTP/1.1, /2 and /3. That's why upgrading is an infrastructure decision that requires no application changes. It's also why “we moved to HTTP/2” is not something your React code can observe directly.

Head-of-line blocking, three times over

“Head-of-line blocking” names three different problems, and separating them is the whole of a good HTTP/2-vs-3 answer.

  1. HTTP/1.1, application level. One request per connection at a time. A slow response blocks everything queued behind it. Browsers worked around it with ~6 parallel connections per origin. Developers worked around that with sprites, concatenation and domain sharding.
  2. HTTP/2, transport level. Multiplexing fixes the application-level problem: many streams share one connection. But they share one TCP stream, and TCP guarantees in-order delivery. So one lost packet stalls every stream until it's retransmitted, even streams whose data already arrived. On a clean connection HTTP/2 is a large win. On a lossy mobile link it can be worse than 1.1's separate connections.
  3. HTTP/3. QUIC moves stream awareness into the transport itself, so a lost packet blocks only the stream it belonged to. That's the entire reason for building on UDP. TCP's ordering guarantee is the thing in the way, and it can't be changed without changing TCP everywhere.

The honest summary. HTTP/2's benefit is largest for many small assets on a decent connection. HTTP/3's benefit is largest on lossy or changing networks, mobile especially. There, QUIC's connection IDs also let a session survive switching from WiFi to cellular without a new handshake.

The practical consequence for frontend workSeveral HTTP/1.1-era optimisations became counterproductive under HTTP/2, and this is a favourite question. Domain sharding now forces extra DNS lookups and handshakes for no gain. Sprite sheets and mega-bundles hurt caching granularity: one changed icon invalidates the whole sheet, and the concurrency they bought is free now. Inlining assets as data URIs makes them uncacheable and unshareable. The modern shape is many small, well-cached, content-hashed files. But don't over-rotate. Thousands of tiny modules still cost per-request overhead and, in a bundler context, worse compression. So “split by route and cache boundary” beats both extremes.

1.x problems

HTTP/1.1 could keep a connection open, but could only use it for one response at a time.

  • Needed multiple TCP connections for concurrency.
  • No header compression; no prioritisation.
  • Head-of-line (HOL) blocking: one response at a time per connection. Forced workarounds: concatenation, sprites, domain sharding.

What 1.1 did fix. Connections are persistent by default (RFC 9112 §9.3). Connection: keep-alive was the HTTP/1.0 opt-in and is redundant on 1.1; Connection: close is the signal that matters. What 1.1 could not do is use that persistent connection for more than one response at a time. Pipelining existed on paper and every browser disabled it. Hence the ~6 parallel connections per host.

SPDY → HTTP/2

HTTP/2 is standardised SPDY, and the 2022 RFCs are the ones to cite.

Numbers. SPDY (Google, 2009) cut page load time by 27–60% in Google's lab tests of the top 25 sites (39–55% over SSL). It became the basis for HTTP/2 (RFC 7540, May 2015; HPACK = RFC 7541). The current HTTP/2 spec is RFC 9113 (June 2022), published alongside HTTP/3 (RFC 9114) and the new semantics/caching RFCs 9110/9111; QUIC itself is RFC 9000 (May 2021) and QPACK is RFC 9204.

HTTP/2

HTTP/2 keeps the semantics and changes the wire: binary frames, many streams on one TCP connection, compressed headers.

  • Binary framing: semantics unchanged; the wire format becomes binary frames. A stream carries messages. Frames from many streams interleave over one TCP connection and reassemble by stream ID.
  • Multiplexing removes app-layer HOL blocking. Prioritisation: RFC 7540’s weight/dependency tree is deprecated by RFC 9113; the current scheme is RFC 9218 Extensible Priorities (the Priority header). HPACK compresses headers with Huffman coding + static/dynamic tables. Credit-based flow control (default window 65,535 B).
  • Server push is dead in practice. Chrome disabled it in 106 (September 2022) and Firefox in 132 (October 2024), so no major browser accepts pushed streams. It failed because the server couldn't see the browser's cache and pushed bytes the client already had. Use <link rel=preload> / 103 Early Hints, which let the browser decide.
  • Concurrency: the server advertises SETTINGS_MAX_CONCURRENT_STREAMS. RFC 9113 recommends no fewer than 100, which is what most servers set. That number, not six, is the new per-origin ceiling.

HTTP/3 (QUIC over UDP)

HTTP/3 swaps TCP for QUIC so that a lost packet stalls one stream, not the whole connection.

  • Independent streams → a lost packet blocks only its own stream (fixes TCP-level HOL blocking). Combined transport+TLS handshake with 0-RTT. Encrypted by default. Survives network switches (WiFi ↔ cellular) via connection IDs.
  • The round-trip arithmetic: TCP+TLS 1.3 costs 2 RTTs before the request (1 for TCP, 1 for TLS). QUIC folds the TLS 1.3 handshake into its own, so a cold connection is 1 RTT. A resumed one is 0-RTT, with the same replay caveat as TLS. At a 150ms mobile RTT that's 150ms versus 300ms of setup.
  • What it doesn't fix: loss still blocks within a stream, so one big bundle gains nothing over HTTP/2; UDP is blocked or throttled on some corporate and mobile networks, so browsers race or fall back to TCP. And the first visit is TCP anyway unless an HTTPS DNS record advertises h3, because Alt-Svc only takes effect on the next connection.
  • Adoption, sourced: W3Techs counts 40.8% of websites advertising HTTP/3 (September 2026). But Cloudflare's 2025 traffic split was HTTP/2 50%, HTTP/1.x 29%, HTTP/3 21% of requests. Offered far more than used, mostly because of that discovery lag and non-browser clients.

Two nuance flags HTTP/2 flow control is hop-by-hop. RFC 9113 §5.2 says it operates between the endpoints of a single connection, not end-to-end through proxies. So a CDN's window to the browser is unrelated to its window to your origin. And server push still appears in older material as a live feature. It isn't: Chrome 106 and Firefox 132 both disabled it, and the answer now is 103 Early Hints / preload.
09 — Pushing data the other way

Real-time transports

Pick the transport by direction and message rate, and treat a WebSocket as the option you have to justify.

  • Short polling: fixed-interval requests (wasteful, laggy). Long polling: server holds the request until data is ready, then the client re-requests.
  • SSE: one-way server→client stream over HTTP (text/event-stream), EventSource, auto-reconnect, text only.
  • WebSockets: full-duplex; starts as an HTTP Upgrade → 101 Switching Protocols, then binary/text frames. Best for live order books and trading updates.
  • Rule of thumb: SSE for one-way feeds; WebSockets for low-latency bidirectional traffic.

Choose by direction and rate, then justify the cost

A WebSocket is the expensive option, so it should be argued for rather than assumed.

What it costs. That framing is what reads as senior. Once you open a socket you own reconnection with backoff, heartbeats to detect dead connections, and resynchronisation after a gap. You also own backpressure when messages outpace rendering. And you own a stateful long-lived connection that complicates load balancing and horizontal scaling. SSE and polling hand most of that back to HTTP infrastructure that already works.

LatencyServer costYou ownUse when
Short pollingUp to the intervalA request per client per interval, mostly returning nothingNothing — it's just HTTP, cacheable and statelessUpdates every few seconds are fine. Genuinely the right answer more often than people admit
Long pollingNear-instantA held connection per client, plus a re-request per messageTimeout tuning, thundering herd on reconnectLegacy environments where SSE and sockets are blocked
SSENear-instantOne held HTTP response per clientVery little — reconnection and Last-Event-ID resume are built inOne-way feeds: notifications, prices, progress, LLM token streams
WebSocketLowest, both waysA stateful connection per clientEverything: reconnect, heartbeat, resync, backpressureGenuinely bidirectional or very high rate: chat, collaboration, order entry

SSE's limits. Two details come up. SSE is text-only (text/event-stream), so binary needs base64 and a ~33% size penalty. That's a real reason to pick a socket for market data. And SSE inherits the per-origin connection limit. Under HTTP/1.1 that's about six per browser, not per tab, so a user with several tabs open can starve the page entirely. Over HTTP/2 they're multiplexed onto one connection and the ceiling becomes the negotiated stream limit, typically 100, since RFC 9113 recommends no fewer. It's a good example of the transport choice depending on the protocol version underneath it.

Where it bites. Buffering is an SSE problem too, not just a socket-upgrade one. nginx proxy_buffering, most CDN defaults and response compression will happily hold your stream and deliver it in batches. So you disable buffering on the endpoint (X-Accel-Buffering: no) and turn compression off for it.

The handshake. The WebSocket handshake is worth knowing precisely, because it's asked as a “how does it start” question. The client sends a normal HTTP GET with Upgrade: websocket, Connection: Upgrade and a Sec-WebSocket-Key. The server replies 101 with a hash of that key derived from a fixed GUID. That proves the server actually understood the WebSocket protocol rather than being a cache replaying a response. After that, the TCP connection is no longer speaking HTTP at all.

10 — Drill until reflex

Scenario drills

Drill 1 — the deploy nobody sees
“You ship a fix, but some users keep getting the old app for days. Diagnose it.”

Almost always index.html being cached. The hashed JS and CSS are fine — new build, new URLs — but the HTML that points at them was served with a long max-age, so the browser never asks for it and keeps loading last week's asset URLs. The fix is the standard split: hashed assets immutable, max-age=31536000, and the HTML no-cache with an ETag so it costs one cheap 304 per visit. I'd also check the CDN's edge TTL for the HTML and whether the deploy purges it, and if there's a service worker, whether it's serving a precached shell — that's the other common cause and it needs a skipWaiting/update flow, not a cache header.

Drill 2 — the header that isn't there
“Your code reads res.headers.get('X-Total-Count') and gets null, but DevTools clearly shows the header. Why?”
Cross-origin response headers must be explicitly exposed

For a cross-origin request, JavaScript can only read the CORS-safelisted response headers — Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified and Pragma. Everything else is invisible to script even though the browser received it, which is exactly why DevTools shows it and your code doesn't. The server has to add Access-Control-Expose-Headers: X-Total-Count. It's a server fix; nothing in the client can work around it.

Drill 3 — it works in Postman
“A teammate says the API is broken because the browser gives a CORS error, but Postman works fine. What do you tell them?”

That both observations are correct and neither means the API is broken. CORS is a browser-enforced rule, so tools that aren't browsers never apply it — Postman working proves nothing about the policy. The browser is telling us the server didn't grant permission for our origin to read the response; the request itself was very likely delivered and processed. The fix is server-side headers (Allow-Origin, and Allow-Credentials plus an exact origin if we send cookies). I'd also point out the security consequence: because the request still goes through, CORS is not access control, so the endpoint still needs real auth.

Drill 4 — the double charge
“A payment POST times out. The client retries. How do you make that safe?”

The client can't distinguish 'never arrived' from 'succeeded and the response was lost', so the retry has to be made harmless rather than avoided. An idempotency key: the client generates a unique id for the logical operation and sends it with every attempt; the server records the key with its result and returns the stored result for repeats instead of charging again. That gives effectively-once semantics on top of at-least-once delivery. I'd scope the key to the operation, not the request, and expire it after a sensible window.

Drill 5 — the wrong language
“After adding a CDN, some users see the site in the wrong language. What happened?”
A missing Vary header

The server returns different content for the same URL based on Accept-Language, but didn't tell caches that. The CDN keys on the URL alone, so whoever requested it first populated the entry and everyone else gets their language. Fix by sending Vary: Accept-Language — or better, put the language in the URL (/fr/...), because a distinct URL is a cache key every layer already understands. And I'd avoid the opposite mistake, Vary: User-Agent, which effectively gives every visitor a private cache entry.

Drill 6 — HTTP/2 didn't help
“You enable HTTP/2 and mobile users report no improvement — some say it's worse. Explain.”

HTTP/2 removes application-level head-of-line blocking but all its streams still ride one TCP connection, and TCP delivers in order — so on a lossy link a single dropped packet stalls every stream until it's retransmitted, where HTTP/1.1's six separate connections would have isolated the damage. That's exactly the mobile case. I'd also check for leftover 1.1-era optimisations now working against us — domain sharding forcing extra handshakes, sprite sheets hurting cache granularity, inlined data URIs that can't be cached. The real fix for lossy networks is HTTP/3, where QUIC makes streams independent at the transport layer.
