00 — Three promises, one mechanism

What a progressive web app actually is

A PWA is a web app that makes three promises, each backed by a specific platform feature. It is not a framework or a checklist badge.

Reliable

It loads regardless of network — a service worker intercepting requests.

Installable

It can live on the home screen and launch without browser chrome — a web app manifest.

Capable

Push, background sync, file access, share targets — platform APIs, progressively.

How it works. The word that matters is progressive. Everything here is an enhancement. The app must work as an ordinary website first. The service worker layer must be removable without breaking it.

Say this. An interviewer asking about PWAs is usually really asking about the service worker: its lifecycle, its caching model, and the update problem it creates.

The honest framingA service worker is a programmable proxy you install on your users' devices. It persists after you deploy. That power is exactly why the update story is the hard part. It is also why “how do you ship a fix to users stuck on a bad service worker” is a favourite senior question.
01 — Install, wait, activate

The service worker lifecycle

A worker is registered, installed, then waits while an older worker controls any page, then activates, and is killed whenever idle.

// page — register after load so it never competes with the first paint
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => navigator.serviceWorker.register('/sw.js'));
}
// sw.js
const VERSION = 'v7';

self.addEventListener('install', e => {
  e.waitUntil(caches.open(VERSION).then(c => c.addAll(PRECACHE_URLS)));
});

self.addEventListener('activate', e => {
  e.waitUntil(
    caches.keys().then(keys =>
      Promise.all(keys.filter(k => k !== VERSION).map(k => caches.delete(k))))
  );
});

self.addEventListener('fetch', e => { /* strategy goes here */ });
StageWhat happens
registerThe browser downloads sw.js and compares it byte-for-byte with the installed copy. Identical means nothing happens. The same check re-runs on every in-scope navigation. It also runs on a push, sync or other background event, or a controlled page's subresource fetch, if the last check is more than 24 hours old. It runs on any register() call with a changed script URL, and whenever the page calls reg.update(). The browser never runs it on a timer.
installFires once per worker version. This is where you precache. waitUntil keeps the worker alive until the promise settles; if it rejects, the install fails and the worker is discarded.
waitingIf an older worker still controls any open page, the new one waits, indefinitely. This is the single biggest source of “my users are on an old build”.
activateFires once the old worker is gone. Delete stale caches here: on the normal path nothing is using them any more. skipWaiting() breaks that guarantee. Activate then runs while pages built against the old assets are still open, so keep the previous version's cache for one release.
idle / terminatedThe browser kills an idle worker aggressively and restarts it on the next event. Nothing in module scope survives.
The detail people missThe page that registers a service worker is not controlled by it. Control begins on the next navigation, or immediately if the worker calls clients.claim() during activation. So a first-visit user gets no caching benefit at all. That is correct: they had to download everything anyway.

Why the waiting state exists at all

The waiting state stops a live page being handed to a worker whose cache it was not built against. It looks like an obstacle and is actually a correctness guarantee.

How it works. A service worker is a proxy that decides what every request from an in-scope page returns. The page currently open was built against a specific set of asset URLs. If the browser swapped in a new worker mid-session, that page would suddenly be served by a worker with a different cache. That cache may have deleted the chunks the running page is about to lazily import.

Say this. The rule is deliberately conservative: one worker version per page lifetime. The waiting state is the browser refusing to create version skew inside a live document. That framing turns “how do I force an update” into the right question: how do I get the page to reload at a moment when swapping is safe. That is exactly what the prompt-to-reload pattern does, and what a bare skipWaiting() skips over.

The byte-for-byte comparison, and what breaks it

A worker is “new” only when the fetched sw.js, imports included, differs byte-for-byte from the installed copy. The consequences surface as real bugs:

  • A build that emits an identical sw.js ships no update, even if every asset changed. If your worker references a precache manifest in a separate file, the worker script itself may never change. That is why every service-worker tooling setup (Workbox included) injects the manifest into the worker file, so its bytes change whenever the assets do.
  • Imported scripts count too. The spec compares the main script and everything it pulls in with importScripts() or a static import. A change to any of them installs a new worker. So a “never-changing” shell that imports a versioned manifest still updates, provided the import is fetched fresh (see updateViaCache below).
  • A worker that changes every build for no reason, such as a timestamp or a random build id, forces an install and activate cycle on every deploy even when nothing about the caching changed. Harmless but noisy. Version it from the content, not the clock.
02 — A worker, not a page

Scope, origin and execution context

A service worker is an HTTPS-only, DOM-less, disposable script that controls every request under its path.

  • HTTPS only, plus localhost for development. A proxy that can rewrite every response is not something to expose over plain HTTP.
  • Scope is path-based. A worker at /sw.js controls the whole origin; one at /app/sw.js controls only /app/. You can widen scope beyond the script's directory only with a Service-Worker-Allowed response header. This is why the file lives at the root.
  • No DOM. There is no window, no document, no direct access to the page. The global is self. You talk to pages via postMessage and the Client API.
  • Classic or module. register('/sw.js', { type: 'module' }) gives you static import. Support: Chrome 91, Safari 15, Firefox only since 147. Module workers cannot call importScripts(). Either way dynamic import() is disallowed inside a service worker, so all code must be resolvable at install time.
  • No synchronous storage. localStorage is unavailable; use the Cache API and IndexedDB.
  • It is event-driven and disposable. Never hold state in module scope expecting it to persist. The worker is terminated between events. Anything that must survive goes in IndexedDB.
  • One worker, many tabs. The same worker serves every client in scope, so a message from one tab affects all of them.
03 — Pick per request type

Caching strategies

Pick a strategy per resource by asking whether staleness or unavailability is worse for it. There is no single right strategy.

StrategyBehaviourUse for
Cache firstServe from cache; only hit the network on a missHashed, immutable build assets — fonts, JS, CSS with a content hash in the filename
Network firstTry the network; fall back to cache on failure or timeoutHTML documents and API reads where staleness is worse than latency
Stale-while-revalidateReturn the cached copy immediately, fetch and update in the backgroundAvatars, non-critical API data, anything where “fast and slightly old” wins
Cache onlyNever touch the networkPrecached app shell in a strictly offline-first design
Network onlyNever cacheAnalytics beacons, mutations, anything personalised or authenticated
// stale-while-revalidate, by hand
self.addEventListener('fetch', event => {
  if (event.request.method !== 'GET') return;   // never cache mutations
  event.respondWith((async () => {
    const cache = await caches.open('runtime');
    const cached = await cache.match(event.request);
    const network = fetch(event.request).then(res => {
      if (res.ok) cache.put(event.request, res.clone()); // clone: a body is read once
      return res;
    }).catch(() => cached);                         // offline: don't reject
    event.waitUntil(network);                        // keep the worker alive for the write
    return cached || network;
  })());
});
Two rules that catch everyoneOnly ever cache GET. cache.put rejects with a TypeError for any other method, and also for a 206 partial response or a Vary: * header. Caching a mutation is a correctness bug regardless. And clone the response before caching: a body stream can be consumed only once, so putting the original in the cache leaves the page with an already-read response.
04 — Storage you control completely

The Cache API

The Cache API is storage entirely under your control: nothing expires until you delete it.

  • It stores Request/Response pairs.
  • It ignores Cache-Control and has no expiry.
  • It evicts nothing on its own. That is a feature and a hazard.
const cache = await caches.open('assets-v7');
await cache.addAll(['/', '/app.css', '/app.js']);  // atomic: all or nothing
const hit = await caches.match(req, { ignoreSearch: true });
await caches.delete('assets-v6');

Service worker cache vs HTTP cache

They are separate layers, so a fetch() inside the worker still passes through the HTTP cache. A request goes page → service worker → HTTP cache → network. So the browser's HTTP cache can still answer a fetch you make from the worker. Pass { cache: 'no-store' } or 'reload' when you need to guarantee a real network hit, for instance when revalidating.

Opaque responses

An opaque response can be cached and replayed but never inspected, and it costs far more quota than its size.

How it works. A cross-origin request without CORS returns an opaque response: status 0, unreadable body and headers. You can cache it and replay it, but you cannot tell whether it succeeded. A 404 caches just as happily as a 200. cache.addAll refuses them outright (status 0 is not ok); only put accepts them.

Numbers. Browsers pad the quota cost substantially. In Chrome each opaque response gets a random padding of up to about 14 MB, roughly 7 MB on average, whatever its real size. So a dozen cached third-party scripts cost you ~85 MB on average.

The fix. Prefer requesting cross-origin assets with CORS (crossorigin on the tag) so you get a real response to inspect.

Quota

Cache Storage and IndexedDB share one origin quota, and storage is best-effort unless the browser grants persistence.

How it works. Check the quota with navigator.storage.estimate() (Safari only gained it in 17). Request durability with navigator.storage.persist(). Without it, storage can be evicted under pressure. That is a normal condition to design for rather than an error.

Where it differs. How persist() is decided varies by browser. Chromium grants silently on engagement signals (installed, bookmarked, notification permission, high site engagement). Firefox shows the user a prompt. Safari 17+ grants silently on heuristics such as the site running as a Home Screen web app.

Chromium extra. Chromium 122 also added the Storage Buckets API (navigator.storageBuckets), so an origin can mark some data persistent and let the rest be evicted first. Chromium-only, so not something to depend on.

05 — The genuinely hard part

The update problem

A new worker installs on the next navigation, then waits until every in-scope tab is closed, and most users never close them.

How it works. Here is the sequence that produces a support ticket. You deploy. The browser fetches sw.js on the next navigation, sees it changed, and installs the new worker. Then it waits, because the open tab is still controlled by the old one.

Why reload doesn't help. The old worker still controls the client during a refresh, because the current page stays alive until the new response arrives. The user must close, or navigate away from, every in-scope tab. Most never will.

Two ways out. You should be able to argue for both.

ApproachTrade-off
self.skipWaiting() in installThe new worker activates immediately. But the currently-loaded page was built against the old assets. It is now served by the new worker and new cache, so lazily-loaded chunks it expects may be gone. Version skew, mid-session.
Prompt to reloadDetect the waiting worker, show “A new version is available — Reload”, and only then message the worker to skipWaiting and reload the page. Slower to roll out, but never breaks a live session.
// page: detect an update and offer a reload
const offer = sw => showUpdateToast(() => sw.postMessage({ type: 'SKIP_WAITING' }));

const reg = await navigator.serviceWorker.register('/sw.js');
if (reg.waiting) offer(reg.waiting);   // already waiting before we loaded
reg.addEventListener('updatefound', () => {
  const sw = reg.installing;
  sw.addEventListener('statechange', () => {
    if (sw.state === 'installed' && navigator.serviceWorker.controller) offer(sw);
  });
});

// reload once the new worker takes over — guard it, or this can loop
let refreshing = false;
navigator.serviceWorker.addEventListener('controllerchange', () => {
  if (refreshing) return;
  refreshing = true;
  location.reload();
});
Never cache sw.js aggressivelySince Chrome 68 browsers ignore caching headers on the top-level worker script by default (the registration's updateViaCache defaults to 'imports'). So the update check is already a real network revalidation. Serve it with Cache-Control: no-cache anyway. That protects you from CDN and proxy caches, and from anyone setting updateViaCache: 'all'. It still governs anything you pull in with importScripts() or import. There is one backstop even for 'all': if the last update check is more than 24 hours old, the spec forces the fetch to bypass the HTTP cache. So a year-long max-age on sw.js can delay an update by a day but never pin it forever. Cache the assets, never the thing that controls them.
The killswitch — a great answer to have ready“If a bad worker ships, I deploy a minimal sw.js that calls skipWaiting(), then self.registration.unregister(), clears all caches, and reloads its clients. Because the browser revalidates the worker script over the network on the next in-scope navigation, that reaches every affected user without them having to clear anything. It is worth knowing before you need it.”

Why a service worker is the most dangerous thing you can ship

A bad worker installs on the device and decides what every future request returns, including the request for your fix. Worth saying plainly, because it's the judgement half of this topic.

How it works. Every other frontend mistake is corrected by the next deploy: a bad bundle is replaced when the HTML revalidates. A bad service worker installs itself on the user's device and then decides what every future request returns. That includes the request for your fix. It cannot intercept the browser's own update check of sw.js, which is why the killswitch works. Get it wrong and you have shipped a persistent, self-serving cache of a broken app to people you can no longer reach through normal deployment.

Where it bites. The specific ways that happens are worth listing, because each has a cheap preventive:

MistakeResultPrevention
Cache-first on the HTML documentUsers are pinned to one build; new deploys are invisible until a changed worker replaces this oneNetwork-first (or stale-while-revalidate) for navigations, cache-first only for hashed assets
Precaching an unhashed asset listThe cache serves stale files under the same URLs foreverOnly precache content-hashed URLs, and version the cache name
A worker whose install fails (a rejected waitUntil, such as a precache 404)The worker is discarded. If a previous one is active, users stay on it indefinitelyKeep install minimal; don't precache anything that might 404
Caching responses opaquelyOpaque cross-origin responses can't be inspected for status, so you happily cache a 404 or an error pageCheck response.ok before caching, and be deliberate about opaque responses

Say this. When asked whether to add one, the honest recommendation is: use Workbox rather than hand-writing this. Not because the API is hard, but because the failure mode is unrecoverable-by-deploy. Workbox has already encoded the lifecycle, the precache-manifest injection, the cache versioning and the expiry policies that people get wrong. Hand-rolling is a reasonable thing to do in an interview to prove you understand the primitives, and a poor thing to do in production.

Know the shape of it. Workbox is on 7.x (7.4.1, May 2026, now owned by Chrome's Aurora team). workbox-strategies ships CacheFirst, NetworkFirst, StaleWhileRevalidate, NetworkOnly and CacheOnly. workbox-precaching injects the hashed manifest and handles versioned cleanup. workbox-expiration caps runtime caches by entry count or age.

The page side. workbox-window runs on the page, wrapping the waiting/controlling events, so the update prompt above is a few lines. vite-plugin-pwa wraps Workbox's build tooling. For Next.js, next-pwa has had no release since August 2022; the maintained option is Serwist (@serwist/next), a fork of Workbox.

06 — Design for the failure, not just the cache

Offline UX & background work

Offline is a design job: a fallback page, data in IndexedDB, an honest UI, and background sync only as an enhancement.

  • An offline fallback page. Precache /offline.html and serve it when a navigation request fails. It is a few lines. It is also the difference between your brand and the browser's dinosaur.
  • Navigation preload. Booting a terminated worker adds latency to every navigation. self.registration.navigationPreload.enable() starts the network request in parallel with worker startup. Read it from event.preloadResponse.
  • IndexedDB for data. The Cache API stores responses. Structured, queryable, mutable data belongs in IndexedDB (via idb or Dexie; the raw API is unpleasant).
  • Background Sync. Queue a failed mutation and register a sync tag. The browser fires a sync event when connectivity returns, even if the page is closed. Chromium-only (Chrome 49; no Firefox or Safari), so treat it as an enhancement over an in-page retry queue, never as the only path. Its siblings are Chromium-only too. Periodic Background Sync (Chrome 80) fires periodicsync on an interval, but only for an installed app and at a cadence the browser throttles by site engagement. Background Fetch (Chrome 74) hands large downloads to the browser so they survive the page and the worker being killed.
  • Be honest in the UI. Show what is cached versus live, disable actions that cannot work offline, and queue the ones that can. Silently accepting a write that never lands is worse than refusing it.
navigator.onLine is not a connectivity checkIt only reports whether the device has a network interface. Connected to a captive-portal Wi-Fi with no route out, it is true. Use it as a hint; determine real reachability from whether your requests succeed.

Storage is not unlimited, and eviction is not your decision

Quota is generous, but the browser evicts when it chooses, and Safari does so after seven days of Safari use without interaction. Numbers make this concrete.

Numbers. Origins share a browser-managed quota. In Chromium that is commonly up to ~60% of total disk space per origin, under a browser-wide cap of about 80%. It is computed from total, not free, deliberately, so the number doesn't vary with how full the machine is. Safari's quota has been comparable since Safari 17: up to 60% of total disk per origin for Safari itself, 15% for other WebKit-hosted apps, replacing the old ~1 GB-and-prompt model.

Where it bites. Safari's real constraint is eviction. It clears all script-writable storage after seven days of Safari use without user interaction for sites that aren't installed to the home screen. So an “offline-capable” app that a user opens fortnightly is, on iOS, usually not offline-capable. Note that it's the eviction policy doing that, not a small quota.

// know your budget before you fill it
const { usage, quota } = await navigator.storage.estimate();

// ask to be exempt from eviction — Chromium/Safari decide silently from engagement, Firefox prompts the user
const persisted = await navigator.storage.persist();

What it costs. Two design consequences. First, cache with an expiry and a cap. An unbounded runtime cache of every API response and image will hit the quota. When it does, cache.put starts throwing QuotaExceededError, usually at the worst moment.

The trap. Second, treat eviction as normal. Your code must work when the cache is empty, because the browser may clear it under storage pressure without telling you. An offline experience that assumes its cache exists is a crash waiting for a full disk.

When not to build a PWA

A service worker pays off on repeat-visit apps or a real offline requirement, not on a site people visit once. The counter-case is worth having, because “should we make it a PWA?” is often the actual question.

Where it earns its keep. Service workers pay for themselves on repeat-visit apps where the same assets are requested again and again. They also pay off where genuine offline use is a product requirement: field tools, note-taking, transit, anything used on a commute.

Where it doesn't. They earn very little on a site people visit once (a marketing page, a checkout funnel from an ad). HTTP caching already does that job with none of the risk. And on iOS the install and notification story remains meaningfully weaker than on Android. So “PWA instead of a native app” is a business decision about your users' platforms, not a technical one.

07 — Making it installable

The web app manifest

The manifest is the JSON file that makes the app installable: its name, icons, start URL, scope and display mode.

{
  "name": "Acme Markets",
  "short_name": "Acme",
  "start_url": "/?source=pwa",
  "scope": "/",
  "display": "standalone",
  "background_color": "#0B1416",
  "theme_color": "#0B1416",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
  • display: standalone removes browser chrome; minimal-ui keeps a slim bar; browser opts out of an app window entirely.
  • Maskable icons matter. Android masks icons to the platform's shape. A non-maskable icon is shrunk onto a white circle instead, which looks out of place. Provide a purpose: "maskable" variant with padding, because a maskable icon's outer edge gets cropped.
  • start_url is where a launch from the home screen lands. It is usually worth tagging so you can measure installed usage separately.
  • Installability on Chromium requires HTTPS (or localhost) and a manifest with a name or short_name, 192px and 512px icons (Chrome's documented list; the check it enforces is one square icon of at least 144px), a start_url, a suitable display (fullscreen, standalone, minimal-ui, or window-controls-overlay via display_override), and no prefer_related_applications: true. A service worker with a fetch handler used to be required. Chrome dropped that for installs from the browser menu in version 108 on Android and 112 on desktop, substituting its own default offline page. Know both, because a lot of material still recites the old list. Chrome's docs lag here. web.dev still lists an engagement gate for beforeinstallprompt: a click plus about 30 seconds on the page. A December 2023 Chrome post says Chrome's own install prompt still needs a fetch handler. Both are stale. Chromium stopped requiring a service worker for the event in 2023, and turned the engagement check off by default in Chrome 131. Chrome 154 fires it on page load with no service worker and no interaction.
  • Lighthouse won't tell you any more. The PWA category was removed in Lighthouse 12.0 (April 2024, in PageSpeed Insights from May 2024). Check the Application panel's Manifest view for installability errors instead.

The install prompt

On Chromium you catch beforeinstallprompt, stash the event, and call prompt() later from your own button.

let deferred;
window.addEventListener('beforeinstallprompt', e => {
  e.preventDefault();          // stop the mini-infobar
  deferred = e;                // stash it
  showInstallButton();
});
installBtn.onclick = async () => { deferred.prompt(); await deferred.userChoice; deferred = null; };
iOS is differentSafari has no beforeinstallprompt. Users install via Share → Add to Home Screen, so you can only instruct, not prompt. iOS has supported service workers since 11.3. But Safari clears a site's script-writable storage, including its service worker registration, after seven days of Safari use without interaction with that site. A web app the user has added to the Home Screen is effectively exempt: it runs outside Safari with its own use counter, which each launch resets. So the cache is fragile for a browsed tab and durable for an installed app, which is one more argument for driving installs on iOS. Two more iOS facts worth having. Since iOS 16.4 third-party browsers can also add to the Home Screen from their Share menu, and Home Screen apps get the Badging API. And in early 2024 Apple announced it would disable Home Screen web apps in the EU under the DMA in iOS 17.4, then reversed that before release. That is a good example of why the iOS PWA story is a platform-policy risk, not just a feature gap.
08 — Two APIs, one permission

Push notifications

Push is two specs working together: the Push API delivers a message to the worker, the Notifications API displays it. Confusing them is a common stumble.

  • The Push API delivers a message from your server to the service worker, even with the page closed.
  • The Notifications API is what actually displays something.
  • Push does not have to result in a notification. But on most browsers you are required to show one for every push you receive.
// page: subscribe (must be behind a user gesture and a real explanation)
const sub = await reg.pushManager.subscribe({
  userVisibleOnly: true,
  applicationServerKey: vapidPublicKey,
});
await fetch('/api/subscriptions', { method: 'POST', body: JSON.stringify(sub) });

// sw.js: receive
self.addEventListener('push', e => {
  const data = e.data.json();
  e.waitUntil(self.registration.showNotification(data.title, {
    body: data.body,
    data: { url: data.url },          // travels with the notification
  }));
});
self.addEventListener('notificationclick', e => {
  e.notification.close();
  // e.notification.data — NOT e.data, which does not exist on this event
  e.waitUntil(clients.openWindow(e.notification.data?.url ?? '/'));
});
  • VAPID keys identify your server to the push service (RFC 8292: a signed JWT per request). The subscription object contains the endpoint and the p256dh/auth keys used to encrypt payloads per RFC 8291, so the push service relays ciphertext it cannot read. The transport itself is RFC 8030. Chrome and Edge reject subscribe() unless userVisibleOnly is true. Firefox accepts it but enforces a quota on silent pushes.
  • Ask at the right moment. Requesting permission on page load is the fastest way to a permanent block, and a denial cannot be re-prompted. Firefox (since 72) and Safari refuse the prompt outright unless it follows a click or key press. Chrome silently embargoes a permission for a week after three dismissals. Explain the value first, ask on a gesture.
  • iOS requires installation. Web push works on iOS 16.4 and later, but only for a web app added to the Home Screen. On macOS 13 Ventura and later, Safari 16 delivers push to ordinary browser tabs, no install needed.
  • Declarative Web Push (iOS and iPadOS 18.4, March 2025; Safari 18.5 on macOS 15.5, May 2025) makes display a guarantee of the browser rather than of your worker. The server sends a JSON payload with a "web_push": 8030 member and the browser displays it itself, with no service worker in play at all; a registered worker still receives the push event and can modify the notification before it shows. So a killed or evicted worker can no longer drop it. Feature-detect with window.pushManager. Safari-only as of 2026: Chromium has an open implementation bug but nothing shipped. So keep the push handler. A browser that understands the declarative format ignores it unless you opt in.
09 — Where it goes wrong

Debugging & the classic failures

Debug in DevTools → Application: the Service Workers pane for lifecycle state, Cache Storage for what you actually cached.

  • DevTools → Application → Service Workers. “Update on reload” forces a new worker every load. It is the single most useful development setting. “Bypass for network” ignores the worker entirely. “Unregister” resets the state you have accidentally cached.
  • Cache Storage in the same panel shows exactly what you cached. That is usually where the bug is visible.
  • Lighthouse no longer has a PWA category. It was removed in Lighthouse 12.0 (April 2024). Verify installability from the Application panel and the browser's install affordance, not from an audit score.
FailureCauseFix
Users stuck on an old buildThe new worker is stuck in waitingAn update prompt, or skipWaiting with versioned assets
White screen after deployCached HTML references hashed chunks that no longer existNetwork-first for documents; keep the previous build's assets around for one release
Stale API data foreverCache-first applied to an API routeNetwork-first or SWR, and never cache authenticated responses
Cached 404s and errorsCaching a response without checking res.ok, or caching opaque responsesOnly cache successful, non-opaque responses
One user seeing another's dataCaching a personalised response in a shared cacheNetwork-only for anything behind auth; clear caches on logout
Closing line“I treat the service worker as deployed infrastructure, not a build artifact: versioned caches, cleanup on activate, network-first for documents, cache-first only for content-hashed assets, an explicit update prompt, and a rehearsed killswitch.”
10 — Drill until reflex

Scenario drills

Drill 1 — the deploy that nobody receives
“We shipped a fix two days ago. Analytics say a third of users are still on the old bundle. Why?”

The new service worker installed and is sitting in waiting, because those users have never closed, or navigated away from, every in-scope tab — a reload is not enough to release the old worker. Short term: ship an update flow that detects reg.waiting, tells the user a new version is available, posts SKIP_WAITING, and reloads on controllerchange. Also confirm no CDN or proxy is caching sw.js. Browsers already skip their own HTTP cache for it by default, but a stale edge copy means they never see the change.

Drill 2 — white screen after release
“After each deploy, some users get a blank page until they hard-refresh. What is happening?”

The HTML is being served cache-first. Users get the previous index.html, which references content-hashed chunks that no longer exist on the CDN, so the app fails to boot. Use network-first for navigation requests with a cached fallback, keep cache-first only for hashed assets (which are safe because their URL changes), and retain the previous build's assets for one release so an in-flight session can still load its chunks.

Drill 3 — pick a strategy
“For each: the app shell HTML, /static/main.4f3a.js, GET /api/portfolio, a user avatar image.”
network-first · cache-first · network-only · SWR

Shell HTML — network-first with a cached fallback: you want the newest, but never a blank page offline. Hashed JS — cache-first: the URL changes when the content changes, so it can be treated as immutable. /api/portfolio — network-only or network-first with a short-lived cache; it is authenticated and personalised, so a shared cache is a data-leak risk and must be cleared on logout. Avatar — stale-while-revalidate: instant, and slightly stale is harmless.

Drill 4 — spot the bug
self.addEventListener('fetch', e => {
  e.respondWith(
    fetch(e.request).then(res => {
      caches.open('v1').then(c => c.put(e.request, res));
      return res;
    })
  );
});
Missing clone, no method/status guard, unawaited write

Three problems. 1) The response body is a stream that can be read once — putting res in the cache and also returning it means one consumer finds the body already used. Here respondWith reads it first, so cache.put rejects with a TypeError and nothing is cached. Cache res.clone(). 2) There is no method or status check: this caches POSTs (cache.put rejects with a TypeError for any non-GET request, and since nothing awaits it you get a silent unhandled rejection) and caches 404s and 500s as if they were content. Guard on e.request.method === 'GET' and res.ok. 3) The caches.open promise is not passed to e.waitUntil, so the worker may be terminated before the write completes.

Drill 5 — get me out of this
“A service worker we shipped breaks the site for anyone who has it. What do you do?”

Deploy a killswitch worker at the same URL: it calls self.skipWaiting() on install, then on activate calls self.registration.unregister(), deletes every cache with caches.keys(), and reloads its clients via the Clients API. Because the browser revalidates the worker script over the network on their next in-scope navigation, this reaches every affected user without them having to clear anything — though a user who never returns is never reached. Serving sw.js with no-cache from day one keeps CDNs and proxies out of that path.

Drill 6 — the deploy nobody receives
“You've shipped four releases and a group of users is still on the version from three weeks ago. No CDN issue. What's happening?”
A service worker serving cache-first HTML, or a worker stuck waiting

Two candidates and I'd distinguish them in DevTools → Application → Service Workers. If the worker is in the waiting state, the new version installed but can't take over while a tab remains open — and an in-page reload doesn't help, only closing or navigating away from every in-scope tab does. If instead the worker is active and serving the HTML document cache-first, those users are pinned to the cached HTML. The browser still re-checks sw.js on each navigation, even one answered from cache, but nothing changes until a changed worker installs and takes over. Fix: network-first for navigations, and an explicit update flow that detects registration.waiting and prompts “new version — reload”. If it's already shipped badly, the killswitch worker — skip waiting, unregister, clear caches, reload clients — reaches those users because the browser revalidates sw.js over the network.

Drill 7 — skipWaiting broke a session
“You added skipWaiting() to force updates. Now users occasionally get a blank screen mid-session. Why?”

You removed the guarantee the waiting state exists to provide. The open page was built against the old build's asset URLs, and skipWaiting hands it to a new worker whose activate step deleted the old cache — so the next lazily-imported chunk 404s and the app dies mid-session. Version skew inside a live document. Either keep the previous version's cache for one release so old chunks still resolve, or — better — don't skip unilaterally: detect the waiting worker, prompt the user, and only then message it to skipWaiting and reload, so the swap happens at a moment when nothing is mid-flight. Guard the controllerchange reload with a flag, or you'll loop.

Drill 8 — offline that isn't
“Your offline-capable app works in testing but iOS users report it's empty when they open it after a week. Explain.”
Safari evicts storage after 7 days of Safari use without interaction

Safari clears all script-writable storage — Cache API and IndexedDB included — after seven days of Safari use without interaction with the site, unless it's been added to the home screen. So a fortnightly-use app is usually not offline-capable on iOS. More generally, eviction is the browser's decision, not yours: quota is shared and the browser can clear under storage pressure at any time. The design consequence is that the app must work with an empty cache — treat the cache as an optimisation, never as a data store — and if offline really is a product requirement on iOS, prompt installation to the home screen and request navigator.storage.persist(), understanding that Safari and Chromium grant it silently on heuristics such as being installed, and Firefox asks the user.
