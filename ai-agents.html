Vibe Coding Tools & AI Agent Concepts

Parts A and B are the general ground — the tools that exist, and how an agent actually works underneath. Part C is the project that proves you've done it: Brelly, a React Native / Expo weather app. The real story isn't the app. It's how you built an AI agent to build it safely.

The hook — open with this

"I don't just prompt an AI and hope. I built a system of guardrails around the agent so it physically can't ship broken or outdated code — the checks, not the prompts, are what make it reliable."

Then give them the map, so they know where you're going: "There are three things I can talk about — the tools and where each one fits, how an agent actually works under the hood, and the guardrail setup I built on my own project. Which is most useful?" Offering the menu reads as senior; it also lets them steer you to the part they're actually assessing.

Part A

Vibe coding & the tool landscape

What the term means, what's on the market, and how you'd choose. This is the part most candidates answer with a list of product names — you answer it with categories and trade-offs.

1 What "vibe coding" actually means — and the version you practise

Andrej Karpathy coined it in a post in February 2025. The original description is stricter than how the phrase gets used now: you "fully give in to the vibes, embrace exponentials, and forget that the code even exists" — you talk or type what you want, accept every diff without reading it, and when something breaks you paste the error back in rather than debugging. Crucially he framed it as fine for throwaway weekend projects. It was named to describe a mode, not to recommend it for production. Collins Dictionary made it their word of the year for 2025, which tells you how fast it escaped its original meaning.

Most people now use "vibe coding" loosely, to mean any AI-assisted coding. That looseness is your opening — drawing the distinction is free credibility, because it shows you've read the source rather than the headlines.

Say this"Strictly, vibe coding means not reading the diffs — Karpathy's own framing was that it's for throwaway projects. Karpathy actually retired the term about a year later and proposed agentic engineering for the professional version: you're not writing the code, you're orchestrating agents and providing oversight. That's the distinction I care about — the AI writes, but the diff still gets reviewed and every change has to survive a machine-checked gate. Same speed, different accountability."

Knowing that the author dropped his own term is the detail that proves you read the source rather than the coverage — and "agentic engineering" is a more precise name for what you actually do.

The autonomy ladder — place any tool on this

Rather than memorising products, hold one axis in your head: how much of the loop the human is still inside. Every tool sits somewhere on it, and the failure mode changes as you climb.

RungWhat the human doesExample shapeDominant failure mode

That's the honest trade, and saying it out loud is the single most senior-sounding sentence in this whole section.

2 The tool landscape — six categories, not thirty product names

Interviewers ask "what tools have you used?" expecting a list. Give them a taxonomy instead, then name what you've actually touched inside it. Products change every quarter; the categories don't.

A. Inline completion — the incumbent

GitHub Copilot (2021 — not the first, Kite and TabNine predate it, but the one that made the category mainstream) and the tab-completion built into Cursor, Devin Desktop (ex-Windsurf) and Zed. The model predicts the next span of code from the surrounding file. Latency budget is brutal — a suggestion that takes more than a few hundred milliseconds arrives after you've typed the line yourself — so these use smaller, faster models than the chat panel next to them.

What it's genuinely good at: boilerplate with a strong local pattern — a fifth test case that looks like the previous four, a mapper between two structs, filling out a switch. Where it hurts: it optimises for "looks like what usually comes next", which is exactly wrong at the points where your codebase is unusual.

B. AI-native editors

Cursor (a VS Code fork) and Devin Desktop are the best-known, with Google's Antigravity the other current entrant; JetBrains and VS Code itself have shipped their own agent modes. Know the Windsurf arc — Windsurf was the other big name until Cognition acquired it and renamed it Devin Desktop in June 2026, which is why Devin and the editor are now the same company. Getting that right is a small currency signal that costs nothing and lands well. The differentiator isn't the model — most of them let you pick from the same handful of frontier models — it's the context plumbing: how the editor decides which files to put in front of the model, and how it applies a diff back into the file without mangling it.

Worth knowing that "apply the edit" is its own hard problem. A big model describes the change; a smaller, faster "apply model" merges it into the real file. When you see an edit land in the wrong place, that second model is usually what failed, not the one that wrote the code.

C. Terminal / CLI agents

Claude Code, OpenAI Codex CLI, Google's Antigravity CLI (which replaced Gemini CLI for individual accounts in June 2026), Aider, OpenHands. The agent lives in your shell, in your repo, with your credentials and your test runner. This is the category that made "agentic coding" real, because the terminal is where the feedback is — the agent can run the failing test itself instead of asking you what happened.

Say why this category matters: an editor plugin sees files; a terminal agent sees files and consequences. That closed loop — edit, run, read the error, edit again — is the difference between a code generator and something that can finish a task.

D. Asynchronous / cloud agents

You hand over an issue and get back a pull request: GitHub Copilot's coding agent, OpenAI Codex in its cloud form, Google's Jules, Cognition's Devin, and the web/cloud modes of the CLI agents. Each task runs in its own sandboxed container with a fresh checkout.

The engineering point: isolation is what makes parallelism safe. Two agents editing one working tree corrupt each other; two agents in two containers (or two git worktrees) don't. If you've used worktrees for this, say so — it's a concrete detail that's hard to fake.

E. Prompt-to-app builders

v0, Bolt.new, Lovable, Replit Agent. Natural language in, a deployed running app out, hosting included. These are the tools the general public means by "vibe coding".

The honest read: extraordinary for the first 80% of a greenfield app and for demos you need this afternoon. They degrade hard once the app has history — an existing schema, an auth model, a deploy pipeline someone else owns. They also generate the security-sensitive parts (auth, row-level access, secrets handling) with the same confidence as they generate a button, and that's where the publicised incidents have come from.

F. AI code review

CodeRabbit, Greptile, GitHub's own PR review, and the review modes inside the CLI agents. Underrated category, and the one to mention if you want to sound like you've thought about the whole lifecycle rather than just the writing half.

The argument for it is arithmetic: if agents multiply how much code gets written, review is the constraint that binds. But note the asymmetry — an AI reviewer is a probabilistic reviewer, so it belongs as an extra pair of eyes with no merge rights, not as the approval. Its real value is the boring sweep (nullability, missing error handling, a changed function whose callers weren't updated) that humans skim past on a big diff.

TrapDon't recite this list as a list. Interviewers hear product names all day. The answer that lands is: "I think of it as three questions — how much autonomy, whether it can run my tests, and whether it's editing my working tree or a sandbox. Everything on the market is a point in that space." Then name two or three you've actually used and what each was bad at.

3 Choosing a tool — the matrix you reason from

The correct answer to "which is best?" is "for what?", but only if you follow it immediately with a real breakdown. Here's the one to have ready.

SituationReach forBecause
Greenfield prototype, throwawayPrompt-to-app builder, or an agent on full autonomyThere's no existing convention to violate and no blast radius. Review cost is the only cost, and you're not paying it.
New feature in a large existing repoTerminal / IDE agent, supervisedThe hard part isn't writing code, it's matching twenty existing conventions. The agent needs to read a lot and you need to see what it read.
Mechanical migration across 200 filesAgent, batched, one file or module per runHighest-value case there is: repetitive, individually verifiable, and a test suite can prove each step. Small independent units also mean a bad one is cheap to throw away.
Debugging a live incidentChat, with you drivingYou need a hypothesis, not a patch. An agent that starts editing before the cause is known produces plausible fixes that hide the symptom.
Security-sensitive code (auth, crypto, payments, access control)Human writes; AI reviewsThese are the paths where "compiles and passes tests" says almost nothing about correctness, and the cost of being confidently wrong isn't a bug, it's a breach.

Say this"My rule of thumb is that autonomy should scale with how cheaply I can verify the result. A migration with a green test suite: run it wide. Auth logic: I write it. The variable isn't how hard the task is, it's how well I can check the answer."

4 What actually changes in the workflow

If they ask "how has this changed how you work?", resist "it makes me faster". Everyone says that, and the research is genuinely mixed on it — a 2025 randomised trial by METR on experienced open-source maintainers working in repos they knew well found they were about 19% slower with AI assistance, while predicting they'd been roughly 20% faster. Volunteer the caveat — METR published a larger late-2025 follow-up that found a much smaller slowdown, flagged serious selection effects, and led them to retire that experiment design. The durable finding isn't the 19%; it's the perception gap, and it's why you shouldn't quote speed numbers about yourself.

The four real shifts

  • Effort moves from writing to reviewing. Your throughput is now bounded by how fast you can read code you didn't write. That's a different skill and a more tiring one.
  • Small diffs get much cheaper; big diffs get more dangerous. The right response is to shrink the unit of work — one task per agent run, one PR per task — precisely because generation is cheap. If a run goes wrong, throw it away and re-run with a better prompt rather than debugging its output.
  • Tests stop being optional. Under human-only development, a test suite is insurance. With an agent it's the control system — it's the only channel by which the agent finds out it was wrong without you telling it.
  • Codebase legibility becomes a performance feature. Clear names, small modules, a real README, typed boundaries — these were always nice; now they measurably raise the agent's hit rate, because they're what it retrieves and reasons over. "Write for the next reader" now includes a machine reader.
Worth namingIndustry survey data consistently shows a trust gap — Stack Overflow's 2025 developer survey had 84% using or planning to use AI tools while only 33% trusted the accuracy of the output and 46% actively distrusted it. That's not a contradiction; it's the correct posture. Use it as your framing: "high adoption, low trust, so the value is in the verification layer."
TrapNever claim a specific multiplier ("it made me 3× faster"). It invites "measured how?", and you don't have an answer. Say instead: "It's clearly faster for the things I can verify cheaply, and I've been burned enough times on the things I can't that I've stopped guessing at the average."

Part B

How an AI agent actually works

The mechanism underneath the products. If you can draw the loop and explain where determinism enters, you are answering a different question from the candidate who lists features.

5 The agent loop — the one diagram to be able to draw

An LLM on its own is a function: text in, text out, no memory, no side effects. An agent is that function placed inside a loop with tools and a stopping condition. That's the entire idea, and it's worth being able to say it in one sentence.

Say this"An agent is a model in a loop with tools. The model can't do anything itself — it emits a request to call a tool, some ordinary code executes it, the result is appended to the conversation, and the model runs again on the longer conversation. It repeats until it emits an answer instead of a tool call."

The loop, step by step

context = [system_prompt, user_task]
while True:
    reply = model(context, tools=TOOL_SCHEMAS)   # 1. model decides
    if not reply.tool_calls:                     # 2. no call = it's done
        return reply.text
    for call in reply.tool_calls:                # 3. HARNESS executes
        result = TOOLS[call.name](**call.args)   #    (ordinary code)
        context += [call, result]                # 4. result fed back

Four properties fall out of those eight lines, and each is worth a sentence:

  • The model never executes anything. It emits structured JSON saying "call read_file with this path". Your harness decides whether to actually do it. Every permission system, sandbox and guardrail lives at line 3 — that's the seam where you can intervene, and it's why guardrails are possible at all.
  • The context grows every iteration. Each tool result is appended, so a 30-step task means the model re-reads a transcript that got longer 30 times. Prompt caching keeps the unchanged prefix cheap to re-send, so the cost curve is gentler than it looks — but attention still has to cross all of it, so long runs get slower and less accurate per step, not just longer in total.
  • Termination is the model's choice. Nothing external decides the task is done — the loop ends when the model stops asking for tools. That's exactly why production harnesses add hard bounds: a max-turns cap, a token budget, a wall-clock timeout.
  • Errors are just more input. A failed command isn't an exception, it's a string appended to the context. This is the whole trick behind self-correction: a stack trace is a better instruction than anything a human would have written in advance.

ReAct — the name to know

The pattern of interleaving reasoning with acting comes from the ReAct paper (Yao et al., 2022): rather than planning everything up front, the model thinks a step, acts, observes the result, and re-plans with what it now knows. The reason it beats plan-then-execute is simple — most of the information you need is discovered during the task, not before it. Modern agents are all essentially ReAct with better tools.

Agents vs. workflows — the distinction people get wrong

Anthropic's widely cited framing: a workflow is a system where the LLM and tools are orchestrated along predefined code paths; an agent is one where the LLM directs its own process and decides which tools to use. Prompt chaining, routing and parallelisation are workflows. Only the model-drives-the-loop case is an agent.

Trap — and the answer that scores"Agent" is the fashionable word, so candidates use it for everything. The senior move is arguing for less agency: most production tasks are better served by a deterministic workflow with an LLM at one or two nodes, because you can test it, reproduce failures and bound the cost. Reach for a real agent only when the number of steps and their order genuinely can't be known in advance. "The right question is how little autonomy the task actually needs."

6 Tool use, mechanically — where determinism enters

People say "the model calls a function". It doesn't. Being precise here is a strong signal.

  1. You send the model a list of tool definitions — each a name, a description, and a JSON Schema for its parameters. These are injected into the prompt, so they occupy context on every request. Caching makes them cheap to re-send and some harnesses defer loading a large catalogue until the model searches for it — but whatever is loaded competes for the model's attention.
  2. The model, instead of ordinary prose, emits a structured tool-use block: the tool name plus arguments matching that schema.
  3. Generation stops. The model is now waiting. Nothing has happened.
  4. Your code — the harness — validates the arguments, decides whether it's allowed, runs it, and captures the output.
  5. The output goes back as a tool-result message and the model is called again with the extended conversation.
The line that shows you understand it"The model chooses; the harness executes. That split is why guardrails work — I can't stop a model from wanting to run rm -rf, but I control the process that would actually run it."

What makes a tool good, and why it's a prompt-engineering problem

The model picks a tool from its description — so tool design is prompt design wearing a different hat.

  • Few, well-separated tools beat many overlapping ones. Two tools whose descriptions could both plausibly apply produce coin-flip selection. If you have twenty tools and half are near-duplicates, accuracy collapses long before the context does.
  • Return errors as text the model can act on. ENOENT is nearly useless; "No file at src/uti.ts — did you mean src/utils.ts?" gets fixed on the next turn. You are writing error messages for a reader that will actually change its behaviour based on them.
  • Cap the output size. A tool that returns a 200k-token file dump destroys the context in one call. Paginate, truncate with an explicit marker, or return a summary plus a handle to fetch more.
  • Make destructive tools narrow. A general run_bash tool is maximally capable and maximally dangerous. Specific tools (run_tests, read_file) are auditable and can be auto-approved; the general one shouldn't be.
Say this if asked "how would you design tools for an agent?""I'd treat the tool description as part of the prompt, keep the set small and non-overlapping, make every error message actionable, and cap output size — because tool results are the main thing that eats the context window."

7 Context engineering — the discipline that replaced prompt engineering

The term has genuinely shifted. Prompt engineering is wording one message well. Context engineering is deciding what occupies the finite window at each step of a long-running loop — which files, which tool results, which history, which instructions — and what gets evicted. For agents, the second is far more of the job, because the prompt is written once and the context is rebuilt every turn.

Why the window is a hard constraint, not a soft one

  • Attention is quadratic — during prefill. Self-attention compares every token to every other, so processing the prompt scales with roughly the square of its length: doubling the prompt is more than double the work. Once generation starts a KV cache makes each new token cost roughly linear in context — still growing, just not quadratically — and prompt caching means the stable prefix often isn't reprocessed at all. Know that split; it's a favourite follow-up. The window is still a hard constraint, but the binding reason is attention quality more than raw FLOPs.
  • Frontier models today are typically 1M tokens — 200k was the norm until recently and still is for the cheap, fast tiers. At roughly 0.75 words per token that's ~750k words at 1M, ~150k at 200k. Sounds enormous until an agent reads six files and runs a test suite whose output is 20k tokens on its own.
  • Quality degrades before the limit does. "Context rot": accuracy on retrieval-style tasks falls as the input grows, and models attend better to the beginning and end than the middle — the "lost in the middle" effect from Liu et al. (2023). A fact buried at 60% depth in a huge context can be effectively invisible.
The counter-intuitive ruleMore context is not better. Every irrelevant token competes for attention with the relevant ones. "The goal is the smallest set of high-signal tokens that makes the next decision correct" — that's the sentence to remember.

The techniques, and when each applies

TechniqueMechanismWhat it costs
CompactionWhen the window nears its limit, summarise the transcript so far and continue from the summary plus the most recent turnsLossy by construction. The detail you drop is gone — so pin the things that must survive (the task, key decisions, file paths)
Just-in-time retrievalDon't preload files; give the agent search and read tools and let it pull what it needs, when it needs itMore turns, so more latency. But it's how humans work, and it keeps the context proportional to the task

The mistake to name: stuffing the entire repo in "just in case". It raises cost and latency on every turn and lowers accuracy — you've buried the three relevant files under two hundred irrelevant ones.

8 Memory — three different things wearing one word

"Does it remember?" is ambiguous and the ambiguity is the answer.

  • In-context (working) memory — the current conversation. Perfect recall, strictly bounded, gone when the session ends. This is the only kind the model actually has.
  • Persistent instructions — a project file (CLAUDE.md, AGENTS.md, cursor rules) loaded into every session. Not memory so much as a standing brief: conventions, commands, architecture, the traps. Highest-leverage thing you can write for a coding agent, because it's the one context that's always present.
  • Retrieved long-term memory — facts written to files or a vector store and fetched when relevant. Genuinely useful and genuinely hard, because the difficulty isn't storing, it's invalidating. A remembered fact about a file you've since refactored is a landmine.
Say this"Models are stateless between calls. Everything that looks like memory is a retrieval-and-re-injection trick built around them — the interesting engineering problem is deciding what to bring back and when to throw it away, not how to store it."

9 MCP — Model Context Protocol

Open standard published by Anthropic in November 2024 and now broadly adopted across vendors; Anthropic donated it to the Linux Foundation's Agentic AI Foundation in December 2025, so it's a genuine cross-vendor standard rather than one company's. The usual one-liner is "a USB-C port for AI applications".

The problem it solves — say it as arithmetic

Before: every AI application needed a bespoke integration with every tool. M applications × N tools = M×N connectors, each maintained separately. With a shared protocol it's M + N: each app implements a client once, each tool ships one server. It's the same shape of argument as the Language Server Protocol, and comparing it to LSP is a good way to show it isn't magic — it's an interface boundary in the right place.

The mechanism

  • Client / server over JSON-RPC 2.0. The host application (your IDE, agent, or desktop app) runs an MCP client; each integration is a server.
  • Two transports. stdio for a local server the host launches as a subprocess, and an HTTP-based transport for remote servers.
  • Three primitives the server exposes. Tools (model-invoked actions), Resources (data the app can read into context), and Prompts (user-invoked templates, e.g. slash commands). The tools/resources split is the detail worth knowing — it separates "the model decided to do this" from "the application supplied this".
Trap — the security follow-upEvery MCP server you connect is untrusted code with your credentials and untrusted text entering your context. A malicious or compromised server can return content designed to steer the agent (see §13), and a legitimate one can leak data across boundaries — the pattern where an agent with access to both a private repo and a public one is talked into moving content between them. Answer: connect servers deliberately, prefer least-privilege tokens over broad ones, and don't auto-approve tool calls from a server whose output you haven't seen.

10 RAG vs. agentic search — why the default flipped, and where it didn't

A useful "I've thought about this" answer, because the intuitive one is out of date and the frontier is genuinely split — so present it as a live disagreement, not a settled result.

RAG (retrieval-augmented generation): pre-chunk the corpus, embed each chunk into a vector, embed the query, fetch the nearest chunks, put them in the prompt. It was the default answer to "how does the AI know about my codebase" for years.

Agentic search: don't index anything. Give the model grep, find and read_file, and let it search the way a developer would — start with a symbol name, follow the imports, read the file.

The split worth knowing. The CLI agents dropped the vector index: Claude Code's lead has said early versions used RAG with a local vector DB and that agentic search simply worked better — simpler, with none of the staleness, privacy or index-maintenance problems. Cursor went the other way, training its own embedding model in late 2025 and reporting around 12.5% higher accuracy on code questions, with the gap widening on repos over a thousand files. Both grep heavily; the disagreement is whether semantic search earns its keep on top. Saying that beats picking a side.

Embedding-based RAGAgentic search
FreshnessIndex goes stale the moment code changes; needs re-indexingAlways current — it reads the working tree
PrecisionSemantic similarity, so it finds "things about auth" but may miss the exact symbolExact. Code is full of unique identifiers, which is ideal for lexical search
Latency & costOne fast lookupSeveral sequential model turns — slower and more tokens
StructureNaive chunking cuts across function boundaries and loses the call graph — AST-aware chunking fixes the first half, not the secondFollows imports and references the way a human would

Say this"For prose, embeddings win — you're searching for meaning. For code, exact search usually wins, because code is full of unique identifiers and the structure is already navigable. The strong setups do both: lexical search for symbols, semantic search for 'where do we handle refunds', and the model decides which to use."

11 Multi-agent systems — and when they're the wrong answer

The common shape is orchestrator–worker: a lead agent decomposes the task and spawns sub-agents, each with its own clean context, each returning a summary. Two real benefits: parallelism (n investigations at once) and context isolation (the lead never has to hold all the raw detail).

Anthropic reported that a multi-agent research system outperformed a single-agent baseline by 90.2% on its internal research eval, on breadth-first queries — and, in the same write-up, that agents burn roughly 4× the tokens of a chat interaction, and multi-agent systems around 15×. That number is the whole trade-off in one figure, so it's worth remembering.

When it helps

  • The subtasks are genuinely independent and mostly read-only — search, research, audit, review from several angles.
  • Breadth matters more than a single deep chain of reasoning.
  • Each subtask's output compresses well into a summary the parent can act on.

When it hurts

  • Shared mutable state. Two agents editing the same files conflict in ways neither can see. Fix: isolate — separate worktrees or containers — or don't parallelise the writes.
  • Tightly coupled steps. If step 2 needs step 1's reasoning, splitting them just loses information across a summary boundary.
  • Cost and debuggability. ~15× a chat, so roughly 4× a single agent — quote the baseline, because "15×" said inside a single-agent comparison is exactly the slip an interviewer who has read the post will catch. And a failure now has to be traced through several transcripts instead of one.
The senior line"Sub-agents are a context-management tool before they're a parallelism tool. The reason to spawn one usually isn't speed — it's that I want the messy 40k tokens of an investigation to happen somewhere that isn't my main context, and only the conclusion to come back."

12 How you'd know an agent is any good — evaluation

Ask an interviewer's favourite unasked question before they ask it. Most candidates have no answer here at all.

  • The benchmark to name: SWE-bench and its human-validated subset SWE-bench Verified — real GitHub issues from real Python repos, scored by whether the model's patch makes the repo's own tests pass. Frontier scores went from single digits in 2023 to around 80% by late 2025 and into the mid-90s through 2026 — Verified is now effectively saturated, with the top models within a point or so of each other, which is why serious evaluation has moved to harder sets like SWE-bench Pro. That saturation is itself the point: the benchmark stopped discriminating long before agents stopped failing on real repos.
  • The caveat that matters more than the score: a benchmark whose tests are withheld from the model at solve time — but published, and therefore plausibly in its training data — measures "produces a patch that passes tests on issues resembling its training distribution". It doesn't measure design quality, matching your conventions, or knowing when to ask instead of guess. Treat leaderboard position as a floor on capability, not a prediction about your repo.
  • Outcome vs. trajectory evaluation. Outcome: did the tests pass? Cheap, objective, blind to a horrifying route to the right answer. Trajectory: did it take sensible steps, avoid destructive commands, stay in scope? Expensive to grade, and where the real risk lives.
  • LLM-as-judge for the things you can't assert on — was the explanation accurate, is this diff in-house style. Fast and scalable, but it inherits the same failure modes as the thing it's grading, so it needs a human-labelled sample to be calibrated against.
  • What I'd actually do on a real system: build a small suite of your own tasks from your own repo with known-good outcomes, and run it whenever you change the model, the prompt or the tools. Twenty representative tasks you trust beat any public leaderboard.

13 Security — the part almost nobody prepares

Prompt injection, and why it isn't a bug you can patch

The model sees one flat sequence of tokens. It has no reliable way to distinguish your instructions from data it fetched. So text inside a web page, a GitHub issue, a dependency's README or a tool result can carry instructions, and the model may follow them. This is a structural property of how LLMs consume input, not a defect awaiting a fix — which is exactly why the mitigation is architectural.

Direct injection is prompt input from the user altering the model's behaviour — in your own sandbox that's just jailbreaking, but in a multi-tenant product it's an attacker overriding your system prompt and guardrails (OWASP's LLM01). Indirect injection is the more insidious one: the payload arrives in content the agent was asked to read, on behalf of a user who did nothing wrong.

The "lethal trifecta" — Simon Willison's framing, and the best thing to quote hereRisk becomes serious when an agent has all three at once: (1) access to private data, (2) exposure to untrusted content, and (3) a way to communicate externally. Any two is usually survivable. All three means an attacker who controls the untrusted content can read your data and get it out. The practical defence is to break the triangle — the agent that reads untrusted input doesn't get network egress, or doesn't hold the secrets.

The other failure modes worth naming

  • Hallucinated dependencies ("slopsquatting"). Models invent plausible package names; attackers register them and wait for the install. Spracklen et al. (USENIX Security 2025) tested 16 models over 576,000 code samples and found 19.7% of recommended packages didn't exist — and, crucially, 43% of hallucinated names recurred in all ten reruns of the same prompt. That repeatability is what makes it exploitable rather than merely annoying: the attacker can predict the name and register it in advance. Rates are far lower on current frontier models, so quote it as "published research found around 20% across the models tested", not as a present-tense figure. Defence: lockfiles, an allowlist/private registry, and a CI check that every new dependency was deliberate.
  • Secrets in context. Anything in the window can end up in a log, a summary, or a request to the provider. Keep credentials in the execution environment, not in the prompt — the agent should call a tool that has the key, not be told the key.
  • Insecure generated code. The model writes what's common in training data, and a lot of training data is insecure. Veracode's 2025 GenAI code-security report tested over 100 models across 80 tasks and found 45% of generated code introduced an OWASP Top 10 flaw — with cross-site scripting and log injection failing well over 80% of the time. It doesn't "know" this is the auth path.
  • Over-broad permissions. An agent with your production credentials has your production credentials. Scope tokens to the task, run in a sandbox or container, and default to read-only unless the task needs writes.
Say this"I treat everything the agent reads as untrusted input and everything it writes as unreviewed code. That means sandboxing, least-privilege credentials, and never putting private data, untrusted content and network egress in the same agent — that combination is where the real incidents come from."

14 Cost & latency — the engineering constraint people forget

  • You pay per token, in and out, and output usually costs several times input. But agents are input-heavy: the whole growing transcript is re-sent every turn. A 30-turn task re-sends an ever-larger prompt 30 times, which is why token spend grows super-linearly with task length.
  • Prompt caching is the main lever. Stable prefixes — system prompt, tool definitions, project instructions — can be cached by the provider so re-sending them is far cheaper than the first time. The design consequence is concrete: put the stable things first and the changing things last, because a cache hit requires an identical prefix. Reordering your system prompt per request quietly destroys the saving.
  • Latency is dominated by output tokens. Generation is sequential — roughly one token at a time — so a verbose answer is slow almost in proportion to its length, while a large input is comparatively cheap to process. "Be concise" is a performance instruction, not just a style one.
  • Route by difficulty. A small fast model for classification, formatting and mechanical edits; a frontier model for the reasoning. Most production systems are mixtures, and saying so shows you've thought past "use the best model".
  • Bound everything. Max turns, token budget, wall-clock timeout. An unbounded loop that can't solve the task will keep trying — the failure mode isn't a crash, it's an invoice.

Part C

Brelly — the project that proves it

A React Native / Expo weather app. The app is the excuse; the guardrail system around the agent is the answer. Everything in Parts A and B is general knowledge — this is the part only you can say.

15 Hooks — deterministic control around a non-deterministic agent

Three hooks, wired in .claude/settings.json. Name them:

  • SessionStart session-context.sh — auto-injects the live task list & "traps" doc into the agent's context, so it never works from stale assumptions. context engineering
  • PreToolUse doc-gate.sh — before the agent edits any JS/TS file (.ts .tsx .js .jsx), it fires a reminder that Expo is v57 and to check the live docs. guardrail vs. outdated knowledge
  • Stop verify-gate.sh — after every turn it runs tsc, lint & tests. On failure it blocks the agent from finishing and feeds the errors back to fix before returning to me. agentic feedback loop
Know the mechanismExit 0 lets the turn end; exit code 2 blocks it unconditionally, and the reason handed back to the agent is your stderr. There is also a richer JSON form on stdout — a decision plus a reason, and additionalContext for injecting text — which is what SessionStart and PreToolUse use to push content into the context. Mine takes the exit-code route because a shell script that already exits non-zero on a failing tsc needs no extra plumbing. Being able to say "exit 2 blocks, stderr is the reason, and JSON is the structured alternative" is the difference between "I configured a hook" and "I understand the contract".

Map each hook back to Part B while you're describing it, because that's what turns three shell scripts into an argument: SessionStart is context engineering (§7) — deciding what occupies the window before the agent has done anything. PreToolUse is an interception at the harness seam (§6) — the point between "the model asked" and "the machine did". Stop is the bound on the loop (§5) — the agent doesn't get to decide it's finished.

16 Skills — reusable, scoped instructions loaded on demand

Five skills in .claude/skills/. Example: implement-feature defines my "definition of done" — zero lint warnings, a test for every new function.

progressive disclosure — the agent pulls the right instructions only when the task matches, instead of one giant prompt

The reason this beats a longer system prompt is §7 in practice: instructions that are always present compete for attention with everything else, and a 4,000-word standing brief makes every rule in it slightly less likely to be followed. A skill is loaded when its description matches the task, so the relevant instructions arrive uncontested. It is still persuasion, not enforcement — that's what the hooks are for — but it's persuasion delivered at the moment it's relevant.

17 Defence in depth — I don't trust the agent's word

Two layers, both backstopped by CI:

  • The code gate (tsc + lint + tests) runs in the Stop hook and again in CI.
  • Convention checks (commit subject must start feat/fix/chore, branch names) run in git hooks (.githooks/commit-msg, pre-push) and are re-checked in CI.

Your line: "Local git hooks can be skipped with --no-verify, so CI re-runs everything — it never trusts them." → shows you know soft rules get bypassed, so real enforcement is machine-checked.

Worth adding the second half of that thought: git hooks also aren't distributed by default — .git/hooks isn't part of the repository, which is why mine live in a checked-in .githooks/ directory pointed at by core.hooksPath. That's a small detail, and small details are what make a story sound lived-in rather than read.

18 Why hooks and not better prompts — the mechanism

This is the follow-up that separates a demo from an engineering answer, so have the reasoning ready rather than the list.

An LLM is probabilistic: the same prompt can produce different output, and there is no instruction you can write that makes compliance certain. A prompt is a request. So any rule that actually matters — "never ship failing types", "always check the current docs" — cannot live in the prompt, because the failure mode is silent and occasional, which is the worst kind.

A hook is deterministic: it's a shell script the harness runs at a fixed lifecycle point, and its exit code is not negotiable. That's the whole design principle in one line — put the soft rules in the prompt and the hard rules in the exit code.

Prompt / CLAUDE.mdPersuasionNothing. It raises the probability of the right behaviour, which is useful but not a guarantee

19 The feedback loop, concretely

Worth walking step by step, because "it self-corrects" sounds like marketing until you describe the actual cycle:

  1. The agent finishes a turn and tries to hand control back to me.
  2. The Stop hook fires first and runs tsc, lint and the test suite.
  3. If anything fails, the script exits 2 and writes the compiler and test output to stderr. (Exit 2 is the unconditional block; the JSON-on-stdout form would carry the reason in a decision field instead.)
  4. The harness treats that as a block: the turn does not end, and stderr is fed back to the agent as the reason — so it now has the exact type error, not a vague instruction to try again.
  5. It fixes and tries to stop again. The loop repeats until the gate passes, and only then do I see the result.

Two things to point out about that loop, because they're the interesting engineering rather than the tooling. The error message is the prompt. A compiler error is a far better instruction than anything I could write in advance — it is specific, current, and grounded in the actual code. And the loop needs a bound. An agent that cannot fix the failure will keep trying, so in practice you want an iteration cap and a way to surface "I'm stuck" to a human rather than burning tokens in a circle.

20 Limits — say these before you're asked

Volunteering the failure modes is what makes the rest credible. The system stops several classes of problem and is blind to others:

CaughtNot caught
Type errors, lint violations, failing testsWeak tests. A gate proves tests ran and passed; it cannot tell whether they assert anything meaningful. An agent that writes the test and the code can satisfy both with the same misunderstanding
Outdated API usage, where the doc-gate reminds it to checkConfidently wrong architecture. Nothing in tsc or lint objects to a design that works and is wrong for the codebase
Convention drift in commits and branchesScope creep. The agent refactoring three files it wasn't asked to touch passes every gate
Obvious regressions in covered pathsAnything uncovered. Coverage gates catch untested code, not untested behaviour

The honest summary line: the gates make the agent's output verifiable, not correct — code review is still mine to do.

The wider cost worth naming if pressed: this setup is friction. Every gate makes the loop slower, and a suite that takes three minutes turns each agent turn into a three-minute wait. That's a real tax, and the reason to keep the Stop-hook gate fast and push the slower checks to CI — the same speed-versus-confidence trade as any test suite.

The one insight to repeat

"AI is fast but confidently wrong — especially when its training is behind the current library version. My whole setup spends effort on the system around the agent — tests, doc-gates, feedback loops — rather than on perfect prompts. That's what turns it from a toy into something I'd ship."

22 Likely questions

On your project

"How do you make sure the AI doesn't write bad code?"

→ The three-layer verification story: Stop hook + git hooks + CI, all re-running tsc/lint/tests. Then the honest qualifier — it makes the output verifiable, not correct.

"What's a limitation of these tools?"

→ Outdated knowledge (my Expo v57 example), confident hallucination, and that they can't tell whether a test is meaningful — a coverage gate stops uncovered code but not weak assertions.

"Have you used agents beyond autocomplete?"

→ Yes: hooks, skills, a Stop-hook feedback loop that self-corrects, and MCP connectors.

"How do you know the AI's tests are any good?"

→ The honest answer: the gate doesn't know. It proves tests ran and passed, not that they assert anything. That's exactly why I read the diff — an agent that writes both the code and the test can satisfy both with the same wrong assumption. Where it matters I write the test first myself, so the agent is coding against an assertion it didn't choose.

"Isn't this a lot of ceremony for a weather app?"

→ Fair, and I'd say the setup was the point rather than the app. But the transferable bit is small: three hooks and a CI job. The reason it scales is that the enforcement is in exit codes rather than in a document people are asked to follow — the same reason we lint in CI instead of writing a style guide nobody reads.

"What would you change if you did it again?"

→ Bound the feedback loop. An agent that can't fix a failure keeps trying, so I'd add an iteration cap and a clean way for it to say it's stuck. I'd also split the gate: a fast check on every turn, the slow suite in CI, because a three-minute gate makes every turn a three-minute wait.

On the concepts

"Explain how an agent works to someone non-technical."

→ "It's a model in a loop. It can't do anything itself — it can only say 'please read this file' or 'please run the tests'. Ordinary code does the thing and hands back the result, and it decides what to do next with that. It stops when it answers instead of asking."

"When would you not use an agent?"

→ When the steps are known in advance — then a deterministic workflow with an LLM at one node is cheaper, testable and reproducible. Also when verification is expensive: auth, payments, anything where "passes the tests" doesn't mean "correct". Autonomy should scale with how cheaply I can check the answer.

"What's the hardest problem in building agents?"

→ Context, in both senses. Getting the right information in front of the model at the right step, and doing it without filling the window with noise — because quality degrades well before the limit is reached. Everything else (tools, loops, retries) is comparatively ordinary engineering.

"How would you stop an agent leaking data?"

→ Break the lethal trifecta: never give one agent private data, untrusted content and network egress simultaneously. Then least-privilege credentials, a sandbox, keep secrets in the execution environment rather than the prompt, and no auto-approval on tools that can send data outward.

"Which coding tool is best?"

→ Don't answer the product question. "They're converging on the same models, so I'd choose on three axes: how much autonomy I want, whether it can run my tests, and whether it edits my working tree or a sandbox." Then name what you've used and its actual weakness.

"Does this make junior engineers unnecessary?"

→ No, but it moves the skill. The scarce ability is now judging code you didn't write and knowing when the confident answer is wrong — which is exactly what you learn by writing code. The risk isn't fewer juniors, it's juniors who never build the judgement because they never had to debug their own mistake. Worth answering thoughtfully; it's often a values question rather than a technical one.

"How do you handle it when the agent is confidently wrong?"

→ Assume it always might be, and design so it costs little. Small units of work, one task per run, a gate it can't talk its way past, and a willingness to discard the whole run rather than debug its output — regenerating is cheap, untangling someone else's confused reasoning isn't.
