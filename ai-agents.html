00 — The word everyone uses loosely

Vibe coding — and the version you actually practise

Andrej Karpathy coined it in a post in February 2025. The original is stricter than how the phrase gets used now: you "fully give in to the vibes, embrace exponentials, and forget that the code even exists" — you say what you want, accept every diff without reading it, and when something breaks you paste the error back in rather than debugging. Crucially he framed it as fine for throwaway weekend projects. It named a mode; it did not recommend it for production. Collins made it their word of the year for 2025, which tells you how fast it escaped that framing.

Most people now use "vibe coding" to mean any AI-assisted coding at all. That looseness is your opening — drawing the distinction is free credibility, because it shows you read the source rather than the headlines.

Say this"Strictly, vibe coding means not reading the diffs — Karpathy's own framing was that it's for throwaway projects. He actually retired the term about a year later and proposed agentic engineering for the professional version: you're not writing the code, you're orchestrating agents and providing oversight. That's the distinction I care about — the AI writes, but the diff still gets reviewed and every change has to survive a machine-checked gate. Same speed, different accountability."

Knowing that the author dropped his own term is the detail that proves you read the source rather than the coverage — and "agentic engineering" is a more precise name for what you actually do. (If it comes up: Karpathy joined Anthropic's pretraining team in May 2026, so the person who named the mode now works at a lab that ships the agents.)

The autonomy ladder — place any tool on this

Rather than memorising products, hold one axis in your head: how much of the loop the human is still inside. Every tool sits somewhere on it, and the failure mode changes as you climb.

RungWhat the human doesDominant failure mode
0 · autocompleteTypes; accepts or rejects each suggestionA plausible-looking line that's subtly wrong — you accept it because it's one keystroke
1 · chatAsks a question, copies the answer acrossRight in general, wrong for your codebase
2 · inline editSelects a region, describes the change, reviews the diffBlast-radius creep — it rewrites more than you selected
3 · supervised agentGives a task; approves each tool callApproval fatigue — after twenty prompts you stop reading them
4 · sandboxed agentGives a task; reviews the finished PRYou review a 900-line diff you didn't watch being written
5 · fleetQueues many tasks; triages resultsReview becomes the bottleneck; nobody holds the whole picture
The pattern to nameAs you climb the ladder, the work doesn't disappear — it moves from writing to reviewing. Rungs 0–2 save you typing. Rungs 3–5 save you typing and then hand you back a reviewing job you didn't have before. That's the honest trade, and saying it out loud is the most senior-sounding sentence in this whole section.
01 — Six categories, not thirty product names

What actually exists, and what each kind is bad at

Interviewers ask "what tools have you used?" expecting a list. Give them a taxonomy, then name what you've actually touched inside it. Products change every quarter; the categories don't.

A · Inline completion

GitHub Copilot (2021 — not the first, Kite and TabNine predate it, but the one that made the category mainstream) and the tab-completion inside Cursor, Devin Desktop and Zed. The model predicts the next span from surrounding code. The latency budget is brutal — a suggestion that takes more than a few hundred milliseconds arrives after you've typed the line — so these run smaller, faster models than the chat panel beside them.

Genuinely good at boilerplate with a strong local pattern: a fifth test case shaped like the previous four, a mapper between two structs, filling out a switch. Where it hurts: it optimises for "looks like what usually comes next", which is exactly wrong at the points where your codebase is unusual.

B · AI-native editors

Cursor (a VS Code fork) and Devin Desktop are the best-known, with Google's Antigravity the other current entrant; JetBrains and VS Code itself have shipped their own agent modes. The differentiator isn't the model — most let you pick from the same handful — it's the context plumbing: how the editor decides which files to put in front of the model, and how it applies a diff back without mangling the file.

Two details worth having. "Apply the edit" is its own hard problem: a big model describes the change and a smaller, faster apply model merges it into the real file — when an edit lands in the wrong place, that second model usually failed, not the one that wrote the code. And know the Windsurf arc: it was the other big name until Google hired away its CEO in a $2.4bn acquihire and Cognition bought what was left in July 2025; Cognition renamed the editor Devin Desktop in June 2026 and retired its Cascade agent for "Devin Local" the following month, which is why Devin and the editor are now the same company. Getting that right costs nothing and reads as current.

C · Terminal / CLI agents

Claude Code, OpenAI Codex CLI, Google's Antigravity CLI (which replaced Gemini CLI for individual accounts on 18 June 2026), OpenCode (the open-source default now — over 200k GitHub stars and releases most weeks; Aider, the original open-source terminal agent, has had no commits since May 2026), OpenHands. The agent lives in your shell, in your repo, with your credentials and your test runner. This is the category that made agentic coding real, because the terminal is where the feedback is — the agent runs the failing test itself instead of asking you what happened.

Say why the category matters"An editor plugin sees files; a terminal agent sees files and consequences. That closed loop — edit, run, read the error, edit again — is the difference between a code generator and something that can finish a task."

D · Asynchronous / cloud agents

You hand over an issue and get back a pull request: GitHub Copilot's cloud agent (renamed from "coding agent" in April 2026, when it stopped being PR-only), OpenAI Codex in its cloud form, Google's Jules, Cognition's Devin, and the web modes of the CLI agents. Each task runs in its own sandboxed container with a fresh checkout.

The engineering point: isolation is what makes parallelism safe. Two agents editing one working tree corrupt each other; two agents in two containers — or two git worktrees — don't. If you've used worktrees for this, say so; it's a concrete detail that's hard to fake. The CLI agents have made it a first-class feature: claude --worktree <name> creates a worktree under .claude/worktrees/ on its own branch and starts the session inside it, a sub-agent can be given isolation: worktree in its frontmatter, and the harness then blocks any edit or git command that would reach back into the main checkout — the isolation is enforced, not requested.

E · Prompt-to-app builders

v0, Bolt.new, Lovable, Replit Agent. Natural language in, a deployed running app out. These are what the general public means by "vibe coding".

The honest read: extraordinary for the first 80% of a greenfield app and for a demo you need this afternoon. They degrade hard once the app has history — an existing schema, an auth model, a deploy pipeline someone else owns. They also generate the security-sensitive parts (auth, row-level access, secrets) with exactly the same confidence as a button, which is where the publicised incidents have come from.

F · AI code review

CodeRabbit, Greptile, GitHub's own PR review, and the review modes inside the CLI agents. Underrated, and the one to mention if you want to sound like you've thought about the whole lifecycle rather than the writing half.

The argument is arithmetic: if agents multiply how much code gets written, review is the constraint that binds. But note the asymmetry — an AI reviewer is a probabilistic reviewer, so it belongs as an extra pair of eyes with no merge rights, never as the approval. Its real value is the boring sweep (nullability, missing error handling, a changed function whose callers weren't updated) that humans skim past on a big diff.

TrapDon't recite this as a list — interviewers hear product names all day. What lands is: "I think of it as three questions: how much autonomy, whether it can run my tests, and whether it's editing my working tree or a sandbox. Everything on the market is a point in that space." Then name two or three you've actually used and what each was bad at.
02 — The matrix you reason from

"Which is best?" is the wrong question — here is the right one

The correct answer is "for what?", but only if you follow it immediately with a real breakdown.

SituationReach forBecause
throwaway prototypePrompt-to-app builder, or an agent on full autonomyNo existing convention to violate and no blast radius. Review cost is the only cost, and you aren't paying it.
feature in a big repoTerminal or IDE agent, supervisedThe hard part isn't writing code, it's matching twenty existing conventions. It needs to read a lot and you need to see what it read.
200-file migrationAgent, batched — one module per runThe highest-value case there is: repetitive, individually verifiable, and a test suite can prove each step. Small independent units also make a bad one cheap to throw away.
live incidentChat, with you drivingYou need a hypothesis, not a patch. An agent that starts editing before the cause is known produces plausible fixes that hide the symptom.
auth / paymentsHuman writes, AI reviewsThese are the paths where "compiles and passes tests" says almost nothing about correctness, and being confidently wrong isn't a bug, it's a breach.
unfamiliar codebaseAgent in read-only mode — ask, don't editThe best underrated use. "Trace what happens when a user hits this endpoint" across 40 files takes it minutes and you a day. No write access, so no risk.
Say this"My rule of thumb is that autonomy should scale with how cheaply I can verify the result. A migration with a green test suite: run it wide. Auth logic: I write it. The variable isn't how hard the task is, it's how well I can check the answer."

The autonomy dial has names in the tooling, and naming them is cheap credibility. Claude Code's permission modes: default (reads only without asking), acceptEdits (file edits auto-approved, shell still asks), plan (read and plan, no edits), auto (a second classifier model reviews each action instead of you), dontAsk (only pre-approved tools; anything that would prompt is denied — for CI), and bypassPermissions (everything, containers only). Deny rules apply in every mode including bypass. The table above is really a mapping from situation to mode.

What actually changes in the workflow

If they ask "how has this changed how you work?", resist "it makes me faster" — everyone says that, and the evidence is genuinely mixed. A 2025 randomised trial by METR on experienced open-source maintainers working in repos they knew well found they were about 19% slower with AI assistance while predicting they'd been roughly 20% faster. Volunteer the caveat: METR's follow-up (data from August 2025 on, published February 2026: 57 developers, 143 repos, 800+ tasks) found a much smaller effect — new recruits about 4% slower, returning participants 18% slower, both confidence intervals crossing zero — and METR said speedups now "seem likely" but that the design could no longer measure them, because developers increasingly refused to work without AI and skipped the tasks they would not attempt unaided. They retired the task-level randomised design. The durable finding isn't the 19% — it's the perception gap, and it's why you shouldn't quote speed numbers about yourself.

  • Effort moves from writing to reviewing. Your throughput is now bounded by how fast you can read code you didn't write. Different skill, more tiring one.
  • Small diffs get much cheaper; big diffs get more dangerous. The right response is to shrink the unit of work — one task per run, one PR per task — precisely because generation is cheap. If a run goes wrong, discard it and re-run with a better prompt rather than debugging its output.
  • Tests stop being optional. Under human-only development a suite is insurance. With an agent it's the control system — the only channel by which it discovers it was wrong without you telling it.
  • Codebase legibility becomes a performance feature. Clear names, small modules, a real README, typed boundaries — always nice, now measurably raising the agent's hit rate, because that's what it retrieves and reasons over. "Write for the next reader" now includes a machine reader.
Worth namingStack Overflow's 2025 developer survey had 84% using or planning to use AI tools while only 33% trusted the accuracy of the output and 46% actively distrusted it. That's not a contradiction, it's the correct posture — and it's your framing: high adoption, low trust, so the value is in the verification layer.
TrapNever claim a specific multiplier ("it made me 3× faster"). It invites "measured how?" and you have no answer. Say instead: "It's clearly faster for the things I can verify cheaply, and I've been burned enough on the things I can't that I've stopped guessing at the average."
03 — The one diagram to be able to draw

An agent is a model in a loop with tools

An LLM on its own is a function: text in, text out, no memory, no side effects. An agent is that function placed inside a loop with tools and a stopping condition. That's the entire idea, and it's worth being able to say it in one sentence.

Say this"An agent is a model in a loop with tools. The model can't do anything itself — it emits a request to call a tool, ordinary code executes it, the result is appended to the conversation, and the model runs again on the longer conversation. It repeats until it emits an answer instead of a tool call."
the loop, in eight lines
# 1. the model decides — it cannot act
context = [system_prompt, user_task]
while True:
    reply = model(context, tools=TOOL_SCHEMAS)
    if not reply.tool_calls:            # 2. no call = it is done
        return reply.text
    for call in reply.tool_calls:       # 3. the HARNESS executes
        result = TOOLS[call.name](**call.args)
        context += [call, result]       # 4. result fed back in

Four properties fall out of those eight lines, and each is worth a sentence:

  • The model never executes anything. It emits structured JSON saying "call read_file with this path". Your harness decides whether to actually do it. Every permission system, sandbox and guardrail lives at line 3 — that seam is why guardrails are possible at all.
  • The context grows every iteration. Each tool result is appended, so a 30-step task means the model re-reads a transcript that got longer 30 times. Prompt caching keeps the unchanged prefix cheap to re-send, so the cost curve is gentler than it looks — but attention still has to cross all of it, so long runs get slower and less accurate per step, not just longer in total.
  • Termination is the model's choice. Nothing external decides the task is done; the loop ends when it stops asking for tools. Exactly why production harnesses add hard bounds — a max-turns cap, a token budget, a wall-clock timeout.
  • Errors are just more input. A failed command isn't an exception, it's a string appended to the context. That is the whole trick behind self-correction: a stack trace is a better instruction than anything a human would have written in advance.

ReAct — the name to know

Interleaving reasoning with acting comes from the ReAct paper (Yao et al., 2022): rather than planning everything up front, the model thinks a step, acts, observes, and re-plans with what it now knows. Why it beats plan-then-execute is simple — most of the information you need is discovered during the task, not before it. Modern agents are essentially ReAct with better tools.

Agents vs. workflows — the distinction people get wrong

Anthropic's widely cited framing: a workflow is a system where LLMs and tools are orchestrated along predefined code paths; an agent is one where the LLM dynamically directs its own process and tool usage. Prompt chaining, routing and parallelisation are workflows. Only the model-drives-the-loop case is an agent.

Trap — and the answer that scores"Agent" is the fashionable word, so candidates use it for everything. The senior move is arguing for less agency: most production tasks are better served by a deterministic workflow with an LLM at one or two nodes, because you can test it, reproduce failures and bound the cost. Reach for a real agent only when the number of steps and their order genuinely can't be known in advance. "The right question is how little autonomy the task actually needs."
04 — Where determinism enters the system

The model chooses; the harness executes

People say "the model calls a function". It doesn't. Being precise here is a strong signal.

  1. You send the model a list of tool definitions — each a name, a description, and a JSON Schema for its parameters. These are injected into the prompt, so they occupy context on every request — the tool-use system prompt alone is roughly 290–350 tokens on current Claude models, plus every schema you send. Caching makes them cheap to re-send and some harnesses defer loading a large catalogue until the model searches for it (Anthropic's API has a tool-search tool for exactly this), but whatever is loaded competes for the model's attention.
  2. The model, instead of prose, emits a structured tool-use block: the tool name plus arguments matching that schema.
  3. Generation stops. The model is now waiting. Nothing has happened.
  4. Your code — the harness — validates the arguments, decides whether it's allowed, runs it, captures the output.
  5. The output goes back as a tool-result message and the model is called again with the extended conversation.
The line that shows you understand it"The model chooses; the harness executes. That split is why guardrails work — I can't stop a model from wanting to run rm -rf, but I control the process that would actually run it."

What makes a tool good — it's a prompt-engineering problem

The model picks a tool from its description, so tool design is prompt design wearing a different hat.

  • Few, well-separated tools beat many overlapping ones. Two tools whose descriptions could both plausibly apply produce coin-flip selection. With twenty tools, half of them near-duplicates, accuracy collapses long before the context does.
  • Return errors as text the model can act on. ENOENT is nearly useless; "No file at src/uti.ts — did you mean src/utils.ts?" gets fixed on the next turn. You are writing error messages for a reader that will genuinely change its behaviour based on them.
  • Cap the output size. A tool returning a 200k-token file dump destroys the context in one call. Paginate, truncate with an explicit marker, or return a summary plus a handle to fetch more.
  • Make destructive tools narrow. A general run_bash is maximally capable and maximally dangerous. Specific tools (run_tests, read_file) are auditable and can be auto-approved; the general one shouldn't be.
If asked "how would you design tools for an agent?""I'd treat the tool description as part of the prompt, keep the set small and non-overlapping, make every error message actionable, and cap output size — because tool results are the main thing that eats the context window."
05 — The discipline that replaced prompt engineering

Context engineering, and the three things called "memory"

The term has genuinely shifted. Prompt engineering is wording one message well. Context engineering is deciding what occupies the finite window at each step of a long-running loop — which files, which tool results, which history, which instructions — and what gets evicted. For agents the second is far more of the job, because the prompt is written once and the context is rebuilt every turn.

  • Attention is quadratic — during prefill. Self-attention compares every token to every other, so processing the prompt scales with roughly the square of its length: doubling the prompt is more than double the work. Once generation starts a KV cache makes each new token cost roughly linear in context — still growing, just not quadratically — and prompt caching means the stable prefix often isn't reprocessed at all. Know that split; it's a favourite follow-up.
  • Frontier models today are typically 1M tokens — 200k was the norm until recently and still is for some small tiers (Claude Haiku 4.5 is 200k; Gemini's Flash models are 1M). The old rule of thumb is one token ≈ 4 characters ≈ 0.75 English words, so ~750k words at 1M and ~150k at 200k — but tokenisers move: Anthropic's current one (Opus 4.7 onward) produces about 30% more tokens for the same text, so 1M is nearer 555k words or 2.5M characters there. Sounds enormous until an agent reads six files and runs a test suite whose output is 20k tokens on its own.
  • Quality degrades before the limit does. "Context rot" is Chroma's term (July 2025): across 18 models, including then-current GPT-4.1, Claude 4 and Gemini 2.5, accuracy fell as input grew even on trivial copy-and-retrieve tasks, and got worse when the distractors were semantically close to the needle. Models also attend better to the beginning and end than the middle — the "lost in the middle" effect from Liu et al. (2023). A fact buried at 60% depth in a huge context can be effectively invisible.
The counter-intuitive ruleMore context is not better. Every irrelevant token competes for attention with the relevant ones. "The goal is the smallest set of high-signal tokens that makes the next decision correct" — that's the sentence to remember.

The techniques, and what each costs

TechniqueMechanismWhat it costs
compactionNear the limit, summarise the transcript and continue from the summary plus the most recent turnsLossy by construction. The detail you drop is gone — so pin what must survive: the task, key decisions, file paths
just-in-timeDon't preload files; give the agent search and read tools and let it pull what it needs, when it needs itMore turns, so more latency. But it's how humans work, and context stays proportional to the task

The mistake to name: stuffing the whole repo in "just in case". It raises cost and latency on every turn and lowers accuracy — you've buried the three relevant files under two hundred irrelevant ones.

Memory — three different things wearing one word

"Does it remember?" is ambiguous, and the ambiguity is the answer.

  • In-context (working) memory — the current conversation. Perfect recall, strictly bounded, gone when the session ends. The only kind the model actually has.
  • Persistent instructions — a project file (CLAUDE.md, AGENTS.md, editor rules) loaded into every session. Not memory so much as a standing brief: conventions, commands, architecture, the traps. The highest-leverage thing you can write for a coding agent, because it's the one context always present.
  • Retrieved long-term memory — facts written to files or a vector store and fetched when relevant. Genuinely useful and genuinely hard, because the difficulty isn't storing, it's invalidating. A remembered fact about a file you've since refactored is a landmine.
Say this"Models are stateless between calls. Everything that looks like memory is a retrieval-and-re-injection trick built around them — the interesting engineering problem is deciding what to bring back and when to throw it away, not how to store it."
06 — The integration standard

Model Context Protocol — and the security question that follows

An open standard published by Anthropic in November 2024 and now broadly adopted across vendors; Anthropic donated it to the Linux Foundation's Agentic AI Foundation in December 2025, so it's a genuine cross-vendor standard rather than one company's. The usual one-liner is "a USB-C port for AI applications".

The problem it solves — say it as arithmetic

Before: every AI application needed a bespoke integration with every tool. M applications × N tools = M×N connectors, each maintained separately. With a shared protocol it's M + N: each app implements a client once, each tool ships one server. Same shape of argument as the Language Server Protocol, and comparing it to LSP is a good way to show it isn't magic — it's an interface boundary in the right place.

The mechanism

  • Client / server over JSON-RPC 2.0. The host application — your IDE, agent or desktop app — runs an MCP client; each integration is a server.
  • Two transports. stdio for a local server the host launches as a subprocess, and Streamable HTTP for remote servers (the original HTTP+SSE transport is deprecated). Authorisation is defined for HTTP only: the server is an OAuth 2.1 resource server, advertises its authorisation server via Protected Resource Metadata (RFC 9728), and the client must send a resource indicator (RFC 8707) so a token minted for one server cannot be replayed at another; a stdio server just reads credentials from its environment.
  • Three primitives the server exposes. Tools (model-controlled actions), Resources (data the application reads into context), and Prompts (user-invoked templates, e.g. slash commands). The who-controls-what split is the detail worth knowing — it separates "the model decided to do this" from "the application supplied this" from "the user asked for this".
Currency check — the 2026-07-28 revisionThe spec revision of 28 July 2026 made MCP stateless: no initialize handshake and no session ID — every request carries its protocol version and capabilities in _meta, and a new server/discover call advertises what a server supports. It also deprecated the client-side Roots and Sampling primitives (pass paths as tool arguments; call your LLM provider directly), moved long-running Tasks out of core into an official extension, and deprecated OAuth Dynamic Client Registration in favour of Client ID Metadata Documents. The server side — Tools, Resources, Prompts — is unchanged, and Elicitation (a server asking the user for more input mid-call) is now the one client primitive worth naming. The official registry (registry.modelcontextprotocol.io) has been in preview since September 2025 and is still not GA. For agent-to-agent rather than agent-to-tool, the sibling standard is Google's A2A (April 2025, donated to the Linux Foundation June 2025, v1.0 January 2026); both now live under the LF's Agentic AI Foundation.
Trap — the security follow-upEvery MCP server you connect is untrusted code holding your credentials, and untrusted text entering your context. A malicious or compromised server can return content designed to steer the agent, and a legitimate one can leak data across boundaries — the pattern where an agent with access to both a private repo and a public one is talked into moving content between them. Answer: connect servers deliberately, prefer least-privilege tokens over broad ones, and don't auto-approve tool calls from a server whose output you haven't seen.
07 — Why the default flipped, and where it did not

RAG, grep, and a disagreement worth knowing about

A useful "I've thought about this" answer, because the intuitive one is out of date and the frontier is genuinely split — so present it as a live disagreement, not a settled result.

RAG (retrieval-augmented generation): pre-chunk the corpus, embed each chunk into a vector, embed the query, fetch the nearest chunks, put them in the prompt. It was the default answer to "how does the AI know about my codebase" for years.

Agentic search: don't index anything. Give the model grep, find and read_file, and let it search the way a developer would — start with a symbol name, follow the imports, read the file.

The split worth knowing. The CLI agents dropped the vector index: Claude Code's lead has said early versions used RAG with a local vector DB and that agentic search simply worked better — simpler, with none of the staleness, privacy or index-maintenance problems. Cursor went the other way, training its own embedding model on agent traces and reporting (November 2025) around 12.5% higher accuracy on code questions (6.5–23.5% depending on the model), with the code-retention gain rising from 0.3% overall to 2.6% on repos over a thousand files. Both grep heavily; the disagreement is whether semantic search earns its keep on top. Saying that beats picking a side.

Embedding-based RAGAgentic search
freshnessIndex goes stale the moment code changes; needs re-indexingAlways current — it reads the working tree
precisionSemantic similarity, so it finds "things about auth" but may miss the exact symbolExact. Code is full of unique identifiers, which is ideal for lexical search
latencyOne fast lookupSeveral sequential model turns — slower and more tokens
structureNaive chunking cuts across function boundaries and loses the call graph; AST-aware chunking fixes the first half, not the secondFollows imports and references the way a human would
best forLarge prose corpora — docs, tickets, support historyCodebases, where identifiers are unique and structure is navigable
Say this"For prose, embeddings win — you're searching for meaning. For code, exact search usually wins, because code is full of unique identifiers and the structure is already navigable. The strong setups do both: lexical search for symbols, semantic search for 'where do we handle refunds', and the model decides which to use."
08 — When more agents is the wrong answer

Orchestrator, workers, and a 15× token bill

The common shape is orchestrator–worker: a lead agent decomposes the task and spawns sub-agents, each with its own clean context, each returning a summary. Two real benefits — parallelism (n investigations at once) and context isolation (the lead never holds all the raw detail).

Anthropic reported that a multi-agent research system outperformed a single-agent baseline by 90.2% on its internal research eval, on breadth-first queries — and, in the same write-up, that agents burn roughly 4× the tokens of a chat interaction, and multi-agent systems around 15×. That figure is the whole trade-off in one number, so remember it.

When it helps

  • The subtasks are genuinely independent and mostly read-only — search, research, audit, review from several angles.
  • Breadth matters more than a single deep chain of reasoning.
  • Each subtask's output compresses well into a summary the parent can act on.

When it hurts

  • Shared mutable state. Two agents editing the same files conflict in ways neither can see. Fix: isolate — separate worktrees or containers — or don't parallelise the writes.
  • Tightly coupled steps. If step 2 needs step 1's reasoning, splitting them just loses information across a summary boundary.
  • Cost and debuggability. ~15× a chat, so roughly 4× a single agent — quote the baseline, because "15×" said inside a single-agent comparison is exactly the slip an interviewer who has read the post will catch. And a failure now has to be traced through several transcripts instead of one.
The senior line"Sub-agents are a context-management tool before they're a parallelism tool. The reason to spawn one usually isn't speed — it's that I want the messy 40k tokens of an investigation to happen somewhere that isn't my main context, and only the conclusion to come back."
09 — The question nobody prepares for

How would you know an agent is any good?

Ask an interviewer's favourite unasked question before they ask it. Most candidates have no answer here at all.

  • The benchmark to name: SWE-bench and its human-validated subset SWE-bench Verified — real GitHub issues from real Python repos, scored by whether the model's patch makes the repo's own fail-to-pass and pass-to-pass tests green. Frontier scores went from single digits in 2023 to around 80% by late 2025 and into the mid-90s through 2026. Verified is now effectively saturated — the top scores sit around 95–96% and within a point of each other — and OpenAI stopped reporting it in February 2026 after showing that frontier models could reproduce the original human-written fixes, i.e. the tasks are in the training data. Serious evaluation has moved to harder sets: SWE-bench Pro (Scale AI: 1,865 tasks across 41 repos in Go, Python, JavaScript and TypeScript, with private and held-out subsets to defeat contamination; the public-set leaders are around 60%), Terminal-Bench 2 (89 curated end-to-end terminal tasks — sysadmin, data processing, model training, security — where the best agents score about 90% on the 2.1 revision), and τ²-bench for tool use under a policy with a simulated user (retail, airline, telecom; succeeded by τ³-bench). Know that HumanEval, the classic single-function benchmark, is saturated at 96–98% and tells you nothing about current models.
  • The caveat that matters more than the score: a benchmark whose tests are withheld from the model at solve time — but published, and therefore plausibly in its training data — measures "produces a patch that passes tests on issues resembling its training distribution". It doesn't measure design quality, matching your conventions, or knowing when to ask instead of guess. And the saturation is itself the point: the benchmark stopped discriminating long before agents stopped failing on real repos.
  • Outcome vs. trajectory evaluation. Outcome: did the tests pass? Cheap, objective, blind to a horrifying route to the right answer. Trajectory: did it take sensible steps, avoid destructive commands, stay in scope? Expensive to grade, and where the real risk lives.
  • LLM-as-judge for what you can't assert on — was the explanation accurate, is this diff in-house style. Fast and scalable, but it inherits the failure modes of the thing it's grading, so calibrate it against a human-labelled sample.
  • What I'd actually do on a real system: build a small suite of your own tasks from your own repo with known-good outcomes, and re-run it whenever you change the model, the prompt or the tools. Twenty representative tasks you trust beat any public leaderboard.
10 — The part almost nobody prepares

Prompt injection is not a bug you can patch

The model sees one flat sequence of tokens. It has no reliable way to distinguish your instructions from data it fetched. So text inside a web page, a GitHub issue, a dependency's README or a tool result can carry instructions, and the model may follow them. This is a structural property of how LLMs consume input, not a defect awaiting a fix — which is exactly why the mitigation is architectural.

Direct injection is prompt input from the user altering the model's behaviour — in your own sandbox that's just jailbreaking, but in a multi-tenant product it's an attacker overriding your system prompt and guardrails (OWASP's LLM01). Indirect injection is the more insidious one: the payload arrives inside content the agent was asked to read, on behalf of a user who did nothing wrong.

The lethal trifecta — Simon Willison's framing, and the best thing to quote hereRisk becomes serious when an agent has all three at once: (1) access to private data, (2) exposure to untrusted content, and (3) the ability to communicate externally. Any two is usually survivable. All three means an attacker who controls the untrusted content can read your data and get it out. The practical defence is to break the triangle — the agent that reads untrusted input doesn't get network egress, or doesn't hold the secrets.

The other failure modes worth naming

  • Hallucinated dependencies ("slopsquatting"). Models invent plausible package names; attackers register them and wait for the install. Spracklen et al. (USENIX Security 2025) tested 16 models over 576,000 code samples and found 19.7% of recommended packages didn't exist — and, crucially, 43% of hallucinated names recurred in all ten reruns of the same prompt. That repeatability is what makes it exploitable rather than merely annoying: the attacker can predict the name and register it in advance. Quote the 19.7% carefully: it is an average dominated by the open-weight models (21.7%) — the commercial models averaged about 5%, and a 2026 re-run on five frontier models (Claude Sonnet 4.6, Haiku 4.5, GPT-5.4-mini, Gemini 2.5 Pro, DeepSeek V3.2) found 4.6–6.1%, with 127 names all five models invented identically, 53 of them still registrable. Lower, not gone. Defence: lockfiles, an allowlist or private registry, and a CI check that every new dependency was deliberate.
  • Secrets in context. Anything in the window can end up in a log, a summary, or a request to the provider. Keep credentials in the execution environment, not in the prompt — the agent should call a tool that has the key, not be told the key.
  • Insecure generated code. The model writes what's common in training data, and a lot of training data is insecure. Veracode's 2025 GenAI code-security report tested over 100 models across 80 tasks and found 45% of generated code introduced an OWASP Top 10 flaw, with cross-site scripting and log injection failing well over 80% of the time. It doesn't "know" this is the auth path. Veracode's spring 2026 update (150+ models) put the failure rate at ~45% again — flat across two years of model releases, while syntactic correctness went past 95%.
  • Over-broad permissions. An agent with your production credentials has your production credentials. Scope tokens to the task, run in a sandbox or container, default to read-only unless the task needs writes.

The defences that have names

"Sandbox it" is table stakes. The follow-up is "what does the research say", and three names cover it:

  • Dual-LLM pattern (Simon Willison, April 2023). A privileged model with tools never sees untrusted text; a quarantined model with no tools reads it and returns only opaque handles or structured values the privileged side can pass around without interpreting.
  • CaMeL (Google DeepMind, March 2025, "Defeating Prompt Injections by Design"). The dual-LLM idea plus capability-based data-flow tracking: the privileged model writes a small program in a restricted language, and an interpreter tracks where every value came from and refuses to send data tainted by untrusted input to a tool that could exfiltrate it. Security comes from the interpreter, not the model's judgement.
  • Spotlighting (Microsoft Research, March 2024). Mark the provenance of untrusted input — delimiters, datamarking every word, or base64-encoding it — so the model can tell data from instructions; reported to cut attack success on GPT-family models from over 50% to under 2%. Cheap, and the weakest of the three, because it still relies on the model complying.

The honest ordering: spotlighting reduces the probability; dual-LLM and CaMeL change the architecture so a successful injection has nowhere to go. The lethal-trifecta test is how you decide which you need.

Say this"I treat everything the agent reads as untrusted input and everything it writes as unreviewed code. That means sandboxing, least-privilege credentials, and never putting private data, untrusted content and network egress in the same agent — that combination is where the real incidents come from."
11 — The constraint people forget

Where the money and the milliseconds actually go

  • You pay per token, in and out, and output usually costs several times input — 5× on Anthropic's and OpenAI's current list prices, 6× on Google's. Concretely (September 2026, per million tokens): Claude Fable 5.1 $10 / $50, Claude Opus 5.5 $4 / $20, Claude Sonnet 5 $2 / $10, Claude Haiku 4.5 $1 / $5; OpenAI GPT-6 Astra $10 / $50, GPT-6 Sol $2 / $10, GPT-6 Luna $0.10 / $0.50; Gemini 3.1 Pro $2 / $12, doubling above 200k input tokens. Batch APIs are 50% off for work that can wait. But agents are input-heavy: the whole growing transcript is re-sent every turn, so a 30-turn task re-sends an ever-larger prompt 30 times, and token spend grows super-linearly with task length.
  • Prompt caching is the main lever. A stable prefix — system prompt, tool definitions, project instructions — can be cached by the provider so re-sending it is far cheaper than the first time. It is a strict prefix match, which makes the design consequence concrete: put the stable things first and the changing things last. Reordering your system prompt per request quietly destroys the saving, because any changed byte invalidates everything after it. The numbers, since "far cheaper" invites "how much": on Anthropic a cache write costs 1.25× the input price (5-minute TTL) or 2× (1-hour TTL) and a cache read 0.1× — 0.05× on Opus 5.5 and 0.025× on Fable 5.1 — so a 5-minute write pays for itself on the very next read; the prefix is built in the order tools → system → messages, you get up to four breakpoints, the minimum cacheable prefix is 512–4,096 tokens depending on the model, and every read refreshes the TTL, so an agent loop that turns over faster than five minutes keeps itself warm. OpenAI and Google both bill cached input at 10% of the base rate; Google additionally charges per token-hour of cache storage, which is the trap in their model.
  • Latency is dominated by output tokens. Generation is sequential — roughly one token at a time — so a verbose answer is slow almost in proportion to its length, while a large input is comparatively cheap because prefill parallelises. "Be concise" is a performance instruction, not just a style one.
  • Route by difficulty. A small fast model for classification, formatting and mechanical edits; a frontier model for the reasoning. Most production systems are mixtures, and saying so shows you've thought past "use the best model".
  • Bound everything. Max turns, token budget, wall-clock timeout. An unbounded loop that can't solve the task will keep trying — the failure mode isn't a crash, it's an invoice.
12 — The project that proves it

Deterministic control around a non-deterministic agent

Everything above is general knowledge. This is the part only you can say: Brelly, a React Native / Expo weather app. The app is the excuse; the guardrail system around the agent is the answer.

Three hooks

Wired in .claude/settings.json. Name them:

  • SessionStart — session-context.sh auto-injects the live task list and "traps" doc into the agent's context, so it never works from stale assumptions. Context engineering, applied.
  • PreToolUse — doc-gate.sh fires before the agent edits any JS/TS file (.ts .tsx .js .jsx), reminding it that Expo is v57 and to check the live docs. A guardrail against outdated training.
  • Stop — verify-gate.sh runs tsc, lint and tests after every turn. On failure it blocks the agent from finishing and feeds the errors back to fix before returning to me. An agentic feedback loop.
Know the mechanismExit 0 lets the turn end; exit code 2 blocks it unconditionally, and the reason handed back to the agent is your stderr. There is also a richer JSON form on stdout — a decision plus a reason, and additionalContext for injecting text — which is what SessionStart and PreToolUse use to push content in. Mine takes the exit-code route because a shell script that already exits non-zero on a failing tsc needs no extra plumbing. Two details the docs add that are worth having: the harness passes stop_hook_active: true to a Stop hook that is already re-running because of a previous block, and it overrides the hook and ends the turn after 8 consecutive blocks — so the loop is bounded by the harness even if your script forgets. Hooks are no longer only shell: type: "prompt" and type: "agent" hooks ask a model to judge the event, and type: "http" posts it to a service. Being able to say "exit 2 blocks, stderr is the reason, and JSON is the structured alternative" is the difference between "I configured a hook" and "I understand the contract".

Map each hook back to the concepts while you describe it — that's what turns three shell scripts into an argument. SessionStart is context engineering: deciding what occupies the window before the agent has done anything. PreToolUse is an interception at the harness seam: the point between "the model asked" and "the machine did". Stop is the bound on the loop: the agent doesn't get to decide it's finished.

Five skills

In .claude/skills/. Example: implement-feature defines my definition of done — zero lint warnings, a test for every new function. Progressive disclosure: the agent pulls the right instructions only when the task matches, instead of one giant prompt.

Why this beats a longer system prompt is context engineering in practice: instructions that are always present compete for attention with everything else, and a 4,000-word standing brief makes every rule in it slightly less likely to be followed. A skill loads when its description matches the task, so the relevant instructions arrive uncontested. It is still persuasion, not enforcement — that's what the hooks are for — but persuasion delivered at the moment it's relevant.

13 — Why hooks and not better prompts

Put the soft rules in the prompt and the hard rules in the exit code

Two layers, both backstopped by CI:

  • The code gate (tsc + lint + tests) runs in the Stop hook and again in CI.
  • Convention checks — commit subject must start feat/fix/chore, branch naming — run in git hooks (.githooks/commit-msg, pre-push) and are re-checked in CI.

Your line: "Local git hooks can be skipped with --no-verify, so CI re-runs everything — it never trusts them." That shows you know soft rules get bypassed, so real enforcement has to be machine-checked. Worth adding the second half: git hooks also aren't distributed by default — .git/hooks isn't part of the repository — which is why mine live in a checked-in .githooks/ directory pointed at by core.hooksPath. Small details are what make a story sound lived-in rather than read.

The mechanism behind the choice

This is the follow-up that separates a demo from an engineering answer, so have the reasoning ready rather than the list.

An LLM is probabilistic: the same prompt can produce different output, and there is no instruction you can write that makes compliance certain. A prompt is a request. So any rule that actually matters — "never ship failing types", "always check the current docs" — cannot live in the prompt, because the failure mode is silent and occasional, which is the worst kind. A hook is deterministic: a shell script the harness runs at a fixed lifecycle point, whose exit code is not negotiable.

LayerEnforcementWhat it can guarantee
promptPersuasionNothing. It raises the probability of the right behaviour, which is useful but not a guarantee
skillScoped instructions loaded on matchStill persuasion — but far more reliable, because the instructions arrive when they're relevant instead of competing with everything else in a giant prompt
hookExit codeA hard stop. Exit 2 blocks the turn and returns stderr as the reason; the agent cannot decide to ignore it

Say this"The prompt is where I ask. The hook is where I insist. CI is where nobody gets a vote."
14 — Volunteer the failure modes

The feedback loop, and what it is blind to

Walk the cycle step by step, because "it self-corrects" sounds like marketing until you describe it:

  1. The agent finishes a turn and tries to hand control back to me.
  2. The Stop hook fires first and runs tsc, lint and the test suite.
  3. If anything fails, the script exits 2 and writes the compiler and test output to stderr. (Exit 2 is the unconditional block; the JSON-on-stdout form would carry the reason in a decision field instead.)
  4. The harness treats that as a block: the turn does not end, and stderr goes back to the agent as the reason — so it has the exact type error, not a vague instruction to try again.
  5. It fixes and tries to stop again. The loop repeats until the gate passes, and only then do I see the result.

Two things to point out, because they're the interesting engineering rather than the tooling. The error message is the prompt — a compiler error is a far better instruction than anything I could write in advance: specific, current, and grounded in the actual code. And the loop needs a bound — an agent that cannot fix the failure will keep trying, so you want an iteration cap and a way to surface "I'm stuck" to a human rather than burning tokens in a circle. Claude Code gives you a floor for free (eight consecutive Stop-hook blocks, then it ends the turn regardless, and stop_hook_active tells your script it is on a retry), but eight runs of a three-minute suite is still twenty-four minutes, so a tighter cap of your own in the script is the senior answer.

Limits — say these before you're asked

Volunteering the failure modes is what makes the rest credible.

CaughtNot caught
type errors, lint, failing testsWeak tests. A gate proves tests ran and passed; it cannot tell whether they assert anything meaningful. An agent that writes the test and the code can satisfy both with the same misunderstanding
outdated API usageConfidently wrong architecture. Nothing in tsc or lint objects to a design that works and is wrong for the codebase
convention driftScope creep. The agent refactoring three files it wasn't asked to touch passes every gate
regressions on covered pathsAnything uncovered. Coverage gates catch untested code, not untested behaviour

The honest summary line: the gates make the agent's output verifiable, not correct — code review is still mine to do.

The cost, if pressedThis setup is friction. Every gate makes the loop slower, and a suite that takes three minutes turns each agent turn into a three-minute wait. That's a real tax, and the reason to keep the Stop-hook gate fast and push the slower checks to CI — the same speed-versus-confidence trade as any test suite.
The one insight to repeat"AI is fast but confidently wrong — especially when its training is behind the current library version. My whole setup spends effort on the system around the agent — tests, doc-gates, feedback loops — rather than on perfect prompts. That's what turns it from a toy into something I'd ship."

Concept vocabulary

TermYour one-liner

Strict sense: you accept all and don't read the diffs — his framing was that it's fine for throwaway projects. He retired the term in early 2026 in favour of agentic engineering for the professional version.
agentAn LLM that can act in a loop — call tools, see results, decide the next step — not just answer once. Model + tools + loop.
workflowLLM calls orchestrated along predefined code paths. Cheaper, testable, reproducible. Prefer it unless the steps genuinely can't be known in advance.
tool useFunctions the agent can invoke, described to it as JSON Schema. The model emits a request; your harness executes it. That split is where every guardrail lives.
harnessThe ordinary, non-AI code around the model that runs tools, appends results, enforces permissions and decides when to stop. Most of an agent's quality lives here, not in the model.
ReActReason → act → observe → repeat, rather than plan-everything-then-execute (Yao et al., 2022). Works because most of what you need is discovered during the task.
context windowThe model's working memory — 1M tokens on most frontier models now, 200k on some small tiers (Claude Haiku 4.5). Everything is re-sent every turn, so it's a budget, not a container.
context engineeringDeciding what occupies that window at each step. Replaced "prompt engineering" as the real skill for agents, because the prompt is written once and the context is rebuilt every turn.
context rotAccuracy degrades as input grows (Chroma's term, July 2025, 18 models), and models attend better to the start and end than the middle. More context is not free — irrelevant tokens compete with relevant ones.
compactionSummarising the transcript when the window fills, then continuing from the summary. Lossy by design — pin what must survive.
