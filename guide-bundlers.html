Frontend interview prep

A bundler is a graph compiler.

It walks your import graph, transforms each node, decides how to cut the graph into files, and emits something a browser can cache. Every config option you'll be asked about is one of those four jobs.

00 — The mental model

Four jobs, one pipeline

Interviewers rarely want you to recite config. They want to know you understand what problem each stage solves, because that's what lets you debug a build you've never seen.

1 · Resolve

Turn every import specifier into a real file. Bare specifiers (react) aren't URLs — someone has to map them to node_modules, honour exports/main/browser, and add extensions.

2 · Transform

Per-module: TS→JS, JSX→createElement/jsx, Sass→CSS, modern syntax→target syntax. In webpack these are loaders; in Vite/Rollup they're plugin hooks.

3 · Optimise & chunk

Tree-shake dead exports, minify, and cut the graph into chunks so the first paint doesn't download the whole app.

4 · Emit

Write hashed assets, a manifest / HTML, and source maps. Hashing is what makes long-term HTTP caching safe.

Why each stage has to exist

The four stages are not a taxonomy someone invented for a diagram. Each one exists because something specific and nameable breaks without it, and being able to say what breaks is the difference between reciting a pipeline and understanding one. Take them one at a time.

1 · Resolve — without it, import React from 'react' never even becomes a request. In the ES module spec a specifier is a URL, resolved relative to the importing module. './utils.js' is relative and works; 'react' is neither relative nor absolute, so resolution fails locally and no fetch is ever attempted — there is no 404, just a module graph that cannot be linked. The module itself parses fine; the failure comes later, while the browser is fetching the graph’s dependencies, and it happens before any module evaluates, so you cannot catch it around the import. Chrome words it Failed to resolve module specifier; Firefox and Safari phrase it differently. Node invented an answer — walk up the directory tree looking in node_modules — but a browser has no filesystem to walk, so somebody has to perform that lookup ahead of time and rewrite the specifier to something fetchable.

  • It is more than a path join. Resolution also picks an entry point from the package’s exports map — honouring conditions like import versus require, which Node implements itself, plus the community ones bundlers set on their own behalf, browser versus node and development versus production — falls back to main, plus the non-standard module and browser fields that bundlers rather than Node honour, adds the extension you left off — something CommonJS and bundler resolvers do but Node’s own ESM resolution pointedly does not — and follows the symlinks that pnpm’s layout is built from.
  • Scale is the reason it must be automated. A mainstream React app resolves thousands of modules across hundreds of installed packages. Every one of those edges is a decision of exactly this kind.
  • When you can skip it: an import map lets the browser resolve bare specifiers natively, which is genuinely a way to run unbundled dependencies. The cost is that the map must cover every bare specifier your dependencies use, not just your own, which in practice means generating it from a CDN or a tool rather than hand-writing it. You have not removed the resolution work; you have moved it into a file you are now responsible for keeping correct.

2 · Transform — without it, the browser cannot even parse your source. This is a parse-time failure, not a runtime one, which is the part worth stressing. const x: number = 1 and <div /> are syntax errors in JavaScript, so the module never begins executing and there is nothing to try/catch. A .vue or .svelte file is not JavaScript at all, and a .scss file is not CSS. Something has to turn each module into the language the platform actually implements.

  • Two different jobs wear the same name. Compiling a non-JS syntax (TypeScript, JSX, Sass) is unavoidable if you use it. Downlevelling modern JavaScript for older engines is a choice you make with a browserslist target, and it is the expensive half — targeting ES5 rewrites async/await into a state machine and pulls in helper runtimes, inflating output for browsers you may no longer support.
  • It is per-module, and that is what makes it parallelisable. Each file is transformed in isolation with no knowledge of the others, so the work spreads across cores freely. Be careful with the causal story, though: Babel is per-file too, so isolation is not what makes esbuild and SWC fast. Their speed comes from being compiled to native code — Go and Rust against Babel’s JavaScript — from using real threads rather than worker processes, and from purpose-built parsers instead of layers over a shared AST. SWC’s own benchmark puts it around 20× Babel on one thread and 70× on four. The isolation matters for a different reason: type checking needs the whole program, so these tools strip types rather than verify them, and tsc --noEmit stays a separate job.
  • When you can skip it: author plain modern JavaScript and target evergreen browsers, and you need no transform stage at all. That is the honest version of the “no build step” setup — it is available, it just costs you TypeScript and JSX.

3 · Optimise & chunk — without it, the first paint downloads the entire application. This stage is where a bundler earns its keep, and it is really three jobs with three separate justifications.

  • Tree shaking needs a view of the whole graph. Deciding that an export is unused is a claim about every module in the program at once, which no per-file tool can make. It works only because ESM import/export statements are static — the names are known without running anything, so the bundler can build a reachability graph and drop what nothing points at. CommonJS mostly defeats this, and it is worth naming the right reason: not that require() takes an expression — it is a literal string almost everywhere, which is how CJS gets bundled at all — but that module.exports is an ordinary mutable object. exports[someExpression] = fn is legal, so the export set is only fully knowable at runtime. Bundlers do recognise the common static patterns, and webpack 5 has grown steadily better at it, but they bail out the moment the code strays. That asymmetry in reliability, not a hard impossibility, is why a library’s ESM build shakes and its CJS build cannot be counted on to.
  • Minification is cheap bytes that compression cannot recover. Renaming locals to single letters, folding constants, and eliminating branches made dead by substituting process.env.NODE_ENV all remove information gzip would otherwise have to encode. It composes with compression rather than competing with it, because gzip is semantics-blind and cannot delete a dead branch at any ratio: minify-then-compress typically lands 30–60% below compressing the unminified source.
  • Chunking exists for two independent reasons, and people usually name only one. The obvious one is latency — a route the user has not visited should not be on the critical path. The one that separates a strong answer is caching: in a single bundle, a one-line change to your own code invalidates the megabyte of vendor dependencies sitting next to it, so every deploy makes every returning user re-download React. Splitting stable dependencies from volatile application code is what makes long-lived caches actually pay.
  • When it backfires: splitting is not free. Each chunk is a separate request with its own headers, and each file is compressed as its own stream — gzip’s 32 KB back-reference window resets at every file boundary — so several small files compress worse than one merged file. That penalty is smaller under brotli, whose built-in ~120 KB dictionary of common web tokens exists precisely to rescue small files. For a rule of thumb, webpack’s splitChunks will not create a chunk below 20 KB of unminified source by default, which is a reasonable proxy for “too small to deserve its own request”. The waterfall risk is narrower than it is usually stated: the naive case, where the browser must parse chunk A to discover chunk B, is largely solved — Vite rewrites dynamic imports to preload their shared chunks in parallel and webpack’s runtime requests an async chunk’s siblings concurrently. What genuinely serialises is nested dynamic imports, a lazy chunk that itself calls import(), which no static preload graph can flatten.

4 · Emit — without it, nothing you just did can be cached or debugged. It sounds like “write the files out”, and it is not. The output filename is derived from a hash of the file’s contents, which makes the URL a unique name for exactly those bytes — and that property is the entire reason Cache-Control: max-age=31536000, immutable is safe to serve. A URL that could change meaning could never be cached for a year.

  • Hashing forces rewriting, which is why this is a stage. Once main.js becomes main.4f3a9c.js, every reference to it has to be updated — in the HTML, in CSS url() declarations, in dynamic import() calls, and in the chunk manifest the runtime uses to fetch lazy chunks. Get this wrong and you ship a build whose parts cannot find each other.
  • The manifest is how anything else finds the current build. A server rendering the HTML, or a framework injecting preload hints, needs a mapping from logical name to hashed file. It is emitted here because this is the first point at which the final names exist.
  • Source maps are the debuggability half. After stages 2 and 3 the shipped code has been transpiled, renamed, merged and stripped of formatting, so a production stack trace points at column 40,000 of a file nobody wrote. The map is not an inverse of the transformation — it is a lookup table from a position in the shipped bytes back to an original file, line, column and identifier name, and it is allowed to leave generated code unmapped. Generate them always, and name the mechanism if asked: hidden-source-map emits the map without appending the sourceMappingURL comment, so you can upload it to the error tracker for readable traces without either publishing your source or giving every user’s DevTools a 404.
  • When you can skip parts of it: content hashing buys nothing for a resource that is not cached long-term, and an app served entirely from a no-cache HTML shell in a short-lived preview environment gains nothing from it either.
Why the order is mostly forcedThe dependencies between stages are real, and saying why is a strong signal. You cannot tree-shake before resolving, because until a specifier points at a real file you do not know which exports exist. You cannot chunk before you hold a complete parsed module graph, because the import() calls that define the split points are only visible once every module has been read and parsed. And you cannot hash before optimising, because minification changes the bytes — hash first and the filename would no longer describe the file. Two honest caveats, both of which read well if you volunteer them: resolve and transform interleave per module rather than running as two completed phases, since each module’s imports are only discovered after it has been parsed; and the parsing constraint is about the parser understanding the syntax, not about emitting JavaScript first — esbuild’s parser reads TypeScript and JSX natively and chunks from that AST before printing any JS.

“Why bundle at all — browsers support ESM now?”

A real answer, not a shrug:

  • Bare specifiers still don't resolve natively without an import map, and you'd have to author one for the whole transitive dependency tree.
  • Request waterfalls. Native ESM discovers imports by parsing each module, so a deep graph serialises round trips. HTTP/2 multiplexing removes connection cost, not latency-per-depth-level.
  • Whole-graph optimisation — tree shaking, cross-module minification, and constant folding need to see the whole program.
  • Non-JS assets — CSS, images, and workers need to be discovered, hashed and rewritten.
  • Content hashing for immutable caching.
Say this“Dev and prod have different constraints. In dev I want the fastest possible edit-to-pixel loop, so unbundled native ESM wins. In prod I want the fewest bytes over the fewest round trips with cacheable, hashed chunks — so I still bundle.”
01 — The one you'll be asked about

Webpack: entry, output, loaders, plugins

// webpack.config.js — the five things that matter
module.exports = {
  mode: 'production',            // sets sane defaults: minify, tree-shake, NODE_ENV
  entry: { app: './src/index.tsx' },
  output: {
    path: __dirname + '/dist',
    filename: '[name].[contenthash].js',   // hash = safe immutable caching
    clean: true,                           // webpack 5: replaces CleanWebpackPlugin
  },
  module: { rules: [
    { test: /\.tsx?$/, use: 'swc-loader', exclude: /node_modules/ },
    { test: /\.css$/,  use: ['style-loader', 'css-loader'] },
    { test: /\.svg$/,  type: 'asset/resource' },  // webpack 5 asset modules
  ]},
  plugins: [ new HtmlWebpackPlugin({ template: './index.html' }) ],
  resolve: { extensions: ['.tsx','.ts','.js'] },
};

Loaders vs plugins — the classic question

  • A loader transforms one file at a time. It's a function: source string in, JavaScript (or an asset) out. It has no view of the graph. babel-loader, css-loader, sass-loader.
  • A plugin taps the compiler lifecycle. Built on tapable, it hooks events like compilation, emit, and done, and can see and mutate the whole build — every module, chunk, and asset. HtmlWebpackPlugin, MiniCssExtractPlugin, DefinePlugin.
  • Rule of thumb: per-file translation → loader; anything cross-cutting or emit-time → plugin.
Gotcha they loveLoaders in a use array run right-to-left / bottom-to-top. ['style-loader','css-loader','sass-loader'] means sass-loader runs first (Sass→CSS), then css-loader (CSS→JS module), then style-loader (inject a <style> at runtime). Read them as function composition: style(css(sass(source))).

02 — Removing what you never used

Tree shaking is a contract, not a switch

Tree shaking is dead-export elimination via static analysis. It only works if the bundler can prove, without running your code, that an export is unused and that dropping the module is safe. Four things have to line up:

  1. ESM syntax. import/export are static — bindings are known at parse time. require() is a runtime function call that can take a computed string, so CommonJS is essentially unshakeable. (webpack 5 analyses some simple CJS export patterns, but nothing you'd rely on.)
  2. Don't let Babel/TS downlevel modules to CJS. @babel/preset-env defaults to modules:'auto' and leaves ESM alone under babel-loader — pin { modules: false } if Babel runs standalone; TypeScript needs "module": "ESNext". Otherwise you hand the bundler CJS and silently lose shaking.
  3. Declare side effects. "sideEffects": false in package.json tells the bundler “if nobody imports a binding from this module, you may delete the module entirely.” If some files do have side effects (CSS imports, polyfills, global registration), list them: "sideEffects": ["*.css", "./src/polyfills.js"].
  4. Production mode. Webpack's usedExports only marks exports as unused; the minifier (Terser/SWC) does the actual deletion.
// Why "sideEffects" matters
// analytics.js
window.__analytics = init();          // side effect at module scope
export const track = () => {};

// app.js
import './analytics';                 // imports nothing — but MUST still run

// With "sideEffects": false, the bundler is allowed to delete this import
// entirely and your analytics silently stop working in prod only.
Barrel filesindex.ts files that export * from everything are the most common real-world cause of “tree shaking doesn't work.” One import pulls the whole barrel into the graph; the bundler must parse every re-exported module before it can prove anything is unused. It bloats bundles and build time. Import from the concrete path, or ship "sideEffects": false plus deep entry points via the exports map.

Things that defeat it

  • import _ from 'lodash' — CJS, no shaking. Use lodash-es, or import debounce from 'lodash/debounce'.
  • Class properties / decorators that the minifier can't prove pure. Libraries mark helpers with a /*#__PURE__*/ annotation so Terser knows the call is droppable.
  • Dynamic access: icons[name] forces the whole icon module set to be kept.
  • Re-assigning imported namespaces, or anything that touches the module object at runtime.
03 — Fewer bytes, better hit rate

Code splitting & long-term caching

Before any of the mechanics, the framing that makes this a senior answer: code splitting trades one round trip for fewer bytes, so it only wins when the bytes saved are worth the latency added. Splitting a 300 KB route out of the initial bundle is an obvious win — nobody visiting the home page pays for the settings screen. Splitting a 4 KB component adds a request, a runtime lookup and a potential spinner to save nothing. The unit that pays is a route or a genuinely heavy leaf: a chart library, a rich-text editor, a PDF renderer, a date-picker locale bundle.

Three ways a chunk gets created:

  • Multiple entries — separate top-level bundles. Rare in an SPA; risks duplicating shared modules unless you dedupe.
  • Dynamic import() — the one that matters. Every import() is a split point; the bundler emits a separate chunk and a runtime loader for it. React.lazy + Suspense is a thin wrapper over this.
  • SplitChunksPlugin — automatic extraction of shared/vendor code so it isn't duplicated across chunks.
// Route-level splitting — the highest-leverage change in most apps
const OrderHistory = React.lazy(() => import(
  /* webpackChunkName: "orders" */ './routes/OrderHistory'
));

// Vite/Rollup use the same syntax; the magic-comment is webpack-specific.

What a split point actually costs at runtime

Worth knowing because it explains the spinner nobody expected. A dynamic import() compiles to a runtime call that: checks whether the chunk is already loaded, injects a <script> (or uses native module loading) if not, waits for it, then resolves the promise. So the first time a user hits that route they pay a full network round trip that could not start until the code deciding to navigate had already run — a waterfall by construction, and on mobile that's 150–300ms before the chunk even begins downloading.

The mitigation is to start the fetch before it's needed. All three of these are worth naming:

// 1. prefetch on intent — the highest-value trick, and it's four lines
<Link onMouseEnter={() => import('./routes/Orders')}   // warms the module cache
      onFocus={() => import('./routes/Orders')} />

// 2. webpack magic comments — browser-scheduled, no code needed
import(/* webpackPrefetch: true */ './routes/Orders');  // idle-time, low priority
import(/* webpackPreload: true */  './Chart');          // medium priority, IN PARALLEL with the parent — rarely right

// 3. route-level prefetch on viewport entry, for a link list

Note the distinction in that snippet, since it's a common confusion: prefetch means “fetch when the browser is idle, for a future navigation” — it starts only after the parent chunk finishes. preload means “start now, in parallel with the parent chunk, at medium priority”. That parallelism, not the priority number, is why preloading a route chunk competes with the resources the current page actually needs.

Chunking for cache hit rate

optimization: {
  runtimeChunk: 'single',   // webpack's module map lives in its own tiny file
  splitChunks: {
    chunks: 'all',          // consider sync + async imports (default is 'async')
    cacheGroups: {
      framework: { test: /[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/,
                   name: 'framework', priority: 40, enforce: true },
      vendor:    { test: /[\\/]node_modules[\\/]/, name: 'vendor', priority: 20 },
    },
  },
}

The reasoning: separate things that change at different rates. React changes a few times a year, your vendor set changes monthly, your app code changes daily. Put them in different files and a deploy only invalidates the file that actually changed. runtimeChunk:'single' matters because webpack's runtime contains the chunk→hash map — leave it inside the vendor chunk and every app deploy re-hashes vendor too.

Serving sideHashed assets should be served Cache-Control: public, max-age=31536000, immutable. The HTML that references them must be no-cache — it's the only mutable pointer into the immutable graph.
Over-splitting is realHundreds of tiny chunks means hundreds of requests, worse compression (gzip/brotli dictionaries don't span files), and more runtime overhead. splitChunks defaults exist for this reason — chunks below minSize (20 KB by default in webpack 5) aren't split out, and maxInitialRequests/maxAsyncRequests cap the fan-out. Prefetch/preload hints (/* webpackPrefetch: true */) recover latency for chunks you know are coming.

Why splitting by change rate beats splitting by size

The instinct is to split until each file is small. The better objective is maximising cache hit rate across deploys, and those are different goals. Work an example: a 600 KB bundle, of which 400 KB is dependencies that change monthly and 200 KB is app code that changes daily.

// one bundle: every deploy invalidates everything
main.a91f.js  600KB   →  daily deploy = 600KB re-downloaded by every returning user

// split by change rate: a deploy invalidates only what changed
framework.7c2a.js  130KB  // react, react-dom — changes ~3× a year
vendor.4b81.js     270KB  // everything else in node_modules — monthly
main.d03e.js       200KB  // your code — daily
runtime.9f10.js      2KB  // the chunk→hash map, isolated on purpose
// daily deploy now costs a returning user 202KB, not 600KB

The runtimeChunk detail is the one people miss and it's worth being able to explain: webpack's runtime holds the map from chunk id to hashed filename, so any change to any chunk changes the runtime's contents. Leave it inside the vendor chunk and vendor re-hashes on every single deploy — you did all the splitting work and got none of the benefit.

The counter-pressures, so the answer isn't one-sided: compression works better on one big file, because gzip and Brotli build a dictionary that can't span files — twenty small chunks compress measurably worse than their concatenation. And each chunk carries per-request overhead plus a runtime lookup. That's why the objective is a handful of chunks grouped by change rate, not the maximum number of files.

04 — The loop you live in

HMR, dev servers, and source maps

Why this matters enough to be a section: the dev loop is the productivity number nobody measures. A 3-second rebuild on every keystroke-save doesn't sound like much until you multiply it by a few hundred saves a day and add the cost of losing your place. That is the entire commercial argument for Vite and for the Rust-based tools, and it's the frame to answer “why did the ecosystem move?” with — not that webpack is bad, but that startup and rebuild time scale with the size of the graph in a way that native-ESM dev servers and Rust bundlers deliberately avoid.

HMR vs live reload

  • Live reload refreshes the page. State is lost.
  • HMR is signalled over a WebSocket; the client then fetches the update manifest and patch over HTTP and swaps the module in the running app, re-running only the accept handlers that opted in — component state, scroll position, and open modals survive. React Fast Refresh is the React-specific implementation; it preserves hook state as long as the file exports only function components and you don't change the hook order.

05 — The modern default

Vite: unbundled dev, bundled prod

Vite's whole insight is that dev and prod want opposite things, so it uses two different engines.

Dev · native ESM

No bundle. The dev server serves each module over HTTP, transforming it on request. Startup time is roughly constant in project size, and an edit invalidates exactly one module.

Dev · dep pre-bundling

node_modules deps are pre-bundled once with Rolldown. This converts CJS deps to ESM and collapses a package with 600 internal files into one request.

Prod · Rolldown

A real bundle with tree shaking, chunking and hashing. Since Vite 8 (March 2026) this is Rolldown, a Rust bundler with a Rollup-compatible API — the default now, not an opt-in.

Why HMR feels instant: because there's no bundle to rebuild, an update is “re-transform this one file, push an invalidation over the WebSocket, let the client re-import it.” Cost is proportional to the changed module and its HMR boundary, not to the app.

// vite.config.ts
export default defineConfig({
  plugins: [react()],
  build: { sourcemap: 'hidden', rolldownOptions: { output: { codeSplitting: {...} } } },
  optimizeDeps: { include: ['some-cjs-dep'] },  // force into pre-bundling
});
// Vite 8 note: build.rollupOptions is now an alias of build.rolldownOptions,
// and the object form of output.manualChunks is gone — use codeSplitting.
Env var trap worth knowingOnly variables prefixed VITE_ are exposed on import.meta.env and inlined into the client bundle. That prefix is a safety boundary — it's why you can't accidentally ship DB_PASSWORD. The flip side: anything you do prefix is public. There is no such thing as a client-side secret in any bundler; DefinePlugin/import.meta.env perform literal text substitution into shipped JS.
Dev/prod divergenceBecause dev is unbundled and prod is Rolldown-bundled, a class of bugs only appears in prod: module execution order, CJS/ESM interop edges, and anything depending on process.env. Run vite build && vite preview in CI, not just vite dev.

The senior framing“The speed difference isn't cleverness, it's language and parallelism. JS bundlers are single-threaded-ish and pay to serialise ASTs between tools; esbuild (Go) and the Rust generation (SWC, Oxc, Rspack, Turbopack, Rolldown) parallelise across cores and keep one AST in memory across parse, transform and print. That's the 10× — and it's why the whole ecosystem is migrating rather than micro-optimising. Vite 8 is the clearest example: it dropped both Rollup and esbuild for Rolldown and Oxc.”

“Would you migrate our webpack build?”

Good answer: measure first. Split the number into cold start, incremental rebuild, and CI build. Cheap wins before a rewrite: turn on cache:{type:'filesystem'}, swap babel-loader for swc-loader/esbuild-loader, narrow include/exclude so you're not transpiling node_modules, and move type-checking off the critical path (tsc --noEmit in parallel, or ForkTsCheckerWebpackPlugin). If it's still slow, Rspack is the lowest-risk migration because the config shape is the same; Vite is the bigger but cleaner jump.

07 — The micro-frontend question

Module Federation

Federation lets one build consume a module from another independently deployed build at runtime. Not an npm dependency resolved at build time — an HTTP fetch of a remote's manifest when the code is first needed.

// remote (the app that publishes)
new ModuleFederationPlugin({
  name: 'trading',
  filename: 'remoteEntry.js',
  exposes: { './OrderBook': './src/OrderBook' },
  shared: { react: { singleton: true, requiredVersion: '^18.2.0' },
            'react-dom': { singleton: true } },
});

// host (the app that consumes)
new ModuleFederationPlugin({
  name: 'shell',
  remotes: { trading: 'trading@https://cdn.example.com/trading/remoteEntry.js' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});

// then, in the host:
const OrderBook = React.lazy(() => import('trading/OrderBook'));
  • Why teams want it: independent deploy cadence. A team ships their surface without rebuilding or redeploying the shell.
  • singleton: true is not optional for React. Two React copies in one page means two hook dispatchers and two context registries — hooks throw or context silently reads undefined.
  • Costs to name in the interview: version skew between independently-deployed remotes; a remote being down or 404ing needs an error boundary and a fallback; cross-remote TypeScript types need generating and publishing; bundle duplication when shared is misconfigured; end-to-end debugging spans several repos.
Balanced take“Federation solves an organisational problem — deploy independence for separate teams — at the cost of real runtime and operational complexity. For a single team, a monorepo with route-level code splitting gets you most of the loading benefit with none of the version-skew risk. I'd reach for it when deploy coupling is the actual bottleneck.”
08 — Attribution, again

“The bundle is 3 MB. Fix it.”

  1. Look, don't guess. webpack-bundle-analyzer, rollup-plugin-visualizer for Vite, or source-map-explorer on the built assets (works for any bundler). Read gzip/brotli size, not raw — that's what users download.
  2. Find the whales. Typical offenders: moment with all locales (→ date-fns/dayjs, or native Intl), full lodash, an entire icon set, a charting or rich-text library on a route most users never open, a duplicated dependency at two versions.
  3. Check for duplicates. Two copies of the same library at different semver ranges is extremely common. npm ls react, npm dedupe, or resolutions/overrides.
  4. Check polyfill cost. An overly-broad browserslist pulls in a lot of core-js. Tightening targets to what you actually support is often a free 50–100 KB.
  5. Split by route, then lazy-load heavy leaf features behind interaction.
  6. Lock it in. A size budget in CI (size-limit, or webpack's performance.hints:'error') that fails the PR. Otherwise it regrows in a quarter.
Say this“I'd start from the analyzer output and gzip numbers rather than intuition, fix the largest attributable item, and add a CI budget so the win doesn't decay. Then I'd verify the user-facing metric actually moved — bundle size is a proxy; LCP and INP are the goal.”
09 — Drill until reflex

Scenario drills

Drill 1 — the vanished analytics
“A teammate adds "sideEffects": false to a shared package. Bundle drops 40 KB, but the theme stylesheet and analytics init stop working — in production only. Why?”

"sideEffects": false is a promise that no module in the package does anything at import time. That's false here: import './theme.css' and the analytics module both work purely by executing. With the flag set, the bundler drops those bare imports because nothing binds from them. Dev doesn't reproduce it because tree shaking only runs in production mode. Fix: "sideEffects": ["*.css", "./src/analytics.js"] — an allowlist rather than a blanket false.

Drill 2 — cache busting everything
“Every deploy invalidates the vendor chunk even when no dependency changed. Users re-download 800 KB of React weekly. What's wrong?”
The webpack runtime is inside the vendor chunk

The runtime holds the module-id → chunk-hash map, so it changes on every build; if it lives in vendor, vendor's [contenthash] changes too. Fix with optimization.runtimeChunk:'single' to extract it, and moduleIds:'deterministic' so ids don't renumber when you add a file. Also confirm you're using [contenthash] and not [hash] — [hash] is per-compilation, so it changes for every asset on every build.

Drill 3 — works in dev, breaks in prod
“A Vite app works locally but throws X is not a function after vite build. Where do you look?”

Dev serves native ESM; prod goes through Rollup. The usual causes are CJS/ESM interop (a CJS dep whose default export shape differs once bundled — fix via optimizeDeps.include or the interop options), reliance on process.env which only exists after define-substitution, or module execution order differences after chunking. Reproduce with vite build && vite preview, build with sourcemap on to get a real stack, and add that command to CI so prod-only breakage is caught on the PR rather than in release.

Drill 4 — loader order
{ test: /\.scss$/, use: ['sass-loader', 'css-loader', 'style-loader'] }
Backwards — the array runs right-to-left

As written, style-loader runs first and receives raw Sass, which it can't handle. The correct order is ['style-loader','css-loader','sass-loader']: sass compiles to CSS, css-loader resolves @import/url() and turns it into a JS module, style-loader injects it. In production you'd swap style-loader for MiniCssExtractPlugin.loader to emit a real .css file instead of injecting at runtime — otherwise CSS arrives only after JS executes, which hurts FOUC and LCP.

Drill 5 — 8-minute builds
“Our webpack build takes 8 minutes in CI and 40 seconds to rebuild locally. Where do you start?”

Separate the two numbers — they have different fixes. Profile first (--profile, speed-measure-webpack-plugin, or the build's own stats) to find which loaders dominate. Local rebuild: enable cache:{type:'filesystem'}, narrow loader include to src/, and pull type-checking out of the transform (SWC/esbuild strips types; run tsc --noEmit in parallel). CI: cache node_modules and the webpack cache directory between runs, and parallelise lint/typecheck/build/test as separate jobs. If transform time still dominates after that, Rspack is a config-compatible swap; only then consider a full migration.

Drill 6 — the leaked secret
“Someone put an API signing key in VITE_API_SECRET (or via DefinePlugin) and says it's safe because it's an environment variable. Respond.”

It isn't safe. Build-time env injection is literal text substitution into the JavaScript you ship — the value is in the bundle, readable with view-source. Environment variables are a build configuration mechanism, not a secrecy mechanism. Anything the browser needs is public by definition. The fix is architectural: keep the secret server-side and have the client call your backend, which signs the request. Also rotate the key, because it's in your git-tagged build artefacts and any CDN cache.

Drill 5 — the cache that never hits
“You split vendor from app code, but returning users still re-download everything on each deploy. Why?”
The webpack runtime is living inside the vendor chunk

The runtime holds the map from chunk id to hashed filename, so any change to any chunk changes its contents — and if it's bundled into vendor, vendor re-hashes on every deploy no matter what actually changed. runtimeChunk: 'single' pulls it into its own ~2KB file that's expected to change every time. I'd also check module ids are deterministic (webpack 5 defaults to that in production, but a custom config can break it) and that nothing else volatile is in vendor — a build timestamp or a env-var-derived string will do the same thing.

Drill 6 — the spinner that appeared from nowhere
“After adding code splitting, the bundle is smaller but users say navigation feels slower. Is that expected?”

Yes — you traded bytes for a round trip. A dynamic import can't start until the code that decided to navigate has run, so the chunk fetch is a waterfall by construction: 150–300ms on mobile before it even begins downloading, and that's a spinner the user didn't see before. The fix isn't to undo the split, it's to start the fetch earlier: prefetch on hover and focus over links, which is four lines and usually makes the click feel instant, or /* webpackPrefetch: true */ to let the browser fetch it at idle. I'd also check the split granularity — splitting a 4KB component adds a request to save nothing; routes and genuinely heavy leaves are the unit that pays.

Drill 7 — split it smaller?
“A teammate proposes splitting every component into its own chunk for 'maximum caching'. Do you agree?”

No — that optimises the wrong objective. The goal is cache hit rate across deploys, not file count, and the way to get it is grouping by change rate: framework, vendor, app code, runtime. Hundreds of tiny chunks make things worse on three axes: compression suffers because gzip and Brotli dictionaries can't span files, so twenty small chunks compress measurably worse than their concatenation; each chunk adds per-request overhead and a runtime lookup; and the waterfall risk multiplies. webpack's own defaults encode this — chunks under 20KB aren't split out, and maxInitialRequests caps the fan-out.
