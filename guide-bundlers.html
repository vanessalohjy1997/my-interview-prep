Frontend interview prep

A bundler is a graph compiler.

It walks your import graph, transforms each node, decides how to cut the graph into files, and emits something a browser can cache. Every config option you'll be asked about is one of those four jobs.

00 — The mental model

Four jobs, one pipeline

A bundler does four jobs: resolve, transform, optimise-and-chunk, emit. Every config option you'll be asked about belongs to one of them.

Why it matters. Interviewers rarely want you to recite config. They want to know you understand what problem each stage solves. That's what lets you debug a build you've never seen.

1 · Resolve

Turn every import specifier into a real file. Bare specifiers (react) aren't URLs — someone has to map them to node_modules, honour exports/main/browser, and add extensions.

2 · Transform

Per-module: TS→JS, JSX→createElement/jsx, Sass→CSS, modern syntax→target syntax. In webpack these are loaders; in Vite/Rollup they're plugin hooks.

3 · Optimise & chunk

Tree-shake dead exports, minify, and cut the graph into chunks so the first paint doesn't download the whole app.

4 · Emit

Write hashed assets, a manifest / HTML, and source maps. Hashing is what makes long-term HTTP caching safe.

Why each stage has to exist

Each stage exists because something specific and nameable breaks without it. The four stages are not a taxonomy someone invented for a diagram. Being able to say what breaks is the difference between reciting a pipeline and understanding one. Take them one at a time.

1 · Resolve — without it, import React from 'react' never even becomes a request.

  • In the ES module spec a specifier is a URL, resolved relative to the importing module.
  • './utils.js' is relative and works. 'react' is neither relative nor absolute, so resolution fails locally.
  • Node invented an answer: walk up the directory tree looking in node_modules. A browser has no filesystem to walk.

How it fails. No fetch is ever attempted, so there is no 404, just a module graph that cannot be linked. The module itself parses fine. The failure comes later, while the browser is fetching the graph’s dependencies, and it happens before any module evaluates, so you cannot catch it around the import. Chrome words it Failed to resolve module specifier; Firefox and Safari phrase it differently.

How it works. Somebody has to perform Node’s lookup ahead of time and rewrite the specifier to something fetchable. That is the resolve stage.

More than a path join. Resolution also picks an entry point from the package’s exports map. It honours the conditions Node implements itself, like import versus require and node, plus the community ones bundlers set on their own behalf: browser, and development versus production. It falls back to main, plus the non-standard module and browser fields that bundlers rather than Node honour. It adds the extension you left off, which CommonJS and bundler resolvers do but Node’s own ESM resolution pointedly does not. And it follows the symlinks that pnpm’s layout is built from.

Why it must be automated. Scale. A mainstream React app resolves thousands of modules across hundreds of installed packages. Every one of those edges is a decision of exactly this kind.

The hazards in Node’s own answer. Conditions in exports are matched in object key order, first match wins. So types must be listed first and default last. A default key (or, in Node, a node key) placed above import silently hands ESM consumers the CJS file. import and require never both match, so their order against each other does not matter. Mapping import and require to two different files is the dual-package hazard: one dependency graph can load both copies, and a class from one fails instanceof against the other. Node loosened the pressure that created it: require(esm) works unflagged since Node 22.12 / 20.19 for modules without top-level await. So the current advice for new libraries is to ship ESM only and let CJS consumers require() it.

When you can skip it. An import map lets the browser resolve bare specifiers natively, which is genuinely a way to run unbundled dependencies. It is Baseline Widely Available, in every engine since March 2023 (Safari 16.4). The cost is that the map must cover every bare specifier your dependencies use, not just your own. In practice that means generating it from a CDN or a tool rather than hand-writing it. You have not removed the resolution work; you have moved it into a file you are now responsible for keeping correct.

2 · Transform — without it, the browser cannot even parse your source.

  • const x: number = 1 and <div /> are syntax errors in JavaScript.
  • A .vue or .svelte file is not JavaScript at all, and a .scss file is not CSS.
  • Something has to turn each module into the language the platform actually implements.

Why it is a parse failure. This is a parse-time failure, not a runtime one, which is the part worth stressing. The module never begins executing, so there is nothing to try/catch.

Two different jobs wear the same name. Compiling a non-JS syntax (TypeScript, JSX, Sass) is unavoidable if you use it. Downlevelling modern JavaScript for older engines is a choice you make with a browserslist target. It is the expensive half: targeting ES5 rewrites async/await into a state machine and pulls in helper runtimes. That inflates output for browsers you may no longer support.

Per-module, so parallelisable. Each file is transformed in isolation with no knowledge of the others, so the work spreads across cores freely. Be careful with the causal story, though. Babel is per-file too, so isolation is not what makes esbuild and SWC fast. Their speed comes from being compiled to native code (Go and Rust against Babel’s JavaScript), from using real threads rather than worker processes, and from purpose-built parsers instead of layers over a shared AST. SWC’s own benchmark puts it around 20× Babel on one thread and 70× on four.

Where isolation does matter. Type checking needs the whole program. So these tools strip types rather than verify them, and tsc --noEmit stays a separate job.

The tsconfig it forces. Set "isolatedModules": true (Vite’s docs make it mandatory). TypeScript then refuses the three things a single-file transpiler cannot get right: re-exporting a name that is only a type (export { SomeType } must become export type), referencing an ambient const enum (the transpiler cannot inline a value it cannot see), and namespaces in script files. verbatimModuleSyntax is the stricter modern form.

When you can skip it. Author plain modern JavaScript and target evergreen browsers, and you need no transform stage at all. That is the honest version of the “no build step” setup. It is available; it just costs you TypeScript and JSX.

3 · Optimise & chunk — without it, the first paint downloads the entire application.

This stage is where a bundler earns its keep. It is really three jobs with three separate justifications.

Tree shaking needs a view of the whole graph. Deciding that an export is unused is a claim about every module in the program at once, which no per-file tool can make. It works only because ESM import/export statements are static. The names are known without running anything, so the bundler can build a reachability graph and drop what nothing points at.

Why CommonJS mostly defeats it. It is worth naming the right reason. It is not that require() takes an expression: that is a literal string almost everywhere, which is how CJS gets bundled at all. It is that module.exports is an ordinary mutable object, so exports[someExpression] = fn is legal and the export set is only fully knowable at runtime. Bundlers do recognise the common static patterns, and webpack 5 has grown steadily better at it, but they bail out the moment the code strays. That asymmetry in reliability, not a hard impossibility, is why a library’s ESM build shakes and its CJS build cannot be counted on to.

Minification is cheap bytes that compression cannot recover. Renaming locals to single letters, folding constants, and eliminating branches made dead by substituting process.env.NODE_ENV all remove information gzip would otherwise have to encode. It composes with compression rather than competing with it, because gzip is semantics-blind and cannot delete a dead branch at any ratio. Minify-then-compress typically lands 30–60% below compressing the unminified source.

Chunking exists for two independent reasons, and people usually name only one. The obvious one is latency: a route the user has not visited should not be on the critical path. The one that separates a strong answer is caching. In a single bundle, a one-line change to your own code invalidates the megabyte of vendor dependencies sitting next to it, so every deploy makes every returning user re-download React. Splitting stable dependencies from volatile application code is what makes long-lived caches actually pay.

Where it backfires. Splitting is not free. Each chunk is a separate request with its own headers, and each file is compressed as its own stream. gzip’s 32 KB back-reference window resets at every file boundary, so several small files compress worse than one merged file. That penalty is smaller under brotli, whose built-in ~120 KB dictionary of common web tokens exists precisely to rescue small files. For a rule of thumb, webpack’s splitChunks will not create a chunk below 20 KB of unminified source by default in a production build (10 KB in development), which is a reasonable proxy for “too small to deserve its own request”.

The waterfall risk is narrower than usually stated. The naive case, where the browser must parse chunk A to discover chunk B, is largely solved. Vite rewrites dynamic imports to preload their shared chunks in parallel, and webpack’s runtime requests an async chunk’s siblings concurrently. What genuinely serialises is nested dynamic imports: a lazy chunk that itself calls import(), which no static preload graph can flatten.

4 · Emit — without it, nothing you just did can be cached or debugged.

  • It sounds like “write the files out”, and it is not.
  • The output filename is derived from a hash of the file’s contents, which makes the URL a unique name for exactly those bytes.
  • That property is the entire reason Cache-Control: max-age=31536000, immutable is safe to serve. A URL that could change meaning could never be cached for a year.

Hashing forces rewriting, which is why this is a stage. Once main.js becomes main.4f3a9c.js, every reference to it has to be updated. That means the HTML, CSS url() declarations, dynamic import() calls, and the chunk manifest the runtime uses to fetch lazy chunks. Get this wrong and you ship a build whose parts cannot find each other.

The manifest is how anything else finds the current build. A server rendering the HTML, or a framework injecting preload hints, needs a mapping from logical name to hashed file. It is emitted here because this is the first point at which the final names exist.

Source maps are the debuggability half. After stages 2 and 3 the shipped code has been transpiled, renamed, merged and stripped of formatting. A production stack trace therefore points at column 40,000 of a file nobody wrote. The map is not an inverse of the transformation. It is a lookup table from a position in the shipped bytes back to an original file, line, column and identifier name, and it is allowed to leave generated code unmapped.

The mechanism to name. Generate them always. If asked how: hidden-source-map emits the map without appending the sourceMappingURL comment. So you can upload it to the error tracker for readable traces without either publishing your source or giving every user’s DevTools a 404.

When you can skip parts of it. Content hashing buys nothing for a resource that is not cached long-term. An app served entirely from a no-cache HTML shell in a short-lived preview environment gains nothing from it either.

Why the order is mostly forcedThe dependencies between stages are real, and saying why is a strong signal. You cannot tree-shake before resolving: until a specifier points at a real file you do not know which exports exist. You cannot chunk before you hold a complete parsed module graph: the import() calls that define the split points are only visible once every module has been read and parsed. And you cannot hash before optimising: minification changes the bytes, so hash first and the filename would no longer describe the file. Two honest caveats read well if you volunteer them. Resolve and transform interleave per module rather than running as two completed phases, since each module’s imports are only discovered after it has been parsed. And the parsing constraint is about the parser understanding the syntax, not about emitting JavaScript first: esbuild’s parser reads TypeScript and JSX natively and chunks from that AST before printing any JS.

“Why bundle at all — browsers support ESM now?”

Because native ESM gives you module loading, but not bare-specifier resolution, flat waterfalls, whole-graph optimisation, asset handling or content hashing. A real answer, not a shrug:

  • Bare specifiers still don't resolve natively without an import map. You'd have to author one for the whole transitive dependency tree.
  • Request waterfalls. Native ESM discovers imports by parsing each module, so a deep graph serialises round trips. HTTP/2 multiplexing removes connection cost, not latency-per-depth-level.
  • Whole-graph optimisation. Tree shaking, cross-module minification, and constant folding need to see the whole program.
  • Non-JS assets. CSS, images, and workers need to be discovered, hashed and rewritten.
  • Content hashing for immutable caching.

The partial fix without a bundler. <link rel="modulepreload"> for the modules you already know are needed. That is exactly what a bundled Vite build emits for every chunk the entry imports statically, indirect imports included, and why it can only cover what is statically known.

Say this“Dev and prod have different constraints. In dev I want the fastest possible edit-to-pixel loop, so unbundled native ESM wins. In prod I want the fewest bytes over the fewest round trips with cacheable, hashed chunks — so I still bundle.”
01 — The one you'll be asked about

Webpack: entry, output, loaders, plugins

A webpack config is five decisions: mode, entry, output, loaders (module rules) and plugins. Everything else is detail.

// webpack.config.js — the five things that matter
module.exports = {
  mode: 'production',            // sets sane defaults: minify, tree-shake, NODE_ENV
  entry: { app: './src/index.tsx' },
  output: {
    path: __dirname + '/dist',
    filename: '[name].[contenthash].js',   // hash = safe immutable caching
    clean: true,                           // webpack 5: replaces CleanWebpackPlugin
  },
  module: { rules: [
    { test: /\.tsx?$/, use: 'swc-loader', exclude: /node_modules/ },
    { test: /\.css$/,  use: ['style-loader', 'css-loader'] },
    { test: /\.svg$/,  type: 'asset/resource' },  // webpack 5 asset modules
  ]},
  plugins: [ new HtmlWebpackPlugin({ template: './index.html' }) ],
  resolve: { extensions: ['.tsx','.ts','.js'] },
};

Loaders vs plugins — the classic question

A loader transforms one file; a plugin taps the whole compilation.

  • A loader transforms one file at a time. It's a function: source string in, JavaScript (or an asset) out. It has no view of the graph. babel-loader, css-loader, sass-loader.
  • A plugin taps the compiler lifecycle. Built on tapable, it hooks events like compilation, emit, and done. It can see and mutate the whole build: every module, chunk, and asset. HtmlWebpackPlugin, MiniCssExtractPlugin, DefinePlugin.

Say this. Per-file translation → loader; anything cross-cutting or emit-time → plugin.

Gotcha they loveLoaders in a use array run right-to-left / bottom-to-top. ['style-loader','css-loader','sass-loader'] means sass-loader runs first (Sass→CSS), then css-loader (CSS→JS module), then style-loader (inject a <style> at runtime). Read them as function composition: style(css(sass(source))).

What webpack 5 changed

Six changes matter in an interview: persistent cache, asset modules, no automatic Node polyfills, Module Federation, deterministic ids and real content hashes.

02 — Removing what you never used

Tree shaking is a contract, not a switch

Tree shaking is dead-export elimination via static analysis, and it only works when four conditions all hold.

How it works. The bundler must prove, without running your code, that an export is unused and that dropping the module is safe. Four things have to line up:

  1. ESM syntax. import/export are static, so bindings are known at parse time. CommonJS resists shaking for a different reason than people usually give. It is not that require() takes an expression (it is a literal string almost everywhere). It is that module.exports is an ordinary mutable object, so the export set is only fully knowable at runtime. webpack 5 does shake the common static CJS patterns (exports.x = …, module.exports = { … }) and bails to “keep everything” the moment the code strays. So a CJS build can shake; it just cannot be relied on to.
  2. Don't let Babel/TS downlevel modules to CJS. @babel/preset-env defaults to modules:'auto' and leaves ESM alone under babel-loader. Pin { modules: false } if Babel runs standalone; TypeScript needs "module": "ESNext". Otherwise you hand the bundler CJS and silently lose shaking.
  3. Declare side effects. "sideEffects": false in package.json tells the bundler “if nobody imports a binding from this module, you may delete the module entirely.” If some files do have side effects (CSS imports, polyfills, global registration), list them: "sideEffects": ["*.css", "./src/polyfills.js"].
  4. Production mode. Webpack's usedExports only marks exports as unused. The minifier (Terser/SWC) does the actual deletion.
// Why "sideEffects" matters
// analytics.js
window.__analytics = init();          // side effect at module scope
export const track = () => {};

// app.js
import './analytics';                 // imports nothing — but MUST still run

// With "sideEffects": false, the bundler is allowed to delete this import
// entirely and your analytics silently stop working. Vite's unbundled dev
// server still runs it, so there it breaks in prod only; webpack honours
// the flag in development mode too.
Barrel filesindex.ts files that export * from everything are the most common real-world cause of “tree shaking doesn't work.” One import pulls the whole barrel into the graph. The bundler must parse every re-exported module before it can prove anything is unused. It bloats bundles and build time. Import from the concrete path, or ship "sideEffects": false plus deep entry points via the exports map.

Things that defeat it

Anything that hides the export set from static analysis defeats shaking.

  • import _ from 'lodash': CJS, no shaking. Use lodash-es, or import debounce from 'lodash/debounce'.
  • Class properties / decorators that the minifier can't prove pure. Libraries mark helpers with a /*#__PURE__*/ annotation so Terser knows the call is droppable.
  • Dynamic access: icons[name] forces the whole icon module set to be kept.
  • Re-assigning imported namespaces, or anything that touches the module object at runtime.
03 — Fewer bytes, better hit rate

Code splitting & long-term caching

Code splitting trades one round trip for fewer bytes, so it only wins when the bytes saved are worth the latency added. That framing is what makes this a senior answer.

  • Splitting a 300 KB route out of the initial bundle is an obvious win. Nobody visiting the home page pays for the settings screen.
  • Splitting a 4 KB component adds a request, a runtime lookup and a potential spinner to save nothing.
  • The unit that pays is a route or a genuinely heavy leaf: a chart library, a rich-text editor, a PDF renderer, a date-picker locale bundle.

Top-level await. One syntax detail interviewers now probe. It turns the module, and every module that imports it, into an async module. webpack has supported it by default since 5.83, marked it stable in 5.102, and has since dropped the experiments.topLevelAwait flag from its schema. It costs nothing at the chunking level. But it does change runtime shape: importers wait on the awaited promise before they evaluate, and a CJS consumer cannot require() such a module at all (Node throws ERR_REQUIRE_ASYNC_MODULE). Use it for genuinely one-off setup, not as a convenience in a leaf.

How a chunk gets created. Three ways:

  • Multiple entries. Separate top-level bundles. Rare in an SPA; risks duplicating shared modules unless you dedupe.
  • Dynamic import(). The one that matters. Every import() is a split point; the bundler emits a separate chunk and a runtime loader for it. React.lazy + Suspense is a thin wrapper over this.
  • SplitChunksPlugin. Automatic extraction of shared/vendor code so it isn't duplicated across chunks.
// Route-level splitting — the highest-leverage change in most apps
const OrderHistory = React.lazy(() => import(
  /* webpackChunkName: "orders" */ './routes/OrderHistory'
));

// Vite/Rollup use the same syntax; the magic-comment is webpack-specific.

What a split point actually costs at runtime

A split point costs a full network round trip that could not start until the code deciding to navigate had already run.

How it works. A dynamic import() compiles to a runtime call. It checks whether the chunk is already loaded, injects a <script> (or uses native module loading) if not, waits for it, then resolves the promise. So the first time a user hits that route they pay that round trip. It is a waterfall by construction, and on mobile that's 150–300ms before the chunk even begins downloading. That is the spinner nobody expected.

The fix. Start the fetch before it's needed. All three of these are worth naming:

// 1. prefetch on intent — the highest-value trick, and it's four lines
<Link onMouseEnter={() => import('./routes/Orders')}   // warms the module cache
      onFocus={() => import('./routes/Orders')} />

// 2. webpack magic comments — browser-scheduled, no code needed
import(/* webpackPrefetch: true */ './routes/Orders');  // idle-time, low priority
import(/* webpackPreload: true */  './Chart');          // medium priority, IN PARALLEL with the parent — rarely right

// 3. route-level prefetch on viewport entry, for a link list

prefetch vs preload. Note the distinction in that snippet, since it's a common confusion. prefetch means “fetch when the browser is idle, for a future navigation”. It starts only after the parent chunk finishes. preload means “start now, in parallel with the parent chunk, at medium priority”. That parallelism, not the priority number, is why preloading a route chunk competes with the resources the current page actually needs.

Chunking for cache hit rate

optimization: {
  runtimeChunk: 'single',   // webpack's module map lives in its own tiny file
  splitChunks: {
    chunks: 'all',          // consider sync + async imports (default is 'async')
    cacheGroups: {
      framework: { test: /[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/,
                   name: 'framework', priority: 40, enforce: true },
      vendor:    { test: /[\\/]node_modules[\\/]/, name: 'vendor', priority: 20 },
    },
  },
}

Separate things that change at different rates, and a deploy only invalidates the file that actually changed.

How it works. React changes a few times a year, your vendor set changes monthly, your app code changes daily. Put them in different files. runtimeChunk:'single' matters because webpack's runtime contains the chunk→hash map for lazy-loaded chunks, so whichever chunk holds it re-hashes whenever one of those changes. With splitChunks alone that is your entry chunk. If vendor is an entry the app dependOns, the runtime lands in vendor, and every deploy that touches a lazy route re-hashes vendor too.

Serving sideHashed assets should be served Cache-Control: public, max-age=31536000, immutable. The HTML that references them must be no-cache — it's the only mutable pointer into the immutable graph.
Over-splitting is realHundreds of tiny chunks means hundreds of requests, worse compression (each file is compressed on its own, so no back-reference reaches across files), and more runtime overhead. splitChunks defaults exist for this reason. Chunks below minSize (20 KB by default in a webpack 5 production build, 10 KB in development) aren't split out, and in production maxInitialRequests/maxAsyncRequests (30 each) cap the fan-out. Prefetch/preload hints (/* webpackPrefetch: true */) recover latency for chunks you know are coming.

Why splitting by change rate beats splitting by size

The objective is maximising cache hit rate across deploys, not making each file small. Those are different goals.

Example. The instinct is to split until each file is small. Work a counter-example instead: a 600 KB bundle, of which 400 KB is dependencies that change monthly and 200 KB is app code that changes daily.

// one bundle: every deploy invalidates everything
main.a91f.js  600KB   →  daily deploy = 600KB re-downloaded by every returning user

// split by change rate: a deploy invalidates only what changed
framework.7c2a.js  130KB  // react, react-dom — changes ~3× a year
vendor.4b81.js     270KB  // everything else in node_modules — monthly
main.d03e.js       200KB  // your code — daily
runtime.9f10.js      2KB  // the chunk→hash map, isolated on purpose
// daily deploy now costs a returning user 202KB, not 600KB

The runtimeChunk detail. This is the one people miss, and it's worth being able to explain. webpack's runtime holds the map from chunk id to hashed filename for every lazy-loaded chunk, so any change to any of them changes the runtime's contents. Leave it inside the vendor chunk (where it lands when vendor is an entry the app dependOns; with splitChunks alone it sits in the entry chunk) and vendor re-hashes on every deploy that touches a lazy route. You did all the splitting work and got none of the benefit.

The counter-pressures. So the answer isn't one-sided: compression works better on one big file, because each file is compressed as its own stream, so gzip's and Brotli's back-references can't reach across files. Twenty small chunks compress measurably worse than their concatenation. And each chunk carries per-request overhead plus a runtime lookup. That's why the objective is a handful of chunks grouped by change rate, not the maximum number of files.

04 — The loop you live in

HMR, dev servers, and source maps

The dev loop is the productivity number nobody measures, and it is the core commercial argument for Vite and, with production build time, for the Rust-based tools.

Numbers. A 3-second rebuild on every keystroke-save doesn't sound like much. Multiply it by a few hundred saves a day and add the cost of losing your place.

The frame. This is how to answer “why did the ecosystem move?”. Not that webpack is bad, but that startup and rebuild time scale with the size of the graph in a way that native-ESM dev servers and Rust bundlers deliberately avoid.

HMR vs live reload

Live reload refreshes the page; HMR swaps one module inside the running app and keeps state.

  • Live reload refreshes the page. State is lost.
  • HMR is signalled over a WebSocket. The client then fetches the new code over HTTP (webpack: an update manifest plus a patch; Vite: the changed module itself, re-imported) and swaps it into the running app, re-running only the accept handlers that opted in. Component state, scroll position, and open modals survive.
  • React Fast Refresh is the React-specific implementation. It preserves hook state as long as the file exports only function components and you don't change the hook order.

How it works. The boundary is the mechanism. An update propagates up the import graph until it reaches a module that called import.meta.hot.accept() (webpack: module.hot.accept()). That module is the HMR boundary: it re-imports the changed module and runs its callback, and nothing above it re-executes. If the walk reaches the root without finding an accepting module, the client falls back to a full page reload. Fast Refresh works by making every component-only module self-accepting for you.

Where it bites. That fallback is why editing a plain utility file with no component export often reloads the page, while editing a component does not.

What Fast Refresh does and does not keep. useState and useRef values survive as long as their arguments and call order don’t change. Effects, useMemo and useCallback always re-run on a refresh; dependency arrays are ignored. So an effect that is not idempotent misbehaves under HMR before it does in prod. Class components always remount, and a file that also exports non-components (a hook, a constant) remounts its components on every edit. Vite’s React plugin spares a primitive constant whose value did not change. // @refresh reset forces a remount when you want one.

05 — The modern default

Vite: unbundled dev, bundled prod

Vite's whole insight is that dev and prod want opposite things, so it uses two different engines.

Dev · native ESM

No bundle. The dev server serves each module over HTTP, transforming it on request. Startup time is roughly constant in project size, and an edit invalidates exactly one module.

Dev · dep pre-bundling

node_modules deps are pre-bundled once with Rolldown. This converts CJS deps to ESM and collapses a package with 600 internal files into one request.

Prod · Rolldown

A real bundle with tree shaking, chunking and hashing. Since Vite 8 (March 2026) this is Rolldown, a Rust bundler with a Rollup-compatible API — the default now, not an opt-in.

Why HMR feels instant. There's no bundle to rebuild. An update is “re-transform this one file, push an invalidation over the WebSocket, let the client re-import it.” Cost is proportional to the changed module and its HMR boundary, not to the app.

// vite.config.ts
export default defineConfig({
  plugins: [react()],
  build: { sourcemap: 'hidden', rolldownOptions: { output: { codeSplitting: {...} } } },
  optimizeDeps: { include: ['some-cjs-dep'] },  // force into pre-bundling
});

Where the split is headingThe “unbundled dev” half is no longer sacred. Vite 8.1 (June 2026) shipped an experimental bundled dev mode (announced as full bundle mode) in which Rolldown bundles during development too, because on very large graphs thousands of native-ESM requests become the bottleneck. The Vite team measured about 15× faster startup on a 10,000-component test app; Linear reported up to 3× faster cold starts and 10× fewer network requests. It is still opt-in (experimental.bundledDev) as of Vite 8.3 (September 2026). But if asked “what’s next for Vite” this is the honest answer: one Rust bundler, fast enough to use for both halves.
Env var trap worth knowingOnly variables prefixed VITE_ are exposed on import.meta.env and inlined into the client bundle. That prefix is a safety boundary; it's why you can't accidentally ship DB_PASSWORD. The flip side: anything you do prefix is public. There is no such thing as a client-side secret in any bundler. DefinePlugin/import.meta.env perform literal text substitution into shipped JS.
Dev/prod divergenceBecause dev is unbundled and prod is Rolldown-bundled, a class of bugs only appears in prod: module execution order, CJS/ESM interop edges (fewer since Vite 8 made the CJS default-import rule the same in dev and build), and anything depending on process.env. Run vite build && vite preview in CI, not just vite dev.
06 — Know the trade-offs, not just the names

The 2026 landscape

Pick by job: Vite for a new app, Rollup for a library, Rspack to speed up a big webpack codebase, Turbopack if you are on Next.js.

The senior framing“The speed difference isn't cleverness, it's language and parallelism. JS bundlers are single-threaded-ish and pay to serialise ASTs between tools; esbuild (Go) and the Rust generation (SWC, Oxc, Rspack, Turbopack, Rolldown) parallelise across cores and keep one AST in memory across parse, transform and print. That's the 10× — and it's why the whole ecosystem is migrating rather than micro-optimising. Vite 8 is the clearest example: it dropped both Rollup and esbuild for Rolldown and Oxc.”
Minifiers: the actual trade-offTerser is the JS reference for output size; the native minifiers trade a sliver of size for an order of magnitude of time. Vite’s own docs put it in numbers. esbuild’s minifier was 20–40× faster than Terser at 1–2% larger output. The Oxc minifier that is now Vite 8’s default is 30–90× faster than Terser at 0.5–2% worse compression. SWC’s minifier sits in the same band. So “switch to Terser” is only ever worth it for a library where every byte is contractual, never for an app build where the CI minute costs more than the kilobyte.

“Would you migrate our webpack build?”

Measure first, take the cheap wins, and only then choose between Rspack and Vite.

How it works. Split the number into cold start, incremental rebuild, and CI build. Cheap wins before a rewrite: turn on cache:{type:'filesystem'}, swap babel-loader for swc-loader/esbuild-loader, and narrow include/exclude so you're not transpiling node_modules. Move type-checking off the critical path (tsc --noEmit in parallel, or ForkTsCheckerWebpackPlugin).

If it's still slow. Rspack is the lowest-risk migration because the config shape is the same. Vite is the bigger but cleaner jump.

07 — The micro-frontend question

Module Federation

Federation lets one build consume a module from another independently deployed build at runtime. Not an npm dependency resolved at build time. An HTTP fetch of a remote's manifest when the code is first needed.

// remote (the app that publishes)
new ModuleFederationPlugin({
  name: 'trading',
  filename: 'remoteEntry.js',
  exposes: { './OrderBook': './src/OrderBook' },
  shared: { react: { singleton: true, requiredVersion: '^18.2.0' },
            'react-dom': { singleton: true } },
});

// host (the app that consumes)
new ModuleFederationPlugin({
  name: 'shell',
  remotes: { trading: 'trading@https://cdn.example.com/trading/remoteEntry.js' },
  shared: { react: { singleton: true }, 'react-dom': { singleton: true } },
});

// then, in the host:
const OrderBook = React.lazy(() => import('trading/OrderBook'));
  • Why teams want it: independent deploy cadence. A team ships their surface without rebuilding or redeploying the shell.
  • singleton: true is not optional for React. Two React copies in one page means two hook dispatchers, and a component rendered by one React but calling the other's hooks finds no active dispatcher.

Where it bites. With two Reacts, every hook in the remote fails, useContext included: dev logs Invalid hook call and the call throws. The silent failure is a duplicated context package. Provider and consumer then hold two different context objects, so useContext in the remote quietly gets the default value.

What it costs. Name these in the interview: version skew between independently-deployed remotes; a remote being down or 404ing needs an error boundary and a fallback; cross-remote TypeScript types need generating and publishing; bundle duplication when shared is misconfigured; end-to-end debugging spans several repos.

Balanced take“Federation solves an organisational problem — deploy independence for separate teams — at the cost of real runtime and operational complexity. For a single team, a monorepo with route-level code splitting gets you most of the loading benefit with none of the version-skew risk. I'd reach for it when deploy coupling is the actual bottleneck.”
08 — Attribution, again

“The bundle is 3 MB. Fix it.”

Measure, fix the largest attributable item, then lock the win in with a CI budget.

  1. Look, don't guess. webpack-bundle-analyzer, rollup-plugin-visualizer for Vite, or source-map-explorer on the built assets (works for any bundler). Read gzip/brotli size, not raw. That's what users download.
  2. Find the whales. Typical offenders: moment with all locales (→ date-fns/dayjs, or native Intl), full lodash, an entire icon set, a charting or rich-text library on a route most users never open, a duplicated dependency at two versions.
  3. Check for duplicates. Two copies of the same library at different semver ranges is extremely common. npm ls react, npm dedupe, or resolutions/overrides.
  4. Check polyfill cost. An overly-broad browserslist pulls in a lot of core-js. Tightening targets to what you actually support is often a free 50–100 KB. The modern spelling is a Baseline query: browserslist 4.26 (September 2025) accepts baseline widely available, and Vite’s default build.target is 'baseline-widely-available'. In Vite 8 that resolves to Chrome/Edge 111, Firefox 114, Safari 16.4 — so if your config still says > 0.5%, last 2 versions, not dead you may be transpiling for browsers with no users.
  5. Split by route, then lazy-load heavy leaf features behind interaction.
  6. Lock it in. A size budget in CI (size-limit, or webpack's performance.hints:'error') that fails the PR. Otherwise it regrows in a quarter.
Say this“I'd start from the analyzer output and gzip numbers rather than intuition, fix the largest attributable item, and add a CI budget so the win doesn't decay. Then I'd verify the user-facing metric actually moved — bundle size is a proxy; LCP and INP are the goal.”
09 — Drill until reflex

Scenario drills

Drill 1 — the vanished analytics
“A teammate adds "sideEffects": false to a shared package. Bundle drops 40 KB, but the theme stylesheet and analytics init stop working — in production only. Why?”

"sideEffects": false is a promise that no module in the package does anything at import time. That's false here: import './theme.css' and the analytics module both work purely by executing. With the flag set, the bundler drops those bare imports because nothing binds from them. It is prod-only when dev serves the package unbundled, as Vite does for a linked workspace package. webpack honours the flag in development mode too. So does Vite’s pre-bundling of an installed package, but only for JS: its CSS imports survive until the build. Fix: "sideEffects": ["*.css", "./src/analytics.js"] — an allowlist rather than a blanket false.

Drill 2 — cache busting everything
“Every deploy invalidates the vendor chunk even when no dependency changed. Users re-download 800 KB of React weekly. What's wrong?”
The webpack runtime is inside the vendor chunk

The runtime holds the chunk-id → hashed-filename map for lazy-loaded chunks, so it changes whenever one of them does; if it lives in vendor, vendor's [contenthash] changes too. It lands there when vendor is an entry the app dependOns; with splitChunks alone it sits in the entry chunk. Fix with optimization.runtimeChunk:'single' to extract it, and moduleIds:'deterministic' so ids don't renumber when you add a file. Also confirm you're using [contenthash] and not [hash] — [hash] is per-compilation, so it changes for every asset on every build.

Drill 3 — works in dev, breaks in prod
“A Vite app works locally but throws X is not a function after vite build. Where do you look?”

Dev serves native ESM; prod goes through Rolldown (Rollup before Vite 8). The usual causes are CJS/ESM interop (a CJS dep whose default export shape differs once bundled — the classic cause before Vite 8 made that rule the same in dev and build; on older Vite fix it with build.commonjsOptions, since optimizeDeps only affects dev), reliance on process.env which only exists after define-substitution, or module execution order differences after chunking. Reproduce with vite build && vite preview, build with sourcemap on to get a real stack, and add that command to CI so prod-only breakage is caught on the PR rather than in release.

Drill 4 — loader order
{ test: /\.scss$/, use: ['sass-loader', 'css-loader', 'style-loader'] }
Backwards — the array runs right-to-left

As written, style-loader runs first and receives raw Sass, which it can't handle. The correct order is ['style-loader','css-loader','sass-loader']: sass compiles to CSS, css-loader resolves @import/url() and turns it into a JS module, style-loader injects it. In production you'd swap style-loader for MiniCssExtractPlugin.loader to emit a real .css file instead of injecting at runtime — otherwise CSS arrives only after JS executes, which hurts FOUC and LCP.

Drill 5 — 8-minute builds
“Our webpack build takes 8 minutes in CI and 40 seconds to rebuild locally. Where do you start?”

Separate the two numbers — they have different fixes. Profile first (--profile, speed-measure-webpack-plugin, or the build's own stats) to find which loaders dominate. Local rebuild: enable cache:{type:'filesystem'}, narrow loader include to src/, and pull type-checking out of the transform (SWC/esbuild strips types; run tsc --noEmit in parallel). CI: cache node_modules and the webpack cache directory between runs, and parallelise lint/typecheck/build/test as separate jobs. If transform time still dominates after that, Rspack is a config-compatible swap; only then consider a full migration.

Drill 6 — the leaked secret
“Someone put an API signing key in VITE_API_SECRET (or via DefinePlugin) and says it's safe because it's an environment variable. Respond.”

It isn't safe. Build-time env injection is literal text substitution into the JavaScript you ship — the value is in the bundle, readable with view-source. Environment variables are a build configuration mechanism, not a secrecy mechanism. Anything the browser needs is public by definition. The fix is architectural: keep the secret server-side and have the client call your backend, which signs the request. Also rotate the key, because it's in your git-tagged build artefacts and any CDN cache.

Drill 7 — the cache that never hits
“You split vendor from app code, but returning users still re-download everything on each deploy. Why?”
The webpack runtime is living inside the vendor chunk

The runtime holds the map from chunk id to hashed filename for lazy-loaded chunks, so any change to any of them changes its contents — and if it's bundled into vendor, vendor re-hashes even when no dependency changed. It lands there when vendor is an entry the app dependOns; with splitChunks alone it sits in the entry chunk. runtimeChunk: 'single' pulls it into its own ~2KB file that's expected to change every time. I'd also check module ids are deterministic (webpack 5 defaults to that in production, but a custom config can break it) and that nothing else volatile is in vendor — a build timestamp or a env-var-derived string will do the same thing.

Drill 8 — the spinner that appeared from nowhere
“After adding code splitting, the bundle is smaller but users say navigation feels slower. Is that expected?”

Yes — you traded bytes for a round trip. A dynamic import can't start until the code that decided to navigate has run, so the chunk fetch is a waterfall by construction: 150–300ms on mobile before it even begins downloading, and that's a spinner the user didn't see before. The fix isn't to undo the split, it's to start the fetch earlier: prefetch on hover and focus over links, which is four lines and usually makes the click feel instant, or /* webpackPrefetch: true */ to let the browser fetch it at idle. I'd also check the split granularity — splitting a 4KB component adds a request to save nothing; routes and genuinely heavy leaves are the unit that pays.

Drill 9 — split it smaller?
“A teammate proposes splitting every component into its own chunk for 'maximum caching'. Do you agree?”

No — that optimises the wrong objective. The goal is cache hit rate across deploys, not file count, and the way to get it is grouping by change rate: framework, vendor, app code, runtime. Hundreds of tiny chunks make things worse on three axes: compression suffers because each file is compressed on its own and no back-reference reaches across files, so twenty small chunks compress measurably worse than their concatenation; each chunk adds per-request overhead and a runtime lookup; and the waterfall risk multiplies. webpack's own production defaults encode this — chunks under 20KB aren't split out, and maxInitialRequests caps the fan-out.
