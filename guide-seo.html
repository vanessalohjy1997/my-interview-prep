Frontend interview prep

Crawl, render, index, then rank.

Most SEO answers fail because they jump straight to meta tags. The engineer's version is a pipeline: can the bot fetch it, does your JavaScript survive rendering, is it indexed under the URL you intended — and only then, what does the page say about itself.

00 — Four stages, not one

How search actually works

SEO answers get vague because people talk about “ranking” as one thing. It is four stages, and a page can fail at any one of them independently:

1 · Discover

The crawler learns a URL exists — from a link, a sitemap, or a redirect.

2 · Crawl

It fetches the URL. robots.txt and status codes decide whether this happens.

3 · Render

Googlebot queues the page for a headless Chromium pass that executes JavaScript.

4 · Index & rank

The rendered content is stored, deduplicated against canonicals, and ranked.

As a frontend engineer you own stages 1–3 almost entirely, and you influence stage 4 mainly through content structure and page experience. When an interviewer asks “how would you improve SEO”, the strong answer starts by identifying which stage is failing rather than listing tags.

The framing to open with“First I check whether the page can be crawled, then whether its content survives rendering, then whether it is indexed under the URL I intend. Only after those do meta tags and structured data matter.”
01 — Crawlable is not the same as indexable

Crawling & indexing controls

ControlWhereWhat it actually does
robots.txt/robots.txtAsks crawlers not to fetch a path. It does not remove a page from the index.
meta robots<meta name="robots" content="noindex">Asks that the page not be indexed. The crawler must be allowed to fetch the page to see it.
X-Robots-TagHTTP response headerSame directives for non-HTML resources — PDFs, images, JSON.
rel=canonicalhead link or HTTP headerA hint about which URL is the primary version of duplicate content.
sitemap.xmlListed in robots.txt / Search ConsoleA discovery aid for URLs that are poorly linked. It does not guarantee indexing.
The classic trapDisallow in robots.txt plus noindex on the page is self-defeating: the crawler obeys the disallow, never fetches the page, and therefore never sees the noindex. The URL can still appear in results — as a bare link with no description — because it was discovered through inbound links. To de-index, allow crawling and serve noindex.

Status codes and redirects are SEO primitives

  • 301 / 308 — permanent. Signals move to the target. This is how you retire a URL without losing its history.
  • 302 / 307 — temporary. The original URL stays indexed, at least initially; leave a “temporary” redirect in place long enough and Google will treat it as permanent and swap the canonical anyway. Using 302 for a known permanent move is a common self-inflicted wound.
  • 404 vs 410 — gone is gone; 410 is a stronger signal but both work. What you must avoid is a soft 404: a “not found” page served with 200 OK.
  • Redirect chains waste crawl budget and add latency — Googlebot follows about 10 hops and then gives up. Signals are not diluted per hop (Google has said 30x redirects do not lose PageRank), so do not repeat that myth; collapse chains anyway, because one broken hop kills the whole path.

Sitemaps, concretely

One sitemap holds up to 50,000 URLs or 50 MB uncompressed; beyond that, use a sitemap index. Include only canonical, indexable, 200-returning URLs — a sitemap full of redirects and noindexed pages is a quality signal against you. lastmod is used if it is consistently honest, so do not set it to the build time of every page.

02 — The part that is actually your job

JavaScript & SEO

Googlebot does execute JavaScript — it renders with an evergreen headless Chromium. But rendering is a second, deferred pass: the page is crawled, queued, and rendered when resources allow. Content that only exists after JS runs is indexed later and less reliably than content in the HTML response.

More importantly, Googlebot is not the only consumer of your HTML. Social and messaging crawlers — the ones that build link previews — generally do not execute JavaScript at all. A client-rendered Open Graph tag simply does not exist for them.

ApproachSEO outcome
CSR (empty shell + bundle)Riskiest. Content depends on the render pass; previews and non-Google crawlers see nothing.
SSRContent is in the initial HTML. The default answer for indexable, dynamic pages.
SSG / ISRBest of all — indexable HTML, CDN-fast, and fast pages help page experience.
Dynamic rendering (serve prerendered HTML to bots)Works, but Google now describes it as a workaround rather than a recommendation. It is a second codepath to keep correct.
Links must be linksA crawler discovers URLs from <a href>. A <div onClick={navigate}> or a <button> that pushes history is invisible for discovery — and unusable with a keyboard or middle-click. This is the single most common SPA SEO defect, and the fix is also the accessibility fix.

The same applies to content behind interaction. Text revealed only after a click may be indexed if it is present in the DOM, but content fetched on click is not there at render time and will not be indexed.

03 — What the page says about itself

On-page fundamentals

  • <title> — one of the strongest on-page signals, and the headline in results. Unique per page, front-load the distinguishing words, roughly 50–60 characters before truncation. Google may rewrite it if it is unhelpful.
  • meta description — not a ranking factor. It influences click-through by supplying the snippet, and is often replaced by Google with page text that better matches the query.
  • Headings — h1–h6 should describe the document outline honestly. One h1 is a sound convention rather than a rule; what matters is that headings are not chosen for their font size.
  • Semantic HTML — main, nav, article, time, real lists and tables. It helps parsers and assistive tech for the same reason.
  • Image alt text — describes the image for image search and screen readers. Decorative images take alt="" so they are skipped, not described badly.
  • URLs — readable, stable, lowercase, hyphenated. Changing a URL costs you its accumulated signals unless you 301 it.
  • Internal linking — how crawl equity flows and how orphan pages get discovered. Descriptive anchor text beats “click here” for both ranking and screen-reader users.

Link preview tags

Open Graph and Twitter Card tags are not search-ranking signals, but they control how the URL appears when shared, and they must be in the server HTML for crawlers that do not run JavaScript.

<title>Order book — Acme Exchange</title>
<meta name="description" content="Live depth and trades for every listed pair.">
<link rel="canonical" href="https://acme.com/markets/btc-usdt">
<meta property="og:title" content="BTC/USDT order book">
<meta property="og:image" content="https://acme.com/og/btc-usdt.png">
<meta name="twitter:card" content="summary_large_image">
Mobile-first indexingGoogle indexes the mobile rendering of your page. Content, structured data, and metadata hidden or dropped from the mobile layout are effectively not indexed. Responsive markup avoids this entirely; separate mobile templates invite it.
04 — Telling the engine what the page is

Structured data

Structured data annotates content with a machine-readable vocabulary (schema.org) so a search engine can recognise a page as a Product, Article, Recipe, Event, or Video. Google's preferred format is JSON-LD in a script tag — it is separate from your markup, so it does not entangle with your components.

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Aeron Chair",
  "offers": {
    "@type": "Offer",
    "price": "1395.00",
    "priceCurrency": "SGD",
    "availability": "https://schema.org/InStock"
  }
}
</script>

What it buys you is eligibility for rich results — star ratings, price and stock, breadcrumbs, recipe and event details — which raise click-through. It is not a direct ranking boost, and eligibility is never a guarantee that Google will show the enhancement.

Do not cite FAQ rich resultsSince August 2023 Google shows FAQPage results only for authoritative government and health sites, and HowTo was retired outright. Naming FAQ accordions as an example is the fastest way to date yourself; naming them as a feature Google withdrew does the opposite.
It must match the pageStructured data that describes content a user cannot see is a policy violation and can earn a manual action. Generate it from the same data that renders the page, never by hand in a template that drifts.
05 — One page per language and region

International SEO

If you ship localised pages, search engines need to know they are alternates of each other rather than duplicates. That is hreflang.

<link rel="alternate" hreflang="en-sg" href="https://acme.com/sg/pricing">
<link rel="alternate" hreflang="ja-jp" href="https://acme.com/jp/pricing">
<link rel="alternate" hreflang="x-default" href="https://acme.com/pricing">
  • Annotations must be bidirectional — every alternate lists every other, including itself. A one-way reference is ignored.
  • Values are BCP 47 tags: language, optionally script, optionally region. x-default marks the fallback for unmatched users.
  • They can live in the <head>, in the sitemap, or in an HTTP header — pick one place and be consistent.
  • Each locale needs its own crawlable URL. Swapping language client-side from a cookie gives search engines a single URL with unstable content.
Never auto-redirect by IPGooglebot crawls predominantly from US IP addresses. IP-based redirects therefore mean it mostly only ever sees your US pages, so the other locales go largely unindexed — Google does run some geo-distributed crawling for locale-adaptive pages, but you cannot rely on it. Detect a preference, suggest the local site with a banner, and let the user choose — the same conclusion the localisation guide reaches for user-experience reasons.
06 — Page experience, precisely

Core Web Vitals as a ranking signal

Google uses page experience as a ranking signal, and its measurable core is the three Web Vitals — assessed on field data from real Chrome users (CrUX), not on your Lighthouse score. Specifically: the 75th percentile of page loads over a rolling 28-day window, segmented by mobile and desktop. That percentile is the most common follow-up question, and it is why a good median with a bad tail still fails.

MetricMeasuresGood
LCPLargest Contentful Paint — when the main content appears≤ 2.5 s
INPInteraction to Next Paint — responsiveness across the visit≤ 200 ms
CLSCumulative Layout Shift — visual stability≤ 0.1

INP replaced FID in March 2024. Saying “FID” in an interview dates you; saying “INP replaced FID because FID only measured the delay of the first interaction and almost everyone passed it” does the opposite.

Keep the weighting honestPage experience is a real but modest signal — a tiebreaker among comparable results, not a substitute for relevance. The strong interview answer says so, rather than implying a fast site outranks a better-matching one.
07 — Where single-page apps quietly fail

SPA pitfalls

  • Soft 404s. A client-side router renders a “not found” view while the server returns 200. Google indexes an error page or flags a soft 404. Return a real 404 status for unknown routes server-side.
  • Fragment routing. /#/products/1 is one URL to a crawler — the fragment is never sent to the server. Use the History API so each view has a real path. The old #! scheme is long deprecated.
  • Head tags never updating. Client-side navigation must update title, description, and canonical. If the crawler renders the page and the head still describes the home page, every route looks duplicate.
  • Infinite scroll. Content loaded on scroll may never be reached. Provide paginated, linked URLs behind the same data, and let infinite scroll be a progressive enhancement.
  • Faceted navigation. Filter combinations explode into near-duplicate URLs. Be precise about which lever you need: noindex and canonical control what gets indexed — a noindexed URL is still fetched, so neither saves crawl budget. To stop the crawling, Disallow the parameter patterns in robots.txt or move filters into URL fragments.
  • Blocked assets. Disallowing /static/ or your JS in robots.txt stops the renderer from building the page — it sees an unstyled, contentless shell.
08 — How you actually diagnose it

Tools & measurement

ToolUse it for
Search ConsoleThe ground truth. Pages report (indexed vs excluded, with reasons), Performance (queries, impressions, CTR), Core Web Vitals from field data, sitemap submission, manual actions.
URL InspectionPer-URL: is it indexed, which canonical did Google pick, and — critically — view the rendered HTML Googlebot produced. This is how you prove a JS rendering problem.
Rich Results TestValidates structured data and shows which rich result types the page qualifies for.
Lighthouse SEO auditA shallow lab check — crawlability, title, description, link text, viewport. Passing 100 means nothing was obviously broken, not that the page is optimised.
Site crawlersScreaming Frog, Sitebulb: crawl the whole site to find redirect chains, orphan pages, duplicate titles, broken canonicals at scale.
Server logsWhat Googlebot actually fetched and how often — the only real view of crawl budget on a large site.
Say this when asked which tools you use“Search Console for whether Google indexed it and under which canonical, URL Inspection's rendered HTML for whether our JavaScript actually produced the content, a crawler for site-wide structural issues, and CrUX for whether the vitals problem is real for users rather than only in my lab run.”
09 — Drill until reflex

Scenario drills

Drill 1 — the page that will not de-index
“We added noindex to /admin and blocked it in robots.txt a month ago. It is still in Google. Why?”

The robots.txt Disallow prevents Google from fetching the page, so it never sees the noindex. The URL stays indexed from inbound links, typically with no description. Fix: remove the disallow so the page can be crawled, keep the noindex, and wait for a recrawl — or use the Removals tool to speed it up. Once it has dropped out, you can re-block if you want to save crawl budget.

Drill 2 — the React app that ranks for nothing
“A CSR React site has good content but almost no organic traffic and link previews show a blank card. Diagnose.”

The HTML response is an empty shell. Confirm it: curl the URL, or use URL Inspection's rendered HTML in Search Console. Google may eventually render it, but the deferred render pass makes indexing slow and unreliable, and social crawlers do not execute JavaScript at all — hence the blank preview. Fix by moving to SSR or SSG so the title, description, Open Graph tags, and main content are in the initial response. Also check that navigation uses real <a href> links so pages are discoverable.

Drill 3 — traffic dropped after a redesign
“We changed URL structure. Rankings collapsed. What went wrong and what do you check?”

Old URLs lost their accumulated signals. Check: are old URLs 301-redirecting to the closest equivalent new page (not all to the home page, which Google treats as a soft 404)? Are there redirect chains? Do internal links and the sitemap point at the new URLs directly? Are canonicals self-referential on the new pages? Then watch the Pages report in Search Console for a spike in Page with redirect or Not found.

Drill 4 — spot the error
<link rel="alternate" hreflang="en" href="/en/">
<link rel="alternate" hreflang="fr" href="/fr/">
// …on the English page only
Missing reciprocity, self-reference and x-default

Two problems. First, hreflang must be bidirectional — the French page must carry the same set, or the annotation is ignored. Second, the set must include a self-reference, and there is no x-default for users whose language matches neither. Also prefer absolute URLs, which is what Google documents for hreflang.

Drill 5 — how would you improve SEO here?
“An e-commerce SPA. Open-ended: what do you do first?”

Resist listing tags. Work the pipeline: (1) Crawl — is robots.txt blocking assets or key paths, do product links use real anchors, are there redirect chains? (2) Render — does the raw HTML contain the product name, price, and description, or only a shell? (3) Index — in Search Console, how many product URLs are indexed versus excluded, and which canonical did Google choose for filtered URLs? (4) Only then: titles and descriptions per product, Product structured data generated from the same data as the page, and Core Web Vitals from field data. Naming the order is the answer they are grading.
