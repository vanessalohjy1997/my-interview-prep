Frontend interview prep

Crawl, render, index, then rank.

Most SEO answers fail because they jump straight to meta tags. The engineer's version is a pipeline: can the bot fetch it, does your JavaScript survive rendering, is it indexed under the URL you intended — and only then, what does the page say about itself.

00 — Four stages, not one

How search actually works

SEO answers get vague because people talk about “ranking” as one thing. It is four stages, and a page can fail at any one of them independently:

1 · Discover

The crawler learns a URL exists — from a link, a sitemap, or a redirect.

2 · Crawl

It fetches the URL. robots.txt and status codes decide whether this happens.

3 · Render

Googlebot queues the page for a headless Chromium pass that executes JavaScript.

4 · Index & rank

The rendered content is stored, deduplicated against canonicals, and ranked.

As a frontend engineer you own stages 1–3 almost entirely, and you influence stage 4 mainly through content structure and page experience. When an interviewer asks “how would you improve SEO”, the strong answer starts by identifying which stage is failing rather than listing tags.

The framing to open with“First I check whether the page can be crawled, then whether its content survives rendering, then whether it is indexed under the URL I intend. Only after those do meta tags and structured data matter.”

Why the stages are worth separating

Because the fixes are unrelated and the symptoms look identical. “We're not showing up in Google” is compatible with all four failures, and each has a different owner:

Failing stageWhat you'd seeWhat fixes it
DiscoverThe URL isn't in Search Console at allInternal links, a sitemap. Nothing on the page itself matters yet
Crawl“Blocked by robots.txt”, or a 4xx/5xx in the Pages reportrobots.txt, status codes, server availability, redirect chains
RenderIndexed, but the rendered HTML in URL Inspection is an empty shellSSR/SSG, or getting content into the initial response
Index“Crawled — currently not indexed”, or indexed under a different canonicalCanonicals, duplicate content, thin pages, quality

Notice that the first two have nothing to do with your application code, and the third is entirely an architecture decision. Meta tags — the thing most answers start with — only matter once all four stages already succeed. That inversion is the point of the framing.

The one number worth knowing: the render queue

Rendering is deferred because it's expensive — running a headless browser per URL costs orders of magnitude more than fetching HTML. Google has said the median delay between crawl and render is seconds, but the tail is what hurts: a page can sit in the queue for days when a site is large or low-priority. So on a client-rendered site, your content isn't unindexable — it's indexed late and less reliably, which for anything time-sensitive (news, listings, stock, events) is functionally the same problem.

01 — Crawlable is not the same as indexable

Crawling & indexing controls

ControlWhereWhat it actually does
robots.txt/robots.txtAsks crawlers not to fetch a path. It does not remove a page from the index.
meta robots<meta name="robots" content="noindex">Asks that the page not be indexed. The crawler must be allowed to fetch the page to see it.
X-Robots-TagHTTP response headerSame directives for non-HTML resources — PDFs, images, JSON.
rel=canonicalhead link or HTTP headerA hint about which URL is the primary version of duplicate content.
sitemap.xmlListed in robots.txt / Search ConsoleA discovery aid for URLs that are poorly linked. It does not guarantee indexing.
The classic trapDisallow in robots.txt plus noindex on the page is self-defeating: the crawler obeys the disallow, never fetches the page, and therefore never sees the noindex. The URL can still appear in results — as a bare link with no description — because it was discovered through inbound links. To de-index, allow crawling and serve noindex.

Status codes and redirects are SEO primitives

  • 301 / 308 — permanent. Signals move to the target. This is how you retire a URL without losing its history.
  • 302 / 307 — temporary. The original URL stays indexed, at least initially; leave a “temporary” redirect in place long enough and Google will treat it as permanent and swap the canonical anyway. Using 302 for a known permanent move is a common self-inflicted wound.
  • 404 vs 410 — gone is gone; 410 is a stronger signal but both work. What you must avoid is a soft 404: a “not found” page served with 200 OK.
  • Redirect chains waste crawl budget and add latency — Googlebot follows about 10 hops and then gives up. Signals are not diluted per hop (Google has said 30x redirects do not lose PageRank), so do not repeat that myth; collapse chains anyway, because one broken hop kills the whole path.

Sitemaps, concretely

One sitemap holds up to 50,000 URLs or 50 MB uncompressed; beyond that, use a sitemap index. Include only canonical, indexable, 200-returning URLs — a sitemap full of redirects and noindexed pages is a quality signal against you. lastmod is used if it is consistently honest, so do not set it to the build time of every page.

Canonicals: a hint, and what makes Google ignore it

The word “hint” in the table above is doing real work, and it's the follow-up question. rel=canonical is one input among several — Google also weighs internal links, redirects, sitemap membership, hreflang clusters and which version is more linked. When those conflict with your declared canonical, Google picks its own, and Search Console tells you so with “Alternate page with proper canonical tag” or “Duplicate, Google chose different canonical than user”. So a canonical that's being ignored is almost always a signal-consistency problem, not a tag problem.

Three rules that prevent most of it: make it self-referential on every page (a page's canonical points at itself), make it absolute, and make it agree with everything else — if you canonicalise to the non-trailing-slash version, your internal links and sitemap must use that version too.

Crawl budget — and when to stop caring about it

Crawl budget is the intersection of what your server can take (crawl rate) and how much Google wants your pages (crawl demand). It is a genuine constraint on large sites — think hundreds of thousands of URLs, or sites generating URL combinations faster than they can be crawled. For a 200-page marketing site it is not your problem, and saying so is a stronger answer than reciting optimisations that don't apply.

Where it does apply, the levers are: don't let faceted navigation generate infinite URL space, collapse redirect chains, return 404/410 promptly for dead URLs, keep the server fast (a slow server directly reduces crawl rate), and remember that noindex doesn't save crawl budget — the page must be fetched for the directive to be seen. Only Disallow stops the fetch.

02 — The part that is actually your job

JavaScript & SEO

Googlebot does execute JavaScript — it renders with an evergreen headless Chromium. But rendering is a second, deferred pass: the page is crawled, queued, and rendered when resources allow. Content that only exists after JS runs is indexed later and less reliably than content in the HTML response.

More importantly, Googlebot is not the only consumer of your HTML. Social and messaging crawlers — the ones that build link previews — generally do not execute JavaScript at all. A client-rendered Open Graph tag simply does not exist for them.

ApproachSEO outcome
CSR (empty shell + bundle)Riskiest. Content depends on the render pass; previews and non-Google crawlers see nothing.
SSRContent is in the initial HTML. The default answer for indexable, dynamic pages.
SSG / ISRBest of all — indexable HTML, CDN-fast, and fast pages help page experience.
Dynamic rendering (serve prerendered HTML to bots)Works, but Google now describes it as a workaround rather than a recommendation. It is a second codepath to keep correct.
Links must be linksA crawler discovers URLs from <a href>. A <div onClick={navigate}> or a <button> that pushes history is invisible for discovery — and unusable with a keyboard or middle-click. This is the single most common SPA SEO defect, and the fix is also the accessibility fix.

The same applies to content behind interaction. Text revealed only after a click may be indexed if it is present in the DOM, but content fetched on click is not there at render time and will not be indexed.

How to prove it rather than argue about it

This question — “does Google see our content?” — is usually settled with opinions. There are three cheap ways to settle it with evidence, and naming them is what makes the answer senior:

  1. URL Inspection → Test live URL → View rendered HTML in Search Console. This is Googlebot's own rendered DOM. If your product description isn't in it, the argument is over.
  2. curl the URL (or view-source) to see the raw HTML response — that's what non-rendering crawlers, including most social preview bots, get.
  3. Disable JavaScript in DevTools and reload. A crude approximation of the pre-render state, but instant and good enough to spot an empty shell.
The honest nuance on “Google renders JS”Both extremes are wrong. “Google can't read JavaScript” has been out of date for years. “Google renders JS so CSR is fine” ignores the queue, the cost, and every other crawler — Bing renders inconsistently, and Slack, WhatsApp, Twitter/X, LinkedIn and iMessage previews generally don't render at all. The defensible position: for pages whose discoverability matters, get the content and the head tags into the HTML response; for logged-in application screens nobody should index, client rendering is completely fine and you can stop worrying about it.
03 — What the page says about itself

On-page fundamentals

  • <title> — one of the strongest on-page signals, and the headline in results. Unique per page, front-load the distinguishing words, roughly 50–60 characters before truncation. Google may rewrite it if it is unhelpful.
  • meta description — not a ranking factor. It influences click-through by supplying the snippet, and is often replaced by Google with page text that better matches the query.
  • Headings — h1–h6 should describe the document outline honestly. One h1 is a sound convention rather than a rule; what matters is that headings are not chosen for their font size.
  • Semantic HTML — main, nav, article, time, real lists and tables. It helps parsers and assistive tech for the same reason.
  • Image alt text — describes the image for image search and screen readers. Decorative images take alt="" so they are skipped, not described badly.
  • URLs — readable, stable, lowercase, hyphenated. Changing a URL costs you its accumulated signals unless you 301 it.
  • Internal linking — how crawl equity flows and how orphan pages get discovered. Descriptive anchor text beats “click here” for both ranking and screen-reader users.

Link preview tags

Open Graph and Twitter Card tags are not search-ranking signals, but they control how the URL appears when shared, and they must be in the server HTML for crawlers that do not run JavaScript.

<title>Order book — Acme Exchange</title>
<meta name="description" content="Live depth and trades for every listed pair.">
<link rel="canonical" href="https://acme.com/markets/btc-usdt">
<meta property="og:title" content="BTC/USDT order book">
<meta property="og:image" content="https://acme.com/og/btc-usdt.png">
<meta name="twitter:card" content="summary_large_image">
Mobile-first indexingGoogle indexes the mobile rendering of your page. Content, structured data, and metadata hidden or dropped from the mobile layout are effectively not indexed. Responsive markup avoids this entirely; separate mobile templates invite it.

Why the title still matters most, mechanically

Of everything in this list, <title> is the one with both a ranking role and a click-through role, which is why it's worth spending real effort on. The practical constraint is pixel width rather than character count — Google truncates around 580px on desktop, which lands near 50–60 characters for typical text but far fewer for wide capitals. That's the reason for front-loading: the distinguishing words must survive the truncation, so “Order book — Acme” beats “Acme Exchange | Trading | Order book”.

And Google rewrites titles for a large share of results when it judges yours unhelpful — boilerplate-heavy, keyword-stuffed, or identical across pages. Being able to say “a rewritten title is usually a signal the title was templated rather than descriptive” is a better answer than a character count.

Where this advice stops applying

Everything in this section assumes a page you want indexed. A logged-in dashboard, an internal tool, a checkout step or a staging environment wants the opposite — and the failure mode there is the mirror image: a staging site indexed because someone relied on Disallow instead of noindex plus HTTP auth, or a customer's order confirmation page turning up in search results. Ask which side of the line the page is on before optimising anything.

04 — Telling the engine what the page is

Structured data

Structured data annotates content with a machine-readable vocabulary (schema.org) so a search engine can recognise a page as a Product, Article, Recipe, Event, or Video. Google's preferred format is JSON-LD in a script tag — it is separate from your markup, so it does not entangle with your components.

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Aeron Chair",
  "offers": {
    "@type": "Offer",
    "price": "1395.00",
    "priceCurrency": "SGD",
    "availability": "https://schema.org/InStock"
  }
}
</script>

What it buys you is eligibility for rich results — star ratings, price and stock, breadcrumbs, recipe and event details — which raise click-through. It is not a direct ranking boost, and eligibility is never a guarantee that Google will show the enhancement.

Do not cite FAQ rich resultsSince August 2023 Google shows FAQPage results only for authoritative government and health sites, and HowTo was retired outright. Naming FAQ accordions as an example is the fastest way to date yourself; naming them as a feature Google withdrew does the opposite.
It must match the pageStructured data that describes content a user cannot see is a policy violation and can earn a manual action. Generate it from the same data that renders the page, never by hand in a template that drifts.

Why JSON-LD rather than microdata

The older formats — microdata and RDFa — annotate your markup with extra attributes, which means the structured data is entangled with your components: a designer moving a div silently breaks the machine-readable meaning, and the same fact often has to be repeated across templates. JSON-LD is one self-contained block, so it can be generated from the same object that renders the page, unit-tested, and diffed. That decoupling is the whole reason Google recommends it, and it's the reason to give if asked.

Where the value actually is

Be precise about the mechanism, because “structured data helps SEO” is the vague version. It doesn't raise your ranking. It makes you eligible for a richer result — stars, price, stock, breadcrumbs, an image — and a richer result occupies more of the page and attracts more clicks at the same position. So the win is click-through rate on the position you already had. Frame it that way and the follow-up ("how would you measure it?") answers itself: Search Console's Performance report, comparing CTR before and after the enhancement appears, at matched positions.

The types that still earn rich resultsProduct (price, availability, reviews), Article/NewsArticle, Breadcrumb, Organization and LocalBusiness, Event, Video, Recipe, JobPosting. The ones that were withdrawn — HowTo retired, FAQPage restricted to government and health sites in August 2023 — are worth naming precisely because they show you track changes rather than repeating a 2019 blog post. Validate with the Rich Results Test, which tells you which enhancements a page qualifies for; the older Structured Data Testing Tool is retired.
05 — One page per language and region

International SEO

If you ship localised pages, search engines need to know they are alternates of each other rather than duplicates. That is hreflang.

<link rel="alternate" hreflang="en-sg" href="https://acme.com/sg/pricing">
<link rel="alternate" hreflang="ja-jp" href="https://acme.com/jp/pricing">
<link rel="alternate" hreflang="x-default" href="https://acme.com/pricing">
  • Annotations must be bidirectional — every alternate lists every other, including itself. A one-way reference is ignored.
  • Values are BCP 47 tags: language, optionally script, optionally region. x-default marks the fallback for unmatched users.
  • They can live in the <head>, in the sitemap, or in an HTTP header — pick one place and be consistent.
  • Each locale needs its own crawlable URL. Swapping language client-side from a cookie gives search engines a single URL with unstable content.
Never auto-redirect by IPGooglebot crawls predominantly from US IP addresses. IP-based redirects therefore mean it mostly only ever sees your US pages, so the other locales go largely unindexed — Google does run some geo-distributed crawling for locale-adaptive pages, but you cannot rely on it. Detect a preference, suggest the local site with a banner, and let the user choose — the same conclusion the localisation guide reaches for user-experience reasons.

What hreflang is actually for — and what it isn't

The common misconception is that hreflang is a ranking or targeting instruction. It isn't: it's a deduplication and swap mechanism. Without it, your /sg/pricing and /uk/pricing pages look like near-duplicate English content, and Google picks one canonical and drops the rest. With it, they're understood as alternates of one page, and Google swaps in the right variant for the user's language and region. The pages already had to earn their ranking independently.

That also explains why the bidirectional requirement is strict rather than pedantic. Google is building a cluster, and it will only trust an edge that both ends confirm — otherwise anyone could claim their page is the German alternate of a competitor's. A missing return link means the whole annotation is discarded, which is the single most common hreflang bug.

  • The language part is required, the region optional. hreflang="en" is valid; hreflang="sg" is not, because SG is a region, not a language — that's the classic invalid value. And en-GB means “English, for users in Britain”, not “British English”.
  • It doesn't have to be a translation. Same-language regional variants — en-us and en-sg differing only in currency and shipping — are exactly the case it was designed for.
  • Canonical and hreflang must agree. If /sg/pricing canonicalises to /pricing, you've told Google the SG page isn't a page in its own right, and the hreflang cluster collapses.
06 — Page experience, precisely

Core Web Vitals as a ranking signal

Google uses page experience as a ranking signal, and its measurable core is the three Web Vitals — assessed on field data from real Chrome users (CrUX), not on your Lighthouse score. Specifically: the 75th percentile of page loads over a rolling 28-day window, segmented by mobile and desktop. That percentile is the most common follow-up question, and it is why a good median with a bad tail still fails.

MetricMeasuresGood
LCPLargest Contentful Paint — when the main content appears≤ 2.5 s
INPInteraction to Next Paint — responsiveness across the visit≤ 200 ms
CLSCumulative Layout Shift — visual stability≤ 0.1

INP replaced FID in March 2024. Saying “FID” in an interview dates you; saying “INP replaced FID because FID only measured the delay of the first interaction and almost everyone passed it” does the opposite.

Keep the weighting honestPage experience is a real but modest signal — a tiebreaker among comparable results, not a substitute for relevance. The strong interview answer says so, rather than implying a fast site outranks a better-matching one.

The reason to be careful here is that the honest version is more persuasive. A slow page with the best answer will usually still outrank a fast page with a worse one; vitals decide between pages that are otherwise comparable. Where the effect is genuinely large is bounce and conversion, which is a business argument rather than a ranking one — and often the more useful one to make internally, since it doesn't depend on guessing Google's weighting.

Why your Lighthouse score and Search Console disagreeThey are measuring different things and both are right. Lighthouse is a single lab run on simulated hardware; Search Console reports the p75 of real Chrome users over 28 days, which includes cheap Android devices, poor connections, cold caches and pages you never test. A perfect lab score with failing field data means your synthetic profile isn't your users — segment CrUX by device to find which cohort is failing. It also means a fix takes weeks to show, because the 28-day window has to roll forward. Never promise an immediate improvement in that report.

One SEO-specific vitals note: CLS is measured across the whole visit, not just the load, so a layout shift caused by a lazy-loaded ad halfway down the page counts. And because the assessment is per-URL but falls back to a group of similar URLs when a page lacks data, a template-level problem can drag down every page that shares it — which is usually the efficient thing to fix.

07 — Where single-page apps quietly fail

SPA pitfalls

  • Soft 404s. A client-side router renders a “not found” view while the server returns 200. Google indexes an error page or flags a soft 404. Return a real 404 status for unknown routes server-side.
  • Fragment routing. /#/products/1 is one URL to a crawler — the fragment is never sent to the server. Use the History API so each view has a real path. The old #! scheme is long deprecated.
  • Head tags never updating. Client-side navigation must update title, description, and canonical. If the crawler renders the page and the head still describes the home page, every route looks duplicate.
  • Infinite scroll. Content loaded on scroll may never be reached. Provide paginated, linked URLs behind the same data, and let infinite scroll be a progressive enhancement.
  • Faceted navigation. Filter combinations explode into near-duplicate URLs. Be precise about which lever you need: noindex and canonical control what gets indexed — a noindexed URL is still fetched, so neither saves crawl budget. To stop the crawling, Disallow the parameter patterns in robots.txt or move filters into URL fragments.
  • Blocked assets. Disallowing /static/ or your JS in robots.txt stops the renderer from building the page — it sees an unstyled, contentless shell.

The one that catches everyone: the head never changes

Worth expanding because it's subtle and extremely common. On a client-side navigation there is no new document, so nothing resets the <head> — your title, description, canonical and Open Graph tags persist from whatever page was loaded first. In a browser you don't notice, because the user is looking at the body. To a renderer, every route is a page whose head describes the home page: identical titles, identical descriptions, and canonicals that all point at / — which actively tells Google to index only the home page and treat every route as a duplicate of it.

// the symptom in Search Console
/products/aeron   → "Duplicate, submitted URL not selected as canonical"
/products/mirra   → "Duplicate, submitted URL not selected as canonical"
/products/setu    → "Duplicate, submitted URL not selected as canonical"
// all three canonicalised to "/" by a stale head tag

The fix is a head manager that updates per route — the framework's metadata API, or a library — and the test is mechanical: navigate client-side to three routes and check that document.title and the canonical link changed. Better still, server-render the head so it's correct before any JavaScript runs.

The trade-off nobody states

All of this costs something. SSR adds server cost, a rendering tier to operate, and a whole class of hydration bugs; static generation adds build time that grows with page count and a staleness problem that ISR then has to solve. For a marketing site, a catalogue, or documentation, that price is obviously worth paying. For an authenticated dashboard behind a login, you're paying it for pages Google will never see. Decide rendering strategy per route, not per app — the pricing page and the trading terminal in the same codebase should not have the same answer.

08 — How you actually diagnose it

Tools & measurement

09 — Drill until reflex

Scenario drills

Drill 1 — the page that will not de-index
“We added noindex to /admin and blocked it in robots.txt a month ago. It is still in Google. Why?”

The robots.txt Disallow prevents Google from fetching the page, so it never sees the noindex. The URL stays indexed from inbound links, typically with no description. Fix: remove the disallow so the page can be crawled, keep the noindex, and wait for a recrawl — or use the Removals tool to speed it up. Once it has dropped out, you can re-block if you want to save crawl budget.

Drill 2 — the React app that ranks for nothing
“A CSR React site has good content but almost no organic traffic and link previews show a blank card. Diagnose.”

The HTML response is an empty shell. Confirm it: curl the URL, or use URL Inspection's rendered HTML in Search Console. Google may eventually render it, but the deferred render pass makes indexing slow and unreliable, and social crawlers do not execute JavaScript at all — hence the blank preview. Fix by moving to SSR or SSG so the title, description, Open Graph tags, and main content are in the initial response. Also check that navigation uses real <a href> links so pages are discoverable.

Drill 3 — traffic dropped after a redesign
“We changed URL structure. Rankings collapsed. What went wrong and what do you check?”

Old URLs lost their accumulated signals. Check: are old URLs 301-redirecting to the closest equivalent new page (not all to the home page, which Google treats as a soft 404)? Are there redirect chains? Do internal links and the sitemap point at the new URLs directly? Are canonicals self-referential on the new pages? Then watch the Pages report in Search Console for a spike in Page with redirect or Not found.

Drill 4 — spot the error
<link rel="alternate" hreflang="en" href="/en/">
<link rel="alternate" hreflang="fr" href="/fr/">
// …on the English page only
Missing reciprocity, self-reference and x-default

Two problems. First, hreflang must be bidirectional — the French page must carry the same set, or the annotation is ignored. Second, the set must include a self-reference, and there is no x-default for users whose language matches neither. Also prefer absolute URLs, which is what Google documents for hreflang.

Drill 5 — how would you improve SEO here?
“An e-commerce SPA. Open-ended: what do you do first?”

Resist listing tags. Work the pipeline: (1) Crawl — is robots.txt blocking assets or key paths, do product links use real anchors, are there redirect chains? (2) Render — does the raw HTML contain the product name, price, and description, or only a shell? (3) Index — in Search Console, how many product URLs are indexed versus excluded, and which canonical did Google choose for filtered URLs? (4) Only then: titles and descriptions per product, Product structured data generated from the same data as the page, and Core Web Vitals from field data. Naming the order is the answer they are grading.

Drill 6 — every route is a duplicate
“Search Console says 40 of your 45 product pages are ‘Duplicate, Google chose a different canonical’, and it chose the home page. What happened?”
A stale head on client-side navigation

Almost certainly the head never updates on route change. Client-side navigation doesn't create a new document, so title, description and canonical persist from the first page loaded — meaning every route renders with a canonical pointing at /, which explicitly tells Google these aren't separate pages. I'd confirm it with URL Inspection's rendered HTML on one product URL, then fix it with a per-route metadata API, ideally server-rendered so it's correct before any JS runs. The test afterwards is mechanical: navigate client-side to three routes and assert the canonical changed.

Drill 7 — the page won't de-index
“You added noindex to a page a month ago and it's still in Google. Why?”

Most likely the URL is also disallowed in robots.txt, so Googlebot never fetches it and never sees the noindex — and it can still list the bare URL because it was discovered through inbound links. The fix is counter-intuitive: allow crawling so the directive can be read, and only add a disallow later if crawl budget matters. Other candidates: the noindex is injected by JavaScript and the page hasn't been re-rendered, or it's in the sitemap and hasn't been recrawled yet. For something urgent I'd use the Removals tool as a stopgap while the real signal propagates.

Drill 8 — the link preview is blank
“The page ranks fine, but sharing it in Slack or WhatsApp shows no title or image. Explain.”

Google renders JavaScript; social preview crawlers generally don't. If the Open Graph tags are injected client-side they exist for Googlebot's render pass and not for Slack, which just fetches the raw HTML. curl the URL and you'll see the tags missing. They have to be in the server response — which is a good argument for server-rendering the head even on a site where the body can be client-rendered.

Drill 9 — push back
“A stakeholder wants the logged-in dashboard server-rendered 'for SEO'. What do you say?”

That SEO isn't the reason to do it, because nothing behind a login can be crawled — Googlebot has no session. If we want SSR there it has to be justified on other grounds: faster first paint on slow devices, or not shipping the data-fetching waterfall to the client. And it isn't free — a rendering tier to operate, hydration bugs, and server cost per request. I'd rather decide rendering per route: static for marketing, SSR for the public catalogue where crawlability and first paint both matter, and client rendering for the authenticated app.
