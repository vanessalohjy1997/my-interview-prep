00 — The diagnostic

Two questions that solve most bugs

Almost every layout bug answers to one of two questions: what box is this, and what is it relative to?

  • (1) What box is this element? Its display and its box-sizing.
  • (2) What is it positioned or sized relative to? Its containing block and its formatting context.

How to use it. When a layout misbehaves, ask both questions before touching any CSS. “Why is it there” and “why is it that size” almost always answer to one of the two.

01 — Content, padding, border, margin

The box model

Every element is a box of four layers, and box-sizing decides which layers width counts.

  • Inside out: content → padding → border → margin.
  • box-sizing: content-box (default): width is the content only. Padding and border add on top.
  • box-sizing: border-box: width includes padding and border.

Example. The question that trips people up is what width refers to. A 200px box with 20px padding renders 240px wide under content-box. Under border-box that 200px stays 200px. This is why teams set *{ box-sizing: border-box } globally.

margin — outside the box, collapses vertically
border
padding — inside the border, painted with the background
content  ·  width & height apply here
content-box: width = the pink box only  ·  border-box: width = pink + cyan + violet

Margin collapsing

Adjacent vertical margins of block elements merge into one, and the result is not the sum.

  • Two positives collapse to the larger of the two.
  • A positive and a negative add together.
  • Two negatives collapse to the most negative.

Where it happens. Between siblings. Between a parent and its first/last child. Within an empty block, where its own top and bottom margins meet. It stops when something separates the margins: padding, border, inline content or a set height. It also stops when the parent establishes a new block formatting context, e.g. overflow: hidden or display: flow-root.

Where it never happens. Horizontal margins never collapse. Neither do the margins of flex items or grid items. Collapsing is a block-layout behaviour only.

What establishes a block formatting context

A BFC is a mini-layout that stops floats and margins leaking through its boundary.

  • Floats stay inside it.
  • Margins do not collapse through it.
  • It will not overlap a float beside it.

What creates one. The root element. Floats. position: absolute/fixed. display: inline-block. Table cells and captions. display: flow-root, the purpose-built one. Flex and grid items. overflow anything but visible or clip. contain: layout | content | paint. Query containers (container-type not normal). Multi-column containers.

The trap. overflow: clip clips but creates no BFC and no scroll container. So it does not fix collapsed margins, and it does not contain floats. overflow: hidden does both. The cost is that the box becomes (programmatically) scrollable.

100vw and the scrollbarViewport units are sized as if scrollbars do not exist. So width: 100vw on a page with a classic (non-overlay) vertical scrollbar is wider than the visible area by the scrollbar width. That causes a horizontal scroll. Every variant behaves this way: vw, svw, lvw, dvw. The spec only subtracts the bar when the root element forces one unconditionally, with overflow: scroll or scrollbar-gutter: stable. When it matters, use width: 100% of the body, or scrollbar-gutter: stable on the root.
02 — Placement & layers

Position & stacking context

ValueBehaviour
staticdefault; in normal flow; ignores top/left
relativeoffset from its normal spot; still occupies its original space
absoluteremoved from flow; positioned to the nearest positioned ancestor (the containing block)
fixedpositioned to the viewport — unless an ancestor has a transform (or translate/rotate/scale), perspective, filter, backdrop-filter, a will-change naming any of those, contain: layout | paint | strict | content, or content-visibility: auto: that ancestor becomes its containing block
stickyrelative until a scroll threshold, then sticks within its nearest scrolling ancestor — and only for as long as its parent is on screen. The two ways it silently fails: an ancestor between it and the scroller has overflow: hidden/auto/scroll (that becomes the scroller), or the parent is exactly as tall as the sticky element, so there is nowhere to stick

Stacking context & z-index gotchas

z-index is only ever compared inside one stacking context, and many innocent-looking properties create a new one.

  • z-index only applies to positioned elements (and flex/grid items). On a static element it does nothing.
  • A child's z-index is only compared within its parent's stacking context. Children can't escape their parent's context.

What creates a stacking context. position: relative/absolute plus a non-auto z-index. position: fixed or sticky, always, no z-index needed. A flex or grid item with a z-index. And a long list of paint effects: opacity < 1, transform (and translate/rotate/scale), filter, backdrop-filter, perspective, clip-path, mask, mix-blend-mode other than normal, isolation: isolate, contain: layout | paint | strict | content, a will-change naming any of those, and anything in the top layer (<dialog>, popovers).

The one to use on purpose. isolation: isolate makes a context with no visual side effect. So a component's internal z-indexes cannot leak out.

The classic bug. A high z-index: 9999 child inside a low-stacked parent still loses to a sibling of the parent. The 9999 is only compared against things inside the same parent. Nothing the child does can lift it above the parent's context.

03 — One dimension

Flexbox

Flexbox lays out items along one axis, and every property is defined in terms of that axis.

How it works. Set display: flex on the container. Items distribute along the main axis and align on the cross axis. The properties that come up:

  • flex-direction sets the main axis: row by default, or column. This is the one that flips everything below it. In a column, justify-content now controls vertical spacing and align-items horizontal.
  • justify-content distributes items along the main axis.
  • align-items aligns items on the cross axis. align-self overrides it for one item.
  • flex: grow shrink basis. flex: 1 means “grow to fill, shrink if needed, from a 0 basis.”
  • gap spaces items without margins.
  • align-content only does anything when items wrap onto multiple lines. It distributes the lines themselves. Since 2024 it also works on plain block containers (Baseline April 2024). So align-content: center vertically centres a block's contents with no flex at all.

The three numbers in flex

      
flex is shorthand for flex-grow flex-shrink flex-basis. The values that come up constantly:

      

        
ShorthandLonghandBehaviour

        
flex: initial0 1 autothe default — don't grow, do shrink, size from content/width

        
flex: 11 1 0%share free space equally, ignoring content width

        
flex: auto1 1 autogrow, but from the content size — wider content keeps a bigger share

        
flex: none0 0 autorigid — never grows or shrinks

      

      
flex: 1 vs flex: autoBoth grow. The difference is the basis. With flex: 1 the basis is 0, so items end up the same width regardless of content. With flex: auto the basis is the content, so a longer label keeps a wider column. Reach for flex: 1 when you want equal columns. Reach for flex: auto when content should have a say.

      
The overflow bug everyone hitsA flex item's min-width is auto, not 0. It refuses to shrink below its content's intrinsic minimum. So a long unbroken string or a nested table blows the row out instead of truncating, and your text-overflow: ellipsis never fires. Fix: min-width: 0 on the item (min-height: 0 for a column). Tailwind spells it min-w-0. The spec's other escape hatch is making the item a scroll container: overflow: hidden, auto or scroll sets the automatic minimum to zero. That is why the ellipsis recipe works with overflow: hidden alone. overflow: clip is not a scroll container, so it does not release the floor.

      
// nav bar: logo left, links right, vertically centred
.nav { display: flex; align-items: center; justify-content: space-between; gap: 16px; }

// the truncating row
.row   { display: flex; gap: 12px; }
.row .label { flex: 1; min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }

    


    

      
04 — Two dimensions

      
Grid

      
Grid lays out in rows and columns at once: define tracks on the container, then place items into them.

      
.layout {
  display: grid;
  grid-template-columns: 200px 1fr;   // sidebar + fluid content
  gap: 16px;
}
// responsive wrap with no media queries:
.cards { display: grid; grid-template-columns: repeat(auto-fit, minmax(220px, 1fr)); gap: 16px; }

      
    
        
  • fr distributes leftover space; minmax(min, max) bounds a track.
    • 
        
  • repeat(auto-fit, minmax(...)) makes items wrap responsively without media queries.
    • 
        
  • grid-template-areas lets you name regions and place items by name. Very readable for page shells.
    • 
        
  • Explicit vs implicit tracks. Tracks you declare are explicit. Anything overflowing creates implicit tracks, sized by grid-auto-rows / grid-auto-columns. “Why is my last row a different height?” is almost always an implicit row.

auto-fit vs auto-fill

      
Both repeat as many tracks as fit; they only differ in what happens to the empty ones.

      
    
        
  • auto-fill keeps the empty tracks. Items stay at their minmax minimum, left-aligned.
    • 
        
  • auto-fit collapses them to zero. The remaining items stretch across the full width.
    • 
      

      
Example. The difference shows when there aren't enough items. Two items in a wide container: auto-fill leaves them narrow, auto-fit makes them half the row each.


      
Why 1fr is really minmax(auto, 1fr)

      
A bare 1fr track has a content-sized floor, so repeat(3, 1fr) does not guarantee three equal columns.

      
How it works. This is the grid twin of the flex overflow bug. The spec treats a bare 1fr as minmax(auto, 1fr). That auto is the largest min-width of the items in the track. For a grid item, that defaults to its content's minimum size. So the track has an automatic minimum it will not shrink below.

      
Where it bites. A long unbroken string or a wide <pre> in one cell grows that track. The others shrink, or the grid overflows. Either way the columns are not equal.

      
The fix. minmax(0, 1fr) removes the floor and gives you the equal thirds you meant. That is exactly why Tailwind's grid-cols-3 compiles to repeat(3, minmax(0, 1fr)). Same fix as flex, spelled on the track instead of the item.

      
Subgrid and container queries

      
Subgrid and container queries are both safe to ship; style queries are newer and still want a fallback.

      
    
        
  • Subgrid (grid-template-columns: subgrid) lets a nested grid adopt the parent's track lines. So card titles, bodies and footers line up across cards. Baseline since September 2023 (Chrome 117, Safari 16, Firefox 71). Safe to use.
    • 
        
  • Container queries size a component by its container, not the viewport. Put container-type: inline-size on the parent and @container (min-width: 40rem) on the child. Baseline since February 2023. The cost people miss: container-type applies size containment on that axis. The container can no longer size itself from its children in that axis. inline-size is the sane default because block size still comes from content.
    • 
        
  • Container units ship with container queries: cqi/cqb (1% of the container's inline/block size), plus cqw/cqh. They make fluid type inside a card trivial.
    • 
        
  • Style queries test a custom property instead of a size: @container style(--variant: compact) { … }. Newly Baseline in May 2026 (Firefox 151 was last; Chrome 111 and Safari 18 had it). Still treat them as progressive enhancement for older browsers.
    •

Grid vs FlexFlexbox for content that flows in one direction (a toolbar, a row of chips). Grid when you need explicit two-dimensional structure (a page shell, a card gallery, aligned rows and columns). They compose: grid areas often contain flex rows.

      
items vs contentFour alignment properties, and interviewers love the distinction. justify-items/align-items position each item inside its own track. justify-content/align-content position the whole set of tracks inside the container. So they only do something when the tracks are smaller than the container: fixed px columns, not 1fr. place-items and place-content are the row-then-column shorthands.

    


    

      
05 — Who wins

      
The cascade & specificity

      
When several rules target one element, the cascade walks a fixed list of criteria in order, and specificity is only step five.

      
How it works. The steps, highest first:

      
    
        
  1. Origin and importance. !important and origin (author vs user vs browser) come first. The full precedence, highest first: running transitions, !important browser, !important user, !important author, running animations, normal author, normal user, normal browser. So a keyframe animation beats every normal author declaration, including an inline style. It loses to !important. That is why an !important declaration on an animated property makes the animation appear not to run.
    2. 
        
  2. Context. Across a shadow DOM boundary, normal declarations from the outer tree win and !important declarations from the inner tree win. So a component can set overridable defaults or hard requirements.
    3. 
        
  3. The style attribute. Inline styles beat any selector-matched rule of the same importance. This is a cascade step, not a specificity score.
    4. 
        
  4. Cascade layers. With @layer, a later layer beats an earlier one, and unlayered styles beat all layers. This is decided before specificity is compared.
    5. 
        
  5. Specificity. ID > class/attribute/pseudo-class > element/pseudo-element, compared as a three-part tuple (id, class, element). :where() contributes zero. :is()/:not()/:has() take their most specific argument.
    6. 
        
  6. Scope proximity. For @scope rules only, the rule whose scoping root is closest to the element wins.
    7. 
        
  7. Source order. If everything above ties, the later rule wins.
    8. 
      

      
Inheritance is separate. Some properties (color, font) inherit. Layout properties (margin, padding) don't. Avoid !important: it escalates specificity wars. Prefer a single low-specificity system.

      
Reading specificity as a tuple, and why it never carries

      
Specificity is compared left to right as separate columns, not as a number, so one ID beats any number of classes.

      
How it works. This is the rule people get wrong under pressure. There is no base-10 carrying between columns. A hundred classes is (0,100,0). It still loses to (1,0,0).

      
#nav .item a:hover        // (1, 2, 1)  — id, [class + pseudo-class], element
.nav .item .link.active   // (0, 4, 0)  — loses: 0 < 1 in the first column
a:where(.item.active)     // (0, 0, 1)  — :where() zeroes everything inside it
a:is(#nav, .item)         // (1, 0, 1)  — :is() takes its MOST specific argument
:not(.a, #b)              // (1, 0, 0)  — same rule: most specific argument counts
li:has(> img.hero)        // (0, 1, 1)  — :has() too: most specific argument
:nth-child(2n of .item)   // (0, 2, 0)  — the pseudo-class itself PLUS its most specific argument

      
Two details worth saying out loud. The “most specific argument” rule applies regardless of which argument actually matched. :is(em, #foo) is (1,0,0) even on a plain <em>. And :nth-child(… of S) is the odd one out. It adds the S specificity to its own (0,1,0) rather than replacing it.

      
Why :where() matters. It is the most useful modern tool in this area. It lets a design system ship defaults at zero specificity, so any consumer rule overrides them without a fight. @layer does the same job at a coarser grain. Layer order is decided before specificity is even compared. That is why a low-specificity rule in a later layer beats a high-specificity rule in an earlier one. Both exist because the alternative was the escalation that ends in !important.

      
The one legitimate use of !important

      
!important is defensible in exactly two places: utilities that must win by design, and third-party styles you don't control.

      
    
        
  • Utility classes that must win by design. .hidden { display: none !important }: if it doesn't hide the thing, it's broken.
    • 
        
  • Overriding third-party or injected styles you don't control.
    • 
      

      
Why have an answer. “Never use it” invites the follow-up. It is not defensible as a way to win a fight with your own stylesheet. That's a signal the specificity architecture is wrong. The fix is layers or lower-specificity selectors, not escalation.

      
The layer twist. !important reverses the layer order: among important declarations, earlier layers win. That is deliberate, so a base layer can lock something down. The corollary that surprises people: unlayered styles sit in an implicit last layer. So an unlayered !important loses to a layered one.

      
The cleaner escape. revert-layer (Baseline 2023) rolls a property back to whatever the previous layer said. You don't need to know what that was.

      
Nesting, @scope and :has() — where they stand in 2026

      
Nesting and :has() are safe to assume; @scope only became Baseline in March 2026 and still wants a fallback.

      
    
        
  • Nesting is Baseline since December 2023 and widely available since mid-2026. The 2024 “relaxed” change (CSSNestedDeclarations: Chrome 130, Firefox 132, Safari 18.2) made declarations written after a nested rule keep their source position instead of being hoisted above it. Before that, color: black after an @media block could lose to the block. The remaining trap: a nested selector that starts with an element name works, but &Element is invalid. Write Element&. Nested & compiles to :is(parent), so the parent's specificity is its most specific selector, not the one that matched.
    • 
        
  • :has(), the parent selector, is Baseline since December 2023 (Firefox 121 was last) and widely available since June 2026. It is safe. The cost is that the engine must re-evaluate ancestors when descendants change. So avoid :has() with deep, unanchored arguments on hot subtrees.
    • 
        
  • @scope gives a rule a lower bound (@scope (.card) to (.slot)) and adds scope proximity to the cascade. Chrome has had it since 118 and Safari since 17.4. Firefox only shipped it in 146 (December 2025), and Safari's version had gaps until 26.4, so it became Baseline in March 2026. Fine to use with a fallback. Not yet something to assume in an interview answer about “all browsers”.
    • 
      

      
Why the cascade is designed this way at all

      
CSS has to merge declarations from sources that don't know about each other, and produce one value per property.

      
    
        
  • The browser's defaults.
    • 
        
  • The user's accessibility settings.
    • 
        
  • Your stylesheet.
    • 
      

      
Why origin comes first. The origin ordering exists so a user's stylesheet with !important beats the author's. That is the mechanism that lets someone force a larger font or higher contrast on your site. Specificity is only the tie-breaker within an origin.

      
Say this. Frame it as conflict resolution across parties, not as a scoring quirk. That is what makes it sound understood rather than memorised.


      
Debugging “my CSS isn't applying” systematically

      
Work through a fixed checklist in order, because that is what you would actually do at the keyboard.

      
How it works. A practical checklist beats guessing. It's a good thing to be able to recite in order:

      
    
        
  1. Is the rule matching at all? DevTools shows unmatched selectors nowhere. Overridden ones are struck through, with the winner linked. If your rule isn't in the Styles panel, it's a selector or a build problem, not a cascade one.
    2. 
        
  2. Is it struck through? Then it matched and lost. Compare the winner's origin and importance, layer, specificity and source order, in that sequence: the cascade's own order.
    3. 
        
  3. Is the property inheritable? Setting font-size on a container works. Setting border on it doesn't reach children.
    4. 
        
  4. Is the property valid in this context? justify-content on a non-flex, non-grid parent does nothing and is not flagged as an error. Same for z-index on a position: static element that isn't a flex or grid item, width on an inline element, and top without positioning.
    5. 
        
  5. Is something else winning at a different layer of the platform? An inline style, a UA default, a !important from a third-party widget, or a shadow DOM boundary your selector cannot cross.
    6. 
      

      
Where it bites. Point four is the highest-yield one. Most “CSS is ignoring me” reports are a property that is silently inapplicable, not a rule that lost.

      
Centering, the canonical answers

      
// flexbox — most common
.parent { display: flex; justify-content: center; align-items: center; }
// grid — shortest
.parent { display: grid; place-items: center; }
// absolute — when out of flow
.child { position: absolute; top: 50%; left: 50%; transform: translate(-50%, -50%); }

    


    

      
06 — Two mechanisms, one budget

      
Transitions & animations


      
A transition interpolates between two states and needs a trigger; an animation runs a keyframe timeline and needs none.

      
    
        
  • A transition needs something to change it: a class, a pseudo-class, an inline style.
    • 
        
  • An animation can start on load, loop, and pass through as many steps as you like.
    • 
      

      
How it works. Two mechanical facts explain most animation bugs. First, a transition needs two computed values it can interpolate between. So animating to or from auto, or from display: none, historically did nothing at all. There was no start value to move from. Modern CSS is fixing this with @starting-style, transition-behavior: allow-discrete and interpolable height: auto, but the fallback behaviour is still what you'll be asked about.

      
Where it bites. Second, the element must already be in the layout for the transition to fire. That is why adding an element and a class in the same frame animates nothing. Both values land in the same style recalculation, so there is no change to interpolate.

      
.btn {
  background: #333;
  transition: background 200ms ease-out, transform 120ms ease-out;
}
.btn:hover { background: #555; transform: translateY(-1px); }

@keyframes pulse {
  from { opacity: 1; }
  50%  { opacity: .4; }
  to   { opacity: 1; }
}
.badge { animation: pulse 1.4s ease-in-out infinite; }

      

        
PropertyWhat it controls

        
transitionShorthand for property duration timing-function delay. List several, comma-separated. Naming the properties beats all, which quietly animates things you did not intend.

        
timing-functionease, linear, ease-in-out, cubic-bezier() for a custom curve, steps() for sprite-style jumps.

        
animation-fill-modeWhat applies outside the run. forwards holds the final keyframe — the usual fix for “it snaps back at the end”.

        
animation-directionalternate reverses every other iteration, so a loop does not jump.

        
animation-play-statepaused / running — pausable without JavaScript rewriting the animation.

      

      
The performance question they are really asking

      
Animate transform and opacity, because they are the two properties every engine hands entirely to the compositor.

      
How it works. filter (and in Chromium backdrop-filter) is composited too. But a blur() gets expensive fast with radius and layer size. Chromium's own list is “transform, opacity, filter, and backdrop-filter”. clip-path and background-color compositing are still work in progress there. Everything else costs you work on the main thread every frame:

      
    
        
  • Animating width, height, top, left, margin → layout on every frame, then paint, then composite.
    • 
        
  • Animating background-color, box-shadow, color → paint on every frame, then composite.
    • 
        
  • Animating transform / opacity → composite only, and it can run off the main thread entirely.
    • 
      

      
Example. “Slide this panel in” is transform: translateX(-100%) → translateX(0). Never left: -300px → left: 0. The FLIP technique generalises this. Measure the First and Last positions. Apply the Invert transform. Then Play by transitioning it away. A layout change animates as a pure transform.

      
will-change is not a free winIt is a hint to promote the element to its own compositor layer ahead of time. That costs memory. For the values you would actually name here (transform, opacity, filter) it also creates a stacking context up front, with all the z-index consequences from the previous section. Apply it shortly before the animation and remove it after. A stylesheet full of permanent will-change makes things slower, not faster. And will-change: transform (or filter) makes the element the containing block for any position: fixed descendant. That is the same trap as a real transform.

      
Where animations sit in the cascadeAnimation declarations outrank every normal author declaration, inline style included. That is why el.style.opacity = 0 visibly does nothing while a keyframe animation on opacity runs. They lose only to !important. A running transition outranks even that. If a “stuck” value will not respond to JavaScript, check whether an animation with fill-mode: forwards is still applying.

      
The gotchas

      
Most transition bugs come down to a missing start value, a discrete property, or listening for the wrong end event.

      
    
        
  • You cannot transition to or from auto. Historically true, and still the portable assumption. The classic accordion fix is a wrapper with display: grid; grid-template-rows: 0fr transitioning to 1fr. Put overflow: hidden on the single child, not the wrapper. The child's automatic minimum size is what would otherwise keep the 0fr track open. Chromium now also ships interpolate-size: allow-keywords and calc-size() (Chrome 129, September 2024), which genuinely do interpolate to auto. As of September 2026 it is still Chromium-only, with no Firefox or Safari. Know it exists and still reach for grid.
    • 
        
  • Transitions need a starting value the browser has rendered. An element inserted already in its end state has nothing to transition from. Historically you forced a reflow. Modern CSS gives you @starting-style (Baseline since August 2024: Chrome 117, Safari 17.5, Firefox 129).
    • 
        
  • display is discrete, so a fade-out to display: none traditionally required JavaScript or a delay. transition-behavior: allow-discrete (Baseline August 2024: Chrome 117, Safari 17.4, Firefox 129) now lets it participate. The switch to none is deferred to the end of the transition. The switch away from none happens at the start.
    • 
        
  • Respect motion preferences. Wrap non-essential motion in @media (prefers-reduced-motion: reduce). Reduce it to a near-instant cross-fade rather than removing feedback entirely.
    • 
        
  • Events differ between the two. transitionend fires once per transitioned property, so check event.propertyName. animationend fires once when the whole animation finishes, after every iteration. The per-iteration event is animationiteration. Animation events carry animationName, not propertyName. Neither “end” event fires if the thing is interrupted. You get transitioncancel / animationcancel instead.
    • 
      

      
The newer motion APIs, and where they stand (September 2026)

      
Same-document View Transitions are Baseline; scroll-driven animations and anchor positioning are not, so gate those with @supports.

      
    
        
  • Scroll-driven animations. animation-timeline: scroll() / view() drive a keyframe animation from scroll position instead of time. They run off the main thread, with no scroll listener. Chrome 115 and Safari 26 ship it. Firefox still has it behind a flag, so it is not Baseline. Progressive enhancement: wrap in @supports (animation-timeline: scroll()).
    • 
        
  • View Transitions. document.startViewTransition(cb) snapshots old and new states and animates between them. view-transition-name pairs elements. Same-document transitions became Baseline in October 2025 when Firefox 144 shipped. The cross-document flavour (@view-transition { navigation: auto } for MPA navigations) is Chrome 126 and Safari 18.2 only, still no Firefox.
    • 
        
  • Anchor positioning. anchor-name / position-anchor / anchor() tether a popover to a trigger with fallback placement, no JavaScript. Chrome 125, Safari 26 and Firefox 147 all ship a version. But the implementations still differ enough that it is not Baseline as of September 2026. Keep a positioning library behind a @supports (anchor-name: --a) check.

07 — Runtime values, not build-time text

      
Custom properties


      
A custom property is a real CSS value that cascades and inherits in the browser; a Sass variable is text that is gone before the browser sees it.

      
How it works. A custom property participates in the cascade like any other value. It inherits down the tree. That is the entire difference from a Sass variable, which is text substituted at build time.

      
:root {
  --space: 8px;
  --brand: #E879F9;
  --btn-bg: var(--brand);
}
.card { --space: 12px; }              /* scoped override, inherits down */
.card .body { padding: var(--space); } /* 12px, not 8px */
.btn { background: var(--btn-bg, #666); } /* fallback if undefined */

      

        
Sass variableCSS custom property

        
ResolvedAt build timeAt computed-value time, in the browser

        
ScopeLexical, in the source fileThe DOM — it inherits to descendants

        
Changeable at runtimeNoYes — by a class, a media query, or JavaScript

        
Readable from JSNoYes

      

      
Why inheritance is the whole point

      
Theming works because you redefine a handful of properties on an ancestor, and every descendant that reads them updates. No duplicated rule blocks, no specificity war:

      
:root         { --bg: #fff; --fg: #111; }
[data-theme="dark"] { --bg: #0B1416; --fg: #E6F0EE; }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { --bg: #0B1416; --fg: #E6F0EE; }
}
body { background: var(--bg); color: var(--fg); }

      
Example. The same idea gives components a styling API. Expose --btn-bg and --btn-radius, and consumers can restyle the button without overriding your selectors. It is the one hook that survives CSS Modules, shadow DOM, and utility frameworks alike.

      
JavaScript interop

      
el.style.setProperty('--x', e.clientX + 'px');
getComputedStyle(el).getPropertyValue('--brand').trim();

      
Setting one property is much cheaper than swapping classes across a tree. That makes this the standard technique for cursor-following effects, live theming, and progress indicators.

      
Three sharp edges1) An invalid substitution is invalid at computed-value time. The property falls back to its inherited or initial value, not to the var() fallback. The fallback only applies when the property is undefined. 2) You cannot use var() in a media query condition. The one place you can branch on a custom property is a container style query, @container style(--theme: dark), Baseline only since May 2026. 3) Custom properties are untyped tokens, so they only animate discretely. They flip at the halfway point rather than interpolating.

      
@property gives them a type

      
@property --angle {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}
.ring { transition: --angle 300ms linear; }

      
Registering a property tells the browser what kind of value it holds, and that is what lets it animate smoothly.

      
What you get. Type checking. A real initial value. And the useful part: smooth interpolation instead of the discrete 50% flip. So gradients and angles driven by custom properties can finally be transitioned and animated properly. @property is Baseline since July 2024 (Firefox 128 was last; Chrome 85, Safari 16.4).

      
Two colour helpers that shrink theme codelight-dark(#fff, #111) picks per color-scheme with no media query (Baseline May 2024). Relative colour syntax, oklch(from var(--brand) l c h / 0.5), derives hover, border and tint shades from one token instead of hard-coding five (Baseline September 2024). Both compose with custom properties. Neither replaces them.

    


    

      
08 — Utility-first

      
Tailwind CSS, briefly

      
Tailwind is a utility-first framework: the same CSS properties you just learned, composed as single-purpose classes in the markup.

      
How it works. Instead of writing a rule and inventing a class name for it, you compose tiny single-purpose classes in the markup. flex items-center justify-between gap-4 is the CSS you just learned. Same properties, same mental model, different authoring surface.

      
What it buys you. Two things, and both are worth saying out loud in an interview:

      
    
        
  • No naming, no dead CSS. The hardest part of a stylesheet is naming things and knowing when a rule is safe to delete. Utilities live and die with the markup that uses them. So the stylesheet stops growing forever.
    • 
        
  • Constraints by default. p-4 comes from a spacing scale, not from someone's guess of 17px. It's a design system enforced by autocomplete.
    • 
      


      
The translation table

      
If you know the CSS, you know Tailwind. The utilities are a naming convention over the same properties:

      

        
CSSTailwind

        
display: flex; flex-direction: columnflex flex-col

        
justify-content: space-betweenjustify-between

        
align-items: centeritems-center

        
gap: 16pxgap-4  (scale = px ÷ 4)

        
flex: 1 1 0%; min-width: 0flex-1 min-w-0

grid-template-columns: 200px 1frgrid-cols-[200px_1fr]  (underscore = space)

        
grid-column: span 2col-span-2

Flip either playground above to its Tailwind tab and the same layout you built comes back as utilities.


      
Variants — the part that isn't just shorthand

      
A utility can be prefixed with a condition, and that is where Tailwind does something plain inline styles can't.

      
How it works. The prefixes compile to real media queries and pseudo-classes, so the utility only applies when the condition holds:

      
<div class="grid grid-cols-1 md:grid-cols-3 gap-4
            hover:shadow-lg focus-visible:ring-2 dark:bg-slate-900">

      
    
        
  • Breakpoints are min-width, and therefore mobile-first. Unprefixed = all sizes. md: = that size and up. Style the small screen first, then layer.
    • 
        
  • State: hover:, focus-visible:, disabled:, first:, odd:.
    • 
        
  • Relational: group-hover: (react to a parent marked group), peer-checked: (react to a sibling), has-[:checked]: (react to a descendant).
    • 
        
  • Data/ARIA: data-[state=open]:rotate-180, aria-expanded:. The glue for headless component libraries.
    • 
        
  • Arbitrary values escape the scale when you genuinely need to: top-[37px], grid-cols-[1fr_auto], bg-[#0B1416].
    • 
      


      
The two gotchas they'll ask about

      
Both gotchas follow from the same fact: Tailwind generates a static stylesheet at build time.

      
1 — Class names must exist as whole stringsThe build scans your source files as plain text. It never runs your code. So text-${color}-500 or `p-${n}` produces nothing. The string text-red-500 never appears in the file. Map to full class names instead (const tone = { red: 'text-red-500', green: 'text-green-500' }), or safelist them. This is the single most common Tailwind bug.

      
2 — Conflicting classes don't cascadeclass="p-2 p-4" doesn't make the last one win. Both rules exist, and source order in the generated stylesheet decides. You don't control that order. So a component that accepts a className prop can't be overridden reliably. The standard fix is tailwind-merge, usually wrapped with clsx as a cn() helper. It resolves conflicts by keeping the last utility per property.

      
// the cn() helper you'll see in every Tailwind codebase
import clsx from 'clsx';
import { twMerge } from 'tailwind-merge';
export const cn = (...i) => twMerge(clsx(i));

// now the caller's p-8 actually beats the default p-4
<button className={cn('p-4 rounded bg-slate-800', className)} />


      
@apply, and when it's a smell

      
@apply inlines utilities into a normal CSS rule, and using it to escape long class lists brings back the problems Tailwind removed.

      
Where it bites. It looks like the fix for “too many classes”. But a stylesheet full of .btn { @apply ... } gives back exactly the naming and dead-code problems Tailwind removed. You've reinvented the framework, slower.

      
The honest answer. Repetition is a component problem, so extract a component. Keep @apply for the handful of cases with no component to hang it on, like styling third-party markup or a base body rule. For components with real variants, class-variance-authority (CVA) is the idiomatic answer: variants as typed props mapping to class strings, merged with cn().


      
What changed in v4

      
v4 moved configuration into CSS and exposes every theme token as a real custom property.

      
    
        
  • Config lives in CSS. @import "tailwindcss" plus an @theme block replaces tailwind.config.js. Design tokens are emitted as real custom properties, so var(--color-brand) works in hand-written CSS too.
    • 
        
  • A new Rust engine (Oxide) with automatic content detection. No content: [] globs to keep in sync.
    • 
        
  • Container queries are built in. @container on the parent, then @md:flex-row on children, sizing off the container rather than the viewport.
    • 
        
  • Output is wrapped in cascade layers. That makes the “does my CSS beat Tailwind's” question predictable at last.
    • 
        
  • Where it is now. v4.0 shipped January 2025. v4.2 (February 2026) added a first-party webpack plugin (@tailwindcss/webpack) and a batch of logical-property utilities. The current line is v4.3 (May 2026), which added scrollbar utilities. The config-in-CSS model above is unchanged.
    • 
      

      
/* app.css — v4, the whole config */
@import "tailwindcss";
@theme {
  --color-brand: #E879F9;
  --spacing-gutter: 1.5rem;
}
/* → gives you bg-brand, text-brand, p-gutter … and var(--color-brand) */


      
If they ask “why not just write CSS?”“Tailwind trades readable markup for a stylesheet that can't rot. On a team, the win is that styles are colocated and deletable, and the scale stops pixel drift — you never have to decide whether some .card--compact is still used. The costs are real: markup gets noisy, you need tailwind-merge for a sane override story, and you must never build class names dynamically. I'd still reach for plain CSS or CSS Modules for a design-system primitive with a complex API, and use custom properties for anything themed at runtime — the two compose fine, since v4 exposes its tokens as custom properties anyway.”

    


    

      
09 — Drill until reflex

      
Scenario drills


      

        
Drill 1 — the z-index that won't work

        
“A dropdown with z-index: 9999 still renders behind the next section. The parent has opacity: 0.98. Why?”

        
        

          
opacity < 1 creates a stacking context on the parent, so the dropdown's z-index is only compared within that parent — it can't rise above elements outside it. Fix: remove the opacity (or the transform/filter) creating the context, or restructure so the dropdown is a child of a higher-stacked ancestor (e.g. portal it to the body).

      


      

        
Drill 2 — box-sizing math

        
.box { width: 200px; padding: 20px; border: 5px solid; }

        
        
content-box → 250px wide · border-box → 200px wide

          
Default content-box adds padding (2×20) and border (2×5) outside the 200px content: 250px total. With box-sizing: border-box, the 200px includes padding and border, so it stays 200px and the content shrinks.

      


      

        
Drill 3 — fixed inside a transform

        
“A position: fixed modal is supposed to cover the viewport but is clipped inside a card. The card has transform: translateZ(0). Why?”

        
        

          
A transform (or filter, backdrop-filter, perspective, a will-change naming one of them, or contain: paint) on an ancestor makes it the containing block for fixed descendants, so ‘fixed’ is now relative to the card, not the viewport. Remove the transform from that ancestor, or render the modal outside it (a portal at the body).

      


      

        
Drill 4 — specificity

        
#nav a { color: blue; }
.link { color: red; }
// <a class="link"> inside #nav

        
        
blue

          
#nav a has an ID (specificity 1,0,1) which beats a single class .link (0,1,0), regardless of source order. To make the class win without !important, raise its specificity or lower the other rule's.

      


      

        
Drill 5 — flex or grid?

        
“A responsive card gallery that wraps to fill the row, equal-width cards, min 220px. Flex or Grid?”

        
        

          
Grid: grid-template-columns: repeat(auto-fit, minmax(220px, 1fr)) wraps and equalises columns with no media queries. Flex can wrap too but making the last row's items match widths is fiddlier. Grid is the two-dimensional tool; use it when you want aligned rows and columns.

      


      

        
Drill 6 — the janky drawer

        
“A side drawer animates with transition: left 300ms and stutters on mobile. Fix it.”

        
        

          
Animating left changes geometry, so the browser runs layout and paint on every frame on the main thread. Switch to transform: translateX(-100%) → translateX(0), which the compositor can handle without layout or paint — and off the main thread. Add will-change: transform just before the animation if you still see a first-frame hitch, and remove it afterwards.

      


      

        
Drill 7 — height: auto

        
“An accordion needs to expand from 0 to its natural height. transition: height 200ms does nothing. Why?”

        
        

          
auto is not an interpolatable value, so there is nothing to animate between. The robust CSS-only fix is a wrapper with display: grid; grid-template-rows: 0fr transitioning to 1fr, with overflow: hidden on the child. Alternatives: animate max-height to a value you know exceeds the content (cheap, but the timing is wrong because the transition covers the unused range), or measure with JavaScript and animate to an explicit pixel height.

      


      

        
Drill 8 — Sass variable or custom property?

        
“When would you use each, and why can a custom property do theming that a Sass variable cannot?”

        
        

          
A Sass variable is text replaced at build time — it cannot change at runtime and does not exist in the browser, which makes it fine for build-time constants like a breakpoint list. A custom property is a real value that cascades and inherits, so redefining --bg on [data-theme="dark"] updates every descendant that reads it, with no duplicated rules and no specificity fight. It is also readable and writable from JavaScript, which is what makes live theming and cursor-driven effects cheap.

      


      

        
Drill 9 — the row that won't truncate

        
.row   { display: flex; gap: 12px; }
.title { flex: 1; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }
// a long title pushes the price button off the edge instead of truncating

        
        
min-width: 0 on .title

          
A flex item's min-width defaults to auto, which is its content's intrinsic minimum — so the item refuses to shrink below the full title and flex-shrink can never do its job. Setting min-width: 0 (or overflow: hidden, which has the same side effect) releases the floor and the ellipsis appears. In a column, it's min-height: 0. Tailwind: min-w-0.

      


      

        
Drill 10 — auto-fit or auto-fill?

        
“A card grid uses repeat(auto-fill, minmax(220px, 1fr)). With only two cards in a 1400px container they sit narrow on the left, and the designer wants them to fill the row. What changes?”

        
        
Swap auto-fill for auto-fit

          
auto-fill creates every track that fits and keeps the empty ones, so the two cards stay at 220px with empty tracks beside them. auto-fit creates the same tracks then collapses the empty ones to zero, so the 1fr maximum lets the two remaining cards absorb the whole row. When the container is full of items the two behave identically — which is why the difference only ever bites at low item counts.

      


      

        
Drill 11 — the Tailwind class that vanishes in production

        
const tone = severity === 'high' ? 'red' : 'green';
return <span className={`text-${tone}-500`}>{label}</span>;
// works in dev after someone used text-red-500 elsewhere; ships colourless

        
        
The class name never exists as a literal string

          
Tailwind's build scans source files as plain text — it does not execute your code, so it never sees text-red-500 in that template literal and never generates the rule. Fix by mapping to complete class names: const tone = { high: 'text-red-500', low: 'text-green-500' }, so the full strings appear in the file. Safelisting works but is a last resort. This is also why className props should receive whole utilities, never fragments.

      

    
      

        
Drill 12 — a hundred classes lose to one id

        
#sidebar .card .title { color: red; }
.theme .page .card .title.large.bold { color: blue; }

        
        
Red wins — (1,2,0) beats (0,6,0)

          
Specificity is compared column by column, left to right, with no carrying — so a single ID beats any number of classes. This is why ID selectors are avoided in component CSS: one of them anywhere in the stylesheet is an override nothing reasonable can beat, and the only escape is another ID or !important. The modern tools for avoiding the fight entirely are :where(), which contributes zero specificity, and @layer, whose ordering is resolved before specificity is even compared.

      


      

        
Drill 13 — the transition that never runs

        
const el = document.createElement('div');
el.className = 'toast';           // opacity: 0; transition: opacity .3s
document.body.append(el);
el.classList.add('visible');      // opacity: 1
// it just appears — no fade

        
        
Both values land in the same style recalculation

          
A transition interpolates between two computed values, and here the element has never had its styles computed with opacity: 0 — the append and the class change are processed together, so the browser sees one state, not two. The classic fixes are to force a style flush by reading a layout property (el.offsetHeight) between them, or to add the class in a requestAnimationFrame callback so it lands in a later frame. The modern answer is @starting-style, which declares the state to transition from when an element first renders. The same underlying rule explains why you can't transition from display: none without transition-behavior: allow-discrete.

      


      

        
Drill 14 — my CSS isn't applying

        
“A junior says their rule is being ignored. Walk them through diagnosing it.”

        
        

          
In order. Is the rule in the Styles panel at all — if not it's a selector or build problem, not a cascade one. Is it struck through — then it matched and lost, so compare the winner's origin, layer, specificity and source order in that sequence. Is the property inheritable — setting a border on a parent doesn't reach children. Then the highest-yield check: is the property even applicable here? justify-content on a non-flex parent, z-index on a static element that isn't a flex or grid item, width on an inline element and top without positioning all do nothing and none of them are flagged as errors. Most 'CSS is ignoring me' reports are a silently inapplicable property rather than a lost rule.
