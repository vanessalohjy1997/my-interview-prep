Frontend interview prep

Server rendering is a question about time.

At what moment does the HTML exist — build, request, or after JavaScript runs? Hydration, streaming, and Server Components are all machinery around that one choice, and each one costs something specific.

00 — The only question that matters

Where does the HTML come from?

Every rendering strategy is one answer to one question: at what moment is the HTML for this page produced? At build time, on the server per request, or in the browser after JavaScript runs. Everything else — hydration, streaming, Server Components — is machinery around that choice.

Interviewers are not testing whether you can name the acronyms. They are testing whether you can say what each one costs, and pick one for a described product. Frame every answer as a trade between TTFB (how fast the first byte arrives), FCP/LCP (how fast the user sees content), data freshness, and server cost.

The framing to open withRendering strategy is a per-route decision, not a per-app one. A marketing page, a product listing, and a logged-in dashboard in the same app should usually be static, revalidated, and server-rendered respectively.
01 — Four strategies, one axis

CSR, SSR, SSG and ISR

StrategyHTML madeStrengthsCosts
CSRIn the browser, after the JS bundle downloads and executesCheap hosting (static shell), rich app-like interactions, no server runtimeSlow FCP/LCP, blank page until JS runs, weakest for crawlers and link previews
SSROn the server, on every requestFresh, personalised HTML; content visible before JS; good for crawlersHigher TTFB, a server per request, harder caching
SSGAt build time; served as files from a CDNFastest possible TTFB and LCP, trivially cacheable, cheapestData is as old as the last build; long builds for large sites
ISR / revalidationAt build, then regenerated in the background after a TTL or on demandStatic speed with bounded staleness; no full rebuildUsers can see stale HTML for one revalidation window; needs a stateful cache

Note that SSR and CSR are not exclusive. Almost every real SSR app is both: the server renders the first page, the client bundle hydrates it, and every subsequent in-app navigation is client-rendered. That is the standard “universal” or “isomorphic” setup.

React's server entry points
// Node streams — the modern default, supports Suspense streaming
import { renderToPipeableStream } from 'react-dom/server';

// Web streams — for edge/workers runtimes
import { renderToReadableStream } from 'react-dom/server';

// Sync, returns a complete string. Cannot wait: a suspending component emits its fallback.
import { renderToString } from 'react-dom/server';

On the client the counterpart is hydrateRoot(container, <App />), which is what you use instead of createRoot(...).render(...) when the container already holds server HTML.

Two details on those entry points that get probed. renderToString cannot wait for anything: if a component suspends, it emits the nearest <Suspense> fallback immediately and the real content only appears once client JavaScript renders it. So every byte of data must be fetched before you call it, which is why the slowest fetch sets your TTFB. And the API surface moved: React 19 removed the old renderToNodeStream and renderToStaticNodeStream, and React 19.2 made renderToReadableStream plus the static prerender / resume APIs available in Node too, while still recommending the Node-stream versions as the faster path.

The timeline, with numbers

The clearest way to show you understand the trade is to walk one request. Assume a mid-range phone on a decent mobile connection: ~150ms round trip, and a 200KB JS bundle taking ~600ms to download, parse and execute.

CSR
0ms    request HTML  →  150ms  empty shell arrives      // nothing visible
150ms  request JS    →  750ms  bundle parsed & run
750ms  request data  →  900ms  data arrives
900ms  content visible AND interactive

SSR
0ms    request HTML  →  server fetches data (~100ms), renders
300ms  content visible                            // LCP here
300ms  request JS    →  900ms  bundle parsed, hydration runs
1000ms interactive                                // 700ms of looks-ready-but-isn't

SSG (from a CDN, no data fetch, no origin)
0ms    request HTML  →   50ms  content visible
…same hydration cost, but the paint happened 250ms earlier

Two things fall out of that. SSR's win is entirely in the middle column — content visible far sooner — and it is a real win, because that's what LCP measures and what a user perceives as speed. And SSR's TTFB is worse, not better: the server now does data fetching and rendering before the first byte, where the CSR shell was a static file. If TTFB is already 800ms because of a slow origin, adding SSR makes the blank-screen period longer, not shorter — which is exactly the case where the honest answer is “fix the origin first”.

The third row is why static wins whenever it's possible: no origin, no per-request work, and a CDN edge close to the user. Escalate away from it only when the data genuinely can't be baked in.

Where Next.js is in 2026

Interviewers who ask about ISR almost always mean Next.js, and its defaults have flipped twice. Have the current picture ready rather than the App Router launch one.

  • Next 15 (Oct 2024) removed the implicit caching. fetch, GET route handlers and the client router cache are uncached by default; you opt back in with cache: 'force-cache' on a fetch or export const dynamic = 'force-static' on a route. params, cookies() and headers() became async.
  • Next 16 (Oct 2025) is the current major; 16.3 (Aug 2026) is the current minor. Turbopack is the default bundler for dev and build, proxy.ts replaces middleware.ts and runs on Node, the sync params escape hatch is gone, Node 20.9+ is required, and runtime = 'edge' is deprecated.
  • Cache Components (cacheComponents: true) is the new model: every page is dynamic at request time by default, and 'use cache' on a file, component or async function opts that output into the cache. The key is build ID + a hash of the function + its serialised arguments (closed-over variables are captured as arguments). cacheLife('hours') sets lifetime, cacheTag('products') tags it; with no cacheLife the default profile is stale 5 minutes on the client, revalidate 15 minutes on the server. Partial Prerendering is built in — the static shell is prerendered and each dynamic hole streams inside its <Suspense> — so the old experimental.ppr and dynamicIO flags are gone, and so are the dynamic, revalidate, fetchCache and dynamicParams segment exports once the flag is on.
  • ISR without Cache Components still works as before: export const revalidate = 60 plus generateStaticParams to list which dynamic paths to prerender at build. After 60 seconds the next request still gets the stale page and kicks off regeneration in the background; the request after that gets the fresh one. A regeneration that throws keeps serving the last good page. Paths not in generateStaticParams render on first request unless dynamicParams = false, which 404s them. It needs the Node runtime and a stateful cache — no static export, no edge.
  • On-demand revalidation is revalidatePath('/posts') or revalidateTag('posts', 'max') — Next 16 made the second argument (a cacheLife profile) required and deprecated the one-argument form. Both only invalidate; regeneration happens on the next request. updateTag(tag), Server-Action-only, expires and refetches in the same request for read-your-writes. Self-hosting trap: the default file-system cache is per instance, so an on-demand call invalidates only the instance that received it — use a shared cache handler.
  • Edge runtime means Web APIs only: no Node built-ins or fs, no eval or new Function, no ISR, and Cache Components require Node. Its remaining job is middleware.ts-style request interception; new code should default to Node.
Say this“Next moved from implicit caching to explicit: 15 turned the fetch and route caches off by default, and 16's Cache Components make it opt-in per component with 'use cache', with PPR streaming the dynamic holes inside a prerendered shell. ISR is stale-while-revalidate: the first request after the window is served stale and triggers the regeneration.”
02 — Attaching behaviour to markup

Hydration

Hydration is not rendering. The DOM already exists — the server sent it. Hydration is React walking the component tree on the client, building its internal fiber tree, and adopting the existing DOM nodes instead of creating them: attaching event handlers, wiring refs, and initialising state and effects.

  • What it produces: an interactive page. Before hydration the HTML is visible but inert — clicks do nothing, controlled inputs are not controlled.
  • What it costs: the client still downloads and executes the component code, and still runs the whole render pass. Server rendering improves perceived load; it does not reduce JavaScript.
  • Why it hurts INP: hydrating a large tree is one long task. During it the main thread is blocked, so early clicks queue. This is the gap people call “uncanny valley” — it looks ready and does not respond.
The sharp answer“SSR moves the first paint earlier but not the first interaction. If Time to Interactive is the problem, server rendering alone will not fix it — you need less client JavaScript: streaming with selective hydration, islands, or Server Components.”

React expects the trees to agree

Hydration assumes the client's first render produces the same tree the server produced. React matches its output against the existing DOM node by node. When they disagree you get a hydration mismatch: React logs a recoverable error and discards the server HTML from the nearest <Suspense> boundary above the mismatch, client-rendering that boundary instead. With no Suspense boundary above it — the common case — that is the entire root, so the whole page silently degrades to client rendering and every benefit of SSR is lost. React 19 recovers the same way for text and structure, but three things did change: it logs one error carrying a server/client diff instead of two errors plus a warning; it no longer patches text you suppressed with suppressHydrationWarning (18 quietly wrote the client value into the DOM, 19 leaves the server text); and it skips unexpected extra tags in <head> and <body> — the usual extension injection — instead of treating them as a mismatch. Attribute differences were never a re-render trigger in either version: they are a development-only warning, the DOM keeps the server's attribute, and production is silent.

That recovery rule is also a concrete argument for placing Suspense boundaries in a server-rendered tree: they bound how much of the page a single mismatch can cost you.

Why hydration has to be so strict

It looks pedantic — why can't React just patch up the difference? Because it isn't a diff. React has no previous fiber tree for server HTML; it has DOM nodes and no idea which component produced which node. Hydration works by walking its freshly-rendered tree and the existing DOM in lockstep, assuming they correspond position by position. That assumption is what makes it fast — it's an adoption, not a comparison. The moment the sequences diverge, React can no longer trust any of the correspondence below that point, so the only safe recovery is to throw away that subtree's DOM and render it properly on the client.

Understanding that also explains the cost profile: hydration is roughly as expensive as a full client render (every component runs) but with additional matching work against the DOM. So a large tree is a long, uninterruptible-feeling task — and this is the specific reason “we added SSR and INP got worse” is a real outcome, not a paradox.

The mechanism behind that, for the follow-up: with hydrateRoot, React 18+ hydrates each Suspense boundary as its own unit with gaps in which the browser can handle events. But a discrete event — a click or keypress — on a boundary that has not hydrated yet makes React hydrate that boundary synchronously, during the event's capture phase, so the handler exists by the time the event reaches its target. The same applies to a root with no boundaries. So an oversized boundary still produces one long task, and it lands at the worst possible moment: the user's first click.

The alternatives, since “less hydration” is the whole industry direction

  • Islands (Astro, Fresh) — the page is static HTML with a few independently-hydrated interactive regions. Everything non-interactive ships zero JavaScript. The cost is that islands can't easily share client state, so it suits content sites far better than applications. Astro 5 added server islands (server:defer): a static page with individual components rendered on demand and fetched after load, which is the islands answer to “one personalised block on an otherwise static page”.
  • Server Components — the component never reaches the client at all, so there is nothing to hydrate. The nuance to name: RSC is about bundle size, islands about hydration scheduling. They compose rather than compete.
  • Progressive / selective hydration — React's own answer: hydrate boundaries independently, in priority order, and prioritise whichever one the user just clicked.
  • Resumability (Qwik) — the more radical position: serialise the framework's state into the HTML so the client never re-runs the components at all, only the specific handler the user triggered. Worth naming as the logical endpoint of the argument even if you'd never ship it.
03 — The bug that eats your SSR

Hydration mismatches

Every mismatch has the same root cause: the server and the client rendered different things. The usual suspects:

CauseWhy it divergesFix
Date.now / new DateThe two renders happen at different instantsPass a timestamp as a prop, or render it after mount
Math.random / uuidNon-deterministic by definitionUse useId() for IDs; otherwise generate on the server and pass down
Timezone / localeServer runs in UTC, the user is in Asia/SingaporePass an explicit timeZone and locale to Intl
typeof window checksThe branch is false on the server, true on the clientTwo-pass render (below), never a bare branch during render
localStorage / cookiesNot readable on the server (cookies are, via the request)useSyncExternalStore with a server snapshot, or read the cookie server-side
Invalid HTML nestingThe browser repairs <div> inside <p> before React sees itFix the markup — React cannot match a tree the parser rewrote
Browser extensionsThey inject attributes and nodes into the server HTMLReact 19 skips unexpected extra tags in <head> and <body>; injections deeper in the tree still mismatch. Reproduce in a clean profile before chasing it

The two-pass render

When content genuinely can only exist on the client, render the server-safe version first and swap after mount. The first client render then matches the server, and the second render — after hydration is finished — is a normal update.

const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);
// identical on server and first client render → hydration matches
if (!mounted) return <Skeleton />;
return <Chart data={readFromLocalStorage()} />;
Do not reach for this firstA two-pass render costs you the server HTML for that subtree — the user sees a skeleton until JS runs. Use it for genuinely client-only things (a chart of local data, a theme from localStorage). For anything the server could know, pass the value down instead.

The sanctioned alternative to the mounted flag: put the client-only subtree inside a <Suspense> boundary and let it throw on the server. React emits the fallback into the HTML and renders the content on the client, with no mismatch. useSyncExternalStore is built for this — omitting getServerSnapshot makes the component throw during server rendering, which is exactly the documented way to force a client-only render; providing it makes the server value and the first client render agree.

suppressHydrationWarning

<time suppressHydrationWarning> tells React to tolerate a text difference on that one element. It is correct for an unavoidably time-dependent leaf; it is a bandage anywhere else, because it silences the warning without making the trees agree.

Two details worth knowing about it: it only applies one level deep, to that element's own text and attributes rather than its whole subtree (a mismatch in a grandchild still throws), and it suppresses the warning — in React 19 the DOM keeps the server's value until something re-renders it, which is why a suppressed timestamp shows the server's time until an update. React 18 behaved differently and quietly patched a suppressed text node to the client value, which is what older blog posts describe. If you need the client value visible on 19, you still need the second pass.

The one that catches everyone: dark mode

Worth having ready because it's the most common real-world mismatch and it has a non-obvious fix. The theme lives in localStorage, which the server can't read, so the server renders light, the client hydrates dark, and you either get a mismatch or a visible flash of the wrong theme.

// the standard fix: a tiny blocking script BEFORE React,
// which sets an attribute the CSS keys off — so the paint is already correct
<script>
  try {
    const t = localStorage.theme ??
      (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light');
    document.documentElement.dataset.theme = t;
  } catch {}
</script>

The insight generalises: the mismatch happens because React is being asked to render something only the browser knows. Moving that decision out of React — into a blocking inline script that mutates an attribute, or into a cookie the server can read — removes the divergence instead of papering over it. A cookie is the better answer when you can set one, because then the server genuinely knows and there's no flash at all.

One honest caveat, and it's the detail that shows you've actually shipped this: the script writes an attribute the server didn't render, so React still warns about extra attributes on <html>. That's why next-themes and every implementation of this pattern put suppressHydrationWarning on the <html> element. Used there it is correct — a one-level-deep acknowledgement of a divergence you created deliberately — as opposed to sprinkling it deeper in the tree to silence a real bug.

04 — Do not wait for the slowest query

Streaming SSR & Suspense

Classic renderToString is all-or-nothing: the server renders the entire tree, then sends it. One slow database call delays the whole document, so TTFB is bounded by your slowest dependency.

Streaming SSR flushes HTML as it becomes ready. You mark slow regions with <Suspense>; the server immediately sends the shell with the fallbacks in place, keeps the connection open, and streams each boundary's real HTML as its data resolves — followed by a tiny inline script that moves the content into place.

<Layout>
  <Nav />                              // in the shell, sent immediately
  <Suspense fallback={<Skeleton />}>
    <Reviews />                        // streamed in when its data resolves
  </Suspense>
</Layout>

Selective hydration

The same boundaries let React hydrate independently and out of order. A boundary can hydrate as soon as its HTML and code have arrived, without waiting for its siblings. Better still, if the user clicks inside a boundary that has not hydrated yet and its code has loaded, React hydrates that boundary synchronously in the capture phase of the click, so the handler is attached before the event reaches the target and the click just works. If the code has not arrived yet, React raises that boundary's priority so it hydrates first once it can. Discrete events are not replayed — React 18 dropped replay because the ordering of queued events was ambiguous and enforcing it cost CPU; only continuous ones (mouseover, focusin, pointerover, dragenter) are queued and re-broadcast after hydration, and only the last of each type.

Say this in an interview“Suspense boundaries on the server are the unit of streaming; on the client they are the unit of hydration. That is why placing them well matters — one boundary around the whole page buys you nothing.”

What it looks like on the wire

The shell is everything outside any Suspense boundary. Where a boundary is pending, React writes the fallback between markers with a placeholder: <!--$?--><template id="B:0"></template><p>loading</p><!--/$-->. When the data resolves it appends <div hidden id="S:0">…real markup…</div> and a tiny inline <script>$RC("B:0","S:0")</script> that moves the hidden content into the placeholder's spot. No React on the client is needed for that swap, only inline script. Since React 19.2 those reveals are batched for a short window so streamed and client-rendered Suspense reveal alike, with a heuristic that stops batching as page load approaches 2.5s so the throttle can't be the reason you miss LCP.

The callbacks, and where the status code goes

  • onShellReady — the shell rendered; set the status and headers here and call pipe(res). This is the last moment you can pick 200 vs 500.
  • onShellError — the shell itself threw; no bytes have gone out, so you can still send a real 500 or a fallback HTML page.
  • onError — fires for every server error, inside or outside the shell; by default it just calls console.error. The documented pattern flips a didError flag here and reads it in onShellReady to choose the status.
  • onAllReady — everything, including every boundary, has rendered. Pipe here instead for crawlers and static generation: you lose progressive reveal but the stream is the complete HTML.
  • abort() — call it on a timer (the docs use 10s) to give up on slow boundaries; React flushes their fallbacks and the client renders the rest.

The asymmetry to name: an error inside a boundary after the shell still calls onError, but you get onShellReady rather than onShellError — React emits the fallback and lets the client retry — and by then the 200 has already left.

What streaming costs you

  • You cannot set a status code or headers after the first byte has flushed — an error deep in the tree can no longer become a clean 500. Frameworks handle this by rendering the shell first and only committing the status once it succeeds.
  • Whole-response caching is harder; edge caches must support streamed responses.
  • Streamed content is in the same response body, but it arrives after the shell, inside a hidden element that an inline script relocates. Googlebot copes: it queues every 200 page for rendering in an evergreen Chromium, which usually happens within seconds but can take longer (Google's own 2019 figure was a 5-second median, minutes at the 90th percentile). Google still says server-side or pre-rendering “is still a great idea” because not all bots run JavaScript — link-preview scrapers in particular read only the first chunk. The clean fix for detected bots is to pipe in onAllReady; otherwise keep anything you cannot risk in the shell.
05 — Components that never reach the browser

React Server Components

RSC is a different axis from SSR. SSR asks “where is the HTML produced?” RSC asks “which components ship to the client at all?” A Server Component runs only on the server, and its code is never included in the client bundle.

Server ComponentClient Component
Marked bythe default in an RSC app'use client' at the top of the file
Canbe async, read a DB or the filesystem, use secretsuse state, effects, refs, event handlers, browser APIs
Cannotuse state, effects, or event handlersbe async, or touch server-only resources
Ships JSnoyes — the component and its imports

The boundary is an import boundary, not a render boundary: once a module has 'use client', everything it imports becomes part of the client bundle too. But a Server Component can still pass a rendered Server Component through a Client Component as children — the child was already rendered on the server, so it stays out of the bundle. That is the standard escape hatch for “a client-side layout wrapping server content”.

// page.jsx — a Server Component
export default async function Page() {
  const post = await db.posts.find(id);   // no API route needed
  return (
    <Collapsible>                        // a Client Component
      <Article post={post} />            // still a Server Component
    </Collapsible>
  );
}

Props crossing the boundary must be serializable — but by React's own serializer, which is considerably richer than JSON. It handles primitives, plain objects and arrays, JSX, Date, Map, Set, BigInt, typed arrays, FormData — and promises, which is what lets a Server Component start a fetch and hand the unresolved promise to a Client Component that unwraps it with use(). What cannot cross: arbitrary functions (only Server Functions marked 'use server') and class instances. What travels to the client is not HTML: it is the RSC payload (the wire protocol is nicknamed Flight), a streamed, line-oriented description of the rendered tree with references to client-component modules where a 'use client' boundary sits. One asymmetry to know: JSX can be a prop sent to the client, but it cannot be an argument sent back to a Server Function.

Do not confuse the directives'use client' marks a module as client code. 'use server' marks Server Functions — functions a client may invoke over the network. React renamed them in September 2024: a Server Function is a Server Action only when it is passed to an action prop or called from inside an action. They are not opposites, and 'use server' does not make a component a Server Component.
06 — Fetch once, not twice

Data on the server

The classic SSR bug is fetching the same data twice: once on the server to render, then again on the client because the component's effect runs after hydration. The fix is to serialise the server's data into the HTML and seed the client cache from it.

// server: render, then embed
<script>window.__STATE__ = ${serialize(state)}</script>
// client: hydrate from it instead of refetching
const store = createStore(window.__STATE__);

Query libraries formalise this — TanStack Query calls it dehydrate on the server and HydrationBoundary on the client; Next's App Router does it for you via the RSC payload.

Serialisation is an injection surfaceEmbedding JSON in a <script> tag lets a string containing </script> break out of it. Escape < as \u003c — still valid JSON, inert to the HTML parser — and never inline unescaped user data. A <script type="application/json"> tag you parse is tidier but needs the same escaping, because </script> ends any script element regardless of its type.

Waterfalls

Server rendering makes request waterfalls invisible but not free: a parent that awaits before rendering a child that awaits serialises two round trips. Start independent requests together (Promise.all, or kick off the fetch before awaiting), and hoist shared data to the closest common parent.

07 — There is no window on a server

What breaks when you render server-side

  • Browser globals. window, document, localStorage, IntersectionObserver do not exist. Guard access inside effects (which never run on the server) rather than during render.
  • Module-level mutable state. A module scope is shared across every request the process handles. A cache, a store singleton, or a “current user” assigned at module level leaks one user's data into another's response. State must be created per request and passed down.
  • Effects do not run. useEffect and useLayoutEffect are skipped on the server, so anything you rely on them for is absent from the HTML. Data needed for the first paint must be fetched before rendering. (React 19 dropped the old “useLayoutEffect does nothing on the server” warning; the behaviour is unchanged.)
  • Cleanup never happens. Subscriptions, timers, or listeners created during render on the server are never torn down, because there is no unmount — a steady memory leak.
  • Environment differences. The server's timezone, locale, and even Intl data can differ from the client's. Be explicit about both.
  • Secrets. Anything reachable from a client module ends up in the bundle. Keep server-only code in server-only modules and rely on your framework's server-only guards.

The module-level state one deserves emphasis because it is the most dangerous bug on this page and it doesn't look like a bug. In the browser, a module scope is per user by definition — the tab is the user. On a server, one process serves thousands of requests, so a module-level variable is shared across all of them.

// looks completely normal. On a server it is a cross-user data leak.
let currentUser = null;                 // module scope = shared by every request
export function setUser(u){ currentUser = u; }
export function getUser(){ return currentUser; }

// two concurrent requests interleave:
// req A sets currentUser = alice → awaits the DB
// req B sets currentUser = bob   → awaits the DB
// req A resumes, reads currentUser → gets BOB, renders Bob's data to Alice

It won't reproduce locally, because you're the only user. It appears under concurrency, intermittently, as “a customer saw someone else's account” — the worst possible way to find out. The rule: anything request-scoped must be created per request and passed down (props, context, or the framework's request-scoped storage). A module-level cache is fine only if it's genuinely shared and non-personalised, and even then it needs a bounded size.

Related and slightly subtler: a query client, store, or cache created once at module scope has the same problem — user A's cached responses are served to user B. Frameworks handle this by creating one per request on the server and a singleton only in the browser, which is why the setup code for those libraries always looks oddly defensive.

08 — The answer is per route

Choosing a strategy

The page is…UseBecause
Marketing, docs, blogSSGSame for everyone, changes rarely — serve files from a CDN
Catalogue, listings, pricesISR / SSR with edge cacheShared across users, must be reasonably fresh and indexable
Personalised, behind authSSR (or CSR shell)Not cacheable publicly; SEO is irrelevant behind a login
A heavy tool or editorCSRLong session, no crawler audience, first paint matters least

SSR interacts directly with HTTP caching. A shared, non-personalised server-rendered page can be cached at the CDN with Cache-Control: public, s-maxage=60, stale-while-revalidate=600 — which is, in effect, ISR implemented in cache headers. A personalised one must be private or no-store, and mixing the two is how one user's dashboard gets served to another.

Closing line“I default to static, escalate to revalidated-static when data ages, and only pay for per-request SSR when the response is genuinely personalised. Then I keep the personalised part small enough that the rest can still be cached.”
09 — Drill until reflex

Scenario drills

Drill 1 — the SSR that stopped working
“We server-render, but Lighthouse shows a blank first paint and the console has a hydration error. What happened?”

A hydration mismatch. React found the client's first render disagreeing with the server HTML, discarded the server tree for that subtree — at the root, the whole page — and re-rendered on the client, so the user effectively gets CSR. Find the non-deterministic render: a date, a random value, a typeof window branch, a locale-formatted number, or invalid HTML nesting the parser repaired. Fix the determinism rather than suppressing the warning.

Drill 2 — TTFB got worse
“We moved from CSR to SSR and TTFB tripled. Users complain the page feels slower to start. What do you do?”

SSR moves work to the server, so TTFB now includes rendering and data fetching. Two fixes: stream — wrap slow regions in <Suspense> and use renderToPipeableStream so the shell flushes immediately; and cache — if the page is not personalised, put it behind a CDN with s-maxage + stale-while-revalidate so most requests never touch the renderer. Also check for a request waterfall in the server data fetching.

Drill 3 — theme flash
“Dark mode is stored in localStorage. Server-rendered pages flash light before switching. Fix it.”

The server cannot read localStorage, so it renders the default theme. Two real fixes: (1) store the preference in a cookie so the server can read it on the request and render the correct class on <html> immediately; or (2) keep localStorage but set the class from a tiny blocking inline script in <head> that runs before first paint, and mark that attribute suppressHydrationWarning. A useEffect fix is too late — it runs after paint, which is exactly the flash.

Drill 4 — where does this code run?
'use client';
import { db } from './db';
export function Panel() { /* ... */ }
Server-only code pulled into the client bundle

This is broken. 'use client' makes the module — and everything it imports — part of the client bundle, so the database module and any secrets it holds get shipped to the browser (and will fail to build or run there). Fetch in a Server Component and pass the data down as serializable props, or expose a Server Action for the mutation.

Drill 5 — SSG or SSR?
“A product page: price and stock change a few times an hour, must rank in Google, gets heavy traffic.”

Static with revalidation (ISR), not per-request SSR. The page is identical for all users, so it is cacheable; a 60-second revalidation window bounds staleness at a cost users never see, and the CDN absorbs the traffic. Render the price server-side so crawlers index it, and if stock must be exact, hydrate a small client component that re-checks it after load — keeping the cacheable shell separate from the personalised or volatile fragment.

Drill 6 — SSR made it slower
“You added SSR to improve performance. LCP improved, but INP got worse and users complain the page is unresponsive at first. Explain.”

Both observations are consistent, and it's the core trade of SSR. Content paints early because the HTML arrives ready, so LCP improves. But the same bundle still downloads and executes, and hydration is roughly a full client render plus matching work against the existing DOM — one long task during which the page looks finished and does nothing. Clicks queue behind it, which is exactly what INP measures. SSR moves the first paint earlier, not the first interaction. The fixes all reduce client JavaScript rather than adding more server work: Suspense boundaries so hydration is selective and out-of-order, moving non-interactive subtrees to Server Components, and code-splitting heavy leaves. I'd confirm with a Performance trace showing the long hydration task around the interaction.

Drill 7 — the cross-user leak
let currentUser = null;
export function setUser(u){ currentUser = u; }
export function getUser(){ return currentUser; }
Module scope is shared across every request on the server

In a browser a module scope is per user — the tab is the user. On a server one process handles thousands of concurrent requests, so this variable is global to all of them. Two requests interleave across an await and one user's page renders another's data. It never reproduces locally because you're the only user; it shows up in production as “a customer saw someone else's account”. Anything request-scoped must be created per request and passed down — props, context, or request-scoped storage. The same trap applies to a query client or cache created once at module scope, which is why those libraries' setup code always looks defensively written.

Drill 8 — the dark mode flash
“Your SSR site flashes light theme before switching to dark, and the console shows a hydration error. Fix it.”

The theme is in localStorage, which the server can't read, so the server renders light and the client renders dark — a genuine divergence, not a React quirk. The fix is to take the decision out of React: a tiny blocking inline script before the app sets data-theme on the html element, so the very first paint is already correct and React's tree is identical on both sides. Better still, store the preference in a cookie — then the server actually knows and there's no flash and no script. You do still put suppressHydrationWarning on the <html> element, because the script adds an attribute the server didn't render — that's what next-themes does and it's the legitimate use of it. What I'd avoid is reaching for it deeper in the tree to paper over a real divergence, or a mounted-flag two-pass, which costs you the server HTML for that subtree.

Drill 9 — pick a strategy
“An e-commerce site: home page, category listings, product pages, cart, and an account area. What renders how?”

Per route, not per app. Home page and any marketing content: static, rebuilt on publish — same for everyone, CDN-served, best possible LCP. Category and product pages: static with revalidation (ISR), or SSR behind an edge cache with s-maxage plus stale-while-revalidate, which is the same thing implemented in cache headers — they're shared across users, must be indexable, and need bounded freshness for price and stock. Cart and account: SSR or a client-rendered shell, marked private so nothing personalised can land in a shared cache — SEO is irrelevant behind a login. The one I'd flag explicitly is stock and price on product pages: if they must be real-time, I'd keep the page cacheable and fetch just those values client-side, rather than making the whole page uncacheable for two numbers.
