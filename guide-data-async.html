00 — The shape of async data

Model the states honestly

Every data-driven view is a small state machine: idle → loading → (success | error), plus refetching. Bugs come from collapsing that into loose booleans that permit impossible combinations. Model it as one value (a discriminated union — see the TypeScript tab), and the UI can't show a spinner and an error at once.

Why booleans rot

The failure is combinatorial, and it's worth being able to say the number out loud. Three booleans — isLoading, error, data — describe 2³ = 8 combinations, of which only about four are meaningful. The other four are states your code can enter but your UI has no rendering for:

// the states nobody designed for
{ loading: true,  error: Error, data: null }   // spinner over an error
{ loading: false, error: null,  data: null }   // blank screen, no explanation
{ loading: true,  error: null,  data: [...] }  // ambiguous: stale or fresh?
{ loading: false, error: Error, data: [...] }  // refetch failed — show old data or the error?

The last two aren't bugs, and that's the point: they're real states you must decide about deliberately. A union forces the decision at the type level rather than leaving it to whichever if happens to run first in the JSX.

type Async<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T; stale: boolean }
  | { status: 'error'; error: Error; lastData?: T };

// the render is now total — every case handled, nothing impossible
switch (s.status) {
  case 'idle':    return null;
  case 'loading': return <Skeleton />;
  case 'success': return <List items={s.data} dimmed={s.stale} />;
  case 'error':   return s.lastData
      ? <List items={s.lastData} banner="Couldn't refresh" />   // keep showing what we had
      : <ErrorState onRetry={retry} />;
}

The two states people forget

  • Empty is not success. A successful response with zero rows is a distinct design problem — “no results for 'xyz', try a broader search” is a different screen from a list. Collapsing them ships the classic bug where a working search looks broken.
  • Refetching is not loading. isLoading should mean “I have nothing to show”; isFetching means “I have something, and I'm checking it”. TanStack Query separates these for exactly this reason. Conflate them and every background refresh flashes a full-page spinner over data the user was reading — the single most common cause of “the app feels janky” complaints that have nothing to do with performance.

Errors aren't one state either

“It failed” is not actionable. In practice you're distinguishing at least four, and each maps to a different UI: network/offline (retry automatically, show a passive banner), 4xx client (don't retry — the request is wrong; 401 means re-authenticate, 403 means show a permission message), 5xx server (retry with backoff, then a real error state), and parse/contract (your assumption about the shape was wrong — log it loudly, because retrying will never help).

Say this“I model async data as one discriminated union rather than three booleans, because booleans allow states we never designed — a spinner over an error, or a blank screen with no explanation. And I keep 'loading' and 'refetching' separate so a background refresh doesn't blow away content the user is reading.”

Promises themselves have their own tab; here the focus is the UI patterns around fetching data.

01 — How to fetch

Data-fetching patterns

  • Fetch-on-render — component mounts, then its effect starts the request. Simple, but causes request waterfalls when nested components each fetch after rendering.
  • Render-as-you-fetch — kick off the request as early as possible (on navigation/event), before or as you render, so data and UI load in parallel.

What a waterfall actually costs

The word “waterfall” undersells it, so do the arithmetic in the room. A page renders <Profile>, which fetches the user; once that resolves it renders <Posts>, which fetches posts; which renders <Comments>. Three sequential round trips. On a good connection at 100ms each that's 300ms — annoying. On mobile at a realistic 150–300ms RTT, it's closer to a second of nothing, and none of it is server time. Fetch them in parallel and the cost is one round trip, not three.

// waterfall: each await blocks the next
const user  = await getUser(id);          // 250ms
const posts = await getPosts(user.id);    // +250ms — needed user.id, unavoidable
const prefs = await getPrefs(id);         // +250ms — did NOT need anything above it

// parallel: only genuinely dependent requests wait
const [user, prefs] = await Promise.all([getUser(id), getPrefs(id)]);  // 250ms
const posts = await getPosts(user.id);                                 // +250ms

The rule to state: a request should only wait on another request if it needs a value from it. Most waterfalls in real apps are accidental — they exist because of where a component sits in the tree, not because of a data dependency. That's the whole argument for route loaders (React Router, Remix, Next.js server components): they hoist fetching to a place that knows what the page needs before the tree renders.

The naive effect, and its pitfalls

useEffect(() => {
  setLoading(true);
  fetch(`/user/${id}`).then(r => r.json())
    .then(setUser).finally(() => setLoading(false));
}, [id]);

This works but has no caching, no de-duplication (two components asking for the same id fetch twice), refetches on every remount, and — critically — a race condition when id changes fast (see §03). Three more sharp edges hide in those five lines:

  • fetch doesn't reject on 404 or 500. It only rejects on network failure. A 500 resolves happily and you call .json() on an HTML error page, producing a confusing parse error instead of a clean “server error”. You must check res.ok yourself — the single most common fetch bug.
  • No error handling at all here. The chain has no .catch, so a failure becomes an unhandled rejection and loading is left true forever — the infinite spinner.
  • StrictMode runs it twice in development. That's deliberate: it's surfacing that the effect isn't cleanup-safe. Don't disable StrictMode to make it stop; fix the cleanup.

This is why teams reach for a server-cache library (TanStack Query, SWR, RTK Query): it keys responses by a query key, dedupes in-flight requests, refetches in the background, retries with backoff, and serves stale-while-revalidate — every one of those a bug class you'd otherwise re-fix per component.

When you don't need the libraryBe ready for the pushback. If the app has three screens and each loads one endpoint once, a query library is ~13KB gzipped and a new mental model to teach for very little. The honest threshold: reach for it when you have shared server data (the same resource read by several screens), background freshness requirements, or mutations that must invalidate other views. If your data is genuinely per-screen and read-once, use() with Suspense, a route loader, or a plain effect with cleanup is a defensible choice — and saying so is a stronger answer than naming a library reflexively.
02 — The distinction that reframes the answer

Server cache is not client state

The most useful idea in this whole area, and the one that most reliably separates a mid from a senior answer: most of what people call “global state” isn't state at all — it's a cached copy of someone else's data. The two behave nothing alike:

Client stateServer cache
Owned byYou. It is the truthThe server. You hold a copy
ExamplesTheme, open modal, form draft, selected tab, cart-before-checkoutUser profile, product list, order history, permissions
Can go staleNo — nothing else can change itYes, the moment after you read it, and you won't be told
NeedsA store, reducers, selectorsKeys, TTLs, revalidation, dedupe, retry, invalidation
TooluseState, Context, Zustand, ReduxTanStack Query, SWR, RTK Query, server components

Putting server data in Redux means hand-writing the entire right-hand column — loading flags, staleness, dedupe, retry, invalidation — as reducers and thunks, per resource. That's what most “our Redux store is enormous and nobody understands it” codebases actually are. Pull the server cache out and the remaining client state is usually small enough that Context or a tiny store handles it comfortably. This is also why Redux Toolkit ships RTK Query: same conclusion, from the Redux team.

Stale-while-revalidate, and why it feels instant

The default behaviour of a query cache: on mount, immediately return the cached value (even if stale) so the screen paints with content, and simultaneously fire a background refetch to correct it. The user sees data in ~0ms instead of a spinner for 300ms, and the correction usually lands before they've finished reading.

Two config values do most of the work, and mixing them up is a common interview stumble:

  • staleTime — how long a cached value is considered fresh. While fresh, mounting a component triggers no network request at all. Defaults to 0, which is why the out-of-the-box experience refetches on every mount and surprises people.
  • gcTime (formerly cacheTime) — how long an unused entry survives in memory after the last component unsubscribes, before it's garbage collected. Default 5 minutes. It controls whether coming back to a screen shows instant stale data or a cold spinner.

So staleTime answers “do I refetch?” and gcTime answers “do I still have anything to show while I do?”. Pick staleTime from how fast the data actually changes: a currency rate 5–30 seconds, a product catalogue minutes, a country list effectively forever.

Cache keys are your dependency array

A query key like ['orders', { status, page }] is doing the same job as a useEffect dependency array, with the same failure mode: omit a variable the request depends on and you serve one filter's data under another filter's key. The user switches to “Cancelled” and sees the open orders, because both wrote to ['orders']. If it's in the URL or the request body, it belongs in the key.

Where the cost landsCaching isn't free either. A long staleTime means a user can act on data that changed minutes ago — fine for a catalogue, dangerous for inventory counts or a balance. Aggressive caching of per-user data is a genuine privacy bug if the cache isn't cleared on logout: the next user on a shared device sees the previous one's orders. Clear the cache on sign-out, and never cache authenticated responses in a shared layer without scoping the key to the user.
03 — The classic bug

Race conditions & cancellation

User types in a search box: request A (“ab”) is slow, request B (“abc”) is fast. B returns first and renders; then A returns and overwrites the newer results with stale data. The last response to arrive wins — but it should be the last one requested.

Say that distinction precisely, because it is the bug: the network gives you completion order and your UI needs request order. Nothing about HTTP guarantees they match — different responses take different paths, hit different cache layers, and vary by payload size. It's also why the bug is so nasty in practice: it's invisible on a fast local connection and reproduces constantly on a train, which makes it a classic “works on my machine” report and a favourite interview question.

Fix 1 — ignore stale responses (cleanup flag)

useEffect(() => {
  let ignore = false;
  fetch(`/search?q=${q}`).then(r => r.json()).then(data => {
    if (!ignore) setResults(data);   // drop superseded responses
  });
  return () => { ignore = true; };    // cleanup runs before the next effect
}, [q]);

When q changes, React runs the previous effect's cleanup before the new effect, flipping the old closure's ignore to true. The stale response still arrives but is dropped. This works precisely because each effect run has its own ignore in its own closure.

Trace it to be sure you can explain it under pressure. Type “ab”: effect run #1 creates ignore₁ = false and starts request A. Type “abc”: React runs cleanup #1, setting ignore₁ = true, then effect run #2 creates a separate ignore₂ = false and starts request B. B resolves, reads ignore₂ — false — and renders. A finally resolves, reads the variable its own closure captured, ignore₁ — now true — and drops silently. Two runs, two variables, no shared mutable flag. If you'd hoisted ignore outside the effect, both closures would share one variable and the fix would break.

Fix 2 — actually cancel (AbortController)

useEffect(() => {
  const ctrl = new AbortController();
  fetch(`/search?q=${q}`, { signal: ctrl.signal })
    .then(r => r.json()).then(setResults)
    .catch(e => { if (e.name !== 'AbortError') throw e; });
  return () => ctrl.abort();          // cancels the in-flight request
}, [q]);

The flag prevents a stale state update; AbortController also stops the wasted network work. Use abort for real cancellation; the ignore flag is the minimal fix.

Three details worth knowing, because they're where this goes wrong:

  • Aborting rejects the promise with an AbortError (a DOMException). If you don't filter it, every keystroke logs an error and a naive .catch(setError) paints an error state on a request you cancelled. Check e.name === 'AbortError' — or signal.aborted — and swallow it.
  • Abort is best-effort on the server. It closes the client's side; the server may well have already run the handler and written to the database. It saves your bandwidth and your parsing, not the server's work. Never rely on it to cancel a side effect.
  • A controller is single-use. Once aborted it stays aborted, so create a new one per request — that's why it lives inside the effect body, not outside. For timeouts, AbortSignal.timeout(5000) and AbortSignal.any([a, b]) compose cleanly with a user-triggered signal.

The version that doesn't involve races at all

Both fixes above are still reactive — you fire a request per keystroke and then discard most of them. For a search box the better answer is usually to fire fewer: debounce the input (~250–300ms of silence before requesting) so you make one request per pause instead of one per character, cutting request volume by roughly 5–10× on a typical query, then still guard the race for the ones you do send. And a query library makes this structural: keying by ['search', q] means an old response can only ever write to its own key, so it can't overwrite the new one. Worth naming — “I'd rather make the race impossible than remember to guard it” is the sort of thing interviewers write down.

Debounce vs throttle — don't blur themDebounce waits for a quiet period and fires once at the end: search-as-you-type, autosave, validation. Throttle fires at most once per interval during continuous activity: scroll, resize, mousemove, dragging. Debouncing a scroll handler means nothing happens until the user stops scrolling — which is exactly wrong for an infinite list.
04 — Perceived speed

Optimistic updates

Update the UI immediately as if the mutation succeeded, then reconcile with the server — rolling back if it fails. It trades a bit of complexity for a UI that feels instant (a “favourite” toggle, adding to a watchlist).

The value is perceptual, and the threshold is well established: interactions under about 100ms feel instantaneous, and past roughly 1 second attention starts to wander. A round trip to a server plus a database write is comfortably in the second range on mobile. Optimistic UI doesn't make the mutation faster — it moves the feedback to the near-instant side of that line while the real work happens behind it.

// TanStack Query optimistic mutation
useMutation({
  mutationFn: toggleFavorite,
  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ['favs'] });
    const prev = queryClient.getQueryData(['favs']);   // snapshot
    queryClient.setQueryData(['favs'], optimistic(prev, id)); // apply now
    return { prev };
  },
  onError: (_e, _id, ctx) => queryClient.setQueryData(['favs'], ctx.prev), // rollback
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['favs'] }),  // reconcile
});

Every line there is load-bearing, and being able to say why is the answer:

  • cancelQueries first — an in-flight refetch started before your optimistic write would land after it, carrying pre-mutation data, and silently undo the update on screen. This is the subtle one, and the reason it's the first line rather than an afterthought.
  • Snapshot before you write — rollback is only possible because you kept the previous value. Returning it as context is what hands it to onError.
  • onSettled invalidates on success and failure — after either outcome, the server is the authority and you re-sync. Your optimistic guess is never allowed to become the permanent truth.

Drift: your guess and the server's answer differ

Rollback handles failure. Drift is the harder case, where the mutation succeeds but not as you predicted. You optimistically show “3 likes”; someone else liked it concurrently and the server says 5. You show the item at the top of the list; the server sorts it third. Neither is an error, so nothing rolls back — the screen is just quietly wrong until something refetches. That's precisely why onSettled reconciles unconditionally rather than only on error.

Related, and worth naming: concurrent mutations. Fire two optimistic toggles quickly and their responses can settle out of order, so the second rollback can restore a snapshot taken before the first. Libraries handle this by tracking mutation order; hand-rolled versions usually don't, which is where “the toggle flips back randomly” bugs come from.

Name the trade-offOptimistic UI improves perceived latency but you must handle rollback and drift — the optimistic value can differ from what the server ultimately stores, so reconcile on settle (refetch/invalidate). Don't use it for operations where showing an unconfirmed result is dangerous (e.g. “order filled”).

Where it's the wrong pattern

The test is: what does the user do differently if the optimistic state is wrong? If a failed “favourite” silently reverts, nobody is harmed — worst case they tap it again. If a trade shows as filled and wasn't, they've made a financial decision on a lie, and a rollback three seconds later doesn't undo it. Same for payments, irreversible deletes, and anything a screenshot might be taken of. Those want a pending state — a disabled button and a spinner that tells the truth — not an optimistic one.

Two more places it fails: when the server is the only thing that can produce the value (an id, a total, an approval decision), because you have nothing honest to guess with; and when rollback would be visually violent — reordering a list, closing a modal, or navigating away, then snapping back. React 19's useOptimistic makes the mechanics cheap for form-shaped mutations, but it doesn't change any of this judgement.

05 — Live data

WebSocket-driven state

Trading UIs stream high-frequency updates (order books, tickers, fills). Patterns that keep this sane:

  • Reducer-merge — apply each incoming delta to local state via a reducer ((book, delta) => merged) so updates are a pure, testable transition rather than scattered setStates.
  • Patch the query cache — for data also fetched over REST, write socket updates into the same cache (queryClient.setQueryData) so the snapshot and the live stream share one source of truth.
  • Coalesce / throttle — batch bursts of messages into one state update per animation frame (or every N ms). A book updating hundreds of times a second must not trigger hundreds of renders.
  • Gap detection & reconnection — one socket is TCP-ordered, so messages never arrive scrambled; the sequence number is there to catch gaps. On reconnect, resync from a REST snapshot, discard buffered events older than its sequence id, then apply deltas contiguously — and back off between attempts.

Why coalescing is not optional, in numbers

The screen physically cannot show you more than 60 updates a second (120 on a ProMotion display). A busy order book pushes 300–1000 messages a second. Render per message and you are asking the main thread to do 5–15× more work than the display can present — every extra render is thrown away before a pixel changes. Worse, each one is a full React render plus reconciliation plus layout, so the main thread saturates, input handlers queue behind it, and the tab becomes unresponsive while the CPU fan spins on work that was never visible.

// buffer messages; flush at most once per frame
const pending = useRef([]);
const frame   = useRef(0);

function onMessage(msg){
  pending.current.push(msg);              // cheap: array push, no render
  if (frame.current) return;              // a flush is already scheduled
  frame.current = requestAnimationFrame(() => {
    const batch = pending.current;
    pending.current = [];
    frame.current  = 0;
    setBook(b => batch.reduce(applyDelta, b));   // ONE render for the whole burst
  });
}

The shape to notice: the socket handler does no React work at all — it appends to a ref, which doesn't trigger a render. Rendering is driven by the display's clock instead of the network's. Under a 500 msg/sec burst this turns ~500 renders/sec into ~60, and the reducer folds the whole batch in one pass, so later deltas for the same price level overwrite earlier ones for free.

Two refinements worth mentioning: for data where only the newest value matters (a ticker price), keep just the last message per key rather than the whole batch — coalescing rather than queueing. And if the tab is backgrounded, requestAnimationFrame stops firing, so your buffer grows unbounded — cap it, or flush on visibilitychange.

Transport choice — say why, not just what

PollingSSEWebSocket
DirectionClient pullsServer → client onlyFull duplex
ProtocolHTTPHTTP (streamed response)Upgraded from HTTP, then its own framing
ReconnectN/AAutomatic, with Last-Event-ID resume built inYou write it — backoff, resync, all of it
InfrastructureWorks everywherePlain HTTP: proxies, CDNs, compression all fineProxies and corporate firewalls sometimes break it
Good forSlow-changing data, simplest thing that worksNotifications, feeds, progress, live prices — one-wayChat, collaboration, order entry — genuinely bidirectional or very high rate

The senior move is to justify the cheapest option that meets the requirement. If updates are one-way and arrive every few seconds, polling with a query library is often correct — it's stateless, cacheable, survives any proxy, needs no reconnection logic, and has no server-side connection to keep alive. If it's one-way but high-frequency, SSE gives you streaming with automatic reconnection and event-id resume for free. Reach for a WebSocket when you actually need to send as well as receive, or when the message rate makes HTTP framing overhead matter. “We used a socket because it's real-time” invites the follow-up “what did it cost you?” — and the answer is: reconnection, resync, heartbeats, backpressure and sticky sessions, all of which you now own.

Reconnection is the part people underestimate

  • Exponential backoff with jitter — 1s, 2s, 4s, 8s, capped at ~30s, each multiplied by a random factor. The jitter matters at scale: without it, a server blip disconnects every client simultaneously and they all retry in lockstep, re-creating the outage at each interval. This is the thundering herd, and randomising the delay is the whole fix.
  • Heartbeats — a dead TCP connection can look perfectly open for minutes; you learn it's gone only when you try to write. Ping every ~30s and treat a missed pong as a disconnect, or you'll display frozen prices as though they were live. Silent staleness is worse than a visible disconnect, so surface a “reconnecting” state in the UI rather than letting the last known values sit there looking current.
  • Snapshot, then replay — on reconnect, buffer incoming deltas, fetch a fresh REST snapshot, discard buffered events at or below the snapshot's sequence id, then apply the rest in order. Applying deltas to a book with a gap in it doesn't error; it silently produces a wrong book, which is the dangerous kind of bug.
  • Backpressure — if you can't keep up, decide deliberately: drop intermediate frames (fine for a price), or slow the producer via a subscription with a lower update rate. Unbounded buffering just converts a CPU problem into a memory problem.
Say this“I treat the socket as a stream of deltas reduced into a single canonical state, batch high-frequency updates into a per-frame render, and on reconnect re-snapshot before replaying — so the UI never renders a partial or stale book.”
06 — Drill until reflex

Scenario drills

Drill 1 — the flickering search
“Search results sometimes show data for a previous query. What's happening and how do you fix it?”

A race: a slower earlier request resolves after a faster later one and overwrites it. Fix by dropping superseded responses — an ignore flag flipped in the effect cleanup, or AbortController to cancel the previous request when the query changes. Abort also saves the wasted network work.

Drill 2 — why does cleanup fix the race?

Each effect run creates its own closure with its own ignore. When the dependency changes, React runs the previous run's cleanup before the next effect, setting that old closure's ignore = true. So when the stale response finally resolves, its if (!ignore) guard is false and it's discarded — only the latest request can write state.

Drill 3 — optimistic rollback
“Walk through an optimistic 'add to watchlist' that can fail.”

On mutate: cancel outstanding refetches, snapshot the current cache, and write the optimistic value so the UI updates instantly. On error: restore the snapshot (rollback). On settle: invalidate/refetch to reconcile with the server's actual state. The snapshot is what makes rollback possible.

Drill 4 — the render storm
“An order-book socket pushes ~300 msgs/sec and the page pins the CPU. What do you do?”

Decouple message rate from render rate: buffer incoming deltas and flush them into one state update per requestAnimationFrame (or every ~16–100ms). Merge deltas with a reducer and virtualize the visible rows. The screen only needs one update per animation frame — ~60/sec, 120 on a ProMotion display — regardless of message volume.

Drill 5 — snapshot on reconnect
“The websocket drops and reconnects. Why not just resume applying deltas?”

You may have missed deltas while disconnected, so replaying from where you left off yields a corrupt book. Re-fetch a fresh REST snapshot, then apply only deltas newer than the snapshot's sequence number, and back off between reconnect attempts to avoid hammering the server.

Drill 6 — the accidental waterfall
“A dashboard takes 1.2s to show anything. The three API calls take 250ms each. Where's the time?”

Three sequential round trips instead of one — a waterfall, probably because each component fetches in its own effect after its parent has rendered, so nothing starts until the one above it finishes. I'd check the Network panel for a staircase pattern. The fix is to only make a request wait when it genuinely needs a value from the previous one: Promise.all the independent ones, or hoist fetching to a route loader / server component that knows what the page needs before the tree renders. 750ms of the 1.2s is queueing, not work.

Drill 7 — is this state?
“Our Redux store has grown to 40 slices and nobody understands it. Where would you start?”

I'd split it by ownership first: which slices are client state we own (theme, modals, form drafts, selections) and which are a cached copy of server data we don't. Usually the large majority is the second kind, and each of those slices is hand-written caching — loading flags, staleness, dedupe, retry, invalidation — re-implemented per resource. Moving those to a query layer (RTK Query keeps the Redux ecosystem, TanStack Query if we're freer) deletes most of that code, and what's left is small enough to be readable. It's a refactor I'd do resource by resource, not in one pass.

Drill 8 — don't be optimistic
“Product wants the 'Place order' button to feel instant. Do you make it optimistic?”

No. The test I use is what the user does differently if the optimistic state turns out to be wrong — for a favourite toggle, nothing; for an order, they act on it financially, and a rollback two seconds later doesn't undo that decision. It's also a case where the server owns values I can't guess: fill price, order id, whether it was even accepted. What I'd do instead is make the pending state feel good — instant button feedback, disabled to prevent double submission, an inline spinner with real status — and spend the effort on making the request genuinely fast. Optimistic UI is for reversible, low-stakes, client-predictable mutations.
