00 — The shape of async data

Model the states honestly

Model async data as one state value, a discriminated union, so the UI can never show two states that contradict each other.

  • Every data-driven view is a small state machine: idle → loading → (success | error), plus refetching.
  • Loose booleans collapse that machine and permit impossible combinations.
  • One value (see the TypeScript tab) means the UI can't show a spinner and an error at once.

Why booleans rot

Three booleans describe eight states, and your UI only designed four of them.

Numbers. The failure is combinatorial, and it's worth saying the number out loud. isLoading, error and data describe 2³ = 8 combinations. Only about four are meaningful. The other four are states your code can enter but your UI has no rendering for:

// the states nobody designed for
{ loading: true,  error: Error, data: null }   // spinner over an error
{ loading: false, error: null,  data: null }   // blank screen, no explanation
{ loading: true,  error: null,  data: [...] }  // ambiguous: stale or fresh?
{ loading: false, error: Error, data: [...] }  // refetch failed — show old data or the error?

Where it bites. The last two aren't bugs, and that's the point. They're real states you must decide about deliberately. A union forces the decision at the type level. Booleans leave it to whichever if happens to run first in the JSX.

type Async<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T; stale: boolean }
  | { status: 'error'; error: Error; lastData?: T };

// the render is now total — every case handled, nothing impossible
switch (s.status) {
  case 'idle':    return null;
  case 'loading': return <Skeleton />;
  case 'success': return <List items={s.data} dimmed={s.stale} />;
  case 'error':   return s.lastData
      ? <List items={s.lastData} banner="Couldn't refresh" />   // keep showing what we had
      : <ErrorState onRetry={retry} />;
}

The two states people forget

Empty and refetching are distinct states, and collapsing either one into its neighbour ships a visible bug.

Empty is not success. A successful response with zero rows is a distinct design problem. “no results for 'xyz', try a broader search” is a different screen from a list. Collapse them and you ship the classic bug where a working search looks broken.

Refetching is not loading. isLoading should mean “I have nothing to show”. isFetching means “I have something, and I'm checking it”. TanStack Query separates these for exactly this reason, and renamed them in v5 to make the split explicit. isPending is “no data yet”, isFetching is “a request is in flight”, and isLoading is now defined as isPending && isFetching: the first load only, never a background refresh.

Where it bites. Conflate them and every background refresh flashes a full-page spinner over data the user was reading. That is the single most common cause of “the app feels janky” complaints that have nothing to do with performance.

Errors aren't one state either

“It failed” is not actionable; in practice you distinguish at least four kinds of error, and each maps to a different UI.

  • Network/offline: retry automatically, show a passive banner.
  • 4xx client: don't retry, the request is wrong. 401 means re-authenticate, 403 means show a permission message.
  • 5xx server: retry with backoff, then a real error state.
  • Parse/contract: your assumption about the shape was wrong. Log it loudly, because retrying will never help.

The trap. The 4xx rule has two exceptions, and an interviewer will name them if you don't. 408 and 429 are retryable. 429 usually carries a Retry-After header, and you should honour it instead of your own backoff.

Say this“I model async data as one discriminated union rather than three booleans, because booleans allow states we never designed — a spinner over an error, or a blank screen with no explanation. And I keep 'loading' and 'refetching' separate so a background refresh doesn't blow away content the user is reading.”

Promises themselves have their own tab; here the focus is the UI patterns around fetching data.

01 — How to fetch

Data-fetching patterns

There are two patterns: fetch after a component renders, or start fetching before it does, and only the second avoids waterfalls.

  • Fetch-on-render: the component mounts, then its effect starts the request. Simple, but nested components each fetch after rendering, which causes request waterfalls.
  • Render-as-you-fetch: kick off the request as early as possible (on navigation or an event), before or as you render, so data and UI load in parallel.

What a waterfall actually costs

A waterfall multiplies the round-trip time by the depth of the tree, and none of that time is server work.

Example. A page renders <Profile>, which fetches the user. Once that resolves it renders <Posts>, which fetches posts. That in turn renders <Comments>. Three sequential round trips.

Numbers. The word “waterfall” undersells it, so do the arithmetic in the room. On a good connection at 100ms each that's 300ms, which is annoying. On mobile at a realistic 150–300ms RTT, it's closer to a second of nothing, and none of it is server time. Fetch them in parallel and the cost is one round trip, not three.

// waterfall: each await blocks the next
const user  = await getUser(id);          // 250ms
const posts = await getPosts(user.id);    // +250ms — needed user.id, unavoidable
const prefs = await getPrefs(id);         // +250ms — did NOT need anything above it

// parallel: only genuinely dependent requests wait
const [user, prefs] = await Promise.all([getUser(id), getPrefs(id)]);  // 250ms
const posts = await getPosts(user.id);                                 // +250ms

The rule to state: a request should only wait on another request if it needs a value from it. Most waterfalls in real apps are accidental. They exist because of where a component sits in the tree, not because of a data dependency.

Why route loaders. That's the whole argument for route loaders (React Router loaders, now on v8, or Next.js server components; Remix was folded into React Router v7 in November 2024). They hoist fetching to a place that knows what the page needs before the tree renders.

The naive effect, and its pitfalls

useEffect(() => {
  setLoading(true);
  fetch(`/user/${id}`).then(r => r.json())
    .then(setUser).finally(() => setLoading(false));
}, [id]);

This works, but it has no caching, no de-duplication, refetches on every remount, and races when id changes fast.

  • No de-duplication: two components asking for the same id fetch twice.
  • No caching: every remount refetches.
  • Critically, a race condition when id changes fast (see §03).

Where it bites. Four more sharp edges hide in those five lines.

fetch doesn't reject on 404 or 500. It only rejects when no response reaches your code at all. A 500 resolves happily, you call .json() on an HTML error page, and you get a confusing parse error instead of a clean “server error”. You must check res.ok yourself; this is the single most common fetch bug. ok is exactly status 200–299. A 304 is not ok, and neither is the opaque redirect (status 0) a browser hands you after redirect: 'manual'.

What does reject. The promise rejects only for a network failure, a CORS failure, a malformed URL or an abort. The first three reject with a TypeError, and a plain abort() with an AbortError. Network and CORS failures even share one message (Chrome's “Failed to fetch”), so the error can't tell you which.

The body is a one-shot stream. res.json() after res.text() throws a TypeError (Node says Body is unusable, Chrome says body stream already read). If you need to log the raw text and parse it, read once as text and JSON.parse, or res.clone() first. A clone buffers whatever the slower branch hasn't read yet, with no limit, so reading only one branch buffers the whole body.

No error handling at all here. The chain has no .catch. A failure becomes an unhandled rejection and loading is left true forever: the infinite spinner.

StrictMode runs it twice in development. That's deliberate. It's surfacing that the effect isn't cleanup-safe. Don't disable StrictMode to make it stop; fix the cleanup.

Three fetch options people are asked about

All three talk to the browser's networking layer, not to your query library.

cache. Talks to the HTTP cache, not to your query library. 'default' obeys Cache-Control. 'no-store' bypasses the cache entirely and doesn't write to it, while 'reload' fetches fresh but updates the cache. 'no-cache' always revalidates with a conditional request. 'force-cache' serves a stale entry if there is one.

The trap. The one people get backwards is 'no-cache'. It still uses the cache; it just checks first.

keepalive: true. Lets the request outlive the page (analytics on unload). The body cap is 64 KiB, shared across all of that document's in-flight keepalive requests (the limit is per fetch group, not per origin). Unlike sendBeacon you get any method, headers and the response.

priority. 'high' | 'low' | 'auto', a hint to the browser's scheduler relative to other fetches. It's the same idea as fetchpriority on images. Use 'low' for prefetches and telemetry so they don't compete with the data the screen is waiting on.

Why the library. This is why teams reach for a server-cache library (TanStack Query, SWR, RTK Query). It keys responses by a query key, dedupes in-flight requests, refetches in the background, retries with backoff, and serves stale-while-revalidate. Every one of those is a bug class you'd otherwise re-fix per component.

Numbers. Know what sits behind “retries with backoff”. TanStack Query retries a failed query 3 times, with min(1000 × 2^attempt, 30000)ms between tries: 1s, 2s, 4s. On the server it retries 0 times. Mutations are not retried by default, because a retried POST can double-submit. SWR's equivalent is exponential backoff from a 5-second errorRetryInterval. The doubling factor is scaled by a random 0.5–1.5 and rounded down, so delays land on whole multiples of 5s and clients don't retry in lockstep. SWR sets no retry cap by default.

When you don't need the libraryBe ready for the pushback. If the app has three screens and each loads one endpoint once, a query library is ~14KB gzipped (@tanstack/react-query 5.x, min+gzip) and a new mental model to teach, for very little. The honest threshold: reach for it when you have shared server data (the same resource read by several screens), background freshness requirements, or mutations that must invalidate other views. If your data is genuinely per-screen and read-once, use() with Suspense, a route loader, or a plain effect with cleanup is a defensible choice. Saying so is a stronger answer than naming a library reflexively.
02 — The distinction that reframes the answer

Server cache is not client state

Most of what people call “global state” isn't state at all; it's a cached copy of someone else's data.

This is the most useful idea in this whole area, and the one that most reliably separates a mid from a senior answer. The two behave nothing alike:

Client stateServer cache
Owned byYou. It is the truthThe server. You hold a copy
ExamplesTheme, open modal, form draft, selected tab, cart-before-checkoutUser profile, product list, order history, permissions
Can go staleNo — nothing else can change itYes, the moment after you read it, and you won't be told
NeedsA store, reducers, selectorsKeys, TTLs, revalidation, dedupe, retry, invalidation
TooluseState, Context, Zustand, ReduxTanStack Query, SWR, RTK Query, server components

Where it bites. Putting server data in Redux means hand-writing the entire right-hand column as reducers and thunks, per resource: loading flags, staleness, dedupe, retry, invalidation. That's what most “our Redux store is enormous and nobody understands it” codebases actually are. Pull the server cache out and the remaining client state is usually small. Context or a tiny store handles it comfortably. This is also why Redux Toolkit ships RTK Query: same conclusion, from the Redux team.

Stale-while-revalidate, and why it feels instant

Stale-while-revalidate returns the cached value now, and corrects it with a background refetch a moment later.

How it works. This is the default behaviour of a query cache. On mount it immediately returns the cached value, even if stale, so the screen paints with content. Simultaneously it fires a background refetch to correct it. The user sees data in ~0ms instead of a spinner for 300ms, and the correction usually lands before they've finished reading.

Where the name comes from. HTTP. Cache-Control: stale-while-revalidate=<seconds> (RFC 5861) tells a CDN to do exactly this: serve the stale copy now, refresh it in the background. The client libraries copy the semantics into memory.

Two more things to quote. Dedupe: two components mounting the same key inside a window share one request. SWR's dedupingInterval is 2000ms; TanStack dedupes any in-flight fetch for the same key. Structural sharing: a refetch that returns identical JSON keeps the old object references, so memoised children don't re-render.

Two config values do most of the work, and mixing them up is a common interview stumble.

staleTime. How long a cached value is considered fresh. While fresh, mounting a component triggers no network request at all. It defaults to 0, which is why the out-of-the-box experience refetches on every mount, window focus and network reconnect (all three are on by default) and surprises people. staleTime: 'static' (added in v5.79, May 2025) means “never refetch automatically”, for genuinely fixed data.

gcTime. How long an unused entry survives in memory after the last component unsubscribes, before it's garbage collected; the default is 5 minutes (Infinity on the server). It controls whether coming back to a screen shows instant stale data or a cold spinner. It was renamed from cacheTime in v5. The React package is still on v5 as of September 2026; only the Svelte adapter has shipped a v6, and the Solid adapter's v6 is still a release candidate.

Say this. staleTime answers “do I refetch?” and gcTime answers “do I still have anything to show while I do?”. Pick staleTime from how fast the data actually changes: a currency rate 5–30 seconds, a product catalogue minutes, a country list effectively forever.

Cache keys are your dependency array

A query key is the request's dependency array: omit a variable the request depends on and you serve one filter's data under another filter's key.

How it works. A key like ['orders', { status, page }] does the same job as a useEffect dependency array, with the same failure mode. If it's in the URL or the request body, it belongs in the key.

Example. The user switches to “Cancelled” and sees the open orders, because both wrote to ['orders'].

The trap. Keys are hashed deterministically. Object property order doesn't matter: { status, page } and { page, status } are the same key, and an undefined property is dropped. But array position does: ['todos', page, status] and ['todos', status, page] are two entries. That's the argument for objects over positional arrays in keys.

Where the cost landsCaching isn't free either. A long staleTime means a user can act on data that changed minutes ago. Fine for a catalogue, dangerous for inventory counts or a balance. Aggressive caching of per-user data is a genuine privacy bug if the cache isn't cleared on logout: the next user on a shared device sees the previous one's orders. Clear the cache on sign-out, and never cache authenticated responses in a shared layer without scoping the key to the user.
03 — The classic bug

Race conditions & cancellation

The race: the network gives you completion order, your UI needs request order, and nothing guarantees they match.

Example. The user types in a search box. Request A (“ab”) is slow, request B (“abc”) is fast. B returns first and renders. Then A returns and overwrites the newer results with stale data. The last response to arrive wins, but it should be the last one requested.

Say this. Say that distinction precisely, because it is the bug: the network gives you completion order and your UI needs request order. Nothing about HTTP guarantees they match. Different responses take different paths, hit different cache layers, and vary by payload size.

Where it bites. It's invisible on a fast local connection and reproduces constantly on a train. That makes it a classic “works on my machine” report and a favourite interview question.

Fix 1 — ignore stale responses (cleanup flag)

useEffect(() => {
  let ignore = false;
  fetch(`/search?q=${q}`).then(r => r.json()).then(data => {
    if (!ignore) setResults(data);   // drop superseded responses
  });
  return () => { ignore = true; };    // cleanup runs before the next effect
}, [q]);

The flag works because each effect run has its own ignore in its own closure, and cleanup flips only the old one.

How it works. When q changes, React runs the previous effect's cleanup before the new effect. That flips the old closure's ignore to true. The stale response still arrives but is dropped.

Trace it, so you can explain it under pressure. Type “ab”: effect run #1 creates ignore₁ = false and starts request A. Type “abc”: React runs cleanup #1, setting ignore₁ = true, then effect run #2 creates a separate ignore₂ = false and starts request B. B resolves, reads ignore₂, finds it false, and renders. A finally resolves, reads the variable its own closure captured, ignore₁, finds it true, and drops silently.

The trap. Two runs, two variables, no shared mutable flag. Moving ignore up into the component body does not break it: a let in the body is a fresh binding on every render, so run #2 closes over a different variable than cleanup #1 flipped. What breaks it is genuinely sharing one flag across runs — a module-level variable, or a ref. And the two break differently: a bare shared flag is never reset, so it stays true after the first cleanup and drops both responses; a ref reset to false at the top of each run is false again by the time A lands, so the stale response wins.

Fix 2 — actually cancel (AbortController)

useEffect(() => {
  const ctrl = new AbortController();
  fetch(`/search?q=${q}`, { signal: ctrl.signal })
    .then(r => r.json()).then(setResults)
    .catch(e => { if (e.name !== 'AbortError') throw e; });
  return () => ctrl.abort();          // cancels the in-flight request
}, [q]);

The flag prevents a stale state update; AbortController also stops the wasted network work.

Use abort for real cancellation; the ignore flag is the minimal fix. Three details are worth knowing, because they're where this goes wrong.

Aborting rejects the promise with an AbortError (a DOMException). If you don't filter it, every keystroke logs an error. A naive .catch(setError) paints an error state on a request you cancelled. Check e.name === 'AbortError', or signal.aborted, and swallow it.

Abort is best-effort on the server. It closes the client's side. The server may well have already run the handler and written to the database. It saves your bandwidth and your parsing, not the server's work. Never rely on it to cancel a side effect.

A controller is single-use. Once aborted it stays aborted, so create a new one per request. That's why it lives inside the effect body, not outside. For timeouts, AbortSignal.timeout(5000) and AbortSignal.any([a, b]) (both Baseline since spring 2024) compose cleanly with a user-triggered signal.

The trap. A timeout rejects with a TimeoutError, not an AbortError, and AbortSignal.any forwards whichever reason fired first. So the e.name !== 'AbortError' filter above lets a timeout through as a real error. That's usually what you want, but only if you meant it.

The version that doesn't involve races at all

Fire fewer requests with a debounce, and key responses so a stale one has nowhere to write.

How it works. Both fixes above are still reactive: you fire a request per keystroke and then discard most of them. For a search box the better answer is usually to fire fewer. Debounce the input (~250–300ms of silence before requesting) so you make one request per pause instead of one per character. A ten-character query typed without pausing is ten requests undebounced and one debounced, so on a typical query that is roughly a 5–10× cut. Then still guard the race for the ones you do send.

Make it structural. A query library keyed by ['search', q] means an old response can only ever write to its own key, so it can't overwrite the new one.

Say this. “I'd rather make the race impossible than remember to guard it” is the sort of thing interviewers write down.

Debounce vs throttle — don't blur themDebounce waits for a quiet period and fires once at the end: search-as-you-type, autosave, validation. Throttle fires at most once per interval during continuous activity: scroll, resize, mousemove, dragging. Debouncing a scroll handler means nothing happens until the user stops scrolling. That is exactly wrong for an infinite list.
04 — Perceived speed

Optimistic updates

An optimistic update shows the result immediately, as if the mutation succeeded, then reconciles with the server and rolls back if it fails.

What it buys. It trades a bit of complexity for a UI that feels instant (a “favourite” toggle, adding to a watchlist). Optimistic UI doesn't make the mutation faster. It moves the feedback to the near-instant side of the line while the real work happens behind it.

Numbers. The value is perceptual, and the threshold is well established (Nielsen's three limits). Under about 100ms feels instantaneous, like directly manipulating the interface. Up to about 1 second the delay is noticeable, but the user's flow of thought stays unbroken. Past roughly 10 seconds attention leaves the task altogether. A round trip to a server plus a database write is comfortably in the second range on mobile.

// TanStack Query optimistic mutation
useMutation({
  mutationFn: toggleFavorite,
  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ['favs'] });
    const prev = queryClient.getQueryData(['favs']);   // snapshot
    queryClient.setQueryData(['favs'], optimistic(prev, id)); // apply now
    return { prev };
  },
  onError: (_e, _id, ctx) => queryClient.setQueryData(['favs'], ctx.prev), // rollback
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['favs'] }),  // reconcile
});

Every line there is load-bearing, and being able to say why is the answer.

cancelQueries first. An in-flight refetch started before your optimistic write would land after it, carrying pre-mutation data, and silently undo the update on screen. This is the subtle one, and the reason it's the first line rather than an afterthought.

Snapshot before you write. Rollback is only possible because you kept the previous value. Returning it as context is what hands it to onError.

onSettled invalidates on success and failure. After either outcome, the server is the authority and you re-sync. Your optimistic guess is never allowed to become the permanent truth.

Drift: your guess and the server's answer differ

Drift is when the mutation succeeds but not as you predicted, so nothing errors, nothing rolls back, and the screen is quietly wrong.

Example. Rollback handles failure; drift is the harder case. You optimistically show “3 likes”; someone else liked it concurrently and the server says 5. You show the item at the top of the list; the server sorts it third. Neither is an error, so nothing rolls back, and the screen is just quietly wrong until something refetches. That's precisely why onSettled reconciles unconditionally rather than only on error.

Concurrent mutations. Related, and worth naming. Fire two optimistic toggles quickly and their responses can settle out of order, so the second rollback can restore a snapshot taken before the first. The library doesn't fix this for you. With two mutations in flight, the first one's onSettled invalidation can refetch and land while the second is still pending, reverting its optimistic write until it too settles.

The fix. The fix the maintainers document (TkDodo's 2025 post on concurrent optimistic updates) is to only invalidate when you're the last one standing: if (queryClient.isMutating({ mutationKey }) === 1) invalidateQueries(...). Key rollback context per mutation rather than sharing one snapshot. Hand-rolled versions rarely do either, which is where “the toggle flips back randomly” bugs come from.

Name the trade-offOptimistic UI improves perceived latency, but you must handle rollback and drift. The optimistic value can differ from what the server ultimately stores, so reconcile on settle (refetch/invalidate). Don't use it for operations where showing an unconfirmed result is dangerous (e.g. “order filled”).

Where it's the wrong pattern

The test: what does the user do differently if the optimistic state is wrong?

Example. If a failed “favourite” silently reverts, nobody is harmed; worst case they tap it again. If a trade shows as filled and wasn't, they've made a financial decision on a lie. A rollback three seconds later doesn't undo it. Same for payments, irreversible deletes, and anything a screenshot might be taken of. Those want a pending state, a disabled button and a spinner that tells the truth, not an optimistic one.

Two more places it fails. When the server is the only thing that can produce the value (an id, a total, an approval decision), because you have nothing honest to guess with. And when rollback would be visually violent: reordering a list, closing a modal, or navigating away, then snapping back. React 19's useOptimistic makes the mechanics cheap for form-shaped mutations, but it doesn't change any of this judgement.

05 — Live data

WebSocket-driven state

Treat the socket as a stream of deltas reduced into one canonical state, rendered on the display's clock rather than the network's.

Trading UIs stream high-frequency updates (order books, tickers, fills). These patterns keep it sane.

Reducer-merge. Apply each incoming delta to local state via a reducer ((book, delta) => merged). Updates become a pure, testable transition rather than scattered setStates.

Patch the query cache. For data also fetched over REST, write socket updates into the same cache (queryClient.setQueryData). The snapshot and the live stream then share one source of truth.

Coalesce / throttle. Batch bursts of messages into one state update per animation frame (or every N ms). A book updating hundreds of times a second must not trigger hundreds of renders.

Gap detection & reconnection. One socket is TCP-ordered, so messages never arrive scrambled; the sequence number is there to catch gaps. On reconnect, resync from a REST snapshot, discard buffered events at or below its sequence id, then apply deltas contiguously. Back off between attempts.

Why coalescing is not optional, in numbers

A 60 Hz display can present at most 60 updates a second and a busy stream sends 300–1000 a second, so rendering per message does work that can never be seen.

Numbers. The screen physically cannot show you more than one update per refresh: 60 a second on a common 60 Hz display, 120 on ProMotion, 144 on many high-refresh monitors. A busy order book pushes 300–1000 messages a second. Render per message at 60 Hz and you are asking the main thread to do 5–17× more work than the display can present. Every extra render is thrown away before a pixel changes.

Where it bites. Each of those renders is a full React render plus reconciliation plus layout. The main thread saturates and input handlers queue behind it. The tab becomes unresponsive while the CPU fan spins on work that was never visible.

// buffer messages; flush at most once per frame
const pending = useRef([]);
const frame   = useRef(0);

function onMessage(msg){
  pending.current.push(msg);              // cheap: array push, no render
  if (frame.current) return;              // a flush is already scheduled
  frame.current = requestAnimationFrame(() => {
    const batch = pending.current;
    pending.current = [];
    frame.current  = 0;
    setBook(b => batch.reduce(applyDelta, b));   // ONE render for the whole burst
  });
}

How it works. The shape to notice: the socket handler does no React work at all. It appends to a ref, which doesn't trigger a render. Rendering is driven by the display's clock instead of the network's. Under a 500 msg/sec burst this turns ~500 renders/sec into ~60 renders/sec. The reducer folds the whole batch in one pass, so later deltas for the same price level overwrite earlier ones for free.

Two refinements. For data where only the newest value matters (a ticker price), keep just the last message per key rather than the whole batch: coalescing rather than queueing. And if the tab is backgrounded, requestAnimationFrame stops firing, so your buffer grows unbounded. Cap it, or flush on visibilitychange.

The senior move is to justify the cheapest option that meets the requirement.

How to choose. If updates are one-way and arrive every few seconds, polling with a query library is often correct. It's stateless, cacheable, survives any proxy, needs no reconnection logic, and has no server-side connection to keep alive. If it's one-way but high-frequency, SSE gives you streaming with automatic reconnection and event-id resume for free. Reach for a WebSocket when you actually need to send as well as receive, or when the message rate makes HTTP framing overhead matter.

What it costs. “We used a socket because it's real-time” invites the follow-up “what did it cost you?”. The answer is reconnection, resync, heartbeats, backpressure and sticky sessions, all of which you now own.

2026 noteWebTransport, multiplexed streams and unreliable datagrams over HTTP/3 (QUIC), became Baseline in March 2026 when Safari 26.4 joined Chrome (97) and Firefox (114). It's the answer to “what would you use for a game or a media stream where a dropped frame shouldn't stall the ones behind it?”. WebSocket is a single ordered stream, so one lost packet head-of-line-blocks everything. For a chat or an order book, ordered delivery is the feature, so WebSocket stays the default. WebSocketStream (Chromium only) is the promise-based variant that gives you real backpressure via the Streams API.

Reconnection is the part people underestimate

Reconnection is really four problems: backoff, liveness, resync and backpressure, and you own all of them.

Exponential backoff with jitter. 1s, 2s, 4s, 8s, capped at ~30s, each multiplied by a random factor. The jitter matters at scale. Without it, a server blip disconnects every client simultaneously and they all retry in lockstep, re-creating the outage at each interval. This is the thundering herd, and randomising the delay is the whole fix.

Heartbeats. A dead TCP connection can look perfectly open for minutes; you learn it's gone only when you try to write. Ping every ~30s and treat a missed pong as a disconnect, or you'll display frozen prices as though they were live. Silent staleness is worse than a visible disconnect. Surface a “reconnecting” state in the UI rather than letting the last known values sit there looking current.

Snapshot, then replay. On reconnect, buffer incoming deltas, fetch a fresh REST snapshot, discard buffered events at or below the snapshot's sequence id, then apply the rest in order. Applying deltas to a book with a gap in it doesn't error. It silently produces a wrong book, which is the dangerous kind of bug.

Backpressure. If you can't keep up, decide deliberately: drop intermediate frames (fine for a price), or slow the producer via a subscription with a lower update rate. Unbounded buffering just converts a CPU problem into a memory problem.

Say this“I treat the socket as a stream of deltas reduced into a single canonical state, batch high-frequency updates into a per-frame render, and on reconnect re-snapshot before replaying — so the UI never renders a partial or stale book.”
06 — Drill until reflex

Scenario drills

Drill 1 — the flickering search
“Search results sometimes show data for a previous query. What's happening and how do you fix it?”

A race: a slower earlier request resolves after a faster later one and overwrites it. Fix by dropping superseded responses — an ignore flag flipped in the effect cleanup, or AbortController to cancel the previous request when the query changes. Abort also saves the wasted network work.

Drill 2 — why does cleanup fix the race?

Each effect run creates its own closure with its own ignore. When the dependency changes, React runs the previous run's cleanup before the next effect, setting that old closure's ignore = true. So when the stale response finally resolves, its if (!ignore) guard is false and it's discarded — only the latest request can write state.

Drill 3 — optimistic rollback
“Walk through an optimistic 'add to watchlist' that can fail.”

On mutate: cancel outstanding refetches, snapshot the current cache, and write the optimistic value so the UI updates instantly. On error: restore the snapshot (rollback). On settle: invalidate/refetch to reconcile with the server's actual state. The snapshot is what makes rollback possible.

Drill 4 — the render storm
“An order-book socket pushes ~300 msgs/sec and the page pins the CPU. What do you do?”

Decouple message rate from render rate: buffer incoming deltas and flush them into one state update per requestAnimationFrame (or every ~16–100ms). Merge deltas with a reducer and virtualize the visible rows. The screen only needs one update per animation frame — ~60/sec, 120 on a ProMotion display — regardless of message volume.

Drill 5 — snapshot on reconnect
“The websocket drops and reconnects. Why not just resume applying deltas?”

You may have missed deltas while disconnected, so replaying from where you left off yields a corrupt book. Re-fetch a fresh REST snapshot, then apply only deltas newer than the snapshot's sequence number, and back off between reconnect attempts to avoid hammering the server.

Drill 6 — the accidental waterfall
“A dashboard takes 1.2s to show anything. The three API calls take 250ms each. Where's the time?”

Three sequential round trips instead of one — a waterfall, probably because each component fetches in its own effect after its parent has rendered, so nothing starts until the one above it finishes. I'd check the Network panel for a staircase pattern. The fix is to only make a request wait when it genuinely needs a value from the previous one: Promise.all the independent ones, or hoist fetching to a route loader / server component that knows what the page needs before the tree renders. 500ms of that 750ms is waiting on the previous call, not work — done in parallel it's 250ms, and the remaining ~450ms of the 1.2s is render and bundle, which is a separate investigation.

Drill 7 — is this state?
“Our Redux store has grown to 40 slices and nobody understands it. Where would you start?”

I'd split it by ownership first: which slices are client state we own (theme, modals, form drafts, selections) and which are a cached copy of server data we don't. Usually the large majority is the second kind, and each of those slices is hand-written caching — loading flags, staleness, dedupe, retry, invalidation — re-implemented per resource. Moving those to a query layer (RTK Query keeps the Redux ecosystem, TanStack Query if we're freer) deletes most of that code, and what's left is small enough to be readable. It's a refactor I'd do resource by resource, not in one pass.

Drill 8 — don't be optimistic
“Product wants the 'Place order' button to feel instant. Do you make it optimistic?”

No. The test I use is what the user does differently if the optimistic state turns out to be wrong — for a favourite toggle, nothing; for an order, they act on it financially, and a rollback two seconds later doesn't undo that decision. It's also a case where the server owns values I can't guess: fill price, order id, whether it was even accepted. What I'd do instead is make the pending state feel good — instant button feedback, disabled to prevent double submission, an inline spinner with real status — and spend the effort on making the request genuinely fast. Optimistic UI is for reversible, low-stakes, client-predictable mutations.
