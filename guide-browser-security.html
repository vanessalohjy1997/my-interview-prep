00 — What this covers

Events, rendering, and trust

HTTP methods, status codes, caching, CORS and TLS have their own tab in this deck. This guide covers the DOM event model, a brief note on how the browser paints, and the web-security essentials that matter double for a product handling money: XSS, CSRF, and safe token storage.

01 — One listener, many targets

Event delegation

The three phases

A dispatched event travels: capture (root → target), target, then bubble (target → root). Handlers run on the bubble phase by default; pass { capture: true } to listen on the way down. Most events bubble — a few don't (focus, blur, mouseenter).

APIDoes
event.stopPropagation()stops the event travelling further up/down — other elements' handlers won't see it
event.preventDefault()cancels the browser's default action (form submit, link navigation) — propagation continues
event.targetthe element the event originated on
event.currentTargetthe element whose listener is currently running

Delegation

// one listener on the parent handles all rows, incl. future ones
list.addEventListener('click', (e) => {
  const row = e.target.closest('[data-id]');
  if (row) select(row.dataset.id);
});

Because events bubble, you attach a single listener on a stable ancestor and read e.target (often with .closest()) to find what was clicked. Benefits: one listener instead of thousands, it works for dynamically added children automatically, and it uses far less memory. React uses exactly this idea — it attaches delegated listeners at the root and gives you a synthetic event.

02 — Briefly

How the DOM becomes pixels

HTML → DOM and CSS → CSSOM combine into a render tree, which is laid out (geometry), painted (pixels), and composited (GPU layers). CSS is render-blocking; transform/opacity can animate without layout/paint. Full detail lives in the Performance tab — worth cross-referencing when an interviewer bridges “rendering” and “performance.”

03 — The one that undoes everything else

XSS, in depth

An attacker gets their JavaScript to run in your origin, where it can read the DOM, non-HttpOnly cookies and localStorage, call your API with the user's session, and rewrite the page. On a trading frontend that means reading positions and placing orders as the user — which is why XSS outranks everything else in this guide.

The three types — by where the payload lives

TypeWhere the payload livesTypical shape
StoredYour database — served to every viewera malicious chat message, display name, or instrument note
ReflectedThe request — echoed straight back in the response/search?q=<payload> rendered into the results heading
DOM-basedNowhere on the server — client code reads a source and writes a sinkel.innerHTML = location.hash.slice(1)

DOM-based XSS is the frontend-owned one. The server response is identical for every user and a server-side scanner sees nothing; the whole bug lives in your bundle. That's the type an interviewer expects a senior frontend engineer to reason about unprompted.

Sources and sinks

A DOM XSS is a source (attacker-controlled input) reaching a sink (an API that turns strings into code or markup). Learn the sinks; the sources are just “anything from the URL, the network, or another window”.

The safe counterparts are boring on purpose: textContent, setAttribute with a validated value, createElement + append, and in React just {value}.

A bare <script> inserted via innerHTML is parsed but not executed — which is exactly why real payloads use event-handler attributes instead. The inspector flags both.

Sanitizing, when you must render HTML

Rich text from users has to become markup somewhere. The rules:

  • Allowlist, never denylist. Stripping <script> and onerror is a game you lose; permit a known set of tags and attributes and drop everything else.
  • Use a maintained library — DOMPurify is the default answer. Sanitize as late as possible, ideally at render, because sanitizing on write and storing the result means a future parser bug reopens every stored record.
  • Watch mutation XSS (mXSS). Markup that is inert when sanitized can become live after the browser re-parses it — innerHTML round-trips normalise the DOM and can resurrect a payload. It's the reason to sanitize with a real parser rather than regexes, and to keep the library current.
  • Trusted Types (require-trusted-types-for 'script') makes this structural on Chromium: assigning a plain string to innerHTML throws, so every write must pass through a policy you wrote. It converts DOM XSS from a code-review problem into a runtime guarantee.
// the shape of a Trusted Types policy
const policy = trustedTypes.createPolicy('app-html', {
  createHTML: (s) => DOMPurify.sanitize(s, { RETURN_TRUSTED_TYPE: false })
});
el.innerHTML = policy.createHTML(userMarkup);   // the only way through

Why escaping is contextual — the rule underneath all of it

The single most useful idea in XSS defence, and the one that explains why “we escape user input” is not an answer: escaping is a function of where the value lands, not of the value itself. The same string is safe in one context and executable in another, so escaping happens at the point of output, in the encoding that context requires.

// the same value, four contexts, four different escapes
<div>{value}</div>                    // HTML body → HTML entity encoding
<div title="{value}">                  // attribute → entity encoding + always quote
<script>var x = "{value}"</script>     // JS context → needs JS encoding, not HTML
<a href="{value}">                     // URL context → scheme allowlist; javascript: is live here

That last one is the classic React-specific hole: JSX escapes everything it renders as text, so {userInput} in a body is safe by construction — but href={userInput} is not, because javascript:alert(1) is a perfectly valid URL. React 16.9 and later log a warning but still render it; React 19 throws outright. The rule is to validate the scheme against an allowlist (https:, mailto:) rather than to escape characters.

Which is why input sanitisation is the wrong layer: at input time you don't know where the value will end up, and stripping characters corrupts legitimate data (O'Brien, 3 < 5, a password containing <). Validate input for shape, escape output for context.

The React-specific sinks worth namingJSX makes the common case safe, so interviewers probe the escapes: dangerouslySetInnerHTML (the obvious one — the name is the warning), href/src with a user-controlled scheme, ref callbacks doing manual DOM writes, a third-party component that renders HTML for you, and server-side JSON.stringify embedded in a <script> tag — where a string containing </script> breaks out of the block. That last one is the SSR state-injection bug the SSR guide flags from the other direction.
04 — Riding the user's session

CSRF

A malicious site causes the victim's browser to send an authenticated request to your site, relying on cookies being attached automatically. The attacker cannot read the response — the same-origin policy still holds — they just trigger the side effect. Which is plenty when the side effect is “transfer funds”.

// evil.com — no user interaction beyond visiting the page
<form action="https://bank.example/transfer" method="POST" id="f">
  <input name="to"     value="attacker">
  <input name="amount" value="10000">
</form>
<script>f.submit()</script>   // the browser attaches bank.example's cookies
  • Anti-CSRF tokens — the primary defense. A server-validated token a cross-site attacker can't read (same-origin policy): a synchronizer token if you're stateful, a signed double-submit cookie if not.
  • SameSite cookies — defense in depth, not the whole answer. Strict blocks the cookie on all cross-site requests; Lax blocks cross-site subrequests and form POSTs but still sends on top-level GET navigations. Three caveats interviewers probe: only Chromium defaults to Lax (Firefox and Safari don't); that implicit default still allows cross-site POSTs for cookies under ~2 minutes old; and SameSite is scoped to the site, so any sibling subdomain counts as same-site.
  • Verify Origin / Sec-Fetch-Site on every state-changing request (Referer as the legacy fallback). Sec-Fetch-Site: cross-site on a POST is a straightforward reject.
  • Never let GET change state. A state-changing GET is reachable from an <img src> and slips past SameSite=Lax on a top-level navigation.
Why a JSON API is partly self-defendingA cross-origin fetch with Content-Type: application/json or a custom header like X-Requested-With is not a “simple request”, so the browser sends a preflight first — and your server simply doesn't approve it. An HTML form can't produce those headers (it's limited to three Content-Type values), so form-based CSRF dies. It is not sufficient on its own: reject requests whose body parses as JSON but arrived as text/plain, and keep the token or Origin check.
Two traps in the double-submit pattern(1) An unsigned double-submit cookie fails if any subdomain — or a subdomain takeover — can set cookies on the parent domain, because the attacker then controls both halves of the comparison. Sign or HMAC the token to the session. (2) CORS is not a CSRF defense. A restrictive Access-Control-Allow-Origin stops the attacker reading the response; the request still arrives and still executes.
Login CSRFThe overlooked variant: the attacker forges a login as their own account, so the victim then shops, saves a card, or places orders inside the attacker's session — and the attacker reads the history later. Protect the login form with a CSRF token too, and regenerate the session id on authentication.
05 — The rest of the surface

The attack catalogue

XSS and CSRF are the two you must know cold. These are the ones that separate “revised the checklist” from “has shipped a frontend that holds money”. Each has a shape and a fix.

UI redressing

Clickjacking

The attacker loads your page in a transparent <iframe> stacked under bait — a game, a “play” button, a cookie banner. The victim thinks they're clicking the bait; the click lands on your Confirm order button, inside their authenticated session. Nothing is injected and nothing is read: the attacker borrows a real click.

Variants: likejacking (social widgets), cursorjacking (a fake cursor drawn offset from the real one), and drag-and-drop tricks that pull text out of a framed document.

FixSend Content-Security-Policy: frame-ancestors 'none' (or an explicit allowlist), which supersedes the legacy X-Frame-Options: DENY — send both while you still support old browsers. For genuinely embeddable widgets, require an explicit gesture inside your own UI rather than a single click, and never rely on JavaScript frame-busting: sandbox on the attacker's iframe disables it.
Window handle leak

Reverse tabnabbing

A link with target="_blank" hands the opened page a window.opener reference. The new tab can then set opener.location and silently replace your tab with a pixel-perfect fake login while the user reads the page they clicked through to. They tab back, see your domain's layout, and type their password.

// on the page the user opened, in a different origin
if (window.opener) window.opener.location = 'https://bank-example.evil/login';
Fixrel="noopener noreferrer" on every outbound target="_blank". Modern browsers imply noopener, but be explicit — user-generated links, markdown renderers and older webviews all still need it, and noreferrer additionally stops leaking the URL the user came from.
Trust transfer

Open redirect

Any endpoint that takes a destination from the URL and navigates to it — /login?next=…, /logout?return=…, /out?url=…. The link the victim sees really is your domain, so it survives an eyeball check and a mail filter, and hands the attacker your reputation. It is also the standard escalation step for stealing OAuth codes: a redirect URI you accept becomes the attacker's collection point.

// all of these escape a naive "must start with /" check
/login?next=//evil.com          // protocol-relative → https://evil.com
/login?next=/\evil.com          // backslash, normalised by some parsers
/login?next=https://evil.com
FixDon't reflect URLs. Store the destination server-side against the session, or accept only a path and rebuild the URL yourself: const u = new URL(next, location.origin); if (u.origin !== location.origin) reject(); — and allowlist the paths you actually redirect to.
JavaScript-specific

Prototype pollution

A recursive merge, a query-string parser or a deep-clone that copies a __proto__ or constructor.prototype key writes onto Object.prototype. Every object in the process suddenly inherits the attacker's property. On its own that's a weird bug; combined with a gadget — some library that reads an option it assumes is undefined — it becomes DOM XSS or a bypassed access check.

merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
({}).isAdmin;                // true — everywhere in the app

// the gadget: a template library reading a config it never set
({}).innerHTML;              // now attacker-controlled
FixReject the keys __proto__, constructor and prototype at the parse boundary; build lookup objects with Object.create(null) or a Map; prefer structuredClone and well-audited merge utilities over hand-rolled recursion; and Object.freeze(Object.prototype) in the app entry point is a cheap, surprisingly compatible backstop.
No script required

DOM clobbering

Named HTML elements become properties of window and document. Injected markup with an id or name can therefore overwrite a global your code reads — with no JavaScript at all, so it sails through sanitizers that only strip scripts and event handlers.

// injected as ordinary, script-free markup
<a id="config" href="https://evil.com/x"></a>

// your code, which assumed config came from your own bundle
const url = window.config || DEFAULT;   // now the <a> element
script.src = url;                        // stringifies to the attacker's URL
FixDeclare globals so they can't be clobbered (const/let at module scope, never implicit window properties), check types before use, strip id and name in your sanitizer config, and namespace anything that must be global under a single frozen object.
Cross-window

postMessage abuse

Two mistakes, both common in embed and SSO code. Sending with a wildcard target — iframe.postMessage(token, '*') — delivers your data to whatever origin currently occupies that frame, which the attacker may control by navigating it. Receiving without checking event.origin means any page that can get a handle on your window can drive your message handler, and handlers routinely do privileged things like “set the auth token” or “navigate”.

window.addEventListener('message', (e) => {
  if (e.origin !== 'https://trusted.example') return;   // never optional
  if (e.source !== expectedFrame.contentWindow) return;   // belt and braces
  const msg = JSON.parse(e.data);                          // validate the shape too
});
FixAlways pass an explicit target origin when sending, always compare event.origin against an allowlist when receiving, validate the payload schema, and treat the message handler as a public API — because it is.
Server config, frontend consequence

CORS misconfiguration

CORS relaxes the same-origin policy; it never tightens it. The classic hole is reflecting the request's Origin header into Access-Control-Allow-Origin together with Access-Control-Allow-Credentials: true — that combination lets any site read authenticated responses from your API. Related mistakes: trusting a suffix match (evil-yourdomain.com passes endsWith('yourdomain.com')), and allowing the null origin, which sandboxed iframes and data: URLs can produce.

FixAn explicit allowlist of exact origins, echoed only on a match, plus Vary: Origin so a cache never serves one origin's ACAO header to another. Wildcard * is fine only for genuinely public, unauthenticated data — the browser already refuses to combine it with credentials.
Third-party code

Supply chain & script skimming

Every <script src> you include runs with your origin's full authority — your analytics vendor can read the DOM of a payment form as easily as your own code can. Compromise arrives through a hijacked npm package (typosquatting, a maintainer account takeover, a malicious postinstall, dependency confusion against a private scope) or through a CDN or tag manager serving altered JavaScript. The payment-page variant, quietly exfiltrating card fields, is the Magecart pattern.

// pin the exact bytes you audited
<script src="https://cdn.example/lib.js"
        integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
        crossorigin="anonymous"></script>
FixSubresource Integrity on every third-party script, a committed lockfile with npm ci, --ignore-scripts in CI, automated dependency review, and a CSP allowlist so an injected script from an unexpected host can't load at all. For payment fields specifically, isolate them in a provider-hosted iframe so your origin never touches the card number — that is the actual reason Stripe Elements is an iframe.

Client-side checks make the happy path pleasant; the server is where the rule is actually enforced, and saying so unprompted is usually what the question was testing.
06 — Defense in depth

Headers & CSP

Headers don't fix bugs; they cap the blast radius of the bug you haven't found. Knowing which header stops which attack is a high-signal, easy-to-verify thing to have memorised.

HeaderStops
Content-Security-Policyinjected/unauthorised script, and with frame-ancestors, clickjacking

X-Content-Type-Options: nosniffMIME sniffing an upload into executable HTML/JS
Referrer-Policyleaking paths, ids and tokens in the Referer of outbound requests
Permissions-Policythird-party frames reaching camera, mic, geolocation, payment
Cross-Origin-Opener-Policycross-window references — severs window.opener entirely
Cross-Origin-Resource-Policyother origins embedding your resources (an XS-Leak primitive)
Cache-Control: no-storeauthenticated pages persisting in a shared or browser cache

A CSP that actually holds

Host allowlists are the trap: Google's 2016 survey (Weichselbaum et al., CCS) found 75.8% of distinct policies used script allowlists an attacker could bypass — usually through a JSONP endpoint or an open redirect on an allowlisted CDN — and 94.7% of policies attempting to restrict script execution were ineffective overall. The modern shape is nonce-based:

Content-Security-Policy:
  script-src 'nonce-{random-per-response}' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  require-trusted-types-for 'script';
  • A fresh nonce per response, on every <script> tag you emit. Reusing one across responses defeats the point.
  • 'strict-dynamic' lets a trusted script load the scripts it needs, so bundlers and third-party loaders keep working without an allowlist.
  • object-src 'none' kills the plugin bypass; base-uri 'none' stops an injected <base> tag redirecting every relative script URL.
  • No 'unsafe-inline', no 'unsafe-eval' — and note that a nonce makes browsers ignore 'unsafe-inline', which is the compatibility trick for old clients.
  • Roll out with Content-Security-Policy-Report-Only plus a report-to endpoint, read the violations for a week, then enforce. Shipping a strict CSP blind breaks production.
Say this about CSP“It's a second line, not the first. Escaping and sanitizing prevent the injection; CSP is what limits the damage when one gets through. I'd deploy it nonce-based with strict-dynamic, report-only first, and treat unsafe-inline as a bug to burn down rather than a setting.”

What a CSP costs, and where it doesn't help

Worth stating so the answer isn't one-sided. A nonce-based policy requires the HTML to be generated per request — a fresh random value on every response — which means a fully static, CDN-cached page cannot use nonces without edge-side injection. That is a genuine architectural constraint, and the reason many static sites end up with a hash-based policy instead (hashes work for a fixed set of inline scripts and break the moment anything is dynamic).

The other costs: inline event handlers and inline styles have to go, which is a real migration in an older codebase; third-party tag managers frequently inject scripts in ways a strict policy blocks, so marketing will find out before you do; and violation reports from browser extensions produce constant noise you have to learn to filter. None of that is an argument against a CSP — it's the reason report-only mode exists and why a week of real traffic before enforcing is not optional.

And be clear about the limit: a CSP does not stop the injection, it stops the payload from doing anything useful. An injected string still lands in your page. If the payload's goal is defacement, a phishing form rendered in your origin, or exfiltration through a channel your policy permits (an allowlisted image host, a DNS prefetch), a CSP may not stop it at all. It raises the cost of exploitation; it does not make the bug not-a-bug.

07 — Where to keep a token

Storage & token trade-offs

Capacity~4KB~5–10MB~5MB
Sent with requestsYes, automaticallyNoNo

LifetimeExpiry / sessionUntil clearedPer tab, until close

The classic auth-token question is a trade-off, not a “correct answer”:

  • HttpOnly cookie — JavaScript can't read it, so an XSS can't steal it. But it's sent automatically, so you need CSRF defenses (SameSite, tokens).
  • localStorage — no CSRF (not auto-sent), but any XSS can read it and exfiltrate the token. It's also readable by any script on the page.
The senior answer“Prefer a short-lived access token in a __Host--prefixed, HttpOnly, Secure, SameSite=Lax cookie with a refresh token, plus CSRF protection — so XSS can't read the token, though it can still ride the session and call your API as the user. (If you ever need SameSite=None for a cross-site embed, Secure is mandatory — browsers reject it otherwise.) Whatever you choose, XSS is the root risk: if an attacker runs script in your origin, most token schemes fall. So escaping/CSP come first.”
08 — Getting the token in the first place

OAuth in the browser & PKCE

The previous section asks where you keep a token. This one asks how it reached the browser safely. A single-page app is a public client: everything it ships is readable, so it cannot hold a client secret, and the flow has to stay secure without one. That constraint is the whole reason PKCE exists.

Why the implicit flow died

The original SPA answer was the implicit flow: the authorization server redirected back with the access token directly in the URL fragment. Every problem with it is a leak:

  • The token is in a URL — so it lands in browser history, in the Referer of the next outbound request, in any analytics that records location.href, and in server logs if a redirect ever turns the fragment into a query.
  • No way to authenticate the client, so the server cannot tell your app from a copy of it.
  • No refresh token in practice, which pushed apps toward long-lived access tokens — exactly the wrong direction.

The replacement is the authorization code flow, which returns a short-lived, single-use code in the redirect and exchanges it for tokens over a back-channel POST. But a confidential client proves it owns that code with its client secret, and an SPA has no secret — which leaves the code interception attack.

The attack PKCE actually stops

The authorization code travels through the least trustworthy leg of the flow: a redirect, through the user agent. If an attacker can observe that redirect — a malicious app registered on the same custom URL scheme on mobile, a compromised browser extension, a proxy, an open redirect on your own domain that forwards the query string — they can steal the code and redeem it themselves. Without a secret, the token endpoint has no way to tell them apart from you.

Name it preciselyPKCE (RFC 7636, “pixie” — Proof Key for Code Exchange) defends against authorization code interception. It is not a CSRF defense, and it does not protect the token once you hold it. Saying “PKCE replaces the client secret with a per-request one” is the one-line version that lands.

How it works

The client invents a fresh secret per authorization request, commits to it with a hash up front, then reveals it at redemption. The commitment travels through the untrusted redirect; the secret itself never does.

  • 1. Generate a code_verifier — 43–128 characters of cryptographically random [A-Za-z0-9-._~]. Keep it in the tab.
  • 2. Derive the code_challenge — BASE64URL(SHA-256(verifier)), sent on the /authorize redirect along with code_challenge_method=S256. The server stores it against the code it issues.
  • 3. Redeem — POST /token with the code and the raw code_verifier. The server hashes the verifier and compares it to the challenge it stored.
  • 4. Mismatch or missing verifier → rejected. An attacker holding a stolen code has the challenge (it was in the URL) but not the pre-image, and SHA-256 is one-way.
// the whole client side of PKCE, in the platform crypto API
const rnd = crypto.getRandomValues(new Uint8Array(32));
const b64url = (buf) => btoa(String.fromCharCode(...new Uint8Array(buf)))
  .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');

const verifier  = b64url(rnd);                     // 43 chars, keep it
const digest    = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
const challenge = b64url(digest);                  // send this

sessionStorage.setItem('pkce_verifier', verifier); // per tab, deleted after exchange
location.assign(`${AUTH}/authorize?${new URLSearchParams({
  response_type: 'code', client_id: CLIENT_ID, redirect_uri: REDIRECT,
  scope: 'openid profile', state: b64url(crypto.getRandomValues(new Uint8Array(16))),
  code_challenge: challenge, code_challenge_method: 'S256',
})}`);
Why S256 and not plainThe spec also defines code_challenge_method=plain, where the challenge is the verifier. That is worthless against the exact attacker PKCE assumes — whoever intercepts the redirect reads the verifier straight out of it. plain exists only for clients that genuinely cannot compute SHA-256; every browser can. Servers should reject plain, and a client must refuse to downgrade if the server pretends not to support S256.

state vs PKCE vs nonce — three different jobs

This is the trap question, because all three are random values you attach to the same redirect. They defend against different things and none substitutes for another:

ParameterStopsChecked by
code_verifier / PKCEAuthorization code interception — someone else redeeming your codeThe authorization server, at /token
stateCSRF on the callback — an attacker feeding you their code so you end up logged into their accountYour client, on the redirect back
nonce (OIDC)ID token replay — an older or borrowed ID token injected into your sessionYour client, inside the ID token claims

PKCE does incidentally break the classic code-injection variant of login CSRF — the injected code fails the verifier check — which is why some servers now treat state as optional. Send it anyway: it is one line, it is the only thing that survives if PKCE is misconfigured, and it is where you round-trip the “return to this page after login” value.

Getting the details right

  • One verifier per authorization request, freshly random, from crypto.getRandomValues — never Math.random(), which is not cryptographic and is predictable from a few outputs.
  • sessionStorage, then delete it right after the exchange. It is per-tab, so two parallel logins do not overwrite each other, and it dies with the tab. A verifier left behind is a live credential for a code that has not been redeemed.
  • Exact redirect URI matching on the server — no wildcards, no prefix matching. Combined with an open redirect on an allowed URI, loose matching hands the code to the attacker, which is precisely the escalation in the attack catalogue.
  • The code is single-use and short-lived (seconds, not minutes). A server seeing a code redeemed twice should revoke the tokens it already issued for it.
  • Refresh tokens for a public client must rotate, with reuse detection: replaying an old refresh token kills the whole chain. A non-rotating refresh token in a browser is a long-lived bearer credential.
  • Handle the callback then clean the URL — history.replaceState the code and state out before anything else can read location.href.
Where PKCE stops helpingPKCE secures the exchange. It does nothing about what happens next: if the resulting access token sits in localStorage, one XSS still exfiltrates it, and the attacker can even run the whole PKCE dance invisibly in your origin against a still-valid session cookie at the authorization server. That is the argument for the BFF pattern — a thin server-side component does the code exchange, holds the tokens, and hands the browser only an HttpOnly, Secure, SameSite session cookie. Browser-based apps that keep tokens in JS are accepting XSS as a total-compromise risk.
Say this“An SPA is a public client, so the implicit flow is out — tokens in URLs leak through history and referrers. I'd use authorization code with PKCE: a random code_verifier per request, S256 challenge on the /authorize redirect, verifier on the token exchange, so a stolen code is useless without the pre-image. state still goes on for callback CSRF, and a nonce if we're using OIDC. PKCE is mandatory for every client in OAuth 2.1, including confidential ones, because a leaked secret alone no longer redeems a code. And if I can put a BFF in front of it I will, so the tokens never touch JavaScript at all.”
09 — Drill until reflex

Scenario drills

Drill 1 — target vs currentTarget
ul.addEventListener('click', (e) => {
  console.log(e.target.tagName, e.currentTarget.tagName);
});
// user clicks a <span> inside an <li> inside the <ul>
SPAN UL

target is where the event originated (the span the user actually clicked); currentTarget is the element whose listener is running (the ul). Delegation uses this: one listener on the ul, target.closest() to find the row.

Drill 2 — stopPropagation vs preventDefault
“A link inside a clickable card navigates AND triggers the card's onClick. How do you stop only the navigation? Only the card handler?”

To stop navigation, call preventDefault() on the link's click (cancels the default action, propagation still happens). To stop the card's handler from also firing, call stopPropagation() (halts bubbling). They're independent: one cancels the browser default, the other stops the event travelling.

Drill 3 — spot the XSS
<div dangerouslySetInnerHTML={{ __html: comment }} />
Stored XSS if comment is user-supplied

This bypasses React's auto-escaping and injects raw HTML — a malicious comment can include an event-handler payload such as <img src=x onerror=...> that runs in your origin (a bare <script> inserted this way isn't executed, but onerror/onload attributes are). Render it as text ({comment}) if possible, or sanitize with DOMPurify before setting it, and add a CSP.

Drill 4 — cookie or localStorage?
“Where do you store the auth token for a trading app, and why?”

Prefer a short-lived access token in an HttpOnly, Secure, SameSite cookie (plus a refresh token) so JavaScript — and therefore any XSS — can't read it; add CSRF protection because cookies are auto-sent. localStorage avoids CSRF but is readable by any script, so one XSS leaks it. Either way, XSS is the root risk, so output escaping and a CSP come first.

Drill 5 — XSS vs CSRF in one line

XSS = the attacker runs their script in your origin (mitigate with escaping/CSP/sanitization). CSRF = the attacker makes the victim's browser send an authenticated request using auto-sent cookies, without reading the response (mitigate with SameSite cookies, CSRF tokens, Origin checks).

Drill 6 — the invisible click
“A user reports orders they never placed. Logs show a normal, authenticated POST from their own browser with a valid CSRF token and a real session. What class of attack fits, and what header would have stopped it?”
Clickjacking — CSP: frame-ancestors 'none'

Everything about the request is genuine, because the user really did click — inside a transparent iframe of your app, positioned under bait on the attacker's page. CSRF tokens don't help: the click happens in your origin, so the token is present and correct. The fix is refusing to be framed — Content-Security-Policy: frame-ancestors 'none', with X-Frame-Options: DENY alongside for old browsers. JavaScript frame-busting doesn't count; the attacker's sandbox attribute disables it.

Drill 7 — the link that rewrites the tab behind it
<a href={post.url} target="_blank">{post.title}</a>
// post.url comes from user-submitted content
Reverse tabnabbing — add rel="noopener noreferrer"

The opened page gets a window.opener handle and can set opener.location, silently swapping your still-open tab for a fake login. Modern browsers imply noopener for target="_blank", but be explicit for user-generated links, markdown renderers and webviews — and noreferrer also stops leaking the URL they came from. Since post.url is user-supplied, validate the scheme too: a javascript: href here is straight DOM XSS.

Drill 8 — spot the pollution
function merge(target, src) {
  for (const k in src) {
    if (typeof src[k] === 'object') merge(target[k] ??= {}, src[k]);
    else target[k] = src[k];
  }
  return target;
}
merge(defaults, JSON.parse(req.body));
Prototype pollution via __proto__

A body of {"__proto__": {"isAdmin": true}} walks into target["__proto__"], which is Object.prototype, and writes there — so every object in the process now inherits isAdmin. Alone it's odd; with a gadget (a library reading an option it assumes is undefined) it becomes DOM XSS or an authorisation bypass. Fix: skip the keys __proto__, constructor and prototype, use Object.create(null) or a Map for dictionaries, prefer structuredClone, and consider Object.freeze(Object.prototype) as a backstop.

Drill 9 — the two CORS headers that shouldn't meet
Access-Control-Allow-Origin: <echoes back the request's Origin>
Access-Control-Allow-Credentials: true
Any site can now read authenticated responses

Reflecting the Origin means every origin is allowed, and Allow-Credentials: true means the browser attaches cookies and hands the response to that page's JavaScript. That's full account read from any site the victim visits. Fix: an exact allowlist, echoed only on a match, plus Vary: Origin so caches don't cross the wires. Note this is a read vulnerability — CORS was never a CSRF defense, since a restrictive policy still lets the request through and execute.

Drill 10 — the redirect on your own domain
const next = new URLSearchParams(location.search).get('next');
if (next?.startsWith('/')) location.assign(next);
Open redirect — //evil.com starts with "/"

A protocol-relative URL passes startsWith('/') and navigates to https://evil.com; some parsers normalise /\evil.com the same way. The link genuinely is your domain, so it survives an eyeball check and a mail filter, and the same flaw is the standard step for stealing OAuth codes. Fix: resolve and compare the origin — const u = new URL(next, location.origin); if (u.origin !== location.origin) return; — or better, keep the destination server-side against the session.

Drill 11 — the message handler
window.addEventListener('message', (e) => {
  const { type, token } = JSON.parse(e.data);
  if (type === 'auth') localStorage.setItem('token', token);
});
No origin check — any page can set your auth token

A message handler is a public API of your window: any page that can obtain a handle to it (opened it, framed it, or was opened by it) can post to it. Without if (e.origin !== 'https://trusted.example') return; an attacker injects their own token — session fixation by another name — or drives whatever else the handler does. Check e.origin against an allowlist, optionally verify e.source, and validate the payload's shape. The mirror-image bug is sending with postMessage(data, '*'), which delivers your data to whatever origin now occupies that frame.

Drill 12 — safe in React?
<a href={user.website}>{user.website}</a>
The text is safe; the href is an XSS sink

JSX escapes the child, so rendering the URL as text is fine. The attribute is a different context: javascript:alert(document.cookie) is a valid URL and executes on click. React 16.9 through 18 log a deprecation warning but still render it, and React 19 throws an error instead — but the warning has always been about the attribute, not the text, and you should not rely on the framework to catch it. The fix isn't character escaping, it's validating the scheme against an allowlist (https:, mailto:) and rejecting anything else. It's the clearest illustration of the underlying rule: escaping is a function of the context the value lands in, not of the value.

Drill 13 — sanitise on input or output?
“A teammate proposes stripping < and > from all form input at the API boundary. Good idea?”

No, on two counts. It corrupts legitimate data — names with apostrophes, a comment saying “3 < 5”, a password containing angle brackets — and that damage is permanent because you've destroyed the original. And it doesn't actually work: at input time you don't know which context the value will be rendered into, and the escaping needed for an HTML body, an attribute, a JavaScript string and a URL are all different. The rule is validate input for shape, escape output for context: reject an email that isn't an email, store the bytes the user gave you, and encode at each render site. Where we genuinely must render user-authored HTML, sanitise with DOMPurify as late as possible — at render, not on write, so a future parser fix protects existing records.

Drill 14 — the CSP that can't ship
“Your site is fully static and CDN-cached. How do you deploy a nonce-based CSP?”

You mostly can't, and that's the right thing to say first — a nonce must be fresh per response, and a cached static document has one body for everyone, so a reused nonce is no better than 'unsafe-inline'. The options are: inject the nonce at the edge (a worker that rewrites the HTML per request, which trades a little latency for the policy), or use a hash-based policy instead, listing the SHA hashes of a fixed set of inline scripts — which works for genuinely static inline code and breaks the moment anything is generated. Either way I'd still ship the non-script directives now, since object-src 'none', base-uri 'none' and frame-ancestors 'none' are free and close real bypasses, and roll out report-only first.
