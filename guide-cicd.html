Frontend interview prep

A pipeline is a promise about every commit.

CI/CD questions look like tooling trivia and are not. What is being tested is whether you can describe the path from a push to production, name what each stage protects against, and say what you would cut when it takes forty minutes. Learn the shape of the pipeline and the tool names become interchangeable.

Integrate Verify Promote Recover
00 — The frame that makes every follow-up easy

Continuous integration is a habit, not a tool

Continuous integration is the practice of merging everyone's work into a shared trunk many times a day, with an automated build and test run proving that the merged result still works. The server that runs it is incidental. The practice is the thing: integrate small, integrate often, and let a machine tell you within minutes if you broke it.

That definition matters in an interview because it explains every other answer. Why keep branches short? Because a five-day branch is five days of un-integrated work, and the conflicts you get are not just textual — they are behavioural. Why keep the pipeline fast? Because a check that takes forty minutes stops being feedback and becomes a queue. Why is a red trunk an emergency? Because a broken trunk blocks everyone else's integration, which is the one thing CI exists to enable.

Integrate

Small change lands on trunk many times a day, behind a flag if unfinished.

Verify

Automated gates prove the merged result builds, type-checks and passes.

Promote

One built artifact moves through environments unchanged.

Recover

When it breaks, restoring service is fast and rehearsed.

The narrative they want to hear

Almost every CI/CD question is a slice of one story. Have it ready end to end, with rough times attached, and you can answer the specific question from inside a structure rather than reciting facts.

  • Push. A branch with one day’s work goes up; a pull request opens.
  • Fast checks (~3 min). Install with the cache warm, then lint, type-check and unit tests, all running concurrently. These are cheap and catch most mistakes.
  • Build (~3 min, alongside the fast checks). Produce the artifact once. Bundle-size budgets are asserted against it.
  • Slow checks (~6 min). Integration and end-to-end tests, sharded across runners, run against a preview deploy of that artifact. Nine minutes of wall clock, not twelve, because the build overlaps the fast checks.
  • Review. A human reads the diff while the machine reads the behaviour. Both are required to merge.
  • Merge queue. The PR is re-tested against the current trunk before it lands, not against the trunk of yesterday.
  • Promote. The same artifact is deployed to staging and then production. Nothing is rebuilt.
  • Verify in production. Smoke tests on the critical path, then error rate and Core Web Vitals watched against the release marker.
  • Recover if needed. Flag off in seconds, or re-point to the previous artifact in a minute.
The opening line“I think of the pipeline as a series of gates that each buy a specific kind of confidence, ordered cheapest-first so failures come back fast. The build happens once and that artifact is promoted unchanged through environments — and I care as much about how quickly we can recover from a bad deploy as about how thoroughly we check before one.”
Where this guide stopsEverything after the deploy — canaries, percentage rollouts, feature flags, A/B tests — is the release topic and lives in its own guide. Deploy and release are deliberately separate ideas: this guide gets a verified artifact onto the infrastructure; that one decides which users are exposed to it.
01 — Push to production, stage by stage

What actually runs when you push

A pipeline is a directed graph of jobs, not a straight line. Jobs that do not depend on each other run at the same time; jobs that consume another job’s output wait for it. Understanding it as a graph is what lets you answer “make this faster” sensibly, because the wall-clock time is the longest path through the graph, not the sum of the jobs.

StageTypicalWhat it buys you
Checkout5–20 sThe code. actions/checkout is already shallow by default (fetch-depth: 1), so the thing to watch is jobs that set fetch-depth: 0 for history — affected-graph tools, changesets, git describe — because a large monorepo’s full history can take minutes.
Install15 s cached
60–120 s cold		Reproducible dependencies. npm ci, not npm install — it wipes node_modules, installs exactly what the lockfile says, and fails if the lockfile and package.json disagree.
Lint20–60 sConsistency and a class of real bugs (unused variables, missing hook dependencies). Cheap, so it runs first.
Type-check30–120 sWhole-program consistency that no single test covers. tsc --noEmit, because your bundler transpiles without checking types.
Unit tests1–4 minLogic correctness at the function and component level. The bulk of your assertions live here.
Build2–5 minThe artifact. Also the first place a broken import or a missing environment variable shows up.
E2E5–20 minProof the assembled system works in a real browser. The most valuable and most expensive stage — and the flakiest.
Deploy1–3 minUpload plus cache invalidation. Short relative to the test stages, which surprises people who expect shipping to be the risky-feeling part.

Fail fast is an ordering decision

The ordering above is not aesthetic. If a typo fails the type-check at 90 seconds, you never spend eight minutes of runner time on end-to-end tests that were doomed anyway. Put the cheapest, highest-yield checks first, and let independent ones run in parallel so a lint failure and a type error surface in the same run rather than one after the other over two pushes.

Worked example. Suppose lint takes 1 min, type-check 2 min, unit tests 3 min, build 3 min, E2E 8 min, and E2E is the only one that needs the build.

  • Strictly sequential: 1 + 2 + 3 + 3 + 8 = 17 min.
  • Graph-aware: lint, type-check and unit tests run concurrently (3 min, the slowest of the three), build runs concurrently with them (3 min), then E2E (8 min) → 11 min.
  • Plus four-way E2E sharding: the build’s 3 min, then each shard re-pays its own checkout, install and browser startup, so a quartered 8-minute suite lands nearer 3 min per shard than a clean 2 → ~6 min. Just over a third of the original, with no test deleted.
The number worth quotingAim for pull-request feedback in under ten minutes. It is not a magic threshold, it is an attention threshold: past roughly ten minutes people start another task, and the cost of a red build becomes a context switch rather than a quick fix. Optimise the PR path hard; the post-merge path can afford to be slower and more thorough.

When fail-fast is the wrong instinct

Stopping at the first failure is right for a routine push and irritating for a big refactor, where you want the whole list of problems at once. Be precise about the mechanism, because candidates routinely are not. Independent top-level jobs already run to completion when a sibling fails — each reports separately by default, so parallelising the gates is not a mitigation, it is what you get. What does cancel work is a matrix’s strategy.fail-fast, which defaults to true and kills the remaining legs of that matrix on the first failing one; set it to false when you want every browser or Node version reported. continue-on-error is a different tool and not interchangeable: it stops a job failing the run at all, which means it stops gating the merge. Use it for a deliberately non-blocking experimental job, never as a way to see more results, and never anywhere on the deploy path — there the first failure genuinely should stop everything.

The trap“Just run everything on every push” is the answer that ends the conversation badly. It is not that it is expensive — it is that a slow pipeline changes behaviour. People batch commits to avoid waiting, batching makes changes bigger, bigger changes are riskier and harder to review, and the risk the pipeline was built to reduce goes back up. Pipeline latency is a code-quality input, not just an infrastructure cost.
02 — The three terms people use interchangeably

Integration, delivery, deployment

Three terms, two of them sharing an abbreviation. Interviewers ask this to check you are precise about something most candidates blur, and the distinction is genuinely about who decides, not about tooling.

TermDefinitionWhere it stops
Continuous integrationEveryone merges to trunk many times a day; every merge is automatically built and tested.At a verified artifact. Nothing has shipped.
Continuous deliveryEvery commit that passes is automatically made deployable — the artifact is built, promoted through environments and sitting ready.At a human clicking deploy. The gate is a decision, not a task.
Continuous deploymentEvery commit that passes goes to production with no human step.It does not stop. Production is the end of the pipeline.

The load-bearing sentence: continuous delivery means you always could deploy; continuous deployment means you always do. The gap is mostly organisational — the same pipeline, minus the approval — but taking the last step usually buys you technical work too, because there is no longer a human in the loop to catch a bad artifact: automated post-deploy verification and a rehearsed, automated rollback stop being nice to have.

Which one should you argue for?

Continuous deployment is the stronger position, but only when three things are true: your automated gates are trusted enough that a human approval adds no real information; you can separate deploy from release, so shipping code is not the same as exposing behaviour; and recovery is fast and rehearsed. Without those, removing the human is not maturity, it is removing the last check while keeping the same risk.

The counter-case is worth saying out loud, because it shows judgement. Continuous deployment is a poor fit where a release is externally coordinated — a mobile app store review, a regulated change window, a marketing launch with a legal sign-off, an on-premise product customers install themselves. In those, continuous delivery is the honest target: the artifact is always ready, the timing is someone else’s call.

Say this“We practise continuous delivery: every green commit produces a promotable artifact. We deploy to production several times a day, but the deploy is still an explicit step because our release windows are coordinated with support. The feature flags are what make that acceptable — the code ships continuously, the exposure is the decision.”
03 — Where the integration in CI comes from

Trunk-based development and merge queues

Branching strategy is a CI question in disguise. The integration in continuous integration has to happen somewhere, and your branching model decides whether it happens continuously in small pieces or all at once in a painful one.

ModelHow it worksCost
Trunk-basedShort-lived branches, hours to a day, merged to main behind flags. main is always releasable.Requires flags, strong gates and the discipline to keep changes small. This is what most product teams should do.
GitHub FlowBranch per feature, PR, merge, deploy from main. Trunk-based with a review step formalised.Degrades into long-lived branches the moment a feature takes two weeks and nobody flags it.
Git FlowSeparate develop, release/* and hotfix/* branches with scheduled merges.Built for versioned, shipped-to-customers software. On a continuously deployed web app it adds days of un-integrated divergence and an entire class of merge pain for no benefit.

Why long branches hurt more than they look

Textual merge conflicts are the visible cost and the smaller one. The expensive failure is the semantic conflict: two branches that merge cleanly and are individually green, but are broken together. Someone renames a hook’s return field while someone else adds a caller of the old shape; git sees two edits to different files and merges them happily; the type-check on trunk goes red after the merge, not before it.

This is precisely why the merge, not the branch, is the thing to test. A pull request whose checks passed against a three-day-old base has proved something about a commit that no longer exists.

Merge queues

A merge queue takes approved PRs in order and re-runs the checks against trunk plus everything already queued ahead of them — one entry or a whole batch at a time, depending on configuration; GitHub’s queue groups several PRs into one merge_group by default — up to five per group, waiting at most five minutes for a minimum of one. Only if that speculative merge is green does the PR actually land. It is the mechanism that closes the semantic-conflict gap without asking everyone to rebase constantly.

  • The trade: latency. A queue serialises merges, so with a 12-minute check suite and ten PRs a day the last one waits a long time. Queues answer this by testing several entries speculatively in parallel — batch A, A+B, A+B+C — and discarding the branches invalidated when one fails.
  • When you do not need one: a small team on a small codebase merging a handful of PRs a day. The window in which trunk moves under you is minutes, so the conflict rate does not justify the wait. Introduce a queue when you can point at broken-trunk incidents, not pre-emptively.
  • Squash on merge keeps trunk history one-commit-per-change, which makes git bisect and revert meaningful. The counter-case is a genuinely multi-part change where the individual commits carry information — then a merge commit is better than flattening it.
The stale-base trap“Require branches to be up to date before merging” sounds like the fix and does not scale: every merge invalidates every other open PR, so with meaningful volume the team spends its day rebasing and re-running CI to chase a moving target. A merge queue gets you the same guarantee without the thundering herd.
04 — The single most common interview task

Caching, parallelism and the affected graph

“Our pipeline takes forty minutes. Make it faster.” This is the most common practical CI/CD interview prompt, and it has a structured answer. Do not start naming tools — start by saying you would measure per-job duration and find the critical path, because optimising a job that is not on it changes nothing.

1. Cache dependencies properly

The mechanism: a cache is a tarball keyed by a string, restored before the install runs. Get the key right and it is the single biggest win available — a cold npm ci on a real app is 60–120 seconds, and with the package store cached it is more like 15–30, because the network fetch disappears and only the local unpack remains.

  • Key on the lockfile hash, e.g. node-${{ hashFiles('**/package-lock.json') }}. The lockfile is the exact input to the install, so a change to it must produce a different key.
  • Never key on the branch name or a fixed string. That is the loose-key failure: a key that does not change when the input does serves a stale node_modules, and you get a green build of dependencies nobody has — or a red build that reproduces nowhere.
  • Cache the package manager’s store, not node_modules — ~/.npm, the pnpm store, the Yarn cache. This is the detail people get wrong. npm ci deletes node_modules before it starts, so a restored node_modules is thrown away unless you also skip the install on an exact cache hit, and actions/setup-node’s built-in cache: npm deliberately caches the store rather than the tree. A warm store means the install skips the network, not the install.
  • Use restore-keys as a prefix fallback. Keys are matched as prefixes, most recent first, so a changed lockfile still restores the nearest previous store and only the new packages are fetched. That partial-hit behaviour is exactly why the store is the right thing to cache — a partially restored node_modules could not be used at all.
  • Know the eviction rules. On GitHub Actions the cache defaults to 10 GB per repository with least-recently-used eviction, and entries untouched for 7 days are removed; both limits are now configurable by an admin, with storage above the free 10 GB billed. A repo that caches a 2 GB Docker context per branch will quietly evict the dependency cache it actually needed.

2. Cache the build, not just the install

Dependency caching is table stakes; build caching is where large repos win. A build cache is content-addressed: hash the inputs to a task — source files, config, dependency versions, environment — and if that hash has been built before, replay the stored output instead of running it. Turborepo and Nx both do this, and both can share the cache remotely so a hit on CI can come from a colleague’s laptop, or vice versa.

The correctness requirement is that hashed inputs must genuinely determine the output. A task that reads an unhashed environment variable, the current time, or a network resource will serve a wrong cached result — and it will look like a mystery bug, not a cache problem.

3. Only build what changed

In a monorepo, most pull requests touch one package. nx affected -t test --base=origin/main and turbo run test --filter=...[origin/main] compute the set of projects reachable in the dependency graph from the changed files, and run tasks only for those. A 30-package repo where a typical PR touches one package plus its two dependants goes from 30 test runs to 3.

The counter-case matters here: affected-graph builds are only as correct as the graph. Implicit dependencies the tool cannot see — a shared JSON fixture read at runtime, a global CSS import, an environment variable, a generated type — produce a PR that skips the test that would have caught the break. Keep a scheduled full run (nightly, or on merge to trunk) so the graph’s blind spots are found by a machine rather than by a user.

4. Shard the slow suite

End-to-end tests are usually the critical path and they parallelise almost linearly because each test is independent. Playwright takes --shard=1/4 and friends; four runners turn a 20-minute suite into roughly 5–6 minutes plus the per-runner fixed cost of checkout, install and browser download.

That fixed cost is the limit. If setup is 90 seconds, sharding a 20-minute suite eight ways gives 90 s + 150 s ≈ 4 minutes, and sixteen ways gives 90 s + 75 s ≈ 2.75 minutes for double the money. Past a point you are paying for runner startup, not for tests. Balance shards by recorded duration rather than by file count, or one shard with all the slow specs becomes the critical path on its own.

5. Stop doing work you do not need

  • Cancel superseded runs. A concurrency group keyed on the branch, with cancel-in-progress, kills the run for a commit nobody is waiting on any more. Free, and on a repo where people push often to open PRs it cuts runner consumption substantially.
  • Path filters. A docs-only change does not need the E2E suite. Be careful making these a required check — a required check that is skipped can block a merge forever unless the platform treats skipped as passed.
  • Split PR checks from post-merge checks. Cross-browser matrices, visual regression across ten viewports and full accessibility sweeps can run after merge or nightly. The PR gate should be the fast, high-signal subset.
  • Right-size the runner. GitHub’s standard hosted runner is small — 2 vCPU on private repositories — and a type-check or a bundler run is CPU-bound. A larger runner is billed at a higher per-minute rate but can be cheaper in absolute terms if it more than halves the duration, and it is always cheaper in engineer-minutes. Put numbers on it: since the January 2026 price cut a Linux 2-core minute is $0.006, 4-core $0.012, 8-core $0.022 and 16-core $0.042, so the 4-core pays for itself at a 2× speed-up but the 8-core needs nearly 4×, which a bundler that does not parallelise across cores will not deliver. Public repositories already get the 4-core, 16 GB machine for free; private ones get 2-core, 8 GB. And set timeout-minutes on every job — the default is 360 minutes, so a hung browser burns six hours of runner time before GitHub kills it.
Answer in this orderMeasure first → parallelise the graph → cache installs → cache builds → run only what is affected → shard the slow suite → move non-blocking work off the PR path. Saying “measure first” and then giving a prioritised list is most of the mark.
The cut you must declareIf you make the pipeline faster by dropping coverage — running E2E only on merge, skipping browsers, sampling tests — say so explicitly and say what compensates. Silent coverage cuts read as “we tested everything” while the risk quietly moved into production. “We moved cross-browser E2E to a post-merge run and accept that a Safari-only regression is caught after merge rather than before it” is a senior sentence.
05 — The invariant that keeps environments honest

One artifact, many environments

The rule: build once, promote the same artifact. Whatever comes out of the build job is what goes to staging, and the identical bytes are what go to production. If each environment rebuilds from source, the thing you tested is not the thing you shipped — a dependency resolved differently, a base image moved, a transient install failure produced a subtly different bundle — and the class of bug you get is “works on staging”, which is expensive to chase precisely because it is not reproducible.

Mechanically this means the build job uploads an artifact (the dist/ directory, a container image, a tarball) tagged with the commit SHA, and every later job downloads that artifact rather than running the build again. It also makes rollback trivial: the previous artifact still exists, addressed by its SHA, so reverting is a re-point rather than a rebuild of a commit you hope still builds.

The frontend’s awkward problem: build-time environment variables

Backends read configuration at process start, so one image genuinely runs anywhere. A frontend bundle does not have a process start you control — the bundler inlines environment variables as string literals at build time. import.meta.env.VITE_API_URL, process.env.NEXT_PUBLIC_* and the old REACT_APP_* are all substituted into the output, then minified, and the resulting JS is a constant. Bake in the staging API URL and the artifact is a staging artifact forever.

Be precise about the boundary, because an interviewer may push on it: what is frozen is the browser bundle. A framework with a server — Next.js, Remix, Nuxt — still reads unprefixed variables at runtime in server code, which is exactly why one Docker image can be promoted through environments. The constraint is on config the browser needs, and that is the config this section is about.

So “build once” and “configure per environment” are in direct tension on the frontend. Four ways out, in the order I would reach for them:

ApproachHowTrade-off
Runtime config endpointApp fetches /config.json before boot, or the server injects window.__CONFIG__ into the HTML it serves.Truly one artifact. Costs a request or a server-render step, and boot must handle the config failing.
Relative pathsCall /api/... and let each environment’s edge or proxy route it.The simplest thing that works, and it removes the variable entirely. Only viable when the API is same-origin.
Placeholder substitutionBuild with a sentinel string, replace it in the artifact at deploy time.Keeps one build but mutates the artifact, so the bytes you tested are not quite the bytes you ship. Verify the substitution actually happened.
Build per environmentRebuild with each environment’s variables.The common default and the weakest. Accept it only for values that genuinely cannot be runtime — and then re-run the smoke tests per environment, because you no longer have one tested artifact.
Nothing in the bundle is secretWhatever a bundler inlines ships to the browser as readable text. NEXT_PUBLIC_ and VITE_ prefixes are not security features, they are a naming convention that makes the exposure obvious — and a reminder that the frontend has no secrets at all. Anything that must stay private lives behind an endpoint you control. This is the single most common way a real key leaks: someone adds VITE_STRIPE_SECRET_KEY because the public one was already there.

Reproducibility

  • Commit the lockfile and install from it. npm ci, pnpm install --frozen-lockfile, yarn install --immutable (Yarn 2+; on Yarn 1 the flag is --frozen-lockfile, and Yarn 1 ignores unknown flags silently, so the wrong one gives you a non-frozen install that looks like it worked). Without this the same commit installs different code on different days, and CI “randomly” breaks on a commit that has not changed.
  • Pin the toolchain. Node version in .nvmrc or engines, read by CI. A minor Node bump has changed both build output and test behaviour before.
  • Stamp the build. Put the commit SHA in the artifact and report it with every error and analytics event. Without it, “is this bug in the current build?” is unanswerable, and a rollback is guesswork.
  • Keep old artifacts. They are immutable and small; retaining a few weeks costs almost nothing and is what makes both rollback and bisecting a production regression possible. Do not rely on the CI provider for this: GitHub’s workflow artifacts expire after 90 days by default, and since actions/upload-artifact@v4 an artifact name is immutable within a run, so a job cannot append to one. The promotable copy belongs in a registry or bucket you control.
06 — What blocks a merge, and what should not

Gates: lint, types, tests, budgets

Each gate exists to catch a class of defect that the others structurally cannot. Being able to say what a gate protects against — rather than listing the tools — is what the question is testing.

GateCatchesBlind to
Format (Prettier)Diff noise and style arguments.Everything else. Never fail a build on it if you can auto-fix it instead.
Lint (ESLint)Real bug patterns: missing hook dependencies, unhandled promises, accidental globals.Anything requiring types or execution.
Types (tsc --noEmit)Whole-program contract breaks — the caller of a renamed field in a file nobody tested.Logic. A well-typed function can still be wrong, and any silently disables the gate.
Unit testsLogic in isolation, fast and precisely located.Integration. Every unit passing says nothing about whether they work together.
Integration / component testsReal wiring — a component with its store, router and mocked network.The real backend, real network conditions, real browser differences.
E2EThe critical path in a real browser: it loads, auth works, checkout completes.Scale, and anything not on the few paths you wrote. Slow and flaky, so keep it to a small high-value set.
Bundle budgetGradual size regression — the import of a 300 KB date library for one format call.Runtime cost. A small bundle can still be slow.
Lighthouse CIPerformance and accessibility regressions on key routes, as a trend.Real-user conditions. Lab numbers are noisy and are not your p75 field data.
Dependency auditKnown CVEs in what you ship.Unknown vulnerabilities, and your own code.

Branch protection makes a gate a gate

A check that reports but does not block is documentation. Required status checks, at least one approving review, and a restriction on force-pushing to trunk are what turn the pipeline into a constraint. Add CODEOWNERS when specific areas need specific reviewers — and be aware it slows those PRs down, so scope it to code that genuinely needs it.

Coverage thresholds, honestly

A global coverage threshold is a weak gate. It measures lines executed, not assertions made — a test that renders a component and asserts nothing scores identically to one that checks behaviour — and once it is a target, people write tests to raise it. The 80% figure is a convention, not a finding.

What works better is diff coverage: require that the lines this PR changed are covered, and let the global number drift. It puts the pressure on new code, where it is cheap to write the test, instead of on a legacy file nobody is touching. Pair it with a ratchet — the global number may not go down — and you get the property people actually wanted from the threshold.

Performance and size budgets

  • Fail on the delta, not the absolute. “This PR adds more than 5 KB gzipped to the main entry” is actionable in review. “The bundle is over 250 KB” fails on the unlucky PR that crossed the line and blames the wrong person.
  • Measure compressed size — gzip or brotli — because that is what crosses the network, and raw size overstates the cost of repetitive code by a lot. Keep an eye on the uncompressed figure too: parse, compile and execute scale with the decompressed bytes, so a 40 KB gzipped file that unpacks to 400 KB still costs real main-thread time on a mid-range phone.
  • Lighthouse in CI is noisy. A shared runner’s CPU contention moves scores by several points run to run. Take the median of three to five runs, assert on the metrics you care about rather than the composite score, and treat it as a trend line with a generous threshold. Otherwise you have built a flaky test with a chart.
  • Be precise about what automated accessibility checks cover. Deque’s own study puts axe-core at about a third of the WCAG 2.1 AA success criteria but roughly 57% of actual issue instances — the auto-detectable failures (contrast, labels, alt text, ARIA) are also the most common ones. Note that the vendor behind axe produced both numbers. Either way the residue is the part that matters: focus order, keyboard traps, whether a custom widget is usable at all. Run it as a gate, and never describe passing it as the page being accessible.
Say this“I want each gate to answer a different question, and I want the fast ones blocking on the PR. Types and unit tests block; E2E blocks on the critical path only; bundle-size and Lighthouse comment with a delta and block only on a threshold we agreed. Anything noisy that blocks will be ignored or bypassed within a fortnight, which is worse than not having it.”
07 — The failure mode that kills a pipeline

Flakiness and the trust budget

A flaky test is one that passes and fails on the same code. It is not a testing detail — it is the failure mode that destroys a pipeline, because the damage is to trust. The first time a red build is spurious, someone re-runs it. Once re-running is the reflex, a real failure gets re-run too, and the pipeline has stopped being a gate while still costing everyone forty minutes a day.

The arithmetic is unforgiving. If each test has a 0.1% chance of failing spuriously and they fail independently, a 500-test suite fails about 39% of runs (1 − 0.999500) — two pull requests in five go red for no reason at all. It takes only about 700 such tests to cross 50%. Per-test flakiness that sounds negligible compounds into a suite nobody believes.

Where the non-determinism comes from

  • Time and waiting. A fixed waitForTimeout(500) passes on a warm laptop and fails on a loaded CI runner with 2 vCPU. Wait for a condition — an element, a network response, a state — never for a duration.
  • Shared state. Tests that write the same database row, localStorage key or module-level variable pass in isolation and fail when run in parallel, or in a different order. The tell: it only fails in CI, where the parallelism is different.
  • Order dependence. Test B relies on state test A left behind. Randomising order surfaces these deliberately; most runners can do it with a seed you can replay.
  • Real network. Any test that hits an external service inherits its availability. Mock at the network boundary.
  • Animation and transitions. An element that is present but still moving fails a click. Disable animations in the test environment.
  • Clock and locale. Tests that break at month end, during a daylight-saving change, or on a runner set to UTC when you are not. Freeze the clock; pin the timezone and locale in the runner config.

What to do about them

The instinct is to retry. Retrying is a legitimate mitigation and a terrible policy, and the difference is whether the retry is recorded. Silent retries: 3 converts a real race condition — the kind that also affects users — into a green build. Retry once, and report every test that passed only on retry, so flakiness stays visible as a number rather than becoming invisible.

The pattern that works:

  • Detect. Re-run the suite against unchanged code on a schedule, and record every retry-pass. This is the only way to distinguish a flaky test from a genuinely broken one.
  • Quarantine. Move a confirmed flaky test out of the blocking suite immediately, into a run that still executes and reports but does not block. This protects trust in the gate.
  • Own and expire. Quarantine with a ticket and a deadline. Without one, quarantine is a graveyard — and a quarantined test is worse than a deleted one, because it looks like coverage that no longer exists.
  • Fix the cause, not the symptom. A flaky test frequently reflects a real race in the product. “The test is flaky” and “the app occasionally does the wrong thing” are often the same sentence.
The trapAnswering “add retries” and stopping is the failing answer. Answering “retry once, report retry-passes, quarantine confirmed flakes with an owner and a deadline, and treat repeat offenders as product races” is the passing one. Same first word, entirely different level.
08 — Preview deploys and what staging is for

Environments and preview deploys

An environment is a place the artifact can run, plus the configuration and data that make it distinct. The interesting question is not how many you have — it is what each one is for, because an environment nobody trusts is pure cost.

EnvironmentPurposeHonest limitation
Preview (per PR)A real URL for this branch, so reviewers, designers and QA can click the change instead of imagining it.Usually points at shared staging data, so it proves the UI works, not that the integration does.
StagingProduction-shaped rehearsal: same infrastructure, same deploy mechanism, seeded data.Never has production’s data volume, traffic shape or third-party behaviour. Staging being green is weak evidence.
ProductionWhere the truth is. Canaries, flags and real monitoring live here.Mistakes are visible. Which is why deploy and release are separated.

Preview deploys are the frontend’s best CI feature

Every PR gets its own deployed URL, posted back as a comment. The mechanics are simple — build the artifact, upload to a unique path or subdomain, comment the link — and the effect on review quality is large, because a reviewer reading a diff of CSS is guessing and a reviewer clicking the page is not. It is also where your E2E suite should run: against a deployed build rather than a dev server, which catches build-only failures like a mis-set base path or a broken production-only code path.

  • Do not index them. Preview URLs need X-Robots-Tag: noindex or authentication. Deployed previews of a public marketing site have been indexed and outranked the real page before.
  • Clean them up. Tear down on PR close, or you accumulate hundreds of live deployments, which is both a cost and a security surface.
  • Never point them at production data. A preview is an unreviewed build with a public URL; treat it as untrusted.

Is staging worth it?

Have the argument ready, because a good interviewer will push. The case against: staging costs real money and attention, its data never matches production, and teams routinely ship things that passed staging and broke anyway — which teaches people that the signal is weak. The case for: some things genuinely cannot be tested anywhere else, principally destructive migrations, third-party integrations in sandbox mode, and infrastructure changes.

The senior position is that staging is for rehearsing changes you cannot safely rehearse in production, and that everything else is better verified in production behind a flag, with a canary and real monitoring. If your staging environment is mostly a slower way to find out what a preview deploy already told you, it is a habit rather than a control.

Database migrations, brieflyThe reason deploys and schema changes are hard together is that for a moment old code and new schema coexist. The pattern is expand and contract: add the new column, deploy code that writes to both, backfill the existing rows, then deploy code that reads the new column, and only drop the old one in a later release. The order matters — switching reads before the backfill points new code at a column that is NULL for every pre-existing row, which is the outage the pattern exists to prevent. Done in that order every step is independently reversible, and no step requires old and new code to disagree about the schema. A single migration that renames a column is what turns a routine deploy into an outage.
09 — Frontend-specific mechanics

Deploying a frontend safely

The deploy step itself is usually the shortest job in the pipeline, and the frontend-specific parts are worth knowing precisely because they are where the sharp edges are. The full treatment of exposure — canaries, percentage rollouts, flags — is the release guide; this is the mechanics of getting bytes in place without breaking the users already on the site.

  • Upload assets before switching the document. Hashed assets first, entry HTML last. The reverse order leaves a window where the HTML references files that 404 — brief, but on a busy site “brief” is thousands of people.
  • Cache headers do the rest. Content-hashed files get a long max-age because a change produces a new URL; the entry document gets no-cache so it always revalidates. Invalidate the CDN for the document only.
  • Keep the previous build’s chunks. A user who loaded the page before the deploy will request a lazy chunk afterwards. If it is gone they get a ChunkLoadError and a blank screen — that is webpack’s name; Vite surfaces the same failure as a vite:preloadError event on window, and its docs suggest reloading in the handler. Retain a few builds and catch chunk-load failures in the app to prompt a reload.
  • Smoke test after deploying. Three to five checks against the real environment: the page loads, auth works, the primary flow completes. This is what catches configuration and environment failures — a missing variable, a wrong API URL, a misconfigured redirect — that no test running before the deploy can see.
  • Make the smoke test gate the promotion. If it fails on staging, the pipeline stops rather than continuing to production. A smoke test whose failure nobody acts on is a notification.

Rollback is a first-class pipeline feature

Design it deliberately, do not assume it. “Re-point the alias to the previous artifact” should be one command or one button, and it should have been tested. The frontend caveat is that rollback is not symmetric with deploy: you can restore the previous files instantly, but browsers already holding the new HTML keep it until it revalidates, and sessions in flight may hold references to either build. That asymmetry is exactly why a flag flip — which changes behaviour without changing which files anyone holds — is the faster kill switch, and why merging behind flags pays for itself here.

Roll back or roll forward?Roll back when the impact is user-visible and the cause is not yet understood — restore known-good first, diagnose second. Roll forward when the fix is small, understood and verified, or when reverting is itself risky, which is usually the case once a migration has run. Saying “always roll back” is the answer of someone who has not had to reverse a data change.
10 — The senior differentiator in this topic

Securing the pipeline itself

This is where a strong candidate separates from an average one, because most people prepare the happy path and stop. A CI pipeline is a machine with write access to production and a credential store, that executes code from pull requests. Treat it as production infrastructure.

Secrets

  • Prefer OIDC to stored keys. Instead of a long-lived cloud access key sitting in CI, the runner requests a short-lived signed token describing the run — repository, branch, workflow — and exchanges it with the cloud provider for temporary credentials. The trust policy on the cloud side restricts which repository and branch may assume the role. Nothing long-lived exists to leak, and revocation is a policy edit rather than a key rotation. Know the mechanics if pushed: the job needs permissions: id-token: write; the token’s sub claim is what the trust policy matches, shaped like repo:org/repo:ref:refs/heads/main, repo:org/repo:environment:prod or repo:org/repo:pull_request; and the aud is whatever the provider expects, sts.amazonaws.com for AWS. One 2026 change to cite: repositories created, renamed or transferred after 15 July 2026 get an immutable subject that embeds owner and repository IDs — repo:org@123/repo@456:ref:... — so a name-matched trust policy silently stops matching for a new repo, and the reason is that a recycled org or repo name could otherwise mint the same sub as the original.
  • Scope tightly and rotate. A deploy credential should be able to deploy and nothing else. The default token in a workflow should be read-only, with write permissions granted per job that needs them.
  • Masking is not containment. CI redacts known secret values in logs, but a base64-encoded or otherwise transformed secret is not matched. Assume anything printed can leak.
  • Never expose secrets to fork pull requests. On a pull_request run from a fork, GitHub withholds them entirely and issues a read-only token — there is no setting that grants them. That restriction is protecting you; the danger is always a workflow that routes around it.

The workflow-level vulnerabilities worth naming

  • Untrusted checkout with privileges. GitHub’s pull_request_target trigger runs the workflow definition from the repository’s default branch — not the pull request’s — with secrets available and a GITHUB_TOKEN at the repository’s default permission level. Be exact about that default: read-only for any enterprise, organisation or personal account created since February 2023, still read-write on older ones that never changed the setting — so the write-capable case is the legacy one, not the norm. Since 8 December 2025 the workflow file and the checked-out commit both come from the default branch, and GITHUB_REF and GITHUB_SHA resolve there too. Checking out and executing the pull request’s code inside it hands an attacker your credentials from any fork. If you need that trigger, do not run the pull request’s build scripts under it.
  • Script injection. Interpolating ${{ github.event.pull_request.title }} into a shell run: step substitutes attacker-controlled text into the script before the shell sees it, so a crafted title executes commands. Pass untrusted values through environment variables and quote them, rather than interpolating into the command.
  • Mutable third-party actions. A version tag is a pointer someone else can move. The March 2025 compromise of tj-actions/changed-files worked exactly this way: existing tags were repointed at code that read the runner process’s memory and printed the result into the workflow log. Get the blast radius right if you cite it — around 23,000 repositories referenced the action, but roughly 218 actually leaked secrets, mostly short-lived job tokens, and only where the logs were public. Pin third-party actions to a full commit SHA, which is the only genuinely immutable reference. Since August 2025 that is enforceable rather than advisory: the allowed-actions policy at enterprise, organisation or repository level has a checkbox that fails any workflow using an action not pinned to a full SHA, and a ! prefix in the allow-list blocks a specific action or version outright, evaluated last so it overrides any other rule.
  • Cache poisoning. A cache is a writable, shared artifact whose contents get executed. GitHub scopes them by branch: a run can read its own scope, the default branch’s and, for a pull request, the base branch’s, while an ordinary pull_request run writes only to its own. The gap was the privileged triggers — pull_request_target and friends ran in the default branch’s cache scope with a write token, which is the documented poisoning route; GitHub made cache tokens read-only for untrusted triggers in June 2026, and in September 2026 exposed the control as a cache-mode key at workflow or job level — read (the default for pull_request_target), write (the default for push), write-only or none. The transferable lesson is that scoping is a boundary you must not design around, not a guarantee that a cache is trustworthy.

Dependencies and the supply chain

  • Lockfile plus frozen installs is the base layer: it removes the ability of a transitive dependency to change under you between the PR run and the deploy run.
  • npm audit is noisy on frontend projects because it reports vulnerabilities in build-time dependencies that never reach a browser and are not reachable in your usage. Gate on high and critical severity for production dependencies, and triage the rest rather than failing every build.
  • Install scripts are arbitrary code execution at install time, on your runner, with your credentials in the environment. --ignore-scripts where your dependencies tolerate it is a real hardening step. The case to cite is the September 2025 Shai-Hulud worm: a postinstall hook that harvested npm tokens, GitHub PATs and AWS, GCP and Azure keys from whatever machine installed it, then used the stolen npm credentials to republish itself into every other package those maintainers owned — over 500 package versions in a few days, with a second wave in November. It spread through CI runners precisely because they install with credentials in the environment.
  • Automate updates with review. Renovate or Dependabot with grouped, scheduled PRs keeps drift small; auto-merging patch updates for dev dependencies once CI is green is reasonable, auto-merging anything that reaches production is not.
  • Provenance and SBOM are the current direction: npm publish --provenance from CI produces a signed, verifiable link between a published package and the exact workflow run and commit that built it, and an SBOM lists what actually went into the artifact. The 2025 sequel is worth knowing: npm trusted publishing lets CI publish with an OIDC token instead of an npm token at all (npm CLI 11.5.1+, id-token: write, the workflow filename registered on npmjs.com), and it emits provenance automatically without the flag. It arrived because publish tokens were the thing being stolen — npm revoked every classic token on 9 December 2025 and capped granular write tokens at 90 days. Expect to be asked what they are, not to have built one.
Say this“The pipeline has production credentials and runs code from pull requests, so I treat it as production. Short-lived OIDC credentials rather than stored keys, least privilege on the default token, third-party actions pinned to a SHA, and no untrusted code executed in a privileged context. Most CI compromises I have read about are one of those four things.”
11 — How you argue for investment

DORA and what to actually watch

“How do you know your pipeline is good?” is a question about whether you can reason with evidence instead of taste. The standard vocabulary is the DORA set of four delivery metrics, and knowing why they come in a set of four is the point.

MetricWhat it isWhy it is in the set
Deployment frequencyHow often you deploy to production.Throughput. High frequency forces small batches, which is the underlying good thing.
Lead time for changesCommit to running in production.Latency. Exposes queues, manual approvals and slow gates.
Change failure rateShare of deploys causing a degradation needing remediation.Quality. This is the brake on the first two.
Failed-deployment recovery timeHow long to restore service when a deploy breaks it. Earlier reports called it time to restore service.Resilience. Fast recovery is what makes frequent deploys safe.

The four are a system, and the pairing is the insight: speed metrics without stability metrics reward recklessness, and stability metrics without speed metrics reward paralysis. A team that deploys once a quarter has a superb change failure rate and is not doing well. DORA’s long-running finding is that speed and stability are not opposed — the fastest cluster also leads on stability, with a change failure rate around 5% against roughly 40% for the slowest — because small changes are easier to verify, review and reverse. State it with the caveat, though: it is not a clean monotonic line, change failure rate has always been the noisiest of the four, and recent reports on AI-assisted development show throughput rising while stability falls. What the data does not support is “we deploy rarely because we are careful”.

Two currency notes, because the interviewer may have read the latest report. The 2024 report added a fifth metric, rework rate — the share of deployments that were unplanned work to fix a user-facing bug or incident — on the grounds that change failure rate was only a proxy for it. And the 5%-versus-40% clusters are the 2024 report’s; the 2025 report replaced elite/high/medium/low with seven team profiles from a cluster analysis (about a fifth of teams were “harmonious high-achievers”, 11% “legacy bottleneck”) and its headline was that AI adoption now correlates with higher throughput and higher instability. Quote the cluster numbers as 2024 figures, not as the current state of the art.

The pipeline’s own health

  • PR feedback time (p50 and p95). The number you actually optimise. Use p95, not the mean — the mean hides the queued run that took 40 minutes.
  • Trunk red time. How long main spends broken. If it is more than minutes, either the gates are missing or nobody treats a red trunk as an emergency.
  • Flaky rate. Percentage of runs failing spuriously, and the count of retry-passes. The leading indicator for the pipeline losing its authority.
  • Runner minutes and cost. The argument for caching and cancellation. GitHub bills Linux runners by the minute on private repositories — $0.006 per 2-core minute since January 2026, after 2,000 free minutes a month on the Free plan, 3,000 on Team and 50,000 on Enterprise; public repositories are free — so cancelling superseded runs and caching installs shows up directly on an invoice, which is a language budget holders understand.
The Goodhart caveatSay it before they do: each of these is gameable in isolation. Deployment frequency rises if you deploy nothing in ten pieces; change failure rate falls if you stop calling things failures; coverage rises with assertion-free tests. They work as a set precisely because gaming one degrades another, which is why quoting a single one as a target is a bad sign rather than a good one.
12 — Recognise these on sight

Pitfalls and anti-patterns

  • Rebuilding per environment. The artifact you tested is not the artifact you shipped, and “works on staging” becomes unfalsifiable. Build once, promote.
  • Secrets inlined into the bundle. Anything a bundler substitutes at build time is readable text in the browser. The PUBLIC prefix is a warning label, not a boundary.
  • A cache key that does not change with its input. Silent staleness: green builds of code nobody has, or failures that reproduce nowhere. Key on the lockfile hash and nothing looser.
  • Auto-retrying flaky tests invisibly. Converts real race conditions into green builds. Retry once and report every retry-pass.
  • Gates that report but do not block. Without branch protection a check is a suggestion, and suggestions lose to deadlines.
  • Testing a PR against a stale trunk. Two individually green PRs can be broken together. That is a merge queue’s entire reason to exist.
  • A forty-minute pipeline. The second-order effect is worse than the wait: people batch commits, batches get big, big changes are riskier — the pipeline makes the code worse.
  • No rollback path. “We would revert the commit and redeploy” is a fifteen-minute recovery through the same pipeline that is currently the problem. Keep the previous artifact and a one-step way back.
  • Long-lived branches with a CI badge. A green build on a branch that has not seen trunk for a week is confidence in something that no longer exists.
  • Deploying by hand “just this once”. Now production contains a state no commit describes. Every subsequent debugging session starts from a false premise.
  • Third-party actions pinned to a moving tag. You have delegated write access to your pipeline to whoever can move that tag.
  • Treating CI as the tests’ problem. Type errors, lint, size budgets, migrations, secrets and rollback are all pipeline concerns. “CI runs our tests” is a small answer to a big question.
13 — Drill until reflex

Scenario drills

Drill 1 — forty minutes
“Our CI takes 40 minutes and engineers are complaining. Where do you start?”

Measure before changing anything: per-job duration across the last few hundred runs, then find the critical path — the longest chain of dependent jobs — because work off that path is free to shorten and changes nothing. Then, in order: run independent jobs concurrently rather than sequentially; cache the install keyed on the lockfile hash, with a prefix restore-key; cache the build with a content-addressed remote cache; in a monorepo, run only affected projects against the merge base; shard the E2E suite by recorded duration, accepting that per-runner setup cost sets the floor; and cancel superseded runs with a concurrency group. Finally, split the gate: fast high-signal checks block the PR, while cross-browser matrices, visual regression and full accessibility sweeps move to post-merge or nightly. I would say explicitly which coverage moved off the PR path and what risk that accepts — a faster pipeline that quietly tests less is not a win.

Drill 2 — works on staging
“A feature works on staging and breaks in production. It has happened three times this quarter. What do you change?”

First check whether staging and production are running the same artifact. If each environment rebuilds, they are not the same bytes — dependency resolution, base images and environment inlining all differ — and the fix is to build once and promote. If it is genuinely one artifact, the difference is configuration or data: diff the environment variables, add a startup assertion that every required config value is present and well-formed so a missing one fails the deploy rather than a user’s page, and add a post-deploy smoke test on the critical path so production tells you within a minute instead of a customer telling you in an hour. Then accept the structural point: staging never has production’s data volume, traffic or third-party behaviour, so some things can only be verified in production — which means a canary and a fast rollback matter more than a better staging environment.

Drill 3 — spot the vulnerability
on: pull_request_target
jobs:
  build:
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}
      - run: npm ci && npm run build
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}
pull_request_target + untrusted checkout = credential disclosure from any fork

pull_request_target runs the workflow from the repository’s default branch with the base repository’s secrets available — and a write-capable token wherever the default permission is still the pre-2023 read-write setting — unlike pull_request, which withholds secrets from forks entirely. This workflow then explicitly checks out the pull request’s head commit and runs npm ci && npm run build on it — so anyone who opens a PR from a fork can execute arbitrary code, via a modified build script or a malicious postinstall, in a context holding DEPLOY_KEY. The fix: use pull_request, which runs without secrets for forks. If you need pull_request_target for something like labelling, keep it to code from the default branch, never check out the pull request head under it, and split any build into a separate unprivileged workflow. Also pin third-party actions to a full commit SHA rather than @v4. One currency check worth adding if you are asked: since mid-2026 actions/checkout refuses this fetch by default, so the modern shape of this bug is a workflow that sets allow-unsafe-pr-checkout: true, or one that fetches the head with raw git and bypasses the action entirely.

Drill 4 — the flaky suite
“About one in five CI runs fails for no reason and everyone just re-runs it. Fix it.”

Treat it as an outage of the gate, because that is what it is — once re-running is the reflex, real failures get re-run too. Start by making flakiness measurable: retry once, and report every test that passed only on retry, so you have a ranked list rather than an anecdote. Quarantine the top offenders into a non-blocking run immediately, each with an owner and a deadline, so the blocking suite is trustworthy again today. Then fix causes rather than symptoms: replace fixed timeouts with condition-based waits, isolate shared state per test, randomise test order to surface order dependence deliberately, mock at the network boundary, disable animations, and pin clock, timezone and locale. Expect a meaningful share of them to be genuine races in the product — a test that is flaky because the app is occasionally wrong is a bug report, not a test problem.

Drill 5 — two green PRs, one red trunk
“Two PRs each passed CI. Both merged. Trunk is broken. How did that happen and how do you prevent it?”

A semantic conflict. Each PR was tested against the base as it was when the run started, not against the other. One renamed or changed the contract of something the other started calling — git merges them cleanly because the edits are in different files, so no textual conflict appears, and neither run ever saw the combined code. Requiring branches to be up to date before merging technically prevents it but does not scale: every merge invalidates every other open PR and the team spends the day rebasing. The right mechanism is a merge queue, which re-runs the checks on trunk-plus-the-queued-changes and only lands the PR if that speculative merge is green, testing several batches in parallel to keep the wait down. Alongside that: keep branches short so the window is small, and make sure the type-check runs on the merge result — it catches most conflicts of this shape for a fraction of the cost of the test suite.

Drill 6 — one artifact, three environments
“You want to build once and promote, but the app needs a different API URL per environment and Vite inlines it at build time. Resolve that.”

Name the tension first: the bundler substitutes import.meta.env.* as string literals during the build, so a bundle with the staging URL baked in is a staging bundle for ever, and build-once is impossible while configuration lives at build time. Move it to runtime. Best is not to need it — call a relative /api path and let each environment’s edge or proxy route it, which deletes the variable. If the API is on another origin, fetch a small /config.json before boot or have the server inject window.__CONFIG__ into the HTML, and handle the failure case so a config outage is not a white screen. Placeholder substitution at deploy time is the pragmatic middle: one build, patched per environment — but it mutates the artifact you tested, so verify the substitution ran. Rebuilding per environment is the fallback, and if you take it you must re-run the smoke tests per environment, because you no longer have a single tested artifact.

Drill 7 — the coverage gate
“Leadership wants an 80% coverage gate on every build. What do you say?”

Agree with the goal, push back on the instrument. Line coverage measures which lines executed, not whether anything was asserted — a test that renders a component and asserts nothing scores the same as one that checks behaviour — so as a target it reliably produces assertion-free tests and a number that means less each quarter. A global threshold also puts the pressure in the wrong place: it fails the PR that touched a legacy file, not the PR that added untested code. Propose two mechanisms instead: diff coverage, requiring the lines this PR changed to be covered, which is cheap to satisfy at the moment the code is written; and a ratchet, so the global figure may not fall. That gives leadership the trend they want and puts the cost where the new risk is. Then offer the metric that actually correlates with quality — change failure rate — as the thing to report upward.
