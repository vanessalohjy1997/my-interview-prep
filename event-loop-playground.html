01 — Reading it

What each lane means

LaneHoldsRule it demonstrates
Call stackmain() while the top-level script runs, then whichever callback is currently executing.Nothing else can run while something is on the stack. The loop only acts when the stack is empty.
Microtask queuePromise reactions (.then/.catch/.finally) and queueMicrotask callbacks.Drained completely — including microtasks added while draining — before any macrotask.
Macrotask queuesetTimeout / setInterval callbacks, sorted by delay then registration order.Exactly one per turn of the loop.
ConsoleEverything your code logged, in real execution order.This is the answer the interviewer is asking for.

Pill labels

  • timeout 0ms #3 — a setTimeout callback; the number is the delay, #3 the registration order. A named function shows its name instead.
  • then · onDone / then #7 — a promise reaction registered by .then().
  • catch, finally, microtask — the other microtask sources.
  • interval 100ms #2 — a repeating timer; it re-arms itself before its callback runs, exactly like the real thing.
Registration vs queueing A .then() on an already-settled promise queues its reaction immediately — you'll see the pill appear on the same step as the call. A .then() on a pending promise queues nothing yet; the pill only appears at the moment the promise settles. That difference is the whole reason await feels like it "pauses".
02 — The sandbox

What you can call

Your code runs inside a function whose console, timers and Promise are instrumented copies. Everything else in the page's JavaScript is available as normal, but only the calls below get traced.

APITraced?Notes
console.log / warn / error / infoyesObjects are printed as JSON where possible.
setTimeout / clearTimeoutyesVirtual clock — no real waiting. Delay only decides ordering.
setInterval / clearIntervalyesCapped by the macrotask budget; call clearInterval or it stops itself.
queueMicrotaskyesThe cleanest way to demo starvation.
Promise + .then/.catch/.finallyyesAll statics work: resolve, reject, all, allSettled, race, any.
async / awaitordering onlyRuns on the native microtask queue, so the output order is exact — but a resumed await doesn't get its own pill. See §04.
sleep(ms)yesHelper: a promise resolved by a virtual timer. await sleep(200).
Budgets 150 microtasks · 200 macrotasks · 1500 trace steps · 4 seconds. Hitting one stops the run and tells you which — that's a finding, not a bug. A synchronous infinite loop (while(true){}) can't be interrupted by anything, here or in a real browser: it will freeze this tab until you reload.
03 — Practise

Predict, then run

Say the output before you press Load. Each button drops the snippet into the playground above.

Drill 1 — the classic
console.log('script start');
setTimeout(() => console.log('setTimeout'), 0);
Promise.resolve().then(() => console.log('promise'));
console.log('script end');
script start · script end · promise · setTimeout

Both logs are synchronous. The stack empties, the loop drains all microtasks (the promise), and only then takes one macrotask (the timer). A 0 ms timer is never "immediate" — it's behind every pending microtask.

Drill 2 — where does await yield?
console.log('A');
async function foo(){
  console.log('B');
  await null;
  console.log('C');
}
foo();
Promise.resolve().then(() => console.log('D'));
console.log('E');
A · B · E · C · D

foo() runs synchronously through B. At await it suspends and returns control, scheduling the rest as a microtask — before the .then(D) is even registered. So E (sync) prints, then the queue drains in FIFO: C, then D. Note await null still yields — await is never free.

Drill 3 — a microtask born inside a macrotask
console.log('start');
setTimeout(() => {
  console.log('timeout1');
  Promise.resolve().then(() => console.log('micro in macro'));
}, 0);
Promise.resolve().then(() => {
  console.log('promise1');
  setTimeout(() => console.log('timeout2'), 0);
});
console.log('end');
start · end · promise1 · timeout1 · micro in macro · timeout2

The senior detail is step 5: after timeout1 returns, the loop does not go straight to timeout2. It drains microtasks first, so micro in macro jumps the queue ahead of a timer that was scheduled earlier.

Drill 4 — do timer delays sort?
setTimeout(() => console.log('100ms'), 100);
setTimeout(() => console.log('0ms · first'), 0);
setTimeout(() => console.log('0ms · second'), 0);
setTimeout(() => console.log('50ms'), 50);
console.log('sync');
sync · 0ms · first · 0ms · second · 50ms · 100ms

The macrotask queue isn't strictly FIFO across different delays — the host queues each callback when its timer elapses. Equal delays keep registration order. The delay is a minimum, never a promise: a busy stack pushes everything back.

Drill 5 — starvation, safely
let n = 0;
function spin(){ n++; queueMicrotask(spin); }
queueMicrotask(spin);
setTimeout(() => console.log('this timer never runs'), 0);
(nothing — the run halts on the microtask budget)

The microtask queue keeps refilling itself, so it never empties — and the loop can't reach the render step or that macrotask. In a real page this is a hard freeze with no paint and no input. Watch the macrotask lane: the timer just sits there. Swap queueMicrotask for setTimeout(spin, 0) and the timer gets its turn between iterations.

Drill 6 — await + timers together
async function main(){
  console.log('fetching…');
  await sleep(200);
  console.log('got it');
}
main();
Promise.resolve().then(() => console.log('microtask wins'));
console.log('sync tail');
fetching… · sync tail · microtask wins · got it

sleep(200) registers a macrotask and returns a pending promise, so main suspends immediately. Everything synchronous finishes, the microtask queue drains, and only then does the loop take the timer — which settles the promise and lets main resume on a later microtask tick.

04 — Honesty

What this can't show you

The execution is real, so the console ordering is always correct. The visualisation is what's approximate:

  • Resumed awaits get no pill. Native await uses the engine's internal promise machinery, which deliberately bypasses the observable .then. Instrumenting it would add extra ticks and change the very ordering you came here to check — so it stays untouched. You'll see the log appear in the right place, just without a labelled microtask.
  • Only instrumented objects are traced. A promise returned by your own async function is a plain native promise, so myAsyncFn().then(…) won't draw a pill. Chain off Promise.resolve() or sleep() when you want to see it.
  • Sub-frames aren't tracked. The stack lane shows main() and callback boundaries, not every function you call inside them.
  • Timers are virtual. Delays sort the queue but nothing waits. Browser realities like the ~4 ms clamp after five levels of nesting, and background-tab throttling, aren't simulated.
  • No render step. requestAnimationFrame, style/layout/paint and MutationObserver aren't modelled — the loop here is stack → microtasks → one macrotask.
  • Node's phases aren't here. No process.nextTick, no setImmediate. This is the browser loop.
Say this in the interview "The engine owns the stack and the microtask queue; the host owns timers, I/O and the task queue. One task, then the microtask queue is drained to empty, then the browser may render." Then reach for a consequence — starvation, jank, or why a 0 ms timer isn't 0 ms. That framing is what gets you the level.
Break it on purpose. The step you can't predict is the one worth learning.
