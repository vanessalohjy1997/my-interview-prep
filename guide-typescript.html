00 — Two facts that explain everything

Structural typing & erasure

  • Structural (duck) typing — compatibility is by shape, not name. If an object has the required members, it fits the type, regardless of what it was declared as. Caveat: a fresh object literal also gets excess property checking, so extra properties error at the assignment site — assign the same value via a variable and it passes. Two identically-shaped types are interchangeable.
  • Types are erased at runtime — TypeScript compiles to plain JavaScript with the types stripped. There is no runtime type information, so you can't instanceof an interface. Runtime validation of external data still needs guards or a schema library (Zod).

Why structural, and what it costs you

The choice follows from the language TypeScript is describing. JavaScript objects are bags of properties assembled at runtime — from literals, spreads, JSON, Object.assign — and almost none of them come from a named class. A nominal system (Java, C#) would reject nearly all idiomatic JS, so TypeScript checks the only thing that's actually knowable: the shape.

The cost is that identical shapes are interchangeable even when they mean completely different things:

type UserId  = string;
type OrderId = string;
function cancel(id: OrderId){}
const u: UserId = 'u_123';
cancel(u);   // compiles fine. Both are string. This is a real bug the compiler can't see.

The fix is a branded type — deliberately adding a property that doesn't exist at runtime, purely to make two shapes structurally different:

type Brand<T, B> = T & { readonly __brand: B };
type UserId  = Brand<string, 'UserId'>;
type OrderId = Brand<string, 'OrderId'>;

const asOrderId = (s: string) => s as OrderId;   // one blessed constructor
cancel(u);              // Error — UserId is not assignable to OrderId
cancel(asOrderId(u));   // explicit, greppable, intentional

Worth reaching for when mixing up two strings has real consequences — ids, currency amounts (cents vs pounds), or a value that must be validated before use (Email vs string). Not worth it for everything: the brand is a lie the compiler maintains, so every crossing needs a cast, and overusing it makes ordinary code ceremonial.

Excess property checking, and why it seems inconsistent

type Props = { id: string };
foo({ id: 'a', extra: 1 });        // Error: 'extra' does not exist in type Props

const o = { id: 'a', extra: 1 };
foo(o);                             // Fine! Same value, no error.

This looks like a bug and is deliberate. Structurally, o is a valid Props — it has everything required — so passing it is sound. But a fresh literal written inline has nowhere else to go: the extra property can only be a typo or a misunderstanding, so TypeScript flags it as a courtesy. It's a heuristic on literals, not a rule about types, which is exactly why it disappears the moment you name the value.

What erasure actually means for your code

“Types disappear” sounds obvious until you list the consequences, which is what interviewers are probing:

  • Nothing you write in types can defend against bad data. An API response typed as User is an assertion, not a check — the compiler trusts you. If the backend renames a field, TypeScript reports nothing and you get undefined at runtime. Boundaries (HTTP, localStorage, URL params, postMessage, third-party SDKs) need real validation. Zod and friends earn their place by producing both the runtime check and the static type from one schema, so they can't drift apart.
  • You can't branch on a type. No instanceof SomeInterface, no reflection over properties. Narrowing has to key off something that survives to runtime: a literal discriminant field, a class, typeof, or the presence of a property.
  • Generics are compile-time only. Array<string> and Array<number> are the same array at runtime — there's nothing to inspect.
  • The exceptions prove the rule. enum, namespace, constructor parameter properties (constructor(private name: string)) and legacy decorators all emit real JavaScript. That's precisely why teams prefer as const objects or union types over enums: everything else in the type layer is free, and an enum quietly isn't.
Say this“TypeScript checks shapes at compile time and then disappears. It protects me from my own code, not from bad data at the boundary — that still needs runtime validation.”
01 — Parametric types

Generics

A generic is a type parameter — a placeholder a caller fills in — so a function/type works over many types while preserving the relationship between them.

function first<T>(arr: T[]): T | undefined { return arr[0]; }
first([1, 2, 3]);        // T = number  -> number | undefined

// constraint: T must have a length
function longest<T extends { length: number }>(a: T, b: T){
  return a.length >= b.length ? a : b;
}

“Preserving the relationship” is the whole point, and it's the sentence to lead with. Compare the two ways of writing the same function:

function first(arr: unknown[]): unknown { ... }   // caller has to cast. Type lost.
function first<T>(arr: T[]): T | undefined { ... } // output tied to input. Type flows through.

A generic isn't “a type that accepts anything” — any already does that, badly. It's a link between positions: whatever went in is what comes out. If a type parameter appears in only one place in the signature, it isn't linking anything and shouldn't be a generic at all.

The smell to namefunction log<T>(x: T): void uses T exactly once, so it links nothing — it's (x: unknown) with extra ceremony. Same for a type parameter only used in a constraint. Rule of thumb: a type parameter must appear at least twice, or in both an input and the output, to be doing work. This is the most common way generics get cargo-culted into a codebase.

Constraints buy you two things

T extends { length: number } restricts what callers may pass, but it also unlocks the body: inside the function you can now read .length, which a bare T would forbid. That's the trade — narrow the callers, widen what you can do. The commonest real use is keying into an object safely:

function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const u = { id: 1, name: 'Ada' };
get(u, 'name');   // string — not `string | number`, the exact property type
get(u, 'nope');   // Error: "nope" is not assignable to "id" | "name"

Two type parameters, each used twice, and the return type is computed from both. That's a generic that pays for itself.

Inference, and when to help it

You almost never pass type arguments explicitly — TypeScript infers them from the call site, which is why first([1,2,3]) just works. It's worth knowing where inference needs a hand: default type parameters (<T = string>) when there's nothing to infer from, and explicit arguments when you want to widen deliberately — useState<string | null>(null), without which null infers as null and you can never set a string.

Generics shine in components and hooks:

function useToggle<T>(a: T, b: T){ /* returns T */ }

type ListProps<T> = {
  items: T[];
  render: (item: T) => React.ReactNode;
};
function List<T>({ items, render }: ListProps<T>){
  return <ul>{items.map(render)}</ul>;
}
<List items={users} render={u => u.name} />  // T inferred as User

Note what that buys the consumer: render's parameter is typed as User automatically, with autocomplete, because T was inferred from items. Without the generic, items: unknown[] would force a cast in every caller.

The .tsx gotchaIn a .tsx file, const f = <T>(x: T) => x fails to parse — <T> reads as a JSX tag. Write <T,> with a trailing comma, or <T extends unknown>, or just use a function declaration. It's a small thing that trips people up live, and knowing why (parser ambiguity, not a type error) reads well.
02 — Modelling state

Unions, intersections & discriminated unions

  • Union A | B — a value is one of these. You may only access members common to all members until you narrow.
  • Intersection A & B — a value has all members of both.

Why a union feels “smaller” than its parts

This trips people up, so have the explanation ready. A union of object types has fewer accessible properties than either member, while an intersection has more. It's not a contradiction — think in terms of which values are allowed versus what you may safely do with them. Circle | Square admits more values (either shape qualifies), and because any given value might be a square, only the properties present on both are safe to touch. Circle & Square admits fewer values (it must satisfy both) but guarantees every property from both.

Discriminated unions — the senior move

type State<T> =
  | { status: 'loading' }
  | { status: 'error'; error: Error }
  | { status: 'success'; data: T };

function view(s: State<User>){
  switch (s.status) {
    case 'loading': return spinner();
    case 'error':   return oops(s.error);   // s.error is known here
    case 'success': return show(s.data);     // s.data is known here
  }
}

The literal status field is the discriminant: checking it narrows the union to one member, and TypeScript then knows exactly which fields exist. This makes illegal states unrepresentable — you can't have data and error at once. Add exhaustiveness with a never default:

default: { const _exhaustive: never = s; return _exhaustive; }
// adding a new status without handling it becomes a compile error

The never trick works because of what never means: the type with no values. If you've handled every case, control flow analysis has eliminated every member by the default, so s is never and the assignment is legal. Add a fourth status and one member survives to the default, so a real type is assigned to never — which nothing is assignable to — and it fails to compile. You've converted “remember to update every switch” into a build error, which is the actual value: it turns a code-review discipline into a compiler guarantee.

For the discriminant to work it must be a literal type that exists at runtime — 'loading', not string. A common failure is building the object where TypeScript widens the field to string, at which point narrowing silently stops working; as const or an explicit annotation fixes it.

Where this pattern pays off in a UINot just fetch state. Form modes ({ mode: 'create' } | { mode: 'edit'; id: string }) stop you reading an id that doesn't exist in create mode. Mutually exclusive props ({ variant: 'link'; href: string } | { variant: 'button'; onClick(): void }) make “a link with an onClick and no href” uncompilable. Any time a comment says “only set when X”, that's a union asking to be written.
03 — From wide to specific

Narrowing

Narrowing is how TypeScript refines a broad type to a specific one within a branch:

  • typeof x === 'string' — primitives.
  • x instanceof Error — class instances.
  • 'id' in x — presence of a property.
  • truthiness (if (x)), equality, and discriminant checks (above).

What's doing the work is control flow analysis: the compiler walks your branches and tracks what must be true on each path, the same way you would reading the code. That framing predicts its limits — anywhere control flow becomes unknowable, narrowing is discarded.

Where narrowing is lost — and where it only looks lost

The folklore here is wrong in a way worth getting right, because the real rule is simpler and the exceptions are more interesting. TypeScript discards a narrowing for exactly one reason: the binding is assigned somewhere in the enclosing function, so the compiler cannot prove what it holds by the time a callback runs.

// LOST — the parameter is reassigned later, so the closure can't be trusted
function a(user: User | null) {
  if (user) setTimeout(() => console.log(user.name), 100);  // 'user' is possibly 'null'
  user = null;
}

// KEPT — a parameter (or let) that is never reassigned narrows into the closure fine
function b(user: User | null) {
  if (user) setTimeout(() => console.log(user.name), 100);  // no error
}

// KEPT — and this one is a soundness hole, not a courtesy
if (this.conn) { await flush(); this.conn.send(); }  // compiles — even though flush() may have nulled it
if (obj.value) { sideEffect(); use(obj.value); }     // compiles — same hazard

So the two halves of the answer point in opposite directions, and saying both is the senior version:

  • Reassignment loses the narrowing. A let or parameter that is assigned anywhere in the function can't be narrowed inside a callback. The fix is to copy to a const first — not because const is magic, but because it makes the binding provably immutable, which is the only thing the analysis needs.
  • Property narrowing survives calls and awaits — and that's the unsound part. TypeScript keeps trusting this.conn across an await that may have nulled it. It compiles and crashes at runtime. The compiler is being optimistic because tracking every possible mutation through every call would make property narrowing useless in practice. Copy to a const before the await so the value you use is the value you checked.

Being able to say “that one's a known unsoundness, not a lost narrowing” is a much better answer than repeating that narrowing evaporates after await — which is what most people say, and it's checkable in thirty seconds.

User-defined type guards & as const

function isUser(x: unknown): x is User {
  return typeof x === 'object' && x !== null && 'name' in x;
}
if (isUser(data)) { data.name; }   // data narrowed to User

const roles = ['admin', 'user'] as const;
// type: readonly ["admin", "user"] — literal, not string[]
type Role = typeof roles[number];  // "admin" | "user"

The x is User return type is a type predicate: it tells the compiler that a true result means x is a User in the following block. as const freezes a value to its most specific literal, readonly type — the bridge from runtime values to precise types.

Type predicates are unchecked promisesLook again at isUser above: it verifies an object with a name property, and then asserts the value is a full User. TypeScript does not verify that the body justifies the claim — return true would compile identically. A predicate is an as cast wearing a function's clothes, so every one is a place you've taken responsibility away from the compiler. Keep them few, keep them next to the type they guard, and for anything crossing a real boundary prefer a schema validator that derives the type from the check instead of the other way round. (TypeScript 5.5 infers predicates for simple cases, which removes some hand-written ones — but any you write by hand are still unverified.)

unknown vs any — and why it belongs here

Both accept anything. The difference is what happens next: any lets you do anything with the value and silently switches the checker off for everything it touches downstream — one any from a badly typed library can hollow out a whole module. unknown accepts anything but permits nothing until you narrow, which forces exactly one thing: a check at the boundary. That's why catch (e: unknown) is the modern default (errors can be any thrown value, not just Error — a rejected promise can carry a string), and why JSON.parse returning any is worth wrapping in something that returns unknown.

04 — Know these cold

Utility types

type User = { id: number; name: string; email: string };

Partial<User>        // all props optional
Required<Partial<User>> // all props required again
Readonly<User>       // all props readonly
Pick<User, 'id' | 'name'>   // { id: number; name: string }
Omit<User, 'email'>         // { id: number; name: string }
Record<string, User>        // { [k: string]: User }

function make(){ return { ok: true, n: 1 }; }
ReturnType<typeof make>      // { ok: boolean; n: number }
Parameters<typeof make>      // []

keyof User                   // "id" | "name" | "email"
User['email']                // string  (indexed access)

keyof gives the union of an object's keys; typeof value lifts a runtime value into the type world; together typeof obj[keyof typeof obj] is a common idiom for “the union of a const object's values.”

The point isn't the list — it's deriving instead of duplicating

Anyone can recite the table. The senior habit is that a type should be written once and everything else derived from it, so the compiler propagates a change instead of letting copies drift. Rename a field on User and every derived type updates; hand-written duplicates silently don't, and you find out at runtime.

// duplicated — two things to remember to change
type UserForm = { name: string; email: string };

// derived — one source of truth
type UserForm  = Pick<User, 'name' | 'email'>;
type UserPatch = Partial<Omit<User, 'id'>>;   // PATCH body: everything but id, all optional
type Handlers  = { [K in keyof Events as `on${Capitalize<K & string>}`]: (e: Events[K]) => void };
The Omit trap — a genuine footgunPick checks its keys; Omit does not. Omit<User, 'emial'> compiles happily and silently omits nothing, because its signature is Omit<T, K extends keyof any> — any string is allowed. So a typo, or a field later renamed, leaves you with a type that quietly includes something you meant to remove. When it matters, use Exclude<keyof User, 'email'> via Pick, or define a checked StrictOmit<T, K extends keyof T>. Being able to name this is a reliable signal you've used the language in anger.

The rest of the set worth knowing by name

TypeDoesReach for it when
Record<K, V>Object with keys K, values VLookup tables. Record<Role, Permission[]> forces you to handle every role — a real exhaustiveness win over an index signature
Exclude<U, X> / Extract<U, X>Filter a union, remove or keepSubsetting states: Exclude<Status, 'archived'>
NonNullable<T>Strips null | undefinedAfter a filter or a guard, when the type still carries nullability
Awaited<T>Unwraps promises, recursivelyAwaited<ReturnType<typeof fetchUser>> — the resolved value of an async function
Parameters<T>A function's args as a tupleWrapping or decorating a function without restating its signature

Two distinctions people mix up: Pick/Omit operate on object keys, while Extract/Exclude operate on union members — different worlds, similar-sounding names. And Partial is not free: making every field optional is right for a PATCH body and wrong for a form model, where it lets you forget a required field and only find out on submit. If a value must eventually be complete, model the partial and the complete states as two types.

05 — Reading level

Mapped & conditional types

You don't need to author fancy ones — you need to read and explain them.

Mapped types

// re-create Partial with a mapped type
type MyPartial<T> = { [K in keyof T]?: T[K] };
// modifiers: ? adds optional, readonly adds immutability, - removes them
type Mutable<T> = { -readonly [K in keyof T]: T[K] };

A mapped type iterates the keys of T (K in keyof T) and produces a property per key. You can add/remove ? and readonly, and remap keys with as.

Read it as a for loop over keys, because that's exactly what it is: for each key K in T, produce a property named K whose type is T[K], with modifiers applied. Once you see the loop, the whole family decodes — every built-in utility except the conditional ones is a two-line mapped type. Key remapping with as is the same loop with a computed name:

type Getters<T> = { [K in keyof T as `get${Capitalize<K & string>}`]: () => T[K] };
Getters<{ name: string }>   // { getName: () => string }

// remap to `never` to DROP keys — the idiomatic filter
type OnlyStrings<T> = { [K in keyof T as T[K] extends string ? K : never]: T[K] };

Conditional types

type IsString<T> = T extends string ? true : false;
IsString<'hi'>   // true
IsString<number> // false

// infer extracts a type from a position
type ElementOf<T> = T extends (infer U)[] ? U : never;
ElementOf<string[]>   // string

T extends U ? X : Y picks a branch based on assignability; infer captures a type from within the checked shape (here, the array's element type).

Read extends here as “is assignable to”, not “inherits from” — it's the same question the compiler asks at every assignment, just asked in the type language. And infer is pattern matching: match this shape, and give me a name for the part in that slot. That's how ReturnType is built — T extends (...a: any[]) => infer R ? R : never, which is worth being able to write from memory because interviewers ask for exactly that one.

Distributivity — the behaviour that surprises everyoneA conditional type over a naked type parameter distributes over unions: it's applied to each member separately and the results are re-unioned. So ElementOf<string[] | number[]> is string | number, not never. Usually that's what you want — it's how Exclude works at all. When you don't want it, wrap both sides in a tuple to defeat it: [T] extends [U] ? X : Y. The classic symptom is a type mysteriously resolving to never — usually because the input was never, which is the empty union, so distributing over it produces nothing at all.

When to stop

Worth saying out loud, because it's a judgement question as much as a knowledge one: type-level programming has a real cost. Deeply conditional types slow the compiler and your editor measurably, produce error messages that no one can read, and are harder to change than the code they describe. If a type takes longer to understand than the function it types, a simpler type plus a runtime check is usually the better engineering. Reach for this machinery when it removes duplication across many call sites — a library boundary, a generated API client, a design-system prop table — not to prove it can be done.

06 — Where FE meets types

Typing React

type Props = {
  title: string;
  count?: number;                 // optional
  children: React.ReactNode;      // anything renderable
  onSelect: (id: string) => void;
};

// events
function onChange(e: React.ChangeEvent<HTMLInputElement>){ e.target.value; }
function onClick(e: React.MouseEvent<HTMLButtonElement>){}
function onSubmit(e: React.FormEvent<HTMLFormElement>){ e.preventDefault(); }

// refs — note the null and the element type
const inputRef = useRef<HTMLInputElement>(null);
inputRef.current?.focus();
  • Type children as React.ReactNode (strings, elements, arrays, null).
  • Event handlers take a typed React.*Event<HTMLElementType> — the element type gives you the right currentTarget. ChangeEvent is the special case that also re-types target; elsewhere target is just EventTarget.
  • Refs are useRef<T>(null); .current is T | null, hence the optional chaining.
  • Many teams prefer typing props directly over React.FC because it complicates generic components. (In older @types/react before v18 it also forced an implicit children prop; that was removed in the React 18 types, so today you declare children yourself or use PropsWithChildren.)

Why target vs currentTarget is typed the way it is

It mirrors the DOM, and the reasoning is worth having ready because it looks like a types annoyance and isn't. currentTarget is the element the handler is attached to — statically known, so React can type it as your element. target is whatever was actually clicked, which thanks to bubbling could be any descendant, so it can only honestly be EventTarget. ChangeEvent gets away with re-typing target because change events don't originate from children of an input. In a click handler, reach for currentTarget — and if you truly need target, narrow it (e.target instanceof HTMLElement) rather than casting.

Making impossible props impossible

The highest-value use of TypeScript in a component library isn't typing string vs number — it's encoding the rules that currently live in a comment or a runtime invariant:

// weak: every combination compiles, including the nonsense ones
type ButtonProps = { href?: string; onClick?: () => void; disabled?: boolean };

// strong: a link needs an href, a button needs an onClick, and never both
type ButtonProps =
  | { as: 'a';      href: string;  onClick?: never }
  | { as: 'button'; onClick: () => void; href?: never };

<Button as="a" onClick={fn} />   // Error — caught at compile time, not in QA

The ?: never members are what stop the union collapsing into “anything goes”: without them, an object with both properties is still structurally assignable to one member. Same technique for “pass value + onChange (controlled) or defaultValue (uncontrolled), never both” — the most commonly violated contract in React component APIs.

Two version-sensitive details

  • Ref typing changed in React 19. ref is now a regular prop on function components, so forwardRef is no longer required to accept one, and its ElementRef-style helpers are being retired. If the codebase is on 18, forwardRef<HTMLInputElement, Props> is still correct — note the argument order (ref type first) since it's a common slip.
  • A ref callback may now return a cleanup function. Which means an arrow body like ref={el => (myRef.current = el)} — an implicit return — is a type error in React 19. Use a block body.
Say this“I use types to make invalid component states uncompilable rather than to annotate what's obvious. If a prop is only valid alongside another, that's a discriminated union, not a comment.”
07 — The settings that decide how much it's worth

Strictness & the escape hatches

Two codebases can both “use TypeScript” and get wildly different value from it. The difference is usually a handful of compiler flags and how disciplined the team is about the escape hatches — a very common interview thread, because it separates people who configured a project from people who inherited one.

FlagWhat it catchesNotes
strictUmbrella for the rest — strictNullChecks, noImplicitAny, and friendsNon-negotiable on a new project. Without strictNullChecks, null is assignable to everything and the compiler cannot see your most common runtime crash
noUncheckedIndexedAccessarr[i] and record[key] return T | undefinedTruthful — indexing can miss. Off by default even under strict, because it's noisy. Worth it on data-heavy code
exactOptionalPropertyTypesDistinguishes “absent” from “present and undefined”Matters when a key's presence is meaningful — PATCH bodies, Object.keys loops
noImplicitOverride, noFallthroughCasesInSwitchSmall, cheap classes of real bugFree wins, no migration cost
verbatimModuleSyntaxForces import type for type-only importsPrevents type imports being emitted and dragging modules in at runtime

The honest note about migration: turning strict on in a large legacy codebase produces thousands of errors at once, which is why it doesn't happen. The workable path is per-file or per-directory — enable it for new code, fix modules as you touch them — rather than one heroic PR that nobody can review.

The three escape hatches, ranked by how much they cost you

  • as (type assertion) — “trust me, it's this type.” No check happens; it's a lie you're allowed to tell. Sometimes necessary (branded types, the result of a validated parse), but each one is a place a refactor can break at runtime with no compiler error. The variant to avoid entirely is the double cast x as unknown as T, which is you telling the compiler its objection is noted and overruled.
  • any — worse than as, because it doesn't stay put. Any value derived from an any is also any, so one badly typed third-party call can disable checking across a whole module without a single visible annotation. Prefer unknown and narrow. Turn on noImplicitAny so the accidental ones surface, and lint against explicit ones.
  • @ts-ignore / @ts-expect-error — suppresses whatever the next line complains about. Always prefer @ts-expect-error: it fails if the error goes away, so it self-cleans after the upstream fix, whereas a @ts-ignore lives forever and hides new errors that appear later on that line.
The non-null assertionvalue! is as NonNullable<T> in one character, which makes it the easiest way to ship a “cannot read property of undefined” while the build is green. It's defensible where the invariant is genuinely outside the compiler's view — document.getElementById('root')! in an entry file. It's not defensible as a way to make an error go away in business logic; there, narrow it or handle the null. If you can't explain why it can't be null, it can be null.
Say this“I'd rather have strict on and a handful of explicit, commented assertions than a loose config and a false sense of safety. The value of the type system is proportional to how rarely we lie to it.”
08 — Drill until reflex

“What does this type resolve to?” drills

Drill 1 — Pick + Omit
type T = { a: number; b: string; c: boolean };
type X = Omit<T, 'b'>;
type Y = Pick<T, 'a'>;
X = { a: number; c: boolean } · Y = { a: number }

Omit removes the listed keys; Pick keeps only the listed keys. They're complementary ways to derive a subset object type.

Drill 2 — as const
const a = ['x', 'y'];
const b = ['x', 'y'] as const;
a: string[] · b: readonly ["x", "y"]

Without as const, TS widens to string[]. With it, the value is frozen to a readonly tuple of literals — enabling typeof b[number] to be the union "x" | "y".

Drill 3 — why does this error?
function area(s: { kind: 'circle'; r: number }
              | { kind: 'square'; side: number }){
  return s.r * s.r;   // ???
}
Property 'r' does not exist on the square member

Before narrowing, only members common to all union members are accessible; r isn't on the square. Narrow first with if (s.kind === 'circle'), then s.r is valid.

Drill 4 — ReturnType
const load = () => ({ id: 1, ok: true });
type R = ReturnType<typeof load>;
R = { id: number; ok: boolean }

typeof load gets the function's type; ReturnType extracts what it returns. Great for deriving a type from a factory/selector instead of re-declaring it.

Drill 5 — the conceptual one
“Why model async UI as a discriminated union instead of { loading, error, data } booleans?”

Separate flags allow impossible combinations (loading && error && data), which every consumer must defensively handle. A discriminated union on status makes illegal states unrepresentable and lets the compiler narrow to exactly the fields that exist in each state — fewer bugs, and exhaustiveness checking catches unhandled cases.

Drill 6 — why does this compile?
type UserId  = string;
type OrderId = string;
declare function cancel(id: OrderId): void;
const u: UserId = 'u_123';
cancel(u);   // ???
It compiles — both are structurally just `string`

TypeScript is structural: a type alias creates a name, not a new type, so UserId and OrderId are indistinguishable. If mixing them up matters, brand them — type OrderId = string & { readonly __brand: 'OrderId' } — so they're structurally different and crossings need an explicit, greppable constructor.

Drill 7 — does this narrowing survive?
function f(user: User | null){
  if (user) setTimeout(() => console.log(user.name), 100);
  user = null;                     // ??? — and what if this line isn't there?
}
With the reassignment: error. Without it: compiles fine.

The rule isn't “callbacks lose narrowing” — it's that a binding assigned anywhere in the enclosing function can't be narrowed inside a closure, because the compiler can't prove what it holds when the callback runs. A parameter or let you never reassign keeps its narrowing. That's also why “copy to a const” works: it makes the binding provably immutable. The genuinely interesting half is the opposite case — property narrowing survives an await or an intervening call (if (this.conn) { await flush(); this.conn.send(); } compiles), which is a documented unsoundness rather than a lost narrowing. It'll compile and crash.

Drill 8 — the silent Omit
type User = { id: number; name: string; email: string };
type A = Omit<User, 'emial'>;   // note the typo
No error — A is the full User, nothing omitted

Omit<T, K> doesn't constrain K to keyof T, so any string is accepted and a typo silently omits nothing. Pick does check. Use Pick<User, Exclude<keyof User, 'email'>> or a StrictOmit<T, K extends keyof T> helper where it matters — the same trap catches you when a field is later renamed.

Drill 9 — the never that isn't a bug
type ElementOf<T> = T extends (infer U)[] ? U : never;
type A = ElementOf<string[] | number[]>;
A = string | number (distributive), not never

A conditional type over a naked type parameter distributes over unions: it's applied to each member and the results re-unioned. That's how Exclude works. To switch it off, wrap both sides in a tuple — [T] extends [(infer U)[]] ? U : never. And note ElementOf<never> is never, because never is the empty union and distributing over it yields nothing — the usual cause of a type mysteriously resolving to never.
