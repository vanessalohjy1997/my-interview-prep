00 — The lay of the land

The four pillars this guide drills

Two of the biggest JavaScript-core topics — the event loop and promises / async-await — have their own dedicated tabs in this deck. This guide covers the four remaining pillars senior interviews probe hardest.

  • Closures — a function keeps a live reference to the scope it was created in. Powers memoization and module privacy, and explains the stale-closure bugs in the React Hooks tab.
  • this — decided by how a function is called, not where it's written (arrows are the lexical exception).
  • Prototypes — objects delegate lookups to other objects; class is syntax over this.
  • Coercion & equality — the type-conversion rules behind == and the famous trick snippets.
The through-lineJavaScript looks forgiving but is governed by a small set of exact rules. Naming the rule — not the vibe — is what reads as senior.
01 — Functions that remember

Closures

A closure is the pairing of a function with the lexical environment it was defined in. When a function is created, it keeps a live reference to the variables in scope at that point — and can read and mutate them later, even after the outer function has returned.

function counter(){
  let n = 0;                  // private to the returned fn
  return () => ++n;
}
const next = counter();
next(); next(); next();       // 1, 2, 3 — n survives between calls

The classic gotcha: var in a loop

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3  3  3

var is function-scoped, so all three callbacks close over the same i. By the time the timers fire (after the loop finishes), i is 3. Fixes:

  • let is block-scoped — each iteration gets a fresh binding, so you get 0 1 2. This is the modern fix.
  • Pre-ES6: wrap in an IIFE to capture the value per iteration: (function(j){ setTimeout(function(){ console.log(j); }); })(i).
Say thisIt's not that the timer "runs late" — it's that with var there is only one i shared by every closure. let creates one per iteration.

Real uses

// memoization — the cache lives in the closure
function memoize(fn){
  const cache = new Map();
  return (arg) => {
    if (cache.has(arg)) return cache.get(arg);
    const out = fn(arg);
    cache.set(arg, out);
    return out;
  };
}
  • Private state / module pattern — expose methods, keep data unreachable from outside (the closure is the only reference).
  • Event handlers & callbacks capture the variables at definition time — which is exactly how a stale closure arises: a handler keeps reading the value it closed over, not the latest one. This is the root of the React useEffect/setInterval stale-state bug (see the Hooks tab).

What a closure actually is at runtime

The definition people give — “a function that remembers its outer variables” — is right but sounds magical, and interviewers push on it. The mechanical version: a function object carries an internal reference to the environment record it was created in. That record is an ordinary object on the heap holding the variable bindings; the function holds a pointer to it, so as long as the function is reachable the environment cannot be collected.

Two consequences fall straight out of that, and they're the two things people get wrong:

  • It captures the binding, not the value. This is the entire explanation for the var loop, and for stale closures in React. Nothing is copied at creation time — the closure reads whatever the variable holds when it runs. Which is why the var case prints 3 (one shared binding, later mutated) and the let case prints 0 1 2 (three separate bindings, each never mutated again).
  • Closures cost memory. Anything reachable from a captured environment stays alive. A single event listener defined inside a function that also had a large array in scope can keep that array alive for the lifetime of the listener — a genuine and hard-to-find leak. The fix is scoping discipline (don't create the closure where the big object is in scope) and removing listeners on teardown.
// the leak shape, in miniature
function mount(){
  const bigData = new Array(1e6).fill(0);   // 8MB
  const id = data.find(d => d.id);
  window.addEventListener('resize', () => console.log(id));
  // the handler only needs `id`, but it closes over the whole scope —
  // engines may keep bigData alive too. And nothing ever removes the listener.
}

Engines do optimise this — V8 generally only retains variables the closure actually references — but the retention is an implementation detail you shouldn't rely on, and the un-removed listener is a leak in every engine.

The React connection, stated precisely

Worth having ready because it's the bridge question between JS core and React. Every render of a component creates new function objects closing over that render's props and state. An effect with an empty dependency array runs its callback once, so the closure it created on the first render — with the first render's count — is the one still executing five seconds later inside a setInterval. The value isn't stale because React is doing something odd; it's stale because a closure captures a binding and that binding belongs to a render that finished. The fixes are the ones the language offers: capture something that does change (list the dependency), or read through a mutable box (a ref), or use the updater form setCount(c => c + 1) so you never need the captured value at all.

02 — Call-site, not definition-site

The this keyword

For a normal function, this is determined by how the function is called. Four rules, in precedence order (highest first):

RuleCall shapethis is
newnew Fn()the brand-new object
explicitfn.call(o) / apply / bindo
implicitobj.fn()obj (the receiver)
defaultfn()undefined in strict mode; the global object otherwise

Why this “breaks”

const user = {
  name: 'Ada',
  greet(){ return `hi ${this.name}`; }
};
const fn = user.greet;
fn();   // strict mode / ES module: this is undefined → TypeError
        // (non-strict browser: "hi " — this is window, and window.name defaults to "")
        // (non-strict Node global: "hi undefined") — the receiver is lost either way
setTimeout(user.greet, 0);   // same detached-receiver problem

Passing a method as a bare reference detaches it from its receiver — the call site is now fn(), so the implicit rule doesn't apply. Fixes: user.greet.bind(user), an arrow wrapper () => user.greet(), or defining the method as a class field arrow.

Arrow functions are differentArrows have no own this — they capture this lexically from the enclosing scope at definition time. They also have no arguments and can't be used with new. That's why an arrow is the right callback when you want to keep the surrounding this (e.g. inside a class method), and the wrong choice for an object method that needs a dynamic receiver.
Trapbind is permanent: a bound function ignores later call/apply receivers, and new on a bound function ignores the bound this (uses the new object). Precedence: new > explicit > implicit > default.

Why the language works this way at all

The design intent is that this makes a function reusable across receivers — one method on a prototype serves every instance, because the receiver is supplied at the call site rather than baked in. That's the same mechanism that makes prototypal delegation work: dog.speak() finds speak on the prototype but calls it with dog as the receiver, so one shared function acts on the right object.

The cost of that flexibility is precisely the detached-receiver bug: if the binding comes from the call site, then extracting the function removes the binding. It isn't a wart on top of an otherwise sane design — it's the direct consequence of the feature. Saying that turns a memorised table into an explanation.

Reading a call site, mechanically

The reliable technique under pressure: ignore where the function was written, find the call expression, and look immediately left of the parentheses.

obj.method()          // dot before the call → this = obj
method()              // nothing before it   → undefined (strict) / global
arr.map(obj.method)   // passed as a value — the call happens inside map as fn() → detached
arr.map(obj.method, obj)  // map's 2nd arg sets thisArg → works
new Ctor()            // new wins over everything except a bound-fn's own construction

// the one that catches people: an arrow ignores all of this
const o = { name: 'Ada', greet: () => `hi ${this.name}` };
o.greet();            // "hi undefined" — the arrow captured module/global scope, not o

That last case is the mirror image of the usual advice. Arrows are the right choice for a callback inside a method (they keep the enclosing this) and the wrong choice for the method itself (there's no enclosing instance to capture). Same reason a class field arrow (handleClick = () => {}) works for event handlers: it's created per instance, inside the constructor's scope, so it captures that instance.

Where this matters in modern code — and where it doesn'tBe ready for the pushback that this is legacy trivia. In function components with hooks, this barely appears, and that's genuinely one of the reasons hooks were introduced. It still matters in: class components and lifecycle methods, any library with an options object of callbacks, addEventListener (where this is the element for a non-arrow listener — occasionally useful, often surprising), and any time you pass a method reference somewhere. The honest answer names both halves: the rules are exact and still worth knowing, but the modern codebase mostly sidesteps them.
03 — Objects all the way down

Prototypes & inheritance

Every object has an internal link, [[Prototype]] (legacy accessor __proto__; read it with Object.getPrototypeOf, set it with Object.setPrototypeOf — or at creation time with Object.create). When you read a property, the engine walks this prototype chain until it finds the key or hits null.

const animal = { speak(){ return 'generic'; } };
const dog = Object.create(animal);   // dog.__proto__ === animal
dog.bark = () => 'woof';
dog.speak();          // 'generic' — found up the chain
dog.hasOwnProperty('speak');   // false — it's inherited

Constructors, .prototype, and class

function Point(x, y){ this.x = x; this.y = y; }
Point.prototype.norm = function(){ return Math.hypot(this.x, this.y); };
const p = new Point(3, 4);
p.norm();             // 5 — method lives on Point.prototype, shared
p instanceof Point;   // true — Point.prototype is in p's chain

class is largely syntactic sugar over prototypal delegation: methods you declare go on Class.prototype (shared across instances), extends wires the prototype chain, and super walks up it. (Not a 100% desugaring — class bodies run in strict mode, aren't hoisted like functions (TDZ), throw if called without new, and define non-enumerable methods.) Two names people confuse:

  • Fn.prototype — the object that instances created with new Fn() will delegate to.
  • obj.__proto__ — the object this object delegates to. For an instance, p.__proto__ === Point.prototype.
Why methods go on the prototypeDefining a method once on the prototype means every instance shares one function object, instead of each instance carrying its own copy. Instance fields (state) go on the object; behaviour goes on the prototype.

The chain, and what it costs

Property lookup walks the chain until it finds the key or reaches null. So p.norm() checks p, then Point.prototype, then Object.prototype, then stops. A miss is the expensive case — it walks the entire chain before returning undefined — which is why 'x' in obj and a failed lookup cost more than a hit near the front.

In practice engines make this fast with inline caches and hidden classes, so chain depth is rarely a real performance problem. The two things that genuinely hurt are worth naming because they're the ones with measurable cost: Object.setPrototypeOf (and writing __proto__) on an existing object deoptimises it — every cached lookup shape is invalidated, and MDN is unusually blunt about avoiding it — and very deep chains built by many extends levels. Set the prototype at creation (Object.create, a constructor, a class), never afterwards.

// shadowing: assignment writes an OWN property, it doesn't reach up the chain
dog.speak = () => 'woof';
dog.speak();                       // 'woof' — own property shadows the prototype's
Object.getPrototypeOf(dog).speak(); // 'generic' — the original is untouched

// and the counter-intuitive corollary
animal.legs = 4;
dog.legs;        // 4 — inherited, live: changing the prototype affects existing instances
dog.legs++;      // reads 4 from the prototype, WRITES 5 as an own property on dog
animal.legs;     // still 4

That read-up / write-own asymmetry is the single most useful prototype fact: reads delegate, writes don't. It explains why mutating a shared prototype object (an array or object on the prototype) leaks across instances while assigning a primitive does not — a classic bug in class-field-free constructor code.

Composition, and when inheritance is the wrong shape

Prototypes are how JavaScript does inheritance, but the interview follow-up is usually about judgement, not mechanism. Deep hierarchies are as brittle here as anywhere: a change to a base class ripples to every descendant, and the classic failure is a taxonomy that seemed obvious (Bird extends Animal, then penguins) turning into overrides that undo the parent. Composition — small functions and objects combined, or plain modules with closures for privacy — is the default in modern JS, and the language now has real private fields (#count) so classes don't need the closure trick for encapsulation either.

Where classes genuinely earn their place: many instances sharing behaviour (so prototype sharing saves real memory), an instanceof-based API, custom Error subclasses, and Web Components. That's a more useful answer than “composition over inheritance” as a slogan.

04 — Type juggling

Coercion & equality

=== (strict) compares type and value with no conversion. == (loose) applies the loose-equality algorithm (IsLooselyEqual; called Abstract Equality pre-ES2021), which coerces operands toward a common type before comparing. Prefer === everywhere; understand == so you can read traps.

The falsy values

Only these values are falsy: false, 0, -0, 0n, "", null, undefined, and NaN (plus the legacy oddity document.all). Everything else — including "0", "false", [], and {} — is truthy.

The greatest hits

0.1 + 0.2 === 0.3     // false  (IEEE-754 float)
NaN === NaN           // false  (use Number.isNaN)
typeof null           // "object"  (ancient bug)
null == undefined     // true
null == 0             // false  (== does NOT coerce null to 0)
'' == 0               // true   ('' -> 0)
'5' + 1               // "51"   (+ prefers string concat)
'5' - 1               // 4      (- forces numeric)
[] == ![]             // true   (see below)

[] == ![] is the party trick: ![] is false (arrays are truthy), so it becomes [] == false → [] == 0 → "" == 0 → 0 == 0 → true. Each step is one coercion rule; none of it is magic.

The one exception worth memorisingnull and undefined are loosely equal to each other and to nothing else — except the same document.all oddity noted above, which is also == null. So == null is the idiomatic “is it null or undefined” check.

The rule underneath all of it

The trick snippets look arbitrary until you know there are only a few conversion rules, applied consistently. Two are worth memorising because everything else follows:

  • == between different types converts toward number — with the sole exception of null/undefined, which are equal to each other and to nothing else. String vs number: the string becomes a number. Boolean vs anything: the boolean becomes a number first (true→1, false→0). Object vs primitive: the object is converted to a primitive, then the comparison retries.
  • Objects convert via valueOf, then toString (the ToPrimitive algorithm; the order reverses when a string is explicitly wanted, and Symbol.toPrimitive overrides both). For a plain array, valueOf returns the array itself — not a primitive — so toString runs, and [].toString() is "". That's the missing step in the [] == ![] trick, and the reason [1,2] + [3] is the string "1,23".

The other asymmetry worth naming: + is the only arithmetic operator that prefers strings. If either operand becomes a string primitive, it concatenates; every other operator (-, *, /, %) forces numeric conversion. Hence '5' + 1 === '51' but '5' - 1 === 4, which looks like a language defect and is one line of specification.

Why 0.1 + 0.2 isn't 0.3 — and what to do about it

Not a JavaScript bug: it's IEEE-754 double-precision binary floating point, the same in Python, Java and C. 0.1 and 0.2 have no exact binary representation, in the same way ⅓ has no exact decimal one, so each is stored as the nearest representable double and the small errors survive the addition. The result is 0.30000000000000004.

The practical answers, which is what the follow-up is really after: compare with a tolerance (Math.abs(a - b) < Number.EPSILON) for general float work, and for money, never use floats at all — store integer minor units (cents) or use a decimal library, because rounding errors that accumulate over a ledger are a correctness bug, not a display one. Number.MAX_SAFE_INTEGER (2⁵³−1) is the other half of that answer: beyond it, integers lose precision silently, which is why a 64-bit id from a backend should arrive as a string and why BigInt exists.

The judgement half of the answerKnowing the coercion table is table stakes; the senior line is that you should never need it in production code. Use ===, keep == null as the one deliberate exception, don't rely on truthiness for values where 0 or "" are legitimate (that's what ?? and ?. are for), and let TypeScript or a linter catch the rest. These rules are for reading unfamiliar code and debugging, not for writing new code cleverly.
05 — Drill until reflex

Output prediction drills

Predict the output, then reveal. Say the rule out loud — that's what's scored.

Drill 1 — loop & closure
const fns = [];
for (let i = 0; i < 3; i++) fns.push(() => i);
console.log(fns.map(f => f()));
[0, 1, 2]

let gives each iteration its own binding of i, so each arrow closes over a different value. With var it would be [3, 3, 3].

Drill 2 — who is this?
const o = {
  x: 10,
  get(){ return this.x; },
  getArrow: () => this.x
};
console.log(o.get());
console.log(o.getArrow());
10 · undefined (classic script) — a module throws on the arrow

o.get() uses the implicit rule — this is o — so 10. getArrow is an arrow, so this is lexical, captured from the surrounding scope, not o. In a classic (non-module) script that's the global object, which has no x → undefined; at module top level this is undefined, so this.x would throw. Either way the arrow never sees o.

Drill 3 — detached method
class C { constructor(){ this.v = 42; } val(){ return this.v; } }
const c = new C();
const f = c.val;
console.log(f());
TypeError: Cannot read properties of undefined (reading 'v')

Class bodies are strict mode, so a bare f() has this === undefined. Reading this.v throws. Fix: c.val.bind(c) or a class field arrow val = () => this.v.

Drill 4 — coercion salad
console.log(1 + '2' + 3);
console.log(1 + 2 + '3');
console.log('5' - -'2');
"123" · "33" · 7

+ is left-to-right: 1 + '2' → "12", then "12" + 3 → "123". Second: 1 + 2 → 3 (numbers), then + '3' → "33". Third: -'2' → -2, and '5' - (-2) forces numeric → 7.

Drill 5 — prototype lookup
function A(){}
A.prototype.hi = () => 'A';
const a = new A();
A.prototype.hi = () => 'B';
console.log(a.hi());
"B"

a holds a live link to A.prototype, not a snapshot. Property lookup happens at call time, so reassigning the prototype method is visible to the already-created instance.

Drill 6 — the conceptual one
“What is a closure, and give one real bug and one real use.”

A closure is a function bundled with the lexical scope it was defined in, keeping those variables alive after the outer function returns. Bug: an event handler or effect that closes over a stale value keeps using the old state (the React setInterval counter trap). Use: encapsulating private state — a memoization cache or a module's internals that nothing outside can reach. Both come from the same mechanism: the function remembers its birthplace scope.

Drill 7 — read up, write own
const animal = { legs: 4 };
const dog = Object.create(animal);
dog.legs++;
console.log(dog.legs, animal.legs);
5 4

Reads delegate up the chain; writes always create an own property. dog.legs++ reads 4 from animal, then assigns 5 onto dog, leaving the prototype untouched. The corollary that bites in real code: a primitive on a prototype is safely shadowed like this, but a shared object or array on the prototype is mutated in place by every instance, because you never assigned — you called a method on it.

Drill 8 — the arrow that shouldn't be
const counter = {
  count: 0,
  inc: () => { this.count++; }
};
counter.inc();
console.log(counter.count);
0 — the arrow never touched counter

An arrow has no own this; it captures the enclosing scope at definition time, which here is the module or global scope — not the object literal, since an object literal doesn't create a scope. So this.count++ operates on something else entirely (and in a module, where this is undefined, it throws). The rule: arrows for callbacks inside a method, normal function shorthand for the method itself.

Drill 9 — the closure that leaks
“A dashboard grows to 900MB after an hour of navigation. What would you look for?”

Closures holding environments alive. A listener, timer, or subscription created inside a component's scope keeps a reference to that entire environment — including any large data that was in scope — for as long as the handler is registered, and if teardown never removes it, that's per-mount retention. I'd take two heap snapshots in DevTools with navigation in between and compare retained size, then follow the retainer path to the closure. Fixes: remove listeners and clear intervals on teardown, use AbortController for fetch and listeners, and avoid creating the closure in a scope that holds anything big.

Drill 10 — the money bug
const total = 0.1 + 0.2;
console.log(total === 0.3, total.toFixed(2));
false "0.30"

IEEE-754 doubles can't represent 0.1 or 0.2 exactly, so the sum is 0.30000000000000004 — the same in Python or Java, not a JS quirk. toFixed hides it for display, which is the dangerous part: the error is still in the value and accumulates across a ledger. For money, store integer minor units or use a decimal library; for general float comparison, use a tolerance. And remember the other precision cliff — past Number.MAX_SAFE_INTEGER (2⁵³−1) integers lose precision silently, which is why 64-bit ids should arrive as strings.
