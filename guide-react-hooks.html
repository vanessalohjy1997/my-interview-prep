Frontend interview prep

Hooks are about synchronizing, not lifecycle.

The senior-level hook questions aren't “what does useState do” — they're about dependency arrays, cleanup, stale closures, and knowing when an effect is the wrong tool entirely.

Effects Refs Derived state Concurrent
00 — The mental shift

From lifecycle to synchronization

Hooks let function components hold state and run side effects. The senior framing: stop thinking “on mount / on update / on unmount” and start thinking “this effect keeps some external system in sync with my current state.” The dependency array is the list of values that, when they change, mean the sync must run again.

Say this“An effect isn't a lifecycle callback — it's a synchronization whose dependencies declare what it depends on. If I list the deps honestly, correctness follows.”

The lifecycle it replaced

You still get asked about class components, partly because plenty of production code still contains them and partly because the mapping is a good test of whether you understand effects. A class component's life had three moments:

class Chart extends React.Component {
  state = { data: null };

  onData = data => this.setState({ data });

  componentDidMount()  { this.sub = subscribe(this.props.id, this.onData); }

  componentDidUpdate(prevProps) {
    if (prevProps.id !== this.props.id) {     // you diff props by hand
      this.sub.close();
      this.sub = subscribe(this.props.id, this.onData);
    }
  }

  componentWillUnmount() { this.sub.close(); }

  render() { return <Canvas data={this.state.data} />; }
}
ClassHooks equivalent
constructor / state =useState or useReducer
componentDidMountuseEffect(fn, [])
componentDidUpdateuseEffect(fn, [deps]) — no manual prevProps comparison
componentWillUnmountthe cleanup function returned from the effect
getDerivedStateFromPropsusually nothing — derive during render, or key the component to reset it
shouldComponentUpdateReact.memo (plus useMemo/useCallback on the props — or, with React Compiler 1.0 enabled, nothing hand-written: the compiler inserts the memoisation)
componentDidCatch / getDerivedStateFromErrorno hook exists — error boundaries are still classes
getSnapshotBeforeUpdateno equivalent. It reads the DOM before React mutates it; useLayoutEffect runs after mutation, so it cannot capture the pre-mutation value

The point of the comparison is not the table, it is what the table shows: in the class version, mount and update are two hand-written code paths that must agree, and the unmount cleanup is a third, far from both. That is why subscription leaks were endemic. One effect with honest dependencies collapses all three into a single description of “what this component synchronizes with, and how to stop”.

The two things hooks still cannot do1) Catch render errors. componentDidCatch and getDerivedStateFromError are class-only, so every error boundary in a hooks codebase is either a small class component or a library wrapping one, such as react-error-boundary. 2) Read the DOM before a mutation. getSnapshotBeforeUpdate — capturing something like scrollHeight that the upcoming commit will destroy — has no hook equivalent either. React's docs say so outright. It is rare, but naming it is a strong answer.
01 — The most-probed hook

useEffect

useEffect is for synchronizing with systems outside React — subscriptions, timers, network, non-React DOM. It is not a general “run some code after render” slot.

Dependencies & cleanup

  • List every reactive value the effect reads (props, state, derived values). The exhaustive-deps lint rule enforces this. [] means “nothing reactive to re-sync on” — valid only if the effect truly reads no reactive value. It does not mean “runs once”: in development StrictMode runs setup → cleanup → setup on mount — one extra development-only cleanup+setup cycle, a stress test that your cleanup really undoes your setup. Since 19.3 it does this during hydration too, not only on client-rendered roots.
  • Return a cleanup function. It runs before the effect re-runs and on unmount — unsubscribe, clear timers, abort in-flight requests. Without it you leak subscriptions and get overlapping work.

The stale-closure trap

useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);              // count is captured once — stuck at 0+1

With [], the interval callback closes over count from the first render forever, so it always computes 0 + 1. Fixes: use the functional update setCount(c => c + 1) (no dependency on count), or add count to deps (re-creates the interval), or — since React 19.2 (October 2025), when it left experimental — move the non-reactive part into a useEffectEvent, which always sees the latest props/state and is deliberately kept out of the deps.

useEffectEvent has rules of its ownDeclare it at the top level like any hook, but call it only from inside an effect (or another effect event) — never during render, never from an event handler, never passed down to a child. Its identity deliberately changes every render, so the linter refuses it in a dependency array. And it is not a way to hide a dependency you actually want to react to: useEffectEvent(() => log(url)) called from an effect with [] deps silently stops logging on URL changes. The test is “should a change in this value re-run the effect?” — if yes, it is a dependency; if no, it is an effect event.
When NOT to use an effectDon't use effects for: derived state (compute it during render — const full = first + ' ' + last, not an effect + state); transforming data for display; resetting state when a prop changes (give the component a key instead); or logic that belongs in an event handler (do it in the handler, not by watching state with an effect). Effects that only sync React state to other React state are usually a smell.

Why an effect-for-derived-state is actually wrong, not just inelegant

Worth being able to show rather than assert, because “you don't need an effect” sounds like taste until you demonstrate the bug:

// the anti-pattern
const [items, setItems] = useState([]);
const [visible, setVisible] = useState([]);
useEffect(() => { setVisible(items.filter(i => i.active)); }, [items]);
// render 1: items=[…], visible=[] ← the user sees an empty list for one frame
// effect runs → setState → render 2: visible correct

// the fix — one source of truth, no extra render, no stale window
const visible = items.filter(i => i.active);

Three concrete costs, in order of severity. It renders twice, and the first render shows a value that is one step behind — visible as a flash on first load and after every change. It creates a second source of truth, so any code path that sets items without the effect running (or that sets visible directly) puts them out of sync permanently. And it invites loops: an effect that sets state which is also in its own dependency array re-runs whenever the new value isn't Object.is-equal to the old — guaranteed for a fresh object or array, intermittent for a primitive that sometimes changes. The intermittent version is the worse one, because it passes review.

The general rule to state: if you can compute it during render, compute it during render. Reach for useMemo only if the Profiler shows the computation is genuinely expensive — memoising a filter over 20 items costs more than it saves.

React Compiler changes the memoisation answerReact Compiler 1.0 shipped in October 2025 and memoises automatically — at build time it tracks which values a component reads and caches JSX, values and callbacks by those inputs, which is what hand-written useMemo/useCallback/memo were for. The docs’ guidance: in new code rely on the compiler and keep manual useMemo/useCallback only where you need precise control, typically a value used as an effect dependency; in existing code, leave memoisation in place, because removing it changes the compiler’s output. Without the compiler the old rule stands: useMemo only pays when the calculation is slow, the value feeds a memo-wrapped child, or it is a hook dependency. Either way the compiler does nothing for a component that mutates during render — it bails out of compiling it, so the rules-of-React lint rules matter more, not less.

When an effect actually runs — layout, passive, paint

The follow-up to any “effects run after render” answer is “after what, exactly?” React commits in phases, and each effect type hangs off a different one:

// one commit, in order
useInsertionEffect   // before layout effects; refs not attached; no setState allowed. CSS-in-JS only
DOM mutations        // React applies the diff
useLayoutEffect      // synchronously, DOM updated, browser has NOT painted — measure here
// ---- browser paints ----
useEffect            // "passive": scheduled after paint, usually
  • useLayoutEffect runs after the DOM is mutated and before the browser repaints, so a measurement plus a setState inside it re-renders synchronously and the user never sees the intermediate frame. That is also its cost: everything in it, and every re-render it triggers, blocks paint. Use it for a tooltip position or a scroll restoration, not by default.
  • useEffect is usually flushed after paint. Two exceptions worth naming. Since React 18, if the render was caused by a discrete input (a click, a keydown), React flushes the resulting passive effects synchronously, before the browser paints, so the event system can observe their result. And React always flushes any still-pending passive effects before starting the next render — so an effect from render N is guaranteed to have run before render N+1 begins, even if the browser never got its idle slot.
  • Cleanup order: on an update React runs every cleanup of the affected effects first, then every setup — except useInsertionEffect, which interleaves cleanup and setup per component.
  • On the server none of them run. Server rendering produces HTML with no commit, so no effect of any kind fires. React 18 additionally warned “useLayoutEffect does nothing on the server”; React 19 removed that warning, so a layout effect in SSR code is now simply inert. The real problem remains: layout-dependent output has to be recomputed on the client, so render a placeholder on the server or opt the component out of SSR with React 19.3’s use(browser()).
Say this“Layout effects run synchronously between DOM mutation and paint, so they can measure and correct without a flash but they block the frame. Passive effects are deferred past paint, except that React flushes them synchronously after discrete input and always before the next render.”

The decision tree for “do I need an effect here?”

You want to…Use
Compute something from props/stateNothing — derive it during render
Do something in response to a user actionThe event handler. Effects are for things that happen because the component is on screen, handlers for things that happen because the user did something
Reset state when a prop changesA key on the component
Adjust some state when a prop changesSet it during render (React re-runs immediately, before paint), or restructure to avoid it
Subscribe to an external storeuseSyncExternalStore, not an effect
Fetch dataA framework loader or query library. A raw effect works but you own the race, cleanup, dedupe, caching and retry
Genuinely synchronise with an external systemuseEffect — a WebSocket, a timer, a non-React widget, an analytics SDK

That last row is the honest scope of the hook, and saying it explicitly — “most of my components have no effects at all” — is a stronger signal than being able to recite the dependency rules.

02 — Escape hatch

useRef — mutable value vs DOM handle

useRef returns a stable { current } box. Two uses:

  • Mutable value that doesn't trigger re-render — a timer id, a previous value, the latest state for a callback. Writing ref.current = x never re-renders.
  • DOM handle — <input ref={inputRef} />, then inputRef.current.focus().

The indeterminate checkbox

const ref = useRef(null);
useEffect(() => { ref.current.indeterminate = mixed; }, [mixed]);
return <input type="checkbox" ref={ref} checked={allChecked} onChange={onToggle} />;

indeterminate is a DOM property with no HTML/JSX attribute — you can't set it declaratively. So you set it imperatively via a ref in an effect. This is the canonical “why would you reach for a ref” example (and it pairs with the checkbox-tree state design below).

Callback refs

A ref can also be a function. React calls it with the node on attach and with null on detach, which is how you measure or observe a node the moment it exists:

// React 19: return a cleanup, exactly like an effect
const observe = useCallback(node => {
  const ro = new ResizeObserver(...); ro.observe(node);
  return () => ro.disconnect();
}, []);
return <div ref={observe} />;

Before React 19 the callback returned nothing and you handled teardown by checking for the null call React made on detach. React 19 lets a callback ref return a cleanup function instead — and when you return one, React no longer calls the ref with null, so a leftover if (!node) return guard becomes dead code. The docs describe the null call for refs that return nothing as a backwards-compatibility behaviour that will be removed in a future version, so treat the cleanup form as the target. StrictMode runs the callback’s setup → cleanup → setup in development, exactly as it does for effects. Note the inline-arrow trap: a callback ref defined inline is a new function every render, so React detaches and reattaches it each time — wrap it in useCallback.

Forwarding a ref to a child

Refs are not props in the ordinary sense, so historically a function component could not receive one — it had to be wrapped:

// React 18 and earlier
const Input = forwardRef(function Input(props, ref) {
  return <input ref={ref} {...props} />;
});

// React 19 — ref is just a prop
function Input({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}

In React 19 ref is passed to function components like any other prop, and forwardRef is on its way out: the reference page carries a banner saying it “will be deprecated in a future release”, but as of 19.3 (September 2026) it still works with no runtime warning, and there is a codemod for the migration. Two nuances: ref is only a prop on function components — a ref on a class component still points at the instance — and it is not in props for anything below 19. Knowing both forms, and that forwardRef still exists for older code, is the expected answer.

useImperativeHandle

Occasionally a parent legitimately needs to do something to a child rather than describe it: focus an input, scroll a list, play a video. useImperativeHandle lets the child expose a deliberately narrow API instead of its raw DOM node:

function Field({ ref, ...props }) {
  const input = useRef(null);
  useImperativeHandle(ref, () => ({
    focus: () => input.current.focus(),
    clear: () => { input.current.value = ''; },
  }), []);
  return <input ref={input} {...props} />;
}
Use it rarely, and say whyEvery imperative handle is an escape from the declarative model, so reach for it only when the action genuinely has no state representation — focus, scroll position, media playback. “Open the modal” is state and belongs in props; “focus this field now” is an event and does not.
03 — Structured state

useReducer vs useState

Both hold state; the difference is how transitions are expressed.

  • useState — simple, independent values. A boolean, a string, a small object.
  • useReducer — when the next state depends on the previous in non-trivial ways, when several sub-values change together, or when transitions are worth naming as actions. It centralizes logic into a pure (state, action) => state function that's easy to test, and dispatch has a stable identity so it's safe in effect deps.
Rule of thumbReach for a reducer when you find yourself calling several setStates together, or when a bug is “the state got into an impossible combination.” A reducer makes the legal transitions explicit.

What a reducer actually buys, beyond tidiness

// four booleans: 16 combinations, ~4 of them meaningful
const [isLoading, setLoading]   = useState(false);
const [error, setError]         = useState(null);
const [data, setData]           = useState(null);
const [isRefetching, setRefetch]= useState(false);
// nothing prevents isLoading && error && data all being truthy at once

// one reducer: the transitions ARE the API, and illegal ones don't exist
function reducer(state, action){
  switch (action.type) {
    case 'fetch':   return { status: 'loading' };
    case 'success': return { status: 'ready',  data: action.data };
    case 'failure': return { status: 'error',  error: action.error };
    case 'refetch': return { ...state, refetching: true };
  }
}

Three specific wins to name. Impossible states become unrepresentable — there is no path that produces loading-and-error simultaneously, because you'd have to write it. The logic is testable without React: a reducer is a pure function, so a state-machine test is three lines and no renderer. And dispatch is referentially stable for the component's lifetime, so it can go in a dependency array or be passed through context without breaking memoisation — which is exactly why the state/dispatch context split works.

The counter-case, so it isn't a blanket recommendation: a reducer moves the logic away from the call site, so for a single boolean it's pure indirection. The trigger is several values that change together or transitions worth naming — not state complexity in the abstract.

useState mechanics the follow-ups probe

Both hooks share one update queue implementation, so these apply to dispatch as much as to a setter.

  • The lazy initialiser. useState(expensive()) calls expensive() on every render and throws the result away after the first. useState(expensive) or useState(() => expensive()) calls it once, when the component mounts. In StrictMode development it is called twice (the second result is discarded), the same as reducers, updater functions and useMemo callbacks — all of which must therefore be pure.
  • A setter does not change the running code’s value. setName('Robin'); console.log(name) logs the old name: state is a snapshot of the render, and the set only affects what the next render’s useState returns.
  • Updates are queued, and updater functions see the queue. Three calls of setN(n + 1) in one handler give 1, because all three read the same snapshot; three calls of setN(n => n + 1) give 3, because each updater receives the previous updater’s result. That is why the functional form fixes the stale-closure interval.
  • Batching. React renders once after the whole event handler has run, not once per set. Before 18 that was only true inside React event handlers; React 18’s automatic batching extends it to setTimeout, promises, native listeners and anywhere else. It does not batch across separate discrete events — two clicks are two renders, so a first click that disables a form is committed before the second is handled. flushSync from react-dom opts out for one callback, forcing a synchronous DOM update (a beforeprint handler, a third-party API that needs the DOM now); it is expensive and can force Suspense fallbacks, so it is a last resort.
  • The Object.is bailout, and its nuance. Setting state to a value Object.is-equal to the current one skips the re-render of the component and its children — which is why mutating an object in place and setting it back does nothing. The nuance the docs flag: “in some cases React may still need to call your component before skipping the children.” Concretely, the eager bail-out only happens when the fiber has no pending work; the first same-value set after a real update renders the component once more and bails out below it, and the next one skips entirely. So a console.log in the body firing once on a no-op set is not a bug.
// React 19.3, verified: a same-value set after a real update renders once more, then bails
set(1)  → render 1, child        // real update
set(1)  → render 1               // component runs, children skipped
set(1)  → (nothing)              // eager bail-out
04 — Reuse & invariants

Custom hooks & the rules of hooks

Custom hooks (useSomething) extract reusable stateful logic. Key point: they share logic, not state — each call site gets its own independent state. useToggle, useDebouncedValue, useFetch are all just functions that call other hooks.

The rules of hooks

  • Only call hooks at the top level — never inside conditions, loops, or nested functions.
  • Only call hooks from React functions — components or other hooks.

Why order matters: React associates each hook's state with the order it's called in, not a name. On every render the hooks must run in the same sequence so the 1st useState maps to the same slot. A conditional hook shifts the sequence and React reads the wrong slot — hence the rule.

The actual data structure is worth getting right, because “an array” is the common simplification and a strong interviewer knows it. Each component instance is a fiber, and fiber.memoizedState points at the first of a singly linked list of hook objects — { memoizedState, baseState, baseQueue, queue, next }. During render React keeps a cursor (currentHook on the committed list, workInProgressHook on the one being built) and every hook call advances it one next. There is no index and no name; a hook is “the node the cursor is on when this call happens”.

// what React is doing, in miniature
fiber.memoizedState → {state:'Ada'} → {state:0} → {deps:[id]} → null   // per instance
cursor = fiber.memoizedState;  useState() → node = cursor; cursor = cursor.next
                               // position in the list IS the identity

// render 1: cond is true
if (cond) useState('a');   // slot 0
useState(0);               // slot 1
useEffect(fn, [x]);        // slot 2

// render 2: cond is false — everything shifts up one
useState(0);               // reads slot 0 → gets 'a'
useEffect(fn, [x]);        // reads slot 1 → compares deps against a number
// In this exact shape React catches it: the cursor still has a `next` after the
// last call, so it throws "Rendered fewer hooks than expected. This may be caused
// by an accidental early return statement." Add one instead and the cursor runs off
// the end: "Rendered more hooks than during the previous render." The silent,
// dangerous case is when the count stays the same and two same-type hooks swap.

Why an array and not names? Because names would have to come from somewhere — a string key per hook — and that's both more to type and impossible to keep unique in a custom hook called twice. Positional identity makes hooks composable for free: useToggle() called three times in one component gets three independent slots without anyone coordinating names. The rule is the price of that composability, and framing it that way is a much better answer than “because React uses an array”.

It also explains why the lint rule matters so much: this failure mode is silent. React catches a changed hook count and throws, and in development it also records each hook’s type per position and warns “React has detected a change in the order of Hooks called by X” with a previous-vs-next table when a useState position becomes a useEffect. But that check is development-only, and two hooks of the same type swapping order pass it — a useState('') that now reads the other useState(0)’s node just gets a number and carries on. Production has neither check.

What a custom hook is, and what it isn't

A custom hook is a plain function that happens to call hooks. There is no registration, no special runtime — the use prefix exists purely so the linter knows to apply the rules to it. Two consequences worth stating:

  • They share logic, never state. Two components calling useCounter() get two independent counters, because the hooks inside run against each component's own slot array. If you want shared state, that's context or a store — and this misunderstanding is a common interview trip-up.
  • They still count toward the caller's hook order. So a conditional call to a custom hook is exactly as broken as a conditional useState, and an if inside a custom hook that skips a hook call is the same bug hidden one level down.
05 — The highest-leverage skill

State design

  • Derived vs stored: never store what you can compute. If a value is a function of existing state/props, derive it during render. Storing it creates two sources of truth that drift.
  • Single source of truth: pick one canonical place for each piece of state; everything else derives from it.
  • Lift state up to the closest common ancestor of the components that need it — but no higher.
  • Colocation: keep state as close as possible to where it's used; only lift when sharing forces it. Over-lifting causes wide re-renders and prop drilling.
The checkbox-tree instinctFor a parent/child checkbox tree, store only the leaf checked-set, and derive each parent's checked/indeterminate state from its descendants. One source of truth, no sync bugs — the parent state can never disagree with its children because it isn't stored, it's computed.
06 — Concurrent features

useDeferredValue & useTransition

These mark work as non-urgent so React can keep the UI responsive by rendering the urgent update first and the expensive one at low priority (interruptibly).

  • useTransition gives you [isPending, startTransition]; wrap the state update that triggers expensive rendering in startTransition.
  • useDeferredValue takes a value and returns a lagging copy that updates at low priority — handy when you don't own the state setter. React 19 added an optional second argument, useDeferredValue(value, initialValue), so the very first render can show a cheap placeholder instead of the expensive value.
Why not just debounce?Debouncing delays work by a fixed timer — you guess the delay, and when it fires it still blocks. A transition doesn't delay: it renders the urgent update (the keystroke) immediately and lets the expensive render (the big filtered list) be interruptible and lower priority, so typing never janks. You still debounce to rate-limit a network request — the two solve different problems and often combine.

How interruption actually works

The mechanism is worth a sentence because it's what makes the feature more than a scheduling trick. React tags each update with a lane (a priority). A transition update renders in a low-priority lane, and because the render phase builds a work-in-progress tree separately from the one on screen, React can abandon a partially-built tree when a higher-priority update arrives — nothing was committed, so nothing visible is wrong. It then restarts the low-priority work from the new state. That's why typing stays smooth: each keystroke is urgent, renders immediately, and throws away the half-finished expensive render behind it.

Two practical notes. The abandoned work is wasted, so transitions trade CPU for responsiveness — on a very slow device a heavily interrupted render can keep restarting for a while. It cannot starve forever, though: each lane has an expiry (transitionLaneExpirationMs = 5000 in the reconciler), and once a transition has waited that long React marks it expired and finishes it synchronously, jank and all. So the honest description is “interruptible for up to about five seconds, then forced”. And the pending flag is what you actually use in the UI: useTransition hands you isPending directly, while with useDeferredValue you derive it by comparing the current value to the deferred one. Either way, dim the stale list rather than replacing it with a spinner — keeping the old content visible is the point.

Deferred value vs transition — how to chooseSame engine, different ergonomics. Use useTransition when you own the setter and can wrap the update. Use useDeferredValue when you only receive the value — a prop, a context, a library's state — and want a lagging copy to feed the expensive part. The classic pairing is a controlled input where value is urgent and useDeferredValue(value) drives the heavy list. And neither replaces debouncing a network call: transitions manage rendering priority, debouncing manages request volume.
Three transition traps that get asked1) A controlled text input cannot be a transition. Its value must update synchronously with the keystroke, so keep the input state urgent and derive the deferred copy — that is exactly the useDeferredValue pairing above. 2) After an await, you are out of the transition. React 19 lets startTransition take an async function (that is what an Action is), and isPending stays true until it settles, but state set after an await is not marked as a transition unless you wrap it in another startTransition — a documented limitation. 3) Transitions used to entangle. Up to 19.2, several in-flight transitions were rendered together, so one slow one held up the rest; 19.3 (September 2026) renders them independently. If you describe transitions as “all batched into one render”, you are describing the old behaviour.
07 — The current API surface

React 19 — Actions, use(), and the new hooks

React 19 is largely one idea followed to its conclusion: the async mutation — pending state, error handling, optimistic UI, and reset — is boilerplate everyone rewrites, so React should own it. That machinery is called an Action.

Actions and useActionState

function Profile({ user }) {
  const [state, formAction, isPending] = useActionState(
    async (prev, formData) => {
      try { await updateName(formData.get('name')); return { ok: true }; }
      catch (e) { return { error: e.message }; }      // error becomes state
    },
    { ok: false }
  );
  return (
    <form action={formAction}>
      <input name="name" defaultValue={user.name} />
      <button disabled={isPending}>{isPending ? 'Saving…' : 'Save'}</button>
      {state.error && <p role="alert">{state.error}</p>}
    </form>
  );
}

Passing a function to <form action> makes React manage the submission: it runs inside a transition, so isPending is handled for you, and uncontrolled fields reset once it succeeds. The same signature works as a Server Action — move the function into a server module and add 'use server', and the component code is unchanged.

APIWhat it gives you
useActionState[state, action, isPending] — the result of the last run, the wrapped action, and its pending flag. Renamed from the experimental useFormState.
useFormStatusImported from react-dom. Reads the pending state of the nearest parent form from inside a descendant — so a shared <SubmitButton> needs no props.
useOptimisticShows an optimistic value while an action is in flight. React discards it when the action settles — so a failure reverts, and a success must have updated the real state by then.
useReads a promise or a context during render. Unlike every other hook it may be called conditionally, including inside a branch or a loop.
const [optimistic, addOptimistic] = useOptimistic(messages,
  (current, draft) => [...current, { ...draft, sending: true }]);

// passed to <form action={send}> — addOptimistic must run inside an action
// or a transition, or React warns and the update is not optimistic
async function send(formData) {
  addOptimistic({ text: formData.get('text') });   // paint immediately
  await postMessage(formData);
}                          // discarded when the action settles — by then
                           // the real state must have caught up, or it snaps back

use()

use(promise) suspends the component until the promise resolves, handing the value back — the nearest <Suspense> shows the fallback and the nearest error boundary catches a rejection. use(SomeContext) reads context and, because it is exempt from the rules of hooks, can do so inside a condition.

Two things to know about use()Do not create the promise during render. A promise made in the component body is a new promise every render, so the component suspends forever; it must come from somewhere stable — a Server Component passing it down, a cache, or a data library. And it cannot be called inside try/catch — wrap the component in an error boundary instead. Both are standard follow-up questions.

The rest of what changed

  • ref is an ordinary prop on function components; forwardRef is no longer required, and callback refs may return a cleanup function.
  • <Context> can be rendered directly as the provider — <Context.Provider> is no longer needed.
  • <title>, <meta> and <link> rendered anywhere in the tree are hoisted into <head>, which removes the need for a helmet library.
  • Resource hints ship as APIs: preload, preinit, preconnect, prefetchDNS from react-dom.
  • Hydration mismatch errors now show a diff of the server and client output instead of a generic warning.
  • Server Components and Server Functions are stable for frameworks to build on. Naming matters: since September 2024 a 'use server' function is a Server Function, and it is a Server Action only when it is passed to an action prop or called from inside an action.
  • Removed: propTypes and defaultProps on function components (use default parameters; classes keep defaultProps), legacy context, string refs, createFactory, findDOMNode, react-dom/test-utils (act moved to react), and the legacy ReactDOM.render/hydrate/unmountComponentAtNode (deprecated in 18, removed in 19) — createRoot and hydrateRoot are the only roots left.

Say the version you mean; “React 19” has spanned almost two years of releases.

Two React 18 hooks that still get asked

Both predate React 19 — worth being precise about, because misattributing them is an easy own goal.

  • useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot) — the correct way to read from an external store (a Redux-like store, matchMedia, navigator.onLine). It guarantees the value is consistent across a concurrent render, which a naive useEffect-plus-useState subscription cannot — that pattern can tear, showing two different values in one paint. How it guarantees it is the follow-up: if the store changes during a non-blocking transition render, React de-opts that update to a blocking one and calls getSnapshot again just before committing, so every subscriber sees the same version. Three rules fall out of that. getSnapshot must return a cached, immutable value — a fresh object each call fails the Object.is check every time and React throws “The result of getSnapshot should be cached to avoid an infinite loop”. subscribe should be declared outside the component, or React re-subscribes every render. And getServerSnapshot is required for any component that renders on the server — omit it and the server render throws.
  • useId() — generates an identifier stable across server and client renders, for wiring htmlFor and aria-describedby. It is not for list keys — keys come from your data. The old “not for CSS selectors” advice is stale: the format was :r0: in 18 and 19.0 (the colons were chosen precisely to be invalid in selectors), «r0» in 19.1 (March 2025), and _r_0_ since 19.2, changed so the ids are valid view-transition-names and XML names. Never build on the format anyway — supply a prefix via identifierPrefix on the root if two React apps share a page.
08 — Drill until reflex

Scenario drills

Drill 1 — the frozen counter
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);
Counter sticks at 1

The interval closes over count from the first render (deps []), so it always computes 0+1. Fix with the functional update setCount(c => c+1), or add count to deps, or read the latest value from a ref.

Drill 2 — effect or not?
“I have firstName and lastName state and want fullName. Should I keep fullName in state and update it in a useEffect?”

No. fullName is derived — compute it during render: const fullName = firstName + ' ' + lastName. Storing it plus an effect creates a second source of truth that lags by one render and can drift. Derive, don't duplicate.

Drill 3 — why does this crash?
function C({ showName }){
  if (showName) { const [n] = useState(''); }
  const [x, setX] = useState(0);
}
Breaks the rules of hooks — hook order changes

The conditional useState changes the number of hooks between renders, so React can't line the call sequence up with its stored linked list. Which error you get depends on the direction: when showName flips true → false the cursor stops with a node left over and React throws “Rendered fewer hooks than expected. This may be caused by an accidental early return statement.”; false → true runs the cursor off the end and throws “Rendered more hooks than during the previous render.” In development it also logs a previous-vs-next table of hook types first. Hooks must be called unconditionally at the top level; move the condition inside or split components.

Drill 4 — reset on prop change
“When the selected userId prop changes, I want the edit form to reset. Effect that setStates the fields?”

Prefer giving the form a key={userId} — changing the key remounts it with fresh state, no effect needed. Effects that copy props into state and reset them are fragile (extra renders, easy to desync). Reserve the effect approach for partial resets.

Drill 5 — deferred vs debounce
“A search box filters a 10k-row list on every keystroke and janks. useDeferredValue or debounce?”

For the rendering jank, useDeferredValue on the query: the input updates instantly (urgent) while the heavy filtered list re-renders at low priority and stays interruptible — no guessed delay. The list must be wrapped in memo, though: without it the urgent re-render re-renders the list anyway and the deferral buys nothing. If you're also hitting an API per keystroke, debounce that request to rate-limit the network. They address different costs and combine well.

Drill 6 — the effect that shouldn't exist
const [items, setItems] = useState([]);
const [visible, setVisible] = useState([]);
useEffect(() => {
  setVisible(items.filter(i => i.active));
}, [items]);
Delete both the effect and the state — derive during render

This renders twice for every change and the first render shows the previous value, so the user sees a stale or empty list for a frame. It also creates a second source of truth that any code path setting items differently can desynchronise permanently. The whole thing is const visible = items.filter(i => i.active). I'd only add useMemo if the Profiler showed the computation mattered — memoising a filter over twenty items costs more than it saves.

Drill 7 — why the rule exists
“Why can't you call a hook inside an if? Explain what React would actually do.”

React stores each instance's hook state as a linked list hanging off the fiber's memoizedState, and identifies hooks by call order, not by name — a cursor that advances one node on each hook call during render. Skip a hook on a later render and everything after it shifts up one node, so a useState reads the previous hook's state and a useEffect compares its dependencies against unrelated values. It's silent when two hooks of the same type swap, which is why the lint rule matters. The reason for positional identity rather than names is composability: a custom hook called twice in one component needs two independent sets of slots without anyone coordinating keys.

Drill 8 — the shared hook that isn't shared
“Two components both call useCart(). One adds an item; the other doesn't update. Why?”
Custom hooks share logic, not state

A custom hook is just a function that calls hooks, so each call site runs those hooks against its own component's slot array — two completely independent pieces of state. Nothing is shared but the code. For shared state the value has to live somewhere both components read from: context (fine for infrequent changes), a store with selectors (better when it changes often or the tree is large), or a query cache if it's really server data. This misunderstanding is common precisely because the hook looks like a singleton.

Drill 9 — transition or debounce?
“A search box filters a 5,000-row table client-side and hits an API. Where do transitions go, and where does debouncing?”

They solve different problems and I'd use both. Rendering: the keystroke is urgent, the table render is not — so useDeferredValue(query) feeds the table while the input updates immediately, and React can abandon a half-built table render when the next character arrives. To dim the stale rows I'd compare query !== deferredQuery, which is the useDeferredValue equivalent of a pending flag — isPending itself only comes from useTransition. Dimming beats swapping in a spinner, since keeping old content visible is the whole point. Network: debounce ~250–300ms so I make one request per pause instead of one per character — that's about request volume, which a transition does nothing for. The trade to acknowledge is that interrupted renders are wasted work, so on a very slow device the table may keep restarting — though not indefinitely, because React expires a starved transition after about five seconds and forces it through synchronously.
