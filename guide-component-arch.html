00 — What we're optimising for

Components as reuse boundaries

Component architecture is the discipline of deciding what becomes a component, how components talk, and where a reusable boundary should sit. The goals are composability, testability, and controlled coupling — not maximum reuse for its own sake.

The guiding tensionEvery abstraction you add buys reuse and costs indirection. Senior judgement is knowing when the reuse is worth the indirection — and when it isn't yet.
01 — The React way

Composition over inheritance

React has no component inheritance. You reuse and specialise by composing: passing children, passing elements as props (“slots”), and wrapping.

function Card({ header, children, footer }){
  return (
    <section className="card">
      {header && <header>{header}</header>}
      <div className="body">{children}</div>
      {footer && <footer>{footer}</footer>}
    </section>
  );
}

Instead of subclassing a base card, callers compose content into named holes. This scales without an inheritance hierarchy and keeps each piece independently testable.

02 — The reuse toolbox

Patterns for sharing

  • Compound components — a set that shares implicit state via Context so the consumer writes declarative markup: <Tabs><Tab/><Tab/></Tabs>. The parent holds the active index; children read it from context.
  • Render props / children-as-a-function — a component owns behaviour and hands data back: <Motion>{v => <Box x={v}/>}</Motion>.
  • Higher-order components — a function wrapping a component. Largely legacy: prone to wrapper-hell and prop collisions.
  • Custom hooks — the modern primitive for sharing stateful logic. Render props/compound components share structure; hooks share behaviour without touching the tree.
// compound components via context
const TabsCtx = createContext(null);
function Tabs({ children }){
  const [active, setActive] = useState(0);
  const value = useMemo(() => ({ active, setActive }), [active]); // stable value — see §04
  return <TabsCtx.Provider value={value}>{children}</TabsCtx.Provider>;
}
function Tab({ index, children }){
  const { active, setActive } = useContext(TabsCtx);
  return <button role="tab" aria-selected={active === index} onClick={() => setActive(index)}>{children}</button>;
}
03 — One-off or reusable?

Where to draw the boundary

  • Rule of three — abstract on the third real occurrence, not the first. Two similar things are often coincidence.
  • Prop explosion is a smell — if making something reusable needs a dozen boolean/variant props, the abstraction is fighting its use cases. Consider composition (slots) instead of configuration.
  • Coupling — a “reusable” component that reaches into a specific store, route, or API isn't reusable. Keep leaf/presentational components dumb; inject data via props.
Say this“Prefer duplication over the wrong abstraction.” Premature abstraction couples unrelated features together, and un-picking a bad shared component is far more expensive than copying a bit of markup.
04 — The hidden re-render cost

Prop drilling vs Context

Prop drilling (threading a prop through many layers) is tedious but explicit — though every layer in the chain re-renders too. Context removes the threading — but has a cost interviewers love: when a provider's value changes, every consumer re-renders, even those that only use part of it, and even if their slice didn't change.

Mitigations:

  • Split contexts by concern (e.g. separate a rarely-changing theme from fast-changing state), so a change wakes only the relevant consumers.
  • Separate state and dispatch into two contexts — components that only dispatch don't re-render on state changes.
  • Memoize the provider value so an unrelated parent re-render doesn't hand consumers a new object — though when the data itself changes, they all still re-render.
  • For high-frequency or selective reads, reach for a store with selectors (Redux, Zustand) that only re-render subscribers whose selected slice changed.
When to reach for a state libraryContext is a dependency-injection mechanism, not a performance-optimised store. When many components read overlapping slices of frequently-changing global state, a selector-based store scales better than one big context.
05 — When Context is the wrong tool

Redux & client state libraries

Context solves distribution — getting a value to a deep consumer without threading props. It does not solve subscription: every consumer re-renders whenever the context value changes, whether or not it cares about the part that changed. A store library solves the second problem.

The Redux model, in four rules

  • All shared state lives in one store, a single serialisable object tree.
  • State is read-only. The only way to change it is to dispatch an action — a plain object describing what happened, not what to set.
  • Changes are computed by pure reducers: (state, action) => newState, returning a new object rather than mutating.
  • Components select the slice they need, and re-render only when that slice changes.

Immutability is not stylistic. Reference comparison is what makes selector-level subscriptions cheap, what makes React.memo work, and what makes time-travel debugging possible at all — every past state still exists because nothing was overwritten.

Redux Toolkit is the answer to “isn't Redux a lot of boilerplate?”

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    added(state, action) { state.items.push(action.payload); },  // Immer draft
    removed(state, action) {
      state.items = state.items.filter(i => i.id !== action.payload);
    },
  },
});
export const { added, removed } = cartSlice.actions;
const store = configureStore({ reducer: { cart: cartSlice.reducer } });

RTK generates the action types and creators, wires the DevTools and thunk middleware, and uses Immer so you write what looks like mutation against a draft while an immutable update is produced underneath. Hand-written switch statements and ACTION_TYPE constants are legacy Redux, and saying so is part of the modern answer.

Selectors

const total = useSelector(s => s.cart.items.length);          // fine: primitive
const items = useSelector(s => s.cart.items.filter(i => i.active)); // new array every time!

useSelector re-renders when the selected value changes by reference. A selector that builds a new array or object on each call therefore re-renders on every store update. Fix it with createSelector from Reselect, which memoises the derived result, or by selecting primitives and composing in the component. This is the most common real Redux performance bug and a very common interview question.

Two more things worth knowingNormalise collections by id rather than storing nested arrays — createEntityAdapter does this — so an update touches one entity instead of rewriting a list. And do not store derived data: compute it in a selector, or the two representations will drift.

Do you actually need it?

NeedReach for
Server data — fetched, cached, refetchedTanStack Query, RTK Query, SWR — not a hand-rolled store
Local UI stateuseState / useReducer, colocated
A few stable values shared widely (theme, locale, current user)Context
Complex client state, many writers, cross-cutting updatesA store: Redux Toolkit, Zustand, Jotai
Time-travel, replayable actions, offline queues, undo/redoRedux specifically — the action log is the feature

Zustand gives you the same selector-based subscription with far less ceremony and no provider; Jotai models state as atoms rather than a single tree. Redux's distinguishing advantage is the serialisable action log — DevTools, replay, middleware — which is worth real boilerplate only if you use it.

The answer to “Redux or Context?”“They solve different problems. Context distributes a value; it has no subscription granularity, so every consumer re-renders when it changes. A store adds selectors, so only components reading the changed slice re-render. I use Context for stable values, a query library for server state, and a store only when client state is genuinely complex and shared — and in that case Redux Toolkit, because the modern API is small.”
06 — The textbook split

Server state vs UI state

The single most useful architectural distinction in a data-heavy app:

UI / client stateServer state
Examplesmodals, form drafts, toggles, selected tabaccount balances, order history, market data
Owned bythe clientthe backend (you hold a cached copy)
Toolslocal state / Redux / ZustandTanStack Query / RTK Query / SWR
Concernssynchronous, ephemeralcaching, dedup, background refetch, staleness

Server state is asynchronous and owned elsewhere, so it needs caching, request de-duplication, background refetching, and stale-while-revalidate — exactly what a query library gives you. Dumping server data into Redux by hand means re-implementing all of that (loading flags, cache invalidation, refetch) manually and badly.

The sharp answer“I keep UI state in a lightweight client store and server state in TanStack Query. Conflating them — hand-managing fetched data in Redux — recreates caching and invalidation logic the query layer already solves.”
07 — Same React, different renderer

React vs React Native

The framing that answers this cleanly: React is the component model and reconciler; the renderer is pluggable. react-dom renders to the DOM, react-native renders to native platform views. Components, props, state, hooks, context, reconciliation and Suspense are the same library doing the same thing — what changes is what a “host component” is.

React DOMReact Native
Primitivesdiv, span, img, buttonView, Text, Image, Pressable, ScrollView
StylingCSS: cascade, inheritance, selectors, media queriesJS style objects. No cascade, no selectors, no media queries; inheritance exists only inside <Text> subtrees. Flexbox only, with different Yoga defaults — flexDirection: column, flexShrink: 0
Unitspx, rem, %, vhUnitless density-independent numbers; percentages in some places
TextAny element can hold textEvery string must be inside a <Text>

StoragelocalStorage, IndexedDB, cookiesAsyncStorage or MMKV; no cookies by default

ReleaseDeploy and every user has itApp store review; only JS-only changes can ship over the air (Expo/EAS Update — Microsoft's hosted CodePush shut down in March 2025)

How it runs

Your JavaScript executes in an engine on the device — Hermes, these days — on its own thread, separate from the platform's main UI thread. Layout is computed with Yoga, a cross-platform flexbox implementation, which is why the layout system is flexbox and nothing else.

  • The old architecture passed messages between JavaScript and native over an asynchronous bridge, serialising to JSON. That is the source of the classic complaints: janky lists, laggy gestures, an expensive startup.
  • The new architecture replaces it with JSI, which lets JavaScript hold direct references to native objects and call them synchronously, plus Fabric (the new renderer) and TurboModules (lazily-loaded native modules with generated type-safe interfaces).
  • Animations should run on the UI thread, not the JS thread — useNativeDriver: true with the Animated API, or Reanimated worklets. An animation driven from JS stutters as soon as the JS thread is busy. The standard follow-up: useNativeDriver only supports non-layout properties such as transform and opacity, so you cannot native-drive width or height — the same compositor-versus-layout distinction as on the web.

What actually transfers between the two

Say this plainly, because it is the practically useful part: logic ports, UI does not. Hooks, state management, API clients, validation, formatting, and tests around them are shared almost unchanged. Anything touching layout, styling, gestures, or navigation is rewritten. Teams that want more sharing use React Native for Web and a design system built on shared primitives — which works, at the cost of designing to the intersection of both platforms.

Do not say “React Native compiles to native code”It does not. Your JavaScript stays JavaScript, running in an engine on the device; React Native drives real native views rather than a WebView, which is the meaningful distinction from Cordova or Ionic. The components are genuinely native; the code driving them is not.
08 — Drill until reflex

Scenario drills

Drill 1 — the context that re-renders everything
“We put the whole app state in one Context. Now typing in a search box re-renders the entire tree. Why, and what do you change?”

Any change to the provider's value re-renders all consumers. Since everything reads that one context, one keystroke wakes the whole tree. Fixes: split the context by concern, separate fast- from slow-changing state, memoize the value, or move to a selector-based store so only components using the changed slice re-render.

Drill 2 — reusable or not?
“A teammate wants to extract a <Button> that already needs 11 boolean props to cover every screen. Good idea?”

The prop explosion is the tell — the abstraction is fighting its use cases. Prefer composition: a small unstyled base plus slots (icon, label) and a handful of variants, letting callers compose the rest. 11 booleans means 2^11 configurations you now own and must test.

Drill 3 — where does this data live?
“Order-book data from the API and the ‘is the trade panel open’ flag — same store?”

No. The order book is server state — cache it in a query library (dedup, background refetch, staleness). The panel-open flag is ephemeral UI state — local component state or a small UI store. Mixing them means hand-rolling caching for server data in a store that isn't built for it.

Drill 4 — HOC vs hook
“You need to share ‘current user’ logic across many components. HOC or custom hook today?”

A custom hook (useCurrentUser()). It shares logic without adding wrapper layers, avoids prop-name collisions, and keeps the component tree flat. HOCs are legacy for this; render props are for sharing structure, not plain logic.

Drill 5 — the conceptual one
“Why 'composition over inheritance' in React specifically?”

React components are functions of props, not classes in a hierarchy; there's no meaningful 'extend a component.' Composition — children, slots, wrapping, and hooks — lets you specialise behaviour and structure without the fragile-base-class and tight-coupling problems inheritance brings. It's more flexible and matches React's data-flow model.
